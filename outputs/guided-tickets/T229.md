4. Read `src/shared/observability/sentry-client.ts`/`sentry-dsn.ts`: `initSentry()` already does the right thing once a real DSN exists as an env var — no source change needed.
5. Owner ran Sentry's setup wizard in the main checkout, adding the config plugin/`metro.config.js` and a real `SENTRY_AUTH_TOKEN` to `.env.local` (gitignored). Moved the tracked-file changes onto this branch via patch; main checkout restored to clean `development`.
6. Added the exact Sentry ingest origin to `vercel.json`'s `connect-src` and `check-csp-headers.mjs`'s `EXPECTED_DIRECTIVES`; documented in `security/README.md`.
7. Ran full local verification (`verify.mjs` 4/4, `security:check-headers`, `test:e2e:security` 17/17, `jest src/shared/observability` 9/9) and a bundle-secret scan confirming `SENTRY_AUTH_TOKEN` doesn't leak into the client bundle. Committed (`acd0b70`, `6d0fb25`).
8. Owner asked to trigger a real test event. A dev-server uncaught-throw attempt (via my own sandboxed browser tool) produced no visible network activity — traced to that tool's `fetch()` being unable to complete cross-origin preflight requests (confirmed via `curl` succeeding against the same URL where the tool's `fetch()` failed). A raw XHR POST from the same tool succeeded (`200`), isolating the problem to `fetch()` preflight specifically, not general connectivity.
9. Hand-built a valid Sentry envelope and posted it via XHR from the sandboxed tool as a workaround — got a `200` and a real event ID (`d2d62673da6448d991369ab281a69ba0`). This was flagged to the owner as inconclusive proof (ingest accepting an envelope doesn't guarantee it survives Sentry's async validation/indexing) rather than claimed as solid evidence.
10. Owner tried the suggested browser-console throw in their own (real, unsandboxed) browser — still nothing appeared in Sentry. Owner asked directly for a real `Sentry.captureException` call. Added a temporary `Pressable` to the landing page invoking `Sentry.captureException(new Error('First error'))`, clearly commented as diagnostic-only.
11. Owner clicked the button in their real browser; DevTools Network tab confirmed a genuine `200` from the SDK's real transport with a matching event ID. Still nothing in Sentry's Issues view. Owner pointed me at the exact onboarding URL they were viewing — its `project=` query param (`4512057182453760`) didn't match the DSN's project ID (`4512057128583168`): **two different Sentry projects existed**, and every test event had been landing in the one the owner wasn't looking at. Owner checked the original project directly too — genuinely empty despite confirmed `200` acks (unresolved, but moot once verification moved to the correct project).
12. Owner decided to use the second project going forward. Updated `.env.local`'s `EXPO_PUBLIC_SENTRY_DSN` to the new project's DSN (ingest host unchanged — same org — so no CSP change needed). Owner clicked the button again; **this time confirmed visible in the Sentry dashboard**. Delivery is proven.
13. Discovered the wizard's second run (used to get the new project's DSN) had also bumped `@sentry/react-native` to `^8.25.0`, breaking Jest (`@sentry/core`'s ESM build not covered by jest-expo's default `transformIgnorePatterns`, which only allowlists `@sentry/react-native` specifically). Fixed by widening the override to `@sentry/.*`. Full suite green again; committed (`3ffe95c`).
14. Removed the temporary test button and its `Sentry`/`Pressable` imports from `landing-page.tsx` now that delivery is confirmed — it was always meant to come out before merge, per T218/T229's "no manual `captureException` in shipped code" boundary. Reran `verify.mjs` (4/4 pass) to confirm the revert is clean.
15. Re-ran the bundle-secret scan and hit an apparent regression (1 leak found) — investigated and found it was **unrelated to Sentry**: the pre-existing local Supabase CLI demo anon key (`localhost:54321`, a fixed, publicly-known value used only for local `supabase start` dev) isn't allowlisted in `.gitleaks.toml` by its literal value (only a placeholder string is), and a stale Metro cache was serving a build with that key baked in regardless of which `.env.local` block was active. `--clear` forced a real rebuild, and a clean scan against the **hosted** Supabase pair (what actually deploys) came back with zero leaks — confirming `SENTRY_AUTH_TOKEN` genuinely never leaks. Filed the unrelated gitleaks-allowlist gap as a separate suggested task (`task_e73babc8`) rather than fixing it here.
16. `.env.local` restored to the local Supabase pair for normal dev use afterward.
