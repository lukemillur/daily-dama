- **What's stored server-side, and its deletion behavior on account deletion** (`auth.admin.deleteUser` in `supabase/functions/delete-account/handler.js`, cascade confirmed in migrations):
  - Profile, custom tricks/sequences, practice history, goals, notes — all have `user_id references auth.users(id) on delete cascade`. These are permanently deleted with the account. (One exception: a practice-session FK from notes uses `on delete set null`, not cascade — irrelevant here since the parent user row cascades first.)
  - `api.feedback` — **no** `user_id`/FK column at all; free-text name/email are optional, unverified, submitter-supplied contact info, not an identity link. Feedback rows are **not** deleted when an account is deleted, and can't be matched to an account to delete selectively.
  - Auth account itself (email, password hash, session) — deleted via `deleteUser`.
- **Guest (no account) storage:** local-only (AsyncStorage → browser `localStorage`), per `AGENTS.md`'s five persistent domains. Nothing guest-side reaches Supabase until/unless the user signs up and the guest-import path runs.
- **Third-party services receiving data:**
  - Supabase (Postgres + Auth + Edge Functions) — account data, as above.
  - Resend — transactional Auth email (confirmation, password reset, email change) via Supabase's SMTP integration. No evidence email content is retained by the app beyond delivery.
  - Sentry (project `daily-dama`, org `luke-miller-technologies`) — automatic error capture only (no tracing/replay, no manual `captureException` in shipped code, per T229 Done). Captures error message/stack/breadcrumbs; T229's verified sample event contained no cookies, tokens, or callback query params, but this is a sample, not a structural guarantee.
  - Vercel Web Analytics — a `_vercel/insights/view` beacon observed in T229's evidence; not yet independently characterized for this doc (see open question below).

- **Error review process:** owner reviews the Sentry `daily-dama` project's Issues dashboard (confirmed in T229).
