## Outcome and boundaries

A recorded hosted acceptance pass covering the complete account lifecycle — signup/verification, guest-data import into a newly created account, sign-out/in with saved data restored, password recovery, email change, and account deletion — using real delivered emails and two disposable account fixtures. Must demonstrate neither disposable account can read/write the other's records, and that deletion removes only the deleted owner's data.

T225 and T230 are complete; T231 already deployed and Auth-verified this exact production release (see `outputs/guided-tickets/T231.md`). This ticket does not require T230/T231 to be closed as a dependency — only that a prepared backend and deployed build exist, which they do (both `Done`). This ticket does not perform any new hosted configuration change, deploy, or migration — it verifies the release T231 already shipped.

**Hard constraint on execution (from the harness's own action-safety rules, which take precedence over ticket instructions):** creating accounts and entering passwords to authenticate are prohibited actions for the agent to perform, even with explicit authorization, and permanently deleting data is likewise prohibited for the agent to perform directly. Concretely, this means:

- The owner performs every signup, sign-in, sign-out, password-entry, email-change, password-recovery, and account-deletion action themselves, in their own browser.
- The agent prepares exact steps, exact copy/values to enter, and what to look for; the agent does not fill credential fields, click "Create account"/"Delete account", or otherwise authenticate as any test account itself.
- The agent can perform read-only verification (checking route availability, inspecting already-completed states the owner reports, reviewing the existing automated authorization test suite, reviewing Resend delivery logs or Supabase Auth logs if the owner shares them) and can reuse `supabase/tests/data-api`'s existing T155.7 cross-user isolation suite as backend-layer evidence rather than re-deriving it by hand.
- Cross-account isolation is proven primarily via T155.7's existing pgTAP/Data-API suite (already `Done`, covers anonymous denial, cross-user isolation, and per-operation grant matrices at the RLS layer) plus the owner's own UI observation that account B's app never shows account A's tricks/history/goals/notes after each performs the same actions with their own data.

### Step 2 — Build guest data, then sign up as account A

- State: ready
- Where and target: `https://www.dailydama.com`, in a **private/incognito window** (so no existing session or local data interferes), not signed in
- Action, in order:
  1. Open the app as a guest (don't sign in). Complete onboarding if prompted (pick a Kentei rank, select a few tricks) — this creates guest profile data.
  2. On Tricks, create one custom trick with a name you'll recognize later, e.g. `T232 Guest Custom Trick A`.
  3. On Sesh, run a short open-ended practice session on any trick and end it — this creates one guest practice-history record.
  4. Go to Sign up. Enter account A's email address and a password meeting the policy (12+ characters, an uppercase letter, a number, a symbol — see Decisions table). Submit.
- Why: guest data must exist *before* signup so the import path (guest → newly created account) is actually exercised, not just an empty new account. Covering onboarding profile, a custom trick, and a Sesh record exercises three of the five persistent domains at the acceptance level; goal/note import already has dedicated domain test coverage, so this pass doesn't need to also create a goal and a note to be representative.
- Expected result: after submitting Sign up, the app shows a "check your email" style screen naming account A's address (T257).
- Return: confirm you reached the check-your-email screen, and that it named the correct address. No need to paste the password.
- If different: describe the exact screen/error shown and stop before continuing — this needs a live diagnosis rather than proceeding to Step 3.
- Observed result: owner's first attempt used `luke@lukemiller.tech` (the owner's real personal address, not a disposable fixture). The confirmation link showed "expired" on click, and a follow-up resend produced no second email. Supabase Dashboard → Authentication → Users nonetheless showed that address as confirmed. Flagged as a low-severity UI/copy discrepancy (confirmation apparently succeeded despite the page's "expired" message) rather than a blocked signup — not fully root-caused, deferred, not blocking this ticket. **Because Step 9 requires deleting one test account, `luke@lukemiller.tech` must not be used as a disposable fixture** — owner agreed and signed up again with a genuinely disposable address as account A.
