## Preparation and implementation

Diagnostic work done in the prior planning conversation, before this branch existed (see the conversation's screenshots and repro attempts, summarized here since they're not separately filed):

1. Read `landing-auth-cta.tsx` and `landing-page.tsx`: confirmed `HeaderBar` already has `display: ${$visible ? 'flex' : 'none'}` alongside `opacity`/`pointerEvents`, driven by `landing-page.tsx`'s `headerVisible` state from `onScroll`/`HEADER_BAR_SCROLL_HIDE_THRESHOLD = 24`. This is exactly T254's shipped fix.
2. Against the live `dailydama.com` DOM, dispatched a plain `scroll` event, then a rapid 20-step sequence of synthetic `wheel` + `scroll` events simulating momentum scrolling. In every case `[data-testid="landing-header-bar"]`'s computed style resolved correctly to `display: none; opacity: 0` with a zero-size bounding rect, and `querySelectorAll` found only one header node (no duplicate/stale node left behind).
3. Confirmed via the user's follow-up screenshot + Q&A that the visible gold bar is a **distinct overlay bar** (not the CTA card's own top edge, which was the alternate hypothesis), and that it reproduces on **every** scroll-down, on both mobile and desktop Chrome.
4. On starting this branch, found an unrelated, already-local, not-yet-pushed commit on `development` (`7d8cb0a`) fixing a *different* landing-page bug: the first screenshot's `FadeInUp` entrance animation could bake in a collapsed layout because `useWindowDimensions()` was still settling on first paint in the static web export, fixed by deferring the animation trigger to a `requestAnimationFrame` tick. This is a different code path (`useHasEnteredViewport`/`ScreenshotEntry`, not `HeaderBar`), but it establishes a real precedent for this exact class of bug in this codebase: **a static-export/hydration-timing issue that only manifests in production, not in a normal dev-server Playwright pass** — which is exactly the gap T254's own verification had. This raises a new, more specific hypothesis worth testing first (see Step 1): the header bar bug may only occur on the **first** scroll shortly after page load/hydration, not on a later scroll once hydration has settled — which would explain why this session's testing (which loaded the page, waited, then scrolled) never reproduced it, since by then hydration had already settled.

Local reproduction/investigation is currently blocked: this session's embedded browser pane cannot perform a real interactive scroll (times out with "Browser pane is currently hidden"), so further progress needs owner-driven DevTools inspection.
