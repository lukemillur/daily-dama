## Outcome and boundaries

Fix a persistent gap/bar blocking the top of the landing page, reported by the owner via screenshot on production mobile and desktop Chrome. No completion dependencies on other tickets.

**The actual root cause was not the header bar.** `Screen` (`src/components/ui/screen.tsx`) adds an 88px `padding-top` on web whenever `includeWebHeaderInset` isn't explicitly set to `false` — space reserved for the app's persistent five-tab web navigation on `/app/*` routes. `LandingPage`'s `<Screen>` never opted out, so the landing page has carried an unexplained 88px empty gap at the very top of the page on every load, regardless of scroll position, since long before this ticket. Both the owner and Claude initially misattributed this to `LandingAuthCta` (the actual, correctly-functioning header component) because of its position and similar height.

## Preparation and implementation

This ticket took several wrong turns before finding the actual defect — recorded here since the investigation trail matters for anyone touching this code again:

1. **Original hypothesis (wrong):** `HeaderBar`'s CSS `display`/`opacity` toggle (T254's shipped fix) was leaving a stale painted frame after a real scroll — a paint/compositing bug. Synthetic `scroll`/`wheel` event dispatch against the live production DOM never reproduced it (computed style always correctly resolved to `display: none`), which was consistent with this theory (paint bugs don't always show up under synthetic events) but never proved it.
2. **First fix attempt (based on hypothesis 1, wrong):** Replaced the CSS toggle with full React mount/unmount of `LandingAuthCta`, reasoning that removing the DOM node entirely sidesteps any stale-paint mechanism. Verified the node was genuinely removed from the DOM on scroll. Owner reported the bug still present on both desktop Chrome and real iOS Safari — this disproved hypothesis 1 entirely, since the component wasn't even in the DOM when the bug appeared.
3. **Second fix (independent improvement, not root-cause-driven):** Reworked `LandingAuthCta` to render as the first element inside the landing page's scrollable content (in normal document flow) instead of `position: absolute` above it, removing the scroll-listener/visibility-state mechanism entirely. This is a genuine simplification but still didn't fix the reported bug — introduced (and fixed in the same pass) an unrelated `width: 100%` circular-sizing bug from the flow change, then owner reported the *original* bug was still present, now visible even on page load without scrolling.
4. **Real diagnosis:** Owner captured the actual DOM around the visible defect via DevTools' element picker. The outermost element carried an inline `style="padding: 88px 0px 0px;"` — traced to `Screen`'s `includeWebHeaderInset` prop (`src/components/ui/screen.tsx:53-54`), which defaults to `true` and reserves 88px of top padding intended for the app's persistent web navigation on `/app/*` routes. `LandingPage`'s `<Screen>` never passed `includeWebHeaderInset={false}`, so the landing route carried that same reserved space despite having no such persistent header.
5. **Real fix:** Added `includeWebHeaderInset={false}` to `LandingPage`'s `<Screen>` (`landing-page.tsx`). Verified via `document.getElementById('root')` inspection in the browser tool that the inline padding is gone and the header now starts at `y: 0`. Owner confirmed on both real desktop Chrome and real iPhone Safari (dev server) that the bug is resolved.
6. Corrected two in-code comments (`landing-auth-cta.tsx`, `landing-page.test.tsx`) that had asserted the disproven "stale painted frame in Chromium and WebKit" theory as established fact, since leaving a wrong causal claim in a comment would mislead a future reader.
7. Added a regression test (`landing-page.test.tsx`, `does not reserve the app web-header inset space above its own content`) asserting the resolved `paddingTop` on the `Screen` root is `0`. Confirmed the test actually catches the regression by temporarily reverting the fix and observing the test fail with `Expected: 0, Received: 88`, then restored the fix.
