## Finding-by-finding disposition

### 1. Signed-in feedback — **reproducible** (not fixed)

Audit claim: a persistent Supabase client sends an authenticated (`authenticated` role) session on feedback submission, but `api.feedback`'s only grant/policy targets `anon`, so a signed-in submission gets `403 / 42501 / permission denied for table feedback`.

Current code confirms the same gap still exists:

- `src/features/feedback/persistence/submit-feedback.ts:39-54` calls `client.from('feedback').insert(...)` using whatever Supabase client session is active (guest or authenticated) — there is no separate anon-only client path.
- `supabase/migrations/20260902000000_add_feedback_table_with_anon_insert.sql` is still the only migration touching `api.feedback`. It grants `usage on schema api to anon` and `insert on api.feedback to anon`, and defines exactly one RLS policy, `feedback_insert_anon`, `to anon`. There is no grant or policy naming `authenticated` anywhere in `supabase/migrations/` (`grep -rn "authenticated" supabase/migrations/20260902000000...sql` returns nothing).
- `supabase/tests/t217_1_feedback.test.sql` only exercises `set local role anon` (three times); it has no authenticated-role case, so this gap has no regression coverage either.

Since RLS defaults deny when no policy grants the acting role, an `authenticated`-role insert against this table still has no permissive policy to match — the 403 the audit reproduced is still live in the schema as committed. No local Supabase stack was started to re-run the literal HTTP call (that requires the Supabase CLI containers, out of scope for a documentation/code-reconciliation pass), but the RLS policy surface is unambiguous by direct inspection: the fix described in the audit (grant authenticated users the same narrow insert + validation) has not been implemented.

**Follow-up ticket state:** `T226` ("Close the signed-in feedback permission and hosted acknowledgment gap"), `TASKS_COLLABORATIVE.md:28`, `Status: Not started`. This is the ticket that owns implementing the fix; T225 does not modify it.

### 3. Dependency-audit failure reporting — **reproducible** (not fixed)

Audit claim: `security/scripts/check-dependency-audit.mjs` ignores Yarn's non-JSON failure/error output and does not require a completed audit summary, so it can report success after a network failure (DNS failure was reproduced).

`git log --oneline -- security/scripts/check-dependency-audit.mjs` shows a single commit, `d09f56f` ([T162.3], PR #221) — the file has never been modified since it was created, and `git diff d09f56f HEAD -- security/scripts/check-dependency-audit.mjs` is empty. Reading the current file confirms the exact mechanism the audit described is still present:

- `runYarnAudit()` (line 22) only throws if `spawnSync` itself errors (e.g., binary missing); it never checks `result.status` (the process exit code) or inspects `stderr`.
- `parseAdvisories()` (line 30) silently skips any NDJSON line it can't parse and never checks for an `auditSummary`-type entry (the record `yarn audit --json` emits when the audit actually completes).
- `main()` (line 49) treats an empty `gated` array as a clean pass ("no high/critical advisories found") with no distinction between "audit ran and found nothing" and "audit produced no advisory lines because it failed before finishing."

Because the file is byte-identical to the version the audit already reproduced a false-success DNS failure against, that reproduction stands without needing to be re-run — the code path making it possible is unchanged. (I did not additionally force a fresh DNS failure in this session: forcing `yarn audit` to fail at the network layer without disrupting the shared worktree's registry access wasn't worth the risk for a code path already proven byte-for-byte unchanged.)

**Follow-up ticket state:** `T228` ("Fail the dependency-audit gate on failed or incomplete audit output"), `TASKS.md:165`, `Status: Not started`. This is a `TASKS.md` (non-collaborative) entry within this same autonomous batch — T225 does not implement it, per this ticket's "no defect implementation" scope limit.

### 4. Sentry / CSP incompatibility — **reproducible** (not fixed)

Audit claim: `src/shared/observability/sentry-client.ts` initializes direct-DSN Sentry transport, but the deployed CSP's `connect-src` only permits `'self'` and `https://*.supabase.co`, so a real Sentry ingest call would be blocked.

Current state:

- `src/shared/observability/sentry-client.ts:33` still calls `Sentry.init({ dsn: config.dsn, sendDefaultPii: false })` with no custom transport or ingest-domain override — a standard Sentry DSN posts to an `*.ingest.sentry.io` (or self-hosted) origin.
- `vercel.json`'s enforced (not report-only) `Content-Security-Policy` header still reads: `connect-src 'self' https://*.supabase.co`. `git log --oneline -- vercel.json` shows the last change to this file was `da03f57` ([T162.2]) and `1870e5c` ([T162.1]), both predating Sentry's introduction; no Sentry ingest origin has ever been added to `connect-src`.
- No mention of "sentry" or "ingest" exists anywhere in `vercel.json`, `security/README.md`, or `DEPLOYMENT_HANDOFF.md` (checked directly).

A real Sentry ingest call from the browser would still be blocked by this CSP as committed. This is a static-configuration finding (DSN origin vs. allowed `connect-src`), confirmed by direct inspection of both files together; it does not require a live browser reproduction to establish, since the CSP is enforced (not report-only) and contains no matching origin for any Sentry ingest host.

**Follow-up ticket state:** `T229` ("Verify safe Sentry delivery through the deployed CSP"), `TASKS_COLLABORATIVE.md:54`, `Status: Not started`.
