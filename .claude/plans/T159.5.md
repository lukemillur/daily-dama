# T159.5 — Finalize guest import only after acknowledgements

## Good enough for this iteration

An authenticated web user can resume one guest import after reload, request loss,
storage failure, or interruption at any import phase. Every accepted operation is
identified durably and retried idempotently; guest source records remain available
until the corresponding server result and any required user choice are durable.
Unresolved or rejected records are retained and visible through the existing import
state. Once all required work is accepted and acknowledged, cleanup completes before
the import is declared complete, the runtime adopts the destination `user:<uuid>`
namespace through the existing identity-generation boundary, and a fresh browser can
rehydrate the same accepted dataset. This remains a web-only implementation; native
hardening, later synchronization UX, and account deletion are out of scope.

## Confirmed implementation context

- `src/features/guest-import/model/guest-import.ts` already models the import phases,
  operation progress, profile choice, conflicts, and identity guards, but its reducer
  has no explicit finalization/cleanup or unresolved-retention contract.
- `guest-import-empty-account.ts` prepares all five domains and persists progress before
  each push, but does not advance attempt metadata, and only the empty-account runner
  cleans guest source records. It persists `acknowledged` before cleanup, which is the
  right crash ordering to preserve, but cleanup is not yet a complete import invariant.
- `guest-import-decisions.ts` plans existing-account decisions and pushes accepted
  operations, but intentionally never deletes guest data and uses non-durable
  operation creation/time values for conflict choices. The current hook starts this
  runner only from `uploading`; profile/conflict decisions therefore need a durable
  continuation path rather than relying on the current one-shot effect.
- `use-guest-import.ts` persists through `useIdentityScopedDomain`, whose generation
  guards and queued writes must remain the only persistence boundary. Its broad catch
  currently settles only `profile` as failed, and its completion path marks all domains
  succeeded without auditing pending operations, unresolved conflicts, or source cleanup.
- `IdentityProvider` is the single Auth-derived identity source. It increments a
  generation when Auth changes and all domain providers rehydrate from their own
  `guest`/`user:<uuid>` storage namespaces. Namespace switching must use this existing
  boundary; do not introduce a second identity store or mix import state into the normal
  sync coordinator.
- T159.2 already proves an empty-account second-browser rehydrate and T159.3/T159.4
  provide the existing-account merge, profile-choice, and per-record conflict data
  structures. Their tests should be extended rather than replaced.

## Ordered implementation plan

### 1. Define the completion and source-ownership contract in the pure model

Update the guest-import state types/reducer so the durable state can distinguish:

1. an operation that is pending, being attempted, accepted by the destination, and
   awaiting source cleanup;
2. an accepted/deduplicated record whose guest copy may be removed;
3. a record explicitly kept in cloud or otherwise rejected; and
4. a conflict or failed operation that remains unresolved and blocks finalization.

Keep operation IDs stable for the entire `importId`; preserve destination namespace,
source namespace, expected revisions, payload snapshots, and attempt/error metadata.
Add guarded actions (or an equivalent pure transition) for durable attempt recording,
accepted-result recording, source-cleanup completion, decision continuation,
finalization, and finalization failure. Completion must be impossible while any
required operation is pending, failed/conflicting, awaiting a profile/conflict choice,
or awaiting cleanup. Stale import IDs and stale identity generations remain no-ops.

Add table-driven reducer tests for every legal/illegal transition, including reloadable
states after each phase and the rule that unresolved records are retained rather than
silently treated as successful.

### 2. Harden the durable progress document and write ordering

Extend `guest-import-persistence.ts`'s version-1 runtime validator and tests for the
new operation/finalization fields. Keep the provisional v1 policy from AGENTS.md: no
migration framework or v2 document. Malformed, wrong-namespace, duplicate-operation,
invalid-status, and invalid-attempt metadata must recover safely without allowing a
partial import to be mistaken for completion.

Centralize progress writes behind the existing identity-scoped `saveNow`/write queue.
Before every network attempt, immutably increment and persist attempt metadata; after a
definitive accepted response, persist the accepted state before touching guest storage;
after each successful guest cleanup, persist cleanup completion. A thrown request,
including a response lost after server commit, must leave the same operation pending or
reconcilable with the same operation ID on the next run.

### 3. Make the runner a resumable, acknowledgement-aware protocol

Refactor the empty-account and existing-account runners around one shared, injected
runner contract where practical (without combining the five domain persistence
providers). The runner should:

- snapshot guest data once per import and create deterministic operation IDs;
- process domains in the documented order and records deterministically;
- resume acknowledged-but-not-cleaned records first;
- persist attempt state before a push and retain the operation ID on every retry;
- classify `succeeded`, idempotent replay, conflict, validation failure, and thrown/lost
  response separately;
- continue unrelated accepted operations where the product rules allow, while parking
  only the failed/conflicting record;
- never mutate guest data for an unacknowledged operation;
- clean only source records whose destination result is accepted or whose user decision
  explicitly discards the guest copy; and
- return a structured paused/blocked result that the reducer can persist, not a generic
  exception that is mapped to the profile domain.

Use injected clock, operation-ID, cleanup, and `beforeOperation`/transport hooks so the
tests can interrupt before preparation, before request, after server commit/before
response, after acknowledgement/before cleanup, during cleanup, and between domains.
Keep network/storage effects outside the reducer.

### 4. Continue existing-account decisions through the same durable runner

When the target is existing, persist the merge plan before uploading. Persist profile
and per-record choices with stable operation IDs derived from the import identity, and
make a resume after a choice/reload continue only the newly accepted work. Reconcile
choices with the already-acknowledged operation ledger so pressing/replaying a choice
cannot create a duplicate operation.

Explicitly retain unresolved conflicts and guest records. A cloud choice may be treated
as an accepted discard only after that choice is durable; a guest choice requires its
revision-guarded destination acknowledgement before cleanup. Identical/deduplicated
records must follow the same accepted-source cleanup rule. A failed accepted-choice
push remains retryable and blocks finalization; unrelated choices continue.

Add focused tests for profile guest/cloud choices, each conflict choice, repeated choice
submission, lost responses, stale revisions, one-record failure with unrelated success,
and reload at `awaitingProfileChoice`/`conflicts`/post-choice states.

### 5. Repair the React driver and finalization sequencing

Restructure `use-guest-import.ts` so every import phase has an idempotent continuation
effect keyed by `importId` and current identity generation, rather than only running
the existing-account runner from `uploading`. It must re-read or reuse only the
durable phase data appropriate to the interruption point, avoid duplicate concurrent
runs, and ignore late results after identity changes.

Route structured outcomes to the correct domain and record, keep the import visibly
paused/retryable, and do not dispatch `completed` merely because a runner returned
without throwing. The hook must persist the final audit state only after all accepted
records and required decisions are acknowledged and guest cleanup has succeeded.

Preserve the current hydration behavior: no initial empty write, no guest inventory for
guest identities, and no cross-identity adoption. Add hook tests for reload/remount,
identity changes during every asynchronous phase, storage failures, no client, manual
retry/continuation, and the absence of an import loop after a failure or dismissal.

### 6. Switch namespaces only after successful finalization

Use the existing Auth → `IdentityProvider` → identity-scoped-domain generation change
as the sole namespace switch. Prove that the source guest namespace is not cleared or
hidden before finalization, that a destination identity change cannot cause a stale
guest runner to write into the user namespace, and that a late response from the old
generation cannot overwrite either namespace.

After finalization, ensure the user namespace is hydrated from the accepted server
state and the guest-import record cannot trigger a second import on that authenticated
generation. If the Auth transition occurs before cleanup can finish, retain a durable
guest-side finalization obligation and resume it safely without exposing guest data as
the user's accepted state; do not solve this by purging unrelated account caches.

Add a two-runtime/second-browser integration harness that seeds guest and destination
fixtures, exercises the complete empty and existing-account paths, switches identity,
then rehydrates all five domain providers and verifies accepted records, profile/trick
state, Stats inputs, goals, and notes match the server while unresolved guest records
remain available.

### 7. Build the complete fault-injection matrix and verify

Extend the guest-import suites with deterministic fault injection across every phase:

- inventory read and cloud inventory pagination;
- confirmation and progress-plan persistence;
- merge snapshot/plan preparation;
- before-request interruption;
- server commit followed by lost response for every domain;
- acknowledged-progress write failure;
- guest cleanup failure for every domain;
- profile choice and each conflict resolution;
- retry after reload/remount;
- identity switch/logout during an in-flight operation; and
- final namespace switch and second-browser rehydration.

For each injected fault, assert no duplicate destination records, stable operation IDs,
correct attempt metadata, no early guest deletion, retained unresolved records, and
eventual completion only after the missing acknowledgement/cleanup is recovered. Add
negative assertions for premature `completed`, profile-only failure reporting, stale
generation writes, and a second import for the same guest source.

Verification for implementation is the affected guest-import/domain persistence Jest
files plus `yarn tsc --noEmit`, `yarn eslint <changed-files>`, and the web export because
the authenticated web route/namespace behavior is involved. Before completion, run the
repository verifier (`node .claude/scripts/verify.mjs`) and the existing second-browser
integration evidence as appropriate. Do not launch iOS/Android tooling.

## Explicit scope boundaries

- Do not redesign ordinary T157 synchronization, add Realtime, or move guest import
  progress into the SyncCoordinator/outboxes.
- Do not implement T160 synchronization-health/conflict UX beyond the existing import
  surface needed to show paused/unresolved import work.
- Do not implement T161 account deletion/purge semantics; only preserve import metadata
  and namespace isolation so that ticket can later purge it safely.
- Do not add migration infrastructure, a backend import endpoint, export UI, or native
  hardening.
