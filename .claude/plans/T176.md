# T176 — Fix Profile's Account section not rendering until a manual refresh

## Investigation summary

- The task assumptions remain valid: `T176` is still in progress, is marked
  `Planning: Required`, and the static implementation contains no obvious stale
  closure or missing dependency that explains the report.
- `AccountSection` renders only when `useAuthState()` returns
  `status: "authenticated"`; `GuestAccountSection` is the mutually exclusive
  guest branch.
- `AuthProvider` starts at `initializing` and changes state only from the
  Supabase `onAuthStateChange` callback. `signInWithPassword` itself returns the
  SDK result and does not set Auth state directly.
- `SignInScreen` navigates to `/app/home` after a successful sign-in result and
  also has an effect that redirects when the provider later becomes
  authenticated. The existing sign-in and AccountSection tests mock these
  boundaries independently, so they do not cover delayed auth notification
  combined with route navigation.
- The app provider hierarchy places `AuthProvider` above the router slot and
  places the app-shell identity/profile providers below it. `IdentityProvider`
  intentionally blocks app-shell rendering while Auth is initializing and
  switches its reactive handle in a microtask after Auth resolves. This timing
  must be observed during reproduction, but it is not itself proof of the
  AccountSection defect.
- A local browser reproduction could not be run in the planner environment:
  the staged worktree has no installed dependencies, and the system Node binary
  fails to load its ICU library. This is an implementation-stage verification
  prerequisite, not a reason to change the ticket assumptions.

## Ordered implementation plan

1. Establish a reproducible web scenario with the Expo development server and a
   confirmed local account: start from a signed-out landing page, sign in,
   immediately navigate to Profile without refreshing, and record the visible
   Profile content and `AccountSection` state. Repeat with a deliberate delay
   before navigation and with a refresh to distinguish route timing from
   persistence/session initialization. Capture the exact order of the sign-in
   action result, Supabase auth event, route transition, and Profile render
   using temporary development-only instrumentation or browser-visible timing
   evidence; remove any instrumentation before completion.
2. Compare the reproduction against the provider lifecycle and route tree in
   `src/app/_layout.tsx`, `src/app/app/_layout.tsx`,
   `src/features/auth/state/auth-provider.tsx`,
   `src/features/auth/components/sign-in-screen.tsx`, and
   `src/app/app/profile/index.tsx`. Identify the first state/render boundary
   that diverges from the expected authenticated flow. Do not assume the fix
   belongs in `AccountSection` until the runtime ordering supports that.
3. Add a focused regression test at the boundary that owns the defect. The
   test must model the real sequence: a successful sign-in action resolves,
   navigation reaches Profile, the authenticated auth event is delivered at
   the relevant timing, and Profile eventually renders the signed-in Account
   section without a refresh. Preserve coverage for the existing initializing,
   guest, authenticated, and password-recovery render branches.
4. Implement the smallest fix that makes the provider/route/render lifecycle
   converge reliably. Keep AuthProvider as the source of truth, keep provider
   state serializable and reactive, and avoid duplicating session state in
   Profile or AccountSection. If the runtime evidence instead identifies a
   router transition or provider-mount issue, fix that boundary and document
   why a local AccountSection workaround would be incorrect.
5. Run the focused auth/Profile tests, then the relevant auth state and Profile
   route tests, followed by `yarn tsc --noEmit` and the required web export if
   route/bundling behavior changed. Verify in the Expo dev server that direct
   sign-in → Profile navigation shows the signed-in Account section without a
   refresh, and retain the exact reproduction evidence in the completion notes.
6. Update `TASKS.md` completion notes with the discovered root cause and the
   passing regression/browser evidence, then move T176 to `TASKS_DONE.md` in
   the implementation commit and remove this durable plan as required by the
   ticket workflow.

## Exit-criteria interpretation

- The implementation is complete only when an automated regression test or a
  reproducible in-browser walkthrough proves sign-in followed by direct Profile
  navigation renders the authenticated Account section without manual refresh.
- The completion notes must name the observed runtime root cause and connect it
  to the chosen fix; a test that only mounts an already-authenticated Profile is
  insufficient.
- Mobile validation remains deferred under the repository's active web-only
  platform scope.
