# T153.8 — Build signup, check-email, verification, and resend

## Confirmed starting state (read before coding)

- `AuthProvider` (`src/features/auth/state/auth-provider.tsx`) has no `signUp` or resend action yet. Everything else it needs (client access, redirect-URL pattern, action shape) is established by `requestPasswordReset`.
- `categorizeAuthError` (`src/features/auth/model/auth-errors.ts`) **already** has `accountAlreadyExists` (`user_already_exists`, `identity_already_exists`), `weakPassword`, `offline`, `rateLimited`, `expiredOrInvalidLink`, `missingVerifier` — all pre-wired for this ticket, per the inline `NOTE for T153.8` comment. Do not add new categories or codes; reuse these.
- `/auth/callback` (T153.7, merged) already handles a signup-confirmation code generically: `exchangeCodeForSession` returns `redirectType: null` for a confirmation code (vs `'recovery'`), and the callback screen already routes `redirectType === null` to `router.replace('/app/home')`, and already renders the expired/missing-verifier/offline/rate-limited copy from a shared `ERROR_COPY` map. **No changes to the callback route are needed for this ticket** — verify this behavior in the manual walkthrough, don't re-derive it in code.
- `validateNewPassword` (`src/features/auth/model/password-policy.ts`) already enforces `MIN_PASSWORD_LENGTH = 10` and password/confirm match. Reuse it; do not duplicate the length constant.
- Local Supabase config (`supabase/config.toml`): `[auth.email] enable_confirmations = true`, `enable_signup = true`, `max_frequency = "1s"`; `[auth.rate_limit] email_sent = 2` (per hour). This means: (a) an unconfirmed-duplicate signup silently resends and returns `{ error: null }` — already indistinguishable from a fresh signup with no code change needed; (b) a confirmed-duplicate signup returns `user_already_exists` (`accountAlreadyExists`); (c) resend testing will hit the 2/hour cap quickly during the manual walkthrough — plan the walkthrough's resend clicks accordingly (1-2 max), don't loop to "prove" the limit beyond triggering `rateLimited` once.
- `TASKS_DONE.md`'s T153.9 closing note explicitly deferred sign-in-sign-up cross-links to **T153.11** ("Add guest account entry points to Profile"). Do not add sign-in/sign-up cross-navigation links in this ticket — that would preempt T153.11's own scope/exit criteria. The existing entry point for the manual walkthrough is T153.12's post-Sesh `PostSeshSignupInvite` (`src/features/sesh/components/sesh.tsx`), which already links to `/auth/sign-up` with a documented `as Href` cast pending this ticket.
- Task's hard constraint: "Do not place the submitted email in route parameters or analytics." This means `/auth/check-email` cannot receive the email via URL/query param, and it cannot be tracked in any `trackAuthEvent` call. The email must live only in in-memory (non-persisted) UI state shared between the two routes.

## Design decision: how /auth/sign-up hands the email to /auth/check-email

Following the existing "derive flow-continuity data from Auth-domain state, not route params" precedent (`reset-password-screen.tsx` relies on `AuthState.status === 'passwordRecovery'`, never a URL param), add a small, ephemeral, non-persisted context scoped to the two new routes:

- New file `src/features/auth/state/pending-verification-email.tsx`: a `PendingVerificationEmailProvider` (plain `useState`, no AsyncStorage, no reducer, no persistence adapter — this is transient UI state, not one of AGENTS.md's three persistent domains) exposing `usePendingVerificationEmail(): string | undefined` and `useSetPendingVerificationEmail(): (email: string | undefined) => void`.
- New file `src/app/auth/_layout.tsx`: wraps `<Slot />` with `<PendingVerificationEmailProvider>`. This is the first layout under `src/app/auth/`, so it will also wrap `sign-in`, `forgot-password`, `callback`, `reset-password` — harmless, since only the two new screens consume the context, and it keeps the provider scoped to the /auth route family rather than hoisting it into the root `_layout.tsx` alongside the three real persistent domains.
- Reload/direct-navigation to `/auth/check-email` with no pending email in memory is an expected, acceptable edge case (matches the reload behavior already accepted for `/auth/reset-password` per T153.10's closing note) — the check-email screen must render a generic, actionable fallback (link back to `/auth/sign-up`) rather than crash or silently break.

## Ordered implementation steps

1. `src/features/auth/model/signup-validation.ts` (new, pure, mirrors `sign-in-validation.ts` / `forgot-password-validation.ts`'s doc-comment style about not leaking account-specific facts client-side).
   - `SignUpFieldErrors { email?, password?, confirmPassword? }`, `SignUpValidation` discriminated union, `validateSignUpFields(email, password, confirmPassword)`.
   - Email check: reuse the same EMAIL_SHAPE_PATTERN used elsewhere (empty -> "Enter your email.", malformed -> "Enter a valid email address.").
   - Password/confirm check: delegate to `validateNewPassword` from `password-policy.ts` (don't re-implement the length/match rules) and merge its errors into the combined result.
   - Add `src/features/auth/model/__tests__/signup-validation.test.ts` covering: empty email, malformed email, short password, mismatched confirm, all-valid.

2. `src/features/auth/state/pending-verification-email.tsx` (new). Simple context + `useState<string | undefined>`, `usePendingVerificationEmail`/`useSetPendingVerificationEmail` hooks that throw if used outside the provider (match `useAuthState`/`useAuthActions`'s pattern). Add a small colocated test (`__tests__/pending-verification-email.test.tsx`) proving: value starts undefined, setting propagates to consumers, and the hooks throw outside the provider.

3. `src/app/auth/_layout.tsx` (new). Thin: import Slot from expo-router, import PendingVerificationEmailProvider from the new module, render PendingVerificationEmailProvider wrapping Slot. Order this after step 2 so the import resolves. Sanity-check after adding this that `sign-in-screen.test.tsx`, `forgot-password-screen.test.tsx`, etc. (which render the screens directly, not through the router tree) are unaffected — they don't go through `_layout.tsx`, so they shouldn't need changes, but re-run the auth suite after this step to confirm.

4. `AuthProvider` (`src/features/auth/state/auth-provider.tsx`): add two actions, following `requestPasswordReset`'s exact shape (fixed redirectTo, no client-supplied destination):
   - `signUp: (email: string, password: string) => Promise<{ error: AuthError | null }>`
   - `resendSignupConfirmation: (email: string) => Promise<{ error: AuthError | null }>`
   - `signUp`: guard on missing client / missing window exactly like `requestPasswordReset`; call `client.auth.signUp({ email, password, options: { emailRedirectTo } })` where emailRedirectTo is `${window.location.origin}/auth/callback`; return `{ error }`.
   - `resendSignupConfirmation`: same guards; call `client.auth.resend({ type: 'signup', email, options: { emailRedirectTo } })`; return `{ error }`.
   - Add both to the actions useMemo and its dep array.
   - Extend `auth-provider.test.tsx` with the same coverage pattern already used for `requestPasswordReset`: forwards args + redirectTo, surfaces a success `{ error: null }`, surfaces a failure error, doesn't mutate AuthState. Add signUp/resend mocks to `createFakeClient`.

5. `src/features/auth/components/sign-up-screen.tsx` (new). Structural twin of `forgot-password-screen.tsx` (loading/authenticated-redirect branch, form branch, "check email" outcome) but the "check email" outcome is a route change, not an internal boolean flag:
   - Fields: email, password, confirm password (same FieldInput/FieldLabel styled-components lifted verbatim from `reset-password-screen.tsx`/`sign-in-screen.tsx` — this is boilerplate duplication already accepted across every existing auth screen in this codebase; don't introduce a shared form-field abstraction as part of this ticket, that's out of scope).
   - Validation via `validateSignUpFields`; same hasSubmitted + isSubmittingRef double-submit guard pattern as `sign-in-screen.tsx`.
   - On submit success: `error === null` OR `categorizeAuthError(error) === 'accountAlreadyExists'` both take the identical path — call the pending-email setter with the trimmed email, `trackAuthEvent('sign_up_success')` (deliberately the same event name/shape for both real-success and already-exists, so Analytics itself cannot become a second enumeration oracle — do not add a distinct accountAlreadyExists tracked category here), then `router.replace('/auth/check-email')`.
   - On any other error category (weakPassword, offline, rateLimited, unknown — expiredOrInvalidLink/missingVerifier/invalidCredentials/unverifiedEmail are unreachable from signUp but the Record<AuthErrorCategory, string> must stay exhaustive for tsc, matching the `forgot-password-screen.tsx` precedent): setSubmitCategory(category), logAuthWarning, trackAuthEvent('sign_up_error', category), stay on the form.
   - useEffect redirect to /app/home when authState.status === 'authenticated', matching every other auth screen.
   - Copy: eyebrow "Sign up", title "Create your account.", one line explaining the 10-character password minimum inline near the password field (don't rely on the error string alone to teach the rule — small UX improvement, in scope since it's this screen's own form).

## Order rationale

Steps 1-3 (validation, ephemeral context, layout) are pure/no-IO scaffolding the screens depend on — do them first so the screens in steps 5-6 aren't written against a moving target. Step 4 (provider actions) must land before the screens that call them. Step 8 (sesh.tsx cleanup) is independent and can happen any time after step 7, but doing it last avoids a transient state where the route exists but the cast hasn't been removed yet. Steps 9-10 close the loop: automated tests first (fast feedback), then the one live walkthrough last, matching the T153.10 precedent of closing exit criteria's live-verification clause only once the code and mocked-test surface are already solid.

## Risks / non-obvious things to watch

- The accountAlreadyExists -> identical-success-path branch is the crux of "generic duplicate-account handling" and the easiest place to accidentally leak an enumeration signal (e.g. by tracking a different Analytics event name, or by a stray console.warn in the "success" path that a future engineer adds without realizing this branch is reachable from an error). Keep it visually and structurally indistinguishable from the true-success branch in the component, not just in copy.
- Local rate limit (email_sent = 2/hour) is easy to blow through by over-testing resend live; rely on the unit test for rateLimited copy and keep live resend clicks minimal.
- Don't let `_layout.tsx` under `src/app/auth/` change existing screen tests — they render components directly, not through the router tree, so they should be unaffected, but confirm this explicitly after adding the layout (step 3) rather than assuming it.
- Do not add sign-in/sign-up cross-links or a Profile entry point — both are explicitly T153.11's scope.
