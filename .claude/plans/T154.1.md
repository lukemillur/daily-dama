# T154.1 — Signed-in password and email change flows

## Decisions settled by scoping / prior tickets (do not re-litigate)

- Current-password verification for password changes is implemented at the app layer, not
  via GoTrue's own `secure_password_change` / reauthentication-OTP mechanism. Concretely:
  `AuthProvider.changePassword` first calls `signInWithPassword(email, currentPassword)` (a real
  re-login against the account's own known email, which is not an enumeration risk since the
  caller is already authenticated and the email is already known to them) and only calls
  `updateUser({ password })` if that succeeds. Leave `secure_password_change = false` in
  `supabase/config.toml` and the hosted project unchanged. This also means "expiry" for the
  password-change path is handled for free: `signInWithPassword` always establishes a brand-new,
  fully valid session immediately before `updateUser`, so a stale/expiring access token cannot
  cause `updateUser({password})` to fail with a session error the way it could without this step.
  Do not add GoTrue's nonce-based `reauthenticate()` flow -- that is OTP/MFA-adjacent and out of
  scope per the task's "Do not add MFA" note.
- Secure email change = GoTrue's `double_confirm_changes` setting (require confirmation on both
  old and new address). This is already `true` locally (`supabase/config.toml`, set by T153.1).
  T153.2's own notes explicitly left the hosted project's equivalent setting unconfigured for
  this ticket -- confirm and, if needed, set it there (see step 3).
- T153.7 fixed the callback to two hardcoded destinations (`/app/home`, `/auth/reset-password`)
  and its own closing note says "the successful email-change destination is deliberately added
  later by T154.1" -- this ticket adds exactly one more fixed destination
  (`/app/profile/account/security`) to that same closed switch. Do not add a `next`/arbitrary
  param; the destination set stays closed and hardcoded.
- `BACKEND_ROADMAP.md`'s frontend route list has only one new route for this ticket:
  `/app/profile/account/security`. Do not add a separate check-email-style route for email
  change -- show pending-confirmation guidance inline on that same screen.
- Identity/sync namespacing (`user:<verified-user-id>`) is keyed off `session.user.id`, not
  email (confirmed in `src/features/auth/model/identity-from-auth-state.ts`) -- an email change
  never touches persistence namespacing. No persistence-domain work is needed for this ticket.

## Key implementation risk to resolve first (step 1) -- read before writing UI

`AuthCallbackScreen` currently has no way to tell "this PKCE code came from an email-change
confirmation link" apart from "this came from a signup confirmation link" -- both return
`redirectType: null` from `exchangeCodeForSession` (confirmed by reading the installed
`@supabase/auth-js@2.112.3` source: `updateUser`'s PKCE code path, unlike
`resetPasswordForEmail`'s, never passes `isPasswordRecovery: true` into
`_getCodeChallengeAndMethod`).

Two candidate designs, in preference order:

**A (preferred, verify first): use GoTrue's own pending-email-change fields.** `User` has
`new_email?: string` and `email_change_sent_at?: string` (confirmed present in
`@supabase/auth-js`'s type declarations). After `exchangeCodeForSession` succeeds, check
`session.user.new_email` -- if truthy, this was (part of) an email-change confirmation; route to
`/app/profile/account/security` instead of `/app/home`. This needs zero redirect-URL /
allowlist changes. Must be verified live (local Supabase CLI + Mailpit) before relying on it:
confirm `new_email` is still populated on the session returned from exchanging both the
old-address and new-address confirmation links (including the final one that completes the
change) -- if GoTrue clears it before returning the session from the last exchange, this signal
won't reliably distinguish the completing exchange.

**B (fallback if A doesn't hold up): app-chosen query discriminator + explicit allowlist entry.**
`AuthProvider.changeEmail` would build `redirectTo` as
`${window.location.origin}/auth/callback?flow=email_change`, and the callback would read a
new `flow` param. This requires a real, non-obvious config change: the installed SDK's own
source comment on `_maybeAppendFlowIdToRedirect` states plainly that "redirect URLs are validated
against the project's allow list including the query string, so an extra parameter can stop
exact (non-wildcard) entries from matching." Since this project's allowlist is deliberately
exact/non-wildcard (T153.2, BACKEND_ROADMAP's "no wildcard production redirects" rule), option B
requires adding the exact `.../auth/callback?flow=email_change` string as its own additional
allowlist entry (both `supabase/config.toml`'s `additional_redirect_urls` and the hosted
project's `uri_allow_list` via the Management API) -- not a wildcard, not a replacement of the
existing entries, just one more exact string alongside them for each of local + production.

Do the live spike (initiate an email change against the local Supabase/Mailpit stack, inspect
the actual Mailpit link and the exchanged session) early, decide A vs B, and only then write the
callback destination logic and (if B) the config changes. Everything below assumes A succeeds;
adjust step 2/5 accordingly if you land on B.

4. `src/features/auth/state/auth-provider.tsx` -- add two new guarded actions, following
   `completePasswordRecovery`'s existing guard pattern (`stateRef.current.status` check, generic
   `AuthError` with a `code` in the closed `auth-errors.ts` set otherwise):
   - `changePassword(currentPassword: string, newPassword: string)`: require
     `stateRef.current.status === 'authenticated'`; read `stateRef.current.session.user.email` --
     if missing, return a `session_not_found`-coded `AuthError` (defensive; this app is
     email/password-only so should not happen in practice); call
     `client.auth.signInWithPassword({ email, password: currentPassword })`; if it errors, return
     that error (surfaces as `invalidCredentials` etc. via the existing category map -- this
     screen can render `invalidCredentials` with a specific, non-generic "Your current password
     is incorrect" string, since no enumeration risk exists once already authenticated); else
     call `client.auth.updateUser({ password: newPassword })` and return its result.
   - `changeEmail(newEmail: string)`: same authenticated guard; build the fixed `redirectTo`
     exactly like `requestPasswordReset`/`signUp` already do
     (`${window.location.origin}/auth/callback`, plus the `?flow=email_change` suffix only if
     design B was chosen in step 1); call
     `client.auth.updateUser({ email: newEmail }, { emailRedirectTo: redirectTo })`.
   - Add both to the `AuthActions` interface, the `actions` `useMemo`, and its dependency array.
   - Extend `auth-provider.test.tsx`'s shared fake-client fixture usage (it already stubs
     `updateUser`/`signInWithPassword`) with new test cases: `changePassword` success (asserts
     both `signInWithPassword` then `updateUser` are called, in that order, with the right args);
     wrong-current-password (asserts `updateUser` is never called); offline on either step;
     not-authenticated guard (neither SDK method called). Same shape for `changeEmail`: success
     (asserts `updateUser` called with `{ email }` and the exact fixed `redirectTo`), offline,
     not-authenticated guard.

7. `src/features/auth/components/account-security-screen.tsx` (new) -- mirror
   `reset-password-screen.tsx`'s structure and `account-section.tsx`'s
   auth-status-gated-render + same-tick `isSubmittingRef` double-submit-guard patterns:
   - `authState.status === 'initializing'` -> loading copy.
   - `authState.status !== 'authenticated'` (guest or passwordRecovery) -> "Sign in to manage
     account security" guidance + a link to `/auth/sign-in`, no form rendered.
   - `authenticated` -> two independent sections, each with its own local submit/error/success
     state (a failure in one must not disturb the other):
     - Password: current password / new password / confirm new password fields ->
       `changePassword`. Error copy: `invalidCredentials` -> "Your current password is
       incorrect." (specific, safe here); `weakPassword`/mismatch -> existing
       `validateNewPassword` field errors; `offline`/`rateLimited` -> same fixed copy pattern as
       other screens; everything else -> generic fallback. Success -> clear all three fields,
       show a one-line success confirmation (no navigation away -- matches an account-settings
       page, not a completion screen).
     - Email: new email field -> `changeEmail`. On success, show inline pending-confirmation
       guidance ("Check both your current and new email inboxes to confirm this change") -- do
       not navigate, do not add a new ephemeral/pending-email provider (unlike T153.8's
       `PendingVerificationEmailProvider`, this state doesn't need to survive a route change,
       since the whole flow stays on this one screen; a plain local `useState` is enough).
       `offline`/`rateLimited`/invalid-email-shape handled the same fixed-copy pattern.

     exactly as other screens do (never pass a raw email/password as a `trackAuthEvent` argument

     `newPassword`/raw error text outside the controlled input values.
   - New `account-security-screen.test.tsx` covering: initializing; guest/passwordRecovery guard

     offline/rate-limited on password change; email-change happy path (pending-confirmation copy
