# T033 — Require a real lace for automatic laced status

## Confirmed bug

`selectUnlockedTrickIds` in `src/features/tricks/model/trick-directory.ts` (lines ~181-188)
marks a trick "unlocked" as soon as *any* practice-history record exists for it, regardless of
`laceCount`:

```ts
export function selectUnlockedTrickIds(
  sessions: readonly PracticeSessionRecord[],
): ReadonlySet<string> {
  return new Set(sessions.map((session) => session.trickId));
}
```

Its own doc comment and an existing test (`trick-directory.test.ts:190-196`,
`'unlocks a trick even when its only record has zero laces'`) both document this as intended
behavior — it is the exact bug this task fixes.

`selectLacedCountByTrickId` (same file) is already correct: it sums `laceCount` per trick and is
used for the "N laces" display. `selectEffectiveUnlockedTrickIds` layers
`manuallyUnlockedTrickIds` on top via set union and is already correct given a correct first
argument.

## Consumers (all found via `grep -rn "selectUnlockedTrickIds\|selectEffectiveUnlockedTrickIds"`)

1. `src/app/tricks.tsx` (lines 61-67) — computes `lacedUnlockedTrickIds` via
   `selectUnlockedTrickIds(sessions)`, then `unlockedTrickIds` via
   `selectEffectiveUnlockedTrickIds(...)`. That single `unlockedTrickIds` value is passed as the
   `unlockedTrickIds` prop to **both** `<TrickDirectory>` (line 173) and `<LacedTricksScreen>`
   (line 125) — i.e. the Tricks directory and the Laced screen already share one derivation by
   construction. Preserve that sharing; do not give either screen its own computation.

2. `src/features/profile/state/kentei-rank-auto-promotion.tsx` (lines 23-31) — rank promotion.
   This file does **not** call `selectUnlockedTrickIds` at all. It already independently computes
   the correct thing inline:
   ```ts
   const lacedCountByTrickId = useMemo(() => selectLacedCountByTrickId(sessions), [sessions]);
   const lacedTrickIds = useMemo(
     () => new Set([...lacedCountByTrickId.entries()].filter(([, count]) => count > 0).map(([trickId]) => trickId)),
     [lacedCountByTrickId],
   );
   ```
   So **rank promotion is not currently affected by the bug** — this contradicts a literal
   reading of the task description but is what the code actually shows. The real defect here is
   duplication/drift risk: this correct logic is reimplemented inline instead of living in
   `trick-directory.ts` next to `selectLacedCountByTrickId`, so a future change to the "laced"
   definition could fix `tricks.tsx` and miss this file (or vice versa). Fixing this task means
   collapsing both call sites onto one shared, correctly-named selector — that satisfies "rank
   promotion follows the corrected definition" by construction (same function, not just same
   result) rather than leaving two independent implementations that happen to agree today.

No other production consumers exist. `src/features/access-gate/**` also uses "unlocked"
terminology but is an unrelated feature-gate concept — do not touch it.

## Naming decision (per task Notes: "rename misleading local selectors where useful")

- Rename `selectUnlockedTrickIds` → `selectLacedTrickIds`, and fix its body to require
  `laceCount > 0`.
- Rename `selectEffectiveUnlockedTrickIds` → `selectEffectiveLacedTrickIds` (logic unchanged —
  it already correctly unions lace-derived IDs with the manual-override list). This keeps the
  selector layer's naming consistent with the product's "laced" terminology (the doc comments in
  this file already say "laced", and the Laced Tricks screen's copy says "laced"/"unlaced").
- Do **not** rename the persisted field `manuallyUnlockedTrickIds`, the `toggleManualUnlock` /
  `removeManualUnlock` actions, or the `unlockedTrickIds` prop on `TrickDirectory` /
  `LacedTricksScreen`. The task explicitly preserves the persisted field name, and renaming the
  UI prop name is a larger, purely cosmetic blast radius (touches two component files and their
  tests for no behavior change) — out of scope for this iteration. Note it as a deferred cleanup
  if you want, don't fold it in.

## Implementation steps, in order

1. **`src/features/tricks/model/trick-directory.ts`** — fix the selector first since everything
   else depends on it.
   - Rewrite `selectUnlockedTrickIds` as `selectLacedTrickIds`:
     ```ts
     // Laced means at least one recorded session for the trick actually landed a lace.
     // A session record merely existing is not enough — see selectLacedCountByTrickId, which
     // deliberately keeps zero-lace sessions in its map (for per-trick lace-count display), and
     // hasPriorLaceForTrick in the practice-history domain, which uses the same laceCount > 0
     // predicate for "first lace" detection.
     export function selectLacedTrickIds(
       sessions: readonly PracticeSessionRecord[],
     ): ReadonlySet<string> {
       return new Set(
         sessions.filter((session) => session.laceCount > 0).map((session) => session.trickId),
       );
     }
     ```
   - Rename `selectEffectiveUnlockedTrickIds` → `selectEffectiveLacedTrickIds`; rename its first
     parameter `lacedUnlockedTrickIds` → `lacedTrickIds`; keep the union-with-manual-override body

## Order rationale

Step 1 (selector fix) must land before anything else compiles/typechecks, since steps 3-6 all
reference the renamed exports. Steps 2 and 1 should be done together (same commit) so the test
suite doesn't go red mid-change. Steps 3-5 are mechanical rename follow-through and can happen in
any order relative to each other. Step 6 (new integration tests) should come last since it's the
one exercising the fixed behavior end-to-end and is the most likely to reveal a mistake in steps
1-4.

## Risks / non-obvious things

- The task description implies rank promotion currently has this bug too; the code shows it
  doesn't (it has its own correct inline logic). Don't "fix" a bug that isn't there — the
  correction needed at that call site is deduplication onto the shared selector, not a behavior
  change. Double-check this by running the existing `kentei-rank-auto-promotion.test.tsx` suite
  unchanged before making any edits, to confirm current green baseline, then again after — it
  should stay green throughout except for the two new tests going from not-existing to passing.
- `selectLacedCountByTrickId` intentionally keeps zero-lace sessions in its map (there's an
  existing test guarding this: `'keeps a trick with a zero-lace session in the map at value 0'`).
  Do not "simplify" `selectLacedTrickIds` by building it on top of that map and filtering — it's
  fine to do so, but if you do, keep it correct (`count > 0`, not just map membership). The plan
  above uses a direct `sessions.filter(...)` implementation instead specifically to avoid that
  trap and to mirror `hasPriorLaceForTrick`'s predicate in
  `src/features/stats/model/practice-history.ts`.
- `src/features/profile/model/user-profile.ts`'s `completeOnboarding` action seeds
  `manuallyUnlockedTrickIds` from onboarding assessment results (`getSeedLacedTrickIds`) — this is
  a legitimate use of the manual-override path, not something this task touches. Don't confuse it
  with the bug being fixed.
