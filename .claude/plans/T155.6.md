# T155.6 — Enforce domain JSON invariants inside Postgres

## Audit result (read this first)

I read every migration under `supabase/migrations/` (T155.1–T155.5) and every
pgTAP file under `supabase/tests/` (t155_2 through t155_5, 140 pgTAP
assertions, all currently green via `supabase db reset` +
`supabase test db --local`). I then stood up the local stack
(`npx --yes supabase@2.115.0 start` + `db reset`) and drove the real Data API
over HTTP with a genuinely confirmed, signed-in `authenticated` JWT (minted
via `POST /auth/v1/admin/users` with `email_confirm:true` using the
service-role key, then `POST /auth/v1/token?grant_type=password`) to probe
exactly the gaps this ticket's notes flagged as suspicious:

- Unknown top-level key added to `profiles.last_sesh` (`{"trickId":...,
  "plan":{...},"unknownTop":"x"}`) → **rejected**, `23514`,
  `profiles_last_sesh_shape`, identical to the pgTAP case.
- Direct nested-sequence reference via `POST /rest/v1/custom_tricks` →
  **rejected**, `23514`, `"nested sequences are not allowed..."`, identical to
  the pgTAP case.
- Ambiguous goal (`kind:"count"` with both `target_count` and `target_ms`
  populated) via `POST /rest/v1/goals` → **rejected**, `23514`,
  `goals_count_shape`, identical to the pgTAP case.
- A completely unrecognized JSON key that isn't any column at all (e.g.
  `"bogusField":true` in a `custom_tricks` insert body) → PostgREST itself
  rejects it pre-database with `PGRST204` ("Could not find the 'bogusField'
  column... in the schema cache"). This is enforced by PostgREST's schema
  cache, not by anything this ticket needs to add.
- Forging a server-owned column on insert (e.g. `"revision":99` on
  `custom_tricks`) → **rejected**, `42501`, `permission denied for table
  custom_tricks`, via the column-level grants T155.5 already added.
- A bulk (JSON-array) `POST` where one element is malformed rolls the whole
  request back atomically (PostgREST wraps one request in one transaction) —
  no partial-insert leak.

**Conclusion: no new CHECK constraints, triggers, or grants are needed.**
T155.2–T155.5 already closed every gap this ticket's notes worried about,
including the two specifically called out (unknown-field rejection via the
`<@ jsonb_build_object(...)` subset-equality pattern in `last_sesh` and the
exact-shape-equality pattern in sequence steps; and ambiguous goal payloads
via the mutually-exclusive `target_count`/`target_ms` CHECK constraints).
Do not add a new migration file for this ticket unless the implementer's own
run of the parameterized suite below (step 3) surfaces a genuine
discrepancy — treat that as a real, reportable finding, not something to
paper over, but I could not reproduce one after directly exercising every
scenario the notes called out.

The actual gap this ticket needs to close is procedural: **no automated,
repeatable Data API (HTTP) test suite exists yet.** Every domain-invariant
proof today is pgTAP (SQL-level, inside a transaction that's rolled back).
The exit criteria explicitly require "parameterized raw Data API tests" —
i.e. real HTTP requests through PostgREST, the actual path a client takes —
and that suite does not exist. Building it, in a form a later session or CI
can re-run unattended, is this ticket's deliverable.

## Why this doesn't conflict with T155.7/T155.8

- T155.7 owns RLS/grant proof (anonymous denial, cross-user isolation,
  ownership-change rejection, practice-session immutability) via its own raw
  HTTP tests. This ticket's suite must stay scoped to domain/shape
  invariants (profile variants, custom-trick steps incl. no-nesting, goal
  variants, invalid ranks) for a single authenticated owner acting on their
  own rows — do not duplicate T155.7's cross-user matrix here, just don't
  accidentally block on it (every case below operates within one user's own
  rows, so it never depends on RLS semantics being separately proven yet).
- T155.8 later consolidates *every* security/migration test source (pgTAP +
  this ticket's Data API suite + T155.7's Data API suite + pagination
  fixtures) into one repeatable command. This ticket only needs to produce
  the new Data API-level tests and wire a single documented command to run
  them today; do not build T155.8's full harness now.

## Implementation steps

### 1. Add a small local-Data-API test helper module

Create `supabase/tests/data-api/lib/local-supabase.mjs`. Responsibilities:

- `getLocalConfig()`: shells out to
  `npx --yes supabase@2.115.0 status -o json` (via `node:child_process`
  `execFileSync`), parses the JSON, and returns `{ apiUrl, anonKey,
  serviceRoleKey }` (`API_URL`, `ANON_KEY`, `SERVICE_ROLE_KEY` in that
  output). If the command fails (stack not running), throw an error whose
  message tells the developer to run `npx --yes supabase@2.115.0 start` —
  do not hardcode the demo anon/service keys as a silent fallback; failing
  loudly here is what stops this suite from being run against the wrong
  target. Cache the parsed result for the process lifetime (calling
  `supabase status` once per test file is fine; once per test case is not).
- `createConfirmedUser(config, email, password)`: `POST
  {apiUrl}/auth/v1/admin/users` with `apikey`/`Authorization: Bearer
  {serviceRoleKey}` and `{ email, password, email_confirm: true }`; returns
  the created user id.
- `signIn(config, email, password)`: `POST
  {apiUrl}/auth/v1/token?grant_type=password` with `apikey: {anonKey}`;
  returns `{ accessToken, userId }`.
- `deleteUser(config, userId)`: `DELETE {apiUrl}/auth/v1/admin/users/{userId}`
  with the service-role key — this is the suite's cleanup path; deleting the
  `auth.users` row cascades to every `api.*` row via the existing `on delete
  cascade` FKs (already proven in the t155_2/3 pgTAP cascade assertions), so
  no per-table teardown is needed.
- `restClient(config, accessToken)`: returns a small `{ post, patch, get
  }` wrapper around `fetch` that always sets `apikey`, `Authorization:
  Bearer {accessToken}`, `Content-Profile: api` / `Accept-Profile: api`, and
  `Content-Type: application/json`, and resolves to `{ status, body }`
  (parsed JSON body, or `null` on an empty response) rather than throwing on
  non-2xx — every test case needs to assert on the exact status/`code`, not
  have the helper swallow it as a thrown exception.

This module has no dependency on `node:test`, so it can be unit-agnostic and
reused by all three suite files below.

### 2. Add three parameterized Data API test files

Mirror the existing one-file-per-resource pgTAP convention, under a new
`supabase/tests/data-api/` directory (kept separate from `supabase/tests/
*.test.sql` so `supabase test db --local`'s file-glob is untouched and this
suite's very different runtime — live HTTP against a running stack, not a
rolled-back SQL transaction — is visually obvious from the path alone):

- `supabase/tests/data-api/t155_6_profiles.test.mjs`
- `supabase/tests/data-api/t155_6_custom_tricks.test.mjs`
- `supabase/tests/data-api/t155_6_goals.test.mjs`

Each file uses `node:test` (`describe`/`test`, matching
`.claude/scripts/test/*.test.mjs`'s existing convention — no new
dependency). Structure, per file:

```js
import { before, after, describe, test } from 'node:test';
import assert from 'node:assert/strict';
import { getLocalConfig, createConfirmedUser, signIn, deleteUser, restClient } from './lib/local-supabase.mjs';

describe('T155.6 profiles Data API JSON invariants', () => {
  let config, userId, client;

  before(async () => {
    config = getLocalConfig();
    const email = `t155-6-profiles-${Date.now()}@example.com`;
    userId = await createConfirmedUser(config, email, 'tencharacters');
    const { accessToken } = await signIn(config, email, 'tencharacters');
    client = restClient(config, accessToken);
  });

  after(async () => {
    await deleteUser(config, userId);
  });

  // one insert to establish the row each valid/invalid case then mutates via PATCH,
  // OR one fresh POST per case with a distinct discriminator — pick per-file below.

  const validCases = [ /* ... */ ];
  for (const { name, patch } of validCases) {
    test(`valid: ${name}`, async () => {
      const { status } = await client.patch(`/profiles?user_id=eq.${userId}`, patch);
      assert.equal(status, 204); // confirmed: PATCH with no Prefer header -> 204, empty body
    });
  }

  const invalidCases = [ /* ... */ ];
  for (const { name, patch, expectedConstraint } of invalidCases) {
    test(`rejected: ${name}`, async () => {
      const { status, body } = await client.patch(`/profiles?user_id=eq.${userId}`, patch);
      assert.equal(status, 400);
      assert.equal(body.code, '23514');
      if (expectedConstraint) assert.match(body.message, new RegExp(expectedConstraint));
    });
  }
});
```

Port the *case data* (not the SQL) from the existing pgTAP files so nothing
new is invented — each pgTAP `lives_ok`/`throws_ok` pair already documents
exactly what's valid/invalid; this suite's job is proving the same truth
holds through the HTTP path with a real JWT, and to catch anything that only
a JSON-over-REST client can trigger (unrecognized column names, forged
server-owned columns, bulk-array atomicity — see below).

**`t155_6_profiles.test.mjs`** cases (source: `t155_2_profiles_and_trick_states.test.sql` lines 11–123):
- Valid: minimal not-onboarded profile (insert); onboarded + full theme +
  `openEnded` `lastSesh` with no target; `openEnded` with
  `targetLandingCount` boundary 999; `timed` with `durationMinutes` boundary
  60.
- Invalid: `kentei_rank` 0 and 13; `kentei_rank` set while
  `has_completed_onboarding=false`; onboarded profile with `kentei_rank`
  cleared to null; theme color missing `#`; theme color with too few hex
  digits; `streak_threshold_ms` not a 60000 multiple; `streak_threshold_ms`
  above 3600000; `lastSesh` unknown `plan.kind`; `lastSesh` `openEnded` with
  an unknown extra key (`unknownTop` at the top level, and an extra key
  nested inside `plan`, both — this is the specific "unknown fields" case
  the ticket calls out); `targetLandingCount` 1000; `durationMinutes` 61;
  empty `trickId`.
- Data-API-specific additions (not in the pgTAP file, because pgTAP can't
  observe them): forging `revision`/`created_at` in the insert body →
  expect `42501`; sending a JSON key that isn't a column at all
  (`"bogusColumn":true`) → expect `400` with `code: 'PGRST204'`.

**`t155_6_custom_tricks.test.mjs`** cases (source:
`t155_3_custom_tricks_and_practice_sessions.test.sql` lines 11–145): valid
minimal standalone, standalone with rank, sequence mixing `existingTrick` +
`customText`, sequence referencing only standard (non-custom) trick ids;
invalid: <2 steps, standalone with steps, `steps` not a JSON array, missing
`name`, missing `sourceTrickId`, unknown extra key on a step, unknown step
`kind`, self-reference, direct nested-sequence reference, retroactive
nested-sequence conversion (convert an already-referenced standalone trick
into `kind:'sequence'` via `PATCH`), unknown top-level `kind` value, blank
name, `kentei_rank` out of range, duplicate id (`23505`). Data-API-specific
additions: forge `revision` on insert (`42501`); unrecognized top-level JSON
key (`PGRST204`); bulk `POST` with one valid + one malformed element in the
same array body → expect the valid element's id to be **absent** afterward
(atomic rollback) — this is the one behavior genuinely specific to going
through PostgREST rather than a single pgTAP `INSERT`.

**`t155_6_goals.test.mjs`** cases (source: `t155_4_goals_and_notes.test.sql`
lines ~11–65): valid count goal, valid time goal; invalid: unknown `kind`,
count goal with `target_ms` also set (ambiguous), time goal with
`target_count` also set (ambiguous, reversed order), `target_count` below
1/above 100000, `target_ms` not a whole-minute multiple, `target_ms` outside
its bounds. Data-API-specific additions: forge `revision` on insert
(`42501`); unrecognized top-level JSON key (`PGRST204`).

Use a fresh `id`/discriminator per case (don't reuse one row across cases
within a file) so cases stay independent and order-agnostic, matching how
the pgTAP files already avoid case-to-case coupling except where the test is
explicitly about a stateful transition (e.g. the retroactive nested-sequence
conversion, which — like its pgTAP counterpart — must run after the sequence
it's being checked against already exists).

## Risks / non-obvious things for the implementer

- **Don't spend time hunting for a schema gap that isn't there.** I already
  verified every scenario this ticket's notes explicitly flagged as
  suspicious (unknown fields, ambiguous goals, nested sequences) via live
  HTTP requests against a freshly reset local stack, and all were correctly
  rejected identically to the existing pgTAP coverage. If your own run
  disagrees with what's recorded here, that's a real regression signal
  (possibly from a migration change made between this plan and
  implementation) — investigate before assuming the plan is wrong.
- **PATCH and POST default response codes differ, and neither returns a
  parseable JSON body unless you ask for one.** Confirmed directly against
  the local stack: a `PATCH` with no `Prefer` header returns `204 No
  Content` (empty body); a `POST` with no `Prefer` header returns `201
  Created` (also empty body). "Valid" case assertions should check the
  status code only (`204` for PATCH, `201` for POST), not try to parse a
  body out of either. Only add `Prefer: return=representation` where a case
  actually needs to inspect the returned row's contents (e.g. the bulk-array
  atomicity check, which is simplest to verify with a follow-up `GET`
  instead).
- **Test-user emails must be unique per run** to avoid colliding with a
  leftover user from a previous, non-cleaned-up run (e.g. a run that
  crashed before `after()`'s `deleteUser` fired). Using `Date.now()` (or
  `crypto.randomUUID()`) in the email local-part, as sketched above, avoids
  this without needing a pre-suite cleanup step.
- **`supabase status -o json`'s local demo `anon`/`service_role` keys are
  fixed, well-known values baked into the Supabase CLI** (not a project
  secret) — reading them dynamically via `getLocalConfig()` is about
  robustness against a future local `jwt_secret` change, not about hiding a
  secret; still avoid hardcoding them as a literal fallback in committed
  test code, matching the spirit of the README's existing "never commit
  `supabase status` output" guidance.
- Keep this suite's assertions scoped to shape/domain invariants only. It
  will incidentally prove a few RLS-adjacent things (e.g. an authenticated
  user can insert their own row at all) as a side effect of setting up each
  case, but do not add cross-user negative assertions here — that's
  T155.7's exit criteria, and duplicating it here would blur which ticket
  actually proved it when someone reads the git history later.
