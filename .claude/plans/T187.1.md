# T187.1 - Add updatedAt to profile, custom-trick, and goal records

## Key finding that changes the shape of this work

No Supabase migration is needed. api.profiles, api.custom_tricks, and
api.goals already have server-owned updated_at columns and mutation
triggers that bump them on every INSERT/UPDATE
(supabase/migrations/20260822193659_add_profiles_and_user_trick_states.sql,
20260822200050_add_custom_tricks_and_practice_sessions.sql,
20260822201500_add_goals_and_notes.sql, hardened further by
20260822210000_protect_server_owned_timestamps_and_ownership.sql). The
generated src/shared/supabase/database-types.ts already types updated_at
on all three Row/Insert shapes. This ticket is 100% app-layer: the local
domain models, reducers, persistence validators, and cloud row->domain
mappers just aren't reading/writing a field the database has carried since
T155. note.ts + note-cloud-mapping.ts are the working reference
implementation to mirror throughout.

Frozen-shape check requested by the task Notes: neither goal.ts nor
user-profile-persistence.ts carries an explicit "this schema is
provisional" comment the way custom-trick's version: 1 does, but both use
the exact same _SCHEMA_VERSION = 1 local-storage versioning pattern as
notes/custom-tricks, and their cloud tables were hardened in the same T155
migration series with no "frozen v1 contract" language anywhere in
supabase/. Nothing in the codebase treats either shape as frozen. Adding
updatedAt in place (no migration infra, no v2 document) is safe for all
three domains, consistent with AGENTS.md's custom-trick provisional-shape
note.

## Domain-by-domain design decisions

Goal (src/features/goals/model/goal.ts): straightforward - add
"readonly updatedAt: number" to GoalBase, mirroring Note's
createdAt/updatedAt pair exactly. createGoal already takes an optional
createdAt = Date.now(); set updatedAt: createdAt inside it, same as
createNote. applyGoalTargetEdit (currently no timestamp param at all)
needs a new updatedAt: number = Date.now() param, applied in its return
value. The one call site (GoalProvider.editGoal) doesn't need code changes
if you keep the default, but pass Date.now() explicitly there anyway for
symmetry with how note-provider.tsx calls things - implementer's call,
not load-bearing either way.

CustomTrick (src/features/custom-tricks/model/custom-trick.ts): note
this domain currently has NO timestamp field at all, not even
createdAt - createCustomTrick(id, validatedDraft) takes no time
parameter. The task only asks for updatedAt, so don't add createdAt too
(that would be scope creep beyond what's asked and what the exit criteria
test for). Add "readonly updatedAt: number" to CustomTrickBase. Give
createCustomTrick a third optional param updatedAt: number = Date.now().
Both CustomTrickProvider call sites (addCustomTrick AND
updateCustomTrick) already call createCustomTrick(id, validation.value)
and rebuild the whole trick object on edit (there's no partial-patch path
here) - leaving the default in place means both create and edit naturally
stamp a fresh Date.now(), which is exactly "set on creation, advances on
every edit."

UserProfile (src/features/profile/model/user-profile.ts): this is the
one genuinely different case and the main source of risk in this ticket.
Unlike Note/Goal/CustomTrick (each mutation dispatches a whole freshly-built
record), userProfileReducer has ~13 action variants that each patch one
field of a single long-lived document, and the timestamp-setting call sites
are scattered across ~13 different useCallbacks in
user-profile-provider.tsx, not centralized. Repeating "updatedAt:
Date.now()" at every one of those dispatch call sites would be exactly the
kind of mechanical duplication this codebase avoids elsewhere. Instead:

- Add "readonly updatedAt?: number" to UserProfile - OPTIONAL, not
  required. INITIAL_USER_PROFILE has no meaningful "last modified" instant
  before the user has touched anything, and other lifecycle-only fields on
  this type (kenteiRank, lastSesh, etc.) are already optional for the
  same reason. It becomes present the first time any reducer branch
  actually changes state post-hydration.
- Split UserProfileAction's existing variants out into an unexported
  UserProfileActionPayload union (today's variants, unchanged), then
  define "export type UserProfileAction = UserProfileActionPayload &
  { readonly updatedAt: number }". This makes the timestamp a mandatory,
  uniform field on every dispatched action without touching each variant
  individually.
- In userProfileReducer, every case that currently returns a NEW object
  (i.e., every case except the no-op branches that return state unchanged,
  e.g. selectedTricksCleared when already empty, kenteiRankAdvanced when
  the rank is unchanged) adds "updatedAt: action.updatedAt" to its returned
  object. Leave the true no-op branches alone - an edit that changes
  nothing shouldn't bump the stamp, matching the existing no-op-safe
  design already present in these reducers. profileRestored needs no
  change: it just returns action.profile as-is, which already carries its
  own updatedAt (or doesn't, if it's a never-touched restored profile).
- In user-profile-provider.tsx, add one wrapper - e.g. "const
  dispatchWithTimestamp = useCallback((payload: UserProfileActionPayload) =>
  dispatch({ ...payload, updatedAt: Date.now() }), [dispatch])" - and switch
  every one of the ~13 action-creator callbacks to call it instead of
  dispatch directly. This is the single Date.now() call site for the
  whole domain, consistent with AGENTS.md's "keep Date.now() calls
  outside pure logic" convention, and it means only one line changes if the
  timestamp strategy ever needs to change later.
- createRestoreAction (passed to useIdentityScopedDomain, used both for
  local-storage hydration and the sync layer's pull-adopt path) builds a
  profileRestored action directly, bypassing the wrapper - since
  UserProfileAction now requires updatedAt on every variant including
  this one, supply "updatedAt: value.updatedAt ?? 0" (or similar) there; the
  reducer ignores it for this branch anyway (profileRestored returns
  action.profile verbatim), so the exact value is inert, just needs to
  type-check.

Critical trap - profile-cloud-mapping.ts's scalar-field diff.
diffProfileForOutboxOperations decides whether to emit a profile-row
upsert by comparing ProfileScalarFields (type ProfileScalarFields =
Omit<UserProfile, 'selectedTrickIds' | 'manuallyUnlockedTrickIds'>) via
JSON.stringify(a) === JSON.stringify(b). If updatedAt is left inside
ProfileScalarFields and the reducer bumps it on EVERY mutation
(including trick-selection-only actions, which don't otherwise touch scalar
fields), scalarFieldsEqual would see a "change" on every single profile
mutation and emit a spurious profile-row upsert even when no scalar field
actually changed - unlike Note/Goal/CustomTrick, where the diff functions
compare the WHOLE record via JSON.stringify and so already, correctly,
treat an updatedAt-only difference as "this record changed" (this is
existing, intentional behavior for notes today - verify it, don't "fix"
it). Profile's diff is different because it's a deliberately SPLIT
comparison. Fix: exclude updatedAt explicitly - "type ProfileScalarFields
= Omit<UserProfile, 'selectedTrickIds' | 'manuallyUnlockedTrickIds' |
'updatedAt'>". mapUserProfileToProfileUpsertInput already omits
updated_at from its return value (server-owned, per its own comment), so
this exclusion is consistent with what that function already does -
updatedAt simply never participates in outbox-diffing or the upsert
payload, exactly like created_at/revision already don't.

## Order rationale

Models before persistence validators before providers before cloud mapping:
persistence validators import types from the model files, providers call
the model's create/edit functions (need the new params to exist first), and
cloud mapping imports both the model types and the persistence file's
isNormalizedText/helper functions. Goals and custom-tricks are
independent of each other and of profile, so they can be done in any
relative order or even interleaved - profile is the one to do last given
its higher blast radius (touches ~13 dispatch call sites and the
scalar-field diff trap).

## Things that do NOT need to change

- No Supabase migration - confirmed above.
- No changes to note.ts/notes anywhere - it's the reference, not a target.
- No createdAt added to CustomTrick - out of scope per the task text.
- mapGoalToInsertInput/mapCustomTrickToUpsertInput/
  mapUserProfileToProfileUpsertInput - all three already omit
  server-owned timestamp columns from their return shapes; no change needed
  there, only in the row->domain read direction.
- The sync/conflict layer (src/shared/sync/) is revision-based, not
  timestamp-based (confirmed by grep - no domain updatedAt references
  there); this ticket's "survives ... the revision-guarded update path"
  exit criterion is about not breaking existing revision handling while
  adding the new field, not about wiring updatedAt into conflict
  resolution itself.
