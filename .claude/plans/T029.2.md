## Scope decision (resolve explicitly, matches the task's own wording)

The task title says "skip the countdown **between** assessment tricks," and
the Notes describe the mechanism as "`MultiTrickSesh` seeds each trick by
**dispatching** `trickSelected`." That description is only true for two of
the three places a trick gets seeded in `multi-trick-sesh.tsx`:

1. **Initial mount** (`useReducer(seshReducer, sequence, initializer)`,
   lines ~81-88) — constructs the first trick's `'countdown'` state
   directly via the lazy initializer function. This is *not* a dispatch.
2. **Post-completion effect** (inside the `useEffect` at line ~110, the
   `dispatch({ type: 'trickSelected', ... })` call at line ~125) — fires
   after a trick's sesh reaches `'completed'` and advances the sequence.
3. **`handleSkipRank`** (line ~145, the `dispatch({ type: 'trickSelected',
   ... })` call at line ~153) — fires when the user presses "Skip this
   rank."

Only (2) and (3) literally match the Notes' description, and both are
transitions *between* tricks — the first trick's own countdown (case 1,
the "get ready" beat before the whole run starts) is out of scope. This
plan does not touch the `useReducer` initializer. If in-browser
verification suggests the very-first-trick countdown should also be
skipped for assessments, that's a product call to raise with the user
before expanding scope — don't fold it in silently.

## Implementation steps

1. **`src/features/sesh/model/sesh.ts`** — no changes. The reducer's state
   graph stays exactly as-is, per the task's Notes. Confirm this after
   reading the file (already verified during planning: `countdownCompleted`
   only transitions `'countdown' -> 'active'`, gated on `state.status ===
   'countdown'`, so dispatching it immediately after `trickSelected`
   is a no-op unless the preceding dispatch actually landed in
   `'countdown'` — safe to always pair the two).

2. **`src/features/sesh/components/multi-trick-sesh.tsx`** — the only
   production file that changes.
   - Add a new optional prop to `MultiTrickSeshProps`, e.g.
     `readonly skipCountdownBetweenTricks?: boolean;` — name it precisely
     enough that a reader doesn't assume it also covers the first trick's
     countdown (mirror the doc-comment style already used for
     `advanceOnFirstLace`/`endActionLabel`: explain what it does
     mechanically, not "when true, this is an assessment").
   - Destructure it in the component's props list.
   - Introduce one small local helper inside the component that both
     existing `trickSelected` dispatch sites call through, instead of
     duplicating the paired-dispatch logic twice:
     ```ts
     const seedNextTrick = (trick: PracticeTrick) => {
       dispatch({ type: 'trickSelected', trick, plan });
       if (skipCountdownBetweenTricks) {
         dispatch({ type: 'countdownCompleted', now: Date.now() });
       }
     };
     ```
     This relies on the same "multiple synchronous `dispatch` calls to a
     `useReducer` fold in order against the queued state, not the stale
     render closure" behavior the codebase already leans on for
     `advanceOnFirstLace` (`handleLaced` dispatches `trickLaced` then
     `seshEnded` back-to-back at lines ~172-178) — not a new risk, just
     the same trick reused.
   - Replace the effect's `dispatch({ type: 'trickSelected', trick:
     nextTrick, plan })` (line ~125) with `seedNextTrick(nextTrick)`.
   - Replace `handleSkipRank`'s `dispatch({ type: 'trickSelected', trick:
     nextTrick, plan })` (line ~153) with `seedNextTrick(nextTrick)`. (Its
     `else` branch, `dispatch({ type: 'seshReset' })`, is unrelated and
     stays as-is.)
   - Do not touch the `useReducer` initializer (mount-time seeding of the
     first trick) — see the scope decision above.

3. **`src/features/sesh/components/assessment-entry.tsx`** — one-line

## Order and why

Steps 2 -> 3 -> 4 in that order: the reducer stays untouched (no ordering
concern there), `multi-trick-sesh.tsx`'s prop and dispatch-pairing logic
has to exist before `assessment-entry.tsx` can pass it, and both need to
exist before the new tests can assert on the resulting behavior. The
merge in the pre-step must happen before any of this — editing
`assessment-entry.tsx` on the stale base would either silently drop
`endActionLabel` or produce an avoidable merge conflict later.

## Risks / non-obvious things

- **Double-dispatch ordering**: confirmed safe by precedent
  (`advanceOnFirstLace`'s `handleLaced` already dispatches twice
  synchronously and this ships in production), but worth re-verifying
  with the new test rather than assuming — `useReducer`'s queued-dispatch
  semantics are the kind of thing worth a passing test rather than a
  comment alone.
- **Scope boundary on the first trick's countdown**: documented above.
  Get this right in the PR description / TASKS_DONE notes even if the
  in-browser check ends up feeling like "shouldn't the very first one
  also skip?" — that's a separate, larger change (touches the
  `useReducer` initializer, which currently can't use `Date.now()` inside
  a lazy initializer the same way `countdownCompleted`'s dispatch path
  does) and should be raised as a follow-up, not folded in.
- **`skipTarget`'s interaction**: `handleSkipRank`'s `else` branch
  (`seshReset` when there's no next trick) is unaffected, but double-check
  after wiring `seedNextTrick` that the `if (!skipTarget) return;` early
  return at the top of `handleSkipRank` still reads correctly — it does,
  it's unrelated to this change.
