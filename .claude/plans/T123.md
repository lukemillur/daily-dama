# T123 plan — looping Big Cup hero (T123.1 + T123.2)

Umbrella task; this plan covers both children in the order they must be
built. T123.1 must land before T123.2 (T123.2 imports the scene T123.1
builds).

## Current state (read before starting)

- `LandingHero` (`src/features/landing/components/landing-hero.tsx`) is a
  hand-drawn `react-native-svg` illustration inside a `HeroPanel` sticker
  container (`testID="landing-hero"`, `paperStrong` background, `ink`
  border, box-shadow). It's the first thing rendered in
  `landing-page.tsx`'s `<Content>`.
- `TrickScene` (`src/features/trick-viz/components/TrickScene.tsx`) has
  no loop. `elapsed.current` clamps at `trick.durationSeconds` and just
  sits there; playback only restarts via the `replay()` handle exposed to
  `children`, which bumps a `playToken` -> `runToken` string that
  `TrickBodies`/`CameraRig`/`KendamaString` all watch to reset without
  remounting `<Canvas>` (remounting loses the WebGL context - handoff
  section 12 trap 1). Building a loop means driving that same
  `replay()`-style reset automatically instead of only on button press.
- The dev sandbox is `src/app/app/stats/trick-viz-sandbox.tsx` (note the
  nested `app/app/stats` path, not `app/stats` as the handoff doc's older
  paths suggest), gated by `if (!__DEV__) return <Redirect href="/app/home" />`.
  There is no `localStorage` profile-flag gate actually in the code
  despite handoff section 12 item 10 describing one - the doc is stale on
  this one point. Doesn't block anything (still dev-only via `__DEV__`);
  don't spend time trying to satisfy a gate that isn't there, and don't
  add one.
- `bigCup` (`src/features/trick-viz/model/tricks/cupCatches.ts`) starts
  hanging and ends caught-in-cup - not the same pose, so any loop restart
  is at minimum a soft discontinuity. Notes already resolve this: hard cut
  or eased rewind, implementer's call, just not jarring/broken.
- No existing r3f component (`Ken`, `Tama`, `TrickScene`, `String`) has a
  unit test - only the pure geometry/timeline modules do (85 tests).
  Visual sandbox inspection is the established verification method for
  the 3D components themselves; keep following that rather than
  inventing component-level jest coverage for the new 3D pieces.
- `jest.config` (`package.json`) uses the `jest-expo` preset, which runs
  under React Native's test environment, not jsdom - there is no
  `document` or real `<canvas>`/WebGL available under `yarn test`. Any
  new code that renders an r3f `<Canvas>` must be mocked out in tests
  that mount it, the same way `landing-page.test.tsx` already mocks
  `expo-image`.
- `eslint.config.js` scopes the `react/no-unknown-property` override
  (r3f's JSX intrinsics like `<group>`, `<ambientLight>`) to
  `src/features/trick-viz/**/*.tsx` only. Keep all raw r3f JSX inside
  that directory; `landing-hero.tsx` should only ever import and render
  a finished component, never write r3f JSX itself.
- No SSR/`typeof window` guards exist anywhere in this codebase today.
  Web export uses `"output": "static"` in `app.json`, which prerenders
  routes at build time in Node - `document` will not exist during that
  pass. This matters directly for T123.2's WebGL-detection code.
- `@react-three/drei` (`^10.7.8`) is already a dependency and pulls in
  `troika-three-text` transitively (confirmed in `yarn.lock`) - drei's
  `<Text>` is available with no new `package.json` entry. Its default
  font is fetched from a CDN at runtime unless a `font` prop is
  supplied. There is no bundled font asset infrastructure anywhere in
  this app today (fonts are all system/CSS-variable fonts in
  `global.css`); this is new ground.

## T123.1 — build and validate the looping hero scene in the sandbox

1. Add a `loop` capability to `TrickScene` (`TrickScene.tsx`).
   - New prop `loop?: boolean` (default `false`) so every existing call
     site (the sandbox's normal scrubber view) is unaffected by default.
   - Implementation: in `TrickBodies`'s `useFrame`, when `loop` is true
     and `scrub === null && isPlaying` and `elapsed.current` reaches
     `trick.durationSeconds`, don't just clamp - hold there briefly
     (recommend ~0.4-0.6s at the caught pose, since Big Cup's end state
     is a held catch, not a hang) and then trigger the same reset
     `replay()` already does: bump `playToken` so `runToken` changes,
     which `TrickBodies`, `CameraRig`, and `KendamaString` all already
     watch to reset cleanly without remounting `<Canvas>`. Do not build
     a separate eased-rewind path - a hard cut with a short hold is
     simpler, satisfies "not jarring," and reuses machinery that's
     already proven correct (the manual Replay button).
   - Concretely: this needs a way for the child (`TrickBodies`, which
     currently returns `null` and only writes refs) to tell the parent
     `TrickScene` to bump `playToken`. Simplest shape: keep the "elapsed
     reached duration" detection inside `TrickBodies`'s `useFrame` (it
     already owns `elapsed`/`timeRef`), and pass an `onLoopComplete?: ()
     => void` callback down only when `loop` is true, called once per
     boundary crossing (guard with a ref flag so it fires once, not
     every frame after the threshold). Calling a state setter from
     inside `useFrame` is fine (it's not render), but confirm the
     `react-hooks/refs` / `react-hooks/immutability` lint rules (handoff
     section 12 trap 8) are happy with the guard-ref pattern - model it
     on the existing `lastRunToken` ref guard already in the same
     function.
   - Do not touch `CameraRig`, `frameSubjects`, or `viewDirectionFor`.
     They're validated and documented as fragile (handoff sections 10
     and 16); the loop only needs to affect the clock/reset, not
     framing.
   - Manually re-verify the existing sandbox scrubber/Replay/free-look
     flow still behaves identically after this change (loop defaults
     off).

2. Spike the 3D text approach first - this is the single highest-risk,
   least-precedented piece, so do it before building the rest of the
   scene around a choice that might not pan out.
   - Try drei's `<Text>` (troika-three-text, already available) with an
     explicit `font` prop pointing at a locally bundled font file rather
     than accepting troika's default CDN font fetch - a production
     landing page shouldn't depend on an external CDN round-trip for a
     decorative wordmark, and a flaky/blocked fetch there is a new
     failure mode this page doesn't have today.
   - Pick one open-license (OFL or similar) display/sans font file, add
     it under a new `assets/fonts/` directory, and resolve a loadable
     URL for it. Since this app is web-only in active scope, the
     pragmatic path is Expo Router web's `public/` directory (files
     there are copied to the export root and served at a stable path) -
     verify this convention works in this Expo/Router version before
     committing to it; if it doesn't behave as expected, fall back to
     `expo-asset`'s `Asset.fromModule(require(...)).uri` pattern, which
     works for both web and native.
   - If bundling a font turns into real yak-shaving, it is an
     acceptable fallback to use troika's default font for T123.1's
     sandbox-only validation and revisit self-hosting during T123.2
     (when the production stakes are higher) - but decide and document
     the choice either way, per the task Notes ("note the choice and
     its bundle-size cost in the commit").
   - Whichever way it resolves, do not read/write `document` or trigger
     network fetches from component render - do it the way
     three.js/troika already expects, driven by the `font` prop.

3. Place the text so it survives the follow camera. `CameraRig` reframes
   every frame based only on ken/tama positions (`frameSubjects`); a
   text mesh at a fixed world position will drift in and out of frame as
   the shot pans. Instead, make the caption camera-relative: a small
   component (e.g. `src/features/trick-viz/components/HeroCaption.tsx`)
   that reads `useThree((s) => s.camera)` and, in its own `useFrame`,
   sets its own `position`/`quaternion` to sit at a fixed offset in
   front of and below the camera each frame (a standard "3D HUD"
   technique). This keeps `CameraRig`/`frameSubjects`/`viewDirectionFor`
   completely untouched.

4. Compose the scene: new
   `src/features/trick-viz/components/LoopingHeroScene.tsx` - a thin
   wrapper rendering `<TrickScene trick={bigCup} loop followAction
   speed={...}>` with no `canvasExtras` (no `OrbitControls` - decorative
   only, no drag/orbit/tap per the resolved product decision) and
   `<HeroCaption />` as a Canvas child. Export it for both sandbox use
   (this step) and landing-page use (T123.2). `bigCup` comes from
   `src/features/trick-viz/model/tricks/cupCatches.ts` (or via
   `TRICK_VISUALIZATIONS` if that lookup is preferred for consistency -
   either is fine, `bigCup` is already exported directly).

5. Wire an isolated preview into the existing sandbox rather than a new
   route - add a toggle chip (e.g. "Hero loop") to
   `src/app/app/stats/trick-viz-sandbox.tsx`'s HUD that swaps the normal
   `TrickScene` + scrubber view for `<LoopingHeroScene />`, so it can be
   watched looping continuously in isolation before any landing-page
   wiring, per the task description. Keep the existing `__DEV__` gate
   as the access control (see "current state" above - no other gate is
   actually wired up).

6. Verify. `yarn test --runInBand`, `yarn lint`, `yarn tsc --noEmit`.
   Then in-browser, in a fresh tab (handoff section 12 trap 5 - stale
   console buffers survive HMR reloads and read as live bugs): watch at
   least 2-3 full loop cycles of the sandbox's hero-loop mode with
   devtools console open, confirming no `THREE.WebGLRenderer: Context
   Lost`, no crash/freeze, and that "Daily Dama" is legible, positioned
   inside frame, and rendered as part of the 3D scene (not an HTML
   overlay).

## T123.2 — wire into the landing page with a WebGL fallback

Depends on T123.1 landing first.

1. Add a WebGL-availability check. New pure utility, e.g.
   `src/features/landing/utils/webgl-availability.ts`, exporting
   `isWebGLAvailable(): boolean`:
   - Returns `false` immediately if `typeof document === 'undefined'`
     (covers the static-export SSR/build-time pass, where there is no
     `document` at all).
   - Otherwise, try/catch: create a canvas element, attempt
     `getContext('webgl2')`, then `getContext('webgl')`, then
     `getContext('experimental-webgl')`; return `true` if any succeed,
     `false` on failure or thrown error.
   - Unit-test this directly (mock `document.createElement`) - covers
     the "feature-detection unit test" option the exit criteria
     explicitly allows in lieu of a manual devtools WebGL-disable check.

2. Capture a static fallback image. Using the sandbox's hero-loop mode
   from T123.1, screenshot a good frame of Big Cup mid-catch with the
   "Daily Dama" text visible, and save it under `assets/images/landing/`
   (mirrors the T117.1 screenshot-capture precedent already used for the
   platform screenshot showcase).

3. Update `landing-hero.tsx`.
   - Keep the outer `HeroPanel`/`testID="landing-hero"` wrapper stable
     across both branches (existing test asserts on that testID; new
     tests should too).
   - Client-only, hydration-safe gating: `const [webglOk, setWebglOk] =
     useState<boolean | null>(null)` with `useEffect(() =>
     setWebglOk(isWebGLAvailable()), [])`. While `webglOk` is `null`
     (SSR and the very first client render, before the effect runs) or
     `false`, render the static fallback `<Image>` (same `expo-image`
     pattern as `landing-photo.tsx`). Once `webglOk` is `true`, render
     `<LoopingHeroScene />` inside a sized wrapper. This mirrors the
     project's existing hydration-skip convention (AGENTS.md: "wait for
     hydration and skip the first persistence effect" - same shape,
     applied here to avoid a client/server render mismatch instead of
     an empty initial store).
   - Size/frame the wrapper so the scene fits the same visual role the
     SVG hero had (roughly the same panel proportions), then check
     mobile widths for overlap.

4. Check layout at mobile widths. At <=480px, confirm the new hero
   doesn't overlap "Why Daily Dama" or any other text below it (the SVG
   hero didn't have this problem structurally, but a canvas with
   different intrinsic proportions might need explicit
   `aspectRatio`/`maxHeight` tuning). Also check a desktop viewport
   frames correctly. Both are manual dev-server checks
   (`preview_start`/`expo start --web`), not automatable.

5. Update tests.
   - `landing-page.test.tsx`'s existing "renders the hero banner"
     assertion (`testID: 'landing-hero'`) must keep passing. Since
     `jest-expo` has no real `document`/canvas, mock out the heavy 3D
     path in this test file - either mock
     `@/features/trick-viz/components/LoopingHeroScene` directly
     (simplest, matches the existing `expo-image` mock style) or mock
     `isWebGLAvailable` to force a deterministic branch. Prefer mocking
     `LoopingHeroScene` so the test doesn't accidentally depend on
     `TrickScene`/r3f internals at all.
   - Add/extend a `landing-hero.test.tsx` (new, colocated with the
     other landing component tests) covering: WebGL available -> scene
     branch renders; WebGL unavailable -> fallback image renders;
     initial/SSR state (before the effect resolves) -> fallback image
     renders (i.e. no hydration-mismatch-prone default of `true`).

6. Verify. `yarn test --runInBand`, `yarn lint`, `yarn tsc --noEmit`,
   then `yarn expo export --platform web --output-dir
   /tmp/daily-dama-web-export` - confirm the export succeeds without a
   `document`-related SSR error (the highest-risk failure mode here,
   since nothing in this codebase has exercised a browser-only API
   during the static-export render pass before) and sanity-check the
   bundle-size delta the Notes call out, since this is the first time
   the WebGL/`react-three-fiber` stack loads unconditionally for every
   landing-page visitor.

7. Manually load `/` at a mobile viewport (<=480px) and a desktop
   viewport in-browser and confirm the exit criteria directly; force
   the fallback path (devtools WebGL disable, or temporarily hardcode
   `isWebGLAvailable`'s return) and confirm the static image renders
   cleanly with no blank/broken state.

## Risk callouts (don't rediscover these)

- Never remount `<Canvas>` to reset playback - always drive resets
  through `runToken`/`playToken`, as the existing `replay()` mechanism
  already does (handoff section 12 trap 1).
- Keep any new plain helper functions in non-component modules - React
  Compiler throws `ReferenceError: not defined` at runtime for
  module-scope helpers defined inside a component file, invisible to
  `tsc` (handoff section 12 trap 2).
- All raw r3f JSX (`<group>`, `<Text>`, etc.) stays inside
  `src/features/trick-viz/components/**`, which is the only glob
  `eslint.config.js` exempts from `react/no-unknown-property`.
- Don't touch `CameraRig`, `frameSubjects`, or `viewDirectionFor` -
  position the caption text relative to the camera transform every
  frame instead of fighting the follow-camera's own reframing.
- `yarn test` runs under `jest-expo`'s RN test environment, not jsdom -
  there is no `document`/WebGL. Any test that mounts a component
  containing `<Canvas>` will fail unless that piece is mocked.
- The static web export prerenders in Node at build time - no
  `document` exists then either. Guard WebGL detection accordingly
  (return `false` when `document` is undefined) and only branch to the
  real 3D scene from a post-mount `useEffect`, not from initial render
  state, to avoid a hydration mismatch.
- Font loading for the 3D text is the step most likely to eat unplanned
  time - spike it early (T123.1 step 2) rather than discovering the
  bundling mechanics after everything else is built around it.
