## Plan

### 1. Fix the Jest asset-resolution gap first (blocks everything else)

Edit `package.json`'s `jest.moduleNameMapper` to add an entry for `@/assets/*` ahead of the general `@/*` rule, mirroring `tsconfig.json`:

```json
"moduleNameMapper": {
  "^@/assets/(.*)$": "<rootDir>/assets/$1",
  "^@/(.*)$": "<rootDir>/src/$1"
}
```

Do this before writing any component code that requires an asset under test. Confirm with a quick `yarn jest src/app/__tests__/index.test.tsx` once the `Image`s are added in step 4.

### 2. Decide and create the asset location

Add a new directory `assets/images/landing/` (mirrors the existing `assets/images/tabIcons/` convention) holding the four PNGs:
- `home-screen.png`
- `sesh-first-lace.png`
- `custom-trick-form.png`
- `trick-goals.png`

Capture screenshots at a mobile viewport (375x812 is a reasonable default -- iPhone-ish, comfortably inside the 320-375px band `AGENTS.md` already treats as the mobile-web convention) so the images themselves read as "phone app" screenshots, not desktop-web captures. Crop each PNG tightly to the app's visible content area (drop browser chrome/OS chrome) before saving. Keep file sizes reasonable (PNG compression / reasonable dimensions, e.g. downscale to ~750px wide @2x) since these ship in the static web export -- this is a landing page, initial load weight matters.

### 3. Capture the four screenshots against seeded, realistic data

Run `yarn expo start --web` (per `AGENTS.md`, use the dev server, not the static export, for browser verification) on an explicit port. Use whatever browser automation/screenshot tool is available in this environment (the same one used for the existing 320px nav-fit checks elsewhere in this project) to drive the flows below. Seed `localStorage` via the browser tool's JS-eval capability (`window.localStorage.setItem(key, JSON.stringify(doc))`) before each reload -- this is simpler and less error-prone than a build-time fixture script, and these are hand-verifiable JSON shapes per the schemas above.

## Risks / non-obvious things to flag

- The Jest `moduleNameMapper` gap (step 1) is the single biggest landmine -- easy to miss since it's invisible until a tested component requires a `@/assets/*` path for the first time. Fix it before writing the `Image` usages, not after chasing a confusing "Cannot find module" failure.
- The first-lace banner is genuinely not persistable/seedable -- resist the temptation to hack it via storage (e.g. trying to fabricate a `landings.length===1` state some other way). It only exists as transient component state produced by a real interaction sequence; plan around driving it live, exactly once, per section 3c.
- Streak/momentum sections in `DailyHome` may depend on session recency relative to "now" (`summaryNow`/`liveClock` in `src/app/app/home.tsx`) -- seeded timestamps that are too old could render a broken-looking streak of 0 or stale "days ago" copy that undercuts the "core practice loop" screenshot goal. Check `src/features/home/model/home-summary.ts`'s streak/momentum derivation before finalizing fixture timestamps, and prefer timestamps within the last 1-2 days plus some older days behind them for a numeric streak.
- Keep the seeded localStorage fixtures out of any committed test/fixture files -- this is a manual, one-off capture aid via the browser tool's console/eval, not new application code or persisted test infrastructure. Only the four PNGs and the landing-page/test/jest-config edits should end up in the diff.
- Downstream tasks (T112.4/5/6) also touch `landing-page.tsx` -- keep this change additive and localized (new section, not a restructure of the existing layout) to minimize merge friction with sibling in-flight work on the same file.
