## Current shapes (read, not re-derived)

Domain (`src/features/stats/model/practice-history.ts`):

```ts
export type PracticeSessionOrigin = 'assessment';

export interface PracticeSessionRecord {
  readonly id: string;
  readonly trickId: string;
  readonly trickName: string;
  readonly startedAt: number;
  readonly completedAt: number;
  readonly durationMs: number;
  readonly laceCount: number;
  readonly plannedDurationMs?: number; // set only for eligible timed attempts
  readonly origin?: PracticeSessionOrigin; // set only for Kentei-assessment sessions
}
```

There is **no explicit `kind` discriminant**. "Timed / open-ended / assessment"
from the task description are just the three interesting *test* shapes, not a
union tag:
- open-ended: `plannedDurationMs` absent, `origin` absent.
- timed: `plannedDurationMs` present, `origin` absent.
- assessment: `origin === 'assessment'`, `plannedDurationMs` may or may not be
  present (assessment entries record via `sesh.tsx`/`assessment-entry.tsx`,
  which don't force a timed plan) — write the assessment round-trip fixture
  without `plannedDurationMs` to keep it a distinct case from "timed".

Row (`src/shared/supabase/database-types.ts`, `api.practice_sessions`):

```ts
Row: {
  completed_at: number
  created_at: string        // server-owned receipt timestamp (timestamptz)
  duration_ms: number
  id: string
  lace_count: number
  origin: string | null
  planned_duration_ms: number | null
  started_at: number
  trick_id: string
  trick_name: string
  user_id: string

Insert: { ...same, created_at?: string, ... }
```

Repository types already exist:
`PracticeSessionRow = Database['api']['Tables']['practice_sessions']['Row']`,
`PracticeSessionInsert = TablesInsert<{ schema: 'api' }, 'practice_sessions'>`,
both exported from `practice-history-cloud-repository.ts`.

Migration CHECK constraints (`supabase/migrations/20260822200050_...sql`),
which define what "malformed" means for the row→domain read boundary:

- `practice_sessions_id_not_blank`: `length(id) > 0`
- `practice_sessions_trick_id_not_blank`: `length(trick_id) > 0`
- `practice_sessions_trick_name_shape`: `length(trick_name) > 0 and trick_name = btrim(trick_name)`
- `practice_sessions_started_at_positive`: `started_at > 0`
- `practice_sessions_completed_not_before_started`: `completed_at >= started_at`
- `practice_sessions_duration_matches_timing`: `duration_ms = completed_at - started_at` (**see caveat below**)
- `practice_sessions_lace_count_nonnegative`: `lace_count >= 0`
- `practice_sessions_planned_duration_positive`: `planned_duration_ms is null or planned_duration_ms > 0`
- `practice_sessions_origin_known`: `origin is null or origin = 'assessment'`
- primary key `(user_id, id)`; RLS: `select`/`insert` only, no update/delete grant at all (immutability is enforced by the database itself, not just by this app's mapping layer).

## Known schema/domain mismatch — flag, don't silently paper over

`sesh.tsx`/`sesh.ts`'s reducer supports **pausing** an active session
(`pausedAt`/`pausedDurationMs`), and `createPracticeSessionRecord` computes
`durationMs = endedAt - startedAt - totalPausedMs`. This is real, shipped,
user-facing behavior (auto-pause-after-lace in multi-trick mode), not dead
code. So a legitimately-recorded local session can have
`durationMs < completedAt - startedAt`. The local storage validator in
`practice-history-persistence.ts` already reflects this
(`durationMs <= completedAt - startedAt`, comment: "active practice time...
can be less than wall-clock elapsed time when a session was paused").

The T155.3 migration's `practice_sessions_duration_matches_timing` CHECK uses
**exact equality**, not `<=`. That's stricter than the actual domain
invariant and would reject a genuinely-valid paused session's insert once
T157.6 wires real writes.

Resolution for this ticket: implement the row→domain "malformed timing"
validation using the **permissive, domain-correct** invariant
(`durationMs <= completedAt - startedAt`, matching local storage validation),
not the DB's stricter equality — this mapping layer's job is to correctly
recognize what the domain model considers valid, not to re-derive the DB's
current (arguably buggy) constraint. Do not attempt to fix the migration in
this ticket — it's a schema change outside T155.12's stated scope and would
need its own planning per AGENTS.md's persistence-domain-boundary rule.
**Leave a comment in the mapping file pointing at this gap explicitly**
(reference `practice_sessions_duration_matches_timing` by name) so whoever
picks up T157.6 doesn't rediscover it the hard way when paused-session sync
starts failing inserts. Do not add a TASKS.md entry for it unless the user
asks — flag it in this plan and in code comments; that's sufficient for now.

## Mapping file design (`practice-history-cloud-mapping.ts`)

Header comment: same two-paragraph shape as T155.10/11 (does NOT wire into
provider/sync; row→domain is a Result type because rows are an untrusted
runtime boundary even though already successfully fetched; domain→row is a
total pure function because `PracticeSessionRecord` is already
reducer-trusted by the time anything calls these mappers). Add a third
paragraph naming the duration-equality caveat above.

```ts
export type PracticeSessionMappingIssueReason =
  | 'wrongType'
  | 'outOfRange'
  | 'malformedShape'
  | 'foreignUser'
  | 'duplicateId'
  | 'invariantViolation';

export interface PracticeSessionMappingIssue {
  readonly path: string;
  readonly reason: PracticeSessionMappingIssueReason;
  readonly message: string;
}

export type PracticeSessionRowMappingResult =
  | { readonly status: 'invalid'; readonly issues: readonly PracticeSessionMappingIssue[] }
  | { readonly status: 'valid'; readonly session: PracticeSessionRecord };

export type PracticeHistoryRowsMappingResult =
  | { readonly status: 'invalid'; readonly issues: readonly PracticeSessionMappingIssue[] }
  | { readonly status: 'valid'; readonly history: PracticeHistory };
```

No `'absent'` status anywhere — like `custom_tricks`, this is a list domain
with no meaningful "row not created yet" singleton case. An empty row array
maps to `{ sessions: [] }` (`INITIAL_PRACTICE_HISTORY` shape), not an
`'absent'` variant.

### `mapPracticeSessionRowToDomainRecord(row, expectedUserId): PracticeSessionRowMappingResult`

Self-contained, never looks at sibling rows (batch-level duplicate check
lives in the collection mapper, same split as custom-tricks). Steps, in
order, treating every field as `unknown` off `row as unknown as
Record<string, unknown>`:

1. `user_id !== expectedUserId` → single `foreignUser` issue, short-circuit
   return immediately (matches custom-trick-cloud-mapping's early return for
   this case — it's the one check that doesn't participate in "collect all
   issues").
2. `id`: `typeof === 'string' && length > 0` → else `malformedShape`.
3. `trick_id`: `typeof === 'string' && length > 0` → else `malformedShape`.
4. `trick_name`: `typeof === 'string' && length > 0 && value === value.trim()`
   → else `malformedShape` (mirrors `trick_name_shape`'s `btrim` check).
5. `started_at`: use `isFiniteNonNegativeNumber` (imported from
   `practice-history-persistence.ts`) for the type/finiteness check
   (`wrongType` if it fails), then a separate `started_at > 0` check
   (`outOfRange` if `0`) — matches `practice_sessions_started_at_positive`
   exactly since that constraint is strictly `> 0`, unlike the more lenient
   local-storage validator's `>= 0`. This row-level check intentionally
   *does* track the DB's stricter constraint here (unlike duration_ms above)
   because there's no competing domain invariant that's more permissive —
   `startedAt` has always logically meant "a session started," and `0`/negative
   isn't a real epoch-ms timestamp for this app's era. Only the duration
   equality constraint is the one that's actually wrong relative to a real
   feature (pausing); say so in a code comment right at this check so the
   asymmetry reads as intentional, not inconsistent.
6. `completed_at`: `isFiniteNonNegativeNumber` (`wrongType`), then — only if
   both `started_at` and `completed_at` individually passed — `completed_at
   >= started_at` (`invariantViolation` if not).
7. `duration_ms`: `isFiniteNonNegativeNumber` (`wrongType`), then — only if
   `started_at`/`completed_at` both valid — `duration_ms <= completed_at -
   started_at` (`invariantViolation`; see the caveat section above for why
   `<=` not `===`).
8. `lace_count`: `Number.isInteger(value) && value >= 0` → else split into
   `wrongType` (not a number/not an integer) vs `outOfRange` (negative
   integer), matching the granularity custom-trick-cloud-mapping uses for
   `kentei_rank`.
9. `planned_duration_ms`: `null`/`undefined` → omit field. Else `typeof ===
   'number'` (`wrongType`) then `> 0` (`outOfRange`).
10. `origin`: `null`/`undefined` → omit field. Else `value === 'assessment'`
    (`malformedShape` otherwise — mirrors the profile mapper's
    enum-of-values malformedShape usage, not wrongType, since it's a valid
    string type but wrong value domain... actually match custom-trick's
    convention: an unrecognized-enum-member gets `malformedShape` there
    too — stay consistent).

Collect all issues (don't short-circuit past step 1) and return `invalid` if
any exist; otherwise build the `PracticeSessionRecord` object literal with
optional fields included only via the same
`...(value !== undefined ? { key: value } : {})` spread idiom
custom-trick-cloud-mapping and profile-cloud-mapping both use — never
`session.plannedDurationMs = undefined`.

### `mapPracticeSessionRowsToDomainHistory(rows, expectedUserId): PracticeHistoryRowsMappingResult`

Same shape as `mapCustomTrickRowsToDomainCollection`:
- Map each row via the single-row mapper, prefixing issue paths with
  `rows[${index}].`.
- Track `seenIds`/`duplicateIds` off the raw `row.id` (defensive, even
  though the DB's `(user_id, id)` primary key should make this unreachable
  for genuinely-fetched pages — worth keeping cheap and DB-independent per
  the same reasoning custom-tricks used).
- Any issues at all → `invalid` (no partial history — a partial Stats
  picture is worse than a loud failure, same reasoning as custom-tricks).
- Otherwise `{ status: 'valid', history: { sessions: mappedSessions } }`,
  preserving row input order exactly (do not re-sort). This is the
  "deterministic pagination identity" contract: the repository's `list()`
  already established the definitive `(completed_at desc, id asc)` order
  server-side; this mapper's job is to preserve that order and preserve each
  row's own `id` verbatim as the domain id (never regenerate it via
  `createPracticeSessionRecordId`) — that's what keeps a page boundary,
  cursor, and later dedup-by-id consistent between what the server returned
  and what the local reducer stores. Say this explicitly in a comment.

### `mapPracticeSessionRecordToInsertInput(session, userId): PracticeSessionInsert`

Total, pure, non-mutating — builds a fresh object literal, never spreads
`session` then mutates. Deliberately **omits `created_at` entirely** (not
even `?? null`) so the DB's `default now()` applies — this is the concrete
mechanism that makes "server receipt timestamps never replace client domain
timestamps" true by construction on the write path: this function has no way
to set `created_at` even if a caller wanted it to, and `started_at`/
`completed_at`/`duration_ms` map straight from the trusted domain record's
own client-fact fields, never touching `Date.now()` or anything row-shaped.

```ts
export function mapPracticeSessionRecordToInsertInput(
  session: PracticeSessionRecord,
  userId: string,
): PracticeSessionInsert {
  return {
    user_id: userId,
    id: session.id,
    trick_id: session.trickId,
    trick_name: session.trickName,
    started_at: session.startedAt,
    completed_at: session.completedAt,
    duration_ms: session.durationMs,
    lace_count: session.laceCount,
    planned_duration_ms: session.plannedDurationMs ?? null,
    origin: session.origin ?? null,
  };
}
```

### `mapPracticeHistoryToInsertInputs(history, userId): readonly PracticeSessionInsert[]`

Maps `history.sessions` in order via the single-record mapper, one insert
input per session. (Named `...InsertInputs`, not `...UpsertInputs` — this
table is insert-only, matching `insertMany`'s naming in the repository; don't
copy `Upsert` terminology from the custom-tricks/profile mappers, since that
would misrepresent this table's actual grants.)

## Test file (`practice-history-cloud-mapping.test.ts`)

Mirror `custom-trick-cloud-mapping.test.ts`'s structure: fixture builder +
`deepFreeze` + `expectRoundTrip` helper, then `describe` blocks.

Fixture builder:

```ts
function makePracticeSessionRow(overrides: Partial<PracticeSessionRow> = {}): PracticeSessionRow {
  return {
    user_id: USER_ID,
    id: 'session-1',
    trick_id: 'lighthouse',
    trick_name: 'Lighthouse',
    started_at: 1_000,
    completed_at: 5_000,
    duration_ms: 4_000,
    lace_count: 3,
    planned_duration_ms: null,
    origin: null,
    created_at: TIMESTAMP,
    ...overrides,
  };

```

### `describe('round-trip: domain -> row -> domain')`

- open-ended session, no `plannedDurationMs`, no `origin`.
- timed session with `plannedDurationMs` set.
- assessment session, `origin: 'assessment'`, no `plannedDurationMs`.
- assessment + timed combined (`origin: 'assessment'` and
  `plannedDurationMs` both set) — confirms these are independent optional
  fields, not a mutually-exclusive union.
- a **paused** session where `durationMs < completedAt - startedAt` (e.g.
  `startedAt: 1_000, completedAt: 10_000, durationMs: 4_000`) — this is the
  case that exercises the permissive-vs-DB-equality caveat directly; comment
  the test to say so.
- a whole `PracticeHistory` with multiple sessions, via
  `mapPracticeHistoryToInsertInputs` → build rows → `mapPracticeSessionRowsToDomainHistory`,
  asserting order is preserved.

### `describe('mapPracticeSessionRowToDomainRecord: malformed rows')`

- rejects `started_at: 0` (`outOfRange`).
- rejects negative `started_at`.
- rejects `completed_at < started_at` (`invariantViolation`).
- rejects `duration_ms > completed_at - started_at` (`invariantViolation`) —
  the case that *should* be rejected even under the permissive rule.
- accepts `duration_ms < completed_at - started_at` (paused case — covered
  above, but also assert directly here as a positive control alongside the
  negative ones).
- rejects non-integer `lace_count`.
- rejects negative `lace_count`.
- rejects `planned_duration_ms: 0` and negative (`outOfRange`).
- rejects `origin: 'something-else'` (`malformedShape`).
- rejects blank/empty `id`, `trick_id`, and untrimmed `trick_name`.
- rejects a row belonging to a different user (`foreignUser`), asserting
  it's the *only* issue returned (short-circuit, matching custom-trick's
  early-return convention).
- collects multiple simultaneous issues rather than failing fast (one row
  with e.g. both bad `lace_count` and bad `origin`).

### `describe('duplicate/foreign-user rejection (batch-level)')`

- rejects two rows in the same batch sharing the same `id`.
- rejects a batch where one row belongs to a different user, even if the
  rest are valid (whole-collection invalidation, not partial history).

### `describe('historical-name preservation')`

- maps a row whose `trick_name` no longer matches what a *hypothetical*
  current trick directory would say (there's no live trick lookup involved
  at all in this mapper — the test just asserts the row's `trick_name` value
  flows straight into `PracticeSessionRecord.trickName` unchanged, proving
  by construction that this mapper never resolves names via `trick_id`
  against any other source).

### `describe('server receipt timestamp vs client domain timestamps')`

- maps two rows that are identical except for wildly different `created_at`
  values (e.g. one `TIMESTAMP`, one a year later) but the same
  `started_at`/`completed_at`/`duration_ms`, and asserts both map to the
  **exact same** `PracticeSessionRecord` — proving `created_at` has zero
  influence on the mapped domain record's timing fields (in fact, on
  anything at all — `PracticeSessionRecord` has no `createdAt` field to
  even carry it).
- asserts `mapPracticeSessionRecordToInsertInput(...)`'s return value does
  **not** have a `created_at` key at all (`expect(insertInput).not.toHaveProperty('created_at')`),
  proving the write direction can't accidentally forward a client-supplied
  receipt timestamp either.

### `describe('no input mutation')`

- `mapPracticeSessionRecordToInsertInput`/`mapPracticeHistoryToInsertInputs`
  don't throw and don't mutate a `deepFreeze`d `PracticeSessionRecord`/
  `PracticeHistory` input.
- `mapPracticeSessionRowToDomainRecord`/`mapPracticeSessionRowsToDomainHistory`
  don't throw and don't mutate a `deepFreeze`d `PracticeSessionRow`/row-array
  input.

## Risks / non-obvious things to keep in mind

- The duration-equality DB constraint mismatch (above) is the main
  non-obvious finding. It doesn't block this ticket, but don't let it get
  silently "fixed" by tightening the mapper to match the DB instead —
  that would make the mapper reject genuinely valid paused sessions and
  contradict the local storage validator's own documented invariant.
- Keep `mapPracticeSessionRecordToInsertInput` a single-purpose, non-`Upsert`
  named function — this table has no update path at all, and reusing
  `Upsert` terminology from the other two mapping files would misdescribe
  the actual grants (`grant select, insert` only, per the migration).
- Don't add a `kind: 'timed' | 'open-ended' | 'assessment'` discriminant
  anywhere in the row or domain shape — that's not how the existing domain
  model represents these three cases, and inventing one here would diverge
  from `isEligibleTimedAttempt`/`selectRegularSessions`'s existing
  `plannedDurationMs`/`origin`-based logic for no benefit.
