## Design decisions for the new control

- Reuse the existing `ColorField` component for the text-color control (same swatch/hex-input/save/hint shape as background and accent) — satisfies "third `ColorField`-style control" and gives the live swatch preview for free, consistent with the existing two fields.
- Wire it to `themeTextColor` / `setThemeTextColor` directly (unlike background/accent, which share `setThemeColors(bg, accent)`, `setThemeTextColor` is already a standalone setter, so `onSave={(hex) => setThemeTextColor(hex)}`).
- "Can be reset independently": the existing `ResetButton` at the bottom clears background+accent only (`setThemeColors(undefined, undefined)`) — leave that behavior unchanged. Add a second, separate reset button scoped to text color only (`setThemeTextColor(undefined)`), disabled when `themeTextColor === undefined`. Do not fold text-color reset into the existing button — the task explicitly wants independent reset, and conflating them would silently clear a field the user didn't touch.
- Contrast copy: keep `contrastRatio`/`WCAG_AA_MIN_CONTRAST_RATIO` display as an informational note, not a blocking one. Drop `hasSufficientContrast` from `canSave` and from `FieldHint`'s `$invalid` styling (that should now key off `isValidHex` only). Rewrite the hint copy so it never reads as a rejection — e.g. always render `"Contrast vs. text: {ratio}:1. Recommended: {WCAG_AA_MIN_CONTRAST_RATIO}:1+."` when valid, and keep the existing invalid-hex-format message otherwise. Keep computing `ratio`/`contrastRatio` — still directly useful info — just make it non-blocking everywhere (including the new text-color field, which should show the same-style hint against the *other* resolved surface — see below).
- What does the text-color field's contrast hint compare against? Background/accent fields currently compare against the fixed `AppColors.ink` (the fixed pre-theming text color) — that reference is now stale/wrong for background and accent too once `themeTextColor` exists, but changing that reference for those two fields is out of scope here (task doesn't ask for it, and it's a separate correctness question about what "text" means once it's itself customizable). For the *new* text-color field specifically, comparing the candidate text color against the resolved background is the only sensible thing (comparing text-vs-text makes no sense). Use `themeBackgroundColor ?? AppColors.sage` (mirroring `resolveTheme`'s fallback) as the reference color for the text field's contrast hint. Do not import `resolveTheme` itself (it wants a full `ThemeColorPreferences` object and pulls in the "automatic" derivation which is irrelevant here); just inline the same fallback constant the way `resolveTheme` does.
- Leave `isValidThemeHexColor` and `maxLength={7}` reuse as-is; no new hex-validation logic needed.

     ```tsx

     ```

     ```tsx

     ```
     Rename the existing reset's label/copy only if needed for clarity (e.g. confirm "Reset to default" still reads as background/accent-only now that a second reset exists — consider relabeling it "Reset background & accent" so the two buttons are unambiguous; use judgment, but accessibilityLabel changes must be mirrored in the test file).
   - Extend `ColorField`'s props with `referenceColor: string` (replacing the hardcoded `AppColors.ink` reference) so background/accent calls pass `AppColors.ink` explicitly and the new text field passes `themeBackgroundColor ?? AppColors.sage`. This keeps behavior for the two existing fields identical while making the third field's hint meaningful.

## Order and rationale

Do the component change first (step 1), then update/extend the test file against the new component behavior (step 2) — the test file already encodes the *current* (soon-to-be-wrong) contrast-gating behavior, so editing it first would leave it inconsistent with itself mid-edit. There's no schema/provider work gating this — T085.1 already supplies everything needed — so this is a single-file-plus-its-test change with no ordering dependency beyond "component before its own tests."
