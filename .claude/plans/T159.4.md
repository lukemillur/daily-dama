# T159.4 — Let users choose profile preferences and resolve import conflicts

## Iteration boundary

Good enough for this ticket is a resumable, web-first existing-account guest-import decision flow. After T159.3 has classified the complete guest/cloud snapshots and uploaded safe records, the user can compare and choose guest or cloud profile/preferences, resolve each same-ID/different-payload import conflict independently, and resume after reload or a lost request. Accepted non-conflicting records continue to advance while conflicts are waiting; completion is impossible until the required profile choice and every required conflict choice are durably resolved.

This ticket does not finalize guest cleanup, switch identities, clear the guest namespace, add Realtime, change ordinary synchronization conflict behavior, or start mobile hardening. T159.5 owns final acknowledgement auditing and cleanup. T160.2’s `/app/profile/sync-conflicts` route remains a separate surface for ordinary signed-in sync envelopes; guest-import conflicts must not be inserted into those envelopes.

## Confirmed implementation context

- `TASKS.md` marks T159.4 in progress, with T159.3 as its prerequisite and T159.5 as the follow-up that owns final cleanup.
- `src/features/guest-import/model/guest-import.ts` already has `awaitingProfileChoice` and `conflicts` statuses, `profileComparison`, `GuestImportConflict`, durable operation progress, and guarded `profileChoiceMade` / `conflictsResolved` actions. The current `conflictsResolved` transition is unconditional, so it does not yet enforce unresolved-choice blocking.
- T159.3’s `planExistingAccountMerge` already produces canonical profile comparisons, accepted operations, deduplications, and independent conflict snapshots in deterministic domain/record order. `use-guest-import.ts` prepares that plan and persists it, but then calls `runEmptyGuestImport` for both target kinds; the existing path therefore needs a decision-aware runner and driver branch.
- Guest-import state is persisted through `useIdentityScopedDomain` and `guest-import-persistence.ts` under the identity-scoped account namespace. The v1 schema is explicitly provisional, so extend it in place and recover malformed/obsolete records to the existing empty state rather than adding migrations.
- `SYNC_DOMAINS` order is profile, customTricks, practiceHistory, goals, notes. Profile includes two distinct boundaries: trick-state union is handled by T159.3, while scalar/profile preferences are held for this ticket’s explicit choice.
- T160.2 provides reusable JSON-safe `ConflictSnapshot`, `isConflictSnapshot`, and deterministic conflict-key ideas, plus the requirement that one conflict must not stop sibling outbox operations. Reuse those value-level primitives where they fit; do not reuse its persisted envelope records, reducers, provider APIs, route, or resolution lifecycle.
- Profile preference fields are the client-owned scalar fields extracted by `extractScalarFields` (onboarding/rank/session/streak/theme preferences as defined by the current mapper). Server metadata and trick-state rows are not part of the guest/cloud scalar choice.
- Web is the only active platform. Do not launch mobile tooling or introduce native-specific implementation/configuration.

## Ordered implementation plan

1. **Define the durable decision model and invariants.**

   Extend the guest-import model with explicit, serializable facts for profile-choice resolution and per-conflict resolution. Preserve the existing comparison/conflict payloads and stable keys, but represent whether each required item is unresolved, keeping guest, or keeping cloud; keep guest/cloud decisions distinct from upload acknowledgement. Make the invariants explicit:

   - `awaitingProfileChoice` requires a complete `profileComparison` and no unresolved domain-upload work.
   - `profileChoiceMade` records exactly one valid source choice and is idempotent for the same import; it must not silently replace a prior choice.
   - Each conflict is resolved by `domain + recordId` and only once for the active import.
   - `conflictsResolved` may transition to `completed` only when a profile choice exists and every classified conflict has a durable resolution; an empty conflict set is valid after the profile choice.
   - A keep-cloud decision acknowledges that no guest payload write is needed; a keep-guest decision owns a revision-aware guest payload operation. Neither decision performs final guest-source deletion in this ticket.

   Use discriminated unions or equivalent typed records instead of boolean flags that permit “resolved” without a source. Keep reducer actions pure and require `importId` on every imperative decision action.

2. **Make persistence validate and restore all decisions safely.**

   Extend `guest-import-persistence.ts`’s version-1 validator/round-trip serialization for the new profile and conflict decision facts. Validate non-empty domain/record keys, allowed choice values, one decision per classified conflict, finite positive revisions where present, and JSON-safe snapshots through `isConflictSnapshot`. Reject duplicate decision keys and decisions for conflicts that are not in the persisted conflict list. Preserve the existing identity-scoped hydration fallback and write queue; do not introduce a second persistence writer or a migration layer.

   Add malformed-shape tests for missing decisions, unknown conflict keys, duplicate keys, invalid choices/revisions/snapshots, and stale completed states that still contain unresolved required choices. Prove a hydrated `awaitingProfileChoice`/`conflicts` state retains the comparison, conflict list, progress, and decisions exactly.

3. **Complete profile-choice semantics in a pure decision planner.**

   Add a small guest-import-only helper beside `guest-import-existing-account.ts` that turns the stored profile comparison and selected source into the necessary destination operation/disposition. Choosing guest produces one canonical profile scalar upsert with the cloud profile revision when a cloud row exists; choosing cloud produces no scalar write and preserves the current cloud values. If the cloud comparison is absent, represent that fact explicitly in the UI/model and do not fabricate cloud preferences or a revision.

   Keep profile trick-state operations from T159.3 separate so choosing a scalar source cannot overwrite the already-unioned selected/manual flags. Use the same canonical mapping functions and destination-user ownership checks as T159.3. The planner must return new immutable operation data and be deterministic for test fixtures.

4. **Implement independent conflict-resolution planning and execution.**

   Add a guest-import-specific resolver that accepts one conflict key and one source choice. For keep-guest, create or reuse a stable operation ID, use the conflict’s cloud revision as `expectedRevision`, and push the guest snapshot through the appropriate existing domain transport. For keep-cloud, create only a durable resolved disposition with no cloud mutation. Reuse the existing transport/revision result types and `ConflictSnapshot` validation; do not route the decision through T160.2’s normal sync envelope or ordinary conflict list.

   Before each mutation, persist the current guest-import progress/decision state. After a successful write, persist acknowledgement before any future cleanup. A stale revision or a transport failure leaves only that decision pending/blocked and keeps sibling operations available. A race result must retain the current conflict rather than treating the guest payload as accepted. The runner must be identity/import-generation aware and must never mutate a different account’s namespace.

5. **Refactor the existing-account runner without changing the empty-account path.**

   Split the shared safe mechanics from `runEmptyGuestImport` only as needed, then add a decision-aware existing-account runner. It should:

   - resume persisted accepted-operation progress without regenerating operation IDs or reclassifying the original snapshots;
   - process accepted records in deterministic domain/record order and mark each record acknowledged independently;
   - continue unrelated accepted records after a conflict or retryable failure;
   - settle each domain when all records have a durable disposition, recording conflict outcomes without stopping other domains;
   - present `awaitingProfileChoice` after T159.3’s non-conflicting upload work, even when conflicts exist;
   - apply the profile choice and each conflict decision independently, persisting after every transition;
   - leave unresolved conflict facts and unacknowledged guest source records available for T159.5.

   Do not dispatch completion, clear the import record, discard the guest namespace, or perform full source cleanup from this runner. Keep `runEmptyGuestImport`’s current semantics and tests intact.

6. **Wire the decision UI into the existing Profile-adjacent import surface.**

   Extend `GuestImportPreview` or split a focused decision component under `src/features/guest-import/components/` for `awaitingProfileChoice` and `conflicts`. Render the canonical guest/cloud profile comparison with accessible labels and explicit selected states, then render each conflict with its domain, record ID, guest snapshot, cloud snapshot, and independent keep-guest/keep-cloud controls. Show progress for accepted/unrelated records and a clear unresolved count.

   The UI must not infer a choice from color, ordering, or the current local profile. It must remain hydration-gated, tolerate a resumed import, disable duplicate submissions for an already-pending key, and make a completed action visibly distinct from an unresolved one. Keep the existing Profile route composition and navigation; do not link to or modify `/app/profile/sync-conflicts`.

7. **Wire the hook with stale-result and resume guards.**

   Update `use-guest-import.ts` so an existing-target import invokes the decision-aware runner rather than `runEmptyGuestImport`. Expose callbacks for profile choice and individual conflict resolution, backed by the latest identity-scoped state. Reuse the established `latestRef`, cancellation cleanup, `importId`, identity generation, and `saveNow` patterns.

   On remount, adopt persisted progress and decisions without re-running the T159.3 classification or duplicating acknowledged records. A late request from another import ID, account identity, or generation must be inert. Ensure a profile choice or one conflict resolution does not reset unrelated domain progress or re-open already resolved choices.

8. **Add table-driven model, persistence, runner, hook, and browser-state verification.**

   Extend the focused tests with these mechanically checkable cases:

   - profile comparison fixtures for guest-only, equal, and different scalar preferences; guest choice emits the expected revision-aware scalar operation, cloud choice emits no scalar write, and trick-state merge stays unchanged;
   - every conflict domain, including practice-history conflicts and goal/note tombstones, resolves guest and cloud choices independently with stable keys and no accidental ordinary-sync conflict record;
   - a combined fixture with accepted records, deduplications, multiple conflicts, and target-only records proves accepted/unrelated records continue, one conflict’s resolution does not resolve siblings, and the target is never replaced by an unresolved payload;
   - reducer tests prove stale import IDs, duplicate decisions, invalid phase actions, incomplete profile choice, and incomplete conflict resolution are no-ops, while the final transition occurs only after all required choices are present;
   - persistence tests prove reload retains pending decisions and progress, malformed decisions recover safely, and no initial empty-state write overwrites restored state;
   - runner tests inject lost acknowledgements, retryable failures, stale revisions, and a conflict in one domain while asserting unrelated records continue and every pre-request/progress/acknowledgement boundary is durable;
   - hook/provider tests exercise existing-target start, resume from `awaitingProfileChoice` and `conflicts`, identity changes, stale import IDs, and no cross-account writes;
   - component/browser-state tests cover accessible profile comparison, independent conflict controls, progress copy, unresolved blocking, and the completed/no-conflicts state on the web route.

   Preserve T159.1–T159.3 tests and add no native verification. Because this touches persisted state, cross-domain orchestration, and Profile UI, finish with the repository’s complete verifier, including web export.

9. **Close only this ticket after evidence passes.**

   The implementer should move T159.4 from `TASKS.md` to `TASKS_DONE.md` in the same implementation commit only after the focused suites, full typecheck, lint, and web export pass. Do not modify T159.5, T160.2, or the ordinary synchronization conflict lifecycle.

## Risks and constraints

- Profile scalar choice must not be conflated with trick-state OR merging; the former is an explicit user decision, while the latter was already made additive by T159.3.
- Guest-import conflicts can include immutable practice-history records, so the mutable-only `SyncConflictRecord` used by T160.2 cannot represent them without losing the import invariant.
- A conflict decision is not the same as guest-source cleanup. Keep-cloud and keep-guest outcomes must remain durably auditable until T159.5 confirms the relevant acknowledgement and cleanup boundary.
- The preflight classification is not a transaction. Revision-aware writes and explicit unresolved state must prevent a stale or lost response from becoming an implicit last-write-wins decision.
- Persisted state is provisional v1. Extend validation in place; do not create migration machinery for this prototype.
