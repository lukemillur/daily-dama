## Implementation order

1. `supabase/functions/delete-account/index.js` (new file, plain JavaScript
   + JSDoc, no TypeScript). This is the core of the ticket; do it first
   since everything else (config, tests) depends on its exact
   behavior/status codes.

   Request handling, in order:
   - Reject non-`POST` methods with `405`. Handle `OPTIONS` with a
     permissive CORS preflight response (`Access-Control-Allow-Origin: *`
     or reflect `Origin`, `Access-Control-Allow-Headers: authorization,
     content-type`, `Access-Control-Allow-Methods: POST, OPTIONS`) -- the
     web app will call this cross-origin via `supabase.functions.invoke` or
     `fetch` in T161.4, and Supabase's own function templates ship this
     boilerplate by default; add it now so T161.4 isn't blocked
     rediscovering it.
   - Parse the `Authorization` header. Missing or non-`Bearer` -> `401`.
   - Parse the JSON body. Not valid JSON, not an object, or missing keys ->
     `400`. Reject unknown/extra top-level keys (e.g. a caller-supplied
     `userId`, `user_id`, or `email`) as malformed rather than silently
     ignoring them -- this is what makes "attempts to supply another
     identity are rejected" testable and true. Only `currentPassword`
     (non-empty string) and `confirmation` (string) are permitted keys.
   - Build an anon-key Supabase client (`createClient(SUPABASE_URL,
     SUPABASE_ANON_KEY, { global: { headers: { Authorization: authHeader }
     } })`) and call `auth.getUser()`. This hits GoTrue's `/auth/v1/user`
     endpoint, which validates the JWT server-side and returns the trusted
     `id`/`email` -- do not decode the JWT locally and do not trust
     anything from the request body for identity. An error or missing user
     here -> `401`. This is the "fetch trusted identity server-side"
     requirement.
   - Check `confirmation === 'DELETE'` (exact, case-sensitive, no
     trim-then-compare leniency). Mismatch -> `400`.
   - Verify the password: create a second, throwaway anon-key client
     (fresh instance, `persistSession: false`) and call
     `signInWithPassword({ email: trustedEmail, password: currentPassword
     })`. An error -> `401` with a generic message (do not distinguish
     "wrong password" from any other reason). On success, discard the
     returned session entirely -- never store, forward, or return its
     access/refresh token. This satisfies both "validate currentPassword"
     (T161.1) and pre-empts T161.2's "without retaining the resulting
     session" by construction.
   - Create the service-role client using `SUPABASE_URL` and
     `SUPABASE_SERVICE_ROLE_KEY` (both auto-injected into the edge
     runtime's `Deno.env` by the Supabase CLI locally and by the hosted
     platform in production -- no manual secret plumbing needed) with
     `{ auth: { persistSession: false, autoRefreshToken: false } }`, and
     call `auth.admin.deleteUser(trustedUserId)` (default hard delete, no
     `shouldSoftDelete` flag). A failure here -> `500`, generic message, no
     internals leaked.
   - On success, return `new Response(null, { status: 204, headers: {
     'Cache-Control': 'no-store', ...corsHeaders } })`.
   - Wrap the whole handler body in try/catch; any unexpected throw -> `500`
     with a fixed generic message. Never let a caught error's `.message`
     (which could echo back parsed input) reach the response body or a log
     line.
   - No `console.log`/`console.error` call anywhere touches the parsed
     body, the `Authorization` header, `currentPassword`, or the resolved
     email -- if you need to log anything for local debugging while writing
     this, remove it before committing.

2. `supabase/config.toml`: add an explicit
   ```toml
   [functions.delete-account]
   enabled = true
   verify_jwt = true
   ```
   section near the existing `[edge_runtime]` block. This is redundant with
   the CLI's default (`verify_jwt = true` when unspecified) but makes the
   JWT requirement explicit and self-documenting, consistent with this
   repo's existing preference for explicit grants over relying on defaults
   (see T155.7's "revoke automatic/default privileges" pattern).
   Gateway-level `verify_jwt` and this function's own `auth.getUser()`
   check are intentionally redundant: the gateway rejects a
   malformed/expired JWT before the function even runs, and `getUser()`
   additionally confirms the identity is still valid/exists at call time
   (handles the case where a JWT is signature-valid but the user was
   already deleted).

     - `notes`: `{ user_id, id: 'note-1', trick_id, trick_name, body: 'Original body' }`
   - Valid deletion (`204` + cascade): call the function with the confirmed
     user's access token, `currentPassword` matching the seeded password,
     `confirmation: 'DELETE'`. Assert `status === 204`,
     `headers.get('cache-control') === 'no-store'`, empty body. Then, using

     `user_id`. Also assert the Auth user itself is gone: GoTrue admin `GET
     /auth/v1/admin/users/<id>` returns `404`.
   - Missing JWT: no `Authorization` header -> `401`.
   - Invalid JWT: `Authorization: Bearer not-a-real-token` -> `401`.
   - Malformed body cases (`400` each): non-JSON body; JSON body that isn't
     an object (e.g. an array or string); missing `currentPassword`;
     missing `confirmation`; `currentPassword` as a non-string (e.g.
     number); empty-string `currentPassword`.
   - Wrong confirmation: `confirmation: 'delete'` (wrong case),
     `confirmation: 'Delete'`, `confirmation: 'DELETE '` (trailing space),
     `confirmation: 'CONFIRM'` -> all `400`.
   - Wrong password: correct JWT/confirmation, wrong `currentPassword` ->

## Order rationale

Function code (1) must exist before its config entry (2) is meaningful, and
both must exist before the test suite (3) can run against anything. The
`package.json` script (4) and `run-db-tests.mjs` wiring (5) depend on the
test file's path existing. README documentation (6) is written last so it
describes what was actually built rather than what was planned. Steps 7-9
are verification, not implementation, and should be the last thing done
before considering the ticket complete.

## Explicitly out of scope for this ticket (deferred to later T161.x children)

- Rate limiting per user/IP (T161.2).
- Structured log redaction infrastructure / audit of every response for
  leakage beyond "don't log sensitive values in the first place" (T161.2).
- Idempotent retry handling for an already-deleted identity -- right now a
  retry after a lost success response will get `401` from `getUser()`
  (expected: the JWT itself may still be structurally valid until its
  1-hour expiry, but `getUser()` should fail once the underlying Auth user
  is gone; confirm this live during implementation and note the actual
  observed behavior -- this exact "retry after lost response"
  reconciliation path is explicitly T161.2's job, not this ticket's).
- Backend acceptance tests for anonymous/expired/wrong-user/stale sessions
  beyond the missing/invalid-JWT cases above (T161.3 -- this ticket's tests
  prove the function's own contract, T161.3 later proves the fuller session
  matrix).
- Frontend route/UI (T161.4) and local-state purge (T161.5).

## Risks / non-obvious things to watch for

- `auth.getUser()` semantics: confirm during implementation whether it
  calls out to GoTrue every time (trusted, server-validated) versus only
  decoding a cached JWT locally under some supabase-js versions/options --
  the roadmap explicitly requires "fetch trusted identity server-side," and
  a purely local JWT decode would not satisfy that even though the method
  name suggests otherwise. If ambiguous, call `/auth/v1/user` directly via
  `fetch` with the bearer token instead of relying on the SDK method, to be
  certain the identity is truly server-verified.
- CORS: don't over-invest here since T161.4 hasn't landed yet and there's
  no frontend caller to prove it against; keep the preflight handling
  minimal and revisit if T161.4 finds it insufficient.
- Deno import resolution: `npm:@supabase/supabase-js@2` requires network
  access the first time the local edge runtime resolves it (same caveat
  the README already documents for the `pg_prove` Docker image pull) --
  expect one slow first run.
- Strict body-schema rejection of extra keys is the mechanism proving
  "attempts to supply another identity are rejected." Don't weaken this to
  "ignore unknown keys" for convenience -- that would silently pass a
  caller who includes a `user_id`/`email` field, which is exactly the case
  this exit criterion is checking for.
