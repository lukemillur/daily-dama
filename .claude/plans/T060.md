# T060 — Explain when a Kentei rank didn't advance after an assessment

## Confirmed current behavior (read before implementing)

- `selectPromotedKenteiRank` (`src/features/tricks/model/trick-directory.ts:149`) is unchanged by
  this task — gapless-from-current-rank promotion stays exactly as-is.
- `AssessmentEntry` (`src/features/sesh/components/assessment-entry.tsx`) already reads live
  `kenteiRank` from `useUserProfile()` and captures `startingKenteiRank` (the rank *before* the run)
  in its `'running'` step, passing both into `selectAssessmentResultCopy` for the wrap-up footer
  (`ResultCopy`, `accessibilityLabel="Assessment result"`). That existing copy ("held Rank X … land
  every trick to advance") already covers a normal in-order non-promotion — do not duplicate or
  replace it; this task adds a *second*, conditional message only for the out-of-order case.
- `AssessmentEntry` has three flows: `fullBottomToTop` (never out-of-order — starts at the true
  bottom), `currentRankOnly` (only offered when `kenteiRank` is defined, and its `rank` is always
  set to the current `kenteiRank` — never out-of-order structurally), and `fromRank` (the
  "Start from a rank" picker in the `'choosingRank'` step — the only flow that can start above the
  stored rank).
- Skipping ("Skip this rank") lives entirely inside `MultiTrickSesh`
  (`src/features/sesh/components/multi-trick-sesh.tsx`): `handleConfirmSkip` calls the
  `describeSkippedRange(fromIndex, targetIndex)` prop (if provided) and appends its return value to
  local `skippedEntries` state, which renders in the wrap-up as its own list. This callback is the
  only hook available to `AssessmentEntry` for observing that a skip happened — `skippedEntries`
  itself is not exposed as a prop/callback beyond that string return value.
- Per onboarding (`require-onboarding.ts`), `kenteiRank` is always defined by the time a user can
  reach `AssessmentEntry`, so the `undefined` branches below are defensive, not load-bearing.

## Plan

1. **`src/features/sesh/model/kentei-assessment-run.ts`** — add two new pure, independently
   testable functions (do not fold into `selectAssessmentResultCopy`; keep the existing
   function/tests untouched):

   - `selectStartedAboveStoredRank(flow: AssessmentFlow, startingKenteiRank: number | undefined, minRank: number): boolean`
     — `true` only when `flow.kind === 'fromRank'` and
     `flow.startingRank > (startingKenteiRank ?? minRank)`. `fullBottomToTop` and
     `currentRankOnly` always return `false`. Starting a `fromRank` run exactly at the stored rank
     (a re-test) is *not* out-of-order — only strictly above it is, since that skips the user's own
     current frontier rank.
   - `selectAssessmentGapNotice(startingRank: number | undefined, resultRank: number | undefined, wasOutOfOrder: boolean): string | undefined`
     — returns `undefined` when `!wasOutOfOrder`. Otherwise computes "promoted" the same way
     `selectAssessmentResultCopy` does (`resultRank !== undefined && (startingRank === undefined || resultRank > startingRank)`)
     and returns `undefined` if promoted, else a fixed explanatory string, e.g.:
     `"Promotion needs every rank cleared in order — go back and clear the earlier or skipped ranks to unlock it."`
     Keep wording distinct enough from the existing "held" copy that a screen reader hearing both in
     sequence isn't redundant.

   Add unit tests for both in `kentei-assessment-run.test.ts`, mirroring the existing
   `describe('selectAssessmentResultCopy', ...)` block's style: cover all three `AssessmentFlow`
   kinds for `selectStartedAboveStoredRank` (including the "exactly at stored rank" boundary and an
   `undefined` `startingKenteiRank`), and cover the not-out-of-order / out-of-order-but-promoted /
   out-of-order-and-held matrix for `selectAssessmentGapNotice`.

2. **`src/features/sesh/components/assessment-entry.tsx`** — wire the two new selectors in:

   - Extend the `'running'` step's shape with `readonly startedAboveStoredRank: boolean`, computed
     once at each `setStep({ kind: 'running', ... })` call site via
     `selectStartedAboveStoredRank(flow, kenteiRank, minRank)` (bounds already available from
     `selectAssessmentRankBounds`).
   - Add `const [skippedDuringRun, setSkippedDuringRun] = useState(false);`, reset to `false` at
     every `setStep({ kind: 'running', ... })` call site (all three flow-start buttons plus the
     rank-picker button) so a skip from a *previous* run can't leak into a new one.
   - Wrap the existing `describeSkippedRange` callback so it also flips `skippedDuringRun` to
     `true` as a side effect, in addition to returning the description string it already returns —
     this is the only signal available for "a skip happened," per the exploration note above.
     Keep the returned string identical to today's; only add the `setSkippedDuringRun(true)` call.
   - Compute `const wasOutOfOrder = step.startedAboveStoredRank || skippedDuringRun;` where
     `step.kind === 'running'` (both booleans are already in scope there).
   - Render the new notice as a second element alongside the existing `ResultCopy`, gated on
     `selectAssessmentGapNotice(step.startingKenteiRank, kenteiRank, wasOutOfOrder)` returning a
     string. Give it its own `accessibilityLabel` (e.g. `"Assessment gap notice"`) so tests and
     screen readers can distinguish it from `"Assessment result"`. Render nothing when the selector
     returns `undefined` — don't render an empty `styled.View`.

3. **(Recommended, same ticket) `src/features/sesh/components/assessment-entry.tsx`
   `'choosingRank'` step** — add a heads-up before the run starts, not just after. Below `RankGrid`,
   when `kenteiRank !== undefined`, render a short conditional `Copy` line, e.g.:
   `"Ranks above ${kenteiRank} won't count toward promotion until Rank ${kenteiRank} and everything below it are cleared."`
   Keep this static (not per-rank-button) to avoid a second interactive-state system — the existing
   `RankChoice` buttons stay exactly as they are. This is low-risk and directly serves the same
   transparency goal the ticket describes as "consider," so implement it rather than split it off;
   drop it only if step 1–2 already eat the iteration's time budget.

4. **Tests in `assessment-entry.test.tsx`** — add a new `describe` block (e.g.
   `'AssessmentEntry gap notice (T060)'`) with at least:

   - Out-of-order, no promotion: seed profile at `kenteiRank: 1`, press "Start from a rank", pick a
     rank strictly above 1 (e.g. rank 3 — use `pressByAccessibilityLabel(root, 'Start from rank 3')`,
     following the existing `RankChoice` `accessibilityLabel` convention), end the assessment
     without lacing anything (`advanceThroughCountdown()` + `pressByVisibleText(root, 'End assessment')`),
     and assert the new `"Assessment gap notice"` node is present and its text matches something
     like `/clear|earlier|skip/i`.
   - Out-of-order, but promoted anyway (lace every trick in the picked-from rank and everything
     above through the max rank, or more cheaply: use a `fromRank` starting rank equal to `maxRank`
     so only one rank's tricks need lacing) — assert the gap notice is absent.
   - In-order, not promoted (the existing "held" test's setup) — assert the gap notice is absent
     (reuse the existing test's setup as a `it(...)` addition or a new assertion in the same test,
     implementer's call).
   - Skip-triggered: seed `kenteiRank: 1`, choose "Full assessment" (or "Start from a rank" at 1,
     equivalent), reach the first countdown, press `'Skip this rank'` then
     `pressByAccessibilityLabel(root, 'Confirm skip rank')` (pattern from
     `multi-trick-sesh.test.tsx`), then end the run without lacing the tricks landed on — assert
     the gap notice appears even though this run technically "started in order."

5. **Verification** — `node .claude/scripts/verify.mjs` (full, since this touches components +
   web-rendered copy).

## Ordering rationale

Step 1 (pure model functions + their own tests) before step 2 (wiring) because the wiring depends
on the exact function signatures being settled first, and the model functions are independently
testable without touching the component tree. Step 3 (pre-run heads-up) is independent of 1–2 but
sequenced after so the core "why didn't it promote" fix lands first if time runs short. Step 4
(component tests) last since it exercises the fully wired behavior.

## Risks / non-obvious things

- The only way to observe "a skip happened" from `AssessmentEntry` today is piggybacking on the
  existing `describeSkippedRange` return-value callback — there's no dedicated
  `onSkip`/`skippedEntries` prop on `MultiTrickSesh`. Don't add one just for this; the side-effect
  wrap is consistent with how `MultiTrickSesh` already treats that prop as an opaque
  string-producing hook for the caller.
- `wrapUpFooter` is a static `ReactNode` computed once per `AssessmentEntry` render while
  `step.kind === 'running'` — it is *not* re-invoked per wrap-up render, but because `kenteiRank`
  (live, from `useUserProfile()`) and `skippedDuringRun` (local state) are both read at
  `AssessmentEntry`'s own render time and `AssessmentEntry` re-renders whenever either changes,
  the footer JSX naturally reflects up-to-date values by the time the wrap-up actually shows. No
  additional plumbing needed here — just don't memoize `wrapUpFooter` in a way that captures stale
  values.
- Do not touch `selectPromotedKenteiRank` or the auto-promotion effect — confirmed out of scope by
  the task's Notes.
- Exact copy text is implementer's judgment; keep it distinct from the existing "held" sentence and
  keep both testable via `accessibilityLabel`.
