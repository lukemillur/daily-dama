# T112.1 - Nest the app under /app, move home to /app/home

## Chosen layout: src/app/app/home.tsx (not home/index.tsx)

Single file, no extra directory, and its route (/app/home) matches the exit
criteria path directly. All other moved routes keep their existing internal
shape (sesh/, tricks/, stats/, profile/ stay directories with their own
_layout.tsx), just nested one level deeper.

## The real architectural change hiding in this "mechanical rename"

This is NOT just updating strings. src/app/_layout.tsx currently renders
<AppTabs /> directly (from src/components/app-tabs.web.tsx / app-tabs.tsx),
and that component IS the Tabs/NativeTabs layout: its TabSlot/NativeTabs
machinery renders whichever route is the DIRECT CHILD of the file that
renders it. Right now that's fine because index, sesh, tricks, stats,
profile are all direct children of the root layout.

Once those routes move to src/app/app/..., the root layout's only direct
child becomes the single segment "app". If <AppTabs /> stays at the root,
the tab navigator has nothing of the right shape to slot in. This is
unambiguous on native: NativeTabs.Trigger name="sesh" etc. must match a
sibling route file of wherever <NativeTabs> is declared - that's a hard
React Navigation constraint, not a style choice. The web <Tabs>
(expo-router/ui) is built the same way (TabSlot renders the active child of
its own layout position), so it needs the same fix for consistency and
correctness even though its href-driven navigation is more forgiving.

FIX: move the tab bar itself one level deeper, to a new
src/app/app/_layout.tsx, so it is once again the direct layout for
home/sesh/tricks/stats/profile. The root src/app/_layout.tsx keeps all its
providers/theme/splash setup exactly as-is, but swaps <AppTabs /> for a
plain <Slot /> so it just passes through to whichever top-level segment
resolves (app/... now, and / - the future landing page - once T112.2 lands,
or a redirect placeholder until then, see below).

This keeps the provider tree unchanged (CustomTrickProvider ->
UserProfileProvider -> PracticeHistoryProvider -> NoteProvider ->
GoalProvider -> AppThemeProvider -> KenteiRankAutoPromotion) - AppTabs reads
useUserProfile() and will still be mounted well inside that tree, just one
Slot boundary lower.

## src/app/index.tsx during the gap before T112.2

The task frees this file up for T112.2's landing page, but T112.1 landing
alone (per its own Notes: land and verify this before starting T112.2) would
otherwise leave production "/" - the currently-live entry point - 404ing
until T112.2 ships. Don't leave that gap: replace src/app/index.tsx with a
minimal Redirect-to-/app/home placeholder. T112.2 will overwrite this file's
contents entirely, so it's not wasted work, and it preserves "no change in
behavior" for the current production root route.

## Risks / things to double-check while implementing

- The Tabs-layout relocation (steps 2-3) is the one piece that isn't pure
  find-and-replace. If Slot at the root doesn't behave as expected (e.g.
  some version-specific quirk with expo-router/ui's Tabs needing to be the
  literal root layout), that will surface immediately as a blank screen or
  "no route matched" in the dev server - verify this first, before grinding
  through the ~30 string updates, since it's the thing most likely to
  require a different approach.
- Confirm the dist/app/stats/[trickId].html path assumption in step 7
  against the actual expo export output before trusting vercel.json.
- This ships a production-facing change to the live root route (/) even
  though the visible behavior should be identical (redirect vs. direct
  render). Worth a deliberate look at the deployed result once this reaches
  production, not just local dev-server verification.
