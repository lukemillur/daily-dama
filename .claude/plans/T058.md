# T058 -- Let "End assessment"/"End Sesh" actually end a multi-trick run early

## Root cause (confirmed)

`MultiTrickSesh` (`src/features/sesh/components/multi-trick-sesh.tsx`) wires
`ActiveSesh`'s `onEnd` to a plain `dispatch({ type: 'seshEnded', now })`
(currently line 259). The `state.status === 'completed'` effect (currently
lines 170-187) is the *only* place that reacts to a completed trick, and it
unconditionally does `advanceTrickSequence` + `seedNextTrick` -- i.e. it can't
distinguish "the user pressed End/End assessment and wants to stop the whole
run" from "this trick's own countdown/timer/lace flow finished naturally and
the run should continue to the next trick." That's the bug: there is
currently no way to reach the "stop the whole run" outcome from `onEnd`
at all.

Three call sites reach `seshEnded` today and must keep their current meaning:
- `onTimerElapsed` -> `timerElapsed` action (a timed trick's own deadline
  passing) -- must keep auto-advancing to the next trick.
- `advanceOnFirstLace`'s second dispatch in `handleLaced` (line ~241) -- must
  keep auto-advancing to the next trick (used by the assessment flow's
  `advanceOnFirstLace` prop).
- `onNextTrick` (line 267) -- same `seshEnded` dispatch, must keep advancing
  one trick and continuing the run (this is the "Next trick" button, a
  different, already-correct action).

Only `onEnd` (backing both the primary "End Sesh"/"End assessment" button and
the "End anyway" button in `ActiveSesh`, `src/features/sesh/components/sesh.tsx`
lines 638 and 643 -- both call the same `onEnd` prop) should change to mean
"stop the whole run," per the task's scoping in Notes (shared
`MultiTrickSesh` level, benefits both the assessment and ad hoc multi-trick
practice callers).

## Design

Add a ref that flags "the completed effect that's about to fire was caused
by the user pressing End, not by a natural per-trick completion":

```ts
const endRunRequestedRef = useRef(false);
```

Add a handler (replacing the current inline `onEnd={() => dispatch(...)}`)
inside the `state.status === 'active'` branch, alongside the existing
`handleLaced`:

```ts
const handleEndRun = () => {
  endRunRequestedRef.current = true;
  dispatch({ type: 'seshEnded', now: Date.now() });
};
```

Wire `onEnd={handleEndRun}` on `ActiveSesh` (replacing the current inline
dispatch).

In the `completed` effect, branch on the ref instead of always advancing:

```ts
useEffect(() => {
  if (state.status !== 'completed') return;

  const summaryId = createPracticeSessionRecordId(state.summary);
  if (recordedSummaryId.current === summaryId) return;

  recordedSummaryId.current = summaryId;
  recordCompletedSesh(state.summary);
  setSummaries((prev) => [...prev, state.summary]);

  if (endRunRequestedRef.current) {
    endRunRequestedRef.current = false;
    setSequence((prev) => advanceTrickSequenceToIndex(prev, prev.tricks.length));
    dispatch({ type: 'seshReset' });
    return;
  }

  const nextSequence = advanceTrickSequence(sequence);
  setSequence(nextSequence);

  const nextTrick = getCurrentSequenceTrick(nextSequence);
  if (nextTrick) {
    seedNextTrick(nextTrick);
  }
}, [recordCompletedSesh, sequence, state, seedNextTrick]);
```

This deliberately reuses the exact same "jump to end + `seshReset`" shape
`handleSkipRank` already uses when `skipTarget` returns an index at or past
the end of the sequence (lines 213-221) -- `advanceTrickSequenceToIndex(...,
tricks.length)` clamped, then `seshReset` to fall out of `completed`/`active`
into `choosing`. `isRunFinished` (lines 146-147) already treats
`status === 'choosing'` with a finished sequence as terminal, so no change is
needed there -- the existing wrap-up gating just works once the sequence is
advanced to its end and `seshReset` is dispatched.

Why a ref and not a `useState`: setting it happens synchronously in the same
event handler that dispatches `seshEnded`, and it must be read during the
*next* effect run triggered by that dispatch, then cleared -- a `useState`
flag would work too but adds a re-render and a set-then-immediately-read
timing subtlety for no benefit; a ref matches how `recordedSummaryId` (same
file) already tracks handler-set/effect-read reducer-adjacent bookkeeping.

Edge cases already handled correctly by this design (verify while
implementing, not just in review):
- Pressing End on the *last* trick in the sequence: `advanceTrickSequenceToIndex`
  clamps to `tricks.length` either way, so this is a no-op change from
  today's behavior -- still reaches the wrap-up in one step.
- Pausing then pressing End: `seshEnded`'s reducer case only checks
  `state.status !== 'active'`, and a paused active trick is still
  `status: 'active'` with `pausedAt` set, so this is unaffected.
- `advanceOnFirstLace`'s auto-fired `seshEnded` in `handleLaced` never touches
  `endRunRequestedRef`, so the assessment flow's auto-advance-after-one-lace
  behavior is untouched.
- `onTimerElapsed` dispatches `timerElapsed`, not `seshEnded`, and never
  touches the ref -- a timed trick's own deadline elapsing still auto-advances
  the run; only explicit End presses end the whole thing.

No changes needed to `trick-sequence.ts` (existing `advanceTrickSequenceToIndex`
is reused as-is) or to `kentei-assessment-run.ts` (its skip-range logic is
already correct per the task's own investigation notes -- this task's bug is
purely in `MultiTrickSesh`'s End handling, not in the skip/rank-messaging
code).

## Implementation order

1. **`src/features/sesh/components/multi-trick-sesh.tsx`**
   - Add `endRunRequestedRef` (`useRef(false)`) near `recordedSummaryId`.
   - Update the `completed` effect to branch on the ref as shown above.
   - Add `handleEndRun` inside the `state.status === 'active'` block (near
     `handleLaced`) and wire it to `ActiveSesh`'s `onEnd` prop, replacing the
     current inline dispatch.
   - Update the doc comment on the `endActionLabel` prop (lines ~57-63) and
     the inline comment above the `onNextTrick`/`onEnd` wiring (lines ~263-267)
     -- both currently describe or imply "End" only ends the current trick;
     reword to state it now ends the whole run, and keep the contrast with
     `onNextTrick` (which still only advances one trick) explicit so a future
     reader doesn't reintroduce this bug by "fixing" `onNextTrick` too.
   - No prop signature changes -- this is entirely internal to the component,
     so `assessment-entry.tsx` and `multi-trick-sesh-entry.tsx` (both callers)
     need zero changes.

2. **`src/features/sesh/components/multi-trick-sesh.test.tsx`**
   - Rewrite `'does not advance on a single lace when disabled (default),
     requiring an explicit End Sesh'` (in the `advanceOnFirstLace` describe
     block, ~line 171): the second half currently asserts pressing "End Sesh"
     advances to `TRICKS[1]`'s countdown -- that assertion is now wrong by
     design. Keep the first half (single lace doesn't auto-advance), but
     replace the "press End Sesh -> advances to trick 1" assertion with:
     press "End Sesh" -> immediately reach the wrap-up (e.g. `'Finish sesh'`
     visible, or `'Sesh complete'` eyebrow text), `session-count:1`,
     `session-0-lace-count:1`, and `TRICKS[1].name` / `TRICKS[2].name` not
     present anywhere in the tree. Rename the test to reflect ending the run,
     not "requiring an explicit End Sesh" to advance.
   - Add a new `describe('MultiTrickSesh "End Sesh" ends the run early', ...)`
     block covering:
     - Pressing End Sesh mid-run (with some laces recorded on the current
       trick, e.g. 2) reaches the wrap-up immediately with exactly one
       summary entry (the current trick's laces-so-far), and the remaining
       tricks are absent from the wrap-up entries (assert on the
       `Wrap-up entry: ...` accessibility-label pattern already used by the
       existing wrap-up tests, not just `findByText`, to match that suite's
       convention).
     - A case that mixes "Next trick" then "End Sesh": advance past trick 0
       via "Next trick", then press "End Sesh" during trick 1 -- wrap-up shows
       exactly two entries (tricks 0 and 1), trick 2 absent. This is the
       interaction the task's scoping note is really about (a long
       multi-rank run where the user has already stepped past a few tricks).
     - A case using `endActionLabel: 'End assessment'` confirming the custom
       label press also ends the whole run (not just wiring -- assert the
       wrap-up is reached with the expected single summary), since the
       assessment caller is the primary motivator for this task and uses
       `endActionLabel`.
   - Leave the existing `'hideTimer'` and `'wrap-up'` describe blocks alone --
     traced through above, neither depends on the old "End only ends current
     trick" behavior (the wrap-up test only presses "End Sesh" on the actual
     last trick, and the hideTimer duration test doesn't check what happens
     after End).
