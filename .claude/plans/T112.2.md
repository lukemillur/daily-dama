# T112.2 — Landing page purpose-and-overview content

## Context confirmed before planning

- T112.1 already landed on `development` (nesting the app under `/app`, home moved to
  `src/app/app/home.tsx`). `src/app/index.tsx` is currently just a redirect placeholder:
  ```tsx
  import { Redirect } from 'expo-router';
  export default function RootRedirect() {
    return <Redirect href="/app/home" />;
  }
  ```
  There is no existing test for this file — clean slate, no redirect test to remove.
- `src/app/app/home.tsx` (`HomeScreen`) is the component that branches on
  `profile.hasCompletedOnboarding && profile.kenteiRank` to render `KenteiOnboarding` or
  `DailyHome`. That branching logic stays exactly where it is — T112.2 does not touch it.
- Root `src/app/_layout.tsx` renders `<Slot />` with no navigation chrome (no tab bar, no
  header) above `_layout`, so `/` is naturally chrome-free today — appropriate for a
  marketing/landing page distinct from the tabbed app shell.
- Typography primitives live in `src/components/ui/typography.tsx`: `Eyebrow`,
  `DisplayTitle`, `BodyText`, all `styled.Text` reading from `ThemeContext` (`theme.text`,
  `theme.textMuted`). `onboarding-intro-step.tsx` is the canonical usage pattern: a
  `styled.View` `Content` wrapper (`max-width`, centered, padded), `Eyebrow` for the small
  caps label, `DisplayTitle` (styled, `margin-top`) for the headline, `BodyText` (styled,
  `max-width`, `color: theme.textMuted`) for body copy, and `Button` for the CTA.
- `Screen` (`src/components/ui/screen.tsx`) provides `SafeAreaView` + background + web
  header inset (88px top padding on web unless `includeWebHeaderInset={false}`) + optional
  `webBottomInset`. This should NOT be disabled here — no reason to opt out of the standard
  web inset since there's no competing header on `/`.
- Longer scrollable screens (e.g. `DailyHome` in `daily-home.tsx`) wrap content in a styled
  `ScrollView` (`HomeScroll`) with a `contentContainerStyle` bottom padding, rather than
  relying on `Screen` itself to scroll. Follow the same shape since landing copy (headline +
  lede + 3 feature bullets + closing line + CTA) will exceed one viewport on narrow widths.
- CTA-as-link pattern used throughout (`daily-home.tsx`, `sesh.tsx`):
  `<Link href="..." asChild><Button accessibilityRole="link">Label</Button></Link>`.
- `AppColors` (`src/constants/theme.ts`) has the art-directed palette: `paper`/`paperStrong`/
  `cream` (warm backgrounds), `yellow` (accent used for the pre-onboarding home background),
  `ink`/`inkSoft`/`textMuted`/`textSubtle` (text), `sage` (default `Screen` background),
  `borderMuted`. Landing should feel distinct from both `DailyHome`'s sage and onboarding's
  yellow — use `AppColors.paper` (or `paperStrong`) as the landing background to read as a
  calmer, editorial "about" page rather than another app screen.
- Test pattern for provider-free/router-touching screens: mock `expo-router`'s `Link`/
  `useRouter` at the top of the test file (see `kentei-onboarding.test.tsx`), mount with
  `react-test-renderer`'s `create()` inside `act()`, and assert on rendered text via
  `findAll`. No AsyncStorage-backed provider is needed for this screen since it takes no
  props and reads no app state.

## Decision: what `/` renders and for whom

`/` becomes an always-on marketing/landing screen — it does not branch on onboarding status.
Rationale: T112.1's stated purpose was to free `/` for a landing page; the exit criteria's
"with no completed onboarding" phrasing describes the test scenario (a fresh visitor), not a
conditional runtime check. Branching `/` on profile state would require pulling in
`UserProfileProvider` context at the root before hydration completes and would blur the
"distinct from both onboarding and app home" boundary the task explicitly asks for. Simpler
and more correct: `/` is always the pitch; the CTA is the only bridge into `/app/home`, which
already owns the onboarding-vs-home branch. A returning, already-onboarded user who bookmarks
`/` sees the pitch again and taps through — acceptable for a prototype, not worth extra
routing logic. Flag this as the one product judgment call in this plan; revisit only if the
user pushes back.

## Implementation steps

1. **Create `src/features/landing/components/landing-page.tsx`** exporting `LandingPage`.
   Structure, in order:
   - `Screen` (`background={AppColors.paper}`, default edges, no `webBottomInset` override
     needed since content scrolls internally).
   - A styled `ScrollView` (mirroring `HomeScroll`) wrapping a centered, max-width `Content`
     `styled.View` (mirroring `onboarding-intro-step.tsx`'s `Content`: `max-width: 620px`,
     `align-self: center`, horizontal padding, generous top/bottom padding since there's no
     tab bar to clear here — use e.g. `padding: 40px 22px 80px` rather than the 130px bottom
     reserved for the tab bar in in-app screens).
   - `Eyebrow` label (e.g. "Why Daily Dama").
   - `DisplayTitle` headline (2 short lines, `{'\n'}`-broken like the onboarding intro).
   - `BodyText` lede paragraph — the flow-state-vs-intentional-practice framing from
     `LANDING_PAGE_BRAINDUMP.md`.
   - A short list of 2-3 feature/value bullets (styled `View` items each with a bold
     sub-heading `Text` + `BodyText`-styled supporting line) translating the braindump's
     concrete pain points (drifting off the stated goal trick; the "it's been 5 minutes but
     feels like nothing" grind; the Kentei ladder placement) into product-benefit language —
     do not lift the founder's raw first-person paragraphs verbatim into the UI.
   - A closing `BodyText` line addressing the "this doesn't want to put you on a screen
     instead of playing" concern from the braindump, in the app's voice.
   - CTA: `<Link href="/app/home" asChild><Button accessibilityRole="link">...</Button></Link>`
     with copy that reads as an invitation, not generic marketing button text (e.g. "Start
     your first Sesh").
   - Draft copy is explicitly placeholder per the task Notes — write it in full sentences in
     the app's voice, but do not treat exact wording as load-bearing.
   - Colocate all styled-components at the bottom of the file, following the existing
     file-local pattern (no separate `styles.ts`).

2. **Replace `src/app/index.tsx`** to render `<LandingPage />` directly (drop the
   `Redirect`/`expo-router` import, add the import from
   `@/features/landing/components/landing-page`). No provider wrapping needed at this route
   — `LandingPage` takes no props and touches no persisted state.

3. **Add `src/app/__tests__/index.test.tsx`** (new directory, matching the
   `src/app/app/__tests__/` convention already used for route-level tests):
   - Mock `expo-router` (`Link` + no-op `useRouter`) the same way `kentei-onboarding.test.tsx`
     does, since the CTA renders a `Link`.
   - Mount `RootRoute` (the default export of `src/app/index.tsx`) with `create()` inside
     `act()` — no providers required.
   - Assert the rendered tree contains a headline text node distinct from onboarding/home
     copy (search by known headline string or by finding a node whose styled component is
     `DisplayTitle`-based — matching text content is simplest and matches the existing
     `findByText`-style helpers used elsewhere in this repo) and a body-copy text node,
     confirming both `Eyebrow`/`DisplayTitle` and `BodyText` elements render.
   - Optionally assert the CTA `Link`'s `href` prop is `/app/home` (inspect the mocked
     `Link`'s props via the mock, or find the pressable and check its `accessibilityRole`),
     to lock in the bridge into the app without hardcoding exact button copy.
   - Keep assertions on *presence and distinctness* of the typography elements, not on exact
     placeholder wording, per the task's explicit instruction not to treat copy as
     load-bearing.

4. **Manual check at 320px web width**: although `/` isn't part of the 5-link nav bar (no nav
   chrome renders on this route), still sanity-check the landing screen doesn't horizontally
   overflow at 320px given `AGENTS.md`'s general web-width discipline — `Content`'s
   `max-width` + horizontal padding pattern already handles this if copied faithfully from
   `onboarding-intro-step.tsx`.

## Order and why

Step 1 (component) before step 2 (route wiring) before step 3 (test) — the test imports the
route file, which imports the component, so nothing compiles/tests green until all three
exist. Step 4 is a manual verification pass, not a code change, and naturally happens last
during `yarn expo export`/dev-server spot check.

## Risks / non-obvious notes

- Don't reuse `AppColors.yellow` (pre-onboarding `Screen` background) or leave `Screen`'s
  default `sage` background for the landing page — both would make `/` visually
  indistinguishable from `KenteiOnboarding` or `DailyHome` at a glance, undermining the
  "distinct from both" exit criterion even though the exit criteria are phrased as
  component-identity checks, not a visual-diff check.
- Keep the feature bullets short and concrete (translate the braindump's specific anecdotes
  into product language) rather than generic flow/mindfulness marketing copy — the task
  explicitly calls out avoiding "a generic marketing-page template with Daily Dama's name
  swapped in."
- This task does not touch `HomeScreen`'s onboarding/home branch, `useRequireOnboarding`, or
  any persistence domain — it is purely a new presentational route + component + test. No
  schema, reducer, or provider changes are in scope.
