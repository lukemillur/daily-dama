# T153.4 -- Static-render-safe web Supabase client and Auth state

## Feasibility check (do this framing first, don't re-derive it)

branch, blocked only on a Docker-capable environment for live GoTrue

  requires to be handled gracefully.

So: do not block on T153.1. Implement and verify this ticket now,
against mocked Supabase responses only. Do not attempt to run supabase
start or hit a live project.

## Design decisions (read before coding)

1. State model is fail-safe-to-guest, not a 4th status. Missing config,
   malformed config, and "client construction succeeded but offline" all
   collapse to status: 'guest' (optionally tagged with a non-authoritative
   reason). The app must never get stuck in initializing and must never
   crash. This matches the roadmap principle: "Guests retain access to
   /app; Auth adds synchronization rather than becoming an application
   gate."

2. Initial/ongoing state comes from onAuthStateChange only -- never from a
   getSession() network round trip. supabase-js v2's onAuthStateChange
   fires an INITIAL_SESSION event synchronously off the storage-cached
   session (if any) as soon as you subscribe, independent of network
   reachability, then continues with SIGNED_IN / SIGNED_OUT /
   TOKEN_REFRESHED / USER_UPDATED / PASSWORD_RECOVERY events. Driving
   state exclusively off this single subscription is what makes "offline
   initialization" well-defined and testable, and is also the standard
   supabase-js recommendation for this exact reason. Do not additionally call
   getSession() on mount -- it is redundant with INITIAL_SESSION and adds a
   network dependency the exit criteria explicitly wants removed.

3. Storage adapter is the AsyncStorage package itself, not raw
   window.localStorage. AsyncStorage's getItem/setItem/removeItem already
   match supabase-js's SupportedStorage shape (Promise-returning), and this
   codebase already treats AsyncStorage access as safe to defer to a
   useEffect (see UserProfileProvider). This sidesteps ever touching window
   directly and gives you the platform seam for free: Phase 5 mobile
   hardening swaps this one storage option for a SecureStore-backed adapter
   (per BACKEND_ROADMAP.md's "Client storage and web security" section)
   without touching the state machine at all. Do not introduce a
   web/native file split for this -- a single Platform.OS === 'web' guard
   (matching the existing inline-guard style in user-profile-provider.tsx)
   is enough, since native returns null (no client) until Phase 5.

4. Client construction is lazy and memoized, called only from inside a
   useEffect. This is the same mechanism that already makes
   UserProfileProvider/CustomTrickProvider/etc. safe for Expo Router's Node
   static-render pass: effects never run during server/static rendering,
   only after client hydration. Do not call the client constructor at
   module scope or in the provider's render body.

5. No hydration gate. Unlike every existing persistence provider (which
   render a fallback screen until hasHydrated), AuthProvider must always
   render children immediately. status: 'initializing' is a value
   consumers can read, not a reason to block rendering. This is the literal
   task instruction (mount Auth above the root Slot, without adding an
   Auth hydration gate) and is what keeps every /app guest route
   renderable regardless of Auth state.

6. Keep the exposed action surface minimal: signInWithPassword and
   signOut only. The exit criteria only requires sign-in/sign-out/token
   refresh/events at the provider level. Signup, password recovery, email
   change, and the PKCE callback exchange belong to T153.6-T153.9 and
   T153.7; they can call the shared client accessor directly for their own
   Supabase Auth methods rather than every method being pre-wrapped here.
   Do not build that surface now -- it is scope creep against this ticket's
   exit criteria.

7. Optional, worth flagging to whoever picks up T153.6/T153.7 later:
   consider also retaining the raw last Supabase event string (e.g.
   lastEvent) alongside status/session in the context value, since
   T153.6's password-reset route will need to distinguish a
   PASSWORD_RECOVERY session (temporary, reset-only) from an ordinary
   SIGNED_IN session -- both currently look identical under the 3-state
   model (status: 'authenticated'). This is cheap to add now (one extra
   field, no new subscription) and would save T153.6 from re-subscribing to
   onAuthStateChange itself. Not required by this ticket's exit criteria,
   so treat it as a recommendation, not a mandate -- implementer's call.

## Files to add

1. package.json -- add the supabase-js package (latest 2.x stable) to
   dependencies. Run yarn install and let the lockfile update land in the
   same commit.

2. src/features/auth/model/auth-state.ts (pure, no SDK import)
   - An AuthStatus type with three values: initializing, guest, authenticated.
   - An AuthState discriminated union: initializing has no extra fields,
     guest carries an optional reason (signedOut, unconfigured, or error),
     authenticated carries the Supabase session object.
     Import only the Session type from the supabase-js package -- type-only
     imports don't pull SDK code into this pure module.
   - A pure function, e.g. deriveAuthState(event, session), mapping
     Supabase's auth events/session to the three-state model. Keep this pure
     and synchronous -- mirrors the Sesh-reducer principle in AGENTS.md of
     keeping decision logic separate from IO/timers. This is the function
     your event-mapping unit tests target directly, no SDK mocking required.

3. src/features/auth/persistence/supabase-config.ts (pure, no SDK import)
   - A SupabaseConfig discriminated union with three statuses: ready
     (carrying url and publishableKey), missing, and malformed (carrying a
     reason string).
   - resolveSupabaseConfig, taking a url and publishableKey as plain string
     or undefined parameters and returning a SupabaseConfig.
     - missing when either is undefined or empty.
     - malformed when url isn't parseable by the URL constructor, or
       publishableKey is blank after trimming.
     - Accept the env values as parameters (don't read process.env inside
       this function) so it's trivially unit-testable without any env-var
       stubbing gymnastics.

4. src/features/auth/persistence/supabase-client.ts
   - getSupabaseClient, returning the Supabase client or null, memoized at
     module scope.
   - Internally: if Platform.OS is not web, return null (Phase 5 seam per
     decision 3 above), then call resolveSupabaseConfig reading
     EXPO_PUBLIC_SUPABASE_URL and EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY from
     process.env, and on anything other than ready, cache and return null
     (log a console.warn, never throw).
   - On ready, construct the client with auth options: flowType set to pkce,
     detectSessionInUrl set to false, persistSession set to true,
     autoRefreshToken set to true, and storage set to the AsyncStorage
     module -- and memoize the result.
   - This function must only ever be invoked lazily (from the provider's
     useEffect), never at module scope -- that's what keeps the static-render
     pass safe even though this file itself imports the real SDK.
   - Export a test-only reset hook, or document that tests should call
     jest.resetModules() between config scenarios -- needed because of the
     module-scope memoization.

5. src/features/auth/state/auth-provider.tsx
   - AuthStateContext and AuthActionsContext, plus useAuthState and
     useAuthActions hooks -- same shape as GoalProvider/UserProfileProvider
     (createContext of undefined, hook throws if used outside the provider).
   - AuthProvider takes children and holds AuthState in useState, starting
     at initializing.
     - A useEffect with empty deps gets the client via getSupabaseClient. If
       null, set state to guest with reason unconfigured and return (no
       subscription to clean up). Otherwise subscribe via the client's
       auth.onAuthStateChange callback, mapping each event/session through
       deriveAuthState, store the returned subscription, and return a
       cleanup that unsubscribes.
     - Wrap the subscribe call in try/catch -- if it throws synchronously,
       fall back to guest with reason error rather than leaving state stuck
       at initializing.
   - Actions, memoized like UserProfileProvider's actions object:
       - signInWithPassword takes email and password. If there is no
         client, resolve an error result without throwing. Otherwise
         forward to the client's signInWithPassword and return its error.
         Don't setState here -- the state transition comes from the
         onAuthStateChange subscription firing SIGNED_IN.
       - signOut follows the same pattern, forwarding to the client's
         signOut with scope local per the roadmap's "other devices remain
         signed in" requirement.
   - Always render both context providers wrapping children directly -- no
     conditional fallback branch, per decision 5.

## Order of implementation

1. package.json dependency add (yarn install) first -- everything else
   imports it.
2. auth-state.ts (pure model plus deriveAuthState) and its unit tests -- no
   SDK mocking needed, fastest feedback loop, and it's the piece every other
   layer depends on for correctness.
3. supabase-config.ts (pure env-validation) and its unit tests -- same
   reasoning, still no SDK mocking.
4. supabase-client.ts and its tests -- this is the first place you need to
   mock the supabase-js package. Test: missing config never constructs a
   client, malformed config never constructs a client, valid config
   constructs a client exactly once with the expected url, publishableKey,
   and the exact auth options (pkce flow, detectSessionInUrl false, storage
   referencing AsyncStorage), and repeated calls reuse the memoized
   instance.
5. auth-provider.tsx and its tests -- mock the getSupabaseClient function
   directly (simpler than mocking the SDK again), returning a fake client
   object you fully control per test (its onAuthStateChange,
   signInWithPassword, and signOut as jest mock functions). Cover:
   - unconfigured (getSupabaseClient returns null) leads to immediate guest
     state with reason unconfigured, children still render synchronously.
   - offline initialization: mock onAuthStateChange to invoke its callback
     synchronously with the INITIAL_SESSION event and a null session
     (guest), and separately with a cached session (authenticated) -- and
     don't give the fake client a getSession method at all, so the test
     fails loudly if the provider is accidentally calling it.
   - SIGNED_IN, SIGNED_OUT, and TOKEN_REFRESHED events update state
     correctly (assert the new session object is reflected after
     TOKEN_REFRESHED).
   - signInWithPassword and signOut forward arguments correctly and
     surface the resulting error, confirm state itself only changes via the
     subsequent simulated onAuthStateChange event, not the action call
     directly.
   - subscribing throws synchronously, falls back to guest with reason
     error instead of hanging.
   - unmount calls the subscription's unsubscribe method.
   - a synchronous-render assertion (no async act or await) proving
     children are present in the very first render pass, before any effect
     has flushed -- this is the concrete test for "no hydration gate."
6. Mount in src/app/_layout.tsx last, once the provider is verified in
   isolation.
7. Full verification with node .claude/scripts/verify.mjs, not the
   skip-export variant -- the expo export success with unset
   EXPO_PUBLIC_SUPABASE_* env vars is itself one of the exit criteria.
   Confirm no new console errors or warnings appear beyond the two
   known-benign ones documented in AGENTS.md.

## Risks and things to watch

- Metro/web resolution of supabase-js's transitive dependencies
  (realtime-js, postgrest-js, and their own websocket client dependency for
  Realtime). This is a well-trodden Expo/RN combination and should resolve
  fine for a web export out of the box, but if the export fails on module
  resolution, the fix is almost always Metro config, not application code --
  don't spend time working around it in auth-provider.tsx.
- Module-scope memoization in supabase-client.ts will leak across test
  files/cases unless each test resets it. Get this right before writing the
  missing versus malformed versus ready test matrix, or later tests will
  silently see an earlier test's cached client.
- process.env.EXPO_PUBLIC_* inlining happens at Expo's build/export time,
  not runtime -- don't try to read these vars anywhere except inside
  supabase-config.ts's caller, and don't assume you can change them without
  restarting the dev server or re-running the export.
- Do not add .env or .env.local entries with real Supabase project values --
  none exist yet (the hosted dev project from T153.2 hasn't happened), and
  none are needed for this ticket's tests or for the export to succeed. If
  you want to document the two var names for later, add commented-out
  lines to .env.example only, matching its existing header comment about
  EXPO_PUBLIC_ variables being bundle-inlined and never secret.
- Don't restore or extend the old access-password-style pattern -- that
  feature was fully removed in T111 and isn't a template to follow beyond
  the EXPO_PUBLIC naming convention itself.
