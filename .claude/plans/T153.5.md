## Design

### 1. `src/features/auth/model/auth-errors.ts` (pure, new)

Export a closed category union and a normalizing function. This is the "actionable UI category"
half of the boundary.

```ts
export type AuthErrorCategory =
  | 'invalidCredentials'   // wrong password AND unknown user both land here (Supabase already
                            // returns one generic code for both — do not try to split them)
  | 'unverifiedEmail'      // sign-in against an existing-but-unconfirmed account
  | 'accountAlreadyExists' // signup against an existing address — caller MUST render the same
                            // UI as a successful signup (see Notes below), never a distinct message
  | 'weakPassword'
  | 'expiredOrInvalidLink' // otp/flow-state expired, PKCE code already used, bad verifier
  | 'rateLimited'
  | 'offline'
  | 'unknown';             // fallback; still actionable ("Something went wrong. Try again.")

export function categorizeAuthError(error: unknown): AuthErrorCategory;
```

Implementation notes:
- Prefer the SDK's stable `code` field (present on `AuthApiError` since well before 2.112) over
  parsing `message` text, which is not a stable contract. Map (non-exhaustive, confirm exact
  strings against the installed SDK's `AuthApiError` `ErrorCode` type at implementation time):
  `invalid_credentials`/`invalid_grant` -> `invalidCredentials`; `email_not_confirmed` ->
  `unverifiedEmail`; `user_already_exists`/`user_already_registered` -> `accountAlreadyExists`;
  `weak_password` -> `weakPassword`; `otp_expired`, `flow_state_expired`, `bad_code_verifier` ->
  `expiredOrInvalidLink`; `over_email_send_rate_limit`, `over_request_rate_limit` ->
  `rateLimited`.
- Detect `AuthRetryableFetchError` (or a plain `TypeError` from a failed `fetch`, which is what
  jsdom/offline tests will throw) -> `offline`.
- Anything else (including non-Error values, since call sites may pass `unknown`) -> `unknown`.
- This module must not log or import anything from the observability module below — keep it a
  pure mapping so it's trivial to exhaustively table-test.
- **Do not** try to make `accountAlreadyExists` invisible at this layer. The actual enumeration
  defense for signup is a call-site behavior owned by T153.8 (treat `accountAlreadyExists` and a
  successful signup identically in the UI). This ticket's job is only to give T153.8 a stable,
  named category to branch on — record this as the interface contract in a comment so T153.8
  doesn't need to re-derive it.

### 2. `src/features/auth/model/redact.ts` (pure, new)

Two exports, both used by the observability module and directly unit-tested:

```ts
export function redactValue(value: unknown, depth?: number): unknown;
export function redactUrl(rawUrl: string): string;
```

`redactValue`:
- Deep-walks strings/arrays/plain objects up to a bounded depth (e.g. 6) to avoid pathological
  recursion; anything deeper collapses to `'[redacted-nested]'`.
- For string leaves, run a regex pipeline (in this order, since JWT-shaped values would otherwise
  partially match the generic long-token pattern):
  1. email: `/[\w.+-]+@[\w.-]+\.[\w-]+/g` -> `[redacted-email]`
  2. JWT-like (three dot-separated base64url segments):
     `/[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}/g` -> `[redacted-jwt]`
  3. generic long opaque token (refresh tokens, PKCE codes/verifiers — base64url, 20+ chars, no
     dots): `/(?<![\w-])[A-Za-z0-9_-]{20,}(?![\w-])/g` -> `[redacted-token]`
- For object leaves, additionally check the **key name** case-insensitively against a deny-list
  (`email`, `password`, `access_token`, `refresh_token`, `provider_token`,
  `provider_refresh_token`, `token`, `token_hash`, `code`, `code_verifier`, `apikey`,
  `authorization`) and fully replace the value with `[redacted]` regardless of whether it matches
  a content regex — this is what catches short passwords and other values that don't look like
  tokens. This is the "nested identifiers" case from the exit criteria (e.g.
  `{ context: { user: { email }, session: { access_token } } }`).

`redactUrl`:
- Parses with the `URL` constructor (falls back to returning `'[unparseable-url]'` on throw,
  rather than passing raw invalid input through).
- Walks both `url.searchParams` and, separately, `new URLSearchParams(url.hash.replace(/^#/, ''))`
  (Supabase's implicit/error flows can put `error`, `error_description`, `access_token` in the
  fragment, not just the query) — for any param name in the same deny-list as above, replace its
  value with `[redacted]`.
- After stripping known params, run the *remaining* full URL string through `redactValue`'s
  regex pipeline too (not just the deny-listed params) as defense-in-depth for an
  `error_description` or similarly free-text param that embeds an email or token inside a
  sentence rather than as its own param value.
- Returns the reconstructed URL string (`origin + pathname + '?' + sanitizedSearch + '#' +
  sanitizedHash`, omitting empty parts).

### 3. `src/features/auth/observability/auth-observability.ts` (new folder, new file)

This is the one boundary every future Auth route/action must import instead of calling
`console.*` or `track()` directly.

```ts
import { track } from '@vercel/analytics';
import { Platform } from 'react-native';
import { redactValue } from '@/features/auth/model/redact';
import type { AuthErrorCategory } from '@/features/auth/model/auth-errors';

export function logAuthWarning(message: string, detail?: unknown): void {
  console.warn(message, detail === undefined ? undefined : redactValue(detail));
}

export function trackAuthEvent(name: string, category?: AuthErrorCategory): void {
  if (Platform.OS !== 'web') return;
  track(name, category === undefined ? undefined : { category });
}
```

Key design choice: `trackAuthEvent`'s second parameter is typed as `AuthErrorCategory | undefined`,
**not** `unknown`/`Record<string, unknown>`. This makes it a structural impossibility to pass a
raw error, email, or URL into Analytics through this function — the type system enforces the
"never place tokens/emails in analytics events" roadmap requirement, rather than relying solely on
redaction-regex correctness for the analytics path. `logAuthWarning` still accepts arbitrary
`detail` (console logging is more forgiving/useful for debugging) but always redacts before
printing.

### 4. `redactUrl` reused for the root Analytics `beforeSend`

Add, in `auth-observability.ts` (keep `redact.ts` free of any `@vercel/analytics` type import so
it stays a dependency-free pure module):

```ts
export function sanitizeAnalyticsEvent<T extends { url: string }>(event: T): T {
  return { ...event, url: redactUrl(event.url) };
}
```

Confirm the real `BeforeSendEvent` type's field name at implementation time (see Context note
above); adjust the generic constraint if it's not literally `url`.

Then in `src/app/_layout.tsx`, change only:

```tsx
{Platform.OS === 'web' && <Analytics beforeSend={sanitizeAnalyticsEvent} />}
```

Keep this a one-line wire-up with no logic in `_layout.tsx` itself, so all behavior is covered by
unit tests on `sanitizeAnalyticsEvent`/`redactUrl` rather than requiring a render test of
`_layout.tsx`.

## File/order plan

1. `src/features/auth/model/redact.ts` + `src/features/auth/model/__tests__/redact.test.ts` first
   — no dependency on anything else, and everything downstream needs it.
2. `src/features/auth/model/auth-errors.ts` + `__tests__/auth-errors.test.ts` — independent of
   step 1, can be done in parallel, but land before step 3 since the observability module imports
   its type.
3. `src/features/auth/observability/auth-observability.ts` +
   `src/features/auth/observability/__tests__/auth-observability.test.ts` — depends on 1 and 2.
   Test with the same `jest.mock('@vercel/analytics', ...)` pattern as
   `user-profile-provider.analytics.test.tsx`, plus a `jest.spyOn(console, 'warn')`. Assert:
   - `logAuthWarning` redacts emails/tokens/nested identifiers before reaching the spy.
   - `trackAuthEvent` is only ever called with `{ category }` or no second arg — never a raw
     error/object — and is a no-op off web (mirror the existing `Platform.OS` test pattern).
4. Wire `sanitizeAnalyticsEvent` into `src/app/_layout.tsx`'s `<Analytics />` — last, since it's
   the only piece touching a shared/rendered file and has no test of its own (covered by step 1's
   `redactUrl` tests plus the adapter's trivial pass-through).
5. Do not touch `auth-provider.tsx`'s existing `console.warn` calls (config-malformed,
   subscribe-failure) as part of *this* ticket unless it's a trivial one-line swap to
   `logAuthWarning` — call it out as an assumption if you make that swap, since T153.5's Notes
   scope this ticket to "before any Auth route is added" (i.e., establishing the boundary), and
   T153.4's two existing warnings are pre-existing, config-only, and don't currently carry
   emails/tokens. Prefer making the swap for consistency (low risk, keeps one console call site
   pattern app-wide) but it is not exit-criteria-blocking.

## Test data for the exit criteria (feed through `redactValue`/`redactUrl`/`categorizeAuthError`)

Build one shared fixture set (e.g. a small `__tests__/fixtures.ts` or inline per test file) reused
across `redact.test.ts` and `auth-observability.test.ts` covering:
- A representative `AuthApiError`-shaped object with `code: 'invalid_credentials'`, `status: 400`.
- `code: 'email_not_confirmed'`, `code: 'user_already_exists'`, `code: 'weak_password'`,
  `code: 'over_request_rate_limit'`, `code: 'otp_expired'`.
- A network-failure `TypeError` ("Failed to fetch").
- A raw string/object containing an email (`user@example.com`), a password-like short string
  under an explicit `password` key, a JWT-shaped triple-segment string, a long opaque
  refresh-token-shaped string, a PKCE `code`/`code_verifier` pair, and a nested identifier 2-3
  levels deep (e.g. `{ session: { user: { email, id } } }`).
- A callback URL with both query (`?code=...&error=...`) and fragment
  (`#access_token=...&refresh_token=...&error_description=...`) sensitive data, to directly test
  `redactUrl`/`sanitizeAnalyticsEvent` against the "callback query and fragment data" exit
  criterion.

Assert two things per case, not just one: (a) none of the original sensitive substrings survive
in the redacted output (the negative/security assertion the exit criteria demands), and (b) at
least one non-sensitive/structural part of the input survives unchanged (proves the function
redacts rather than blanking everything, keeping UI categories/log context actionable).

## Non-goals for this iteration

- No route/UI work (sign-in, sign-up, recovery, callback screens) — those are later tickets that
  will *consume* `categorizeAuthError`/`logAuthWarning`/`trackAuthEvent`.
- No per-route UI copy strings mapping `AuthErrorCategory` -> user-facing text — each route ticket
  owns its own copy since phrasing is contextual (e.g. `invalidCredentials` reads differently on
  sign-in vs. a security/password-change route).
- Don't swap `auth-provider.tsx`'s two `console.warn` call sites unless it's the trivial
  same-signature substitution described in step 5.
