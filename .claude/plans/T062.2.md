# T062.2 — Filter Stats and Home reads to exclude Kentei-assessment sessions

## Context confirmed in code (2026-08-14, branch already claimed)

- `PracticeSessionRecord.origin?: 'assessment'` already exists in
  `src/features/stats/model/practice-history.ts` (from merged T062.1). Absent = regular session.
- Four independent read sites pull `sessions` straight from `usePracticeHistory()` with no shared
  filtered intermediate:
  1. `src/app/stats/index.tsx` — one `sessions` pull feeds `aggregatePracticeStats(sessions)`
     (Overview + By-trick) and `useSelectNeglectedTricks(..., sessions)` (Needs-attention) via
     `selectNeglectedFocusedTricks`.
  2. `src/app/stats/[trickId].tsx` — its own separate `usePracticeHistory()` call; `sessions` feeds
     both the `trickSessions` filter/sort (Past seshes list + `trickName` fallback) and
     `bestsByDuration`'s calls to `getPersonalBest(sessions, trickId, durationMs)`.
  3. `src/app/index.tsx` — `sessions` is passed into `createHomeSummary({ ..., sessions, now })`,
     which internally derives `recentSession`, `momentum`, `currentStreak`, and
     `timeLoggedWindows` all from that one array. `createHomeSummary` itself must stay
     origin-agnostic (it is a pure model function with its own unit tests); filter at the call site
     in `index.tsx` before invoking it.
  4. `src/features/profile/state/kentei-rank-auto-promotion.tsx` reads `usePracticeHistory()`
     independently and must NOT be touched — it needs to keep seeing assessment-origin landings
     for rank auto-promotion. No code change here, only a regression test (see below).
- `usePracticeHistory()` / `PracticeHistoryProvider` itself must not change — confirmed no shared
  filtered selector is exposed there today, and the task explicitly forbids adding one at that
  level (would break `KenteiRankAutoPromotion`).

## Implementation order

### 1. Add a shared pure selector to the model (do this first — everything else depends on it)

In `src/features/stats/model/practice-history.ts`, add:

```ts
export function selectRegularSessions(
  sessions: readonly PracticeSessionRecord[],
): readonly PracticeSessionRecord[] {
  return sessions.filter((session) => session.origin === undefined);
}
```

Place it near `hasPriorLaceForTrick`/`isFirstLaceForTrick` (other small pure selectors already
living in this file), with a one-line comment: excludes Kentei-assessment-sourced sessions from
Stats/Home reads; `KenteiRankAutoPromotion` deliberately reads unfiltered history and must not
call this.

Add unit tests in `src/features/stats/model/practice-history.test.ts` (new `describe('selectRegularSessions', ...)`
block near the other small-selector `describe`s): a session with no `origin` is kept, a session
with `origin: 'assessment'` is dropped, and a mixed array preserves order of the kept sessions.

### 2. Apply the filter at each of the three UI read sites (independent of each other, do in any order)

- **`src/app/stats/index.tsx`**: immediately after `const { sessions } = usePracticeHistory();`,
  derive `const regularSessions = selectRegularSessions(sessions);` and use `regularSessions`
  everywhere `sessions` is currently used (`aggregatePracticeStats(regularSessions)` and the
  `useSelectNeglectedTricks(selectedTrickIds, customTricks, regularSessions)` call). Don't rename
  the `usePracticeHistory()` destructure itself — keep the filter as an explicit local step so a
  future reader sees exactly where the exclusion happens.

- **`src/app/stats/[trickId].tsx`**: same pattern — `const { sessions } = usePracticeHistory();`
  then `const regularSessions = selectRegularSessions(sessions);`. Replace both uses of `sessions`
  inside the `trickSessions` and `bestsByDuration` `useMemo`s (including inside
  `getPersonalBest(sessions, trickId, durationMs)`) with `regularSessions`, and add
  `regularSessions` (in place of `sessions`) to those `useMemo` dependency arrays.

- **`src/app/index.tsx`**: `const { sessions } = usePracticeHistory();` then
  `const regularSessions = selectRegularSessions(sessions);`. Use `regularSessions` for:
  - the `summaryNow` reduce (`sessions.reduce(...)` → `regularSessions.reduce(...)`) — an
    assessment session's `completedAt` shouldn't be treated as "now" for display purposes either,
    since its session is otherwise invisible to Home;
  - the `createHomeSummary({ ..., sessions: regularSessions, now: summaryNow })` call;
  - the `useMemo` dependency array (`regularSessions` instead of `sessions`).

  Import `selectRegularSessions` from `@/features/stats/model/practice-history` in all three files.

## Risks / non-obvious things for the implementer

- `stats/index.tsx`'s `EmptyStats` branch triggers on `stats.sessionCount === 0` computed from the
  *filtered* `regularSessions` — a profile with only assessment-origin history will now correctly
  show the empty state even though `PracticeHistoryProvider` isn't empty. This is intended (matches
  "Stats reflects only regular sessions"), just don't be surprised by it in manual QA.
- Do not filter inside `aggregatePracticeStats`, `selectNeglectedFocusedTricks`, `getPersonalBest`,
  or `createHomeSummary` themselves — keep them origin-agnostic pure functions and filter only at
  the three call sites. This matches the task's explicit instruction not to push filtering into
  shared plumbing, and keeps those functions' existing unit tests (which construct
  `PracticeSessionRecord`s without `origin`) valid unchanged.
- `[trickId].tsx`'s `bestsByDuration` builds a `durations` Set from `trickSessions` and then calls
  `getPersonalBest` separately for each — make sure *both* the list-driving `trickSessions` value
  and the `getPersonalBest(sessions, ...)` argument move to `regularSessions`; it's easy to filter
  the visible list and miss the personal-best computation since they live in the same `useMemo`
  but reference `sessions` independently.
- Expo-router's `useLocalSearchParams` mock must use `jest.requireActual('expo-router')` inside the
  factory, not a bare `require('expo-router')` — the latter recurses into the mock factory itself
  and blows the call stack (confirmed by hitting `RangeError: Maximum call stack size exceeded`
  while probing this during planning).
