# T248.2 — App-level local-save warning and retry action

## Context already in place (T248.1, merged)

`src/shared/persistence/storage.ts` exports:

```ts
export type LocalDurabilityStatus<State> =
  | { readonly status: 'saved' }
  | { readonly status: 'failed'; readonly snapshot: State; readonly retry: () => Promise<ScopedSaveOutcome> };
```

Each of the five domain providers exposes a `use<Domain>Durability()` hook reading this from its
own context, distinct from the existing `*Sync`/`SyncStatus` contexts:

- `useGoalDurability()` — `src/features/goals/state/goal-provider.tsx`
- `useCustomTrickDurability()` — `src/features/custom-tricks/state/custom-trick-provider.tsx`
- `useNoteDurability()` — `src/features/notes/state/note-provider.tsx`
- `useUserProfileDurability()` — `src/features/profile/state/user-profile-provider.tsx`
- `usePracticeHistoryDurability()` — `src/features/stats/state/practice-history-provider.tsx`

Each domain's own `retry()` closure already captures that domain's latest failed snapshot and
replays it through that domain's own serial write queue (`createWriteQueue` in `storage.ts`), and
each domain already resets to `{ status: 'saved' }` synchronously on an identity/generation switch
(see `use-identity-scoped-domain.ts`). This task must not duplicate any of that per-domain
mechanics — it only aggregates five already-correct signals and adds one UI surface.

Provider nesting order (`src/app/app/_layout.tsx`): `IdentityProvider > CustomTrickProvider >
UserProfileProvider > PracticeHistoryProvider > NoteProvider > GoalProvider >
SyncCoordinatorProvider > AppThemeProvider > (KenteiRankAutoPromotion, AppTabs)`. All five
`use*Durability()` hooks are only callable from inside `GoalProvider` (the innermost of the five),
i.e. from `AppThemeProvider` downward.

## Design decisions

1. New shared aggregation hook, `src/shared/persistence/use-app-local-durability.ts`:
   - Calls all five `use*Durability()` hooks directly (no new context needed to *read* the five
     statuses — they're already each individually available wherever this hook is called).
   - Builds a small domain-labelled list, e.g.:
     ```ts
     export interface AppLocalDurabilityDomainEntry {
       readonly domain: 'goals' | 'customTricks' | 'notes' | 'profile' | 'practiceHistory';
       readonly label: string; // 'Goals', 'Custom tricks', 'Notes', 'Profile', 'Practice history'
       readonly status: LocalDurabilityStatus<unknown>;
     }
     ```
     (Cast/narrow to `LocalDurabilityStatus<unknown>` at the call site — the aggregator only ever
     needs `status`/`retry`, never the domain-specific `State` shape.)
   - Derives `failedEntries` via a pure, separately-exported, unit-testable function
     `deriveFailedDomainLabels(entries): readonly string[]` (or similar) so the precedence/labeling
     logic has a fast non-DOM test, mirroring `deriveSyncStatus` in `src/shared/sync/sync-status.ts`.
   - Exposes:
     ```ts
     export interface AppLocalDurabilitySummary {
       readonly hasFailure: boolean;
       readonly failedLabels: readonly string[];
       readonly isRetrying: boolean;
       readonly retryAll: () => Promise<void>;
     }
     ```
   - `retryAll` dedup logic: track an internal `useRef<boolean>` (`isRetryInFlightRef`) plus
     `isRetrying` state for rendering. On call: if already in flight, return immediately (no-op) —
     this is the "no duplicate concurrent attempts" guarantee, enforced at the aggregator, not by
     relying on each domain's write queue to make a second call harmless. Otherwise, snapshot the
     currently-failed entries' `retry` closures (evaluated at call time, so "latest snapshot" per
     the exit criteria falls out of reading `durability` fresh at call time rather than memoizing
     stale closures), set `isRetrying = true`, run all of them concurrently via
     `Promise.allSettled`, then clear the flag in a `finally`. Cross-domain concurrency is fine and
     desired (five independent write queues); only concurrent re-invocation of the aggregate
     "Retry" action itself is guarded against.
   - Do not add a `SyncStatus`-style `kind` union or merge with cloud sync data — keep this file
     import-free of anything under `src/shared/sync/`.

2. New presentational component, `src/components/local-durability-warning-banner.tsx`:
   - Calls `useAppLocalDurability()` (or whatever the hook above is named) and renders `null` when
     `!hasFailure`.
   - When failing: a single `View` with `accessibilityRole="alert"` and
     `accessibilityLiveRegion="assertive"` (RN Web maps these to `role="alert"` /
     `aria-live="assertive"`; this is the "accessibly announced" requirement — there's no existing
     announcer utility in the repo to reuse, so this is new). Content:
     - Copy that names the failing domain(s) by label and explicitly says local/on-this-device
       save failed — explicitly avoid any wording resembling `SyncStatus`'s cloud-facing copy
       (`formatPendingCount`, "conflict", "syncing"). Example: "Some changes aren't saved on this
       device yet: Goals, Notes. This is separate from cloud sync." Keep exact copy simple; product
       wording isn't load-bearing for the exit criteria, but the *distinction* from cloud-sync
       status is.
     - A `Pressable`/button labelled "Retry" (`accessibilityRole="button"`, disabled while
       `isRetrying`, calling `retryAll()`). While `isRetrying`, swap label to "Retrying…" and keep
       `disabled`.
     - After a retry that doesn't fully clear the failure (some domain still failing), the banner
       stays mounted with the same alert semantics and updated domain list — no separate "retry
       failed" sub-state is needed beyond what `hasFailure`/`failedLabels` already re-derive.
   - Style with `AppColors.red` background (existing warning/danger token — see
     `src/constants/theme.ts`) and `AppColors.paper`/`cream` text for contrast, using the existing
     `ThemedText`/plain `View`/`Pressable` primitives already used elsewhere (e.g.
     `src/components/app-tabs.web.tsx`'s `AppFooterBar`) rather than introducing new theme tokens.
     Do not gate meaning on color alone — the text content already carries it.
   - No route/pathname awareness in this component at all; visibility across route changes is a
     consequence of *where* it's mounted (next point), not of anything in this component.

3. Wiring, `src/app/app/_layout.tsx`:
   - Render `<LocalDurabilityWarningBanner />` as a sibling of `<AppTabs />`, inside
     `<AppThemeProvider>`, before `<AppTabs />`:
     ```tsx
     <AppThemeProvider>
       <KenteiRankAutoPromotion />
       <LocalDurabilityWarningBanner />
       <AppTabs />
     </AppThemeProvider>
     ```
   - Rationale for this placement over embedding it inside `app-tabs.web.tsx`'s `CustomTabList`:
     `CustomTabList`'s nav layer is `position: absolute; inset: 0` relative to the `<Tabs>`
     component's own root view (React Native's default `position: 'relative'` on `View` makes
     every `View` a positioned ancestor, so this absolute layer is scoped to `Tabs`' own box, not
     the whole page). A sibling rendered one level up, before `<AppTabs />`, sits in normal flow
     above that box and pushes it down via ordinary flex layout — it is never occluded by the tab
     nav or footer bar, and it renders once at the layout level so it survives every route change
     under `/app/*` without remounting (`Slot`/`TabSlot` only swap the routed content beneath it,
     never this layout component). This also means the same JSX line covers both `AppTabs`
     variants (native `NativeTabs`-based `app-tabs.tsx` and web's `app-tabs.web.tsx`) without any
     platform-specific insertion — native rendering is unverified here (native is out of scope per
     `AGENTS.md`'s current platform scope) but this placement doesn't require native-specific code
     to reach it, so it costs nothing extra to leave in.
   - This file lives in `src/app` (a composition root) importing a component from `src/components`
     and a hook from `src/shared/persistence` — consistent with the existing "composition roots
     wire feature/shared code together" rule; the reusable pieces themselves live outside `src/app`.

## Implementation order

1. `src/shared/persistence/use-app-local-durability.ts` + a colocated
   `use-app-local-durability.test.ts` covering the pure derivation function and the hook's
   dedup/retry-all logic with lightweight fake `LocalDurabilityStatus` inputs (no real providers
   needed for this file — mock the five `use*Durability` imports).
2. `src/components/local-durability-warning-banner.tsx` + a colocated
   `local-durability-warning-banner.test.tsx` ("app-shell component test" from the exit criteria):
   mock `@/shared/persistence/use-app-local-durability` directly, and assert:
   - renders nothing when `hasFailure` is `false`.
   - renders one alert-role element naming the failed domain(s) when `hasFailure` is `true`.
   - pressing Retry calls `retryAll` once; pressing it again while `isRetrying` is `true` does not
     call `retryAll` a second time (assert the mock's call count, proving the button is actually
     disabled/no-op, not just visually styled as disabled).
   - the banner instance does not remount when an unrelated sibling ("routed content" stand-in)
     changes across rerenders — mount `<LocalDurabilityWarningBanner />` next to a toggling sibling
     in a small test harness and confirm the banner's own effect/mount marker only fires once.
3. Wire into `src/app/app/_layout.tsx` (the two-line change described above).
4. `src/app/app/__tests__/local-durability-warning.integration.test.tsx` (or a similarly-named
   file next to the existing `src/app/app/__tests__/` suite) — the "fully wired five-provider
   integration test" from the exit criteria. Follow
   `src/shared/sync/logout-guard.discard-isolation.test.tsx`'s harness precedent exactly:
   - Mock `@react-native-async-storage/async-storage` with the real jest async-storage mock.
   - Mock every `*-sync-transport` module and `getSupabaseClient` the same way that file does, so
     `SyncCoordinatorProvider` never touches real Supabase and its background sync activity can't
     interfere with the local-durability assertions.
   - Mount the real five providers (`CustomTrickProvider > UserProfileProvider >
     PracticeHistoryProvider > NoteProvider > GoalProvider > SyncCoordinatorProvider`) plus
     `AppThemeProvider` plus the new `LocalDurabilityWarningBanner`, with a small "route" stand-in
     sibling that changes across renders (to stand in for a route change, since exercising the
     real Expo Router is unnecessary to prove "no remount / stays visible").
   - Use `jest.spyOn(AsyncStorage, 'setItem')` keyed on each domain's storage-key constant
     (`GOALS_STORAGE_KEY`, `NOTES_STORAGE_KEY`, `CUSTOM_TRICKS_STORAGE_KEY`,
     `USER_PROFILE_STORAGE_KEY`, `PRACTICE_HISTORY_STORAGE_KEY` — all from each domain's
     `*-persistence.ts`) to fail writes for one or more domains, exactly like
     `goal-provider.durability.test.tsx`'s existing per-domain durability tests.
   - Drive one mutation per domain that goes through the write queue (`addGoal`, `addNote`/
     equivalent, `addCustomTrick`, a profile action such as `addSelectedTrick`, and a practice-
     history action — check each provider's `use*Actions()` for the exact exported mutator name
     before writing this test) to produce two simultaneous domain failures.
   - Assert: exactly one alert-role banner is present (not two, not one-per-domain) naming both
     failing domains; it remains present after toggling the "route" stand-in; pressing Retry once
     resolves both domains' writes (restore/relax the `setItem` spy first, matching
     `goal-provider.durability.test.tsx`'s retry test) and the banner then disappears; a second,
     concurrent Retry press while the first is still in flight does not double-invoke either
     domain's `retry()` (assert via a spy/count on the write path, e.g. counting `setItem` calls
     for that domain's key across the retry window).
5. Run `yarn eslint` on the changed/added files, then full `yarn tsc --noEmit` (state/persistence
   contract change per the verification table), then the affected test files plus
   `src/features/*/state/*.durability.test.tsx` (unchanged, but confirms nothing in this task
   regressed the underlying per-domain contracts) before considering this done. A full
   `yarn expo export --platform web` pass is warranted given this changes the app-shell layout
   composition (`_layout.tsx`), not just an isolated feature file.
6. Manually verify in the real web dev server (per `AGENTS.md`'s browser-verification guidance):
   force a local-save failure (e.g. temporarily throw from one domain's `save`, or use browser
   devtools to make `localStorage.setItem` throw — do not ship this override), confirm the banner
   is legible and the Retry control operates at a 320px viewport width, then revert the temporary
   failure injection.

## Risks / things to double-check while implementing

- Confirm the exact action names before writing the integration test — only `useGoalActions`'s
  `addGoal` was directly inspected in planning; verify `useNoteActions`, `useCustomTrickActions`,
  `useUserProfileActions`, and `usePracticeHistoryActions`' exact mutator signatures (some may
  require constructing a domain-shaped input object, e.g. a full `PracticeHistoryRecord`).
- `PracticeHistoryProvider` and `UserProfileProvider` may have side effects on other providers
  (e.g. `GoalProvider`'s `addGoal` calls `addSelectedTrick` internally) — when driving mutations in
  the integration test, trigger each domain's mutation independently and confirm via each
  provider's own `use<Domain>Durability()` (or a debug exposer) that only the intended domain
  actually failed, to avoid a flaky test that accidentally fails on cross-domain writes.
- Double check that `AppThemeProvider`'s `StyledThemeProvider` and the other context providers
  above it in `_layout.tsx` don't themselves render a wrapping `View` — if any of them do, the
  flex-column sibling-pushes-content-down reasoning above needs rechecking against that node
  instead of assuming a flat parent.
- Do not let this task's banner or hook read anything from `src/shared/sync/` — the Notes
  explicitly forbid combining local durability with `SyncStatus`; a `grep` for `sync` imports in
  the two new files before finishing is a cheap self-check.
- Keep the new hook and component out of `src/app` entirely (only the two-line wiring belongs
  there) so the module-boundary rule in `AGENTS.md` holds.
