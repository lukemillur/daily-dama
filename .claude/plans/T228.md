## 1. What was verified while planning (do not re-derive)

All of this was measured on this branch, on 2026-09-04, with Yarn Classic 1.22.22 and Node 24. Treat it as
established ground truth; re-run only the two live commands in step 8.

**A. The false-success path is real and locally reproducible without touching DNS.**

```sh
yarn --https-proxy http://127.0.0.1:9 --proxy http://127.0.0.1:9 audit --json
```

produces:

- exit status **1**
- stdout: exactly one line, `{"type":"info","data":"Visit https://yarnpkg.com/en/docs/cli/audit for documentation about this command."}` — no advisories, **no `auditSummary`**
- stderr: `{"type":"warning","data":"../../../../package.json: No license field"}`, a plain-text Node
  `DEP0169` deprecation warning, and
  `{"type":"error","data":"Error: https://registry.yarnpkg.com/-/npm/v1/security/audits: tunneling socket could not be established, cause=connect ECONNREFUSED 127.0.0.1:9\n    at ..."}`

The current script reads stdout only, ignores `result.status`, ignores stderr, and reports
`no high/critical advisories found` with exit 0. This is the exact defect from `SHIP_READINESS_AUDIT.md`
section 1 / `outputs/ship-readiness/T225.md` finding 3.

Note two traps in that output: yarn's **generic failure exit code is 1, which is bit-identical to the
`EXIT_INFO` severity bit**, so exit status can never discriminate failure from a legitimate advisory mask;
and stdout is **not empty** on failure, so "stdout had no advisories" is not a usable signal either.

**B. The healthy path.** `yarn audit --json` on this branch: exit status **12**, stdout is 25 NDJSON lines
(~110 KB), containing only `auditAdvisory` (24 lines, 7 unique advisory ids) and exactly one `auditSummary`:

```json
{"type":"auditSummary","data":{"vulnerabilities":{"info":0,"low":0,"moderate":13,"high":11,"critical":0},
 "dependencies":1158,"devDependencies":0,"optionalDependencies":0,"totalDependencies":1158}}
```

Stderr on the healthy path still carries the `No license field` warning and the non-JSON Node deprecation
lines. **Unparseable stderr lines are normal — never fail on them.**

**C. The exit code is computed exactly from the summary counts.** From
`/opt/homebrew/Cellar/yarn/1.22.22/libexec/lib/cli.js:59670-59680` (`audit`'s `run()`):

```js
var EXIT_INFO = 1; var EXIT_LOW = 2; var EXIT_MODERATE = 4; var EXIT_HIGH = 8; var EXIT_CRITICAL = 16;
var exitCode = (vulnerabilities.info ? EXIT_INFO : 0) + (vulnerabilities.low ? EXIT_LOW : 0)
  + (vulnerabilities.moderate ? EXIT_MODERATE : 0) + (vulnerabilities.high ? EXIT_HIGH : 0)
  + (vulnerabilities.critical ? EXIT_CRITICAL : 0);
```

It is a presence mask (nonzero count → bit), computed *before* reporting, so `--level` genuinely cannot
affect it. Observed: `moderate 13 → 4`, `high 11 → 8`, total `12`. So `status === maskOf(summary)` is an
exact, deterministic invariant — safe to assert, not a heuristic.

**D. `auditSummary` is emitted on every completed audit, including a clean one.** `Audit.prototype.report()`
(same file, line 59906) ends with `this.summary()`, and `Audit.prototype.summary()` returns early only when
`this.auditData` is undefined — which happens only when the audit request never completed. So "exactly one
well-formed `auditSummary`" is a precise completion signal, and its absence is precisely the incomplete case.

**E. Advisory line counts do NOT match summary counts.** The summary counts findings/paths (high: 11) while

zero/nonzero per severity is comparable (see the consistency rules in step 3).

## 3. Failure/pass policy the new script implements

Exit codes (documented in the script header and README):

- **0** — audit provably completed and every gated advisory is accepted.
- **1** — audit completed; at least one un-accepted `high`/`critical` advisory. Policy failure.
- **2** — the audit could not be trusted to have completed. Operational/blocked failure.

Every exit-2 message is prefixed `[check-dependency-audit] BLOCKED:` so a log reader can tell a real finding
from an unavailable verification. Exit 2 is a failure, never a pass.

Classification rules, in order (all of these produce exit 2):

1. `result.error` is set (spawn failure: `ENOENT`, `ENOBUFS`, `ETIMEDOUT`). Report `error.code` and message.
2. `result.signal` is non-null (killed, e.g. by the timeout below).
3. `result.status === null` or not an integer (process did not exit normally).
4. Any JSON line on **stdout or stderr** with `type === "error"`. Include its `data` (first ~500 chars) in the
   failure message — this is what turns the reproduction in step 1A into a legible network diagnosis.
5. Zero or more than one `auditSummary` line on stdout.
6. The single `auditSummary`'s `data.vulnerabilities` is missing, not an object, or lacks a finite
   non-negative integer for each of `info`, `low`, `moderate`, `high`, `critical`.
7. A line with `type === "auditAdvisory"` whose `data.advisory` is missing, or whose `advisory.id` is missing,
   or whose `advisory.severity` is not one of the five known severities. (The current `catch { continue }` that
   silently drops unparseable lines is part of the defect; a *malformed advisory* must be loud.)
8. Mask inconsistency: `result.status !== maskOf(summary.data.vulnerabilities)` using the constants in 1C.
9. Report inconsistency: the summary reports `high > 0` or `critical > 0`, but zero parsed advisories carry
   that severity. (`report()` iterates `auditData.actions`; if npm ever returns advisories with no
   corresponding actions, gated advisories would be invisible while the summary still counted them. Fail
   rather than pass green.)
10. `security/accepted-dependency-advisories.json` is unreadable, not a JSON array, has a duplicate id, or has
    an entry failing the field validation in step 5.

Deliberately **not** failures:

- A nonzero `result.status` that equals the summary mask — this is the whole point of the ticket. A tree with
  only moderate advisories exits 4 and must pass.
- Unparseable lines on **stderr** (Node deprecation warnings are normal, see 1B).
- Unparseable lines on stdout when a valid summary is present: count them and print the count as a notice, but
  do not fail. Rule 5 is the completion gate; noise tolerance keeps the gate from breaking on cosmetic yarn
  output changes.
- An accepted advisory that no longer appears in the audit, or that is now below the gated severity. Print a
  notice suggesting the entry may be removable; keep exit 0. (A stale allowlist entry is not a security risk,
  and a fatal check here would be a flaky gate.)

## 4. Step-by-step: rewrite `security/scripts/check-dependency-audit.mjs`

Keep it one file, ESM, no dependencies, same style as `select-ci-scans.mjs`. Export the pure pieces so the
test suite drives them without a network or a subprocess; keep the impure `spawnSync` and file read in `main`.

Replace the header comment with a present-tense statement of the invariants (per AGENTS.md, comments explain
the current constraint, not ticket chronology): the `--level` exit-code behaviour, the mask semantics from 1C,
and that `auditSummary` presence is the completion signal because yarn exits 1 on generic failure.

Exports and shapes:

- `const GATED_SEVERITIES = new Set(["high", "critical"])` and
  `const SEVERITY_EXIT_BITS = { info: 1, low: 2, moderate: 4, high: 8, critical: 16 }`.
- `export function summaryExitMask(vulnerabilities)` → integer mask.
- `export function parseAuditStreams(stdout, stderr)` →
  `{ advisories: Advisory[], summaries: object[], yarnErrors: string[], malformedAdvisories: string[], unparsedStdoutLines: number }`.
  Split on `\n`, `trim()`, skip empties. stdout lines that fail `JSON.parse` increment `unparsedStdoutLines`;
  stderr lines that fail `JSON.parse` are ignored entirely. Dedupe advisories by `String(advisory.id)` (yarn
  emits one line per dependency path — keep the existing dedupe and say why in a comment).
- `export function classifyAuditRun(result)` → `{ ok: true, advisories, summary } | { ok: false, reasons: string[] }`,
  applying rules 1-9 above. Collect *all* applicable reasons rather than returning on the first, so a failing
  CI log explains everything at once.
- `export function loadAcceptedAdvisories(path)` → validated array (step 5).
- `export function evaluatePolicy({ advisories, summary, acceptedAdvisories })` →
  `{ gated, unaccepted, notices }`.
- `export function runDependencyAuditGate({ runAudit, acceptedAdvisories, log = console.log, logError = console.error })`
  → exit code `0 | 1 | 2`. `runAudit()` returns a spawn-result-shaped object; this is the seam the tests use.
- `function main()` — builds the real `runAudit` and reads the real allowlist path, then
  `process.exitCode = runDependencyAuditGate({...})`. Wrap the allowlist load in try/catch and map a throw to
  exit 2 with a `BLOCKED:` message (rule 10). Guard invocation with
  `if (process.argv[1] === fileURLToPath(import.meta.url)) main();`, matching `select-ci-scans.mjs`.
  (Node resolves `argv[1]` to an absolute path, so CI's relative `node security/scripts/...` invocation still
  matches — `select-ci-scans.mjs` already relies on this.)

Real `runAudit`:

```js
spawnSync("yarn", ["audit", "--json"], {
  cwd: REPO_ROOT, encoding: "utf8",
  maxBuffer: 32 * 1024 * 1024,   // real output is ~110 KB today; the 1 MB default is one dependency-tree growth away
  timeout: 5 * 60 * 1000,        // a hung audit becomes a signal/error, i.e. exit 2, never a silent pass
});
```

Output on success (keep it short but evidential — a green run must show it actually audited something):

```
[check-dependency-audit] audit completed: 1158 total dependencies; vulnerabilities info=0 low=0 moderate=13 high=11 critical=0 (yarn exit 12, matches severity mask).
```

then either `no high/critical advisories found.` or the existing `id | package | severity | accepted | title | url`
table followed by the existing accepted/unaccepted verdict lines. Preserve the current wording of the
unaccepted-advisory error message — it tells the reader to fix the dependency or add a dated, reasoned entry,
and that guidance is still correct.

## 5. Allowlist validation and refresh

**Validation** (`loadAcceptedAdvisories`): the parsed value must be an array; each entry must be a plain object
with `id` (integer or non-empty string), `package` (non-empty string), `severity` (one of the five known
severities), `reason` (non-empty string) and `reviewedAsOf` matching `/^\d{4}-\d{2}-\d{2}$/`. Duplicate ids are
an error. Anything else throws with the offending index and field. Compare ids as `String(id)` on both sides so
a future string-shaped advisory id cannot silently miss the allowlist.

**Refresh** `security/accepted-dependency-advisories.json`. Rename `noPatchAsOf` → `reviewedAsOf` on all four
entries: the field name currently asserts something that is false for two of them, and one uniform field is
simpler to validate than two conditional ones. The gate reads only `id`, so this cannot change gate behaviour.
Set `reviewedAsOf` to the date the implementer actually re-runs the live audit. Rewrite the two stale reasons
using the evidence in 1F, for example:

- `1139427` (nanoid, high): note that an upstream patch exists at `>=3.3.18`, that the tree resolves `3.3.17`
  transitively through `expo-router` and `postcss` (Metro/bundler build-time only, not shipped in the web
  bundle), and that the lockfile bump is deliberately not part of this ticket.
- `1119441` (uuid, moderate): note the upstream patch at `>=11.1.1`, that the tree resolves `uuid@7.0.3`
  transitively, and that this entry is documentation only — `moderate` is below the gated threshold, so it does
  not currently affect the gate.

Leave `1138808`/`1138809` reasons as they are apart from the field rename; `patched_versions: "<0.0.0"` still
confirms no upstream patch exists.

Do not add, remove, or re-severity any entry. Do not add the three new moderate advisories.

## 6. Regression suite: `security/scripts/verify-dependency-audit-gate.mjs`

New file, `node:test` + `node:assert/strict`, matching `verify-secret-detection.mjs`'s style but with no Docker
and no network. Add a small `ndjson(...entries)` helper and a `summaryLine(counts)` helper, plus
`fakeAdvisory({ id, severity, module_name })`, so cases read as one or two lines each. Capture output by
passing `log`/`logError` collectors into `runDependencyAuditGate`, and assert on both the returned exit code
and the presence of the key phrase in the captured text — an exit code alone does not prove it "fails visibly".

Cases (each maps to an exit-criteria clause):

Operational failures — all must return **2** and mention `BLOCKED`:

1. `result.error = Object.assign(new Error("spawn yarn ENOENT"), { code: "ENOENT" })`, `status: null`.
2. `{ status: null, signal: "SIGKILL", stdout: "", stderr: "" }`.
3. The real network-failure fixture from 1A: stdout is the single `info` line, stderr contains the yarn
   `type:"error"` tunneling/ECONNREFUSED line, `status: 1`. Assert the message includes the yarn error text.
   This is the regression case for the reported defect — comment it as such.
4. A `type:"error"` line on **stdout** instead of stderr, `status: 1`, no summary.
5. Advisories present and well-formed but **no `auditSummary`**, `status: 12`. (Proves parsed advisories alone
   never constitute completion.)
6. Two `auditSummary` lines.
7. `auditSummary` with `data: {}`; and a second variant with `vulnerabilities: { info: 0, low: 0, moderate: 0, high: "3", critical: 0 }`.
8. `{"type":"auditAdvisory","data":{}}` alongside a valid summary.
9. An advisory with `severity: "sev-high"` (unknown severity) alongside a valid summary.
10. Mask mismatch: summary `high: 3`, `status: 0`.
11. Report inconsistency: summary `high: 3`, `status: 8`, zero `auditAdvisory` lines.
12. Garbage-only stdout (`"yarn: command failed"`), `status: 127`.
13. `loadAcceptedAdvisories` on a temp file containing `{}`; on `[{ "id": 1 }]`; and on two entries with the
    same id — each throws, and `main`'s mapping of that throw to exit 2 is covered by case 16b.

Policy outcomes:

14. Complete output, `status: 12`, three high advisories all in the injected accepted list, plus moderate
    advisories → **0**, output contains the completed-audit line and `accepted` markers.
15. Same, but one high advisory absent from the accepted list → **1**, output names that advisory id and the
    accepted-advisories file.
16. Same, but the un-accepted advisory is `critical` (`status: 16 | 12`) → **1**.
17. Complete output with `vulnerabilities` all zero, `status: 0`, no advisories → **0**, prints
    `no high/critical advisories found`.
18. **Nonzero status is not a failure**: only moderate advisories, `status: 4` → **0**. Also `status: 6`
    (low+moderate). This is the ticket's explicit "do not treat every nonzero exit as operational failure".
19. An accepted id that does not appear in the audit output → still **0**, with the stale-entry notice.

Process-level cases (prove `process.exitCode` actually propagates — the gate's real contract):

20. Create a scratch dir with `mkdtempSync(join(tmpdir(), "dep-audit-gate-"))` containing an executable `yarn`
    shim (`#!/bin/sh` + a heredoc). Run
    `spawnSync(process.execPath, [CHECK_SCRIPT], { env: { ...process.env, PATH: `${shimDir}:${process.env.PATH}` }, encoding: "utf8" })`.
    - 20a: shim prints a valid all-zero `auditSummary` and exits 0 → child status **0**. (All-zero means the
      real committed allowlist is irrelevant, so this case cannot break when the allowlist changes.)
    - 20b: shim prints `yarn: fatal` to stderr and exits 127 → child status **2**, stderr mentions `BLOCKED`.
    Use `t.after` to `rmSync` the scratch dir. Unlike `verify-secret-detection.mjs`, the OS tmpdir is fine here
    — the `.security-scratch/` convention exists only because Docker cannot mount `/tmp` on macOS, and no
    container is involved.
