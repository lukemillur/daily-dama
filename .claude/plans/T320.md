# T320 plan: Android status-bar icon style follows the visible background

## Findings from the current code

- Nothing in `src/` or `app.json` sets a status bar. `expo-status-bar` ~57.0.1 is installed but unused, and there is no `<StatusBar>` anywhere. On Android the window default (react-native-screens `ScreenWindowTraits`: `statusBarStyle ?: "light"`) and the system appearance decide the icons. The app saves its own theme (`userInterfaceStyle: automatic`), so a pale Red page on a dark-mode phone gets white icons.
- Edge-to-edge is already the Expo 57 / RN 0.86 default. `app.json` has no edge-to-edge key, and none should be added. The Screen component (`src/components/ui/screen.tsx`) uses `SafeAreaView` edges, and native-stack headers draw under the status bar. This is JS-only work, so no native rebuild is expected. If the implementer ends up changing `app.json` or a plugin, AGENTS.md's complete configuration sequence applies and the Android client has to be rebuilt.
- Visible colour behind the status bar, per area:
  - Tab scenes and the nested-stack headers (Tricks, Sesh, Profile): `theme.background` (`useResolvedTheme`, `src/features/profile/state/use-resolved-theme.ts`). `deriveNestedStackScreenOptions` sets the header and `contentStyle` to this colour.
  - The Tricks index on native has a transparent header over the `contentStyle` background (same colour).
  - Auth group (`src/app/auth/_layout.tsx`): `CachedAppThemeProvider`'s theme (`useCachedGuestTheme`), so `theme.background`.
  - Home before onboarding completes (`src/app/app/home.tsx` line ~100): `profile.themeBackgroundColor ?? AppColors.yellow`. This is NOT `theme.background` (the default is sage), so a plain theme-derived bar would be wrong there.
  - Landing, account-deleted, feedback and native-start use the fixed palette (`AppColors.paper` etc.). Landing uses `AppColors.paper`.
  - `src/app/app/stats/sesh-sequence-sandbox.tsx` uses paper (a dev tool).
- Native-stack trap, the main non-obvious risk. react-native-screens (4.26) Android applies `isAppearanceLightStatusBars` from the top screen's `statusBarStyle` option. The moment ANY screen sets `statusBarStyle`, it flips a global `didSetStatusBarAppearance` flag. After that every transition re-applies the window style, falling back to `"light"` for screens that did not set it. That would silently override a React Native `StatusBar`. So pick exactly one owner:
  - Chosen design: the React Native/Expo declarative `<StatusBar style=...>` only. Never set `statusBarStyle` in `screenOptions` or on screens. Add a test asserting no `statusBarStyle` key in `deriveNestedStackScreenOptions` and `deriveTricksIndexScreenOptions`.
  - Fallback only if device checks prove the declarative bar loses to the Screens traits (the Tricks nested route is the likely place): set `statusBarStyle` through `screenOptions` on every native-stack and tab layout, and stop using `<StatusBar>`.
- RN's `StatusBar` keeps a stack of mounted instances, and the last-mounted entry wins. React runs child mount effects before parents. So do NOT mount a root-level bar plus deeper bars, because the root would win. Mount exactly one bar per mutually exclusive route group, so nothing nests and nothing goes stale. `expo-status-bar`'s `StatusBar` has `style: 'auto' | 'inverted' | 'light' | 'dark'` (`'dark'` means dark icons). Always pass an explicit `light`/`dark`, never `auto`, because `auto` follows the system scheme.

## Steps

1. Pure selector (TDD first). Add `src/shared/color/status-bar-style.ts` (+ `.test.ts`) exporting `deriveStatusBarStyle(background: string): 'light' | 'dark'`. Use `contrastRatio` from `src/shared/color/contrast.ts`. Return `'dark'` when contrast against black is at least the contrast against white, else `'light'`. For invalid hex, fall back to the contrast result for the default palette (document the choice). Tests: pale Red preset (look up the Red preset background in `src/features/profile/components/theme-preset-grid.tsx` / the preset data), the default sage, a dark custom background (`#101820`), pure white and black, and an invalid hex. Also assert the chosen icon colour reaches at least 3:1 (the system-icon target) for each preset background that the theme tests already enumerate.
2. Shared "visible scene background" rule. Extract the Home onboarding rule (`hasCompletedOnboarding ? theme.background : (themeBackgroundColor ?? AppColors.yellow)`) into one small function (for example `selectSceneBackground(profile, theme)` in `src/features/profile/state/`), used by both `home.tsx` (replacing the inline expression) and the status bar, so they cannot drift. Keep `blockingOnboardingRender` semantics in `home.tsx` as they are. Do not change the visible behaviour, and cover the function with tests.
3. Component. Add `src/components/app-status-bar.tsx`: `AppStatusBar({ background })` renders `<StatusBar style={deriveStatusBarStyle(background)} />` from `expo-status-bar` and returns `null` on web (the web StatusBar is already a no-op; confirm via `StatusBar.web.ts`). Add a test that mocks `expo-status-bar` and asserts the style prop for light/dark backgrounds and that no render happens on web.
4. Mount one owner per route group.

   - `AuthLayout` (`src/app/auth/_layout.tsx`): bar from the cached theme. `CachedAppThemeProvider` exposes the theme through styled-components context only, so read it with `useCachedGuestTheme()` in a small inner component rendered inside the provider, or via `ThemeContext`.    - Fixed-palette routes outside `/app` and `/auth` (landing `/`, `account-deleted`, `feedback`, the native-start surfaces). First list the actual route entries (`src/app/index.tsx`, `account-deleted.tsx`, `feedback.tsx`) and their visible backgrounds. Mount the bar in each such route (or its screen component) with the right fixed colour. Do not put a bar in the root `_layout.tsx` (the child-first ordering above).
   - Do not add a bar to nested stacks or screens.
5. Tests for ownership. - Home's pre-onboarding yellow background: the step 2 shared rule handles it, and it can only be checked by test and by reading, not on device (do not replay onboarding).
