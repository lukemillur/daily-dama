# T083.1 — Add theme color fields to the Profile persistence domain

## Scope decision

Own the schema, reducer, persistence, and provider plumbing for
`themeBackgroundColor` / `themeAccentColor` here. T083.2 ("saves them via the
profile provider") depends on a working `useUserProfileActions().setThemeColors`
call already existing — adding it now is the natural conclusion of adding the
reducer action, not scope creep, and keeps the persistence-domain API
self-contained per AGENTS.md's per-concern ownership pattern.

**Value format decision:** store both fields as 6-digit hex strings
(`#RRGGBB`, case-insensitive, normalize to lowercase on validate — do not
normalize on serialize, store exactly what's passed in reducer to keep the
reducer dumb; persistence validation is case-insensitive). No alpha channel —
T083.2's WCAG contrast check needs a single opaque RGB triple, and free-form
pickers (e.g. `react-native-color-picker`-style libraries) commonly emit hex.
This is a new decision this ticket must make; flag it to the user only if a
picker library is later chosen that can't emit plain hex.

## Files touched, in order

### 1. `src/features/profile/model/user-profile.ts`

- Add two new optional fields to `UserProfile`:
  ```ts
  readonly themeBackgroundColor?: string;
  readonly themeAccentColor?: string;
  ```
  (Right after `manuallyUnlockedTrickIds` to match declaration order used
  elsewhere in the file.)
- Add a new action variant to `UserProfileAction`:
  ```ts
  | {
      readonly type: 'themeColorsUpdated';
      readonly themeBackgroundColor?: string;
      readonly themeAccentColor?: string;
    }
  ```
  Both fields optional and independently settable/clearable in one action —
  matches T083's "picked independently" note, and lets a future "reset to
  default" affordance in T083.2 clear one or both by passing `undefined`
  explicitly. Use a full replace (not merge-if-present) semantics: whatever
  is passed becomes the new value, including `undefined` to clear. This
  avoids an ambiguous "omitted vs. explicitly cleared" distinction — the
  action always carries both keys.
- Add the reducer case:
  ```ts
  case 'themeColorsUpdated':
    return {
      ...state,
      themeBackgroundColor: action.themeBackgroundColor,
      themeAccentColor: action.themeAccentColor,
    };
  ```
  Do this before persistence changes — persistence tests need the type to
  exist, and the reducer is the layer the round-trip semantics are specified
  against.

### 2. `src/features/profile/persistence/user-profile-persistence.ts`

- Add a hex-color validator near the other `isX` helpers:
  ```ts
  function isThemeColor(value: unknown): value is string {
    return typeof value === 'string' && /^#[0-9a-fA-F]{6}$/.test(value);
  }
  ```
- In `parseUserProfile`, destructure `themeBackgroundColor` and
  `themeAccentColor` from `value` alongside the existing fields, validate
  each independently with `isThemeColor` when not `undefined` (same
  `if (x !== undefined && !isThemeColor(x)) return undefined;` pattern used
  for `streakThresholdMs` / `manuallyUnlockedTrickIds`), and add them to both
  the `hasCompletedOnboarding` and not-yet-onboarded return branches using
  the same spread-of-conditional-field pattern already used for
  `lastSeshField` / `streakThresholdField` / `manuallyUnlockedTrickIdsField`.
  This keeps the "absent key round-trips to `undefined`, doesn't force the
  key to exist" behavior consistent with every other optional field in this
  domain.
- No changes needed to `serializeUserProfile`, `deserializeUserProfile`,
  `loadUserProfile`, or `saveUserProfile` — they already operate generically
  on `UserProfile`/the parsed document and don't enumerate fields.
- Per AGENTS.md, do **not** bump `USER_PROFILE_SCHEMA_VERSION` or add
  migration logic. Old persisted documents simply parse with both fields
  `undefined`, which is the desired default.

### 3. `src/features/profile/state/user-profile-provider.tsx`

- Add `setThemeColors` to the `UserProfileActions` interface:
  ```ts
  readonly setThemeColors: (
    themeBackgroundColor: string | undefined,
    themeAccentColor: string | undefined,
  ) => void;
  ```
- Add the `useCallback` wiring alongside `setStreakThresholdMs`:
  ```ts
  const setThemeColors = useCallback(
    (themeBackgroundColor: string | undefined, themeAccentColor: string | undefined) => {
      dispatch({ type: 'themeColorsUpdated', themeBackgroundColor, themeAccentColor });
    },
    [],
  );
  ```
- Add `setThemeColors` to the `actions` object and its `useMemo` dependency
  array (alphabetical, matching existing ordering convention in that file).
- No hex validation belongs here — validation before dispatch (including the
  WCAG contrast guardrail) is explicitly T083.2's job per the task split.
  This provider layer just plumbs values through, same as every other
  setter in this file.

## Tests to add

### `src/features/profile/model/user-profile.test.ts`

Add a new `describe` block (or extend the existing style) with:
1. A test that dispatching `themeColorsUpdated` with both colors set sets
   both fields on state.
2. A test that dispatching `themeColorsUpdated` with one field `undefined`
   clears only that field, leaving the other and all pre-existing fields
   (e.g. `selectedTrickIds`) untouched — proves the reducer doesn't
   clobber unrelated state.
3. A test that an unrelated action (e.g. `selectedTrickToggled`) dispatched
   on a state that already has theme colors set leaves
   `themeBackgroundColor`/`themeAccentColor` unchanged — proves other
   reducer branches don't need to know about the new fields (they use
   `{ ...state, ... }` spreads already, but an explicit test documents the
   invariant the same way `lastSesh`/`streakThresholdMs` are already
   covered).

### `src/features/profile/persistence/user-profile-persistence.test.ts`

Add, mirroring the existing `streakThresholdMs`/`manuallyUnlockedTrickIds`
coverage:
1. A round-trip test: serialize a profile with both
   `themeBackgroundColor`/`themeAccentColor` set, deserialize, `toEqual` the
   original — proves round-trip through (de)serialization, the same path
   `loadUserProfile`/`saveUserProfile` use for hydration.
2. A test that `deserializeUserProfile(serializeUserProfile(COMPLETE_PROFILE))`
   (i.e. `COMPLETE_PROFILE` with no theme fields) yields a profile where
   both fields are `undefined` — the "default to undefined when unset"
   exit criterion, exercised through the actual hydration path rather than
   just the reducer's initial state.
3. An `it.each` malformed-value test analogous to the existing
   `streakThresholdMs`/`manuallyUnlockedTrickIds` ones, covering: not a
   string, missing `#`, wrong length (`#fff`, `#1234567`), non-hex
   characters (`#gggggg`), empty string. Confirms `deserializeUserProfile`
   returns `undefined` (safe-recovery path) rather than accepting garbage.
4. Extend/duplicate the existing `loadUserProfile` "loads a valid persisted
   profile" test with a variant that includes theme colors, to exercise the
   full `loadUserProfile` → `status: 'loaded'` path, not just
   `deserializeUserProfile` directly — this is the literal "round-trip
   through hydration" wording in the exit criteria.
5. Confirm existing tests in this file are otherwise unaffected (they should
   pass unmodified since the new fields are optional and `COMPLETE_PROFILE`
   doesn't set them) — no changes needed to those, but run the full file
   after the change to be sure nothing regressed.

No new provider-level test file is needed: this codebase doesn't unit-test
`user-profile-provider.tsx` directly (its behavior is exercised through
consuming component tests like `sesh.tsx`'s and `kentei-onboarding.tsx`'s
suites). T083.2 will exercise `setThemeColors` through its own picker
component test per its exit criteria ("picking valid colors saves them via
the profile provider").

## Order of work

1. `user-profile.ts` (type + reducer) — everything else depends on the type
   existing.
2. `user-profile.test.ts` — lock in reducer behavior before touching
   persistence, since persistence tests construct `UserProfile` values that
   must already type-check.
3. `user-profile-persistence.ts` (validator + parse/branches).
4. `user-profile-persistence.test.ts`.
5. `user-profile-provider.tsx` (setter wiring) — no dedicated test, but
   verify `yarn tsc --noEmit` catches any interface mismatch.
6. Run `node .claude/scripts/verify.mjs` (full four-step sequence; this is a
   schema/model change, not docs/test-only, so don't use `--skip-export`).

## Risks / non-obvious notes

- Keep the "explicit `undefined` clears the field" semantics in mind when
  T083.2 wires up a "reset to default" control — it should dispatch
  `themeColorsUpdated` with `undefined` for the field being reset, not omit
  the action entirely.
- Don't be tempted to validate contrast or reachability here — that's
  explicitly T083.2's job (WCAG AA 4.5:1 guardrail). This ticket only
  validates *shape* (valid hex string or absent), not perceptual properties.
- `COMPLETE_PROFILE` in the persistence test file is declared `as const`;
  new test fixtures that add theme fields should follow the same pattern
  (spread + `as const`) used for the existing `lastSesh`/`streakThresholdMs`
  variants, not a fresh object literal, to keep fixture drift minimal.
