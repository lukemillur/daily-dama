# T072 — Return multi-trick completion to Sesh home

## Goal

Make the casual multi-trick Sesh flow leave its child route after the wrap-up
`Finish sesh` action and return to the canonical `/sesh` home picker. Preserve
the existing setup back/cancel behavior, practice-history recording, and the
ability to start a new multi-trick run by entering `/sesh/multi-trick` again.

## Current state and constraints

- `src/features/sesh/components/multi-trick-sesh-entry.tsx` owns the local
  selection/configuration/running wizard.
- Its `handleFinished` callback currently resets the wizard to
  `choosingTricks`, clears the local selection/options, and is passed to both
  `MultiTrickSesh.onFinished` and `onCancelRun`.
- The selection screen's `Back to Sesh` action already calls
  `router.replace('/sesh')`, so that route contract must remain intact.
- `MultiTrickSesh` records completed per-trick history before rendering its
  wrap-up and only invokes `onFinished` when the wrap-up button is pressed.
  Do not move or duplicate that recording logic.
- The canonical home UI is `Sesh` rendered by `src/app/sesh/index.tsx`; its
  picker includes the `Practice format` controls and the `Practice several
  tricks` route action. The child route is `src/app/sesh/multi-trick.tsx`.
- Web is the active verification target. Do not add native-specific work.

## Ordered implementation plan

1. **Change completion/cancel ownership at the entry route boundary.**
   Update `MultiTrickSeshEntry` so the callback used after the running flow
   finishes routes with `router.replace('/sesh')` instead of resetting the
   local wizard. Keep the existing selection-screen `Back to Sesh` handler
   unchanged. The same callback is currently used for the first countdown's
   cancel action, so that cancellation should also leave the child route via
   `/sesh` rather than reset into an in-route selection state. Avoid changing
   `MultiTrickSesh` or practice-history reducer behavior.

2. **Add an integration-level regression test around the route transition.**
   Extend or add the Sesh/multi-trick entry test with a controlled
   `expo-router` mock and a small route harness. The harness should render the
   multi-trick entry for `/sesh/multi-trick`, update its current route when
   `router.replace` is called, and render the real Sesh home picker for
   `/sesh` using the existing provider setup (key the child by route if needed
   so a new child mount is explicit). Drive a two- or three-trick run
   through countdown, active progression, and the wrap-up `Finish sesh` action;
   assert that:

   - the completed run invokes `replace('/sesh')`;
   - the home picker is visible (for example, `Practice format` and
     `Practice several tricks` are present);
   - the multi-trick selection UI (`Pick your lineup.` / its selection
     controls) is no longer shown;
   - practice history still contains one record per attempted trick; and
   - mounting/entering the multi-trick route again still presents a fresh
     selection screen, proving that route-based remounting replaces the old
     local reset behavior.

3. **Lock down both setup cancellation paths.**
   In the same test area, press the selection screen's `Back to Sesh` action
   before starting a run and assert that it calls `replace('/sesh')` and the
   Sesh home picker is rendered. Also start a run, press `Cancel` during the
   first countdown, and assert that it uses the same route-home transition
   without recording a practice session.

4. **Run focused and baseline verification.**
   Run the new/updated Sesh tests first, then the repository verification
   sequence:

   ```sh
   yarn test --runInBand
   yarn lint
   yarn tsc --noEmit
   yarn expo export --platform web --output-dir /tmp/daily-dama-web-export
   ```

   Review any warnings against the two documented benign warnings and ensure
   no new route or runtime error is introduced.

## Expected files

- `src/features/sesh/components/multi-trick-sesh-entry.tsx`
- `src/features/sesh/components/multi-trick-sesh-entry.test.tsx`, or a new

No persistence schema, state-management boundary, shared sequencing logic, or
native configuration changes are expected.
