# T157.5 — Synchronize custom tricks and sequences

## Scope boundary (read first)

This is domain rollout 2 in the T157 chain, directly following the pattern
`T157.4` (`.claude/plans/T157.4.md`, now merged — read `git show
37d7c3d:.claude/plans/T157.4.md` if you want the full original text; it is
summarized and adapted below) established for `profile`. Read this plan in
full before writing code; it calls out three places where the custom-tricks
domain is **structurally simpler** than profile (one table, not two; no
`recordId === userId` routing needed) and one place where it needs a genuinely
new mapping function `diffCustomTricksForOutboxOperations` that has no
profile-domain equivalent to crib line-for-line.

**In scope:** real pull+push synchronization for the `customTricks`
`SyncDomain` (`api.custom_tricks`, one table), wired into
`CustomTrickProvider` additively, with a real Supabase adapter, a durable
per-domain outbox/envelope (reusing `SyncEnvelope`/`replacePendingOperationForRecord`
etc. from `src/shared/sync/sync-envelope.ts` — already generic, added by
T157.4, **no shared-file changes needed this time**), idempotent retries,
revision-guarded pushes, and parked (not auto-resolved) conflicts — while
preserving stable trick ids, stored step-name snapshots, and the
no-nested-sequences rule.

**Explicitly out of scope, same reasons as T157.4:**
- Dispatching into the shared `syncCoordinatorReducer` (`src/shared/sync/coordinator.ts`).
  Still only `profile` + (after this task) `customTricks` are wired; the
  reducer needs all five `SYNC_DOMAINS` settled to reach `idle`. T157.9 wires
  the shared coordinator once T157.4–T157.8 all exist. This task again builds
  a **domain-local sync driver** whose return value is already
  `DomainSyncRecord`-shaped, so T157.9 can plug it in with no reshaping.
- Debounced/coalesced login/foreground/reconnect/manual triggers (T157.9).
  Reuse the exact "one auto-run per identity generation after hydration, for
  signed-in users" trigger T157.4 already built, plus a manually callable
  `runSync`.
- Any visible conflict UI or automatic last-write-wins resolution (T160.1/T160.2).
  A `'conflict'` push outcome is recorded and left pending, never silently
  resolved in either direction, and must never block other records.
- Modifying `src/shared/supabase/*-cloud-repository.ts` or
  `custom-trick-cloud-repository.ts`'s existing contract. As with T157.4, the
  revision-guarded/idempotent push logic lives in a **new** adapter file, not
  bolted onto the existing repository.
- DB schema changes. `api.custom_tricks` (T155.3) already has everything this
  task needs: a server-owned `revision` column bumped on every UPDATE, and
  **no tombstone column — deletes are hard deletes** (unlike goals/notes,
  which T155.4 apparently gave a soft-delete story; that is not this table's
  shape). The task description's "deletion tombstones" phrasing is satisfied
  by the **outbox's own** `operationType: 'delete'` + idempotent-retry design
  (identical to T157.4's `user_trick_states` delete branch), not by a new DB
  column. Do not add one.

## Key finding: this domain is simpler than profile's, in three ways

1. **One table, one row type.** `api.custom_tricks` has no scalar/child-table
   split the way `profiles`/`user_trick_states` did. `CustomTrickSyncTransport`
   therefore needs exactly one `pull` method (not two), and its shape is
   literally `SyncTransportRepository<CustomTrickRow>` from
   `src/shared/sync/transport.ts` — you can type the adapter's return value as
   that shared interface directly instead of inventing a bespoke one the way
   `ProfileSyncTransport` had to.
2. **No `recordId === userId` routing in `push`.** Every operation's
   `recordId` is a custom-trick id (`custom-<...>`, from `createCustomTrickId`),
   never the user's own uuid — there is nothing to disambiguate. `push` is a
   single upsert/delete branch on `request.operationType`, not the
   profile-scalar-vs-trick-state fork `profile-sync-transport.ts` needed.
3. **Idempotent upsert and revision-guarded update are already proven for
   this exact table.** `createCustomTrickCloudRepository(client).upsert()`
   (`custom-trick-cloud-repository.ts`) already does insert-then-update-on-`23505`
   scoped to `(user_id, id)`, and the migration's column grants
   (`20260822210000_protect_server_owned_timestamps_and_ownership.sql`,
   section 6) show the UPDATE-grantable columns are exactly `name, kentei_rank,
   steps` — the same three fields the new adapter's revision-guarded `update`
   patch must use. Read `custom-trick-cloud-repository.ts`'s `upsert()` doc
   comment closely: it explains *why* this isn't a native `.upsert()` call
   (column-level grants don't cover `id`/`user_id`/`kind`, the conflict
   target) — the new adapter's insert-then-update-on-conflict branch must
   follow the same shape, not a native upsert.

One more finding worth flagging explicitly, since the task notes ask you to
check it: **`revision` is bumped on UPDATE only; `kind` is pinned immutable on
UPDATE** (`enforce_custom_trick_mutation_invariants`, same migration, section
4). There is no supported "convert a standalone trick into a sequence in
place" path server-side, matching the local model (`createCustomTrick`/
`updateCustomTrick` never change `kind` for an existing id either). Nothing in
this task needs to handle a kind-changing update; don't build for it.

## Nested-sequence rule across the sync boundary — what actually happens

The local UI already prevents constructing a nested sequence
(`selectSequenceStepCandidates` never offers a sequence as a step candidate).
The DB's own trigger (`private.enforce_custom_trick_step_invariants`,
T155.3's migration) is the second, independent line of defense, and it fires
on every INSERT/UPDATE, raising a `23514` check-violation if a pushed
sequence's `existingTrick` step references another row that is (already, or
becomes) `kind = 'sequence'`. Read `mapPostgrestError`
(`src/shared/supabase/cloud-repository.ts`): `23514` classifies as
`{ kind: 'validation' }`, which the driver hook surfaces as a `'failed'` push
outcome (not `'conflict'` — this is not a revision race, it's a genuinely
invalid write). The operation stays parked in the outbox with a descriptive
`lastErrorMessage`, exactly like any other failed push; it is not retried
into silent success and does not corrupt other records. **No new handling
code is needed for this** — it falls out of the existing `mapPostgrestError`
classification and the existing "failed pushes stay pending, don't block
siblings" behavior `pushOutboxOperations` already guarantees. Add one adapter
test (in the real-stack `.test.mjs` file) proving this end-to-end, since it's
a named product invariant even though the code path is generic.

The trigger does **not** require the referenced row to already exist (a
`select ... where ct.id = step ->> 'sourceTrickId'` that matches zero rows
leaves `referenced_kind` `NULL`, which fails the `= 'sequence'` check safely)
— so push ordering between a standalone trick and a sequence that references
it is **not** load-bearing server-side. Don't build push-ordering logic
("push standalone tricks before sequences") into the driver; it isn't needed
and would add complexity with no corresponding requirement.

## The pure diff: `CustomTrickCollection` change → outbox operations

New exports in `custom-trick-cloud-mapping.ts` (the same T155.11 file that
already has `mapCustomTrickToUpsertInput`/`mapCustomTrickCollectionToUpsertInputs`,
whose header comment already flags "does NOT wire into ... any
synchronization/diff logic — that's a later ticket"; this is that ticket):

```ts
export function diffCustomTricksForOutboxOperations(
  previous: CustomTrickCollection,
  next: CustomTrickCollection,
  userId: string,
): readonly NewOutboxOperationInput[]
```

- Build `Map<id, CustomTrick>` for `previous.tricks` and `next.tricks`.
- A trick id present in `next` but absent from `previous`, or present in
  both but not deep-equal (JSON.stringify comparison, same rationale as
  `scalarFieldsEqual` in `profile-cloud-mapping.ts` — every field is plain
  JSON-serializable data constructed exclusively by the trusted reducer),
  emits `{ domain: 'customTricks', operationType: 'upsert', recordId: id,
  payload: mapCustomTrickToUpsertInput(trick, userId) as unknown as
  Record<string, unknown> }`.
- A trick id present in `previous` but absent from `next` emits
  `{ domain: 'customTricks', operationType: 'delete', recordId: id, payload: null }`.
- Stable order: ascending id (there is no "scalar op first" concept here
  since there's only one row type — unlike `diffProfileForOutboxOperations`,
  don't invent a two-tier ordering that has nothing to be ordered against).
- Add unit tests in `custom-trick-cloud-mapping.test.ts` (alongside the
  existing row-mapping tests): no-op diff; trick added (standalone and
  sequence); trick edited (name, kentei_rank, steps — assert full-payload
  replacement, not a partial patch, matching `mapCustomTrickToUpsertInput`'s
  existing behavior); trick deleted; a batch of several tricks changed at
  once, asserting op count/shape and stable id-ascending order.

## The adapter: `SyncTransportRepository<CustomTrickRow>` over the real client

New file `src/features/custom-tricks/persistence/custom-trick-sync-transport.ts`.
`createCustomTrickSyncTransportAdapter(client: SupabaseClient<Database, 'api'>,
userId: string): SyncTransportRepository<CustomTrickRow>` (the shared generic
interface from `transport.ts` — no bespoke interface needed, per the "Key
finding" above).

**Pull**: `pull(request: CloudPageRequest)` delegates directly to
`createCustomTrickCloudRepository(client).list(request)` — its existing
return shape is already structurally identical to
`SyncTransportPullResult<CustomTrickRow>`, same one-line-wrapper pattern as
`profile-sync-transport.ts`'s `pullProfileRow`/`pullTrickStatePage`. Feed it
into `pullAllPages` from `transport.ts` unchanged.

**Push**: `push(request: SyncPushRequest): Promise<SyncTransportPushResult<CustomTrickRow>>`.
Defensively re-validate `request.payload` first (round-tripped through
AsyncStorage JSON — treat as `unknown`), reusing `isNormalizedText`/
`isOptionalKenteiRank`/`isSequenceStep` from `custom-trick-persistence.ts`
plus a `kind === request.recordId`-free structural check (id/user_id/kind/name
present and well-typed; `steps` shape matching `kind`). Return
`{status:'failed', error: {kind:'validation', ...}}` on a malformed payload.

- `operationType === 'delete'`: mirror T157.4's `pushTrickStateDelete`
  exactly, scoped to `(user_id, id)` instead of `(user_id, trick_id)`:
  - `expectedRevision === null`: unconditional delete; 0 rows matched is a
    success (idempotent no-op — never existed server-side).
  - `expectedRevision !== null`: delete with `.eq('revision', expectedRevision)`
    added; 0 rows matched → re-fetch by `(user_id, id)`: gone ⇒ `'succeeded'`
    (already-applied retry); still present at a different revision ⇒
    `'conflict'`.
  - Fabricate a placeholder row on a successful delete
    (`fabricateDeletedCustomTrickRow(userId, id)`, same "inert placeholder,
    never read for real data, only for cache bookkeeping" doc comment as
    T157.4's `fabricateDeletedTrickStateRow`).
- `operationType === 'upsert'`: mirror T157.4's `pushTrickStateUpsert`
  exactly, scoped to `(user_id, id)`, patch = `{ name, kentei_rank, steps }`
  (the exact UPDATE-grantable column set):
  - `expectedRevision === null`: insert; on `23505`, fall back to a **blind**
    update (no revision filter) — same accepted first-push-ever limitation
    as profile's scalar branch.
  - `expectedRevision !== null`: revision-guarded update;
    `PGRST116` (0 rows) → re-fetch by `(user_id, id)` → `'conflict'` with the
    real `serverRevision`. A genuine `23514` (nested-sequence/malformed-step
    violation from the trigger) falls through `mapPostgrestError` to
    `'failed'`, per the "Nested-sequence rule across the sync boundary"
    section above — do not special-case it into `'conflict'`.

**Real-stack tests**: new file
`supabase/tests/data-api/t157_5_custom_trick_sync_transport.test.mjs`, built
identically to `t157_4_profile_sync_transport.test.mjs` (register
`alias-loader.mjs`, `createConfirmedUser`/`deleteUser` from
`local-supabase.mjs`, sign in, run via `yarn test:data-api`). Cover:
1. Idempotent retry of the same standalone-trick upsert (simulated lost ack):
   second call succeeds, no duplicate row, revision bumped once.
2. Idempotent retry of a sequence-trick upsert, same shape, `steps` payload
   round-trips correctly.
3. Revision-guarded update: seed a second write via the plain repository to
   bump `revision`, then push with the now-stale `expectedRevision` →
   `'conflict'` with the correct `serverRevision`; row content is untouched.
4. Idempotent retry of a delete (push twice): both succeed, second is a
   no-op.
5. Delete of a trick that was never created (`expectedRevision: null`, no
   prior insert) succeeds as a no-op.
6. A sequence upsert whose step references another row that is `kind =
   'sequence'` returns `'failed'` (validation), and the malformed row is
   never persisted — the concrete proof for the "no-nested-sequences rule ...
   across browsers" exit criterion at the transport layer.
7. `pull` against real seeded rows (standalone + sequence) — basic smoke,
   not a full pagination re-proof (T155.8 already owns that).

## The driver hook

New file `src/features/custom-tricks/state/use-custom-trick-domain-sync.ts`,
structurally a near-mechanical adaptation of `use-profile-domain-sync.ts`,
simplified for the single-table domain:

```ts
export interface UseCustomTrickDomainSyncOptions {
  readonly collection: CustomTrickCollection;      // current state from the PRIMARY reducer
  readonly hasHydratedCollection: boolean;
  readonly dispatchCollection: (action: CustomTrickAction) => void;
  readonly getTransport: () => SyncTransportRepository<CustomTrickRow> | undefined;
}

export interface UseCustomTrickDomainSyncResult {
  readonly runSync: (trigger: SyncTrigger) => Promise<DomainSyncRecord>;
  readonly isSyncing: boolean;
  readonly lastResult: DomainSyncRecord | undefined;
}
```

Internals (deltas from `use-profile-domain-sync.ts` called out explicitly;
everything else copies that file's structure):
- `identity`/`generation` via `useIdentityHandle()`, same rationale (single
  internal read shared with the envelope's own `useIdentityScopedDomain`
  call).
- Own `useIdentityScopedDomain<SyncEnvelope<CustomTrickSyncSnapshot>,
  CustomTrickSyncEnvelopeAction>` instance.
- `runSyncImpl`:
  1. No-op if `identity.kind !== 'user'` or `getTransport()` is `undefined`.
  2. **Pull phase**: single `pullAllPages(transport, { pageSize: 200,
     startCursor: null })` call (no second pull the way profile needed one
     for trick-state) → `trickPull`. On `trickPull.status === 'failed'`,
     settle `'failed'`.
  3. If outbox empty: `mapCustomTrickRowsToDomainCollection(trickPull.rows,
     userId)` (existing T155.11 function); on `status === 'valid'`, set
     `suppressNextDiffRef.current = true` and dispatch the primary reducer's
     existing `customTricksRestored` action (same action hydration itself
     uses — this is the "second-browser rehydrate" mechanism, reusing an
     action that already exists, unlike profile which also reused
     `profileRestored`), and rebuild `trickRevisions` from `trickPull.rows`.
     On `'invalid'`, touch nothing (a malformed server response must never
     clobber good local state).
  4. If outbox non-empty: refresh `trickRevisions` only for ids with no
     pending operation (pending records keep whatever revision they last
     observed; their own push outcome is what advances or conflicts them) —
     identical logic to profile's trick-state branch, just without the
     scalar/`userId` special case.
  5. Dispatch `revisionRecorded` with the rebuilt snapshot.
  6. **Push phase**: snapshot `envelope.outbox` once,
     `getExpectedRevision = (op) => trickRevisionsCache[op.recordId] ?? null`,
     call `pushOutboxOperations(transport, outboxSnapshot, {
     getExpectedRevision })`.
  7. Per outcome: `'succeeded'` ⇒ `operationAcknowledged` +
     `revisionRecorded` (delete removes the id from the cache; upsert sets
     the new revision). `'conflict'`/`'failed'` ⇒ `operationAttemptRecorded`
     with a descriptive message, operation stays pending, unrelated records'
     outcomes unaffected (generic `pushOutboxOperations` guarantee, same as
     T157.4).
  8. Settle `'succeeded'` unless the pull itself failed or an adapter call
     threw (caught, settle `'failed'`).
- Diff-watching `useEffect`: same "skip on first hydration per generation,
  suppress-on-pull-adopt" ref pattern as `use-profile-domain-sync.ts`, but
  calling `diffCustomTricksForOutboxOperations` instead of
  `diffProfileForOutboxOperations`.
- Same "one auto-run per identity generation after both domains hydrate, for
  signed-in users only" trigger effect, copied verbatim in structure.

Tests: `use-custom-trick-domain-sync.test.tsx`, same RTL/fake-transport
pattern as `use-profile-domain-sync.test.tsx`. Cover (mapped from this task's
exit criteria):
1. Offline create of a standalone trick and of a sequence (fake transport
   always network-errors): both enqueue outbox ops; envelope persists them;
   remounting under the same identity/generation reloads the same pending
   ops (durability).
2. Offline edit and offline delete, same durability proof.
3. "Reconnect": remount with a transport that now succeeds — pending ops
   push, get acknowledged, revisions recorded; **no duplicate rows** (assert
   the fake transport's upsert call count/idempotency, not just the final
   state).
4. Second-browser rehydrate: fresh envelope (empty outbox, fresh identity
   generation) pulls a fake-seeded server fixture (mix of standalone +
   sequence rows) and the primary reducer ends up matching it exactly.
5. **Historical step-name preservation**: seed a sequence trick whose
   `existingTrick` step snapshot name differs from its `sourceTrickId`'s
   current live name in the fake-seeded fixture (simulating the source
   trick having been renamed after the sequence was created); after a
   pull-adopt, assert the restored sequence's step `name` is the **stored
   snapshot**, not anything derived from the (absent, in this fake) live
   source trick — this is the direct executable proof of the "preserve
   historical step names after source rename/deletion" exit criterion at
   the sync layer, complementing T155.11's own mapping-level tests.
6. A stale-revision conflict on one trick does not block an unrelated
   trick's operation in the same run, and the conflicted op is still present
   (unacknowledged) in the envelope afterward — this task's specific
   provider-integration-level proof of "surface same-record stale revisions
   without blocking unrelated tricks."
7. Rapid edits to the same trick id offline coalesce to one pending outbox
   operation.
8. Guest identity never enqueues operations and `runSync` is a no-op.

## Risks / non-obvious things to flag to the implementer

- Resist scope creep into T157.9 (real shared coordinator, debounced
  triggers) or T160 (visible conflict UI, last-write-wins) — identical
  temptation and identical reason to decline as T157.4 flagged; the
  dependency graph in `TASKS.md` (`T157.9` depends on `T157.4–T157.8`,
  `T160.2` depends on `T157.4–T157.8`) still confirms this.
- Do not add push-ordering logic (standalone-before-sequence) — the "Nested
  sequence rule across the sync boundary" section above shows the DB trigger
  tolerates a not-yet-existing referenced row; building ordering logic
  would be solving a problem that doesn't exist and adding untested
  complexity.
- Do not add a soft-delete/tombstone column or migration. `api.custom_tricks`
  is a hard-delete table (confirmed by reading
  `20260822200050_add_custom_tricks_and_practice_sessions.sql`); the task
  description's "tombstone semantics" is satisfied entirely by the existing
  outbox `operationType: 'delete'` + idempotent-retry pattern already proven
  by T157.4's trick-state delete branch. Introducing a new DB column here
  would also cut against AGENTS.md's "do not introduce migration
