# T155.8 — Repeatable database security and migration test harness

## Scope for this iteration

Consolidate the three test sources that already exist piecemeal (pgTAP under
`supabase/tests/*.test.sql`, the Data API HTTP suite under
`supabase/tests/data-api/`, and the two-command manual reset dance in
`supabase/README.md`) into one documented command. Add the one genuinely new
piece of coverage the exit criteria calls for — a >1,000-row paginated
practice-session fixture — as a new file in the existing Data API suite. Add
an opt-in, automated "mutation check" that proves the harness fails closed
when a representative RLS policy is weakened.

Out of scope (do not fold in): wiring any of this into `.github/workflows/`
(the task's "suitable for... CI" language is a property of the command's
exit-code/non-interactive behavior, not a request to add a CI job — no
existing workflow references Supabase, so there is nothing to wire against
yet), new pgTAP invariant coverage (T155.1–T155.7 already own that), and any
change to `.claude/scripts/verify.mjs` (that wrapper is deliberately scoped
to the no-Docker-required sequence; this harness needs a running local
Supabase/Docker stack and stays a separate, explicitly-invoked command, same
as `yarn test:data-api` already is today).

## What already exists (confirmed live against a fresh local stack)

- `npx --yes supabase@2.115.0 db reset` then `npx --yes supabase@2.115.0 test
  db --local` runs all 5 pgTAP files (150 assertions) clean from a reset —
  no extra reset is needed *between* those two commands. Every `.test.sql`
  file wraps in `begin; ... rollback;` (confirmed by reading
  `t155_2_profiles_and_trick_states.test.sql` and
  `t155_7_grants_and_rls_independence.test.sql`), so pgTAP itself never
  leaves committed state — the README's "always finish on another db reset"
  guidance is about the *Data API* suite's committed HTTP-level rows and any
  regression check that manually drops a constraint outside a transaction,
  not about pgTAP needing a reset before or after by itself.
- `yarn test:data-api` (`node --test 'supabase/tests/data-api/**/*.test.mjs'`)
  passes 102/102 against a freshly reset stack. Each file creates/deletes its
  own confirmed users via `supabase/tests/data-api/lib/local-supabase.mjs`,
  cascading away their own rows.
- `npx --yes supabase@2.115.0 db query --local "<sql>"` runs a raw statement
  against the local DB with no extra dependency (no `pg` package, no `psql`
  binary needed — confirmed `psql` is not even installed in this
  environment, so this is the only zero-new-dependency way to run ad hoc SQL
  locally).

## New pagination fixture test (the one new invariant this task adds)

Add `supabase/tests/data-api/t155_8_pagination.test.mjs`, same shape/imports
as the existing `t155_6_*`/`t155_7_*` files (import from
`./lib/local-supabase.mjs`, `node:test` + `node:assert/strict`, its own
`before`/`after` creating and deleting one confirmed test user).

Why this needs a *new* fixture rather than reusing an existing one:
`supabase/config.toml` sets `max_rows = 1000` (PostgREST's default page
cap). Confirmed live: an unfiltered `GET /practice_sessions?order=...` with
no `limit` silently truncates to exactly 1000 rows and returns 200 (not an
error) — the one way to prove pagination is *actually* wired correctly
(not just "small enough to never notice a missing page") is a fixture that
exceeds that cap.

Fixture design (confirmed live: bulk insert of 1200 rows via one POST array
completed in ~80ms, well inside normal HTTP timeouts):

- Seed 1,200 `practice_sessions` rows for one freshly created user via a
  single bulk POST (`client.post('/practice_sessions', rows)`, matching the
  existing "bulk JSON-array insert" pattern already proven elsewhere in this
  suite per `supabase/README.md`).
- **Include duplicate `completed_at` values on purpose** (e.g. groups of 3
  rows sharing a `completed_at`, ~400 distinct timestamps), not all-unique
  timestamps. The user-scoped index added in T155.2/T155.3 is
  `(user_id, completed_at desc, id)` — `id` has no explicit direction, so its
  tiebreak order is ascending. An all-unique-timestamp fixture (what an
  initial probe used to validate the mechanics) never exercises that
  tiebreak and would pass even if the query ordered by `id.desc` instead of
  `id.asc`. Query with `order=completed_at.desc,id.asc` to match the index
  exactly, and assert the tiebreak explicitly: for any two adjacent
  same-`completed_at` rows in the concatenated result, `id` must be
  non-decreasing.
- Paginate with `limit`/`offset` (PostgREST's `Range`/`limit`+`offset` both
  work; use `limit`+`offset` for readability, with a page size that does
  **not** evenly divide the group size or the total — e.g. `limit=137` — so
  page boundaries routinely fall mid-duplicate-group, which is exactly the
  scenario that would silently drop or duplicate a row if the tiebreak were
  wrong.
- Assertions: total rows collected across all pages equals 1,200; the set of
  `id`s collected has no duplicates and is exactly the set inserted (no gaps,
  no repeats); the concatenated sequence is non-increasing by `completed_at`
  and non-decreasing by `id` within each `completed_at` group.
- Clean up: `deleteUser` in `after()`, same as every other file in the suite
  — no per-row teardown needed (cascade).
- Do **not** modify `local-supabase.mjs`'s `restClient` to expose response
  headers for this — a `Content-Range`/`count=exact` header check is a
  nice-to-have, not needed to prove the pagination invariant, and touching
  the shared helper is unnecessary blast radius for a suite four other test
  files depend on. Skip it.

Run order matters here only insofar as this file joins the existing glob —
no runner change needed for discovery, `node --test`'s glob already picks up
any new `*.test.mjs` under `supabase/tests/data-api/`.

## Consolidated command

Add `supabase/tests/run-db-tests.mjs` (plain Node, no new dependency —
`node:child_process` + `node:fs`, matching `.claude/scripts/verify.mjs`'s
style: one line of `PASS`/`FAIL` per step, full output on failure, single
non-zero exit on any failure). Wire it up as `"test:db": "node
supabase/tests/run-db-tests.mjs"` in `package.json`.

Default invocation (`yarn test:db`), steps run in this order and this order
only (each depends on the previous):

1. `npx --yes supabase@2.115.0 start` — idempotent; confirmed live it
   succeeds (printing status) even when the stack is already running, so
   this is safe to always run first and makes the command genuinely
   one-shot on a machine where Docker is up but the stack isn't started yet.
   (Not independently re-verified from a fully cold/stopped stack in this
   planning pass — flag this as a residual gap for the implementer to spot
   check once, since a cold start takes materially longer and this session's
   time budget didn't include a full teardown/rebuild cycle.)
2. `npx --yes supabase@2.115.0 db reset` — clean slate; re-applies every
   migration.
3. `npx --yes supabase@2.115.0 test db --local` — pgTAP (all 5
   `t155_*.test.sql` files: catalog/constraint/grant/RLS assertions from
   T155.1–T155.7).
4. `yarn test:data-api` — the Data API HTTP suite (`t155_6_*`, `t155_7_*`,
   and the new `t155_8_pagination.test.mjs`): anonymous denial, cross-user
   isolation, protected/server-owned columns, malformed JSON, bulk-insert
   atomicity, practice-session immutability, and now the paginated fixture.
5. `npx --yes supabase@2.115.0 db reset` — final cleanup, always run even if
   step 3 or 4 failed (belt-and-suspenders: pgTAP itself never leaves
   committed state per above, and the Data API suite's own `after()` hooks
   already delete their test users, but this matches the existing README
   convention and guarantees a clean stack for whatever runs next,
   independent of whether every suite's cleanup hook actually reached).

Exit-code semantics: steps 1–4 stop-on-first-failure (matching
`verify.mjs`'s default, non-`--keep-going` behavior) *except* step 5 always
runs regardless of whether 1–4 succeeded (`finally`-style), so the local
stack is never left dirty by a failed run. The script's own exit code is
non-zero if *any* of steps 1–4 failed, even though step 5 ran and passed
afterward — a passing cleanup reset must never mask an earlier failure.

## Mutation check (the "exits non-zero when a policy is weakened" proof)

Design choice: **automated, opt-in flag**, not folded into the default
`yarn test:db` run. Reasoning: T155.7's `t155_7_grants_and_rls_independence
.test.sql` already carries a permanent, rolled-back-transaction version of
this exact proof (grants alone block with RLS disabled; RLS alone blocks
with grants widened) as regression coverage that runs on every invocation.
This task's mutation check is a different, complementary thing — a live
demonstration that the *whole outer harness* (not just one pgTAP file) fails
closed against a real committed policy regression, which is inherently
noisier (it prints an expected-looking test failure, and it mutates then
resets the live local DB) and isn't the kind of check you want firing on
every routine `yarn test:db` call. Confirmed live in this session that
automating it is cheap (~2.5s) and completely repeatable, so "documented
manual curl-style steps" (the pattern used elsewhere in `supabase/README.md`
for Auth policy checks that have no automatable HTTP surface yet) would be
strictly worse here for no reason — automate it.

Add `--mutation-check` as a second, mutually exclusive mode of
`run-db-tests.mjs` (when passed, run *only* this sequence, not the 5-step
default):

1. `npx --yes supabase@2.115.0 db reset` — clean baseline.
2. `npx --yes supabase@2.115.0 db query --local "alter policy
   practice_sessions_select_own on api.practice_sessions using (true);"` —
   deliberately weaken the representative policy. `practice_sessions` is the
   right representative table: it is the strictest exposed shape (insert-only,
   snapshot columns, immutability), and this is its cross-user isolation
   policy, so weakening it to `using (true)` makes it silently readable by
   any authenticated user regardless of `user_id` — a realistic, severe
   regression.
3. `node --test 'supabase/tests/data-api/t155_7_cross_user_isolation.test.mjs'`
   — confirmed live: with the policy weakened, this file's "B's filtered GET
   against A's row returns an empty array" assertion for `practice_sessions`
   fails with the leaked row in the body, and the file's overall process
   exit code is non-zero (other tables' blocks in the same file still pass;
   the file remains 1 failing assertion is enough for a non-zero exit).
4. `npx --yes supabase@2.115.0 db reset` — always run, regardless of step
   3's outcome, to restore the migration-defined policy.
5. Meta-assertion: if step 3's exit code was non-zero, the mutation check
   **passed** (the harness correctly caught the weakened policy) — the
   script itself exits 0 and prints a clear "mutation check passed: harness
   detected the weakened policy" line. If step 3's exit code was 0 (the
   suite didn't notice), the mutation check **failed** — the script exits 1
   with a loud "mutation check FAILED: a weakened RLS policy went
   undetected" message, since that is a real coverage gap, not a passing
   result.

Document this as `yarn test:db -- --mutation-check`: run it whenever RLS
policies change, and periodically as a sanity check that the harness still
fails closed — not part of the routine per-commit loop.

orchestration around already-proven commands and depends on step 1 existing
to have something meaningful to consolidate. README and `package.json`
documentation changes come last because they describe the finished command,
not the other way around.

## Risks / non-obvious things

- `supabase db query --local` was confirmed as the correct zero-dependency
  way to run raw SQL locally in this session (no `psql`, no `pg` npm
  package installed) — don't reach for either as an alternative.
- The mutation check's `db query` invocation runs `ALTER POLICY ... USING
  (true)` directly against the *migration-defined* policy name
  (`practice_sessions_select_own`). If that policy is ever renamed or
  restructured by a future migration, this line needs to move with it —
  call this out with a comment in `run-db-tests.mjs` pointing at the
  migration file (`supabase/migrations/20260822200050_...sql`) that defines
  it.
- Step 5's cleanup `db reset` must not be allowed to swallow an earlier
  failure's exit code — write the runner so the final exit code is
  determined by steps 1–4 only, with step 5 always attempted but never
  overriding a prior failure (and its own failure, if steps 1-4 passed,
  should still surface as non-zero, since a dirty stack after a "passing"
  run is itself a real problem for whoever runs the command next).
- `supabase start`'s cold-start behavior (Docker up, but no local Supabase
  containers yet) was not independently re-verified in this session — the
  idempotent "already running" case was. If the implementer hits a timeout
  or unexpected first-boot behavior, that's new information, not something
  this plan already ruled out.
