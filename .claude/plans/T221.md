# T221 -- Diagnose and fix the feedback form's missing success state

## What's already ruled out by static inspection (do not re-derive)

- `feedback-screen.tsx`'s branch logic is correct: `submitFeedback` returns a
  `CloudMutationResult<void>`; `'failed'` sets `hasError` and returns early,
  anything else falls through to `setSubmitted(true)`. There is no missing
  `await`, no stale closure, no dropped `result.status` check.
- `submit-feedback.ts`'s insert call is correct: it uses `getSupabaseClient()`
  (web-only, memoized), inserts into `.from('feedback')` under the client's
  `db.schema: 'api'`, and maps `error`/thrown exceptions to `'failed'`.
- The local Supabase CLI stack (T217.1/T217.2) verified the migration,
  pgTAP, and manual REST calls all correctly, including anon insert-only
  RLS. Re-testing that stack is not diagnosis; it is already-collected
  evidence that the bug is not in code shape or in the local schema.

So this is a runtime/config drift problem, most likely between "what the
local CLI stack has" and "what the live environment (dailydama.com, backed
by the hosted Daily Dama Dev project, ref ylyoqswauqyesuwmetnl) actually
has." This exact class of gap has hit this repo before and is documented in
supabase/README.md's Troubleshooting sections and supabase/RESEND_DNS_AUTH.md's
T195 entry:

- T188/T197: an Edge Function fix was verified locally but the hosted
  project had zero deployed functions -- nothing in CI/git push deploys
  them.
- T192/T195: a hosted Auth email template was stale because nothing had
  re-pushed it after a local fix.
- T217.1 itself: its exit criteria ("Met: ... npx supabase db reset applied
  it cleanly ... Reset the stack clean afterward") only ever mentions the
  local CLI stack. There is no mention anywhere in TASKS_DONE.md,
  supabase/README.md, or supabase/HOSTED_DEV_CONFIG.md of the api.feedback
  migration -- or any migration -- ever being pushed to the hosted project.
  CI (.github/workflows/ci.yml) has no Supabase deploy/push step. Treat
  "the hosted project never got this migration" as the leading hypothesis,
  not a fallback.

A second, independent, non-mutually-exclusive possibility the task's Notes
also name: an env var used by the live build. DEPLOYMENT_HANDOFF.md sections
4 and 7 (written 2026-08-10, before Auth/Supabase existed) explicitly flag
that nobody has ever confirmed Vercel's build-time env vars are correct --
and EXPO_PUBLIC_SUPABASE_URL/EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY did not
exist yet when that doc was written. No later task closes that gap for
these two vars specifically. If they were never added to Vercel's
Production environment scope (as opposed to a developer's own .env.local),
resolveSupabaseConfig returns 'missing' on the live site,
getSupabaseClient() returns null, and submitFeedback returns 'failed'
before any network call -- which would also mean Auth on the live domain
has been silently broken since it shipped, since every previous hosted-Auth
verification in TASKS_DONE.md ran through localhost:8081 pointed at the
hosted project, never through the deployed dailydama.com build itself.

Both hypotheses are checkable without needing dashboard/CLI credentials,
because EXPO_PUBLIC_* values are inlined verbatim into the shipped JS
bundle and are explicitly non-secret (.env.example: "the anon/publishable
key is safe to inline into the client bundle"). Diagnose bottom-up from the
real production artifact before touching anything.

## Diagnosis steps (in order)

1. Extract what the live bundle actually has baked in.
   - `curl -sI https://dailydama.com/feedback.html` (static-export route
     name per DEPLOYMENT_HANDOFF.md section 2's shape) to confirm the route
     exists and get a 200.
   - `curl -s https://dailydama.com/feedback.html` and find the referenced
     `_expo/static/js/web/*.js` bundle path(s) in the HTML script tags.
   - Fetch that bundle to a scratch file, then search it for a
     `*.supabase.co` URL substring and a publishable-key-shaped token near
     it (current Supabase publishable keys are prefixed `sb_publishable_`;
     older anon keys are JWT-shaped -- check both patterns).
   - If neither a `*.supabase.co` URL nor a key-shaped token is found
     anywhere in the exported bundle: EXPO_PUBLIC_SUPABASE_URL /
     EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY are not set for Vercel's
     Production environment. This is the defect -- skip to Fix path A
     below. Every Supabase-backed feature on the live site (feedback and
     Auth) is silently degraded, so flag this prominently regardless of
     which fix path applies.
   - If found, confirm the URL matches
     `https://ylyoqswauqyesuwmetnl.supabase.co` (the one documented hosted
     project -- a mismatch would itself be the defect, e.g. pointing at a
     stale/different project). Record the exact URL and key for step 2.

2. Reproduce the exact PostgREST response directly, using the real
   extracted anon key (do this even if step 1 found a URL/key -- this
   step is what tells you the actual Postgrest error, not a guess). POST
   to `https://ylyoqswauqyesuwmetnl.supabase.co/rest/v1/feedback` with
   headers `apikey`/`Authorization: Bearer <extracted-key>`,
   `Content-Type: application/json`, and -- important, mirrors the JS
   client's `db.schema: 'api'` option for non-public schemas, omitting it
   would misdiagnose a working setup as broken -- `Content-Profile: api`
   and `Accept-Profile: api`, with a body like
   `{"message":"T221 diagnosis probe"}`. Read the response body and HTTP
   status carefully:
   - PGRST106 / "The schema must be one of the following: public,
     graphql_public" -> the hosted project's Data API config (Dashboard ->
     Project Settings -> API -> Data API -> Exposed schemas, or Management
     API GET/PATCH /v1/projects/ylyoqswauqyesuwmetnl/config/postgrest's
     db_schema field) never had `api` added. This is a hosted-only
     setting, not read from supabase/config.toml's local [api] block --
     same category of gap HOSTED_DEV_CONFIG.md already documents for
     [auth]. Skip to Fix path B1.
   - PGRST205 / "Could not find the table 'api.feedback' in the schema
     cache" (with `api` otherwise a valid schema) -> the schema is exposed
     but the table doesn't exist there: the migration was never applied to
     the hosted project's Postgres. Skip to Fix path B2.
   - 42501 / "permission denied" or "new row violates row-level security
     policy" -> table exists, schema is exposed, but the anon grant/policy
     is missing or drifted. Compare live grants against
     supabase/migrations/20260902000000_add_feedback_table_with_anon_insert.sql
     line by line; this would mean an earlier partial apply happened.
     Less likely given the "no push pipeline exists" evidence above, but
     don't skip verifying it if the response doesn't match B1/B2 exactly.
   - 201 Created -> the insert actually succeeds against the hosted
     project with real credentials. This rules out both leading hypotheses
     and reframes the whole task: the defect is a live-browser-only bug
     (something environment-specific to the actual page load -- e.g. a CSP
     script-src hash mismatch silently breaking hydration so state updates
     never repaint, a stale cached JS bundle serving a pre-fix
     feedback-screen.tsx, or a duplicate/hidden component instance). Go
     straight to step 3's live walkthrough to find it; do not guess.

3. Live walkthrough on the real environment, required by the exit criteria
   regardless of what steps 1-2 found (this is also what proves the fix,
   not just diagnoses the break): open https://dailydama.com/feedback in a
   real browser with devtools Network tab open, submit a Message-only
   form, and confirm:
   - The exact request fired (URL, headers, body) -- should match step 2's
     manual reproduction once fixed.
   - The exact response status/body.
   - Whether `submitted` state visibly renders (the "Thanks for the
     feedback." screen) immediately after a 201.
   If step 2 already reproduced a clear failure, this walkthrough is mainly
   confirmation before/after the fix, not additional discovery -- don't
   spend time re-diagnosing here if step 2 was conclusive.
