# T288 plan: withhold unsupported account promises from the native guest experience

Branch: `task/T288-withhold-unsupported-account-promises` (resumed). JS/TS-only change; **no native rebuild needed** (no native dependency or config plugin changes; the existing `com.dailydama.app` dev client loads the new JS from Metro).

## Findings that shape the design

- Native gap is real: `getSupabaseClient()` (`src/shared/supabase/supabase-client.ts`) returns `null` whenever `Platform.OS !== 'web'`, so `AuthProvider` settles at `{status:'guest', reason:'unconfigured'}` on native. Do not touch that guard.
- Unsupported entry points (all assume working accounts):
  1. `src/features/auth/components/guest-account-section.tsx` (Profile; "keep your progress backed up", Sign up/Sign in buttons).
  2. `src/features/landing/components/landing-auth-cta.tsx` (landing header Sign up/Sign in). Authenticated Log out branch is unreachable natively; leave it.
  3. `src/features/sesh/components/sesh.tsx`: `InlineSignupInvite` (first regular Sesh) and `PostSeshSignupInvite` (every 5th after), gated by `showSignupInvite` computed at ~line 173 from `authStatus === 'guest' && isRegularSessionInviteEligible(...)`. Copy says "Sign up to keep it..." (backup promise).
  4. Direct routes under `src/app/auth/*`: sign-in, sign-up, forgot-password, reset-password, check-email, callback (all rendered through `src/app/auth/_layout.tsx` `<Slot />`). Other in-app links into these (e.g. sign-up screen -> sign-in) sit inside those screens and are covered by gating the layout.
- Do NOT key the capability off `reason === 'unconfigured'`: `profile/__tests__/index.test.tsx` and `sesh/__tests__/layout.test.tsx` use that reason for web-behaviour assertions, and a web dev build without env vars would also be mislabelled. Key it off platform, mirroring the client guard.
- jest-expo defaults `Platform.OS` to `'ios'` in tests (see `landing-page.test.tsx`, which forces `ReactNative.Platform.OS = 'web'` for the file). Existing web account/invitation tests will therefore start seeing the native path and must pin web explicitly. This is the main churn/risk of the change.

## Steps

1. **Capability model (new, pure).** `src/features/auth/model/account-availability.ts`:
   `export function areAccountsAvailable(platformOS: string): boolean { return platformOS === 'web'; }` plus a tiny hook `useAccountsAvailable()` (in `src/features/auth/state/` or same file if kept dependency-light) that reads `Platform.OS` from `react-native`. Comment the invariant: this must stay in lockstep with the `Platform.OS !== 'web'` guard in `getSupabaseClient`; when S040 enables native auth, flip this one predicate (and delete the withholding). Optionally have `supabase-client.ts` import the same predicate so the two cannot drift, but only if that does not create an import cycle (auth/model has no deps; fine). Unit test the predicate (web true; ios/android false).
2. **Shared unavailable-copy constant** in the same model file (single source of truth for wording), e.g. title "Accounts aren't available on iPhone yet", body "Your practice is saved on this device. Sign-up and backup are coming later." Keep it accurate: do not say "backed up"; do say data stays on-device. Avoid mentioning iOS-only strings if the same component might render on Android (use "in the mobile app").
3. **Profile.** In `guest-account-section.tsx`, when `!useAccountsAvailable()`: render the Account section with the unavailable note only (no buttons, no "backed up" copy). Keep the `authState.status !== 'guest'` null guard. Extend `guest-account-section.test.tsx`: pin `Platform.OS='web'` for existing cases; add native cases asserting no "Sign up"/"Sign in" labels, no "backed up" text, and `router.push` never called.
4. **Landing.** In `landing-auth-cta.tsx`, when guest and accounts unavailable return `null` (the brand-only bar adds nothing; the landing page has its own brand/hero). Check `landing-page.tsx` layout (line ~145) and `includeWebHeaderInset` still look right with it absent on native; if the header spacing depended on the bar, render the brand-only `HeaderBar` instead. Pin web in existing `landing-auth-cta.test.tsx`/`landing-page.test.tsx` as needed; add native case (no Sign up/Sign in).
5. **Sesh invitations.** Prefer gating at the source: in `sesh.tsx` the `inviteEligible` computation (~line 173) additionally requires `areAccountsAvailable(Platform.OS)` (or add a prop-free hook call), so neither the first-time inline nor every-fifth overlay renders and no state is set. Keep the pure `isRegularSessionInviteEligible` and its cadence tests untouched. Consider whether a short non-promissory "Your history is saved on this device" note is wanted; default is to render nothing (YAGNI). Update `sesh.test.tsx`: pin web for the existing invitation cases; add native cases for first Sesh and 6th Sesh proving no `Guest signup invitation` node, with the completion summary still rendering and Sesh recording unchanged (history still saved exactly once).
6. **Direct auth routes.** Create `src/features/auth/components/account-unavailable-screen.tsx` (uses `Screen`, `DisplayTitle`/`BodyText`, `Button`): explains unavailability with the shared copy and one action, "Back to app", doing `router.replace('/')` (landing; if onboarded users get redirected home by the existing landing redirect, fine) -- verify the destination is escapable for both onboarded and fresh guests; pick `/app/home` only if it is safe for non-onboarded guests (it uses `useRequireOnboarding`, which redirects). Give the button an accessibilityLabel and focus the heading on mount per the AGENTS.md web UX baseline. In `src/app/auth/_layout.tsx`, render `<AccountUnavailableScreen />` instead of `<Slot />` when `!areAccountsAvailable(Platform.OS)`. Gating in the layout means no auth screen (and thus no `useAuthActions` call, no network, no form) mounts for sign-up, sign-in, forgot-password, reset-password, check-email or callback. `account-deleted.tsx` is outside this layout and is informational; leave it. Layout tests: native -> unavailable screen shown, children (a sentinel `Slot` mock) not rendered, auth actions never called, back button navigates; web -> `Slot` rendered. Also confirm `PendingVerificationEmailProvider` mounting position is harmless (keep providers, swap only the child).
7. **Existing test pinning sweep.** Run `yarn jest src/features/auth src/features/landing src/features/sesh src/app` and pin `Platform.OS = 'web'` (per the landing-page.test.tsx pattern, restoring in `afterAll`) in each web-behaviour file that now fails. Do not weaken assertions. Keep web behaviour unchanged.
8. **Integration proof (native chain).** One test with the real `AuthProvider` under `Platform.OS='ios'` (as `auth-provider.test.tsx` does with a null client) rendering `GuestAccountSection` + `LandingAuthCta` + the auth layout: asserts all CTAs absent and the unavailable screen shown. Guards the predicate/guard pairing.
9. **Docs in same change.** Update `ARCHITECTURE.md` (auth section: native is guest-only; accounts gated by `areAccountsAvailable`; temporary until S040) and the T288 line in `TASKS.md` per workflow when closing (move to `TASKS_DONE.md` per repo convention). Note in DESLOPPIFY.md S040 row only if the convention requires; BACKLOG_STORIES S040 stays Proposed. ## Risks / notes

- Hidden coupling: predicate vs `getSupabaseClient` guard (mitigated in step 1/8).
- Initial `initializing` auth state is irrelevant to the platform predicate, so no flash of auth forms natively.
- Do not add SecureStore, callbacks, identity transitions or sync; do not edit `AuthProvider` or the client guard.
- Existing web tests silently running as iOS is the likeliest source of surprising failures; pin web rather than changing production logic to satisfy them.
