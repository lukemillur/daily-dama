# T247 - Prevent logout when pending-data discard is not durable

Branch: `task/T247-prevent-logout-when-pending-data-discard`
Source finding: DESLOPPIFY.md D001. Corrective follow-up to T158.

## 1. What is actually broken today (verified on this branch)

The discard path is fail-open at three separate links:

1. `src/shared/persistence/use-identity-scoped-domain.ts:110-160` - the write-queue worker
   awaits `optionsRef.current.save(...)`, calls `onSaveFailed` when the result is
   `{ status: "failed" }`, and then **resolves normally**. `saveNow` is typed
   `(value: State) => Promise<void>`, so the caller cannot tell a durable write from a failed
   one. A superseded generation is likewise indistinguishable: the worker either early-returns,
   or `guardedStorage.setItem` silently no-ops while `save` still reports `{ status: "saved" }`.
2. Each of the five domain hooks (`use-profile-domain-sync.ts:408-417`,
   `use-custom-trick-domain-sync.ts:365-374`, `use-practice-history-domain-sync.ts:309-318`,
   `use-goal-domain-sync.ts:373-382`, `use-note-domain-sync.ts:380-389` - all five bodies are
   byte-identical) does `await envelope.saveNow(result.envelope)` and then *unconditionally*
   dispatches `outboxDiscarded`. A failed disk write therefore clears the in-memory outbox
   while the old outbox survives on disk, so the discarded operations are replayed on the next
   hydration of that identity.
3. `src/shared/sync/sync-coordinator-provider.tsx:72` (`discardAllPending`) returns
   `Promise<void>` via `Promise.all`, and `use-logout-guard.ts:131-145` treats *resolution* as
   success and dispatches `discardFinished`, whose reducer case is commented as
   "Unconditional" and goes straight to `signingOut`.

Every `save*` implementation in the repo already catches and returns `PersistenceSaveResult`
(`saveSyncEnvelope` at `src/shared/sync/sync-envelope.ts:368-379`, `saveGuestImportState`, the
five primary-domain saves). So today the *returned-failure* path is the reachable one. A
genuinely thrown save would today reject `saveNow`, reject `Promise.all`, produce an unhandled
rejection in the discard effect .then chain, and leave the guard wedged in `discarding` forever.
Both paths must be closed.

## 2. Design decisions (settle these before writing code)

**D1 - One typed outcome vocabulary, three statuses, defined in shared/persistence.**
Add to `src/shared/persistence/storage.ts`, next to `PersistenceSaveResult`:

```ts
export type ScopedSaveOutcome =
  | { readonly status: "saved" }
  | { readonly status: "failed"; readonly error: unknown }
  | { readonly status: "superseded" };
```

`PersistenceSaveResult` (the adapter-level contract) stays exactly as-is. `ScopedSaveOutcome` is
the *hook-level* contract that additionally knows about identity generations. T248.1 will build
its durability state on this type, so keep it in `storage.ts` rather than hiding it in the hook.

**D2 - `saveNow` never rejects.** It resolves with a `ScopedSaveOutcome`. This is a deliberate
behavior change for a thrown `save`: it becomes `{ status: "failed", error }` plus an
`onSaveFailed` call instead of a rejected promise. It also removes the latent unhandled
rejection from the effect-driven writer `void enqueueWrite(...)`. Document both in the comment.

**D3 - Superseded means "do not act on this result", not "nothing was written".** If the
generation flips *after* a successful `setItem` but before the worker returns, report
`superseded`. The disk write did land in the correct (old) namespace, so there is no replay
risk, but the caller must not dispatch into a now-rehydrating reducer and the logout flow must
not advance. Do not call `onSaveFailed` on the superseded path (it never did, and that report
would belong to a stale identity).

**D4 - Preserve the FIFO queue and both generation guards exactly.** `createWriteQueue` keeps
one queue per domain for the whole domain lifetime, keeps the `pending = result.catch(...)`
failure containment, and keeps the two-layer guard (cheap pre-check plus the authoritative
synchronous re-check inside `guardedStorage.setItem`). The only change is that the worker return
value now reaches the caller. Do not add a second writer, a per-identity queue, or a retry loop
(retry belongs to T248.1).

**D5 - Partial success is a legitimate terminal state, and there is no rollback.** When one
domain write fails, the four that succeeded stay durably cleared. Re-pressing "Discard and log
out" retries only the still-pending domain (the others take the empty-outbox fast path). Never
re-add discarded operations to a domain that already cleared them.

**D6 - Aggregation precedence: superseded > failed > discarded.** If any domain reports
`superseded`, the identity moved underneath the whole flow and the guard is about to be reset
anyway; per-domain failure copy for a stale identity would be noise. Encode this in a *pure*
helper so it is unit-testable without the provider tree.

**D7 - The guard returns to `prompt` on failure, and to `idle` on supersession.** Returning to
`prompt` is what keeps the overlay mounted (`account-section.tsx` `showPrompt` already includes
`prompt`) with the live, now-smaller `pendingCount` and actionable copy. Never reach
`signingOut` from a non-discarded outcome.

**D8 - The new guard state field is required, not optional.** `discardFailedDomains:
readonly SyncDomain[] | undefined` mirrors the existing `errorCategory: ... | undefined`
convention and forces every existing `LogoutGuardState` literal in `logout-guard.test.ts` to be
updated. That is desirable: those `toEqual` assertions must assert the new field.

## 3. Ordered implementation steps

Do these in order. Each step compiles on its own except where noted.

### Step 1 - `src/shared/persistence/storage.ts`

- Add the `ScopedSaveOutcome` union from D1.
- Widen the queue so a worker value reaches its caller, without changing ordering or failure
  containment:

```ts
export function createWriteQueue<T, R = void>(write: (value: T) => Promise<R>) {
  let pending: Promise<unknown> = Promise.resolve();

  return (value: T): Promise<R> => {
    const result = pending.then(() => write(value));
    pending = result.catch(() => undefined);
    return result;
  };
}
```

`pending` must be typed `Promise<unknown>` (it holds `Promise<R | undefined>` after the first
write). Check that the other caller, `writeStatus` in `sync-coordinator-provider.tsx:29`, still
infers cleanly with `R = void`.

### Step 2 - `src/shared/persistence/use-identity-scoped-domain.ts`

- Change `UseIdentityScopedDomainResult.saveNow` to `(value: State) => Promise<ScopedSaveOutcome>`
  and update its doc comment (it currently says "durably queued"; it now says durably written,
  or reports why not).
- Rewrite the `createWriteQueue` worker body to return `Promise<ScopedSaveOutcome>`:
  - Early bail-out becomes `return { status: "superseded" };` (keep the existing comment).
  - Add `let supersededDuringWrite = false;` captured by `guardedStorage.setItem`; when the
    synchronous re-check fails, set it true before the existing `return Promise.resolve()`.
  - Wrap the `await optionsRef.current.save(...)` call in try/catch.
  - After a resolved save: if `supersededDuringWrite` is true OR
    `!context.isCurrentGeneration(taggedGeneration)`, return `{ status: "superseded" }`
    **before** inspecting `result.status` (D3). Then map a failed result to an `onSaveFailed`
    call plus `{ status: "failed", error }`, otherwise `{ status: "saved" }`.
  - In the catch: same superseded pre-check, then `onSaveFailed?.(error)` and
    `{ status: "failed", error }`.
- `saveNow` and the write effect are otherwise untouched. The effect keeps `void enqueueWrite(...)`
  and ignores the outcome; consuming it is T248.1 work.

### Step 3 - `src/shared/sync/discard-outcome.ts` (new file)

A small pure module so the aggregation rule is testable without React:

```ts
import type { SyncDomain } from "@/shared/sync/domain";

export type DomainDiscardOutcome =
  | { readonly status: "discarded" }
  | { readonly status: "failed"; readonly error: unknown }
  | { readonly status: "superseded" };

export interface DiscardFailure { readonly domain: SyncDomain; readonly error: unknown }

export type DiscardAllPendingResult =
  | { readonly status: "discarded" }
  | { readonly status: "failed"; readonly failures: readonly DiscardFailure[] }
  | { readonly status: "superseded" };

export function aggregateDiscardOutcomes(
  entries: readonly (readonly [SyncDomain, DomainDiscardOutcome])[],
): DiscardAllPendingResult;
```

`aggregateDiscardOutcomes` implements D6: collect every failed entry into `failures` (preserving
the caller entry order, which follows `SYNC_DOMAINS`), return `superseded` if any entry is
superseded, else `failed` if there is at least one failure, else `discarded`. The header comment
must state the precedence and the reason for it.

### Step 4 - the five domain sync hooks (identical edit, five files)

`src/features/profile/state/use-profile-domain-sync.ts`,
`src/features/custom-tricks/state/use-custom-trick-domain-sync.ts`,
`src/features/stats/state/use-practice-history-domain-sync.ts`,
`src/features/goals/state/use-goal-domain-sync.ts`,
`src/features/notes/state/use-note-domain-sync.ts`.

- In each `Use*DomainSyncResult` interface, change `discardPending: () => Promise<void>` to
  `() => Promise<DomainDiscardOutcome>`.
- The body becomes:

```ts
const discardPending = useCallback(async (): Promise<DomainDiscardOutcome> => {
  const { identity: currentIdentity, envelopeState, envelopeDispatch } = latestRef.current;
  if (envelopeState.outbox.length === 0) return { status: "discarded" }; // nothing to clear

  const result = discardPendingOperations(envelopeState, currentIdentity);
  if (result.status !== "applied") return { status: "superseded" }; // identity changed underneath

  const saveOutcome = await envelope.saveNow(result.envelope);
  if (saveOutcome.status === "failed") return { status: "failed", error: saveOutcome.error };
  if (saveOutcome.status === "superseded") return { status: "superseded" };

  // Only now is the cleared outbox durable, so the in-memory clear can follow.
  envelopeDispatch({ type: "outboxDiscarded", identity: currentIdentity });
  return { status: "discarded" };
}, [envelope]);
```

- Map the statuses explicitly (never `return saveOutcome`) so `ScopedSaveOutcome` and
  `DomainDiscardOutcome` stay independent vocabularies.
- Keep the order as written: **persist first, then dispatch**. That order is what makes
  "failure preserves the outbox in memory and on disk" true for free - a non-saved outcome
  leaves the reducer state unchanged, so the effect-driven writer never fires either.

## 4. Risks and edge cases

- **Promise.all to allSettled is load-bearing.** With `all`, the first rejection settles the
  aggregate before the other four outcomes are known - exactly how a partial failure would
  become an unreported sign-out.
- **Do not add `generation` to the discard effect dependency array** (Step 8). It would re-fire
  `discardAllPending()` mid-flight. The explicit ref comparison is the intended mechanism.
- **Pessimistic supersession is intentional** (D3): a write that landed and *then* saw a
  generation flip reports superseded, not saved. The caller must not dispatch into a rehydrating
  envelope, and there is no data-loss consequence because the disk write completed.
- **Concurrent envelope mutation during a discard** (a background sync run dispatching
  `operationAcknowledged` or `operationAttemptRecorded` while the prompt is open) can still, in
  principle, interleave with the snapshot the discard captured from `latestRef`. That is
  pre-existing T158 behavior, is not what D001 describes, and must not be redesigned here.
  Mention it in the PR description if you end up working near it.
- **`use-guest-import.ts` also calls `saveNow`** (lines 267, 287, 317) inside a try/catch and
  ignores the outcome. After D2 a thrown save no longer reaches that catch. Nothing changes in
  practice today, because `saveGuestImportState` already catches and returns a failed result, so
  leave guest-import untouched; consuming the new outcome there is T248 visibility work.
- **Scope fence:** no retry loop, no retained unsaved snapshot state, no app-level durability
  banner, no `onSaveFailed` redesign, no second write path. Those belong to T248.1 and T248.2.
- **Copy check:** the prompt is a full-screen overlay, so the added failure line must not push
  the buttons off a 320 px wide viewport. Keep it to one short paragraph and reuse the existing
  `RetryFailedCopy` sizing.
