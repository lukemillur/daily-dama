# T217.1 -- Add `api.feedback` table with anon insert-only RLS

## Context already confirmed

  `anon` currently has **no** `USAGE` on schema `api` at all (step 5's final

  `20260823010000_extend_goals_update_grant_for_target_editing.sql`. Use a

## Design decisions locked in for this plan

1. **Both a table-level CHECK layer and a matching RLS `WITH CHECK`.** The
   task text asks for the validation "via an RLS policy with a WITH CHECK
   clause." Satisfy that literally in the policy. Additionally mirror the
   same bounds as table-level `CHECK` constraints, matching this repo's
   existing convention (`profiles`, `user_trick_states` both encode their
   domain invariants as table CHECK constraints, independent of RLS). This
   is intentional duplication, not sloppiness -- say so in a migration
   comment: table CHECKs are enforcement that holds regardless of future
   grants/policy changes to any role (including `service_role`, which
   bypasses RLS entirely but not CHECK constraints); the policy's `WITH
   CHECK` is what the task explicitly asked for and is what actually gates
   `anon` specifically.
2. **Email format check**: Postgres `~` uses POSIX ERE, no `\s`/`\d` -- use
   bracket classes: `email ~ '^[^@[:space:]]+@[^@[:space:]]+\.[^@[:space:]]{2,}$'`.
   This is deliberately basic (no full RFC 5322 validation) -- matches the
   task's "basic email-format check" framing.
3. **Message non-empty check**: `length(btrim(message)) > 0` -- rejects
   whitespace-only messages, not just the empty string, since `message text
   not null` alone only blocks literal `NULL`/`''`.
4. **Do not edit the historical migration file's stale comment.** Editing
   `-- 5. ... anon gets nothing here or anywhere else ...` in
   `20260822191737_...sql` in place is tempting but risky: that file may
   already be applied to the hosted "Daily Dama Dev" project (T153.2), and
   rewriting an already-applied migration's contents is exactly the kind of
   drift Supabase's migration tracking is designed to catch/complain about.
   The task's own wording offers "update **or annotate**" -- take the
   annotate branch: the new migration's own leading comment block
   explicitly says this is a deliberate, narrow exception to that earlier
   file's stated policy, quotes the stale line, and explains why it's now
   inaccurate. That is discoverable by anyone reading the new file (and by
   anyone reading the old file's history), without touching already-shipped
   SQL.
5. **Grant `USAGE` on schema `api` to `anon`.** This is new, not present
   anywhere yet, and is the actual mechanism that makes the old blanket
   claim stale. Do not grant `anon` `USAGE` on schema `private` -- no reason
   to, table lives entirely in `api`.

2. Create `supabase/migrations/<timestamp>_add_feedback_table_with_anon_insert.sql`
   with the exact SQL contract in the next section below (not just a
   sketch -- create the file with this content, adjusting comment wording
   only to match repo voice if needed).

```sql
-- Add api.feedback (T217.1): a narrow, deliberate exception to the "anon
-- gets nothing here or anywhere else" policy stated in
-- 20260822191737_create_private_and_exposed_schemas.sql's step 5. That
-- comment is now stale: this migration grants `anon` USAGE on schema `api`
-- and INSERT-only access to exactly one table, so users can submit feedback
-- without an account. No other anon grant exists anywhere else in the
-- schema; anon still cannot SELECT/UPDATE/DELETE this table or reach any
-- other table or schema. See TASKS.md T217/T217.1 for why this table exists
-- (Resend inbound email was rejected during scoping -- shared send-quota
-- risk with Auth transactional email) and why anon-insert was chosen over
-- server-side/service-role insertion (would bypass RLS entirely for that
-- connection, a larger blast radius for an app-code bug than an
-- RLS-scoped anon grant, for no real increase in anonymous capability).

-- 1. Table. No user_id/ownership column at all -- feedback is intentionally
--    anonymous-or-not (name/email are free-text, optional, unverified
--    contact info the submitter volunteers, not an identity).
create table api.feedback (
  id uuid primary key default gen_random_uuid(),
  created_at timestamptz not null default now(),
  name text,
  email text,
  message text not null,

  -- Table-level CHECK constraints are the durable enforcement layer: they
  -- hold regardless of which role writes (including service_role, which
  -- bypasses RLS) and regardless of future grant/policy changes. The RLS
  -- policy below intentionally repeats the same bounds in its WITH CHECK,
  -- which is what actually gates `anon` specifically.
  constraint feedback_message_not_blank check (length(btrim(message)) > 0),
  constraint feedback_message_length check (length(message) <= 2000),
  constraint feedback_name_length check (name is null or length(name) <= 100),
  constraint feedback_email_length check (email is null or length(email) <= 254),
  constraint feedback_email_format check (
    email is null or email ~ '^[^@[:space:]]+@[^@[:space:]]+\.[^@[:space:]]{2,}$'
  )
);

comment on table api.feedback is
  'Free-text user feedback, submitted with no account required (T217). name/email are optional, unverified, submitter-supplied contact info -- not an identity or FK. anon may INSERT only; no SELECT/UPDATE/DELETE grant exists for any non-privileged role.';
```

```sql
-- 2. RLS + grants. anon gets schema USAGE (new -- see file header) and
--    INSERT only on this one table. No SELECT grant means an anon INSERT's
--    default (Prefer: return=minimal) response has no representation to
--    return, which is fine and intended; granting SELECT to make
--    return=representation work would break "insert-only".
grant usage on schema api to anon;

alter table api.feedback enable row level security;

grant insert on api.feedback to anon;

create policy feedback_insert_anon on api.feedback
  for insert
  to anon
  with check (
    length(btrim(message)) > 0
    and length(message) <= 2000
    and (name is null or length(name) <= 100)
    and (email is null or length(email) <= 254)
    and (email is null or email ~ '^[^@[:space:]]+@[^@[:space:]]+\.[^@[:space:]]{2,}$')
  );
```

Ordering rationale: schema `USAGE` grant before `ENABLE ROW LEVEL
SECURITY`/table grant/policy doesn't matter functionally, but keep it first
since it's the new/unusual part callers should notice immediately; table
creation must precede everything else naturally.

   against a freshly reset stack). Get keys first:

```sh
npx --yes supabase@2.116.0 status -o json
```

   Export `ANON_KEY`, `SERVICE_ROLE_KEY`, and use `http://127.0.0.1:54321`
   as the API URL (matches every other manual-verification block in

   **(a) Well-formed insert succeeds:**

```sh
curl -i -X POST 'http://127.0.0.1:54321/rest/v1/feedback' \
  -H "apikey: $ANON_KEY" \
  -H "Authorization: Bearer $ANON_KEY" \

{"name": "Test User", "email": "test@example.com", "message": "Loving the app!"}
```

   Expect `201 Created`, empty body (no `Prefer` header sent, so
   `return=minimal` is the default -- do not treat an empty body as a
   failure).

   **(b) SELECT/UPDATE/DELETE with anon key are rejected:**

```sh
curl -i 'http://127.0.0.1:54321/rest/v1/feedback' \
  -H "apikey: $ANON_KEY" \
  -H "Authorization: Bearer $ANON_KEY" \
  -H "Accept-Profile: api"
```

```sh
curl -i -X PATCH 'http://127.0.0.1:54321/rest/v1/feedback?message=eq.Loving%20the%20app!' \
  -H "apikey: $ANON_KEY" \
  -H "Authorization: Bearer $ANON_KEY" \
  -H "Content-Profile: api" \
  -H "Content-Type: application/json" \
  --data-binary @edit-attempt.json
```

   `edit-attempt.json`: `{"message": "edited"}`

```sh
curl -i -X DELETE 'http://127.0.0.1:54321/rest/v1/feedback?message=eq.Loving%20the%20app!' \
  -H "apikey: $ANON_KEY" \
  -H "Authorization: Bearer $ANON_KEY" \
  -H "Content-Profile: api"
```

   Expect all three to be rejected (no `SELECT`/`UPDATE`/`DELETE` grant
   exists at all for `anon`, so Postgres denies at the privilege layer --
   PostgREST typically surfaces this as `401` with `"code":"42501"`,
   `"message":"permission denied for table feedback"`; confirm the actual
   status/code returned rather than assuming a specific number, and record
   what was actually observed).

   **(c) Insert violating a length/format constraint is rejected.** Reuse
   the exact POST call from (a), swapping only the request body for each
   case (still against `http://127.0.0.1:54321/rest/v1/feedback` with the
   same anon headers):

   - Empty message: `{"message": ""}`
   - Message too long: `{"message": "<2001+ repeated characters>"}`
   - Malformed email: `{"message": "hi", "email": "not-an-email"}`

   Expect each to be rejected with a `4xx` (either the table CHECK
   constraint fires as `23514`/`400`, or the policy `WITH CHECK` fires as
   `42501`/`401` -- both are "rejected"; note which one actually fired for
   each case, since it's a useful confirmation the two enforcement layers
   are both live).

   **(d) service_role/direct DB access can read back the row from (a):**

```sh
curl -i 'http://127.0.0.1:54321/rest/v1/feedback?message=eq.Loving%20the%20app!' \
  -H "apikey: $SERVICE_ROLE_KEY" \
  -H "Authorization: Bearer $SERVICE_ROLE_KEY" \
  -H "Accept-Profile: api"
```

   Expect `200` with exactly the row inserted in (a) (same `name`/`email`/
   `message`, a generated `id`, a `created_at` close to when it was
   inserted). This is what actually proves (a) persisted rather than just
   returning a misleadingly-successful status.

## Order-of-operations rationale

Table DDL must exist before RLS/grants/policy (step 2 is one file, so this
is just intra-file ordering, already reflected above). The pgTAP file (step
5) and manual REST verification (step 6) both need a clean, already-applied
migration (steps 2-3) and, for step 6 specifically, correct generated types
are not a dependency (types don't gate REST behavior) but should still land
before or alongside the migration in the same commit so the repo is never
left with a schema/types mismatch -- do step 4 before finishing, not
necessarily before step 6's manual checks.
