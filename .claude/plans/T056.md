# T056 — Show the rank's trick list before skipping it in a Kentei assessment

## Where this lives

All the logic change is confined to `src/features/sesh/components/multi-trick-sesh.tsx`.
Confirmed by reading the current code:

- `SkipRankButton` (`src/features/sesh/components/sesh.tsx`, in `Countdown` and
  `ActiveSesh`) is a bare presentational button — it only ever calls the
  `onSkipRank` prop it's given. It doesn't need to change; only what the
  caller's `onSkipRank` *does* changes.
- The only caller that ever supplies `onSkipRank` is `MultiTrickSesh`
  (`skipTarget ? handleSkipRank : undefined`, two call sites: the `Countdown`
  branch and the `ActiveSesh` branch). The plain single-trick `Sesh` component
  never passes `onSkipRank` at all, so this task cannot affect it.
- `MultiTrickSesh` already holds everything needed for the preview with no new
  data plumbing, exactly as the task Notes say:
  - `sequence.tricks` is the full ordered `readonly PracticeTrick[]` for the
    run (from `trick-sequence.ts`), and `sequence.currentIndex` is "where we
    are now."
  - `skipTarget(sequence.currentIndex)` (passed in from
    `assessment-entry.tsx`, backed by `selectNextRankStartIndex` in
    `kentei-assessment-run.ts`) already computes the target index.
  - So `sequence.tricks.slice(currentIndex, targetIndex)` is exactly the set
    of tricks a confirmed skip would discard — no changes needed to
    `kentei-assessment-run.ts` or `assessment-entry.tsx`.
  - `describeSkippedRange(fromIndex, targetIndex)` (also already threaded in
    from `assessment-entry.tsx`) already produces a string like
    `"Rank 10 — 3 tricks skipped"`. Reuse it as-is for the confirmation
    panel's heading/caption instead of inventing new copy-generation logic —
    it's optional today (used only for the wrap-up) and stays optional; the
    confirmation panel should degrade gracefully (generic trick-count text)
    if a future caller omits it.

## Current behavior being changed

`handleSkipRank` (multi-trick-sesh.tsx:259-278) currently fires immediately on
press: computes `targetIndex`, records the skipped-range description, jumps
the sequence, and seeds the next trick (or resets), all synchronously in one
handler. This task inserts a confirmation step between "user taps Skip this
rank" and that commit.

## Implementation steps

1. **Add `pendingSkip` state to `MultiTrickSesh`.**
   `const [pendingSkip, setPendingSkip] = useState<{ readonly fromIndex: number; readonly targetIndex: number } | undefined>(undefined);`
   Placed alongside the other run-local `useState`s near the top of the
   component (with `skippedEntries`, `isFirstCountdown`, etc).

2. **Split `handleSkipRank` into three handlers:**
   - `handleSkipRankRequest` — replaces the *first half* of today's
     `handleSkipRank`. Guards on `skipTarget`, computes
     `const targetIndex = skipTarget(sequence.currentIndex)`, and sets
     `pendingSkip({ fromIndex: sequence.currentIndex, targetIndex })`. Does
     **not** touch `isFirstCountdown`, `skippedEntries`, `sequence`, or
     dispatch anything — nothing observable changes yet, which is what makes
     "canceling leaves the run unaffected" trivially true.
   - `handleConfirmSkip` — the rest of today's `handleSkipRank` body, reading
     `fromIndex`/`targetIndex` off `pendingSkip` instead of recomputing them:
     `setIsFirstCountdown(false)`, append to `skippedEntries` via
     `describeSkippedRange(fromIndex, targetIndex)` if provided,
     `advanceTrickSequenceToIndex(sequence, targetIndex)`, `setSequence`,
     seed the next trick or `dispatch({ type: 'seshReset' })` — identical to
     today. Finish by `setPendingSkip(undefined)`.
   - `handleCancelSkip` — just `setPendingSkip(undefined)`.

   Important: compute `targetIndex` once, at request time, and carry it in
   `pendingSkip` rather than recomputing it in `handleConfirmSkip`. `tricks`
   is fixed for the life of the run (per the component's own doc comment) so
   this is safe, and it guarantees the preview list and the actual skip
   target can never disagree.

3. **Update both `onSkipRank` wiring sites** (the `Countdown` branch and the
   `ActiveSesh` branch, currently both `onSkipRank={skipTarget ? handleSkipRank : undefined}`)
   to point at `handleSkipRankRequest` instead. `SkipRankButton` itself in
   `sesh.tsx` needs no changes.

4. **Add a new early-return branch** at the top of `MultiTrickSesh`'s render
   logic (before the `state.status === 'countdown'` check), so it takes
   priority regardless of whether the run is currently in `countdown` or
   `active`:
   ```
   if (pendingSkip) {
     const skippedTricks = sequence.tricks.slice(pendingSkip.fromIndex, pendingSkip.targetIndex);
     return (
       <SkipRankConfirmation
         tricks={skippedTricks}
         description={describeSkippedRange?.(pendingSkip.fromIndex, pendingSkip.targetIndex)}
         onCancel={handleCancelSkip}
         onConfirm={handleConfirmSkip}
       />
     );
   }
   ```
   Because this only reads local state and doesn't dispatch, the underlying
   `state`/`sequence` are untouched while the panel is showing — canceling
   returns exactly to whatever countdown/active render was already correct
   before the tap (no need to reconstruct or re-derive anything).

5. **Add the `SkipRankConfirmation` component**, local to
   `multi-trick-sesh.tsx` next to `MultiTrickWrapUp` (same file, same
   pattern — a small presentational component that takes plain props, no
   hooks into the reducer):
   ```
   function SkipRankConfirmation({
     tricks,
     description,
     onCancel,
     onConfirm,
   }: {
     readonly tricks: readonly PracticeTrick[];
     readonly description?: string;
     readonly onCancel: () => void;
     readonly onConfirm: () => void;
   })
   ```
   Render, inside the existing `ScrollArea`/`ActiveContent` wrapper pattern
   used by `MultiTrickWrapUp`:
   - `accessibilityLabel="Skip rank confirmation"` on the outer content view,
     so tests/automation can assert the panel is showing.
   - `<Eyebrow>Skip this rank?</Eyebrow>`.
   - The `description` string if provided (reusing `describeSkippedRange`'s
     output, e.g. "Rank 10 — 3 tricks skipped"); if `undefined`, fall back to
     a generic `` `${tricks.length} trick${tricks.length === 1 ? '' : 's'} in this rank` ``
     so the panel still reads sensibly for a hypothetical future caller that
     doesn't supply `describeSkippedRange`.
   - The trick list itself: reuse the existing `WrapUpList`/`WrapUpRow`-style
     rows (or a minimally trimmed variant — just trick names, no lace
     count/time columns since these were never practiced) rather than
     inventing new list styling from scratch. `tricks.map((trick) => ...trick.name...)`,
     keyed by `trick.id`.
   - `<BodyCopy>` line clarifying consequence: nothing recorded for these
     tricks, mirrors existing wrap-up framing (e.g. "These tricks won't be
     recorded — you can revisit this rank later.").
   - Two actions using the existing `Button` component (same one `CancelButton`
     in `sesh.tsx` wraps): a primary "Skip rank" button
     (`accessibilityLabel="Confirm skip rank"`, `onPress={onConfirm}`) and a
     secondary "Cancel" button (`accessibilityLabel="Cancel skip rank"`,
     `onPress={onCancel}`, `variant="secondary"`) — distinct accessibility
     labels even though visible text ("Cancel") happens to overlap with the
     unrelated run-cancel button elsewhere, since they're never rendered
     simultaneously but tests should key off the unambiguous label.

6. **Update `multi-trick-sesh.test.tsx`.** Every existing test that presses
   "Skip this rank" and asserts on the *result* needs a confirm-button press
   inserted in between, since pressing "Skip this rank" now only opens the
   preview instead of committing:
   - `'lands directly in active on the next rank after "Skip this rank"'`
     (line ~381): after `pressByVisibleText(root, 'Skip this rank')`, add
     `act(() => { pressByAccessibilityLabel(root, 'Confirm skip rank'); })`
     before asserting `TRICKS[2]` is active.
   - `'excludes skipped tricks from the wrap-up...'` (line ~632) and
     `'reports a skipped rank as skipped, not failed...'` (line ~714): same
     insertion.
   - `'does not render Cancel on the second trick countdown after skipping past the first'`
     (line ~841): same insertion.
   Also add new coverage for the behavior this task actually introduces:
   - Pressing "Skip this rank" shows the confirmation panel
     (`accessibilityLabel="Skip rank confirmation"`) listing the specific
     tricks in that rank by name (assert `findByText` for each trick name in
     the skipped range), and does **not** yet advance — the original trick
     from before the tap is still the active/countdown trick underneath
     (i.e. no session recorded, `session-count:0` still holds if checked via
     `SessionSummary`).
   - Pressing "Cancel skip rank" dismisses the panel, returns to the exact
     prior state (same trick still showing, countdown/active as before), and
     a subsequent normal completion of that trick still records correctly —
     i.e. the skip had zero effect.
   - Confirming records no history for the skipped tricks (reuse the
     existing `SessionSummary`/`usePracticeHistory` assertions already used
     by the wrap-up tests) — this is "confirming skips exactly as today,"
     just gated behind one extra press.

## Order and why

Steps 1-4 are really one atomic edit to `multi-trick-sesh.tsx` (the state
split has no valid intermediate state), so implement them together, then add
the new component (step 5), then get it compiling/rendering before touching
tests (step 6) — the existing tests are the fastest signal that the
confirm/cancel wiring behaves like the old direct-skip did. Do TASKS.md (step
7) last, after `verify.mjs` passes.

## Things to double check while implementing

- `advanceTrickSequenceToIndex` clamps `targetIndex` to
  `[currentIndex, tricks.length]`. `skipTarget`'s own return (via
  `selectNextRankStartIndex`) is already bounded to `tricks.length`, so the
  preview slice (`sequence.tricks.slice(fromIndex, targetIndex)`) and the
  actual skip destination can never disagree — don't reclamp `targetIndex`
  separately in the confirmation panel or you risk the preview and the
  commit drifting apart.
- The `isFirstCountdown` flag (controls whether `onCancelRun`'s "Cancel"
  shows on the very first trick's countdown) must only flip in
  `handleConfirmSkip`, not in `handleSkipRankRequest` — this is what makes
  "canceling the skip leaves the run unaffected" true for that flag too, not
  just for `sequence`/`state`.
- `onSkipRank` is passed into both `Countdown` (shown before a trick starts)
  and `ActiveSesh` (shown once landings may already exist on the current,
  about-to-be-skipped trick). The confirmation panel is a full-screen replace
  in both cases (matches the existing `laceAcknowledgment` full-screen-replace
  pattern in the same component), so no special-casing is needed between the
  two — verify manually that skipping from mid-active-trick still shows the
  same panel and that canceling correctly resumes the in-progress trick
  (landings/timer untouched, since no dispatch happened).
- Only `assessment-entry.tsx` currently supplies `skipTarget`/
  `describeSkippedRange`, and only with `hideTimer`/`OPEN_ENDED_SESH_PLAN` —
  there's no live countdown-timer-versus-confirmation-panel race to worry
  about for the current caller, but don't assume that stays true forever;
  the confirmation panel intentionally doesn't touch `state`/timers at all,
  so it's safe regardless.

  `node .claude/scripts/verify.mjs` (or the four commands individually per
  AGENTS.md) — this task touches both component and test files, so don't use
  `--skip-export`.
