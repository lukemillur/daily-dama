## Step 1: Storage adapter module (new, plain, pure where possible)

New file `src/shared/supabase/session-storage.ts`.

- Export `type SessionStorage = SupportedStorage` (re-use the supabase-js type).
- `createEncryptedSessionStorage({ secureStore, asyncStorage, randomBytes })` returns an adapter with dependencies injected, so tests need no native modules.
  - `setItem(key, value)`:
    1. Get or create the AES-256 key in SecureStore under `${key}.aes-key`. Store it hex-encoded.
    2. Encrypt `value` with AES-CTR using a fresh random counter or IV.
    3. Write the IV and ciphertext (hex or base64, version-prefixed) to AsyncStorage under `key`.
    - Ordering is crash-safe: the key must exist before ciphertext is written. A crash after key creation but before the blob write leaves no session, which is a safe state.
  - `getItem(key)`: read the blob. If it is `null`, return `null`. Read the key. If the key is missing or decryption fails, return `null`. Do NOT throw, and do NOT remove the key. Treat it as signed out.
  - `removeItem(key)`: remove the AsyncStorage blob first, then the SecureStore key.
  - Any rejected write propagates as a rejection from `setItem`.
- If Step 0 allows direct SecureStore, export `createSecureStoreSessionStorage` instead, as a thin pass-through with the same interface. Do not build both. One implementation only, chosen by the gate.
- Export `getSessionStorage(): SessionStorage`. It is platform-selected at call time and memoized:
  - web returns `AsyncStorage`, unchanged;
  - ios and android return the native adapter.
- Add `resetSessionStorageForTests()`, or fold it into `resetSupabaseClientForTests`.
- Where the adapter checks the value shape, never log values. Redact.
- SecureStore options: `keychainAccessible: AFTER_FIRST_UNLOCK` is appropriate so background auto-refresh works while the device is locked. Confirm the constant name in Step 0.

## Risks and non-obvious points

- **Throw vs `{ error }`:** supabase-js does not convert storage rejections into `AuthError` results. Without the Step 3 wrapper a storage failure becomes an unhandled rejection in the sign-in form handler.
- **Do not set `storageKey`.** It signs every web user out. `resolveGoTrueStorageKey` is pinned by a test.
- **`inactive` is not `background`.** Only `background` stops refresh.
- **Hung retry:** a fresh client is required, not just a re-subscribe.
- **AES key loss:** if the keychain item is lost, for example after a reinstall (iOS Keychain can survive app deletion while AsyncStorage does not), a surviving key with no blob is fine. The inverse (blob with no key) decrypts to `null`, so the user is signed out cleanly. It must not crash.
- **Sign-up and email flows on native are still broken until T313.2.** Do not paper over the `window` guards here.
- **Android:** no dev build. Record checks as not run.
