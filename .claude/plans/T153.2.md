## Real blocker to flag up front

Creating and configuring a *hosted* Supabase project requires either:
(a) an authenticated interactive dashboard session (Supabase account login,
organization membership), or (b) a Supabase **personal access token** (PAT)
scoped to that organization, used non-interactively via the Supabase CLI or
the Management API (`https://api.supabase.com/v1/...`).

An autonomous agent has neither by default. This is very likely a hard stop
partway through implementation unless the user (Luke) has already created
the org/PAT or is available to do the one-time interactive parts. Concretely:

- If no `SUPABASE_ACCESS_TOKEN` (or equivalent) is available in the
  implementer's shell environment and no project already exists, **stop and
  report this as a blocker** rather than guessing at credentials or trying to
  drive a browser OAuth login non-interactively. Ask the user to either:
  1. Generate a PAT at https://supabase.com/dashboard/account/tokens and
     export it as `SUPABASE_ACCESS_TOKEN` in their own shell before handing
     off, so the CLI/Management API steps below can run headlessly, or
  2. Create the project manually via the dashboard themselves (name,
     org, region, free plan, a generated DB password stored only in their
     password manager / local `.env.local`) and hand back just the project
     ref, so the implementer can take over from the Auth-policy-configuration
     step onward.
- Outbound network access to `api.supabase.com` and `<ref>.supabase.co` must
  work from wherever these commands run. If the implementer's sandbox blocks
  outbound network entirely, this must also be reported as a blocker (or the
  live-config/probe steps run outside the sandbox, by the user, following the
  documented commands) rather than silently skipped.

## Ordered implementation steps

1. **Confirm credentials and non-goals before touching anything.**
   Verify `SUPABASE_ACCESS_TOKEN` (or dashboard access) is actually available.
   Confirm no hosted project already exists for this purpose (check for an
   existing project matching a "daily-dama-dev"-style name via
   `npx --yes supabase@2.115.0 projects list --output json`, or ask the user).
   If a project already exists, skip to step 4 (don't create a second one).

2. **Determine the organization to create the project under.**
   `npx --yes supabase@2.115.0 orgs list --output json` (requires the PAT env
   var). Confirm with the user which org this belongs to if more than one
   exists — this is an account-ownership decision, not one to guess.

3. **Create the single hosted free development project.**
   Generate a strong DB password locally (e.g. `openssl rand -base64 24`) and
   do not commit it anywhere — store it only in the user's password manager
   or gitignored `.env.local`. Create via CLI:
   ```
   npx --yes supabase@2.115.0 projects create "daily-dama-dev" \
     --org-id <ORG_ID> --plan free --region <region> --db-password <generated>
   ```
   (Verify current flag names against `--help` output at run time; CLI flags
   drift between versions even though this task is pinned to `2.115.0` for
   local dev — the *projects create* surface is a hosted-API call, not part
   of `config.toml`, so treat the exact flags as needing a live check, not
   memorized from this plan.) Name it distinctly from the reserved future
   production project (e.g. `daily-dama-dev` vs. a later `daily-dama-prod`)
   so Phase 1 item 6 cannot be confused with this one later.
   Poll `npx --yes supabase@2.115.0 projects list` (or the dashboard) until
   the project reaches `ACTIVE_HEALTHY` — Auth config API calls fail on a
   still-provisioning project.

4. **Configure the Auth policy to mirror `supabase/config.toml` exactly.**
   Use the Management API (`GET` then `PATCH`
   `https://api.supabase.com/v1/projects/{ref}/config/auth`, bearer-authed
   with the PAT) rather than guessing field names from memory — `GET` first
   to see the current live schema/field names (these are known to drift
   across Supabase API versions), then `PATCH` only the fields that map to:
   - Require email confirmation before sign-in (mirrors
     `enable_confirmations = true` locally — the hosted equivalent is
     commonly `mailer_autoconfirm: false`, but confirm the live field name
     via the `GET` response before writing).
   - `password_min_length` (or equivalent) → `10`.
   - `jwt_exp` (or equivalent access-token lifetime field) → `3600`.
   - `site_url` → `https://dailydama.com`.
   - The redirect allowlist field (commonly `uri_allow_list`, a
     comma-separated *exact*-match list, no wildcards) → exactly
     `http://localhost:8081/auth/callback,https://dailydama.com/auth/callback`
     — nothing else. If the project ships a wildcard/default entry, remove
     it; do not append to it.
   - Leave email/password as the only enabled provider (this is the new
     project's default — verify rather than assume, but do not enable
     phone/OAuth providers here).
   - Do not touch custom SMTP (T153.3) or secure-email-change/reauth fields
     (T154.1) in this pass.
   If dashboard-only access is available instead of the Management API, the
   same values map to: Authentication → Sign In / Providers → Email (confirm
   email toggle ON), Authentication → URL Configuration (Site URL + Redirect
   URLs, replacing any default wildcard with the exact two-URL list),
   Authentication → Sessions (access token / JWT expiry → 3600s), and the
   password-length/complexity setting under Authentication → Policies (or
   wherever the current dashboard surfaces it — dashboard layouts also drift;
   confirm the exact location live rather than trusting this description).

5. **Re-`GET` the Auth config after writing it and diff against the intended
   values** before moving on, so the written record reflects what's actually
   live, not just what was requested.

6. **Run the two required live probes against the hosted project**, mirroring
   `supabase/README.md`'s local curl pattern but pointed at
   `https://<ref>.supabase.co` with the hosted project's **publishable/anon**
   key (never the service-role key) as `apikey`:
   - Nine-character password signup → expect a 4xx citing the 10-character
     minimum (`weak_password` locally; confirm the hosted response shape
     matches).
   - A 10+ character signup, followed immediately by a sign-in attempt with
     the same credentials before confirming the email → expect the sign-in
     to be denied (`email_not_confirmed` locally; confirm hosted response).
   Use a throwaway address (e.g. `test+t153-2@example.com`-style, matching
   T153.1's convention) and be mindful the hosted project's default mailer
   has a low send-rate limit before T153.3 configures Resend — this task
   only needs the *one* successful signup call, so this isn't a real
   constraint, but don't loop retries against `/signup` if something fails;
   diagnose instead of hammering the rate limit.
   Do not attempt to verify actual email delivery/template content here —
   that's explicitly T153.3's job (Resend + template mirroring), and the
   default Supabase sender's copy is not the repository-owned template yet.

7. **Write the dated, secret-free configuration record.**
   New file: `supabase/HOSTED_DEV_CONFIG.md`, colocated with the existing
   local `supabase/README.md` so both docs for the two environments live
   together. Contents, modeled on T153.1's TASKS_DONE closing-note style and
   `supabase/README.md`'s "Local Auth policy" section:
   - A date and a one-line statement of which hosted project this documents
     (name/ref is fine to include — it is not a secret — but no anon key,
     no DB password, no PAT).
   - Each of the four policy values as configured and re-confirmed via the
     `GET` in step 5 (email confirmation required, 10-char minimum, 3600s
     JWT, the exact two-URL redirect allowlist verbatim).
   - The exact live-probe results observed in step 6 (status codes / error
     codes seen), analogous to how T153.1's TASKS_DONE note quotes the real
     422/400 responses it saw.
   - An explicit non-goals line: no custom SMTP/DNS (T153.3), no
     secure-email-change policy (T154.1), no production project created.
   - A short "where the real values live" pointer: anon/publishable key and
     project URL go in each developer's own gitignored `.env.local` per
     `.env.example`'s existing comment, not in this file or any tracked file.

8. **Move the task to Done.**
   Update `TASKS.md`/`TASKS_DONE.md` per the project's existing convention
   (status flip, closing note summarizing what was confirmed live, in the
   same commit as `supabase/HOSTED_DEV_CONFIG.md`). No `.env.example` change
   is needed since it already anticipates these variable names.

9. **Verify.**
   No application source changes occur in this task, so
   `node .claude/scripts/verify.mjs --skip-export` is sufficient (skip the
   web export since nothing web-facing changed) — run it anyway as a sanity
   check that nothing else on the branch regressed before committing.

## Ordering rationale

Project creation must precede any Auth-config write (step 3 before 4); the
config write must precede both re-verification and the live probes (4 → 5 →
6), since probing against unconfigured defaults would produce meaningless
results (e.g. a fresh project's default password minimum is shorter, so a
9-character signup might already fail for the wrong reason). The record
(step 7) is written last so it reflects the *observed* re-`GET` and probe
results, not the requested values — matching this task's own exit-criteria
wording ("live probes reject...").

## Risks / non-obvious traps for the implementer

- Do not reuse the reserved-production naming or accidentally set
  `site_url` to a local value on the hosted project (that field affects
  hosted email templates' base URL, unlike the local project which
  legitimately points at `localhost:8081`).
- Supabase Management API field names for Auth config are not guaranteed
  stable across CLI/API versions; `GET` the live schema before writing
  rather than trusting field names recalled from documentation or this
  plan.
- If the org already has a project that looks like a candidate "hosted dev
  project" from earlier manual exploration, confirm with the user before
  reconfiguring or replacing it — don't silently adopt an unknown project.
- Keep the DB password, PAT, and anon/publishable key out of every tracked
  file, including this record and any commit message; only the project
  name/ref is safe to write down.
