# T156.3 — Prove cross-account local-data isolation

## Context established by exploration

- T156.1 (`identity.ts`, `identity-context.ts`, `scoped-storage.ts`, `identity-from-auth-state.ts`) and
  T156.2 (`use-identity-scoped-domain.ts`, `identity-provider.tsx`, all five providers converted) are both
  merged (`TASKS_DONE.md`). No further production code is required for this task — it is test-only.
- The shared mechanism (`useIdentityScopedDomain`) is identical across all five domain providers
  (`user-profile-provider.tsx`, `custom-trick-provider.tsx`, `practice-history-provider.tsx`,
  `goal-provider.tsx`, `note-provider.tsx`). T156.2's own test
  (`src/features/auth/state/__tests__/identity-rehydration.test.tsx`) deliberately proved the
  load-race and one write-leak case on only two representative domains (profile, custom tricks) and
  explicitly deferred "the full five-domain isolation matrix" to this task.
- "pending-metadata fixtures" in the task description does **not** refer to a sixth persisted domain —
  no such domain exists in the codebase, and none should be added here (that would be scope creep into
  T157's outbox). It refers to a write that is queued (pending) in a domain's `createWriteQueue` at the
  moment of an identity switch — i.e. the "late queued write" race named explicitly in the exit
  criteria. This plan treats it as a race scenario to simulate, not a fixture domain to seed.
- Provider nesting order (must match `src/app/app/_layout.tsx` and the existing test's `mount()`):
  `AuthProvider > IdentityProvider > CustomTrickProvider > UserProfileProvider > PracticeHistoryProvider
  > NoteProvider > GoalProvider`. `GoalProvider` depends on `UserProfileProvider`'s `addSelectedTrick`.
- Storage keys/serializers per domain (all under `src/features/*/persistence/*.ts`):
  - Profile: `USER_PROFILE_STORAGE_KEY` / `serializeUserProfile`
  - Custom tricks: `CUSTOM_TRICKS_STORAGE_KEY` / `serializeCustomTricks`, fixtures via `createCustomTrick`
  - Practice history: `PRACTICE_HISTORY_STORAGE_KEY` / `serializePracticeHistory` (build
    `PracticeSessionRecord` objects directly — no need to drive the Sesh reducer)
  - Goals: `GOALS_STORAGE_KEY` / `serializeGoals`, fixtures as plain `Goal` objects
  - Notes: `NOTES_STORAGE_KEY` / `serializeNotes`, fixtures as plain `Note` objects
  - All physical keys are namespaced via `physicalKey(identity, logicalKey)` from
    `src/shared/persistence/scoped-storage.ts`, exactly as `identity-rehydration.test.tsx` already does.
- Race-simulation technique already established and reusable: `jest.spyOn(AsyncStorage, 'getItem' |
  'setItem').mockImplementation(...)` gated behind a manually-resolved `Promise`, keyed off the
  specific physical key under test, falling back to `getMockImplementation()`'s original for
  everything else (see `identity-rehydration.test.tsx`'s delayed-load test for the exact pattern —
  reuse it verbatim for `getItem`, and adapt it for `setItem` for the late-write case).

## Plan

1. **New test file**: `src/features/auth/state/__tests__/identity-isolation-matrix.test.tsx`.
   Do not extend `identity-rehydration.test.tsx` — that file is scoped to T156.2's own exit criteria
   (two representative domains); this is a new, explicitly-five-domain matrix per T156.3's exit
   criteria. Keep both files; they're complementary, not duplicative.

2. **Shared test scaffolding** (mirror `identity-rehydration.test.tsx`'s structure closely so the two
   files stay easy to compare):
   - Same `jest.mock` calls for `@react-native-async-storage/async-storage`,
     `react-native-reanimated`, and `@/shared/supabase/supabase-client`.
   - Same `createFakeClient`/`sessionWithUserId` helpers (copy, don't import — these are tiny and
     test-local in the existing file).
   - `USER_A_IDENTITY` / `USER_B_IDENTITY` constants with fixed UUIDs (reuse the same UUIDs as
     `identity-rehydration.test.tsx` for readability, no need to be unique across files).

3. **Per-domain fixture table.** Define one small config object per domain with:
   - `seed(identity, tag)`: writes a fixture to `physicalKey(identity, KEY)` via
     `AsyncStorage.setItem` + the domain's `serialize*` function, deriving distinguishable content
     from `tag` (e.g. `tag = 'guest' | 'userA' | 'userB'`) so assertions can tell fixtures apart
     (rank numbers, trick names, goal/note bodies, session ids all include the tag string).
   - A way to read the *currently rendered* state for that domain from the harness component (see
     step 4) — expose it through the shared `captured` object, one field per domain, matching the
     `captured.kenteiRank` pattern already in `identity-rehydration.test.tsx`.
   - A way to read *stored* state directly from `AsyncStorage` for a given identity (for asserting
     writes never land in the wrong namespace) — `AsyncStorage.getItem(physicalKey(identity, KEY))`
     parsed with the domain's existing `deserialize*`.
   - A `writeUnderCurrentIdentity()` action that performs one real user-driven write through the
     provider's public action hook (not a raw dispatch), to prove "submit" isolation, not just
     "render" isolation:
     - profile: `toggleSelectedTrick('some-trick-id')` (already used in the existing test)
     - custom tricks: `addCustomTrick({ kind: 'standalone', name: <tag-derived name> })`
     - practice history: `recordCompletedSesh(summary)` — build a minimal `SeshSummary` fixture;
       check `src/features/sesh/model/sesh.ts` for the exact shape before writing this helper, since
       it wasn't pulled into this plan's exploration (this is the one domain whose write helper needs
       a fixture builder, not a passthrough call)
     - goals: `addGoal({ kind: 'count', trickId: 'some-trick-id', trickName: 'Some Trick',
       targetCount: 3 })`
     - notes: `addNote({ trickId: 'some-trick-id', trickName: 'Some Trick', body: <tag-derived text> })`

4. **Harness component**: one component rendered at the bottom of the provider tree that reads all
   five domains' hooks (`useUserProfile`/`useUserProfileActions`, `useCustomTricks`/
   `useCustomTrickActions`, `usePracticeHistory`/`usePracticeHistoryActions`, `useGoals`/
   `useGoalActions`, `useNotes`/`useNoteActions`) and mirrors relevant fields into the shared
   `captured` object inside a `useEffect`, exactly like the existing test's `Harness`. Also capture
   each domain's action callbacks so test bodies can invoke them via `captured.<domain>Actions`.

5. **Test 1 — full seed-and-switch matrix, no cross-identity rendering.**
   - Seed all five domains for guest, user A, and user B (distinct tags).
   - Emit `INITIAL_SESSION(null)` → assert all five `captured.*` fields match guest fixtures only.
   - Emit `SIGNED_IN(userA)` → assert all five match user A only (not guest, not user B — assert
     both positively and negatively, e.g. `toContain('userA')` and `not.toContain('guest')`).
   - Emit `SIGNED_IN(userB)` → assert all five match user B only.
   - Emit `SIGNED_IN(userA)` again (repeated switch, revisit) → assert all five restore exactly user
     A's original fixtures (not merged with anything touched under B, not reset to empty).
   - Emit `SIGNED_OUT(null)` → assert all five restore exactly guest's original fixtures.
   - This single test satisfies "no identity can render another identity's fixtures" and "returning to
     each identity restores exactly its own state" across all five domains at once.

6. **Test 2 — no cross-identity write ("submit") leakage, all five domains.**
   - Seed guest + user A fixtures (user B not needed here).
   - Switch to user A. For each of the five domains, call its `writeUnderCurrentIdentity()` action
     inside `act()`, flushing microtasks (reuse the `await Promise.resolve()` ×2–3 pattern from the
     existing test — the write queue and dispatch are async).
   - Assert each write landed at `physicalKey(USER_A_IDENTITY, KEY)` (read directly via
     `AsyncStorage.getItem` + `deserialize*`) and did **not** land at
     `physicalKey(GUEST_IDENTITY, KEY)`.
   - Switch to guest (`SIGNED_OUT`) → assert none of the five `captured.*` fields show user A's
     written content, and guest's own stored fixtures are byte-for-byte unchanged from what was
     seeded (parse and deep-equal, not just a substring check, to also catch accidental overwrites
     with an empty/default collection).
   - This directly satisfies "no identity can ... overwrite[] or submit ... another identity's
     fixtures."

7. **Test 3 — late hydration result discarded after switching (representative domains).**
   - Port the existing delayed-`getItem` gate technique from `identity-rehydration.test.tsx` verbatim
     (it is already domain-agnostic — gates on a specific physical key).
   - Run it for **two** domains, not all five: user profile (already covered in T156.2's test, so
     re-run here for completeness inside the consolidated matrix) plus one domain T156.2 did not
     cover for this race — pick **notes** (arbitrary but exercises a different provider than
     profile/custom-tricks, which the existing file already covers). Gate `AsyncStorage.getItem` for
     `physicalKey(USER_A_IDENTITY, NOTES_STORAGE_KEY)`, sign in as user A (load stuck), sign in as
     user B before releasing the gate (user B's load must proceed and hydrate normally), then release
     the gate and assert: `captured.notes` still shows user B's fixture, not user A's, and no
     hydration-fallback text ("Loading your tricks...", matching `NoteProvider`'s and `GoalProvider`'s
     actual fallback copy — confirm exact string in `note-provider.tsx` before asserting) is present.
   - Running this race for every one of the five domains would be redundant coverage of an already
     domain-agnostic mechanism (`useIdentityScopedDomain`'s generation guard is identical code for
     all five) — two domains is enough to prove the wiring, consistent with T156.2's own precedent of
     "two representative domains ... share the exact same call shape."

8. **Test 4 — late queued write discarded after switching (the "pending-metadata" scenario, one
   representative domain).**
   - This is new relative to T156.2's test (which only proved the late-*load* race, not a late-
     *write* race) and is the part of the exit criteria most directly named "a late queued write ...
     discarded after switching."
   - Pick **goals** as the representative domain (arbitrary; any domain works since
     `useIdentityScopedDomain`'s write-queue guard is shared code — see
     `use-identity-scoped-domain.ts` lines ~103-131, which double-checks `taggedGeneration` both
     before calling `save` and again synchronously inside `guardedStorage.setItem`).
   - Gate `AsyncStorage.setItem` (not `getItem` this time) for
     `physicalKey(USER_A_IDENTITY, GOALS_STORAGE_KEY)` behind a manually-resolved promise, using the
     same `getMockImplementation()` capture-before-replace technique the existing file uses for
     `getItem` (to avoid the self-recursion trap already documented in that file's comment).
   - Sequence: seed guest + user A + user B fixtures for goals. Sign in as user A. Call
     `addGoal(...)` under user A — this triggers the write-queue's `save`, which will call
     `guardedStorage.setItem`, which is now gated and stuck (not yet resolved).
   - While that write is stuck, switch to user B (`SIGNED_IN(userB)`), flush microtasks. Assert
     `captured.goals` now shows user B's fixtures (the switch itself proceeds independently of the
     stuck write, since hydration and the write queue are separate effects).
   - Release the gate. Flush microtasks. Assert:
     - `physicalKey(USER_A_IDENTITY, GOALS_STORAGE_KEY)` in `AsyncStorage` was **never actually
       written** with the new goal (still equals the original seeded user-A fixture) — this proves
       the synchronous `guardedStorage.setItem` generation check, not just that the dispatch was
       discarded.
     - `captured.goals` still shows user B's fixtures, unaffected.
   - Note the asymmetry vs. the load-race: the write is tagged with the generation *at dispatch
     time* (`taggedGeneration = context.getGeneration()`, captured synchronously when the state
     change enqueues the write effect), so the write is captured before the gate stalls it. This is
     worth a one-line comment in the test so a future reader doesn't think the test is racing the
     wrong thing.

9. **Assertion-completeness pass**: after writing tests 1–4, cross-check each exit-criterion clause
   against a specific assertion:
   - "no identity can render another identity's fixtures" → Test 1
   - "no identity can ... overwrite ... another identity's fixtures" → Test 2 (guest fixture
     byte-for-byte unchanged) + Test 4 (user A's stored goal literally never mutated)
   - "no identity can ... submit ... another identity's fixtures" → Test 2 (write action lands only
     under the acting identity's own namespace)
   - "a late queued write ... discarded after switching" → Test 4
   - "a late hydration result ... discarded after switching" → Test 3
   - "returning to each identity restores exactly its own state" → Test 1's repeated-switch step
     (A → B → A) plus final `SIGNED_OUT` back to guest

10. **`afterEach` cleanup**: same as the existing file — `jest.restoreAllMocks()`,
    `mockGetSupabaseClient.mockReset()`, `await AsyncStorage.clear()`, and reset every field on the
    shared `captured` object (all ten-ish fields across five domains, not just the four the existing
    file resets).

11. **Verify**: `node .claude/scripts/verify.mjs` (full sequence, not `--skip-export` — this is a real
    test-suite change but touches no styling/export-relevant code, so `--skip-export` would still be

## Risks / non-obvious things for the implementer

- **`SeshSummary` shape is unverified in this plan.** Read `src/features/sesh/model/sesh.ts` before
  writing the practice-history write helper in step 3 — don't guess the fields of `PracticeTrick` or
  `SeshSummary.plan`. Building `PracticeSessionRecord` fixtures directly for *seeding* (step 3's
  `seed`) is safe since that shape was read directly from `practice-history-persistence.ts` above; only
  the `writeUnderCurrentIdentity` action for practice history needs the unverified `SeshSummary` shape.
- **Microtask flushing is easy to get subtly wrong.** Follow the existing file's exact pattern of
  `await act(async () => { emit(...); await Promise.resolve(); await Promise.resolve(); await
  Promise.resolve(); })` rather than inventing a different flush count — the three domains chained
  through `useIdentityScopedDomain`'s effect → dispatch → write-queue pipeline need multiple
  microtask turns, and under-flushing produces flaky, not deterministic, failures.
  `jest.useFakeTimers()` is not used anywhere in this mechanism (it's all promise-based, not
  timer-based), so don't introduce fake timers here — they'd fight with `createWriteQueue`'s plain
  promise chaining for no benefit.
- **`getMockImplementation()` capture-before-replace is required**, not optional style, for gating
  `AsyncStorage.getItem`/`setItem` — the mock module's `getItem`/`setItem` are already `jest.fn()`s,
  and `jest.spyOn` on an already-a-mock reuses the same object, so grabbing a "reference" before
  `mockImplementation` just aliases the about-to-be-replaced dispatcher. See the exact comment in
  `identity-rehydration.test.tsx` (lines ~232-239) and mirror it for the `setItem` gate in Test 4.
- **Don't add a sixth "pending-metadata" persisted domain.** Re-read this plan's Context section if
  tempted — that would be unrequested new production surface area and would collide with T157.1's
  outbox design, which the task's own Notes explicitly reserve for later ("Outbox-specific assertions
  are extended when T157.1 lands").
- **Keep this to one new test file.** The task says "one automated matrix," and splitting the four
  tests above across multiple files would fragment the very thing the exit criteria asks to prove in
  one place. Four `it()` blocks in one `describe()` is the right granularity — not one giant test, not
  five-per-domain duplication.
