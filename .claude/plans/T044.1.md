- Deps: expo ~57.0.23, react-native 0.86.3, react-native-safe-area-context ~5.7. No keyboard library is needed; do not add one.

## Design decision
Use the ScrollView-native approach, not KeyboardAvoidingView:
`automaticallyAdjustKeyboardInsets` (iOS only) makes UIKit grow the scroll view's bottom content inset by the actual overlap between the keyboard frame and the scroll view's frame. That absorbs the in-flow tab bar and safe-area bottom automatically (no offsets, no per-device numbers) and RN scrolls the focused input into view. KeyboardAvoidingView needs a `keyboardVerticalOffset` equal to header/tab geometry, which is exactly the fixed offset the ticket forbids.
Fallback if the simulator shows the prop is insufficient (for example the focused input in a nested/inner ScrollView is not scrolled into view): wrap with `KeyboardAvoidingView behavior="padding"` with the offset derived from measured layout (`onLayout` page Y of the wrapper), never a constant. Only fall back with simulator evidence; record which was used.

## Steps
1. New primitive `src/components/ui/keyboard-aware-scroll.tsx` (name may be `FormScrollView`), a thin wrapper over `ScrollView`:
   - Props: pass-through `ScrollViewProps` (so screens keep their own headers, `contentContainerStyle`, and action layout; it is NOT a visual shell and renders no header/footer slots).
   - Defaults, overridable by the caller: `keyboardShouldPersistTaps="handled"`, `automaticallyAdjustKeyboardInsets`, `keyboardDismissMode={Platform.OS === 'ios' ? 'interactive' : 'on-drag'}`, `contentInsetAdjustmentBehavior` left unset, `style` base `{ flex: 1, width: '100%' }` merged with caller style.
   - Web: native-only props are no-ops on react-native-web; set them through a `Platform.select`/`Platform.OS !== 'web'` guard so the web render props (and thus layout) are identical to today. Check `keyboardDismissMode` is harmless on web; otherwise gate it too.
   - Keep to ~30 lines; export a short doc comment explaining why `automaticallyAdjustKeyboardInsets` is used instead of fixed offsets (present-tense reason).
   - Styled-components: callers can `styled(KeyboardAwareScroll)` if they need extra styles; the wrapper must forward `style`.

## Risks and notes
- `automaticallyAdjustKeyboardInsets` is not applied on web or Android; Android is out of scope here and must be recorded as not run, not passed.
- The form is rendered inside a tab-hosted screen, not a modal; confirm the screen's own content is not wrapped by an outer ScrollView or KeyboardAvoidingView in the tricks route before assuming the inset applies (read the tricks route above `CustomTrickForm` in step 3).
- `automaticallyAdjustKeyboardInsets` combined with `Screen`'s bottom safe-area edge: if a double bottom gap appears when the keyboard opens, it is a sign the inset math already includes safe area; fix by observing, not by subtracting constants.
- Do not add react-native-keyboard-controller or any dependency. If simulator evidence shows neither the ScrollView prop nor the measured KeyboardAvoidingView fallback can satisfy the criteria, stop and report a blocker for owner approval of a dependency.
- Design for T044.2: the primitive is a drop-in for the `ScrollView` those screens already use, with identical default props, so adoption is a one-line swap per screen (note/goal screens use `Scroll` with the same props; the Profile streak and access gate are not yet inspected).
