# T313.3 plan: sign-up and sign-in screens on native

## Findings from the current code (verified on the branch)

- The four screens (`sign-in-screen.tsx`, `sign-up-screen.tsx`, `forgot-password-screen.tsx`, `check-email-screen.tsx`, all in `src/features/auth/components/`) already use `Screen` (SafeAreaView, all edges; bottom/left/right/top edges are honored natively, the 88px web header inset is web-only) and a plain `ScrollView` with `keyboardShouldPersistTaps="handled"`. There is no keyboard avoidance anywhere in the repo (`grep KeyboardAvoidingView` is empty; no keyboard-controller dependency).
- `textContentType` is already set: sign-in email `username`, sign-in password `password`, sign-up password and confirm `newPassword`, forgot-password email `username`. `PasswordInput` defaults to `password`. No screen sets `autoComplete`. `PasswordInput` does NOT forward `autoComplete`, and does not forward `blurOnSubmit`-independent extras, so it must be extended (it is a closed prop interface, not `...rest`).
- Focus order: sign-in and sign-up already chain email -> password -> (confirm) via refs and `onSubmitEditing`. Forgot-password has one field and no `returnKeyType`/`onSubmitEditing`, so the return key does nothing on native. Sign-up `blurOnSubmit={false}` is on the first password input only; email has it.
- The web keydown handlers are already `Platform.OS === 'web'` guarded (sign-in, sign-up). Forgot-password has none. Do not change them.
- Autocorrect: leave `autoCorrect={false}` and everything else about it untouched (T311 owns it).

## Blocker analysis: T313.2 not merged

`auth-provider.tsx` `signUp` (line ~296), `requestPasswordReset` (~268), `resendSignupConfirmation` (~313) all return `new AuthError('Unable to resolve the callback URL.')` when `typeof window === 'undefined'`. On Hermes/iOS `window` is defined as the global object (RN defines `global.window = global`), so the guard passes, but `window.location` is undefined and `window.location.origin` throws a TypeError, i.e. native sign-up rejects/throws before it ever calls Supabase. Architecture doc line 189 confirms: "native sign-up, resend, password-reset ... still return an error because they derive `redirectTo` from `window`".

Consequence: the exit criterion "sign-up reaches check-email" CANNOT pass on this branch alone against local Supabase. Sign-in (no redirect) is unaffected and can be fully verified. Do NOT reimplement T313.2's callback URL logic here (conflict risk, owner gate pending). Options for the implementer, in order of preference:
1. Verify sign-in, keyboard, and form behavior on this branch; verify sign-up reaching check-email only after T313.2 merges and this branch is rebased onto development (ticket stays open for that one criterion), or by temporarily stacking locally on the T313.2 branch (`origin/task/T313.2-complete-email-links-in-the-app`) for the manual check only, never committed.
2. Record in the PR: "sign-up -> check-email: not run / blocked on T313.2" rather than passing it. Per AGENTS.md, unperformed checks are recorded as not run.
The screen-level sign-up behavior (error banner shown, keyboard, focus) can still be exercised on native, and the failure surface must be checked: confirm the thrown TypeError does not leave the button stuck in "Creating account..." (see step 5); if it does on this branch, that is a pre-existing robustness defect worth a `try/finally` in the screen since AGENTS.md requires total control flow in submit handlers.
