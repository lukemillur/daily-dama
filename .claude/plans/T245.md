# T245 — Hide the trick list's scrollbar

Branch: `task/T245-hide-the-trick-list-s-scrollbar`
Area: Tricks · Priority: Low

## 0. Read this before you start: the ticket's stated cause is wrong

The ticket description says:

> on web `showsVerticalScrollIndicator` alone doesn't suppress the browser's native
> scrollbar (that needs a CSS-level hide on the underlying scroll container)

**That is not true for the version of `react-native-web` this repo pins.** I verified it in
the installed dependency, not by reasoning from general RN-Web folklore:

- `react-native-web@0.21.2` (`package.json` pins `~0.21.0`).
- `react-native-web/dist/exports/ScrollView/ScrollViewBase.js:121`
  ```js
  var hideScrollbar = showsHorizontalScrollIndicator === false || showsVerticalScrollIndicator === false;
  ...
  style: [style, !scrollEnabled && styles.scrollDisabled, hideScrollbar && styles.hideScrollbar]
  ...
  hideScrollbar: { scrollbarWidth: 'none' }
  ```
- `react-native-web/dist/exports/StyleSheet/compiler/index.js:381` special-cases
  `scrollbarWidth` and emits **both** rules:
  ```
  .r-scrollbarWidth-2eszeu::-webkit-scrollbar{display:none}
  .r-scrollbarWidth-2eszeu{scrollbar-width:none;}
  ```
  I confirmed this output by running RNW's own `preprocess` + `atomic` compiler directly on
  `{ scrollbarWidth: 'none' }`.
- The prop reaches that code: `SectionList` → `VirtualizedSectionList` → `VirtualizedList`
  (`dist/vendor/react-native/VirtualizedList/index.js:1116`, `scrollProps = {...this.props, ...}`)
  → RNW `ScrollView.render()` (spreads `other` into `ScrollViewBase`) → the scrolling `div`.

So `showsVerticalScrollIndicator={false}` *does* apply a CSS-level hide on the underlying
scroll container on web today. **No `+html.tsx` CSS, no style injection, and no wrapper
component is needed as the primary fix.** Do not add one speculatively.

### What the actual defect is

`hideScrollIndicator` defaults to `false`, and one of the four listed call sites never
passes it:

| Call site | File | Passes `hideScrollIndicator`? |
|---|---|---|
| Tricks route | `src/app/app/tricks/index.tsx:72` | yes |
| Multi-trick sesh entry | `src/features/sesh/components/multi-trick-sesh-entry.tsx:156` | yes |
| Onboarding selection | `src/features/onboarding/components/onboarding-selection-step.tsx:31` | yes |
| **Trick goals — "Add goal" trick picker** | `src/features/goals/components/all-trick-goals-screen.tsx:138-148` | **no** |

That last one (`GoalTrickPicker`, reached from `/app/tricks/goals` → **Add goal**) is the
screen that genuinely renders a scrollbar today. It matches the exit criterion's phrase
"when defining a new trick goal".

The fix is therefore to make hiding unconditional in the shared component, which is exactly
what the Notes predicted ("one change should cover all of them") — just for a different
reason than the description gives.

**Do not treat this section as permission to skip in-browser verification.** The exit
criterion is browser-confirmed absence on all four surfaces. If a scrollbar still shows up
on one of the three that already pass the prop, the cause is something *other* than
`showsVerticalScrollIndicator`, and §5 tells you how to find it before changing code.

## 1. `src/features/tricks/components/trick-directory.tsx` — remove the prop, hide always

No current call site wants the scrollbar visible, so delete the escape hatch rather than
flipping its default. Three edits:

1. **Line 46** — delete the prop from `TrickDirectoryProps`:
   ```ts
   readonly hideScrollIndicator?: boolean;   // delete this line
   ```
2. **Line 86** — delete `hideScrollIndicator = false,` from the destructured parameter list.
3. **Line 141** — replace
   ```tsx
   showsVerticalScrollIndicator={!hideScrollIndicator}
   ```
   with
   ```tsx
   // Always hidden. On web react-native-web turns `showsVerticalScrollIndicator={false}`
   // into a real CSS hide on the scrolling element (`scrollbar-width: none` plus
   // `::-webkit-scrollbar { display: none }`), so no extra web-only CSS is needed here.
   // The list still scrolls by wheel, trackpad, touch drag, and keyboard.
   showsVerticalScrollIndicator={false}
   ```

Keep the literal `false` — RNW's check is a strict `=== false`, so passing `undefined`
would silently re-show the scrollbar.

Nothing else in this file changes. Leave `fixedHeader` / `fixedFooter` / `ListContainer`
(`overflow: hidden`) alone.

## 6. Contingency — only if a scrollbar is still visible somewhere after §5

Diagnose before you touch anything. In DevTools, right-click the visible scrollbar's
container → Inspect, and identify which element actually has `overflow-y: auto|scroll` and a
scrolling `scrollHeight > clientHeight`. Then:

**Case A — the scroller is the `SectionList`'s own `div` and it still shows a bar.**
Something is overriding RNW's atomic rule. Add an explicit, narrowly-scoped CSS hide:

1. In `trick-directory.tsx`, give the `SectionList` a DOM id:
   ```tsx
   id="trick-directory-scroll"
   ```
   `id` is on RN's `ViewProps` (`react-native/types_generated/.../ViewPropTypes.d.ts:383`) so
   this typechecks, and RNW forwards it to the scrolling element. Do **not** use `dataSet` —
   RNW supports it at runtime but it is not in RN's TypeScript `ViewProps`, so `yarn tsc`
   would fail. Note the id is only safe because exactly one `TrickDirectory` is mounted at a
   time today; add a comment saying so.
2. Extend the **existing single-line** `<style>` string in `src/app/+html.tsx` (line 14):
   ```tsx
   <style dangerouslySetInnerHTML={{ __html: 'html,body{background:#f4c94d}#trick-directory-scroll{scrollbar-width:none}#trick-directory-scroll::-webkit-scrollbar{display:none}' }} />
   ```

   ⚠️ **`security/dangerous-html-audit.test.ts` will bite you here.** That guard asserts
   there is exactly one raw-HTML sink in `src/`, that it is on one line, that the line still
   contains the literal `html,body{background:#f4c94d}`, and that it contains no `${`
   interpolation. So: keep it one string literal on one line, keep that background substring
   verbatim, and do **not** add a second `<style dangerouslySetInnerHTML>` element. Then run:
   ```sh
   yarn jest security/dangerous-html-audit.test.ts
   ```
   CSP is fine — `vercel.json` already allows `style-src 'self' 'unsafe-inline'`.
3. Because `+html.tsx` affects the exported document shell, add a web export to your
   verification: `node .claude/scripts/verify.mjs --only export` (or the full
   `yarn expo export --platform web --output-dir /tmp/daily-dama-web-export`).

**Case B — the scroller is some *other* element** (e.g. `Scroll` in
`all-trick-goals-screen.tsx:153`, `DirectoryContent` in `tricks/index.tsx:513`,
`TrickDirectoryColumn`, or `SelectionContent`). Then it is not the trick list's scrollbar and
it is out of this ticket's scope as written. Record what you found, fix only if it is
unambiguously "the trick list's scrollbar" to a user, and otherwise note it as a follow-up
rather than expanding scope.

**Do not** apply a blanket "hide scrollbars everywhere" rule in `+html.tsx`. Stats, notes,
the goals list, and the custom-trick forms all scroll too, and silently removing their
affordance is a product change nobody asked for.

## Risks / notes

- **Accessibility tradeoff (call it out, don't silently absorb it):** hiding the scrollbar
  removes a visible affordance that the list is scrollable and removes scrollbar-drag as an
  input method. Keyboard scrolling (arrow keys / Page Up-Down once the list has focus), wheel,
  and touch drag all still work. This is what the ticket asks for; just be aware the "drag"
  in the exit criterion means trackpad/touch drag, not dragging the (now absent) thumb.
- **Native platforms:** `showsVerticalScrollIndicator={false}` also hides the indicator on
  iOS/Android. That is consistent intent, costs nothing, and per `AGENTS.md` §Active platform
  scope you should **not** validate on a simulator or emulator. Record native validation as
  deferred.
- **Scope guard:** the only files that should change in the happy path are
  `trick-directory.tsx`, its test, and the three call sites. Four small diffs. If the diff is
  growing beyond that without a DevTools finding from §6 justifying it, stop.
