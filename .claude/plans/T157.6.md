# T157.6 — Synchronize immutable practice history

## Scope boundary (read first)

This is domain rollout 3 in the T157 chain, directly following the pattern
`T157.5` (`git show 530d431:.claude/plans/T157.5.md`) established for
custom tricks, which itself followed `T157.4` (`git show
37d7c3d:.claude/plans/T157.4.md`) for profile. Read T157.5's plan in full —
this plan only calls out deltas, not a restatement of the whole pattern.

**In scope:** real pull+push synchronization for the `practiceHistory`
`SyncDomain` (`api.practice_sessions`, one table, insert-only), wired into
`PracticeHistoryProvider` additively, with a real Supabase adapter, a
durable per-domain outbox/envelope, idempotent inserts (23505-as-success,
matching T155.9's own pattern), and a corrected DB CHECK constraint that
currently blocks a real, already-shipped local feature (paused sessions)
from ever syncing at all — see "Blocker: fix the duration CHECK constraint"
below, which is load-bearing for this task's own exit criteria and must be
done first.

**Explicitly out of scope, same reasons as T157.4/T157.5:**
- Dispatching into the shared `syncCoordinatorReducer` (T157.9's job).
  Build a domain-local driver whose `runSync` return value is already
  `DomainSyncRecord`-shaped.
- Debounced/coalesced login/foreground/reconnect/manual triggers (T157.9).
  Reuse the "one auto-run per identity generation after hydration, for
  signed-in users" trigger plus a manually callable `runSync`.
- Any conflict UI or last-write-wins resolution (T160.x). This domain has no
  revision-guarded updates at all (see below), so there is structurally no
  push-side conflict to resolve — don't invent one.
- Modifying `practice-history-cloud-repository.ts`'s existing contract
  (T155.9) or `practice-history-cloud-mapping.ts`'s existing row↔domain
  mappers (T155.12) — only *add* a new diff function to the mapping file,
  exactly as T155.12's own header comment anticipates ("that's T157.6").
- Any UPDATE/DELETE support for this domain, client- or server-side. It is
  immutable by design (T155.3 schema, T155.5/T155.7 grants). Do not add a
  revision column, a tombstone, or any conditional-update machinery — none
  of it applies here.

## Blocker: fix the duration CHECK constraint (do this first)

`practice-history-cloud-mapping.ts`'s header comment (T155.12) already flags
this exactly: `supabase/migrations/20260822200050_add_custom_tricks_and_practice_sessions.sql`
line ~206 has

```sql
constraint practice_sessions_duration_matches_timing
  check (duration_ms = completed_at - started_at),
```

I confirmed this is **still unfixed** (grepped every later migration; none
touch this constraint). It is also **still wrong**: `src/features/sesh/model/sesh.ts`
supports pausing an active session (`seshPaused`/`seshResumed` actions,
`pausedDurationMs` tracked in state), and `completeSesh`/the early-end path
computes `durationMs: endedAt - state.startedAt - totalPausedMs` — which is
strictly less than `completedAt - startedAt` for any session with real
paused time. `practice-history-persistence.ts`'s own local validator already
encodes the correct, permissive invariant (`durationMs <= completedAt -
startedAt`), and `practice-history-cloud-mapping.ts`'s row→domain validator
already uses that permissive invariant on the read side. Only the DB's own
CHECK constraint is still the stricter, wrong one — so **any push of a
genuinely valid paused session will be rejected by Postgres with `23514`**,
parking that record in the outbox forever (never auto-retried into success,
since the payload is correct and will fail identically every time).

This blocks the exit criteria directly: a full offline→reload→retry
integration test that happens to record a paused session cannot pass until
this is fixed, and it would be dishonest to write the test only against
never-paused sessions to dodge it.

**Fix, in place, in the existing T155.3 migration file** (not a new
corrective migration): change the constraint to

```sql
constraint practice_sessions_duration_matches_timing
  check (duration_ms <= completed_at - started_at),
```

This is safe to edit in place rather than append a new migration:
`BACKEND_ROADMAP.md` states plainly, "Because there are no cloud users,
schema corrections during these first phases can replace provisional
migrations before production rather than carrying compatibility migrations
for nonexistent accounts" — confirmed there is no live production Supabase
project yet (only the Vercel frontend has a `production` branch;
`DEPLOYMENT_HANDOFF.md` and `BACKEND_ROADMAP.md`'s own roadmap step 6,
"create the reserved production Supabase project," hasn't happened). Local

## Why this domain is simpler than custom-tricks/profile

`api.practice_sessions` has **no revision column and no UPDATE/DELETE grant
at all** (confirmed: `practice_sessions` `Row`/`Insert`/`Update` types in
`database-types.ts` have no `revision` field; the T155.5 migration's column-
grant section states outright "this table has no UPDATE grant at all... so
there is no update column list to narrow"). Consequences that simplify this
task relative to T157.4/T157.5's template — **do not port over machinery
that doesn't apply here**:

- No `expectedRevision`/revision-cache concept anywhere in this domain's
  envelope, diff, or driver. Every push is `expectedRevision: null`
  unconditionally.
- No `'conflict'` push outcome is ever structurally possible for this
  domain (nothing to conflict against — there's no second write to the same
  row, ever). The transport's `push` still returns the shared
  `SyncTransportPushResult<Row>` type (so it satisfies
  `SyncTransportRepository<PracticeSessionRow>`), but its implementation
  never produces a `'conflict'` branch.
- No `operationType: 'delete'` is ever emitted by this domain's diff
  function — there is no local delete/edit action for practice history at
  all (`practiceHistoryReducer` only has `historyRestored` and
  `sessionRecorded`, and `sessionRecorded` already dedupes by `id`). The
  transport's `push` should still handle a `'delete'` request defensively
  (return a `'failed'`/`validation` result without ever calling the
  network) since the shared `push(request: SyncPushRequest)` signature
  can't statically rule it out — but this is a defensive guard, not a real
  code path, and needs no elaborate handling.
- **Pull-adopt should always merge, not gate on `outboxIsEmpty`.** This is
  the one genuine design deviation from the T157.4/T157.5 template — call
  it out explicitly to whoever implements this, since "authoritative
  locally when outbox is non-empty" was custom-tricks/profile's caution
  against a stale pulled *edit* clobbering a pending local edit. That
  scenario cannot happen here: practice-session records are immutable and
  content-addressed by their own id
  (`createPracticeSessionRecordId = "${startedAt}:${endedAt}:${trickId}"`),
  so a duplicate id occurring in both local state and a pulled row is
  guaranteed to be the *same* record, never a competing edit. This means
  every sync run can unconditionally union pulled rows into local state by
  id, regardless of outbox contents — which is also exactly what's needed
  for "reload and retry after a lost acknowledgement": if a push actually
  landed server-side but the ack was lost, the very next pull will already
  contain that record, and the union-merge silently absorbs it (no special-
  casing needed against the still-pending outbox operation; the outbox
  entry gets a normal chance to retry-and-idempotently-succeed on its own
  push turn, treated as a no-op 23505).

## The pure diff: `PracticeHistory` change → outbox operations

New export in `practice-history-cloud-mapping.ts` (the T155.12 file whose
header comment already anticipates this):

```ts
export function diffPracticeHistoryForOutboxOperations(
  previous: PracticeHistory,
  next: PracticeHistory,
  userId: string,
): readonly NewOutboxOperationInput[]
```

- Build a `Set<id>` for `previous.sessions`. Any session in `next.sessions`
  whose `id` is **not** in that set emits `{ domain: 'practiceHistory',
  operationType: 'upsert', recordId: id, payload:
  mapPracticeSessionRecordToInsertInput(session, userId) as unknown as
  Record<string, unknown> }` (reuse the existing T155.12 mapper verbatim).
- No delete branch — a session id present in `previous` but absent from
  `next` should never occur (nothing in this domain removes sessions); if a
  future bug somehow produced one, silently drop it rather than fabricate a
  delete operation type that push must always reject anyway.
- No content-equality check needed for ids present in both (immutable
  records never change) — unlike `diffCustomTricksForOutboxOperations`,
  don't add a `JSON.stringify` comparison; it would be dead code for this
  domain.
- Stable order: ascending id, same rationale as custom-tricks (each op
  targets a distinct `recordId`; order has no semantic meaning beyond
  determinism).
- Add unit tests in `practice-history-cloud-mapping.test.ts`: no-op diff
  (identical `sessions`); one new session added (assert op shape/payload);
  several sessions added in one diff (assert stable ascending-id order);
  a session present in both with byte-identical content produces no
  operation (regression guard against accidentally reintroducing a
  content-diff).

## The adapter: `SyncTransportRepository<PracticeSessionRow>`

New file `src/features/stats/persistence/practice-history-sync-transport.ts`.
`createPracticeHistorySyncTransportAdapter(client: SupabaseClient<Database,
'api'>, userId: string): SyncTransportRepository<PracticeSessionRow>`.

**Pull**: delegates directly to
`createPracticeHistoryCloudRepository(client).list(request)` — already
structurally identical to `SyncTransportPullResult<PracticeSessionRow>`,
same one-line-wrapper pattern as the custom-tricks/profile adapters. Feed
into `pullAllPages` unchanged (reuses T157.3's function and T155.8's proven
`(completed_at desc, id asc)` tiebreak order — pull-adopt itself doesn't
care about row order since it merges by id, but keep the delegation as-is
rather than re-deriving pagination).

**Push**: defensively re-validate `request.payload` first (round-tripped
through AsyncStorage JSON — treat as `unknown`), reusing
`isFiniteNonNegativeNumber` from `practice-history-persistence.ts` plus
inline checks matching `PracticeSessionInsert`'s shape (`user_id`/`id`
matching the request, `trick_id`/`trick_name` non-empty, `started_at`/
`completed_at`/`duration_ms`/`lace_count` well-typed, `duration_ms <=
completed_at - started_at` — the same permissive invariant now also true in
the DB after the fix above). Return `{status:'failed', error:{kind:
'validation', ...}}` on a malformed payload, without ever calling the
network.

- `request.operationType === 'delete'`: **never emitted by this domain's
  diff, but must be handled defensively** — return `{status:'failed',
  error:{kind:'validation', message:'practice-history records are
  immutable; delete is not supported.'}}` immediately, no network call.
  This is the client-side half of "reject attempted remote mutation."
- `request.operationType === 'upsert'`: `client.from('practice_sessions').insert(input).select('*').single()`.
  - Success → `{status:'succeeded', row: inserted.data}`.
  - `error.code === '23505'` (duplicate `(user_id, id)` — a lost-ack retry
    of an insert that actually landed): **do not attempt any update** (there
    is no update grant to fall back to, unlike custom-tricks/profile's
    23505 handling). Instead, re-fetch the existing row by `(user_id, id)`
    and return it as `{status:'succeeded', row: existing}` — this *is*
    T155.9's "insert-then-handle-23505-as-success" pattern, adapted for a
    table with no update path at all.
  - Any other error → `mapPostgrestError(error)`, `{status:'failed', ...}`
    (e.g. a genuine `23514` from a still-malformed payload, or `42501` if
    grants were ever misconfigured — surfaced plainly, parked in the
    outbox, never silently retried into success).
- `expectedRevision` is accepted (part of the shared `SyncPushRequest`
  shape) but **always ignored** — this domain never guards on it. Don't
  build any branching on `request.expectedRevision` in `push`.

**Real-stack tests**, new file
`supabase/tests/data-api/t157_6_practice_history_sync_transport.test.mjs`,
built identically to `t157_5_custom_trick_sync_transport.test.mjs`. Cover:
1. Idempotent retry of the same session upsert (simulated lost ack): second
   call succeeds, returns the same row content, no duplicate row (`list`
   afterward shows exactly one row for that id).
2. A push with `operationType: 'delete'` returns `'failed'`/`validation`
   without ever reaching the network (assert no row exists for that id
   before/after — nothing to accidentally create either).
3. **Reject attempted remote mutation, proving the grants hold through this
   exact sync path**: insert a row through `transport.push` (the real
   adapter, the same authenticated `client`/`userId` it was constructed
   with), then attempt a raw `client.from('practice_sessions').update(...)`
   and a raw `client.from('practice_sessions').delete(...)` against that
   same row using that same client — assert both fail with Postgrest error
   code `42501` and the row's original content is unchanged afterward. This
   is deliberately a *second*, sync-path-specific proof beyond T155.7's own
   raw-Data-API grant tests (which the task notes explicitly call out as
   already covering the DB boundary in isolation) — it confirms the sync
   adapter's own client instance and code path never accidentally routes
   around those grants.
4. A paused-session payload (`duration_ms < completed_at - started_at`)
   pushes successfully — the concrete, executable proof that the migration
   fix above actually unblocks this task's own exit criteria, not just the
   pgTAP suite.
5. **Synchronize more than 1,000 records**: reuse `t155_8_pagination.test.mjs`'s
   `buildFixtureRows`-style generator (1,200 rows, duplicate-`completed_at`
   groups, a page size that doesn't evenly divide the total) to bulk-insert
   via the plain repository's `insertMany` (fast — this represents "history
   already synced from another device/session," not 1,200 individual
   pushes), then call `pullAllPages(transport, { pageSize: 137, startCursor:
   null })` directly and assert exactly 1,200 distinct rows come back with
   no drops/duplicates. This proves the *sync transport/pullAllPages* path
   specifically (not just raw PostgREST, which T155.8 already proved) stays
   correct past PostgREST's 1,000-row page cap.
6. `pull` against real seeded rows — basic smoke.

## The driver hook

New file `src/features/stats/state/use-practice-history-domain-sync.ts`,
structurally a near-mechanical adaptation of `use-custom-trick-domain-sync.ts`,
simplified per "Why this domain is simpler" above:

```ts
export interface UsePracticeHistoryDomainSyncOptions {
  readonly history: PracticeHistory; // current state from the PRIMARY reducer
  readonly hasHydratedHistory: boolean;
  readonly dispatchHistory: (action: PracticeHistoryAction) => void;
  readonly getTransport: () => SyncTransportRepository<PracticeSessionRow> | undefined;
}

export interface UsePracticeHistoryDomainSyncResult {
  readonly runSync: (trigger: SyncTrigger) => Promise<DomainSyncRecord>;
  readonly isSyncing: boolean;
  readonly lastResult: DomainSyncRecord | undefined;
}
```

`runSyncImpl`:
1. No-op (`settle({status:'succeeded'})`) if `identity.kind !== 'user'` or
   `getTransport()` is `undefined`.
2. **Pull phase**: `pullAllPages(transport, { pageSize: 200, startCursor:
   null })`. On `status === 'failed'`, settle `'failed'`.
3. **Merge, unconditionally** (no `outboxIsEmpty` gate — see the design
   note above): `mapPracticeSessionRowsToDomainHistory(pull.rows, userId)`
   (existing T155.12 function). On `'invalid'`, touch nothing (malformed
   server response must never clobber good local state). On `'valid'`,
   compute the union: start from the current local `sessions` (read fresh
   via `latestRef`, not the closed-over `options.history`), add any pulled
   session whose `id` isn't already present locally. If the union differs
   from the current local sessions (by id set), set
   `suppressNextDiffRef.current = true` and dispatch `{type:
   'historyRestored', history: { sessions: mergedSessions } }` into the
   PRIMARY reducer. If the union is identical to current local state
   (nothing new), skip the dispatch entirely (avoid a pointless re-render/
   suppress-flag churn).
4. Dispatch `revisionRecorded` on the envelope with `{ history: {sessions:
   mergedSessions} }` (or the unchanged snapshot if step 3 was a no-op) so
   the envelope's own mirror stays self-contained.
5. **Push phase**: snapshot `envelope.outbox` once, call
   `pushOutboxOperations(transport, outboxSnapshot, { getExpectedRevision:
   () => null })` (always `null` — no revision cache exists for this
   domain, don't build one).
6. Per outcome: `'succeeded'` ⇒ `operationAcknowledged`.
   `'failed'` ⇒ `operationAttemptRecorded` with a descriptive message,
   operation stays pending, unrelated records' outcomes unaffected
   (`pushOutboxOperations`' existing "continue after one failure"
   guarantee). `'conflict'` is handled defensively (same shape as
   `'failed'`, recorded via `operationAttemptRecorded`) even though this
   domain's own transport never actually produces it — don't assume it's
   unreachable at the type level and skip handling it.
7. Settle `'succeeded'` unless the pull failed or an adapter call threw
   (caught, settle `'failed'`).

Diff-watching `useEffect`: same "skip on first hydration per generation,
suppress-on-pull-adopt" ref pattern as the custom-tricks driver, calling
`diffPracticeHistoryForOutboxOperations` instead. Same "one auto-run per
identity generation after both domains hydrate, for signed-in users only"
trigger effect, copied verbatim in structure.

Tests: `use-practice-history-domain-sync.test.tsx`, same RTL/fake-transport
pattern as `use-custom-trick-domain-sync.test.tsx`. Cover (mapped from this
task's exit criteria):
1. **Record sessions offline**: fake transport always network-errors;
   `recordCompletedSesh`-equivalent local mutations (dispatch
   `sessionRecorded` directly against the primary reducer via the test
   harness) enqueue outbox ops; envelope persists them; remounting under the
   same identity/generation reloads the same pending ops (durability).
2. **Reload and retry after a lost acknowledgement**: seed the fake
   transport so its *pull* already contains a row whose id matches a still-
   pending local outbox operation (simulating "the push actually landed,
   the ack was lost, and now this device is retrying") — after a sync run,
   assert the record ends up present exactly once in local state and the
   *push* attempt for that pending op also completes (via 23505-as-success
   in the fake transport, or is simply superseded — assert whichever the
   implementation actually does, but assert no duplicate and no infinite
   pending state).
3. **Deduplicate by stable record identity**: two sync runs where the
   second run's pull returns a row identical in id to one already present
   locally (already-synced) — assert exactly one session with that id in
   local state afterward, and assert `aggregatePracticeStats` computed from
   the resulting local history counts it exactly once (not double-counted).
4. **Second-browser rehydrate**: fresh envelope (empty outbox, fresh

5. **Stats derivation parity — the requirement genuinely new to this

   one at a time via the reducer and compute `aggregatePracticeStats` over
   the resulting local state; (b) start from an empty local reducer, seed
   the fake transport's pull with the same fixture rows, run a sync,  and
   compute `aggregatePracticeStats` over the resulting (rehydrated) local
