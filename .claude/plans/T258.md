# T258 implementation plan -- remove feedback's manual email field; server-owned email + message limit

## Scope confirmation / non-goals
- Do not touch `mapPostgrestError`'s `42501 -> 'authorization'` mapping (Notes explicitly defer this).
- Do not add column-level INSERT grants revoking `email` from clients. The exit criteria requires a
  spoofed client-supplied `email` to be **silently overridden**, not rejected with `42501` -- that is
  the opposite of the column-grant hardening pattern in `20260822210000_...ownership.sql` (which makes
  forged writes to server-owned columns throw outright). A `BEFORE INSERT` trigger is the only piece
  needed here; leave `api.feedback`'s existing whole-table `INSERT` grants to `anon`/`authenticated` as-is.
- Do not touch `feedback_email_format`/`feedback_email_length` CHECK constraints or the matching clauses
  inside `feedback_insert_anon`/`feedback_insert_authenticated`'s `WITH CHECK`. They become effectively
  unreachable for hostile input once the trigger always writes either `null` or a verified JWT email, but
  they're still real defense-in-depth (e.g. against a future non-trigger write path) and removing them
  isn't asked for.
- Do not add a Data API (`.test.mjs`) suite for feedback -- none exists today; pgTAP is the established
  coverage layer for this table (T217.1/T221 precedent).

## Ordering and why
Schema/trigger before app code: the trigger changes what `email` *means* server-side (client input is now
advisory-and-discarded), so writing the pgTAP proof first means the client-side removal has a settled
contract to build against, not the reverse. Message-limit UI is independent and can be done in the same
pass as the email-field removal since both land in `feedback-screen.tsx`.

1. **New migration** -- `supabase/migrations/20260909000000_enforce_feedback_email_server_owned.sql`
   (next available timestamp; last existing migration is `20260908210000_...`).

   Mirror `20260822210000_protect_server_owned_timestamps_and_ownership.sql`'s trigger shape exactly
   (SECURITY INVOKER -- the default, don't declare it -- `language plpgsql`, `set search_path = ''`,
   every non-builtin identifier schema-qualified so the empty search_path is safe):

   ```sql
   create function private.enforce_feedback_mutation_invariants()
   returns trigger
   language plpgsql
   set search_path = ''
   as $$
   begin
     if auth.uid() is not null then
       new.email := auth.jwt() ->> 'email';
     else
       new.email := null;
     end if;
     return new;
   end;
   $$;

   create trigger feedback_enforce_mutation_invariants
   before insert on api.feedback
   for each row execute function private.enforce_feedback_mutation_invariants();
   ```

   `BEFORE INSERT` only -- `api.feedback` has no `UPDATE` grant for any role (T217.1/T221 both confirm this
   with `throws_ok` `42501` assertions), so there's nothing to enforce on update.

   Ordering-correctness note the implementer should verify empirically against the local stack, not just
   trust from memory: Postgres evaluates RLS `WITH CHECK` expressions against the **post-BEFORE-trigger**
   row for INSERT (documented Postgres behavior -- BEFORE ROW triggers run first and their `NEW` mutations
   are what RLS/CHECK constraints ultimately see). This is why forcing `new.email` here doesn't fight the
   existing `feedback_email_format` WITH CHECK clause: by the time that clause runs, `email` is always
   either `null` or a real, well-formed JWT-derived address. If local pgTAP disagrees with this (a spoofed
   value survives, or a well-formed forced value gets rejected), that's a stop-and-report moment, not
   something to route around.

   Use `auth.jwt() ->> 'email'` (not the `auth.email()` helper) -- same underlying `request.jwt.claims`
   GUC, but explicit and consistent with how this file's own header comments reason about `auth.*`
   functions elsewhere (no prior `auth.email()` usage anywhere in this repo to match instead).

   Header comment should state: this is the first trigger on `api.feedback` (T217.1/T221 only used
   role-scoped grants/RLS); references the `20260822210000` pattern it mirrors; states plainly that
   `email` is fully server-owned as of this migration -- client-supplied values are always discarded, not
   validated, which is why `feedback_email_format`/`feedback_email_length` remain in place as
   belt-and-suspenders but are no longer reachable through a client request.

2. **New pgTAP test** -- `supabase/tests/t258_feedback_server_owned_email.test.sql`, matching
   `t217_1_feedback.test.sql`/`t221_feedback_authenticated.test.sql`'s file conventions
   (`begin; create extension if not exists pgtap with schema extensions; select plan(N); ... select *
   from finish(); rollback;`). Six assertions:

   - `anon`, no `email` supplied -> row's `email` is `null` (`lives_ok` insert + `is(...)` readback via an
     unrestricted/`reset role` context, matching the existing files' readback pattern).
   - `anon`, an explicit spoofed `email` value supplied -> still succeeds, and readback confirms `email` is
     `null` regardless (proves override, not rejection).
   - `authenticated` with a real session context (`set_config('request.jwt.claims',
     json_build_object('sub', <uuid>, 'role', 'authenticated', 'email', '<address>')::text, true)`,
     mirroring `t155_5_protect_server_owned_timestamps.test.sql`'s existing `set_config` pattern -- this is
     the only place in the repo that already does this, so match it exactly rather than inventing a new
     style) with an explicit spoofed `email` value in the insert -> succeeds, and readback confirms `email`
     equals the JWT's own email claim, not the spoofed value. This is the assertion the exit criteria
     names explicitly ("an authenticated insert attempting to set an arbitrary/spoofed email value is
     silently overridden rather than accepted").

   Use distinct `message` values per case as the lookup key for readback (existing files' convention).

3. **Update `t217_1_feedback.test.sql` and `t221_feedback_authenticated.test.sql`.** Their "malformed

## Risks / non-obvious things to flag
- The BEFORE-trigger-runs-before-RLS-WITH-CHECK ordering is the load-bearing assumption behind step 1 and
  step 3's test rewrites. It's standard, well-documented Postgres behavior and consistent with how this
  repo's own T155.5 migration already uses BEFORE triggers to force values that satisfy separate CHECK
  constraints (e.g. `revision := 1` alongside NOT NULL) -- but this ticket is the first place a trigger's
  forced value interacts with a WITH CHECK clause that *would have* rejected the raw client input if the
  trigger didn't run first. Confirm this with the actual pgTAP run before trusting it structurally.
- `auth.jwt() ->> 'email'` depends on GoTrue actually putting an `email` claim in the access token for
  every authenticated session this app creates. This project's local/hosted Auth config is
  password+verified-email only (no phone/anonymous auth per `supabase/README.md`), so this should hold for
  every real session; if some session type here ever lacks an email claim, the trigger's `else` branch
  never fires for it (falls through the `auth.uid() is not null` branch to a `null` email from `->>` on a
  missing key) -- same as today's optional-email shape, not a hard failure, but worth knowing why a
  signed-in row might occasionally still show `null` email if this assumption is ever violated.
- Don't skip the hosted-application step even though it's mechanically the same `db push --linked` command
  T230 already documented -- T221's own history shows a schema change that passed every local check still
  failed in production for an unrelated environment-config reason (the Data API "Exposed schemas" gap).
  Local `yarn test:db` green is necessary, not sufficient, per this ticket's own exit criteria.
