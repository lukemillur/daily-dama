# T159.2 — Import all guest data into a new empty account

## Iteration boundary

Good enough for this ticket is a resumable, empty-target import across all five local domains (`profile`, `customTricks`, `practiceHistory`, `goals`, and `notes`) that uses the existing typed mappings, identity-scoped persistence, outboxes, and repositories. A lost response, process interruption, or failure at any domain boundary must be safe to retry: acknowledged operations may be removed from the guest source only after durable acknowledgement, while every unacknowledged source record remains recoverable locally. Existing-account merge policy, profile choice, record conflicts, final guest-namespace purge, and new UI beyond the existing progress surface are deferred to T159.3–T159.5.

## Current contracts to preserve

- `src/features/guest-import/model/guest-import.ts` already owns the import state machine and stable `importId`; extend it only with facts needed to resume an empty-target upload, not with network or storage effects.
- `src/features/guest-import/persistence/guest-import-persistence.ts` is the durable progress boundary. The persisted record must identify the source guest namespace, destination user namespace, import ID, and per-domain operation/acknowledgement progress. Invalid or obsolete data must use the existing recovery-to-empty behavior.
- `src/shared/sync/sync-envelope.ts`, the five domain envelope wrappers, and `useIdentityScopedDomain` are the standard ordered-write/outbox mechanism. Do not create a guest-import-specific queue or bypass the write queue.
- The five `*-cloud-mapping.ts` modules produce authoritative insert/delete operation inputs; the five `*-sync-transport.ts` adapters are the repository boundary. Preserve the existing operation ID on every retry and let the adapters’ duplicate handling turn a lost acknowledgement into success.
- Guest source reads must use the guest-pinned/scoped storage path already proven by `countLocalGuestRecords`; destination reads/writes must be scoped to the newly authenticated user and guarded by identity generation.

## Ordered implementation plan

1. **Inventory the exact source snapshot and destination precondition.** Add a pure import-preparation module under `src/features/guest-import/persistence/` (or a narrowly named orchestration module if the implementation naturally belongs beside the hook). It should load all five guest documents once, validate through the existing persistence loaders, and produce deterministic domain operation inputs using the same mapping/diff functions as normal local sync. Represent profile as its scalar operation plus one operation per selected/manually-unlocked trick, and preserve immutable practice-session IDs and the stable IDs of custom tricks, goals, and notes. Confirm the destination is empty using the already-established inventory result; do not silently turn this path into a merge.

2. **Define durable per-domain import progress.** Extend the T159.1 progress contract with a serializable record for each prepared operation (domain, record ID, operation ID, operation type, payload or a safe reference to the guest snapshot, and status such as pending, acknowledged, or failed). Store enough information to resume without regenerating IDs or rereading a potentially changed guest document. Keep operation payloads runtime-validatable and never store native handles, promises, or `Error` instances. If the current v1 shape needs to change, update it in place per the project’s provisional-schema rule rather than introducing migration infrastructure.

3. **Stage operations in the destination’s standard envelopes.** Add a small, testable adapter/orchestrator that loads the destination user’s five envelopes, appends the prepared operations with `createOutboxOperation(operationId, input, createdAt)`, and persists each envelope through its existing `save*SyncEnvelope`/identity-scoped write path. Operation IDs must be generated once per import and domain record, persisted before a push attempt, and reused after interruption. Avoid dispatching normal user-mutation diffs from the imported destination state while staging; imported payloads are authoritative for this empty-target flow and must not be duplicated by a provider effect.

4. **Push one domain boundary at a time with acknowledgement-aware commits.** Use the existing `pushOutboxOperations` contract and each domain transport, preserving FIFO order within a domain and a deterministic order across the five domains. After each successful repository result, persist the returned row/revision metadata and remove only that exact operation ID from the destination outbox using the identity-checked envelope reducer. Then mark that source record acknowledged in the import progress record. The ordering is deliberate: a source record is never deleted merely because a request was sent, and an acknowledgement is durable before source cleanup is attempted. A 23505/idempotent retry or equivalent repository success is an acknowledgement of the original operation ID, not a new operation.

5. **Clean up source records individually and conservatively.** Add acknowledgement-aware guest cleanup helpers that operate on the guest-scoped documents and remove only records whose exact operation IDs are durably acknowledged. For profile, preserve unrelated selected/unlocked trick IDs and scalar fields; for collections, remove only acknowledged stable IDs; for practice history, never rewrite or compact unacknowledged sessions. If cleanup persistence fails, leave the source record and retain the acknowledged progress so a later resume can safely retry cleanup. Do not clear the guest namespace, import progress, or any unacknowledged record in T159.2.

6. **Make the hook resume rather than restart.** Extend `src/features/guest-import/state/use-guest-import.ts` so confirmation invokes the import orchestrator, resumes a hydrated `uploading` state using the persisted import ID/progress, and gates all async completions by import ID, destination identity, and identity generation. Persist progress after every domain/operation boundary, tolerate a lost acknowledgement by leaving the operation pending for the next run, and settle a domain only from recorded outcomes. Keep the reducer pure: timestamps, AsyncStorage, repositories, timers, and cleanup stay in the driver/orchestrator.

7. **Complete the empty-target state transition only after all five domains.** The empty path may transition to `completed` only when every prepared operation has a repository acknowledgement and corresponding source cleanup has succeeded (or cleanup is durably recorded for a safe retry, depending on the final progress contract). A failed/conflicting/non-empty result must remain pending and visible to later tickets rather than being treated as completion. Ensure account namespace activation/rehydration does not expose partially staged data and that a second browser can pull the complete destination dataset through the ordinary domain sync drivers.

8. **Add focused unit and integration/fault-injection coverage.** Extend guest-import model/persistence tests for progress round trips, malformed progress, stale import IDs, identity changes, and idempotent resume. Add preparation/orchestrator tests with fixtures covering all five domains, asserting deterministic operation IDs/payloads, destination envelope contents, FIFO behavior, returned revision adoption, per-record acknowledgement, and selective source cleanup. Add a real multi-domain integration harness using in-memory/AsyncStorage-backed guest and user namespaces plus fake repositories that can:

   - interrupt before staging, between every domain, and after each operation;
   - apply a server write but drop its acknowledgement;
   - return retryable failure or malformed/validation failure at each domain;
   - restart with the same persisted import ID and prove no duplicate rows or regenerated operation IDs;
   - prove every unacknowledged guest record remains byte-for-byte recoverable;
   - rehydrate a second browser/user provider tree and verify the complete profile, custom tricks, practice history, goals, and notes result.

   Keep the fault matrix table-driven so each of the five domain boundaries is exercised by the same assertions. Include a test that a late result from an old generation cannot acknowledge or delete data in a new guest/user namespace.

9. **Update progress documentation only as part of implementation completion.** The implementer should update `TASKS.md`/`TASKS_DONE.md` only when the ticket’s exit criteria pass, not as part of this planning artifact. Any behavior deliberately deferred to T159.3–T159.5 should be recorded in the implementation recap and, if needed, in a narrowly scoped code comment.

## Material assumptions and risks

- “New empty account” means the cloud inventory is empty across all five domains, while the guest namespace may contain data in every domain.
- The existing repositories remain the server idempotency boundary. If they cannot expose an acknowledgement for a previously applied operation, fix that contract before adding import-specific behavior; do not infer success from a request response that was not received.
- The key design risk is the two-storage transaction boundary: destination acknowledgement and guest cleanup cannot be made atomic. Durable per-record progress plus idempotent destination operation IDs makes either ordering recoverable; source deletion must never precede acknowledgement.
- Profile’s scalar and trick-state records share one domain but have distinct repository routes/revision caches. The implementation must preserve that split while reporting one `profile` domain outcome.
