# T186.2 — Resolve guest-import's own profile-preference and record conflicts automatically

## Confirmed starting point

Branch `task/T186.2-resolve-guest-import-s-own-profile` already has T186.1 (`3bb8542`) and
T187.2 (`ea50508`)/T187.1 (`2cd5639`) merged in. T186.1 already removed the manual
`awaitingConfirmation`/`inventorying` confirm UI from `guest-import-preview.tsx`; the
`uploading`/`awaitingProfileChoice`/`conflicts` branches (and their manual
`chooseProfile`/`resolveConflict`/`finishConflicts` callers) are exactly what's left, and
exactly what this ticket removes. T187.2 left guest-import's own conflict machinery
untouched on purpose (see the doc comment atop `src/shared/sync/json-snapshot.ts`) — this
ticket is that follow-up.

## Design decision (read before starting)

Two shapes were possible: (A) keep the `awaitingProfileChoice`/`conflicts` states/actions and
just auto-fire the same actions a manual UI would (mirrors T186.1's `autoConfirmedRef`
precedent, smaller diff), or (B) resolve everything at merge-*planning* time inside
`planExistingAccountMerge`, so those states/actions become genuinely unreachable and can be
deleted outright (mirrors what T187.2 itself did to the domain-sync conflict flow — full
removal, not auto-click).

**Go with (B).** Reasons, concretely established by reading the current code:

- `planExistingAccountMerge` already has every value needed to decide a winner right there
  (guest item and cloud item, before either is reduced to a canonical payload) — no new data
  plumbing beyond adding `updatedAt` is required to resolve in place.
- Once profile/record resolution happens at plan time, the only remaining job of
  `guest-import-decisions.ts` (`planProfileChoice`, `planConflictChoice`,
  `runExistingGuestImport`) is injecting already-decided operations into `progress` *later*,
  at upload time — which becomes pure duplication once planning does it up front.
  `runExistingGuestImport` turns out to add nothing over `runEmptyGuestImport` (which already
  supports `cleanupReferences`) once conflicts are pre-resolved, so the two upload paths
  collapse into one.
- `use-guest-import.test.tsx`'s existing structure (`UseGuestImportResult`'s
  `chooseProfile?`/`resolveConflict?`/`finishConflicts?` are already optional, and
  `guest-import-preview.test.tsx` never mocks them) shows the codebase already treats these as
  removable surface, not load-bearing.
- Exit criteria says "delete the manual choice/JSON-snapshot UI **entirely**" — (B) makes that
  literal: there is no longer any state that would need such UI, not just a UI that no longer
  renders it.

This is a real state-machine/persistence-domain change (removes reducer states, actions, a
persisted-document version, and a whole module), which is exactly why this ticket carries
`Planning: Required`. It touches ~13 files. That size is inherent to doing (B) correctly, not
scope creep — flag if you'd rather do the smaller (A) instead, but (A) leaves dead-but-typed
states/actions/UI branches sitting unreachable, which the codebase doesn't otherwise tolerate
outside a documented case like `resumeRequested` (which stays reachable via a different
caller — this isn't that).

## The primitive being reused

`src/shared/sync/conflict-resolution.ts`:

```ts
export function resolveUpdatedAtConflict(
  localUpdatedAt: number,
  serverUpdatedAt: number | undefined,
): 'local' | 'server'
```

Ties and unparseable/missing server timestamps both resolve to `'server'`. Every domain sync
driver (`use-profile-domain-sync.ts` etc.) already imports this directly — do the same, don't
re-derive the comparison.

## Where each side's `updatedAt` comes from

Confirmed by reading the domain models directly:

| Domain | Guest-side updatedAt | Cloud-side updatedAt |
|---|---|---|
| profile | `UserProfile.updatedAt` (optional) | not currently threaded through `ExistingAccountSnapshot` — needs adding (see step 3) |
| customTricks | `CustomTrick.updatedAt` | `CustomTrick.updatedAt` (same mapped shape both sides) |
| practiceHistory | none — `PracticeSessionRecord` has no `updatedAt` (immutable) | none |
| goals | `Goal.updatedAt` | `GoalCloudEntry.goal.updatedAt` (present on both `'active'` and `'deleted'` status) |
| notes | `Note.updatedAt` | `NoteCloudEntry.note.updatedAt` (present on both statuses) |

`practiceHistory` never has a local `updatedAt` to prove it's newer, so treat it like
`resolveUpdatedAtConflict`'s own documented "can't prove local is newer" case: always keep
cloud. Don't special-case it — just let a `guestUpdatedAt: undefined` fall through the normal
resolver and it naturally resolves to `'server'`/cloud.

## Ordered steps

### 1. `src/features/guest-import/model/guest-import.ts` — trim the state machine

Everything else types against this file, so shrink it first:

- `GuestImportStatus`: drop `'awaitingProfileChoice'` and `'conflicts'`.
- Delete `GuestImportConflict`, `GuestImportProfileComparison`, `GuestImportConflictResolution`
  from state (they move to being merge-*planning*-internal, not state-carried — see step 3).
  Keep `GuestImportChoice` (`'guest' | 'cloud'`) exported; it's still the natural return type
  of the resolution helper even though nothing stores it anymore.
- `GuestImportState`: drop `profileChoice`, `conflictResolutions`, `conflicts`,
  `profileComparison`. Keep `deduplications` — it's still how source-side cleanup is driven,
  and step 3 will start routing cloud-wins record conflicts into it too (see step 3's note).
- `GuestImportAction`: drop `profileChoiceMade`, `conflictResolved`, `conflictsResolved`.
  Shrink `existingMergePrepared`'s payload to `{ importId, progress, deduplications, now }`
  (drop `profileComparison`/`conflicts`).
- Reducer:
  - `existingMergePrepared` case: just sets `progress`/`deduplications`, no longer needs the
    dropped fields.
  - `domainUploadSettled`: currently does
    `status: state.targetKind === 'empty' ? 'completed' : 'awaitingProfileChoice'` once all
    domains settle. Since there's no more choice to await, collapse this the same way
    `progressPrepared`/`progressUpdated` already do:
    `isGuestImportFinalizable(next) ? { ...next, status: 'completed' } : next` (still
    `'uploading'` while operations are pending/unacknowledged, regardless of `targetKind`).
- `isGuestImportFinalizable`: drop the `profileChoice === undefined && targetKind === 'existing'`
  check and the `conflicts.some(...)` check — neither field exists anymore.
- `isGuestImportPendingResolution`: drop the `'awaitingProfileChoice'`/`'conflicts'` cases from
  the switch.

### 2. `src/features/guest-import/persistence/guest-import-existing-account.ts` — resolve at plan time

- `ExistingAccountSnapshot`: add `profileUpdatedAt: number | null`.
- `readExistingAccountSnapshot`: `mapProfileRowToDomainFields` already returns `updatedAt`
  alongside `fields` in its `'valid'` branch (see `profile-cloud-mapping.ts`'s
  `ProfileRowMappingResult`) — thread it through the same way `profileFields` already is:
  `profileUpdatedAt: profileMapped.status === 'absent' ? null : profileMapped.updatedAt`.
- Add an exported pure resolver, colocated here since this is where both sides' `updatedAt`
  are already in scope:
  ```ts
  export function resolveGuestImportChoice(
    guestUpdatedAt: number | undefined,
    cloudUpdatedAt: number | undefined,
  ): GuestImportChoice {
    return resolveUpdatedAtConflict(guestUpdatedAt ?? -Infinity, cloudUpdatedAt) === 'local' ? 'guest' : 'cloud';
  }
  ```
  (`guestUpdatedAt ?? -Infinity` keeps it a single call into the shared primitive rather than
  a bespoke undefined-branch, while still always losing to any defined cloud value and to the
  tie-break-to-server default when cloud is also undefined — verify this reads correctly
  against `resolveUpdatedAtConflict`'s doc comment before relying on it, and use an explicit
  `if (guestUpdatedAt === undefined) return 'cloud'` short-circuit instead if `-Infinity`
  feels like a smell in review.)
- Profile section of `planExistingAccountMerge`: after computing `guestScalar` and the existing
  `profileComparison`-shaped guest/cloud snapshots (for now, only used to build the payload —
  see below), decide the winner:
  ```ts
  const guestProfileUpdatedAt = options.guest.profile.updatedAt;
  const cloudProfileUpdatedAt = options.cloud.profile === null ? undefined : options.cloud.profileUpdatedAt ?? undefined;
  const profileWinner = options.cloud.profile === null ? 'guest' : resolveGuestImportChoice(guestProfileUpdatedAt, cloudProfileUpdatedAt);
  ```
  If `profileWinner === 'guest'`, build and push the scalar upsert operation — this is exactly
  what `planProfileChoice` in `guest-import-decisions.ts` does today (payload via
  `mapUserProfileToProfileUpsertInput`, `expectedRevision: options.cloud.profile === null ? null : <cloud revision>` —
  note profile doesn't carry a revision in `ExistingAccountSnapshot` today the way trick-states
  do; check whether the existing `planProfileChoice` even threads a real revision or always
  passes `null`/an externally supplied `expectedRevision` — read `guest-import-decisions.ts` again at
  implementation time to port this faithfully, since `planExistingAccountMerge` doesn't
  currently take an `expectedRevision` input for the profile row the way it does for other
  domains). Inline this operation-building into `planExistingAccountMerge` (or keep it as a
  small private helper in this same file) rather than importing from `guest-import-decisions.ts`,
  since that module is being deleted in step 3. Keep `GuestImportProfileComparison`'s old
  `guest`/`cloud` scalar snapshot values around only if you still want them for a future
  completion-summary; if nothing reads them once resolution is automatic, don't keep the type
  at all — the model change in step 1 already dropped it from state, so don't reintroduce a
  parallel unused return field on `ExistingMergePlan` either.
- Per-record section (the `domains` loop that currently pushes to `conflicts` on a payload
  mismatch): add a small per-domain `updatedAt` accessor next to `toPayload` in the `domains`
  tuple array (guest item and cloud item have different shapes per domain — see the table
  above; `goals`/`notes` cloud items are `GoalCloudEntry`/`NoteCloudEntry`, not the raw
  `Goal`/`Note`). Replace the `else { conflicts.push(...) }` branch with:
  ```ts
  else {
    const winner = resolveGuestImportChoice(guestUpdatedAtOf(domain, guestItem), cloudUpdatedAtOf(domain, cloudItem));
    if (winner === 'guest') {
      operations.push(operation(domain, id, guestCanonical, revision, options));
      counts[domain].creates += 1;
    } else {
      deduplications.push({ domain, recordId: id });
      counts[domain].deduplicated += 1;
    }
  }
  ```
  This is a deliberate, in-scope behavioral improvement: a cloud-wins record conflict now goes
  into `deduplications` (today's mechanism for "guest's local copy is safely superseded, clean
  it up") the same way an identical payload already does — previously a cloud-chosen conflict
  never got its guest-side source record cleaned up at all. Note it as an intentional
  side-effect of correctly implementing the operations/deduplications split, not scope creep.
- Delete the `conflict()` helper, the `GuestImportConflict`-typed accumulator, and
  `ExistingMergePlan.conflicts`. Drop the `.conflicts` bucket from the per-domain `counts`
  return shape too (nothing produces it anymore) — grep the repo first to confirm nothing reads
  `result.counts.conflicts` before deleting the field (a quick check while exploring this
  ticket found no such read, but re-verify at implementation time).
- `snapshot()`/`ConflictSnapshot` casting is no longer needed for conflicts; check whether
  anything else in this file still needs `ConflictSnapshot` after this change (`equal()` for
  the dedup check does not — it works on plain `unknown`).

## Verification

This is a persistence/state-machine change per AGENTS.md's escalation tiers (removes a reducer
status/action, changes a persisted-document version, and removes a whole module) — but it does
not touch provider hierarchy, hydration ordering, identity, or cross-domain writes (guest-import
still owns exactly one AsyncStorage key with the same load/save adapter shape, just a version
bump). Treat it as: affected-domain persistence/model/hook/UI tests while iterating, all of them
plus full typechecking before opening the PR.

- While iterating: `yarn jest src/features/guest-import` (covers model, both persistence test
  files, both hook/component test files) plus `src/app/app/__tests__/home-guest-import.test.tsx`.
- Full `yarn tsc --noEmit` before completion — deleting fields/actions/a module will surface any
  stray reference you missed far more reliably than grep alone (e.g. anything importing
  `GuestImportConflict`/`GuestImportProfileComparison`/`planProfileChoice` that this exploration
  didn't catch).
- Before opening the PR: the standard task-branch bar from AGENTS.md — relevant local evidence
  passing is enough; CI's full app checks are the release gate, not a second full local run.
  Given the size of this change, running the full `node .claude/scripts/verify.mjs` locally once
  before opening the PR (rather than relying solely on CI) is a reasonable extra margin here, not
  a requirement — your call based on how the scoped runs go.
