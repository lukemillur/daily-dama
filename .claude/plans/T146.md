# T146 — Preview a theme during onboarding before committing

## Current behavior (confirmed in code)

`src/features/onboarding/components/kentei-onboarding.tsx`, `themeSelect` case:

```tsx
case 'themeSelect': {
  const finishOnboarding = () => {
    const lacedTrickIds = getSeedLacedTrickIds(state.rank, state.landedTrickIds);
    completeOnboarding(state.rank, state.selectedTrickIds, lacedTrickIds);
    router.replace('/app/sesh');
  };
  return (
    <OnboardingThemeStep
      onSelectPreset={(preset) => {
        setThemeColors(preset.backgroundColor, preset.accentColor);
        finishOnboarding();
      }}
      onSkip={finishOnboarding}
    />
  );
}
```

`onSelectPreset` both applies the preset and immediately finishes onboarding. `onSkip` already only calls `finishOnboarding` — leave it untouched.

`setThemeColors` (from `useUserProfileActions`) is already the app's live-apply mechanism: it dispatches `themeColorsUpdated` into the user-profile reducer, which persists immediately and is consumed by `DefaultAppThemeProvider` app-wide. This is exactly how `src/features/profile/components/rainbow-theme-presets.tsx` (`RainbowThemePresets`) previews presets on the Profile screen today — tapping a preset there calls `setThemeColors` and nothing else; there is no separate "preview vs. commit" plumbing anywhere in the theme system. So "preview" for this task means: reuse `setThemeColors` exactly as `RainbowThemePresets` does, and simply stop calling `finishOnboarding()` from `onSelectPreset`. No new preview-only state layer is needed or architecturally justified — introducing one would duplicate a distinction the app deliberately doesn't have. This does mean tapping a preset during onboarding writes to persisted profile state immediately (same as Profile screen); that's consistent with existing behavior, not a new risk.

`ThemePresetGrid` (`src/features/profile/components/theme-preset-grid.tsx`) already supports an optional `isPresetSelected` prop used by `RainbowThemePresets` to highlight the active preset via `useUserProfile()` comparison. `OnboardingThemeStep` currently doesn't pass this — adding it is small, in-scope polish (selection indicator via `accessibilityState`/underline, not color alone, matching the invariant in AGENTS.md) but not required by the exit criteria. Include it since it's cheap and keeps the two preset-selection UIs consistent; skip it only if it meaningfully complicates the plumbing (it shouldn't — see step 2).

## Risks / non-obvious things

- Check the user-profile reducer's initial/default `hasCompletedOnboarding` value before writing the exact assertion in test A — don't assume `false`; read `INITIAL_USER_PROFILE` (or equivalent) in `user-profile-provider.tsx` / its model file to get the right expected value.
- `setThemeColors` writes to AsyncStorage immediately (per the persistence architecture: writes go through `createWriteQueue`), so test A's `readPersistedProfile()` after flushing microtasks should already reflect the color change even though onboarding isn't complete — this is expected, not a bug, and matches how `RainbowThemePresets` already behaves on the Profile screen (theme changes persist independent of any "commit" step there too).
- Don't add a reducer/state-machine change to `kentei-assessment.ts` — the `themeSelect` status itself doesn't need new fields unless you pursue the optional `selectedPresetId` polish, and even then it can be derived in `kentei-onboarding.tsx` from existing profile state rather than added to the assessment reducer's state shape. Keep the assessment reducer untouched.
- Multiple presets can be tapped before finishing (preview → change mind → preview again → finish) — this already works naturally since `onSelectPreset` is now a pure "call `setThemeColors` again" with no completion side effect; no extra guarding needed.
