# T208 -- Replace Home's new-account banner with a global, celebration-style acknowledgment

## Context confirmed by exploration

- src/app/app/home.tsx currently owns the whole T207 mechanism: a HomeSearchParams
  read via useLocalSearchParams, a lazy-initialized showNewAccountBanner state, a
  ref-guarded one-shot router.replace('/app/home') strip effect, and the inline
  NewAccountBanner component plus its styled-components (BannerCard, BannerCopy,
  BannerEyebrow, BannerTitle, BannerDismiss, BannerDismissText). All of this is
  banner-only; useLocalSearchParams, useRouter, BodyText, Pressable, and styled
  are not used anywhere else in the file.
- src/features/auth/components/auth-callback-screen.tsx already redirects to
  router.replace with pathname '/app/home' and params newAccount: '1' on the default
  (signup-verification) branch, never on recovery or email_change. No change needed
  here -- this stays the trigger, per the task.
- src/features/profile/components/rank-up-celebration-modal.tsx is the reuse precedent:
  a View with StyleSheet.absoluteFill, zIndex 1000, background from
  useContext(ThemeContext) accent or AppColors.yellow, wrapping
  OnboardingRankRevealStep with rewritten copy. It requires a rank number prop for
  OnboardingRankRevealStep's big numeral badge -- not applicable here, so the new
  component reuses the layout pattern (eyebrow, big center stage, title, copy) but
  cannot literally reuse OnboardingRankRevealStep's numeral badge. Use a checkmark glyph
  in the same ink-circle stage instead of a rank number.
- RankUpCelebrationModal requires a manual tap (onContinue / buttonLabel Nice!); T208
  explicitly wants auto-dismiss with no tap required, so do not reuse its button.
- src/app/_layout.tsx (root layout, above Slot) currently mounts, in order:
  ThemeProvider (expo-router's, for DarkTheme/DefaultTheme -- unrelated to
  styled-components) then Analytics (web-only) then AnimatedSplashOverlay then
  DefaultAppThemeProvider (styled-components ThemeProvider, fixed resolveTheme({})
  palette, already mounted here specifically so routes above UserProfileProvider can read
  theme.accent/theme.background) then AuthProvider then Slot. So a component reading
  ThemeContext (styled-components) already works at this level without new provider
  wiring -- RankUpCelebrationModal's own useContext(ThemeContext) pattern transfers
  directly.
- src/app/app/_layout.tsx (the /app group layout, below IdentityProvider,
  UserProfileProvider, PracticeHistoryProvider) is where KenteiRankAutoPromotion and
  RankUpCelebrationModal actually render today. T208 deliberately does not reuse that
  mount point -- it must work regardless of what's rendered under it (Home content or
  onboarding) and survive navigating away from Home, which only the root layout guarantees.
- No test currently exists for src/app/_layout.tsx. src/app/__tests__/index.test.tsx
  (testing src/app/index.tsx) is the closest sibling precedent: it imports the real
  component, mocks out its heavy dependencies via jest.mock, and asserts on
  root.toJSON()/rendered nodes. src/components/app-tabs.web.test.tsx shows the
  established pattern for mocking 'expo-router' wholesale (object literal with
  useRouter/useLocalSearchParams/usePathname stubs) rather than using real
  navigation context -- no test in this repo mounts the real Slot.
- home.test.tsx's describe block "HomeScreen new-account acknowledgment banner (T207)"
  (2 tests, near the end of the file) plus its mockRouter/mockSearchParams
  scaffolding comment referencing T207 need to be deleted or updated, since the mechanism
  moves out of HomeScreen entirely. mockSearchParams/mockRouter themselves may still
  be needed by other tests in the file -- check before deleting the scaffolding, only
  remove the newAccount-specific describe block and the now-stale comment above
  mockSearchParams.

## Design decisions for this task

1. New component: src/features/auth/components/new-account-welcome-overlay.tsx,
   exporting NewAccountWelcomeOverlay. Visually: StyleSheet.absoluteFill overlay,
   zIndex high enough to sit above Slot's content (reuse 1000 from
   RankUpCelebrationModal for consistency), background from
   useContext(ThemeContext) accent or AppColors.yellow. Internally lay out eyebrow, big
   ink-circle stage with a checkmark glyph, title, copy, matching
   OnboardingRankRevealStep's visual rhythm. Write the new component's own local
   styled-components (mirroring OnboardingRankRevealStep's constants) rather than trying
   to force-fit its Button-driven onContinue API, since that component's contract is
   built around a manual-tap onboarding step and shouldn't be distorted for this use.
   - Copy: reuse the wording already validated for this exact feature by T207 -- eyebrow
     "Welcome to Daily Dama", title "Your account is verified and you're signed in." (or
     similar) -- this is this feature's own copy, not RankUpCelebrationModal's trick-lace
     copy, so reusing it is fine and keeps behavior stable for anyone who saw the T207
     banner already.
   - accessibilityLabel "Account verified" on the outer View, matching T207's existing
     label so any downstream reliance on that string (docs, prior manual QA notes) still
     resolves; the exit criteria don't require preserving it but there's no reason to churn
     it.
   - Auto-dismiss: accept an onDismiss callback prop; internally start a setTimeout
     in a useEffect on mount (empty deps) and call onDismiss() when it fires, clearing
     the timeout on unmount. Duration: 2600ms -- long enough to read two short lines, short
     enough not to block interaction meaningfully; export it as a named constant
     (NEW_ACCOUNT_WELCOME_AUTO_DISMISS_MS) so tests can reference it instead of a magic
     number. No manual dismiss control -- the exit criteria explicitly says no tap is
     required, so do not add a close button (unlike T207's banner dismiss X, which no
     longer applies here).
   - entering animation (FadeIn/ZoomIn from react-native-reanimated, matching
     OnboardingRankRevealStep) is fine to reuse for visual consistency but keep it simple;
     don't over-invest in new animation work beyond that precedent.

2. Ownership/trigger logic moves to src/app/_layout.tsx, replacing home.tsx's removed
   logic:
   - Import useGlobalSearchParams, useRouter, usePathname from expo-router.
   - Read params via useGlobalSearchParams with a typed shape { newAccount?: string | string[] }.
   - Local firstStringOrUndefined helper (copy the one-line helper from home.tsx/
     auth-callback-screen.tsx -- small enough that duplicating it locally is fine and
     matches this codebase's existing precedent of each file having its own copy; do not
     invent a new shared util module for a 3-line function unless also folding in the other
     two call sites, which is out of scope here).
   - showNewAccountWelcome state initialized via a lazy useState initializer that reads
     firstStringOrUndefined(params.newAccount) === '1' -- the lazy initializer captures
     the value from the very first render, exactly like home.tsx's removed
     showNewAccountBanner state did. This is what keeps the mount-time check a single
     synchronous read instead of a render-then-effect toggle (the flicker-avoidance pattern
     called out in the task Notes) -- do not replace this with a useEffect-driven
     setState on mount, which would cause a visible one-frame pop-in instead of showing
     from the very first paint.
   - A one-shot strip effect, ref-guarded the same way home.tsx's was
     (hasStrippedNewAccountParamRef), calling router.replace(pathname) where
     pathname comes from usePathname() -- not the hardcoded '/app/home' home.tsx used.
     Since this now lives above every route, hardcoding the redirect destination is both
     unnecessary and would break the "regardless of what's rendered under it" contract if
     newAccount=1 ever hit a different route in the future. usePathname() returns the
     path without the query string, so replacing to it strips just the param.
   - Render the overlay conditionally as a child of DefaultAppThemeProvider (for
     ThemeContext), sibling to AuthProvider, so it doesn't depend on auth state and
     doesn't get unmounted by any auth transition. Rough shape:
       DefaultAppThemeProvider
         conditional NewAccountWelcomeOverlay (onDismiss clears the state)
         AuthProvider
           Slot
   - The existing hydration-gate discipline in this file (SplashScreen
     .preventAutoHideAsync(), AnimatedSplashOverlay) is untouched -- this addition
     doesn't interact with that hydration boundary at all, it's a plain post-mount state
     read.

3. Order of edits (schema/trigger before UI wiring before cleanup, so nothing is

   1. Create new-account-welcome-overlay.tsx (new file, no dependents yet -- safe first

      Test cases (per the exit criteria):

   5. Clean up src/app/app/home.tsx: remove HomeSearchParams,

## Risks / non-obvious things to watch

- Don't hardcode /app/home in the new root-layout strip logic. home.tsx's original code
  could hardcode it because it was route-scoped; the whole point of moving to the root
  layout is that it must work "regardless of what's rendered under it," so use
  usePathname() to generalize the strip target instead of copying the literal.
- The lazy useState initializer is load-bearing for avoiding a flicker, not incidental --
  an implementer tempted to "simplify" this into a useEffect that sets state on mount
  would reintroduce exactly the extra render-then-pop-in the task's Notes warn about. Keep
  the synchronous-first-render pattern.
- Do not mount the overlay inside AuthProvider unless there's a concrete reason to -- it
  has no dependency on auth state, and keeping it a sibling avoids any risk of an auth state
  transition (e.g. a stale-session sign-out check) unmounting it mid-display.
- OnboardingRankRevealStep cannot be reused verbatim (its rank number prop drives the
  numeral badge, and its Button-driven onContinue assumes a manual tap) -- build a new
  component that echoes its layout/spacing conventions rather than importing it directly,
  per the task's explicit "not the trick-lace celebration copy or component instance"
  instruction, which generalizes to "not the onboarding component instance either" -- the
  task only licenses reusing the pattern.
- Verify @vercel/analytics/react's Analytics component is inert under Jest's default
  Platform.OS before assuming no mock is needed -- check quickly rather than guessing; if
  it throws or does network-ish work under test, mock it out.
- Manual/in-browser verification (per exit criteria) requires the real Supabase local stack
  signup plus email-verification flow per supabase/README.md -- do this after automated
  tests pass, confirming: overlay shows full-screen regardless of what's under it, exactly
  once, auto-dismisses without a tap, and a regular sign-in shows nothing. This is web-only
  per the project's active platform scope.
