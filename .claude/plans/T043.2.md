# T043.2 plan: verify backgrounded Sesh behavior on iOS Simulator

Verification-first ticket. Code changes happen only if a platform-specific defect shows up in the Sesh lifecycle wiring (never the Sesh domain model/reducer). Android, physical device and VoiceOver: record "not run".

## Current state (verified in source at HEAD ee445e7)

- `src/features/sesh/hooks/use-app-foreground.ts`: `AppState` 'change' to `'active'` calls back with `Date.now()`. Wired in `sesh.tsx` and `multi-trick-sesh.tsx` (line ~197) as `dispatch({type:'appForegrounded', now})`.
- Reducer (`src/features/sesh/model/sesh.ts` ~203-220): `appForegrounded` only calls `completeIfDeadlinePassed` (active + timed + not paused: completes at `startedAt + durationMs + pausedDurationMs`). Open-ended and paused are timestamp-derived, no state change.
- Wake lock: `shouldKeepScreenAwake(status)` is true for `countdown` and `active` only. Pause is a flag inside `active`, so the lock STAYS held while paused (expected; do not "fix"). Both `sesh.tsx` (tag `sesh-active`, ~line 188) and `multi-trick-sesh.tsx` (tag `multi-trick-sesh-active`, ~line 282) activate in an effect keyed on `state.status` and deactivate in its cleanup. Cleanup also runs on unmount (cancel / route leave).
- Between-tricks countdown is the shared `Countdown` component (`sesh.tsx` ~541): a 3 -> 2 -> 1 chain of `setTimeout(1000)` and `onComplete()` dispatching `countdownCompleted` with `Date.now()`. It is NOT timestamp-reconciled. iOS suspends JS timers in background, so expect it to resume with the remaining count (not skip ahead). The lace-acknowledgment timeout in `multi-trick-sesh.tsx` (~line 301, dispatches `seshEnded`) is likewise a pure timer.
- Existing automated coverage: `use-app-foreground.test.tsx`, `sesh-foreground.test.tsx`, `multi-trick-sesh.test.tsx`. The worktree has no `node_modules`; run `yarn install` first.

### 2. Wake-lock evidence (decided now)
The Simulator cannot show real idle-sleep, and `expo-keep-awake` exposes no JS-readable "currently held" state besides event listeners. Evidence is therefore instrumented logs on the pinned bundle:
- Temporarily add `console.log` lines (prefix `[T043.2 keepawake]`, include tag, `state.status`, `Date.now()`) immediately before/after `activateKeepAwakeAsync(...)` resolve/reject and inside the `deactivateKeepAwake(...)` cleanup, in BOTH `sesh.tsx` and `multi-trick-sesh.tsx`. Optionally also subscribe via `addListener` from `expo-keep-awake` if the installed version exports it (check `node_modules/expo-keep-awake/build` after install) and log its activate/deactivate events per tag; this is stronger evidence of the native side.
- Read the logs from the Metro terminal output (Metro forwards device `console.log`), saved to the scratchpad dir.
- Passed = for each scenario below, an `activate` line when the Sesh enters countdown and a matching `deactivate` line when it reaches completed, is cancelled (Cancel on first countdown, End, or leaving the screen), or the component unmounts; no activate without a later deactivate across a full run; and no stray double-activate leak after a background/foreground cycle. A Metro log gap with no device logs at all means the pin or log capture failed: blocked, not passed.
- Blocked = log forwarding cannot be captured, or activate promise rejects for a reason that is not understood. State plainly that actual screen-dimming behavior was NOT observed and that `isAvailableAsync`/native release is inferred from the library call plus event, not from the display staying lit. Physical-device screen-sleep stays "not run".
- REMOVE all instrumentation before committing (`git diff` must show no `[T043.2` strings; `grep -rn "T043.2 keepawake" src` empty).
