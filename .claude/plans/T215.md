# T215 -- Fix Stats showing a false empty state right after a guest-to-account merge

## Diagnosis (confirmed against current code)

`StatsScreen` (`src/app/app/stats/index.tsx`) reads `usePracticeHistory().sessions`
straight from `PracticeHistoryProvider`'s primary reducer and renders `EmptyStats`
whenever `aggregatePracticeStats(regularSessions).sessionCount === 0` -- with no
guest-import gate at all, unlike `home.tsx`.

This is not simply "add `isGuestImportPendingResolution` to Stats and stop."
Gating strictly on `isGuestImportPendingResolution(guestImportState)` (as `home.tsx`
does) is necessary but not sufficient here, for the same structural reason T199
needed a second, domain-specific gate beyond it for the profile domain:

- `useGuestImport`'s upload phase (`use-guest-import.ts`, `runEmptyGuestImport` /
  `planExistingAccountMerge`) writes imported records directly to each cloud
  repository via `transports[domain].push` (`guest-import-empty-account.ts`,
  `guest-import-existing-account.ts`). It never goes through
  `practice-history-provider.tsx`'s own reducer, outbox, or push path. So when the
  import reaches `'completed'`, the destination identity's local
  `PracticeHistory` reducer (what `usePracticeHistory()` returns) has not been
  told anything new exists in the cloud.
- The only thing that would normally pull that cloud data into the local reducer
  is `usePracticeHistoryDomainSync`'s `runSync`, which is orchestrated by
  `SyncCoordinatorProvider` -> `useSyncCoordinator`'s login effect
  (`src/shared/sync/use-sync-coordinator.ts`, `loginFiredGenerationRef`). That
  effect fires once per identity generation, gated only on
  `allDomainsHydrated` -- i.e. as soon as the app finishes local hydration after
  sign-in, well before the guest-import upload (inventory -> confirm -> upload)
  has finished writing to the cloud. Because it's gated per-generation (not
  per-import-completion), it never re-fires once the import later finishes.
- This is exactly the same shape of gap `home.tsx` hit for the `profile` domain in
  T199, fixed there by an explicit `runSync('login')` call (via
  `useUserProfileSync()`) keyed off `guestImportState.status === 'completed'`,
  deduplicated per `importId`. `usePracticeHistorySync()` (already exported from
  `practice-history-provider.tsx`, already wired into `SyncCoordinatorProvider`)
  exposes the identical shape: `{ runSync, hasHydrated, pendingCount, ... }`.

Conclusion: Stats needs both
1. the same `isGuestImportPendingResolution` gate `home.tsx` uses (covers the
   window where the import itself is still inventorying/uploading/awaiting
   confirmation), and
2. its own resync-after-import effect targeting the `practiceHistory` domain
   specifically (covers the window between the import reaching `'completed'` and
   the local practice-history reducer actually adopting the pulled cloud rows) --
   this is the part that's independent of Home and was previously entirely
   missing.

No schema, persistence-envelope, or reducer changes are needed. This is
UI-layer composition of already-existing primitives, mirroring `home.tsx`'s
existing pattern almost mechanically -- but the mechanical part is which sync
hook to resync, and that requires exactly the trace above to get right.

## Implementation

### Step 1 -- src/app/app/stats/index.tsx

Add imports (alongside the existing ones):
- useEffect, useRef, useState from react (file currently only imports useMemo)
- isGuestImportPendingResolution from @/features/guest-import/model/guest-import
- useGuestImport from @/features/guest-import/state/use-guest-import
- useIdentityHandle from @/shared/persistence/identity-provider
- usePracticeHistorySync from @/features/stats/state/practice-history-provider
  (add to the existing usePracticeHistory import line)

Inside StatsScreen, in the existing unconditional-hooks zone (i.e. before
the "if (!isOnboardingComplete) return null;" early return -- all hooks in this
component already run unconditionally above that line; preserve that ordering
so this doesn't become a conditional-hooks bug), add:

    const { identity } = useIdentityHandle();
    const { state: guestImportState } = useGuestImport();
    const { runSync: runPracticeHistorySync } = usePracticeHistorySync();

    const importPending = identity.kind === 'user' && isGuestImportPendingResolution(guestImportState);

    // Mirrors home.tsx's identical resync effect (T199), targeting the
    // practiceHistory domain instead of profile -- see the diagnosis above for
    // why this domain needs its own independent resync.
    const [isResyncingAfterImport, setIsResyncingAfterImport] = useState(false);
    const resyncedImportIdsRef = useRef<Set<string>>(new Set());

    useEffect(() => {
      if (identity.kind !== 'user') {
        // eslint-disable-next-line react-hooks/set-state-in-effect
        setIsResyncingAfterImport(false);
        return;
      }
      if (guestImportState.status !== 'completed') return;
      const importId = guestImportState.importId;
      if (importId === undefined) return;
      if (resyncedImportIdsRef.current.has(importId)) return;
      resyncedImportIdsRef.current.add(importId);

      let cancelled = false;
      setIsResyncingAfterImport(true);
      void runPracticeHistorySync('login').finally(() => {
        if (!cancelled) setIsResyncingAfterImport(false);
      });
      return () => {
        cancelled = true;
      };
    }, [identity, guestImportState.status, guestImportState.importId, runPracticeHistorySync]);

    const blockingRender = importPending || isResyncingAfterImport;

Change the render so the blocking window never reaches EmptyStats:

    return (
      <Screen edges={['top', 'left', 'right']}>
        {blockingRender ? null : stats.sessionCount === 0 ? (
          <EmptyStats />
        ) : (
          <PopulatedStats neglectedTricks={neglectedTricks} stats={stats} />
        )}
      </Screen>
    );

Leave stats/neglectedTricks computed where they already are (before the
isOnboardingComplete bail) -- no need to reorder those; only the JSX decision
changes.

Note: calling useGuestImport() a second time here (Home already calls it) is
safe and matches the existing precedent -- it's a bare hook backed by
useIdentityScopedDomain, not a shared context. Each mounted call site loads
its own copy of the same persisted, identity-scoped state independently, and
the reducer's own status guards (e.g. importRequested only fires from 'idle')
make a second concurrent/sequential mount a no-op with respect to side
effects -- it just re-observes whatever status is already persisted (typically
already 'completed' by the time a user reaches Stats, since Home is the
landing screen). That's exactly why Stats needs its own resync effect: it
can't assume Home's resync (which only touches the profile domain) already
covered practice history.

## Risks / non-obvious things for the implementer

- Don't gate solely on isGuestImportPendingResolution and call it done -- that
  was the trap this task's Notes explicitly warned about, and the trace above
  shows it's provably insufficient (the resync gap is a distinct window after
  'completed').
- Keep all new hooks in the same unconditional zone above
  "if (!isOnboardingComplete) return null" -- don't be tempted to early-return
  before calling useGuestImport/usePracticeHistorySync, or you'll create a
  conditional-hooks violation across renders where isOnboardingComplete flips
  from false to true mid-flow (which is exactly what happens during this very
  race).
- The mocked practiceHistory.push handler in the test must actually persist
  what it receives into the same array the mocked pull reads from -- a test
  that stubs pull to unconditionally return canned data would pass even
  without the fix, which defeats the point (this is the same caution the
  existing T199 test's comment block calls out explicitly for the profile
  domain).
- usePracticeHistoryDomainSync's pull-adopt (unionSessionsById) is a set-union
  keyed by session id -- reusing the exact same session id between the seeded
  local-guest record and what gets pushed to "cloud" in the test is fine and
  expected (that's literally what the real upload path does: it pushes the
  guest's own record id verbatim).
