# T119 — Add additional kendama imagery to the landing page

## Scoping decision (read first)

The task's own Notes already resolved the licensing question in favor of sourcing a real,
externally-licensed photo (not an in-house SVG). I looked for a reasonable alternative
(matching T118's hand-drawn SVG pattern, which would avoid an external-asset dependency
entirely) and it's a legitimate option, but the Notes explicitly re-affirm "source imagery
from a permissive, no-attribution-required license" as a scoping decision, not an open
question — so this plan follows that instruction rather than re-litigating it. Flagging once,
per the working agreement, then proceeding.

## Sourced image

**File:** "Green Kendama for game.JPG" — Wikimedia Commons
**File page:** https://commons.wikimedia.org/wiki/File:Green_Kendama_for_game.JPG
**Direct original:** https://upload.wikimedia.org/wikipedia/commons/6/62/Green_Kendama_for_game.JPG
**License:** Public domain (`PD-self`) — uploader ジダネ released it as "own work" into the
public domain worldwide. Verified via the Commons API (`imageinfo|extmetadata`):
`LicenseShortName: "Public domain"`, `AttributionRequired: "false"`, `Copyrighted: "False"`,
`Restrictions: ""`. This is strictly stronger than the Unsplash-style baseline the Notes ask
for (no attribution required, not just "permitted without attribution by platform policy") and
needs no attribution text in the UI — but the *source URL and license* still get recorded in
the commit message per the Notes, and it doesn't hurt to also state "public domain, Wikimedia
Commons" in an inline code comment above the `require(...)` call site so a future reader
doesn't have to dig through commit history.

**Why this file over other Commons kendama results:** most Commons search hits for "kendama"
are `CC BY` or `CC BY-SA` (attribution required — doesn't satisfy the Notes' constraint).
Three results are plain `PD-self` product photos of a physical kendama with no people in
frame: "Kendama frontal.JPG", "Green Kendama for game.JPG", "Kendama seperat.JPG". Of those,
"Green Kendama for game.JPG" has the best native resolution (1920×2560, portrait 3:4) and a
clean, centered product shot — a good fit for a portrait sticker-card treatment matching the
existing `ScreenshotItem` cards.

I already downloaded and verified this file opens as a valid JPEG at 1920×2560. It has not
been added to the repo — that's the implementer's first step below, so the exact processed
bytes that land in `assets/images/landing/` are produced (and can be inspected) during
implementation rather than smuggled in via the plan.

## Placement

Outside both the hero (`LandingHero`, top of page) and the screenshot showcase
(`ScreenshotSection`), per the exit criteria. Insert a new photo card between
`ScreenshotSection` and `Closing` in `landing-page.tsx` — right before the closing paragraph
about kendama being "one of the best excuses to put your phone down." A real photo of the
physical toy, placed right where the copy pivots from the app back to the object itself, reads
as an intentional beat, not filler. It also gives the page a second "grounding" visual moment
(SVG hero at the top, real-object photo near the bottom) instead of clustering all imagery
around the screenshots in the middle.

Do not attach new caption copy to the photo. `LandingHero` sets the precedent for an
image-only sticker panel with just an `accessibilityLabel`/`alt` and a `testID` — the existing
`Closing` paragraph immediately below already carries the thematic text, so a caption here
would just duplicate it.

## Implementation steps, in order

1. **Process and add the asset first** (schema/asset before UI, since the component's
   `require()` will fail to resolve otherwise).
   - Download the original:
     `curl -sL "https://upload.wikimedia.org/wikipedia/commons/6/62/Green_Kendama_for_game.JPG" -o /tmp/kendama-source.jpg`
   - Resize/compress with `sips` (matches the existing landing screenshots, which are all
     well under 100KB — the untouched original is 2.8MB and shouldn't ship as-is):
     `sips -Z 900 -s format jpeg -s formatOptions 80 /tmp/kendama-source.jpg --out assets/images/landing/kendama-photo.jpg`
     This produces a 675×900 JPEG (~145KB in my test run). Verify the output dimensions with
     `sips -g pixelWidth -g pixelHeight assets/images/landing/kendama-photo.jpg` and confirm
     the aspect ratio used in code (`675 / 900`) matches whatever `sips` actually produces —
     use the real output dimensions, not the numbers above, if they differ slightly.
   - `git add assets/images/landing/kendama-photo.jpg`.

2. **Add `src/features/landing/components/landing-photo.tsx`**, mirroring
   `landing-hero.tsx`'s structure (an `expo-image` `Image`, not `react-native-svg`, since this
   is a raster photo, not an illustration):
   ```tsx
   import { Image } from 'expo-image';
   import { styled } from 'styled-components/native';

   import { AppColors, Radii } from '@/constants/theme';

   // Public domain (Wikimedia Commons, "Green Kendama for game.JPG",
   // https://commons.wikimedia.org/wiki/File:Green_Kendama_for_game.JPG) — no attribution
   // required.
   const PHOTO_ASPECT_RATIO = 675 / 900; // update if the processed asset's dimensions differ

   export function LandingPhoto() {
     return (
       <PhotoPanel testID="landing-photo" style={{ boxShadow: `8px 8px 0 ${AppColors.ink}` }}>
         <Image
           source={require('@/assets/images/landing/kendama-photo.jpg')}
           accessibilityLabel="A green kendama, the wooden cup-and-ball toy Daily Dama is built around"
           alt="A green kendama, the wooden cup-and-ball toy Daily Dama is built around"
           contentFit="cover"
           style={{ width: '100%', aspectRatio: PHOTO_ASPECT_RATIO, borderRadius: Radii.panel }}
         />
       </PhotoPanel>
     );
   }

   const PhotoPanel = styled.View`
     margin-top: 40px;
     max-width: 260px;
     align-self: center;
     padding: 10px;
     background-color: ${AppColors.paperStrong};
     border: 2px solid ${AppColors.ink};
     border-radius: ${Radii.panel}px;
   `;
   ```
   - `max-width: 260px` keeps it visually secondary to the CTA/hero (280px) and screenshot
     cards (360px) rather than competing with them — adjust to taste, but keep it narrower
     than the hero so it doesn't read as a second, competing hero.
   - Reuses the established `boxShadow` prop pattern (see the comment above `CtaPanel` in
     `landing-cta.tsx` for *why* it's a `style` prop and not baked into `.attrs`) — don't
     switch to the CSS `box-shadow` shorthand.

3. **Wire it into `landing-page.tsx`:**
   - Import: `import { LandingPhoto } from '@/features/landing/components/landing-photo';`
   - Insert `<LandingPhoto />` immediately after the closing `</ScreenshotSection>` and before
     `<Closing>`.

4. **Test coverage** — add to `src/features/landing/components/landing-page.test.tsx`, inside
   the existing `describe('LandingPage')` block (next to the existing
   `it('renders the hero banner', ...)` test), following the same `testID` pattern:
   ```tsx
   it('renders the kendama photo', async () => {
     const root = await mount();

     expect(root.root.findAllByProps({ testID: 'landing-photo' }).length).toBeGreaterThan(0);
   });
   ```
   No new mocks are needed — `expo-image` is already mocked at the top of that test file, and
   the mock is a generic stand-in that passes through props, so `testID` still resolves.

5. **Browser check** (exit criteria requires this explicitly): run `yarn expo start --web`,
   load the landing page, and confirm the photo renders between the screenshot showcase and
   the closing paragraph, at both a mobile-width and desktop-width viewport (the 320px nav
   width constraint from `AGENTS.md` applies to the nav bar, not this card, but eyeball that
   the card doesn't overflow or look cramped at narrow widths regardless).

6. **Full verification:** `node .claude/scripts/verify.mjs` (all four steps — this is a
   feature change, not docs/test-only, so don't use `--skip-export`).

## Risks / things to double-check

- The `sips` resize numbers above (675×900, ~145KB) are from a scratch-directory test run
  during planning, not the final in-repo asset — re-verify actual output dimensions/size after
  running the real command, and keep `PHOTO_ASPECT_RATIO` in sync if they differ.
- Don't confuse this with T118's `LandingHero` — that component intentionally has no external
  asset dependency; this one intentionally does. Keep them as separate files/components rather
  than merging, since their asset-sourcing story (in-house SVG vs. licensed external photo)
  is a meaningful distinction worth preserving for future readers.
- No `Closing` copy changes are in scope here — leave that paragraph's text alone.
