# T259 — Branded fallback screen for fatal app errors

## Confirmed Expo Router convention (SDK 57 / expo-router 57.0.10)

Verified directly against `node_modules/expo-router/build/views/Try.js` and
`useScreens.js` (installed version, not assumed from memory):

- A route module (any file under `src/app`, including a layout) may export a
  named `ErrorBoundary: (props: ErrorBoundaryProps) => JSX.Element`, where
  `ErrorBoundaryProps = { error: Error; retry: () => Promise<void> }`. Both are
  publicly exported from `expo-router` (`exports.d.ts`).
- When a route module exports `ErrorBoundary`, `useScreens.js`'s `fromImport`
  wraps the *entire* default-exported component in an internal `Try` class
  component: `<Try catch={ErrorBoundary}>{createElement(DefaultExport, props)}</Try>`.
  `Try` is a real `getDerivedStateFromError` class boundary, so it catches
  errors thrown anywhere in the wrapped subtree, not just inside the layout
  function body itself.
- Consequence for placement: exporting `ErrorBoundary` from the root
  `src/app/_layout.tsx` puts `Try` above `TabLayout`'s entire returned tree —
  above `ThemeProvider`, `DefaultAppThemeProvider`, `AuthProvider`, and
  `<Slot/>` (and everything any nested route/layout renders, since no other
  layout in this app exports its own `ErrorBoundary`, so all fatal render
  errors bubble to this single top-level boundary via normal React
  error-boundary bubbling). One export at the root is sufficient; do not
  duplicate it in `src/app/app/_layout.tsx`.
- Critical implication: the fallback component renders outside every context
  provider the app normally relies on (styled-components `ThemeProvider`,
  navigation `ThemeProvider`, `AppThemeProvider`/`useTheme()`, `AuthProvider`).
  It must not call `useTheme()`, use `ThemedText`, or use the styled-components
  `Button` (`src/components/ui/button.tsx`, which reads `theme.buttonBackground`
  via styled-components' `ThemeProvider` and will crash inside the crash
  handler if used here). Build it from bare `View`/`Text`/`Pressable` +
  `StyleSheet`, using raw `AppColors`/`Spacing` constants from
  `@/constants/theme` (plain JS values, not hooks) — same pattern already used
  by `src/components/local-durability-warning-banner.tsx`, minus its
  `ThemedText` dependency.
- expo-router also ships its own default `ErrorBoundary`
  (`views/ErrorBoundary.js`, black background, "Something went wrong" heading,
  white bordered "Retry" button) used when a route/layout throws and no one
  exports a custom `ErrorBoundary`. This is "the default red-box/blank-screen
  failure" the task refers to; our branded component must render visibly
  different copy so a test (and a user) can tell them apart.

     ```tsx
     class RouteErrorBoundaryHarness extends Component<
       PropsWithChildren<{ catch: ComponentType<ErrorBoundaryProps> }>,
       { error?: Error }
     > {
       state: { error?: Error } = {};
       static getDerivedStateFromError(error: Error) {
         return { error };
       }
       retry = () => new Promise<void>((resolve) => this.setState({ error: undefined }, resolve));
       render() {
         const { error } = this.state;
         const { catch: Fallback, children } = this.props;
         if (!error) return children;
         return <Fallback error={error} retry={this.retry} />;
       }
     }
     ```

## Risks / non-obvious things for the implementer

- The single biggest risk is reaching for `ThemedText`, `useTheme()`, or the
  styled-components `Button` inside the fallback component — any of those
  will throw inside the error handler itself in production, because none of
  their required context providers are mounted at the point this component
  renders. Keep it dependency-free RN primitives only.
- `retry()` returns `Promise<void>` and only resolves once React has
  re-rendered with the error cleared — awaiting it in the test
  (`await retryButton.props.onPress()`) is what makes the post-retry
  assertions safe to make synchronously afterward without an extra
  `act()`/flush.
- Do not add `Sentry.captureException` inside this boundary — explicitly out
  of scope per the task's Notes (automatic capture from T218 already covers
  this; manual capture here is a deferred follow-up, not required now).
- Don't be tempted to also export `ErrorBoundary` from
  `src/app/app/_layout.tsx` "for extra coverage" — it's redundant given the
  root-level placement (see the bubbling argument above) and would create two
  different fallback UIs to keep in sync for no behavioral gain.
