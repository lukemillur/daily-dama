# T030 — Make the Profile screen scrollable on mobile

## Root cause (confirmed in code)

`src/app/profile/index.tsx` renders:

```tsx
<Screen align="center" edges={["top", "left", "right"]}>
  <Content>...</Content>
</Screen>
```

`Content` is `styled.View` with `flex: 1; justify-content: center; padding: 40px 22px 130px;` — a plain `View`, not a `ScrollView`. On web, `src/app/+html.tsx` renders `<ScrollViewStyleReset />` (from `expo-router/html`), which sets `html`/`body`/`#root` to `height: 100%; overflow: hidden`. That means nothing outside an actual RN `ScrollView` can scroll — a plain flex `View` taller than its container just clips. Because `Content` also vertically centers (`justify-content: center`), the overflow is clipped symmetrically top and bottom, which is exactly why the rank tile (first child) disappears off the top and the streak save button (last child) is unreachable off the bottom.

This matches the task Notes exactly and confirms the fix: swap the plain `View` for a real `ScrollView`, and drop the vertical-centering behavior now that content flows top-to-bottom.

## Reference pattern already established elsewhere

`src/app/stats/index.tsx` (most recently touched, cleanest instance of the pattern) does this:

```tsx
<Screen edges={['top', 'left', 'right']}>
  <StatsScroll contentContainerStyle={{ paddingBottom: 120 + BottomTabInset }}>
    <StatsContent>...</StatsContent>
  </StatsScroll>
</Screen>
```

```ts
const StatsScroll = styled(ScrollView)`flex: 1; width: 100%;`;
const StatsContent = styled.View`width: 100%; max-width: 760px; align-self: center; padding: 36px 22px 0;`;
```

Identical shape appears in `src/app/tricks.tsx` (`FormScroll`/`FormContent`), `src/features/home/components/daily-home.tsx` (`HomeScroll`/`HomeContent`), and `src/features/goals`/`src/features/notes` screens. Key details to replicate:

- `Screen` is used with its **default** `align` (`stretch`), not `align="center"`. Horizontal centering of the content column is done by the inner `View` itself via `align-self: center` + `max-width`, not by the `Screen`'s `align-items`.
- The `ScrollView` is a direct styled wrapper (`flex: 1; width: 100%;`) around the content `View`.
- The bottom safe-scroll allowance goes on the `ScrollView`'s `contentContainerStyle` as `paddingBottom: 120 + BottomTabInset`, not baked into the content `View`'s own `padding`. `BottomTabInset` (`src/constants/theme.ts`) is `Platform.select({ ios: 50, android: 80 }) ?? 0` — i.e. 0 on web, because the web tab bar (`src/components/app-tabs.web.tsx`) floats at the **top** of the screen (that's what `Screen`'s `padding-top: 88px` web header inset already reserves for), not the bottom. None of the sibling screens pass `webBottomInset` to `Screen` for this reason — confirmed by checking `stats/index.tsx`, `tricks.tsx`, and the `Sesh` component, none of which set it. `daily-home.tsx`'s `webBottomInset={24}` on the *home* route is unrelated (small extra margin for its dev-only sandbox links) and shouldn't be copied here.
- The content `View`'s own top padding (36–40px range across these screens) is independent of `Screen`'s 88px web header inset — that inset is already applied via `Screen`'s `padding-top`, so nothing here needs to account for it a second time. Profile's current `Content` already uses 40px top padding, which is consistent with this and needs no change.

## Implementation steps

All changes are in one file: `src/app/profile/index.tsx`.

1. **Imports.** Add `ScrollView` to the existing `import { TextInput } from "react-native";` (→ `import { ScrollView, TextInput } from "react-native";`), and add `BottomTabInset` to the existing `import { AppColors } from "@/constants/theme";` (→ `import { AppColors, BottomTabInset } from "@/constants/theme";`).

2. **`Screen` props.** Drop `align="center"` from the `<Screen>` call at line 30, leaving `<Screen edges={["top", "left", "right"]}>`. This matches every sibling screen using this pattern; horizontal centering moves to the content `View` in step 4.

3. **Wrap `Content` in a `ScrollView`.** Introduce a new styled component (place it next to `Content` in the styled-components block, same convention as `StatsScroll`/`StatsContent`):

   ```ts
   const ProfileScroll = styled(ScrollView)`
     flex: 1;
     width: 100%;
   `;
   ```

   In the JSX, replace:

   ```tsx
   <Screen edges={["top", "left", "right"]}>
     <Content>
       ...
     </Content>
   </Screen>
   ```

   with:

   ```tsx
   <Screen edges={["top", "left", "right"]}>
     <ProfileScroll contentContainerStyle={{ paddingBottom: 120 + BottomTabInset }}>
       <Content>
         ...
       </Content>
     </ProfileScroll>
   </Screen>
   ```

   No changes to the JSX children of `Content` itself — `StreakSettings` and all the section content render exactly as before.

4. **Update the `Content` styled-component.** Change from:

   ```ts
   const Content = styled.View`
     width: 100%;
     max-width: 760px;
     flex: 1;
     justify-content: center;
     padding: 40px 22px 130px;
   `;
   ```

   to:

   ```ts
   const Content = styled.View`
     width: 100%;
     max-width: 760px;
     align-self: center;
     padding: 40px 22px 0;
   `;
   ```

   - Remove `flex: 1; justify-content: center;` — that's the vertical-centering behavior that caused symmetric clipping; content should now flow naturally from the top inside the scroll container.
   - Add `align-self: center;` to replace the horizontal centering previously provided by `Screen`'s `align="center"`.
   - Change the baked-in `130px` bottom padding to `0` — the scroll-clearance allowance now lives on `ProfileScroll`'s `contentContainerStyle` (`120 + BottomTabInset`), matching `StatsContent`/`HomeContent`/`FormContent`.

No other files need to change. `StreakSettings` is a plain function component already rendered as a child of `Content`; it needs no changes since it doesn't own any scroll/layout container itself.

## Order and rationale

This is a single-file, single-concern layout fix with no schema, state, or cross-feature dependency — there's no meaningful ordering constraint beyond doing the edits top-to-bottom in the file (imports → `Screen` props → JSX wrap → styled-component). No other screen or test references `ProfileScreen`'s internal structure, so there's no ripple effect to sequence around.

## Risks / non-obvious things

- **Don't reach for CSS `overflow`/web-only tricks.** The reason nothing scrolls today is `expo-router/html`'s `<ScrollViewStyleReset />` in `src/app/+html.tsx`, which sets `html`/`body`/`#root` to `overflow: hidden`. Only an actual RN `ScrollView` will scroll on web in this app shell — this is why the fix must be a real `ScrollView`, not a style tweak on the existing `View`.
- **Don't add `webBottomInset` to `Screen`.** It's tempting since the task mentions "the floating tab bar," but the web tab bar sits at the *top* (covered by `Screen`'s existing 88px web header inset), and `BottomTabInset` is already 0 on web — it only matters on iOS/Android. Adding a redundant web bottom inset would just add dead space under the `ScrollView`'s own `paddingBottom`.
- **Don't double-count the web header inset.** `Screen`'s `padding-top: 88px` (web only, `includeWebHeaderInset` defaults true) already reserves space for the top nav. `Content`'s existing `40px` top padding is independent of that and should stay as-is — no need to add or subtract anything for the header when making this change.
- Removing `align="center"` from `Screen` and moving centering to `Content` via `align-self: center` is a behavior-preserving refactor (visually identical horizontal centering) — confirmed by cross-referencing `StatsScreen`/`daily-home.tsx`, which use exactly this split.

## Verification

This is explicitly a browser-verified exit criterion, not a unit-test one (per the task Notes) — a test asserting a `ScrollView` exists wouldn't prove the defect is fixed.

1. Run the standard sequence: `yarn test --runInBand`, `yarn lint`, `yarn tsc --noEmit`, `yarn expo export --platform web --output-dir /tmp/daily-dama-web-export` — confirms no regressions/type errors from the edit.
2. Start the Expo **dev server** (not the static export — extensionless routes like `/profile` need dev-server routing) and open it in-browser.
3. Resize the browser viewport to 375px width (mobile).
4. Navigate to `/profile` as a user who has completed onboarding (has a `kenteiRank` — the screen returns `null` otherwise, so use/seed a profile that's past onboarding).
5. Confirm at load: the assessed-rank tile (`RankNumber`/`RankLabel`/`RankContext`) is fully visible at the top, not obscured by the floating web nav.
6. Scroll down through the page and confirm every section renders in order and is reachable: Assessment (retake), Kentei assessment (start), Daily streak (minutes input + Save button) — the Save button must be fully visible and tappable above the bottom edge, not clipped or hidden under the nav.
7. Sanity-check desktop width (≥480px, where the nav shows its "Daily Dama" wordmark) isn't visually broken by the `Screen`/`Content` change — this fix should be layout-neutral there since desktop already had enough viewport height in practice, but the `align`/`align-self` swap touches shared styling.
8. Recheck the 320px web-nav-fits constraint noted in `AGENTS.md` is untouched — this change doesn't touch `app-tabs.web.tsx`, so it should be a non-issue, but worth a glance since it's a hard constraint elsewhere in the codebase.
