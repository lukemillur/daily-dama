## Read this first: the ticket's premise is wrong, and it changes the work

T239's Description says `targetLandingCount` "is local component state only" and that a
persistence-domain decision is still open. **Both are already false.** Commit `4a02d17`
(`[T048] Persist open-ended sesh target laces across sessions`, PR #59, `TASKS_DONE.md:1195`)
implemented exactly this feature, and the domain decision T239 asks for was made there: the
**user-profile domain**, inside the existing `lastSesh` field.

The end-to-end path that exists today:

1. `src/features/sesh/components/sesh.tsx:200` — `handleTrickSelected` calls
   `setLastSesh(trick.id, plan)` when a trick is picked.
2. `src/features/profile/state/user-profile-provider.tsx:138` → `createLastSesh`
   (`src/features/profile/model/user-profile.ts:48`) stores
   `{ kind: 'openEnded', targetLandingCount: N }` on `UserProfile.lastSesh.plan`.
3. `src/features/profile/persistence/user-profile-persistence.ts:44-56` (`isLastSesh`) validates
   and round-trips that shape through AsyncStorage; `profile-cloud-mapping.ts` round-trips it to
   the `profiles.last_sesh` jsonb column.
4. `src/app/app/sesh/index.tsx:38-44` derives `initialPlan` from `lastSesh`, including
   `createOpenEndedSeshPlan(lastSesh.plan.targetLandingCount)`.
5. `sesh.tsx:345-352` (`TrickPicker`) seeds `planKind` and `targetLandingCount` from `initialPlan`.

**I verified this empirically**, not just by reading. I ran a throwaway Jest test in this worktree
that mounted the real providers over the mocked AsyncStorage, mirrored the route's `initialPlan`
derivation, set the target field to `5`, ran and ended an open-ended sesh, unmounted the whole
tree, then mounted a second time (forcing a real hydration from storage). The second mount rendered
`Target lace count` with `value === "5"` and the `Open-ended` radio `checked`. The scratch files
were deleted; nothing from that experiment is committed.

So T239's exit criteria are **already satisfied by current behavior**. This is not a blocker — the
ticket still has real, unfinished work — but the work is different from what the entry describes,
and the implementer must not go looking for a missing feature to build.

### What is actually missing (do this)

1. **There is no regression test for it.** T048 tested `createLastSesh` and the persistence
   round-trip in isolation, but nothing asserts the behavior the exit criteria describe —
   "reopening sesh setup shows that value pre-filled". Grep confirms: `initialPlan` appears in
   tests only twice (`sesh.test.tsx:2480,2531`), both `createTimedSeshPlan(1)`, never open-ended
   with a target. The prefill path is entirely uncovered.
2. **The route's derivation is untestable where it lives.** The `lastSesh → SeshPlan` mapping is
   inlined in the route component (`src/app/app/sesh/index.tsx:38-44`), so any test has to either
   mount the whole route (heavy: `useLocalSearchParams`, `useRequireOnboarding`, `useAuthState`,
   `useCustomTricks`) or duplicate the mapping — and a duplicated mapping means the test would
   still pass if the route regressed. Extract it so the test and the route share one function.

### What is also broken, but is NOT in scope (record it, do not fix it)

The remembered target is stored *inside* `lastSesh.plan`, which is a discriminated union. A single
timed sesh therefore overwrites it. I confirmed this with a second scratch test: open-ended with
target `5` → remount shows `"5"` → run one **timed** sesh → remount, switch to Open-ended → the
field is `""`. Under the ticket's own Description ("pre-filled the next time they open sesh setup")
this is a genuine defect, and it is the most plausible thing the user actually hit during the
S111 QA pass, since `Timed` is the picker's default format.

**Do not fix it in this ticket.** Making the target survive a timed sesh means adding a key that
`lastSesh` cannot currently hold. `supabase/migrations/20260822193659_add_profiles_and_user_trick_states.sql:60-99`
defines the `profiles_last_sesh_shape` CHECK constraint, which pins `last_sesh` to exactly
`{trickId, plan}` (`last_sesh <@ jsonb_build_object('trickId', ..., 'plan', ...)`) and each plan
variant to exactly its own two keys. There is even an explicit rejection test for an extra
top-level key (`supabase/tests/data-api/t155_6_profiles.test.mjs:131`). A new top-level
`UserProfile` field is no cheaper: `mapUserProfileToProfileUpsertInput` writes an explicit column
list, so an unmapped field would be silently dropped on any cloud pull-adopt. Either route requires
a new SQL migration, updates to `supabase/tests/t155_2_profiles_and_trick_states.test.sql` and
`supabase/tests/data-api/t155_6_profiles.test.mjs`, a local Supabase stack run
(`supabase/README.md`), and eventually an owner-authorized hosted migration. That is a separate,
larger ticket — not a Medium-priority test-coverage ticket.

Record it in the closing notes and the PR body (step 8). Do **not** allocate a new task ID for it;
IDs are shared across four files and other agents may be allocating concurrently. Leave the

### Step 1 — Extract the route's `initialPlan` derivation into the profile model

File: `src/features/profile/model/user-profile.ts`

Add a `selectInitialSeshPlan` next to `createLastSesh` (it is that function's inverse, so keep them
adjacent). Line 1 currently does `import type { SeshPlan } from '@/features/sesh/model/sesh';` —
change it to a combined value + type import. This direction is already established
(`user-profile-persistence.ts` value-imports from the sesh model) and creates no cycle: `sesh.ts`
imports only `@/features/tricks/model/trick`.

```ts
import {
  createOpenEndedSeshPlan,
  createTimedSeshPlan,
  isValidTimedSeshMinutes,
  type SeshPlan,
} from '@/features/sesh/model/sesh';

/**
 * The plan Sesh setup should open with: an explicit challenge duration from a
 * deep link if there is one, otherwise the shape of the last sesh this profile
 * ran (including its open-ended lace target). The inverse of `createLastSesh`.
 *
 * Total and non-throwing on purpose: `challengeDurationMs` arrives from a URL
 * query parameter, so an out-of-range or non-integer-minute value must fall
 * back to the persisted plan rather than throwing `createTimedSeshPlan`'s
 * RangeError out of a route render.
 */
export function selectInitialSeshPlan(
  lastSesh: LastSesh | undefined,
  challengeDurationMs?: number,
): SeshPlan | undefined {
  if (challengeDurationMs !== undefined && Number.isFinite(challengeDurationMs)) {
    const minutes = challengeDurationMs / 60_000;
    if (isValidTimedSeshMinutes(minutes)) return createTimedSeshPlan(minutes);
  }
  if (!lastSesh) return undefined;
  return lastSesh.plan.kind === 'timed'
    ? createTimedSeshPlan(lastSesh.plan.durationMinutes)
    : createOpenEndedSeshPlan(lastSesh.plan.targetLandingCount);
}
```

Behavior notes to preserve exactly:

- A valid challenge duration still wins over `lastSesh` (matches today's ternary order).
- `lastSesh.plan.durationMinutes` and `plan.targetLandingCount` are already validated at the
  persistence boundary by `isLastSesh`, so the `createTimedSeshPlan`/`createOpenEndedSeshPlan`
  calls on that branch cannot throw. Leave them unguarded; do not add defensive parsing there.
- The only intentional behavior change is the invalid-`challengeDurationMs` branch: today
  `createTimedSeshPlan(challengeDurationMs / 60_000)` throws (e.g. a hand-edited
  `/app/sesh?plannedDurationMs=30000` yields `0.5` minutes and crashes the route render). It now
  falls back. Keep this change — it is two lines inside a function you are writing anyway, and
  leaving a known crash path in new code is worse than the tiny scope addition. Call it out in the
  closing notes.

## Risks and traps

- **Biggest risk is scope drift.** The instinct on reading the ticket is to build the persistence.
  It exists. Resist expanding into the timed-sesh gap; that is a Supabase migration ticket.
- **The write-queue flush** (`await act(async () => { await Promise.resolve(); })`) between ending
  the sesh and unmounting is not optional. Without it the second mount hydrates a stale document
  and the test fails for a reason unrelated to the behavior under test.
- **`UserProfileProvider` renders a hydration fallback, not children, until `hasHydrated`.** Every
  mount must be wrapped in `await act(async () => ...)` or the tree will contain only the "Loading
  your practice..." fallback and every `findByProps` will fail.
- **Do not widen `isLastSesh`.** It is an untrusted-boundary validator whose failure mode is
  resetting the whole profile to `INITIAL_USER_PROFILE`. Nothing in this ticket needs it changed.
- **Do not add a top-level field to `UserProfile`.** `mapUserProfileToProfileUpsertInput`
  (`profile-cloud-mapping.ts`) writes an explicit column list, so an unmapped field survives
  locally but is silently dropped whenever a cloud pull-adopt dispatches `profileRestored`. Any new
  profile field needs a column, a migration, and mapper changes.
- **`Sesh` has exactly one call site** (documented in its own props comment), so the Step 1/2
  refactor cannot break an unnoticed second consumer — but re-run the full `src/features/sesh`
  suite anyway, since `sesh.test.tsx` renders `Sesh`, `ActiveSesh`, `CompletedSesh`, and
  `Countdown` directly.
- **Fresh worktrees have no `node_modules`.** Several prior tickets' notes record this; run
  `yarn install` first.
