# T189 — Fix logout destination and reset session-scoped app state

## Root cause (confirmed against current code)

- `/` (`src/app/index.tsx`) renders outside `IdentityProvider` (that only wraps
  `/app/*` in `src/app/app/_layout.tsx`), exactly like the `/auth/*` group T170
  already fixed. So `/`, like `/auth/*`, has no live identity resolution and must
  always treat itself as guest.
- `useRedirectOnboardedVisitorHome` (`src/features/landing/state/redirect-onboarded-visitor-home.ts`)
  calls `useCachedOnboardingStatus`, which calls
  `readCachedOnboardingStatus` (`src/features/profile/persistence/read-cached-onboarding-status.ts`).
  That function still reads only the bare legacy key
  `USER_PROFILE_STORAGE_KEY` ('daily-dama:user-profile'). Since T156.2,
  `UserProfileProvider` persists through `createGuestMigratingStorage`, which
  writes every value to the identity-scoped physical key
  (`guest:daily-dama:user-profile` for a guest, or `user:<uuid>:...` once
  signed in) and only reads the bare key once, as a one-time migration
  fallback. So after logout, the bare key holds a stale snapshot (either never
  migrated, or belonging to whatever identity last touched it), and
  `readCachedOnboardingStatus` sees `hasCompletedOnboarding: true` from that
  stale data and immediately redirects `/` back to `/app/home`.
- `readCachedThemeBackgroundColor` (`src/features/profile/persistence/read-cached-theme-background.ts`)
  has the identical bug: it's used by `AnimatedSplashOverlay`
  (`src/components/animated-icon.web.tsx`), which is mounted once at the root
  layout and reads a synchronous pre-hydration snapshot to pick the splash
  background before hydration/routing resolves. It only reads the bare key
  today, so a full page load anywhere in the app (including a hard refresh on
  `/` right after logging out of an account with a custom theme) can flash the
  stale account's theme instead of the guest default.
- T170 already solved exactly this class of bug for `/auth/*` via
  `readCachedGuestTheme`/`useCachedGuestTheme`
  (`src/features/profile/persistence/read-cached-guest-theme.ts`,
  `src/features/profile/state/use-cached-guest-theme.ts`): read the
  identity-scoped guest key first (`physicalKey(GUEST_IDENTITY,
  USER_PROFILE_STORAGE_KEY)` = `'guest:daily-dama:user-profile'`), falling back
  to the bare legacy key only when the scoped read is empty. This mirrors
  `createGuestMigratingStorage`'s own read order and is read-only (never writes
  back). This task applies that identical pattern to the two remaining
  bare-key readers.
- Note: `/`'s styled-components *theme* (`DefaultAppThemeProvider` in
  `src/features/profile/components/app-theme-provider.tsx`) is already fixed
  to the default palette regardless of cache state — that part of the landing
  page is not part of this bug. The theme-background fix here is specifically
  about `AnimatedSplashOverlay`'s pre-hydration splash-background flash, not
  `/`'s rendered page theme.

## Plan

1. **`src/features/profile/persistence/read-cached-onboarding-status.ts`**
   Add `GUEST_SCOPED_KEY = physicalKey(GUEST_IDENTITY, USER_PROFILE_STORAGE_KEY)`
   (same imports as `read-cached-guest-theme.ts`: `GUEST_IDENTITY` from
   `@/shared/persistence/identity`, `physicalKey` from
   `@/shared/persistence/scoped-storage`). Change the read to
   `getItem(GUEST_SCOPED_KEY) ?? getItem(USER_PROFILE_STORAGE_KEY)`, matching
   `readCachedGuestTheme` exactly. Update the doc comment to explain the
   scoped-first/bare-fallback order and reference `read-cached-guest-theme.ts`
   as the pattern being mirrored (the current comment saying "mirrors
   read-cached-theme-background.ts" becomes circular once both are fixed
   together — reword both docstrings to point at `read-cached-guest-theme.ts`
   as the canonical explanation, and keep the mechanical detail local).

   Do this first: it's the file the exit criteria's specific regression test
   depends on, and `use-cached-onboarding-status.ts` and
   `redirect-onboarded-visitor-home.ts` both consume it unchanged (same
   `getItem` signature), so no caller-side signature change is needed here.

2. **`src/features/profile/persistence/read-cached-onboarding-status.test.ts`**
   Add tests mirroring `read-cached-guest-theme.test.ts`'s new-behavior cases:
   - falls back to the bare key when the guest-scoped key is empty
   - prefers the guest-scoped key over the bare key when both exist
   - the exit-criteria case verbatim: a stale bare-key snapshot with
     `hasCompletedOnboarding: true` plus an empty/absent guest-scoped key for a
     fresh guest identity (i.e. guest-scoped key present but
     `hasCompletedOnboarding: false`, or guest-scoped key absent and bare key
     stale) must resolve to `{ hasCompletedOnboarding: false, kenteiRank:
     undefined }`. Write it as: guest-scoped key holds a document with
     `hasCompletedOnboarding: false`, bare key holds a stale document with
     `hasCompletedOnboarding: true, kenteiRank: <n>` — assert the scoped value
     wins and produces the default status. Existing tests are unaffected since
     they use a `getItem` that ignores its `key` argument and returns the same
     document for both key reads.

3. **`src/features/landing/state/use-cached-onboarding-status.ts`**
   Mirror `use-cached-guest-theme.ts`'s native branch exactly: import
   `GUEST_IDENTITY` and `physicalKey`, compute the same `GUEST_SCOPED_KEY`
   constant, and change the native `AsyncStorage.getItem(...)` call from
   `USER_PROFILE_STORAGE_KEY` to `GUEST_SCOPED_KEY`. The web branch needs no
   change — `readCachedOnboardingStatus((key) =>
   window.localStorage.getItem(key))` already passes a real per-key lookup, so
   step 1's internal two-key read works through it unchanged. This
   intentionally does not add a bare-key fallback on native (native is not an
   active verification target here, and `useCachedGuestTheme` established the
   same simplification — its native path only ever fetches the scoped key).
   Update the doc comment's "falls back to one non-blocking `AsyncStorage.getItem`
   read" wording only if it currently implies bare-key semantics; otherwise
   leave as-is.

4. **`src/features/landing/state/use-cached-onboarding-status.test.tsx`**
   Update the native describe block: the existing test seeds
   `AsyncStorage.setItem('daily-dama:user-profile', ...)` (bare key) and
   expects it to resolve — change that seed to the scoped key
   (`physicalKey(GUEST_IDENTITY, USER_PROFILE_STORAGE_KEY)`, i.e.
   `'guest:daily-dama:user-profile'`) to match the new native read target. Add
   a web-describe-block test for the exit criteria's specific scenario
   (post-logout guest identity, no completed guest onboarding, stale bare-key
   snapshot present) so the fix is verified at the hook level too, not just in
   `read-cached-onboarding-status.test.ts`. Import `GUEST_IDENTITY` and
   `physicalKey` for the key constant, matching how `read-cached-guest-theme.test.ts`
   computes `GUEST_SCOPED_KEY`.

5. **`src/features/profile/persistence/read-cached-theme-background.ts`**
   Same transform as step 1: add `GUEST_SCOPED_KEY = physicalKey(GUEST_IDENTITY,
   USER_PROFILE_STORAGE_KEY)`, change the read to `getItem(GUEST_SCOPED_KEY) ??
   getItem(USER_PROFILE_STORAGE_KEY)`. Its only caller,
   `animated-icon.web.tsx`, is web-only and already passes
   `(key) => window.localStorage.getItem(key)`, so no caller change is needed.
   Update the doc comment to describe the new fallback order (currently it
   only mentions the pre-hydration synchronous-read rationale, not
   scoping) and reference `read-cached-guest-theme.ts`.

6. **`src/features/profile/persistence/read-cached-theme-background.test.ts`**
   Add the same three new-behavior tests as step 2 (falls back to bare key,
   prefers scoped key when both exist, and a stale-bare-key-with-fresh-guest
   case: guest-scoped key has no custom color, bare key has a stale custom
   color — assert the result is the default background, not the stale color).

7. **Manual in-browser verification** (exit criteria explicitly requires this,
   not just unit tests): run the Expo dev server, sign in as / create an
   account with a custom theme, complete onboarding, log out via
   `AccountSection`, and confirm landing on `/` shows the default theme and
   does not redirect back to `/app/home`. Also do a hard refresh on `/`
   immediately after logout to check the splash-background flash is gone
   (step 5's fix). No new automated browser test is in scope — this mirrors
   how T170's own exit criteria were verified.

## Ordering rationale

Steps 1–2 (the direct cause of the reported redirect bug) come before 3–4 (the
hook wrapper around it) because the hook's behavior is entirely downstream of
`readCachedOnboardingStatus`; fixing the hook first would leave the underlying
helper's bug uncovered by its own dedicated test. Step 5 (theme background) is
independent of 1–4 and could be done in either order, but is sequenced after
since it's the secondary, lower-visible-impact half of the fix explicitly
named in the task's Description. Step 7 (manual verification) is last because
it depends on all code changes being in place.

## Risks / non-obvious things to watch

- Do not change `readCachedOnboardingStatus`'s or
  `readCachedThemeBackgroundColor`'s exported signature (`getItem: (key:
  string) => string | null`) — only the internal read logic changes. Existing
  callers and most existing tests (which use a `getItem` that ignores its
  argument) keep passing unmodified.
- Do not add any write-back behavor to these two helpers. Like
  `readCachedGuestTheme`, they must stay read-only; migration write-through is
  `createGuestMigratingStorage`'s job once a real provider mounts.
- Do not touch `useSyncExternalStore`'s hydration-mismatch gate in either
  `use-cached-onboarding-status.ts` or `animated-icon.web.tsx` — T145's
  flicker-free first paint depends on that boundary staying exactly as-is;
  this task only changes which storage key is read after that boundary has
  already passed.
- `landing-cta.tsx` also calls `useCachedOnboardingStatus` for CTA copy; it
  gets the same fix for free with no separate change needed — worth a quick
  sanity look after the change but not a separate plan step.
- Confirm no other caller currently relies on `readCachedOnboardingStatus` or
  `readCachedThemeBackgroundColor` reading the bare key for a *signed-in*
  identity's data on `/`. Per `read-cached-guest-theme.ts`'s own documented
  precedent, `/` (like `/auth/*`) has no live identity resolution and is
  treated as always-guest; this is a deliberate, already-accepted
  approximation from T170, not a new gap introduced by this task.
