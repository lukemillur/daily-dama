# T083.3 -- Apply theme colors to post-onboarding screens

## Design decision (read first)

Two fixed tokens map 1:1 onto the two theme fields already on `UserProfile`:

- `AppColors.sage` (the `Screen` component's default page background) -> `themeBackgroundColor`
- `AppColors.yellow` (used everywhere as the app's primary accent -- button labels, badge/CTA
  backgrounds, highlighted values, selected-state text) -> `themeAccentColor`

`AppColors.sage` and `AppColors.yellow` are otherwise not used for anything else in the
post-onboarding tree (confirmed by grep -- see enumeration below), so the mapping is unambiguous.
No other decorative background/accent tokens exist beyond these two.

Mechanism: a single `styled-components/native` `ThemeProvider`, mounted once near the app root,
fed by one `useResolvedTheme()` hook that reads `UserProfileProvider` state and falls back to the
fixed `AppColors` values when a field is `undefined`. Every touched call site stops importing the
literal `AppColors.sage` / `AppColors.yellow` and instead reads `theme.background` / `theme.accent`
via styled-components' automatic `theme` prop (or `useTheme()` for the one plain-`StyleSheet` call
site). This is the single resolved-theme mechanism the task requires -- no per-site fallback logic
is duplicated anywhere.

Why this doesn't touch onboarding, even though a couple of shared components (`Button`,
`OnboardingRankRevealStep`) are used both during onboarding and after: `themeBackgroundColor` /
`themeAccentColor` can only be set from the Profile screen's `ThemeColorPicker`, and Profile is
only reachable once `hasCompletedOnboarding` is true (`useRequireOnboarding` redirects everything
else to `/`, and the tab bar hides those tabs until then -- see
`src/features/onboarding/state/require-onboarding.ts`, `src/components/app-tabs.tsx`). So on every
reachable path, `profile.themeBackgroundColor`/`themeAccentColor` are still `undefined` for the
entire lifetime of the onboarding flow, and the resolved theme is byte-identical to today's fixed
colors while onboarding renders. No branching on `hasCompletedOnboarding` is needed inside the
theme hook itself -- verify this invariant still holds before implementing (see Risks below for the
one latent counter-example, `restartOnboarding`, which is currently dead code).

## Enumeration of every fixed-color usage this touches

Grep basis: `grep -rln "AppColors.sage\|AppColors.yellow" --include="*.ts*" src` (excluding tests).
Eighteen files matched; below is the full disposition of each.

### In scope -- convert `AppColors.sage` -> `theme.background`

1. `src/components/ui/screen.tsx` -- `Screen`'s default `background` prop value. This is the
   mechanism's single choke point: every tab-route `<Screen>` call (Home, Sesh, Sesh multi-trick,
   Tricks index/goals/notes/laced/custom-new/custom-edit/custom-delete, Stats index/detail,
   Profile index, Kentei assessment) renders with no explicit `background` prop today and so
   already relies on this default -- fixing it here threads the resolved background through all of
   them without touching those files individually.
2. `src/app/index.tsx:41` -- the one `<Screen>` call that does pass an explicit background
   (`profile.hasCompletedOnboarding ? AppColors.sage : AppColors.yellow`). Change the onboarded
   branch to `undefined` so it falls through to `Screen`'s own (now themed) default; leave the
   pre-onboarding branch as the literal `AppColors.yellow` -- untouched, exactly as today.

Two call sites explicitly override `background` to `AppColors.paper` and are correctly excluded
because they never went through `sage` in the first place: `src/features/access-gate/components/access-gate-screen.tsx`
(pre-app password gate, not post-onboarding) and `src/app/stats/sesh-sequence-sandbox.tsx` (dev-only
sandbox, not linked from any tab, explicitly documented as such in its own file comment).

### In scope -- convert `AppColors.yellow` -> `theme.accent`

Plain interpolation (`color: ${AppColors.yellow};` -> `color: ${({ theme }) => theme.accent};`, or
the `background-color` equivalent) unless noted otherwise:

- `src/components/ui/button.tsx:55` -- `ButtonLabel`'s primary-variant text color. Shared by every
  screen including onboarding; safe per the invariant above. Needs a prop-conditional edit:
  `color: ${({ $variant, theme }) => ($variant === 'primary' ? theme.accent : AppColors.ink)};`
- `src/features/onboarding/components/onboarding-rank-reveal-step.tsx:62` -- `RankNumber` text
  color. Shared between `kentei-onboarding.tsx` (pre-onboarding) and `RankUpCelebrationModal`
  (post-onboarding, rank-up trigger). Same invariant applies -- convert directly, no prop plumbing.
- `src/features/profile/components/rank-up-celebration-modal.tsx:36` -- `styles.overlay.backgroundColor`
  is a plain `StyleSheet`, not a styled-component, so it can't read `theme` via interpolation. Add
  `const theme = useTheme();` (from `styled-components/native`) and pass
  `style={[styles.overlay, { backgroundColor: theme.accent }]}` on the `View`. Leave the
  `StyleSheet.create` default as-is (harmless, defensive fallback).
- `src/app/stats/index.tsx:157` -- `OverviewValue` text color (sits on an `AppColors.ink` card --
  contrast-safe, see Risks).
- `src/app/stats/[trickId].tsx:123` -- `BestValue` text color (same ink-card pairing).
- `src/app/tricks/index.tsx:543` -- `ToggleMark`, prop-conditional:
  `${({ $selected, theme }) => ($selected ? theme.accent : AppColors.red)}`. Only the `$selected`
  branch changes; the `AppColors.red` (unselected/functional) branch stays fixed.
- `src/features/goals/components/trick-goals-screen.tsx:269` -- `KindMark`, same prop-conditional
  pattern as `ToggleMark`.
- `src/features/home/components/daily-home.tsx:220` -- `StreakValue` text (on `AppColors.ink` badge).
- `src/features/home/components/daily-home.tsx:222` -- `Hero` background color.
- `src/features/home/components/daily-home.tsx:258` -- `MomentumValue` text (on `AppColors.ink` strip).
- `src/features/sesh/components/multi-trick-sesh-entry.tsx:198` -- `FinishBackdrop`, prop-conditional:
  `${({ $pinned, theme }) => ($pinned ? theme.accent : AppColors.paper)}`.
- `src/features/sesh/components/multi-trick-sesh-entry.tsx:215` -- `AdvanceOnFirstLaceMark` text.
- `src/features/sesh/components/sesh.tsx:1163` -- `PlanChoiceTitle`, prop-conditional:
  `${({ $selected, theme }) => ($selected ? theme.accent : AppColors.ink)}`.
- `src/features/sesh/components/sesh.tsx:1172` -- `ChallengeChoiceTitle`, same pattern.
- `src/features/sesh/components/sesh.tsx:1226` -- `NextTrickButton` background color.
- `src/features/sesh/components/sesh.tsx` (~1230, the block right after `NextTrickButtonText`) --
  `MultiTrickAction` background color. Matched by the same grep but on a wrapped multi-line
  template, so it doesn't have its own distinct line number above.
- `src/features/sesh/components/sesh.tsx:1241` -- `CelebrationBannerCard` background color.
- `src/features/sesh/components/sesh.tsx:1254` -- `NotePromptButtonText` text color.

Note `onboarding-selection-step.tsx` also matched the grep (it has its own `FinishBackdrop`,
`AppColors.yellow`) but is a separate, differently-scoped component only ever rendered from
`kentei-onboarding.tsx` -- it is not reachable post-onboarding and must stay untouched. Don't
confuse it with `multi-trick-sesh-entry.tsx`'s `FinishBackdrop` above, which is in scope -- same
name, different file, different reachability.

### Explicit non-goals (leave untouched)

- All five provider hydration-fallback screens (`AppColors.yellow` `backgroundColor` in
  `src/features/custom-tricks/state/custom-trick-provider.tsx`,
  `src/features/notes/state/note-provider.tsx`,
  `src/features/profile/state/user-profile-provider.tsx`,
  `src/features/goals/state/goal-provider.tsx`,
  `src/features/stats/state/practice-history-provider.tsx`). These render before their own domain
  (or, for the other four, potentially before `UserProfileProvider`) has hydrated from
  AsyncStorage, so the resolved theme isn't knowable yet -- there's no profile to read. Theming
  them would require cross-domain hydration-order coupling, which conflicts with each persistence
  domain owning its own hydration fallback independently (see AGENTS.md, State and persistence
  boundaries). Boot-time flicker between a themed fallback and the real themed screen a moment
  later would also be worse UX than staying fixed.
- `src/features/onboarding/components/onboarding-selection-step.tsx` and everything else under
  `src/features/onboarding/` and `kentei-onboarding.tsx` -- pre-onboarding, must render identically
  to today regardless of any theme fields.
- `src/features/access-gate/components/access-gate-screen.tsx` and
  `src/app/stats/sesh-sequence-sandbox.tsx` -- not post-onboarding screens (see above).
- All functional colors: `AppColors.red` (errors/destructive), `AppColors.ink`/`inkSoft`/`textMuted`/
  `textSubtle` (text), `AppColors.paper`/`paperStrong`/`cream`/`borderMuted` (fixed surfaces). None
  of these are touched by this task regardless of where they sit next to an accent/background color.

## Implementation order

1. Type plumbing first (nothing depends on this but everything after needs it to typecheck): add
   `src/types/styled-components.d.ts` declaring `DefaultTheme` for `'styled-components/native'`
   with `{ readonly background: string; readonly accent: string }`, following the existing
   `src/types/styles.d.ts` module-augmentation precedent.
2. The resolved-theme hook: add `src/features/profile/state/use-resolved-theme.ts` exporting
   `useResolvedTheme()`, reading `useUserProfile()` and returning
   `{ background: profile.themeBackgroundColor ?? AppColors.sage, accent: profile.themeAccentColor ?? AppColors.yellow }`.
   Co-locate next to `user-profile-provider.tsx` since it's profile-domain-derived state.
3. Root wiring: add `src/features/profile/components/app-theme-provider.tsx` exporting
   `AppThemeProvider({ children })`, which calls `useResolvedTheme()` and renders
   `<ThemeProvider theme={...}>{children}</ThemeProvider>` (import `ThemeProvider` from
   `'styled-components/native'`, aliased if needed to avoid clashing with the existing
   `expo-router` `ThemeProvider` import in `_layout.tsx`). In `src/app/_layout.tsx`, this must sit
   inside `UserProfileProvider` (so the hook has profile context to read) -- replace the current
   `<KenteiRankAutoPromotion /><AppTabs />` pair inside `<GoalProvider>` with
   `<AppThemeProvider><KenteiRankAutoPromotion /><AppTabs /></AppThemeProvider>`. Order matters:
   this must come before step 4 so `Screen`/`Button`/etc. have a `ThemeProvider` ancestor once they
   start reading `theme`.
4. Screen and Button (the two shared UI primitives, touched before any feature screen so the
   primitives are already theme-aware when feature files are converted):
   - `src/components/ui/screen.tsx`: drop the `AppColors.sage` default; call
     `const theme = useTheme();` and compute `const resolvedBackground = background ?? theme.background;`
     inside the component body (not in the destructuring default -- that would call a hook
     conditionally). Remove the now-unused `AppColors` import if nothing else in the file needs it.
   - `src/components/ui/button.tsx`: convert `ButtonLabel`'s primary-variant color as described
     above.
5. `src/app/index.tsx`: change the explicit `background` prop as described above.
6. Remaining feature/screen files, in any order (each is an independent, mechanical edit) --
   `onboarding-rank-reveal-step.tsx`, `rank-up-celebration-modal.tsx`, `stats/index.tsx`,
   `stats/[trickId].tsx`, `tricks/index.tsx`, `trick-goals-screen.tsx`, `daily-home.tsx`,
   `multi-trick-sesh-entry.tsx`, `sesh.tsx` (5 separate declarations in this one file).
7. Run the verification sequence once all conversions are in, then do the in-browser check below.

Steps 1-4 must precede 5-6 because 5-6 assume a working `theme.background`/`theme.accent` contract
and a mounted provider; doing them first would leave `theme` undefined and mask mistakes.

## In-browser verification plan

Run the Expo web dev server and, for each of the three required checks, reload/navigate rather than
relying on Fast Refresh to carry stale styled-components theme state:

1. Unset theme renders identically to today: with no theme ever set (fresh profile, or after
   pressing "Reset to default" on the Profile screen's `ThemeColorPicker`), visually compare Home,
   Sesh (both single-trick and multi-trick entry, plus an active/completed session to see
   `NextTrickButton`/`CelebrationBannerCard`/`NotePromptButtonText`), Tricks (index list toggle
   marks, a Trick Goal form's kind picker), Stats (overview + a trick detail page), and Profile
   against the `development` branch's current rendering (or a screenshot taken before starting).
   Background should be sage, accent should be yellow, everywhere.
2. Saved custom theme reflects everywhere: from Profile, set a background and accent through
   `ThemeColorPicker` that pass the WCAG guardrail (e.g. background `#2b2440`, accent `#ff8a3d` --
   pick values clearly distinguishable from sage/yellow at a glance) and confirm every one of the
   five tab screens picks up both colors without a manual reload (React state propagates through
   the `ThemeProvider` automatically) -- check page background on all five, and accent on: Button
   primary-variant CTAs, Home hero/streak badge/momentum strip, Sesh's next-trick/celebration/plan-
   choice controls, Tricks' selected toggle marks, Stats' overview/best values.
3. Pre-onboarding stays yellow: clear the profile (or use a fresh browser profile/incognito) so
   onboarding runs from scratch, confirm it still renders the fixed yellow throughout regardless of
   any theme previously saved in that browser's storage -- this is really testing the "theme fields
   don't exist yet during onboarding" invariant, so if a leftover `themeAccentColor` from a prior
   session is still in AsyncStorage/localStorage while `hasCompletedOnboarding` is somehow `false`,
   that's the one scenario worth deliberately trying (see Risks) even though it shouldn't be
   reachable through normal UI flows today.
4. Also re-check the known 320px web nav width constraint isn't affected (it shouldn't be -- no
   layout dimensions change here) and that the two known-benign warnings are the only console
   warnings present.

## Risks / things to double-check before or during implementation

- `restartOnboarding` is dead code today (reducer action + provider callback exist, but no UI
  calls it -- confirmed by grep). Its reducer branch (`case 'onboardingRestarted'`) resets
  `kenteiRank`/`hasCompletedOnboarding` but does not clear `themeBackgroundColor`/
  `themeAccentColor`. If this action is ever wired up in a future ticket, a user who set a theme and
  then restarted onboarding would see the onboarding flow themed instead of fixed-yellow, breaking
  the "pre-onboarding yellow state is unaffected" guarantee. Not a blocker for T083.3 since it's
  unreachable today, but flag it in the PR description so it isn't silently forgotten; the eventual
  fix (whenever `restartOnboarding` is wired up) is to also clear the theme fields in that reducer
  case, not to special-case it here.
- Contrast is only guaranteed against `AppColors.ink`. `ThemeColorPicker`'s WCAG check (T083.2)
  validates each of background/accent independently against the fixed `ink` text color -- and by
  the enumeration above, every converted usage does pair the accent with `ink` (as text-on-ink-
  surface or ink-text-on-accent-surface). Two exceptions exist where a third, unrelated fixed color
  sits on top of the accent surface: `HeroMarker`/`Eyebrow` (`AppColors.red` text) on `Hero`'s
  `AppColors.yellow`/accent background in `daily-home.tsx`, and `CelebrationBannerEyebrow` (also
  red) on `CelebrationBannerCard`'s accent background in `sesh.tsx`. Neither pairing has any
  contrast guarantee today (fixed yellow vs. fixed red already just happens to work). A user-chosen
  dark accent could make that red eyebrow text hard to read. This is a pre-existing gap in T083.2's
  guardrail (which only checks against `ink`), not something to solve inside T083.3 -- call it out
  explicitly when reporting this ticket done, and eyeball it in the browser with a deliberately dark
  accent color during verification so it's a documented, seen tradeoff rather than a silent one.
- `Button` and `OnboardingRankRevealStep` are shared with the onboarding tree. Converting them is
  safe only because of the "theme fields are always undefined during onboarding" invariant
  established above -- re-verify that invariant holds against the actual `development` code at
  implementation time (it may have shifted since this plan was written) before relying on it.
- Watch for the `ThemeProvider` naming collision in `_layout.tsx` (`expo-router`'s navigation
  `ThemeProvider` is already imported there under that exact name) -- import styled-components'
  version under an alias, e.g. `import { ThemeProvider as StyledThemeProvider } from 'styled-components/native';`,
  inside `app-theme-provider.tsx` (which doesn't otherwise need the `expo-router` one, so no
  aliasing needed there -- only worth double-checking `_layout.tsx` itself doesn't end up importing
  both).
- No existing jest test renders `Screen`/`Button`/the converted feature components wrapped in a
  styled-components `ThemeProvider` (confirmed: only `theme-color-picker.test.tsx` references
  `AppColors` in a test, and it doesn't test any of the touched components). Styled-components
  supplies an empty `{}` theme object when no provider is present rather than throwing, so
  `theme.accent`/`theme.background` will just resolve to `undefined` in isolated component tests --
  harmless for existing assertions (none check rendered color values) but confirm this with
  `yarn test --runInBand` rather than assuming it.
