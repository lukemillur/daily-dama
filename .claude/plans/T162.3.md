# T162.3 -- Add dependency, secret, and built-bundle scanning to CI

## Ground truth gathered before writing this plan

- `.github/workflows/ci.yml` today has one job (`verify`: checkout, setup-node,
  `yarn install --frozen-lockfile`, test, lint, tsc), triggered on `pull_request`/`push`
  to `main`/`development`, no explicit `permissions:` block. `gh api
  repos/lukemillur/daily-dama/actions/permissions/workflow` confirms the repo's actual
  default token permission is already `read`, but the workflow file itself doesn't say
  so -- this task should make it explicit and auditable in the file, not rely on an
  external setting nobody reading `ci.yml` can see.
- Repo is a **private** repo (`gh repo view --json visibility` -> `PRIVATE`) owned by a
  **personal account**, not an org (`gh api users/lukemillur --jq .type` -> `User`).
  This rules out `actions/dependency-review-action` -- GitHub's own docs
  (`dependency-review-action` README) state it only works on private repos with a paid
  GitHub Advanced Security license, which AGENTS.md's "do not add paid observability"
  rules out. Use `yarn audit` instead (already in the task's own suggested list).
  The personal-account status is also why `gitleaks/gitleaks-action` is usable
  without a paid `GITLEAKS_LICENSE` (that's only required for org-owned repos).
- `security/scripts/build-and-serve.mjs` already exports a reusable `buildExport()`
  that runs `yarn expo export --platform web --output-dir dist` with placeholder
  Supabase env vars defaulted in if real ones aren't set. Reuse this, don't
  re-implement the export invocation.
- I actually ran `yarn audit --level high` locally: **`--level` does not gate Yarn
  Classic's exit code** (known upstream bug -- the flag only filters the printed
  report). Exit code is a bitmask of every severity present, regardless of `--level`.
  Real current findings on `development`: 3 distinct high advisories + 1 moderate,
  all inside `expo`'s Metro/bundler devDependency chain, all "No patch available":
  - `1138808` (high) -- image-size ICNS parser infinite-loop DoS
  - `1138809` (high) -- image-size JXL/HEIF parser infinite-loop DoS
  - `1139427` (high) -- nanoid zero-size generator infinite loop
  - `1119441` (moderate) -- uuid missing buffer bounds check
  Zero critical findings today. These are all build-time-only (Metro bundler), not
  shipped in the web bundle, and have no upstream fix yet -- gating CI on them today
  would either permanently red-flag `development` or force a same-day allowlist,
  neither of which is "CI passes on the clean repository." A hand-rolled severity gate
  (see step 4) with a small, dated, reasoned allowlist is the correct fix, not lowering
  the bar to "critical only" and not relying on `--level`'s broken behavior.
- I actually ran `gitleaks detect --source . --redact -v` (v8.30.1, downloaded fresh)
  against the full `development` history (812 commits scanned) and got **18 findings,
  all confirmed false positives, zero real secrets**:
  - `src/features/auth/model/auth-test-fixtures.ts:6` -- the canonical jwt.io example
    JWT (`eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIn0.dozjg...`),
    rule `jwt`.
  - `src/features/auth/model/auth-test-fixtures.ts:7` -- synthetic `REFRESH_TOKEN`
    fixture (`vJv8bZ0kL3nQ7wR2xY9dC1mF4hT6sA8u`), rule `generic-api-key`.
  - `e2e/auth/01-sign-in-equivalence.spec.ts:21` -- `WRONG_PASSWORD =
    'incorrect-horse-battery-1'` test fixture, rule `generic-api-key`.
  - `supabase/README.md` and `.claude/plans/T153.10.md` (history-only, file since
    deleted) -- multiple `curl -H "apikey: LOCAL_ANON_KEY"` documented example
    commands, rule `curl-auth-header`, where `LOCAL_ANON_KEY` is a literal placeholder
    string, not a real key.
  This means a naive `gitleaks-action` drop-in **fails "CI passes on the clean
  repository" out of the box** unless a `.gitleaks.toml` allowlist is added first (step
  1 below) -- do this before wiring the CI job, not after discovering a red build.
- I built a real web export (`yarn expo export --platform web`) and ran
  `gitleaks detect --no-git --source <dist>` against it: **zero findings**, confirming
  the current bundle is clean and a bundle-scan job can also start green.
- Default gitleaks rules already include a generic `jwt` rule (any `eyJ...eyJ...`
  shape) and `generic-api-key`. Since this app's only real Supabase secrets
  (anon/service_role keys, Auth session/refresh JWTs) are all JWT- or
  high-entropy-token-shaped, the default ruleset already covers "service-role keys" and
  "Auth sessions" from the task description without needing hand-written
  Supabase-specific regexes. No default rule exists for Resend/SMTP secrets
  specifically, but nothing in this repo's source or env handling currently touches
  those (SMTP config is Supabase-dashboard-side per `supabase/RESEND_DNS_AUTH.md`), so
  this is not worth a bespoke rule for this task -- note it as a documented gap in
  `security/README.md` rather than over-building.
- `actions/checkout@v4.2.2` -> SHA `11bd71901bbe5b1630ceea73d27597364c9af683`.
  `actions/setup-node@v4.1.0` -> SHA `39370e3970a6d050c480ffad4ff0ed4d3fdee5af`.
  `gitleaks/gitleaks-action@v3.0.0` -> SHA `e0c47f4f8be36e29cdc102c57e68cb5cbf0e8d1e`
  (v3, not v2: v2 is Node20-based and GitHub's own deprecation timeline in the
  gitleaks-action README already has both the "opt-out required" and "Node20 removed
  entirely" dates in the past relative to today's date -- v2 may already be broken).
  `zricethezav/gitleaks` Docker image `v8.30.1` -> digest
  `sha256:c00b6bd0aeb3071cbcb79009cb16a60dd9e0a7c60e2be9ab65d25e6bc8abbb7f` (used for the
  bundle scan and the self-test, since `gitleaks-action` only scans a checked-out
  repo's git history, not an arbitrary directory -- running the plain `gitleaks` CLI
  via its official Docker image, pinned by digest, is the way to scan `dist/`).
- Docker is already an assumed local dependency in this repo (`supabase/README.md`:
  "Docker Desktop (or a compatible engine)... running locally" for the local Supabase
  stack), so requiring Docker for the new bundle-scan/self-test scripts locally is
  consistent with existing conventions, not a new burden. `ubuntu-latest` GitHub-hosted
  runners have Docker preinstalled, no extra setup step needed in CI.

## Design decisions this plan is committing to

1. **Four new CI jobs**, all triggered by the existing `on:` block (no new triggers
   needed), running in parallel with the existing `verify` job (no `needs:` between
   them -- keep the fast feedback of independent jobs): `dependency-audit`,
   `secret-scan`, `bundle-secret-scan`, `secret-scan-self-test`.
2. Add a workflow-level `permissions: contents: read` in `ci.yml`. This is currently
   already the *effective* org/repo default (verified via `gh api
   .../actions/permissions/workflow` -> `"default_workflow_permissions":"read"`), so
   this is a no-op functionally, but makes the "no write permissions" guarantee visible
   in the file itself rather than an invisible external setting -- do this explicitly
   rather than relying on repo settings an implementer three months from now can't see
   from the workflow file. No job needs more than `contents: read` (secret-scan's
   PR-comment feature is explicitly disabled, see step 3).
3. `gitleaks-action` needs `pull-requests: write` only for its PR-commenting feature.
   Disable that feature (`GITLEAKS_ENABLE_COMMENTS: "false"`) rather than granting the
   permission -- this is what makes "runs for pull requests... without gaining write
   permissions" true. Leave `GITLEAKS_ENABLE_UPLOAD_ARTIFACT` at its default (`true`) --
   uploading a workflow-run artifact does not require any extra token scope.
4. Dependency audit gate: severity `>= high` fails the job, **except** advisory IDs
   listed in a small, dated, reasoned local allowlist file (the four IDs found above).
   Do not use `yarn audit`'s own `--level` flag to gate (it's broken, per the finding
   above) -- parse `yarn audit --json`'s NDJSON output directly in a small script and
   apply the threshold/allowlist there.
5. No committed secret/bundle "fixture" files anywhere in the repo. The "isolated test"
   required by the exit criteria builds its fixture content into a scratch temp
   directory *at test run time* (a throwaway scratch repository, initialized fresh and
   never pushed anywhere, plus a copy of a real dist export with a fake secret string
   appended to one file), asserts gitleaks catches it, then discards it. This proves
   the negative path is real without ever putting secret-shaped content into this
   repo's actual, permanent git history -- exactly the trap a naively-designed "commit
   a fixture secret" test would fall into. This self-test *does* run as a normal CI job
   on every PR (it never reads or writes the real repo's history or working-tree
   secrets, so it's safe and cheap to run always), acting as a permanent regression
   guard that the scanning wiring itself still works -- same spirit as this repo's
   existing `dangerous-html-audit.test.ts`.

## Implementation order

1. **`.gitleaks.toml`** (new, repo root). `[extend] useDefault = true` plus one
   `[[allowlist]]` block with `regexes` (not `paths` -- matching on the exact leaked
   *value*, not blinding a whole file, so a real secret later pasted into
   `supabase/README.md` would still be caught) for the four confirmed false positives
   found above: the literal jwt.io example JWT, the literal synthetic refresh-token
   fixture string, the literal `incorrect-horse-battery-1` string, and the literal
   `LOCAL_ANON_KEY` placeholder. Comment each entry with why it's not a real secret and
   which file it comes from. Do this first -- every later step that runs gitleaks
   against real repo history depends on this existing, or step 7's CI job starts red.

2. **`security/scripts/gitleaks-cli.mjs`** (new, shared helper, no CLI entry point of
   its own). Exports a `runGitleaks({ sourceDir, extraArgs })` function that shells out
   via `spawnSync` to `docker run --rm -v "<sourceDir>:/scan:ro" -v
   "<repoRoot>/.gitleaks.toml:/gitleaks.toml:ro"
   zricethezav/gitleaks@sha256:c00b6bd0aeb3071cbcb79009cb16a60dd9e0a7c60e2be9ab65d25e6bc8abbb7f
   detect --no-git --source=/scan --config=/gitleaks.toml --redact --exit-code=1
   <extraArgs>`, and returns `{ status, stdout }`. Centralize the pinned image digest
   here as a single named constant so it's updated in one place later.

3. **`security/scripts/check-bundle-secrets.mjs`** (new). Imports `buildExport` from
   `security/scripts/build-and-serve.mjs` (reuse, per the task notes -- don't
   reimplement the export invocation or its placeholder-env fallback), calls it to
   produce `dist/`, then calls `runGitleaks({ sourceDir: 'dist' })` from step 2 and
   exits with its status, printing its stdout (already `--redact`ed, so this is safe --
   never print unredacted gitleaks output anywhere in these scripts). Add a
   `"security:check-bundle-secrets"` script to `package.json` for local reuse.

4. **`security/accepted-dependency-advisories.json`** (new) -- the four `{ id, package,
   severity, reason, noPatchAsOf }` entries found above (image-size x2, nanoid, uuid),
   each reasoned as "Metro/bundler build-time devDependency, not shipped in the web
   bundle, no upstream patch available as of 2026-08-24 -- revisit on next Expo/Metro
   upgrade." Keep this as data, separate from script logic, so pruning it later doesn't
   require touching the script.

   **`security/scripts/check-dependency-audit.mjs`** (new). Runs `yarn audit --json`
   via `spawnSync`, parses the NDJSON output line-by-line, keeps only `type ===
   "auditAdvisory"` entries, filters to `severity` in `{high, critical}`, drops any
   whose `id` is in the accepted-advisories file, and fails (prints a table: package,
   severity, title, advisory URL, for every finding -- accepted or not, for
   visibility) if anything remains. This is not secret data, so no redaction concern
   here. Add a `"security:check-dependency-audit"` script to `package.json`.

5. **`security/scripts/verify-secret-detection.mjs`** (new, `node:test`-based, same
   style as `security/scripts/check-csp-headers.mjs`). Two independent `test()`
   blocks:
   - **History-style detection**: create a scratch temp directory, initialize it as a
     fresh, throwaway version-control repository, write a file containing a
     representative fake secret (reuse a Supabase-service-role-shaped fake JWT with a
     `"role":"service_role"` payload -- clearly synthetic signature, not a real key),
     commit it, run `runGitleaks` against it in history-scanning mode (no `--no-git`)
     and assert nonzero exit + a finding is reported; then assert a control scan taken
     before that commit (or of an empty scratch repo) exits 0, proving the assertion
     isn't vacuously true.
   - **Bundle-style detection**: copy a freshly-built `dist/` (via the same
     `buildExport()` reused in step 3) into a scratch dir, append the same fake secret
     string into one exported `.js` file, run `runGitleaks({ sourceDir: scratchDir })`
     and assert nonzero exit + a finding; assert the unmodified copy scans clean (exit
     0) as the control.
   Clean up scratch dirs in `t.after()`. Add a `"security:verify-secret-detection"`
   script (`node --test security/scripts/verify-secret-detection.mjs`) to
   `package.json`.

6. **`.github/workflows/ci.yml`**. Add workflow-level `permissions: contents: read`.
   Leave the existing `verify` job's `actions/checkout@v4`/`actions/setup-node@v4`
   as-is (out of scope, no functional need to touch it -- optionally note in the PR
   description that SHA-pinning those too would be a reasonable, low-risk follow-up
   for full consistency, but don't fold it into this ticket unprompted). Add four new
   jobs, each `runs-on: ubuntu-latest`:
   - `dependency-audit`: checkout (SHA-pinned `actions/checkout@11bd719...`),
     setup-node (SHA-pinned `actions/setup-node@39370e3...`, node 22, yarn cache),
     `yarn install --frozen-lockfile`, `node security/scripts/check-dependency-audit.mjs`.
   - `secret-scan`: checkout (SHA-pinned, `fetch-depth: 0` -- full history is the
     point), then `gitleaks/gitleaks-action@e0c47f4...` (v3.0.0) with `env:
     GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}`, `GITLEAKS_ENABLE_COMMENTS: "false"`.
     No `yarn install` needed -- this job never runs app code.
   - `bundle-secret-scan`: checkout (SHA-pinned), setup-node (SHA-pinned), `yarn
     install --frozen-lockfile`, `node security/scripts/check-bundle-secrets.mjs`.
   - `secret-scan-self-test`: checkout (SHA-pinned, default shallow depth is fine -- it
     never scans the real repo's history), setup-node (SHA-pinned), `yarn install
     --frozen-lockfile`, `node --test security/scripts/verify-secret-detection.mjs`.

7. **`security/README.md`** -- extend it (it already documents T162.1/T162.2; this is
   T162.3 in the same file, matching the existing single-handoff-doc convention). Add
   a new top section or subsection covering: what each of the four new checks does and
   why (mirroring the existing "Policy rationale" style); the `yarn audit --level`
   exit-code bug and why the gate is hand-rolled; the accepted-advisories file and its
   revisit trigger ("next Expo/Metro upgrade"); the `.gitleaks.toml` allowlist and why
   each entry is not a real secret; the documented gap that there's no Resend/SMTP-
   specific rule (nothing in-repo touches those secrets today); that all four new jobs
   run automatically on every PR/push per `ci.yml`'s existing triggers (unlike
   `security:check-headers`/`test:e2e:security`, which are documented as manual-only --
   call out this asymmetry explicitly so a future reader doesn't assume parity); and
   the local commands (`yarn security:check-dependency-audit`, `yarn
   security:check-bundle-secrets`, `yarn security:verify-secret-detection`), each
   noting the Docker requirement where applicable, following the existing "It requires
   Docker/the local Supabase stack, same as..." phrasing precedent already used for
   `test:db`.

8. **Local verification before pushing**: run the three new yarn scripts individually
   first (they need Docker running locally for the two that shell out to it), then run
   `node .claude/scripts/verify.mjs` (all four standard steps -- this task doesn't
   touch app code, but the new scripts under `security/scripts/` should still pass
   lint/tsc if they're `.mjs` plain JS consistent with the existing scripts in that
   directory, which aren't type-checked by `tsc --noEmit`'s `include`, so confirm
   that's still true rather than assuming). Then push the branch and open the PR -- the
   **actual GitHub Actions run on that PR is the authoritative evidence** for "CI
   passes on the clean repository" and "runs for pull requests... without gaining
   write permissions" (check the job's `permissions` in the Actions UI/logs, not just
   the YAML). The `secret-scan-self-test` job passing on that same PR run is the
   CI-observable evidence for "fails on representative committed-secret and
   generated-bundle fixtures in an isolated test."
