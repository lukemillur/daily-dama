# T085.3 -- Apply theme text color across post-onboarding screens

## Read first: the scope tension this plan resolves

The task Notes derived the file list from a grep across post-onboarding areas for
AppColors.red, AppColors.ink, AppColors.inkSoft, and AppColors.textMuted -- i.e. all four
fixed "text" tokens, not just AppColors.ink. Confirmed still current on development as of this
plan. That grep basis is much broader than what the task description's short example list
(Eyebrow/DisplayTitle/BodyText, SectionTitle/NextTrickName/NextTrickMeta) suggests literally,
and it matters for one reason.

resolveTheme()'s automatic text fallback (deriveAutomaticTextColor, confirmed by
use-resolved-theme.test.ts) resolves to exactly AppColors.ink when nothing is customized. So
converting any site that is already AppColors.ink to theme.text is byte-identical when unset --
the same guarantee T083.3 relied on for sage/yellow. But AppColors.red (eyebrows/labels, e.g.
Eyebrow itself) and AppColors.textMuted/AppColors.inkSoft (body/meta text) are not equal to ink,
so converting those sites to theme.text will visibly change today's unset rendering -- red
labels go ink-green, muted body copy goes solid ink-green. This is a real conflict with the exit
criterion "an unset theme renders identically to today's fixed colors" if read as pixel-exact.

This isn't a stale/blocking exit-criteria conflict (nothing external changed since scoping) --
it's a same-ticket internal tension between the description's explicit inclusion of Eyebrow
(currently red) and BodyText (currently textMuted), and the "identical" wording. Resolution,
consistent with how the parent ticket frames this (T085's Notes call the WCAG-gate removal "a
deliberate accessibility trade-off, made by the user ... not re-litigated here"): proceed with
converting Eyebrow/red-label text and BodyText/muted-body text to theme.text as the description
explicitly directs, since the Notes' grep basis deliberately included red and
textMuted/inkSoft alongside ink. Read "identical when unset" as "uses the same always-defined
fallback contract established by resolveTheme()" (true for every site, since text is always
well-defined, never undefined), not as "pixel-identical to every site's prior individual hex
value" (only literally true for the ink-colored sites). Flag this explicitly during in-browser
verification and in the completion report -- screenshot the red-label -> ink-label shift
specifically -- so it's a seen, documented product call rather than a silently-introduced
surprise, mirroring how T083.3 flagged its own eyebrow-on-accent contrast gap instead of
silently absorbing it. If this shift reads as a regression once seen in the browser, that's a
legitimate reason to stop and check with the user before proceeding further -- it's a judgment
call this plan makes on your behalf, not a certainty.

## In-scope / out-of-scope rule (apply per call site, not per file)

A color declaration on rendered text (styled.Text, styled(SomeTextComponent), or an inline
Text with a style prop) that resolves, on the "no theme set" path, to AppColors.ink,
AppColors.inkSoft, AppColors.textMuted, or AppColors.red is in scope -- replace with theme.text
(or the theme-driven prop-conditional branch, see below), unless it falls into one of these
exclusions, which stay fixed:

- Decorative surface: background-color / border / border-left-color / border-bottom-color using
  these tokens. Task scope is text color only (title/eyebrow/label/body text), not framing.
- Functional/state-conditional text: any branch of a prop-conditional that signals validity,
  success/failure, or a destructive action -- e.g. an "invalid" flag choosing between
  AppColors.red and a neutral color, a "beaten"/"met" outcome flag, ErrorText, DeleteActionText,
  RemoveText. Only the non-functional branch of such a conditional converts (the neutral-color
  branch becomes theme.text); the functional/red branch is explicitly protected by this task's
  own exit criteria ("functional colors (errors/success) are unaffected").
- Already-established exclusion from T083.3: ToggleMark's unselected branch in tricks/index.tsx
  and KindMark's equivalent in trick-goals-screen.tsx -- T083.3 already classified the
  unselected/red branch as functional (a selection-state indicator, not label content) and left
  it fixed. Don't re-litigate; leave as-is.
- Fixed contrast pairings: text colors paired with a fixed (non-theme) background, where the
  pairing only works because both sides are fixed together -- e.g. PlanChoiceCopy/
  ChallengeChoiceCopy in sesh.tsx (their "selected" branch is cream, their selected background
  is fixed ink, not theme-driven) and ToggleTitle/ToggleCopy/RankNumber's dark-text branch in
  tricks/index.tsx. Convert only the unselected branch, which sits on the plain page background
  and is theme-appropriate; leave the selected/dark-text branch fixed.
- UI chrome / action affordances, not content: single-glyph or short link/action text that
  functions as a control rather than title/eyebrow/label/body copy -- e.g. TextLink/StatsLink/
  NextTrickAction in daily-home.tsx, BackLink/CompactBackLink in stats/[trickId].tsx and the sesh
  entry files, ChoiceArrow/TypeArrow/StepActionText/RemoveText in sesh.tsx/tricks/index.tsx.
  Leave fixed. If a given site is genuinely ambiguous between "chrome" and "label content",
  default to leaving it fixed (under-converting is a cheap, easy follow-up; over-converting
  risks the "functional colors unaffected" guarantee).
- Hydration-fallback screens: user-profile-provider.tsx, practice-history-provider.tsx (both
  confirmed still present, AppColors.ink/AppColors.inkSoft at their StyleSheet.create hydration
  wordmark/message styles). Same non-goal as T083.3 and for the same reason -- these render
  before UserProfileProvider itself has hydrated, so there's no profile to resolve a theme from.
  Do not touch.
- Pre-onboarding-only files (kentei-onboarding.tsx and everything under
  src/features/onboarding/, except the two components already shared with post-onboarding per
  the invariant below) and access-gate-screen.tsx / sesh-sequence-sandbox.tsx (not
  post-onboarding, per T083.3's own disposition, still true).

## Missing type plumbing (do this first -- blocks everything else typechecking)

src/types/styled-components.d.ts's DefaultTheme currently only declares background and accent
(readonly string fields). T085.1 added text to ResolvedTheme/resolveTheme()/AppThemeProvider's
runtime value, but never updated this type declaration -- confirmed still missing on
development. Any theme.text reference in a styled-components template will fail
tsc --noEmit until this is fixed. Add a readonly text: string field to the interface. This must
land before touching any call site.

## Implementation order

1. Type fix: add text to DefaultTheme in src/types/styled-components.d.ts (above). Nothing else
   compiles cleanly without it.
2. src/components/ui/typography.tsx: convert Eyebrow (AppColors.red to theme.text), DisplayTitle
   (AppColors.ink to theme.text), BodyText (AppColors.textMuted to theme.text). This is the
   single highest-leverage change -- every styled(Eyebrow)/styled(DisplayTitle)/styled(BodyText)
   subclass across every screen inherits theme.text for free unless it locally re-declares color.
3. Strip redundant local color overrides on styled(Eyebrow|DisplayTitle|BodyText) subclasses that
   currently re-pin the same value the base component already had (now dead weight that silently
   defeats step 2). Confirmed present at minimum in: assessment-entry.tsx's Copy (color:
   AppColors.textMuted), multi-trick-sesh-entry.tsx's Copy (same), app/profile/index.tsx's Copy
   (same), stats/[trickId].tsx's SessionMeta (styled(BodyText) plus a color: AppColors.textMuted
   override), and daily-home.tsx's HeroCopy/UnavailableCopy (color: AppColors.inkSoft override).
   Re-grep each target file for styled(Eyebrow)/styled(DisplayTitle)/styled(BodyText) combined
   with a color override in the same block to catch any others -- this pattern is easy to miss by
   inspection alone since the override currently looks like intentional styling, not dead code.
4. src/components/ui/button.tsx: convert ButtonLabel's secondary-variant branch (above).
5. Per-screen sweep, each independent -- for every file below, re-run a grep for
   AppColors.red / AppColors.ink / AppColors.inkSoft / AppColors.textMuted against that file to
   get the current call sites (this plan's site names may drift), then apply the in-scope/
   out-of-scope rule above. Order doesn't matter between files; do them in the order listed in
   the task description for easiest cross-referencing.
6. Run the verification sequence (node .claude/scripts/verify.mjs) once all conversions are in.
7. In-browser verification (below).

Steps 1-4 must precede step 5 for the same reason T083.3's steps 1-4 preceded its 5-6: step 5
assumes a working theme.text contract and inherits automatically from the typography primitives
wherever no local override exists, so doing it first would mean re-editing everything a second
time once the primitives change underneath it.

## In-browser verification plan

Run the Expo web dev server; reload/navigate rather than relying on Fast Refresh for each check.

1. Unset theme renders identically for ink-family sites, visibly different for
   red/textMuted-family sites -- with no theme ever set, walk every enumerated screen and
   confirm: titles/names/values that were already AppColors.ink look unchanged; eyebrow-style
   small-caps labels that were AppColors.red now render in the same dark ink-green as titles (a
   real, expected color change -- confirm it reads as a deliberate unification, not a rendering
   bug, i.e. no two different text colors appear where the same component type is used); muted
   body copy that was AppColors.textMuted/inkSoft reads slightly darker/more saturated than
   before but still clearly distinguishable in weight/size from titles. Screenshot at least one
   screen (Home is enough) as the artifact for the completion report's callout of this change.
2. Saved custom theme's text color reflects everywhere -- from Profile, set a custom text color
   distinct from ink/cream (e.g. a deep purple) via ThemeColorPicker and confirm every converted
   site on every enumerated screen picks it up without a manual reload, including the ones
   sitting on an accent-colored surface (e.g. NextTrickButtonText, CelebrationBannerEyebrow) and
   distinguishing it from Button's primary-variant label, which stays theme.accent, not
   theme.text -- don't confuse the two.
3. Auto-derived case -- clear the custom text override (if ThemeColorPicker supports an
   auto/reset control) and set only background/accent to a dark pair; confirm text switches to
   cream automatically per deriveAutomaticTextColor, and every converted site reflects it.
4. Pre-onboarding stays yellow/fixed -- fresh onboarding flow (clear profile or incognito)
   renders with the fixed palette throughout regardless of a theme saved in a prior session,
   same reasoning and same caveat about restartOnboarding being dead code as documented in
   T083.3's plan -- re-confirm that invariant still holds (no UI now calls restartOnboarding)
   before relying on it for Eyebrow/Button being safely shared with onboarding.
5. Functional colors unaffected -- deliberately trigger an error/invalid state (e.g. an invalid
   duration in Sesh or Multi-trick Sesh entry, an invalid custom-trick form field) and confirm
   it's still the fixed AppColors.red, unaffected by any saved custom text color. Also check a
   beaten/met Sesh outcome banner and a delete/remove action's red text.
6. Re-check the 320px web nav width constraint (unaffected by a text-color-only change, but
   cheap to confirm) and that only the two known-benign console warnings appear.

## Risks / things to double-check before or during implementation

- The scope-tension discussed at the top is the main risk -- if the red-label-to-ink-label shift
  reads poorly in the browser, stop and flag it before continuing rather than pushing through;
  this plan makes a judgment call the user hasn't explicitly seen yet.
- The redundant-override pattern (step 3) is easy to miss because the override currently looks
  like deliberate styling rather than dead weight -- don't skip the re-grep for
  styled(Eyebrow|DisplayTitle|BodyText) plus a local color override across all ten files, not
  just the ones confirmed here.
- ResultBanner in sesh.tsx is the one site where converting only the text but not the
  (already-fixed, non-theme) surrounding background/border could look mismatched once an unusual
  custom text color is set against its fixed backgrounds -- verify by eye with a saturated
  custom text color, not just the default.
- PracticeAction in neglected-tricks-section.tsx and SearchResultAdd/ReferencedMeta/StepNumber
  in tricks/index.tsx are the label-vs-chrome judgment calls flagged inline above -- if any reads
  more like a button/action than a label once seen rendered, it's fine to leave it fixed and note
  the divergence from this plan in the PR description.
- trick-directory.tsx's raw-hex Title/Introduction colors are outside this task's literal file
  list and don't match any of the four target tokens -- don't proactively convert them, but don't
  be surprised if they look inconsistent once tricks/index.tsx's own header goes theme-reactive;
  that's a plausible T083.3-style follow-up ticket, not something to silently fold into this one.
- No existing jest test asserts rendered color values on any touched component (confirmed --
  only use-resolved-theme.test.ts and theme-color-picker.test.tsx reference AppColors in tests,
  neither renders the touched screens) -- yarn test --runInBand should be unaffected, but don't
  assume; run it rather than skip it.
