## Files to add/change, in order

### 1. `supabase/config.toml` (new -- generate, then edit)

Generate the scaffold first so the file matches the installed CLI's schema exactly, rather than hand-writing a toml that might drift from the CLI version:

```sh
npx --yes supabase init
```

This creates `supabase/config.toml`, `supabase/.gitignore`, and `supabase/.temp/` (ephemeral, already ignored). Then edit `config.toml`:

- `project_id`: replace the generated directory-derived value with a stable `"daily-dama"`. (The generated default is derived from the current working-directory name, which is worktree-specific garbage in an agent sandbox -- must be a fixed string so Docker container/volume names are stable across checkouts.)
- `[auth]`:
  - `site_url = "http://localhost:8081"` (matches the Expo web dev server's fixed port used elsewhere in this repo -- see `.claude/launch.json` and `TRICK_VIZ_HANDOFF.md`'s port note; do not use `127.0.0.1`, since the callback origin must match the browser origin the app actually serves).
  - `additional_redirect_urls = ["http://localhost:8081/auth/callback"]` -- replace the generated placeholder entries (`https://127.0.0.1:3000` etc.) entirely; this is the *only* local redirect this ticket authorizes. Do not add the production `https://dailydama.com/auth/callback` here -- that belongs to the hosted project config in T153.2, not the local CLI config.
  - `jwt_expiry = 3600` -- already the CLI default, but set it explicitly (not left as an implicit default) with a comment noting it's a deliberate one-hour policy decision from `BACKEND_ROADMAP.md`, so a future CLI default change can't silently drift local policy.
  - `minimum_password_length = 10` (default is 6).
- `[auth.email]`:
  - `enable_confirmations = true` (default is `false`) -- this is what makes an unverified user's sign-in fail; without it every signup is auto-confirmed and the "unverified user cannot sign in" exit criterion is untestable.
  - Leave `double_confirm_changes`, `secure_password_change`, `max_frequency`, `otp_length`, `otp_expiry` at their generated defaults -- those belong to T154.1's secure email/password-change work, not this ticket (per T153.2's note: "Secure email change belongs to T154.1").
- `[auth.email.template.confirmation]` (new block, not present in the generated scaffold by default):
  ```toml
  [auth.email.template.confirmation]
  subject = "Confirm your Daily Dama account"
  content_path = "./supabase/templates/confirmation.html"
  ```
  Confirmed against the CLI's own source (`packages/config/src/auth/email.ts`, `apps/cli-go/pkg/config/auth.go`) that `confirmation` is the exact recognized template key for the signup-confirmation email (as opposed to `invite`, `recovery`, `magic_link`, `email_change`, `reauthentication`). `content_path` resolves relative to the **repository root** (the parent of `supabase/`), not relative to `supabase/` itself -- confirmed in the CLI source's path-resolution comment -- so `./supabase/templates/confirmation.html` is correct, not `./templates/confirmation.html`.
- Leave `[api]`, `[db]`, `[studio]`, `[local_smtp]` (Mailpit, port 54324, already `enabled = true` by default), `[storage]`, etc. at generated defaults. This ticket only needs Auth policy + email delivery; don't hand-tune unrelated ports/services.

Do this step first: the template file and the README both reference the config's callback URL and template path, so get the config settled before writing prose or HTML that describes it.

### 2. `supabase/templates/confirmation.html` (new)

A minimal, repository-owned branded template -- not Supabase's built-in copy -- so the "repository-owned confirmation email" exit criterion is satisfiable. Use Go's html/template variables that GoTrue populates for confirmation emails: `{{ .ConfirmationURL }}` is the one that matters (it already carries the `redirect_to`/`next` parameter GoTrue got from the client's `emailRedirectTo`, so the template itself does not need to hardcode `localhost:8081` -- the redirect target is a runtime value, not a template-time constant). Keep it small:
- Daily Dama branding/name in the subject and body copy (already distinct from Supabase's generic "Confirm your signup" default).
- A single visible link/button using `{{ .ConfirmationURL }}`.
- No inline `{{ .SiteURL }}`-only fallback links that bypass the confirmation flow.

This is prototype-facing local dev tooling, not a production transactional email -- keep styling simple (inline styles, no external assets) rather than building a full email design system now.

### 5. `supabase/README.md` (new) -- the documented workflow

This is the "smallest documented workflow" the exit criteria require. Contents, in order:

1. **Prerequisites**: Docker Desktop (or Colima/OrbStack) running; Supabase CLI via `npx supabase@<pinned version>` or a global install. State the CLI version this config was authored/tested against (record whatever version is actually used when this is implemented -- pin it in prose so "reproducible" doesn't silently drift).
2. **First-time / clean-reset workflow**:
   ```sh
   npx supabase start      # boots Postgres, GoTrue, Mailpit, Studio, etc.
   npx supabase db reset   # clean local database reset (re-applies migrations/seed)
   npx supabase status     # prints local API URL, anon key, service_role key, Studio/Mailpit URLs
   ```
3. **Never commit output of `supabase status`.** If you save the printed anon/service keys anywhere for manual testing, put them in `.env.local` at the repo root (already gitignored) -- never in `.env.example` or any tracked file.
4. **Manual verification of the three behavioral exit criteria** (no frontend exists yet -- T153.4+ builds the client -- so drive GoTrue's REST API directly with curl, using the anon key from `supabase status` as the apikey header):
   - **Nine-character signup rejected**: POST to `http://127.0.0.1:54321/auth/v1/signup` with headers `apikey: LOCAL_ANON_KEY` and `Content-Type: application/json`, body `{"email":"test@example.com","password":"ninechar1","options":{"emailRedirectTo":"http://localhost:8081/auth/callback"}}`. Expect a 4xx rejection citing the 10-character minimum.
   - **Unverified user cannot sign in**: repeat signup with a 10+ character password (confirmation email goes to Mailpit, account stays unconfirmed), then POST to `http://127.0.0.1:54321/auth/v1/token?grant_type=password` with the same apikey header, body `{"email":"test@example.com","password":"tencharacters"}`. Expect a 400 "Email not confirmed" (or equivalent) rather than a session.
   - **Mailpit receives the repository-owned email targeting the exact callback**: open `http://127.0.0.1:54324`, find the confirmation email, confirm (a) the subject/body match `supabase/templates/confirmation.html` (not Supabase's generic default copy) and (b) the confirmation link's redirect_to (or next) query parameter is exactly `http://localhost:8081/auth/callback`, not a substring/prefix match and not silently falling back to site_url.
5. **Note on host consistency**: use `localhost:8081` (not `127.0.0.1:8081`) everywhere in this workflow, matching `additional_redirect_urls`, because browsers treat these as different origins for storage/PKCE purposes; a mismatch here is the single most likely way to silently break the callback and waste time debugging what looks like a config bug.
6. Cross-reference this file from `AGENTS.md`'s "Feature-specific handoffs" list with one line, consistent with the existing pattern for `TRICK_VIZ_HANDOFF.md` and `DEPLOYMENT_HANDOFF.md`.

## Risks / non-obvious pitfalls for the implementer

- **content_path is root-relative, not supabase/-relative.** Get this wrong and `supabase start`/`db reset` will fail to find the template file with a config error, not silently ignore it.
- **enable_confirmations defaults to false.** Forgetting this flag makes every signup auto-verified, silently defeating the "unverified user cannot sign in" exit criterion while everything else looks configured correctly.
- **localhost vs 127.0.0.1** must be picked once and used consistently across site_url, additional_redirect_urls, and the app dev server. The task fixes this to `http://localhost:8081/auth/callback`; don't let Studio's default 127.0.0.1 API URL bleed into the callback/site config by copy-paste.
- **This ticket does not touch the hosted project.** T153.2 mirrors this same policy remotely; don't pre-emptively add the production callback or hosted secrets here -- scope creep into T153.2's territory.
- **No Docker in this planning sandbox.** If the implementer's actual environment also lacks Docker, the live exit criteria cannot be completed in that environment at all -- this is a real blocker to closing the ticket, not a formality, and should be reported rather than worked around with static-only checks.
