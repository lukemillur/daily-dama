# T252 — Onboarding-aware guest/back-to-app button on Sign up and Sign in

## Confirmed gap and resolution (per Notes)

`useCachedOnboardingStatus()` only reads the guest-scoped profile key (see
`src/features/landing/state/use-cached-onboarding-status.ts`), so it is blind to a signed-in
user's onboarding state. `landing-cta.tsx` already solved exactly this gap for T242/T243:

```ts
const isReturning = authState.status === 'authenticated' || hasCompletedOnboarding;
```

The comment above it in `landing-cta.tsx` explains why: an `authenticated` session is itself
sufficient proof of a returning visitor, `initializing` deliberately does not count (so the
prerendered/first-client render matches today's output). This task reuses that exact rule, so
the "signed-in user reaching these screens" gap flagged in the Notes is already answered — no
new handling needed beyond applying the same `status === 'authenticated' || hasCompletedOnboarding`
check on these two screens.

## Design decision: shared helper vs. inline duplication

Both sign-in-screen.tsx and sign-up-screen.tsx need the identical boolean rule and the
identical label mapping ("Continue as guest" / "Back to app"). Inlining it separately in both
screens would mean the authState.status === 'authenticated' || hasCompletedOnboarding rule now
exists in three call sites (landing-cta.tsx plus these two) with no shared kernel -- worth
avoiding per AGENTS.md repetition guidance now that a third consumer exists.

Add one small pure function, not a hook (both screens already call useAuthState() and would
need useCachedOnboardingStatus() too -- no benefit to hiding those two hook calls behind a
third):

- New file: src/features/auth/model/guest-back-button.ts

  import type { AuthState } from "@/features/auth/model/auth-state";

  export function resolveGuestBackButtonLabel(
    authStatus: AuthState["status"],
    hasCompletedOnboarding: boolean,
  ): "Continue as guest" | "Back to app" {
    const isReturning = authStatus === 'authenticated' || hasCompletedOnboarding;
    return isReturning ? "Back to app" : "Continue as guest";
  }

  Check the actual exported type name/shape for AuthState status field in
  src/features/auth/model/auth-state.ts before writing the signature -- use whatever the file
  already exports (do not invent a new union type). If AuthState["status"] does not resolve
  cleanly as a standalone type reference, accept the full AuthState and read .status inside
  the function instead of trying to extract a narrower type.
- Do NOT touch landing-cta.tsx in this task -- it has its own copy/variant model (CtaCopy,
  sage/yellow theming, "Start your first Sesh"/"Back to practice" strings) that is a different
  shape from a single button label. Refactoring it to consume the new helper is optional
  follow-up cleanup, not required by this task exit criteria; leave a note in the PR
  description if deferring it, but do not fold it into this change.
- Add a co-located unit test src/features/auth/model/guest-back-button.test.ts covering the
  combinations relevant to the boolean truth table (at minimum: guest+incomplete -> guest label,
  guest+complete -> back label, authenticated+incomplete -> back label, authenticated+complete ->
  back label, initializing+incomplete -> guest label).

## Risks / non-obvious things to watch

- Do not accidentally change accessibilityLabel semantics elsewhere: every other button on
  both screens uses a static accessibilityLabel matching its static visible text exactly
  (e.g. "Sign up", "Forgot password?"). Keep that same 1:1 pattern for the new dynamic
  label -- accessibilityLabel={guestButtonLabel} with {guestButtonLabel} as the children --
  rather than leaving a stale static accessibilityLabel="Continue as guest" while the
  visible text changes.
- useCachedOnboardingStatus() reads synchronously on web only after a useSyncExternalStore
  hydration gate; before that gate resolves it always returns the DEFAULT_STATUS
  (hasCompletedOnboarding: false). This matches the existing landing-cta.tsx behavior (a
  brief first-time-copy flash is already accepted there for the equivalent copy) -- no new
  handling needed, but do not be surprised if a naive first-paint assertion in a test needs
  the same act(async () => ...) mount pattern the existing test suites already use to get
  past that gate.
- Sign-up screen authenticated/initializing early-return branch is identical in shape to
  sign-in own; verify it still shows only the loading copy (no guest button) in both states
  -- this should fall out for free since the new button lives in the same return block as
  the rest of FormActions, after that early return.
- Confirm the exact type name/shape exported for AuthState status field from
  src/features/auth/model/auth-state.ts before writing guest-back-button.ts signature.
