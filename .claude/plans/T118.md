# T118 — Kendama hero banner on the landing page

## Decision: build a static in-house SVG illustration, not trick-viz reuse

`src/features/trick-viz/` is a `@react-three/fiber` WebGL scene (`TrickScene.tsx`) built
around a keyframed `Trick` timeline model, verlet string simulation, and a `Canvas`. It exists
to *animate* a specific trick, not to render a static decorative graphic, and pulling it into
the landing page would add a WebGL dependency, camera/lighting setup, and a fake/idle "trick"
just to get a still image — heavyweight and risky for a first-impression page. `react-native-svg`
(15.15.4) is already a project dependency and already used outside trick-viz
(`src/features/profile/components/color-spectrum-picker.tsx`), confirmed to work through
`yarn expo export --platform web`. Build the hero as a hand-drawn SVG icon in the app's existing
sticker-card visual language (ink-outlined shapes, flat `AppColors`, hard-offset `boxShadow`
panels — see `landing-cta.tsx` and `trick-card.tsx`), not sourced external imagery. This avoids
T119-style licensing concerns entirely since nothing is sourced.

## Ordering decision

Task text says the banner goes "above the existing `Eyebrow`/`Headline`/`Lede` text stack."
Place it as the very first child of `Content` in `landing-page.tsx`, before `<Eyebrow>`. This
keeps the CTA (`<LandingCta />`) exactly where T114 left it — after `<Lede>`, before
`<FeatureList>` — so the existing ordering test (`renders the CTA before the feature-list
content in document order`) is untouched. Resulting order: **Hero banner -> Eyebrow -> Headline
-> Lede -> CTA -> Features -> Screenshots -> Closing.** This reads as: show the visual hook
first, then the pitch, then the action, which is a defensible and simple choice — flag it to
the user as a default rather than a forced one, since T114/T118 don't mandate it, but implement
it as the default unless corrected.

Keep the hero inside the existing `Content` wrapper (`max-width: 620px`, centered, existing
horizontal padding) rather than going full-bleed above it. Exit criteria only requires the
banner to render above the headline stack and be visible pre-scroll on both viewport widths —
it does not require full-bleed treatment, and `Content`'s padding/max-width already produces
correct mobile and desktop behavior for every other element on this page. Full-bleed would need
new layout plumbing (breaking out of `Content`'s padding inside a `ScrollView`) for no
exit-criteria benefit; treat it as out of scope for this iteration.

## Files to add/change

1. **New file: `src/features/landing/components/landing-hero.tsx`** — new `LandingHero`
   component, exported for direct import (mirrors how `LandingCta` is structured/imported).

   - Outer wrapper: a sticker panel matching the established language — `styled.View` (plain
     `View` is fine; no entrance-animation requirement in the exit criteria, so `Animated.View`
     is optional polish, not required) with `border: 2px solid ${AppColors.ink}`,
     `border-radius: ${Radii.panel}px`, a background fill (e.g. `AppColors.sage` or
     `AppColors.paperStrong` — pick whichever reads better against the yellow/red SVG accents),
     and the same hard-offset `boxShadow` pattern used by `CtaPanel`/`ScreenshotItem`: pass
     `style={{ boxShadow: '8px 8px 0 ' + AppColors.ink }}` as an explicit JSX `style` prop (not
     via `.attrs`), per the documented reasoning already in `landing-cta.tsx` — don't
     rediscover this by trial and error, reuse the existing comment/approach.
   - Give the outer wrapper `testID="landing-hero"` — this is what the new test asserts on.
     Also set `accessibilityRole="image"` and an `accessibilityLabel` (e.g. "Illustration of a
     kendama") on the SVG or its wrapper so the banner is announced sensibly, consistent with
     `alt`/`accessibilityLabel` handling already used for the screenshots in this file.
   - Inside: an `<Svg>` (`react-native-svg`) with a fixed `viewBox` (e.g. `0 0 240 240`) and
     `style={{ width: '100%', aspectRatio: 1 }}` (or similar) so it scales responsively at both
     mobile and desktop widths the same way the screenshot images already do
     (`style={{ width: '100%', aspectRatio: screenshot.aspectRatio }}` in `landing-page.tsx`).
   - SVG content — a simplified, recognizable kendama silhouette built from primitives (not
     freehand path coordinates that are hard to verify without visual feedback):
     - **Tama (ball):** `Circle` (e.g. `cx=120 cy=70 r=52`), `fill={AppColors.yellow}`,
       `stroke={AppColors.ink}` `strokeWidth={6}`. A smaller concentric `Circle`
       (`r~10`, `fill={AppColors.paperStrong}`, same ink stroke) for the ball's hole.
     - **String:** a `Path` with a gentle S-curve (`stroke={AppColors.ink}`, `fill="none"`,
       `strokeWidth={4}`, `strokeLinecap="round"`) connecting the hole to the ken's spike.
     - **Ken:** a simplified cross/T silhouette (spike + crossguard with big/base/small cups) —
       build from a couple of `Rect`/`Path` primitives with `rx` rounding rather than trying to
       reproduce exact kendama proportions; this is a decorative sticker icon, not the
       geometry-accurate trick-viz model, so "recognizably kendama-shaped" is the bar, not
       measured accuracy.
     - Optional decorative touches consistent with existing motifs: a faint oversized shape or
       a couple of small "motion" marks (compare `CtaMotif`'s giant translucent bullet-glyph in
       `landing-cta.tsx`) to add energy without competing with the ball/ken silhouette.
   - **This SVG must be iterated on visually** — run `yarn expo start --web` (or the dev server)
     and eyeball it at both a mobile width (~375px) and a desktop width (~1280px) before
     considering this file done. The coordinates above are a reasonable starting sketch, not a
     spec to copy blindly; adjust proportions/colors by looking at the rendered result.

## Risks / non-obvious notes

- The riskiest part is purely visual (does the SVG actually read as "kendama" at a glance) and
  cannot be verified from static code reading alone — budget time for a couple of rounds of
  visual iteration against the dev server rather than shipping the first coordinate sketch.
- Don't let the hero's decorative background shape (if any) get clipped oddly by the panel's
  `overflow: hidden`/border-radius the way `CtaMotif` is deliberately clipped by `CtaPanel`'s
  `overflow: hidden` — if adding a similar giant background motif, copy that established pattern
  rather than fighting it.
- Keep the SVG's `viewBox` square (or matched to a fixed aspect ratio) and size purely via the
  wrapper's `style={{ width: '100%', aspectRatio }}`, matching how the screenshot images already
  scale responsively — don't hardcode pixel width/height on `<Svg>` itself, which would break
  responsiveness at the mobile/desktop breakpoint this task must support.
- `landing-cta.test.tsx` and the rest of `landing-page.test.tsx`'s existing assertions (CTA
  ordering, screenshot sets) must keep passing unchanged — this task only adds content above the
  existing stack, it doesn't restructure `FEATURES`/`SCREENSHOT_CONTENT`/screenshot logic.
