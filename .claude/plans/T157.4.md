# T157.4 — Synchronize profile and trick state first

## Scope boundary (read first)

This is the first domain wired end-to-end and genuinely the largest task in the
T157 chain so far. Read the whole plan before starting; several design
decisions below only make sense together.

**In scope:** real pull+push synchronization for the `profile` `SyncDomain`
(both `api.profiles` scalar fields and `api.user_trick_states` rows — "trick
state" in the task title means trick selection/unlock flags, **not**
`custom_tricks`, which is a separate domain owned by T157.5), wired into
`UserProfileProvider` additively, with a real Supabase adapter satisfying
(most of) `SyncTransportRepository<Row>`, a durable per-domain outbox/envelope,
idempotent retries, revision-guarded pushes, and parked (not auto-resolved)
conflicts.

**Explicitly out of scope, deferred to named later tickets — do not build
these now:**
- Dispatching into the shared `syncCoordinatorReducer` (`src/shared/sync/coordinator.ts`).
  Read that file's own header comment: it is one **global**, cross-domain
  state machine — a run only reaches `idle` again once **all five**
  `SYNC_DOMAINS` report `domainSettled`. Since only `profile` is wired today
  (customTricks/practiceHistory/goals/notes aren't until T157.5–T157.8), any
  run dispatched into that reducer right now would never complete. T157.9
  ("Depends on T157.4–T157.8") is explicitly the ticket that builds the
  driver hook wrapping this reducer once every domain exists. This task
  instead builds a **profile-domain-local sync driver** whose outcome value
  is already shaped like `DomainSyncRecord`/`DomainSyncOutcome` (reusing
  those exact types), so T157.9 can plug it in later with no reshaping.
- Debounced/coalesced login/foreground/reconnect/manual triggers — that's
  T157.9's job too ("Wire login, foreground, local mutation, reconnection,
  and manual-retry triggers into the coordinator with debouncing/coalescing").
  This task provides one simple, direct trigger (auto-run once per identity
  generation after hydration, for signed-in users only) plus a manually
  callable `runSync`, both sufficient to exercise every exit criterion, but
  no real browser online/offline listener and no debouncing.
- Any visible conflict UI or automatic last-write-wins resolution. T160.2 is
  explicit: **"No automatic last-write-wins option"** for profile (named
  alongside custom-trick/goal/note conflicts). A push that comes back
  `'conflict'` must be recorded and left pending (parked), never silently
  overwritten in either direction, and must never block other records'
  operations. T160.1/T160.2 build the user-facing status/resolution UI later.
- Modifying `src/shared/supabase/*-cloud-repository.ts` files or their
  contracts. T157.3's plan already decided real revision-guarded/idempotent
  push logic lives in a separate adapter satisfying `SyncTransportRepository`,
  not bolted onto the T155.9 repositories. Follow that precedent.

If, having read this, the reviewer decides even this slice is too large for
one pass, the next-narrowest defensible cut is "push only, defer pull" — but
per the exit criteria (which requires both directions plus revision
resolution) that cut is not taken here; the design below keeps pull and push
each individually small.

## Key finding: what the real repository already gives you for free

Read `src/features/profile/persistence/profile-cloud-repository.ts` and
`supabase/migrations/20260822210000_protect_server_owned_timestamps_and_ownership.sql`
closely before writing the adapter.

1. **Idempotent upserts already work, for free, keyed on the row's own
   natural PK** — `upsertProfile`/`upsertTrickState` already do
   insert-first, then update-on-`23505` conflict, keyed on `user_id` (and
   `user_id`+`trick_id`). Because this task always uses a **stable
   `recordId`** (the user's own `userId` for the scalar profile row; the
   `trickId` for a trick-state row — see below), retries of the *same*
   local outbox operation naturally land on the same row every time. No new
   idempotency ledger is needed the way `transport.test.ts`'s fake needed
   one keyed on `operationId` — the DB's own unique constraint is the
   idempotency key here. This directly answers the task's own framing
   question: yes, build a shim on top of T155.9's real client, not new
   idempotency machinery.
2. **Revision is server-owned and blindly bumped on every `UPDATE`** (see
   `enforce_profile_mutation_invariants`/`enforce_user_trick_state_mutation_invariants`
   in the migration above) — `revision := old.revision + 1` unconditionally.
   There is **no built-in optimistic-concurrency guard** in the existing
   repository methods (`upsertProfile`, `upsertTrickState`, `deleteTrickState`
   all omit any `.eq('revision', …)` filter). But nothing stops **this
   task's adapter** from adding that filter itself: `revision` is a plain,
   `SELECT`-able, `UPDATE`-filterable column (RLS scopes rows by
   `user_id = auth.uid()`, not by column value), so
   `.update(patch).eq('user_id', userId).eq('revision', expected)` is a
   legal Postgrest call today. Zero rows matched is the observable "stale
   revision" signal — Postgrest with `.single()` reports that as `PGRST116`
   (already classified `'notFound'` by `mapPostgrestError`); the adapter
   must catch that specific case in the revision-guarded branch and turn it
   into `SyncTransportPushResult.status === 'conflict'` (fetching current
   server state to report `serverRevision`), not surface it as a generic
   `'failed'`.

So: build one new adapter file per profile-domain that does its own
Postgrest calls (reusing `mapPostgrestError`/`mapNetworkError` and the row
types already exported from `profile-cloud-repository.ts`), rather than
inventing a parallel outbox-idempotency mechanism.

## Data model additions (all new files/exports — nothing existing changes shape)

**`UserProfile`, `userProfileReducer`, `loadUserProfile`/`saveUserProfile`,
`USER_PROFILE_STORAGE_KEY` stay completely unchanged.** The primary
`useIdentityScopedDomain({ reducer: userProfileReducer, ... })` call in
`UserProfileProvider` is untouched — this is the literal mechanism for
"preserving current reducer authority... and local offline writes." Every
`useUserProfile()`/`useUserProfileActions()` consumer in the app keeps
working exactly as today, synchronously, offline-first, with zero awareness
that sync exists.

Sync bookkeeping lives in a **second, parallel** identity-scoped domain
instance, driven by a second `useIdentityScopedDomain` call inside (or
alongside) `UserProfileProvider`, whose `State` is a `SyncEnvelope<ProfileSyncSnapshot>`
— not `UserProfile` itself:

```ts
// src/features/profile/persistence/profile-sync-envelope.ts
export interface ProfileSyncSnapshot {
  readonly profile: UserProfile;                          // mirror of the primary reducer's state
                                                            // at the moment of the last envelope mutation
  readonly profileRevision: number | null;                 // last known server revision, profiles row
  readonly trickStateRevisions: Readonly<Record<string, number>>; // trickId -> last known server revision
}
```

- `isProfileSyncSnapshot(value): value is ProfileSyncSnapshot` — the
  `SyncEnvelopeCodec<ProfileSyncSnapshot>.isState` predicate.  Reuses the
  same field validators `user-profile-persistence.ts` already exports
  (`isKenteiRank`, `isLastSesh`, `isStreakThresholdMs`, plus
  `isValidThemeHexColor` from the model file). **Small prerequisite edit:**
  export `parseUserProfile` (currently private) from
  `user-profile-persistence.ts` so this file can validate the embedded
  `profile` field without duplicating ~60 lines of shape-checking. Purely
  additive (`export function` instead of `function`) — no behavior change,
  safe to do first.
- `createInitialProfileSyncSnapshot(profile: UserProfile): ProfileSyncSnapshot`
  → `{ profile, profileRevision: null, trickStateRevisions: {} }`.
- `PROFILE_SYNC_ENVELOPE_STORAGE_KEY = 'daily-dama:profile-sync-envelope'`.
- `loadProfileSyncEnvelope`/`saveProfileSyncEnvelope` — thin wrappers around
  `loadSyncEnvelope`/`saveSyncEnvelope` (`src/shared/sync/sync-envelope.ts`)
  with `domain: 'profile'` baked in.
- A tiny **pure reducer** so this can plug into `useIdentityScopedDomain`
  exactly like the primary domain does:

  ```ts
  export type ProfileSyncEnvelopeAction =
    | { type: 'envelopeRestored'; envelope: SyncEnvelope<ProfileSyncSnapshot> }
    | {
        type: 'localMutationApplied';
        identity: Identity;
        now: number;
        nextSnapshot: ProfileSyncSnapshot;         // pre-computed by the caller (pure diff, see below)
        operationInputs: readonly NewOutboxOperationInput[]; // 0..N, already deduped/coalesced by caller
        operationIds: readonly string[];           // one per operationInput, pre-generated by the caller
                                                    // (no Math.random()/Date.now() inside this reducer)
      }
    | { type: 'operationAcknowledged'; identity: Identity; operationId: string }
    | {
        type: 'operationAttemptRecorded';
        identity: Identity;
        operationId: string;
        attemptedAt: number;
        errorMessage: string | null;
      }
    | { type: 'revisionRecorded'; snapshot: ProfileSyncSnapshot } // after a successful push or a safe pull-adopt
    | { type: 'cursorUpdated'; identity: Identity; cursor: string | null; updatedAt: number };
  ```

  Implementation is a thin dispatcher onto `applyLocalMutation` /
  `acknowledgeOutboxOperation` / `recordOutboxOperationAttempt` /
  `updateSyncCursor`, folding multiple `operationInputs` in
  `localMutationApplied` sequentially via the **new** coalescing helper
  below, and treating every `status: 'rejected'` result as a no-op (return
  state unchanged) — matching how other reducers in this codebase treat
  invalid transitions.

- **One small, additive change to the shared `sync-envelope.ts`:** add
  `replacePendingOperationForRecord(envelope, identity, recordId, operationInput, createdAt, operationId?)`.
  Reason: a burst of rapid local edits to the *same* record (e.g. toggling
  one trick's selection on/off repeatedly offline) must not pile up N
  distinct pending outbox operations for that `recordId` — `applyLocalMutation`
  always **appends**. Without coalescing, `getExpectedRevision` (below)
  would need mid-batch mutation to stay correct across ops for the same
  record within one `pushOutboxOperations` call, which the transport
  contract doesn't support. Coalescing to "at most one pending operation per
  `(domain, recordId)`" sidesteps that entirely: remove any existing pending
  entry for `recordId` first, then append the fresh one (same identity/domain
  guards as `applyLocalMutation`). This is a generically useful primitive —
  future domains (T157.5–T157.8) will hit the same rapid-edit case — so it
  belongs in the shared file, not duplicated per-domain. Add unit tests to
  `sync-envelope.test.ts` for: coalescing replaces (not appends) a pending
  entry for the same recordId; a *different* recordId still appends
  normally; identity/domain mismatch still rejects.

## The pure diff: UserProfile change → outbox operations

New exports in `src/features/profile/persistence/profile-cloud-mapping.ts`
(same file that already owns `mapUserProfileToProfileUpsertInput`/
`mapUserProfileToTrickStateUpsertInputs` — this completes what its own
header comment already flagged as deferred: "does NOT compute deletions...
that diff belongs to the future sync layer"):

```ts
export function diffProfileForOutboxOperations(
  previous: UserProfile,
  next: UserProfile,
  userId: string,
): readonly NewOutboxOperationInput[]
```

- Compare `ProfileScalarFields` (the existing exported type — everything but
  the two trick-id arrays) by value; if changed, emit one
  `{ domain: 'profile', operationType: 'upsert', recordId: userId, payload: mapUserProfileToProfileUpsertInput(next, userId) as unknown as Record<string, unknown> }`.
  **`userId` is the `recordId`** for the scalar row — this is what lets the
  push adapter route "is this the profile row or a trick-state row?" by a
  single `request.recordId === userId` check with no ambiguity (`userId` is
  always a UUID per `isValidVerifiedUserId`; standard trick ids and custom
  trick ids — `custom-<...>` — are never UUID-shaped, confirmed by reading
  `createCustomTrickId` and the Kentei catalog's id scheme).
- Diff `mapUserProfileToTrickStateUpsertInputs(previous, userId)` vs
  `...( next, userId)` as maps keyed by `trick_id`: a trick id whose
  `(is_selected, is_manually_unlocked)` pair is new or changed emits an
  `upsert` op (`recordId: trickId`); a trick id present in `previous` but
  absent from `next` emits a `delete` op (`recordId: trickId, payload: null`).
- Add unit tests in `profile-cloud-mapping.test.ts`: no-op diff when nothing
  relevant changed; scalar-only change; trick added/removed/flag-changed;
  a batch covering several trick ids at once, asserting emitted op count and
  shape, and asserting op order is stable (scalar op, if any, first, then
  trick ops in a deterministic order) purely so downstream tests are not
  flaky — order otherwise has no semantic meaning within one diff call since
  each op targets a distinct `recordId`.

## The adapter: `SyncTransportRepository` over the real client

New file `src/features/profile/persistence/profile-sync-transport.ts`.
Constructed the same way `createProfileCloudRepository` is —
`createProfileSyncTransportAdapter(client: SupabaseClient<Database, 'api'>, userId: string)`.

**Pull** — two separate methods, *not* one generic `pull` (the domain spans
two tables with two independent Row types; forcing them through one
`SyncTransportRepository<Row>.pull` would need a discriminated-union Row for
no benefit):

- `pullProfileRow(): Promise<SyncTransportPullResult<ProfileRow>>` — the
  existing `createProfileCloudRepository(client).getProfile()` already
  returns a `CloudReadResult<ProfileRow>` whose shape (`{status:'succeeded', page:{items,nextCursor}} | {status:'failed', error}`)
  is structurally identical to `SyncTransportPullResult<ProfileRow>`. Reuse
  it directly (no reimplementation) via a one-line delegating wrapper.
- `pullTrickStatePage(request: CloudPageRequest): Promise<SyncTransportPullResult<UserTrickStateRow>>`
  — same reasoning: `listTrickStates(request)`'s existing signature and
  return shape already satisfy `SyncTransportRepository<UserTrickStateRow>['pull']`
  verbatim. Pass it straight into `pullAllPages` from `transport.ts` — no
  new pagination logic needed at all.

**Push** — the one method that's actually new logic, satisfying
`SyncTransportRepository<ProfileRow | UserTrickStateRow>['push']`:

```ts
push(request: SyncPushRequest): Promise<SyncTransportPushResult<ProfileRow | UserTrickStateRow>>
```

Routes on `request.recordId === userId` (profile-scalar branch) vs anything
else (trick-state branch, `recordId` is the `trick_id`). Before touching
either branch, defensively re-validate `request.payload` (it round-tripped
through AsyncStorage JSON — treat as `unknown` at this boundary, same
philosophy as `profile-cloud-mapping.ts`'s row-mapping functions) and return
a `'failed'`/`kind: 'validation'` `CloudRepositoryError` on a malformed
payload rather than throwing.

*Profile-scalar branch* (`operationType` must be `'upsert'` — this domain
never deletes the whole profile row; that's account deletion, T161.5, out of
scope):
- `expectedRevision === null` (never observed a revision — first-ever push,
  or a device that never pulled): `insert`, and on `23505` fall back to a
  **blind** `update` (no revision filter) exactly like today's
  `upsertProfile()` already does. This is a deliberate, explicitly accepted
  limitation, not new scope: a device that has never pulled has no revision
  to guard against, and this exactly matches the *existing*, already-shipped
  repository's unconditional-overwrite behavior for that one branch. Flag
  this plainly in code comments so a future reader doesn't mistake it for
  an oversight.
- `expectedRevision !== null`: `update(patch).eq('user_id', userId).eq('revision', expectedRevision).select('*').single()`.
  A returned row ⇒ `'succeeded'`. `PGRST116` (0 rows matched) ⇒ re-fetch via
  `pullProfileRow()` to learn the current `serverRevision`, then return
  `{status:'conflict', conflict:{operationId, recordId: userId, expectedRevision, serverRevision}}`.
  Any other Postgrest/network error ⇒ `'failed'` via the existing mappers.

*Trick-state branch:*
- `operationType === 'delete'`: if `expectedRevision === null`, delete
  unconditionally (`.eq('user_id', userId).eq('trick_id', recordId)`); if
  it matches 0 rows, that's a **success** (idempotent no-op — the row was
  never created server-side, e.g. an offline select-then-deselect before
  ever syncing; deleting something that never existed is not a conflict).
  If `expectedRevision !== null`, delete with an added
  `.eq('revision', expectedRevision)`; on 0 rows matched, re-fetch the row
  by `(user_id, trick_id)`: if it's genuinely gone ⇒ `'succeeded'` (already
  deleted by an earlier attempt — idempotent retry, not a conflict); if it
  still exists at a different revision ⇒ `'conflict'`.
- `operationType === 'upsert'`: same insert-then-conditional-update pattern
  as the scalar branch, scoped by `(user_id, trick_id)` instead of just
  `user_id`, same null-vs-non-null `expectedRevision` split.

**Real-stack tests** (per the task's own instruction — this needs a real
local Supabase, following the exact pattern T155.9 already established):
new file `supabase/tests/data-api/t157_4_profile_sync_transport.test.mjs`,
built the same way `t155_9_cloud_repositories.test.mjs` is (import
`getLocalConfig`/`createConfirmedUser`/`deleteUser` from `./lib/local-supabase.mjs`,
register `./lib/alias-loader.mjs`, sign in a real confirmed user, run under
`node --test` via `yarn test:data-api`). Cover:
1. Idempotent retry of the *same* profile-scalar upsert twice (simulating a
   lost ack): second call succeeds, no duplicate row, revision only bumped
   once (this is where `insert`-then-`update`-on-`23505` keyed by `user_id`
   proves out for real, not just in the fake used by `transport.test.ts`).
2. Idempotent retry of a trick-state upsert, same shape.
3. Revision-guarded update: push with a stale `expectedRevision` (seed a
   second write via the plain repository first to bump `revision`) returns
   `'conflict'` with the correct `serverRevision`, and the row's actual
   content is untouched by the rejected push.
4. Idempotent retry of a trick-state delete (push twice): both calls
   succeed; second call doesn't error.
5. Delete of a trick-state row that was never created (no prior insert,
   `expectedRevision: null`) succeeds as a no-op.
6. `pullProfileRow`/`pullTrickStatePage` against real seeded rows — basic
   smoke, not a full pagination re-proof (T155.8 already owns pagination
   correctness at the DB/RLS layer).

## The driver hook

New file `src/features/profile/state/use-profile-domain-sync.ts`. Takes its
transport dependency **injected**, exactly like `useIdentityScopedDomain`
takes `load`/`save` and `transport.ts`'s functions take a `repository`
parameter — this is what makes it testable with a fake in jest while
production code supplies the real adapter.

```ts
interface UseProfileDomainSyncOptions {
  readonly identity: Identity;
  readonly profile: UserProfile;                 // current state from the PRIMARY reducer
  readonly hasHydratedProfile: boolean;
  readonly getTransport: () => {                 // lazy: only resolved when actually syncing
    readonly pullProfileRow: ProfileSyncTransport['pullProfileRow'];
    readonly pullTrickStatePage: ProfileSyncTransport['pullTrickStatePage'];
    readonly push: ProfileSyncTransport['push'];
  } | undefined;                                  // undefined ⇒ no client available (native/misconfigured); no-op
}

interface UseProfileDomainSyncResult {
  readonly runSync: (trigger: SyncTrigger) => Promise<DomainSyncRecord>;
  readonly isSyncing: boolean;
  readonly lastResult: DomainSyncRecord | undefined;
}
```

Internals:
- Owns its own `useIdentityScopedDomain<SyncEnvelope<ProfileSyncSnapshot>, ProfileSyncEnvelopeAction>`
  instance (`load`/`save` = the wrappers above, `createRestoreAction` =
  `envelopeRestored`). Gets the same generation-guarded hydration/write-queue
  behavior as the primary domain for free.
- A `useEffect` watching `profile` (skip-on-first-hydration-per-generation,
  same ref pattern as `useIdentityScopedDomain`'s own `shouldSkipNextWrite`,
  since this is a second independent piece of state): on change, compute
  `diffProfileForOutboxOperations(previousProfileRef.current, profile, userId)`;
  if guest identity, skip entirely (no `userId` to diff against — guests
  never sync); else generate `now`/`operationIds` outside the reducer and
  dispatch `localMutationApplied` with the coalescing-aware operation list.
- `runSync(trigger)`:
  1. No-op (return a synthetic `'succeeded'`/trivial record) if
     `identity.kind !== 'user'` or `getTransport()` returns `undefined`.
  2. Local single-flight guard (a ref): if already running, return the
     in-flight promise rather than starting a second run. Comment explains
     this is a deliberately simple per-domain stand-in, superseded once
     T157.9 wires the real shared `syncCoordinatorReducer`.
  3. **Pull phase:** `pullProfileRow()` + `pullAllPages(pullTrickStatePage, ...)`.
     If the envelope's outbox is **empty**: safe to fully adopt — compose
     via `composeUserProfileFromCloudRows` (existing T155.10 function) and,
     if `status === 'valid'`, dispatch the primary reducer's
     `profileRestored` action (the same action hydration itself uses — this
     is the literal "second-browser rehydrate" mechanism) and update the
     envelope's revision cache from the pulled rows. If the outbox is
     **non-empty**, do **not** touch the primary reducer (pending local
     writes stay authoritative locally, per T160.2's no-auto-resolve rule)
     — only refresh the revision cache for records that have **no** pending
     operation (so future pushes for *those* records use fresh
     `expectedRevision`; records with a pending op keep whatever revision
     they last observed, since the pending push's own outcome is what will
     correctly advance or conflict it).
  4. **Push phase:** snapshot `envelope.outbox` once, build
     `getExpectedRevision = (op) => op.recordId === userId ? snapshotProfileRevision : snapshotTrickStateRevisions[op.recordId] ?? null`
     from the (stable, pre-push) revision cache, call
     `pushOutboxOperations(adapter, outbox, { getExpectedRevision })`.
  5. For each outcome: `'succeeded'` ⇒ dispatch `operationAcknowledged` +
     `revisionRecorded` (new revision from the returned row). `'conflict'`
     ⇒ dispatch `operationAttemptRecorded` with a descriptive
     `lastErrorMessage` (e.g. `"stale revision: expected {expected}, server has {serverRevision}"`)
     — the operation **stays in the outbox**, parked, not acknowledged, not
     retried automatically this run; unrelated records' outcomes are
     unaffected (this is `pushOutboxOperations`'s own "continue after one
     conflict/failure" guarantee, already proven by T157.3). `'failed'` ⇒
     same as conflict (`operationAttemptRecorded`, stays pending) — a
     network blip must not drop the operation.
  6. Build and return a `DomainSyncRecord` (`domain: 'profile'`, `outcome`
     derived from whether any push failed hard vs. everything at least
     attempted — a `'conflict'` alone does not make the whole domain
     `'failed'`, matching `DomainSyncOutcome`'s two-value shape: treat
     `'conflict'`/`'succeeded'` outcomes as domain `'succeeded'`, reserve
     domain `'failed'` for pull failure or an unrecoverable adapter
     exception).
- One more `useEffect`: once for each identity generation (ref-guarded,
  same "once per generation" idiom as elsewhere in this codebase), if
  `identity.kind === 'user'` and both the primary and envelope domains have
  hydrated, call `runSync('login')`. This is the one built-in trigger this
  task adds; everything else (foreground, real reconnect detection,
  debouncing) is T157.9.

Tests: `use-profile-domain-sync.test.tsx`, RTL harness reusing the
`IdentityHandleTestProvider` pattern from `use-identity-scoped-domain.test.tsx`
(driving identity/generation directly, bypassing Auth), with a **fake**
transport (in-memory maps, same shape as `transport.test.ts`'s fake but only
needs `pullProfileRow`/`pullTrickStatePage`/`push`). Cover:
1. Offline create (fake transport always fails/network-errors): profile
   change enqueues an outbox op; envelope persists it; remounting the
   provider under the same identity/generation reloads the same pending op
   (proves durability across reload).
2. "Reconnect": remount with a fake transport that now succeeds — the
   pending op pushes, gets acknowledged, revision recorded.
3. Second-browser rehydrate: a fresh envelope (empty outbox, fresh identity
   generation) pulls a fake-seeded server profile+trick-state fixture and
   the primary reducer ends up matching it exactly.
4. A conflict on one trick id doesn't block an unrelated trick id's
   operation in the same run, and the conflicted op is still present
   (unacknowledged) in the envelope afterward.
5. Rapid toggle of the same trick id offline coalesces to one pending
   outbox operation, not N.
6. Guest identity never enqueues operations and `runSync` is a no-op.

## Implementation order

1. Export `parseUserProfile` from `user-profile-persistence.ts` (trivial,
   unlocks the codec below).
2. `replacePendingOperationForRecord` in `sync-envelope.ts` + its tests —
   shared primitive everything else depends on.
3. `diffProfileForOutboxOperations` in `profile-cloud-mapping.ts` + its
   tests — pure, no I/O, easiest to get right in isolation.
4. `profile-sync-envelope.ts` (snapshot type, codec, load/save, reducer) +
   its tests.
5. `profile-sync-transport.ts` (the adapter) + the real-local-Supabase test
   file. Do this **before** the driver hook — the driver's fake tests are
   only trustworthy once the real adapter's semantics (what counts as
   conflict vs. idempotent-success) are nailed down against the actual
   schema/triggers, and it's much cheaper to iterate on the adapter's
   conflict/idempotency edge cases directly against Postgrest than through
   the extra layer of the driver hook.
6. `use-profile-domain-sync.ts` + its fake-transport tests.

## Risks / non-obvious things to flag to the implementer

- The biggest risk is silently drifting into T157.9's job (wiring the real
  shared coordinator, building debounced triggers) or T160's job (visible
  conflict UI, last-write-wins). Both are explicitly out of scope above —
  resist the temptation even though "integrate... coordinator" appears in
  the task description; the coordinator's own header comment and the
  dependency graph (`T157.9` depends on `T157.4–T157.8`) both confirm the
  shared reducer isn't meant to be driven until every domain exists.
- Do not let `getExpectedRevision` read from a cache that can go stale
  *within* one `pushOutboxOperations` call for the same `recordId` twice —
  the coalescing-to-one-pending-op-per-record design above is what
  guarantees that never happens; don't skip it as "just an edge case."
- The profile-scalar branch's unconditional-overwrite fallback when
  `expectedRevision === null` is an accepted, pre-existing limitation
  (matches today's shipped `upsertProfile()` exactly), not something to
  "fix" by inventing new DB-level compare-and-swap semantics — that's a
  bigger schema change outside this task's scope.
- `PGRST116` is already classified `'notFound'` by `mapPostgrestError` for
  *read* paths (`getProfile`'s `.maybeSingle()` never triggers it — only
  `.single()` on zero rows does). Reusing `mapPostgrestError` inside the
  adapter's revision-guard branch is fine for genuine errors, but the
  "0 rows matched by an `.update()...eq('revision',...).single()`" case
  must be special-cased to `'conflict'` **before** falling through to
  `mapPostgrestError`, not treated as a generic `'notFound'` failure.
- Keep `Date.now()`/`Math.random()` entirely out of `profileSyncEnvelopeReducer`
  — generate `now`/`operationIds` in the driver hook's effect body (a React
  effect, not a reducer) and pass them through the action, exactly like
  `applyLocalMutation`'s own `createdAt`/`operationId` parameters and
  AGENTS.md's Sesh-timer convention.
