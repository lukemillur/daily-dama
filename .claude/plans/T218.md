# T218 Add Sentry error tracking for the web build

## Confirmed facts (from live docs/registry lookups, 2026-09-02)

- Installed versions: expo ~57.0.10, expo-router ~57.0.10, react-native 0.86.2,
  react 19.2.3. Latest at-sentry-slash-react-native on npm is 8.24.0
  (peer deps: expo >=49, react >=17, react-native >=0.65 -- all satisfied).
- The @sentry/react-native package's entrypoint (packages/core/src/js/index.ts at that tag)
  has NO top-level side effects -- it is pure re-exports from @sentry/core,
  @sentry/react, @sentry/browser, plus this package's own init/wrap functions. Simply
  importing the module is safe anywhere, including during Expo Router's Node
  static-render pass; only calling Sentry.init(...) does real work.
- Sentry.init() (in sdk.tsx) hooks into the runtime's global uncaught-exception and
  unhandled-rejection handlers automatically -- this is exactly the task's "automatic
  capture only" scope, no Sentry.captureException call sites needed anywhere.
- Sentry.init() has an early-return no-op: if isRunningInMetroDevServer() return.
  That flag is driven by process.env.___SENTRY_METRO_DEV_SERVER___, which is only
  ever set by the @sentry/react-native/metro Metro serializer plugin. We are NOT
  installing that plugin (see Scope decisions below), so this no-op path never
  triggers -- yarn expo start --web dev-server testing will work for the manual
  Sentry-dashboard check in the exit criteria.
- Sentry.wrap(RootComponent) (in sdk.tsx) wraps the tree in TouchEventBoundary plus
  a Profiler plus FeedbackFormProvider. It is NOT an error boundary and does not
  swallow/catch render errors -- confirmed by reading the source. It exists for touch
  breadcrumbs, performance/app-start tracing, and the optional feedback widget, none
  of which this task needs. Skipping it does not reduce automatic-capture coverage
  and keeps the root layout's render tree unchanged (lower risk, smaller diff).
- Platform gating precedent already exists twice in this codebase for exactly this
  kind of "web-only, don't touch native behavior" concern:
  @vercel/analytics's Analytics component is rendered only when
  Platform.OS === 'web' in src/app/_layout.tsx, and getSupabaseClient()
  (src/shared/supabase/supabase-client.ts) returns null on any non-web platform
  and is ONLY EVER invoked from inside a useEffect, specifically so it never
  runs during Expo Router's Node static-render pass (see that file's docstring and
  AuthProvider's usage). This plan reuses both patterns for Sentry.

## Scope decisions (deviating from the docs' default snippet -- flag these)

1. No @sentry/react-native/expo config plugin in app.json, no
   metro.config.js Sentry serializer. Both exist purely to auto-upload source
   maps/debug symbols during NATIVE builds and require SENTRY_AUTH_TOKEN (a real
   secret, explicitly out of scope per the task). Skipping the Metro plugin also
   avoids the isRunningInMetroDevServer() no-op described above. No native config
   changes at all, per AGENTS.md's active-platform-scope rule.
2. No Sentry.wrap(). Confirmed via source it is not an error boundary, but its
   only job here (touch/tracing/feedback instrumentation) is unused -- omit for a
   smaller diff. Note as an easy follow-up if tracing is wanted later.
3. sendDefaultPii: false, no tracesSampleRate/profilesSampleRate/session
   replay options. The docs' example snippet defaults sendDefaultPii to true
   (captures IP, cookies, etc.) and offers tracing/profiling/replay toggles. This
   app has an explicit redaction discipline for Auth data
   (src/features/auth/observability/auth-observability.ts,
   src/features/auth/model/redact.ts) and the task scopes this to error capture
   only -- stay conservative and don't opt into extra data collection or SDK
   surface area that wasn't asked for.
4. initSentry() is called only from a useEffect in the root layout, never at
   module scope. This mirrors the Supabase-client precedent exactly and is the
   one genuinely risky detail in this task: calling Sentry.init() eagerly at
   import time would run during the "yarn expo export --platform web" Node
   static-render pass, where browser globals Sentry.init()'s fetch-transport path
   expects may not behave as in a real browser.

## Implementation order

1. Add the dependency:
   npx expo install @sentry/react-native
   (repo uses Yarn and has yarn.lock; expo install detects and uses Yarn
   automatically, and resolves the version Expo SDK 57 considers compatible rather
   than assuming latest is correct). Confirm package.json/yarn.lock picked up
   a single new top-level entry and no unexpected native-config side files were
   generated (app.json and metro.config.js should be untouched by the
   install itself -- the config plugin has to be added by hand, and we are
   deliberately not adding it).

2. src/shared/observability/sentry-dsn.ts (new file) -- a pure, unit-testable
   resolver, structurally identical to
   src/features/auth/persistence/supabase-config.ts. It exports a SentryDsnConfig
   discriminated union with status 'ready' (carrying dsn), 'missing', or
   'malformed' (carrying a reason string), plus a resolveSentryDsn(dsn) function
   that trims the input, returns 'missing' for an empty/undefined value, attempts
   new URL(trimmed) and returns 'malformed' if that throws, otherwise returns
   'ready' with the trimmed dsn.
   'missing' must stay silent at the call site -- no EXPO_PUBLIC_SENTRY_DSN set
   locally (today's default state, before it's added to Vercel) is expected, not
   an error condition. 'malformed' should log a warning at the call site, same
   split as resolveSupabaseConfig's missing vs malformed.

3. src/shared/observability/sentry-client.ts (new file) -- the single place
   that imports @sentry/react-native, mirroring supabase-client.ts's shape:
   - initSentry(): void -- idempotent via a module-level boolean (guards
     accidental double-invocation, e.g. React Strict Mode double-effects),
     returns immediately if Platform.OS !== 'web' (mirrors the
     Analytics/getSupabaseClient web-only gate -- no native Sentry behavior
     without native config, per task scope), resolves
     resolveSentryDsn(process.env.EXPO_PUBLIC_SENTRY_DSN), no-ops silently on
     'missing', warns (via console.warn, consistent with logAuthWarning's
     level) on 'malformed', and otherwise calls
     Sentry.init({ dsn, sendDefaultPii: false }).
   - resetSentryClientForTests(): void -- clears the module-level idempotency
     flag, mirroring resetSupabaseClientForTests().

4. Tests, colocated under src/shared/observability/__tests__/:
   - sentry-dsn.test.ts -- plain unit tests of resolveSentryDsn (ready,
     missing, malformed cases), same shape as any resolveSupabaseConfig test would
     be (there isn't a standalone one today -- supabase-client.test.ts covers
     both together; do the same here, or split, whichever keeps each file's
     scenarios readable).
   - sentry-client.test.ts -- mirror
     src/shared/supabase/__tests__/supabase-client.test.ts's structure exactly:
     mock @sentry/react-native's init as a jest.fn(), assert
     (a) non-web Platform.OS never calls init, (b) missing DSN never calls
     init and does not console.warn, (c) malformed DSN never calls init
     and does console.warn, (d) valid DSN calls Sentry.init exactly once
     with { dsn, sendDefaultPii: false }, (e) calling initSentry() twice
     only invokes Sentry.init once (idempotency), resetting state via
     resetSentryClientForTests() between cases like the Supabase test does
     with afterEach.

5. Wire it into src/app/_layout.tsx. Add a useEffect that calls initSentry()
   on mount (empty dependency array) inside TabLayout, importing initSentry from
   @/shared/observability/sentry-client. Do NOT call it at module scope or
   in the render body -- see Scope decision 4. Leave the Analytics
   Platform.OS === 'web' JSX gate and everything else in this file untouched;
   this is an additive, independent effect. No test currently imports
   src/app/_layout.tsx directly (checked -- only a comment references it in
   stats.guest-import-resync.test.tsx), so this change can't break an existing
   test by introducing a real @sentry/react-native import into that tree; rely
   on the new unit tests plus the web export step instead of adding a new
   _layout test (no such test convention exists yet in this codebase -- don't
   introduce one just for this).

6. .env.example -- add a new commented block for EXPO_PUBLIC_SENTRY_DSN,
   following the existing Supabase block's phrasing and citing this task: a
   short comment explaining it's for T218's automatic uncaught-exception and
   unhandled-rejection capture on web, noting Sentry DSNs are designed to be
   public (unlike source-map upload auth tokens) and are safe to inline into
   the client bundle, followed by a commented-out EXPO_PUBLIC_SENTRY_DSN=
   line so it's discoverable but not accidentally left blank-but-active.

7. Verification -- Configuration/dependencies tier per AGENTS.md: run
   node .claude/scripts/verify.mjs (the full sequence: yarn test --runInBand,
   yarn lint, yarn tsc --noEmit, yarn expo export --platform web). Watch
   the export step specifically for anything Sentry-related failing to bundle
   for web -- that's the first real signal if the package doesn't tree-shake
   cleanly for the web target; if it does fail, do not add native-platform
   workarounds to fix a web-only task, report back instead.

## Blocker to flag, not silently route around: the dashboard-confirmation exit criterion

The exit criteria require confirming, in an actual Sentry project's dashboard,
that a deliberately thrown error from a running web build was received. That
needs a real Sentry account, organization, project, and DSN, none of which
exist in this execution environment, and creating a Sentry account/org is an
external-service decision an agent should not make unilaterally (this is the
same category of gap flagged for tasks needing external credentials elsewhere
in this project's history, e.g. a Supabase Management API PAT gap on a recent
task).

Do not treat "code compiles and Sentry.init was called without throwing" as
satisfying this criterion -- the task explicitly calls that out as insufficient.

Recommended path for the implementer:
- Complete steps 1-7 above and get full local automated verification green.
  That is real, checkable evidence independent of any Sentry account.
- For a local smoke check of the mechanics (without a real dashboard), a
  temporary local-only DSN in .env.local (excluded from version control, never
  committed) plus a manually-thrown error in a dev-server session can confirm
  the SDK actually attempts an outbound request to Sentry's ingest endpoint
  (visible in the browser network tab) -- this is useful supporting evidence
  but is not a substitute for the actual dashboard check.
- Leave T218's TASKS.md status reflecting that the dashboard-confirmation half
  of the exit criteria is pending real Sentry credentials from the project
  owner (Luke), rather than marking the task fully Done. Say this plainly in
  the PR description too: code plus automated verification complete, manual
  dashboard confirmation blocked on credentials/access this environment
  doesn't have.
- If Luke provides a real EXPO_PUBLIC_SENTRY_DSN (e.g., via a message or by
  setting it in the Vercel dashboard directly), the remaining step is purely
  manual verification, no further code changes are anticipated.
