# T149 — Hide focused tricks while searching in trick goals

## Confirmed current behavior

`src/features/tricks/components/trick-directory.tsx`, in the `sections` memo (around line 95-104):

```ts
const sections = useMemo(
  () => {
    const normalizedQuery = search?.query.trim().toLowerCase() ?? '';
    const visibleTricks = normalizedQuery.length === 0
      ? tricks
      : tricks.filter((trick) => trick.name.toLowerCase().includes(normalizedQuery));
    return createTrickSections(visibleTricks, showFocusedSection ? sectioningTrickIds : undefined);
  },
  [tricks, search?.query, showFocusedSection, sectioningTrickIds],
);
```

`normalizedQuery` already filters `visibleTricks` by search, but the second `createTrickSections` argument (the sectioning/focus list) is gated only on `showFocusedSection`, never on whether a query is present. That's the bug: the "Focused tricks" section keeps appearing (and keeps whatever focused tricks still match the filtered set) regardless of `search.query`.

## Consumer audit (confirms scope)

`showFocusedSection` is passed in three places, not just `GoalTrickPicker`:

- `src/features/goals/components/all-trick-goals-screen.tsx` (`GoalTrickPicker`, ~line 138-148) — passes both `showFocusedSection` and `search={{ query, onChangeText: setQuery }}`.
- `src/app/app/tricks/index.tsx` (main Tricks route, ~line 69-97) — passes `showFocusedSection` but **no** `search` prop.
- `src/features/sesh/components/multi-trick-sesh-entry.tsx` (multi-trick sesh picker, ~line 154-192) — passes `showFocusedSection` but **no** `search` prop.

Onboarding (`onboarding-selection-step.tsx`) and `trick-directory-column.tsx` don't use `showFocusedSection` or `search` at all.

Because only `GoalTrickPicker` supplies a `search` prop, gating the focused-section visibility on `normalizedQuery.length === 0` inside `TrickDirectory` itself is safe for the other two `showFocusedSection` consumers: their `search` prop is `undefined`, so `normalizedQuery` is always `''` and the new condition is always true (no behavior change for them). This matches the task note's instruction to widen scope only if another consumer actually shares the `showFocusedSection` + `search` combination — none currently do, so no other files change.

## Implementation

1. **`src/features/tricks/components/trick-directory.tsx`** — in the `sections` memo, compute the focus gate from both `showFocusedSection` and the presence of a query:

   ```ts
   const sections = useMemo(
     () => {
       const normalizedQuery = search?.query.trim().toLowerCase() ?? '';
       const visibleTricks = normalizedQuery.length === 0
         ? tricks
         : tricks.filter((trick) => trick.name.toLowerCase().includes(normalizedQuery));
       const shouldSectionByFocus = showFocusedSection && normalizedQuery.length === 0;
       return createTrickSections(visibleTricks, shouldSectionByFocus ? sectioningTrickIds : undefined);
     },
     [tricks, search?.query, showFocusedSection, sectioningTrickIds],
   );
   ```

   No new prop, no signature change. `createTrickSections(visibleTricks, undefined)` already falls back to plain rank sectioning when the sectioning-ids argument is `undefined` (this is the same path used today when `showFocusedSection` is `false`), so passing `undefined` while searching reuses existing, already-tested behavior rather than adding a new code path.

   This is the only production-code change needed. Do not touch `all-trick-goals-screen.tsx`, `tricks/index.tsx`, or `multi-trick-sesh-entry.tsx` — none of them need edits because the gating lives centrally in `TrickDirectory` and is a no-op where `search` is absent.

2. **`src/features/tricks/components/trick-directory.test.tsx`** — add one test covering both states (hide while searching, restore when cleared), matching the exit criteria's request for "a test covering both states" in one place. Add near the existing `showFocusedSection` test (after the block ending at line 84):

   ```tsx
   it('hides the focused-tricks section while a search query is present, and restores it when cleared', () => {
     function Wrapper() {
       const [query, setQuery] = useState('');
       return (
         <TrickDirectory
           tricks={FIXTURE_TRICKS}
           showFocusedSection
           focusedTrickIds={['trick-3']}
           search={{ query, onChangeText: setQuery }}
         />
       );
     }

     let root!: import('react-test-renderer').ReactTestRenderer;
     act(() => {
       root = create(<Wrapper />);
     });

     expect(allText(root)).toContain('Focused tricks');

     const searchInput = root.root.findByProps({ accessibilityLabel: 'Search tricks' });
     act(() => {
       searchInput.props.onChangeText('Big');
     });
     expect(allText(root)).not.toContain('Focused tricks');

     act(() => {
       searchInput.props.onChangeText('');
     });
     expect(allText(root)).toContain('Focused tricks');
   });
   ```

   Add `import { useState } from 'react';` to the test file's imports (currently only imports `describe, expect, it` from `@jest/globals` and `act, create` from `react-test-renderer`).

   Note: after `onChangeText('Big')`, the visible-tricks filter also narrows to tricks matching "Big" (i.e. "Big Cup" only), so this simultaneously exercises the existing search-filter path and the new focused-section gating — that's fine and matches real usage (search text always narrows both at once), but don't assert on the filtered trick list itself; keep the assertion scoped to the presence/absence of the "Focused tricks" section header text, which is what this task is about.

## Order and risk

- Single-file production change first (step 1), then the test (step 2) — there's no cross-file sequencing risk here, just keep them in one commit since the test directly verifies the new conditional.
- Low risk: this is a pure gating tweak to an existing memoized computation, no new props, no persistence/schema/reducer involvement, and it's a no-op for the two `showFocusedSection` consumers that never set `search`.
- Watch for one subtlety in the test: `SectionList`'s `ListEmptyComponent` renders "No tricks match your search." when the filtered `tricks` array is empty. If you reuse `FIXTURE_TRICKS` as-is, ensure the query you type ("Big") still matches at least one trick ("Big Cup") so the list isn't empty and the section-header assertions aren't confused by the empty-state text.
