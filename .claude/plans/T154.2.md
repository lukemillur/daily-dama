## Key finding: most of the provider layer already exists

`src/features/auth/state/auth-provider.tsx` (merged via T153.4-era work) already has:

```ts
const signOut = useCallback(async () => {
  const client = getSupabaseClient();
  if (!client) return { error: new AuthError('Supabase is not configured.') };
  const { error } = await client.auth.signOut({ scope: 'local' });
  return { error };
}, []);
```

exposed through `useAuthActions().signOut`, and `src/features/auth/model/auth-state.ts`'s
`deriveAuthState` already unconditionally maps a `SIGNED_OUT` event to
`{ status: 'guest', reason: 'signedOut' }`, wired through the provider's
`onAuthStateChange` subscription. `src/features/auth/state/__tests__/auth-provider.test.tsx`
already has a passing test ("forwards signOut with scope local and surfaces the error").

**So this task is not "add a signOut action" — it's "add the Profile UI that calls the
existing action, and confirm/document how offline and expired-session responses behave".**
Do not duplicate or restructure the existing provider action; only add UI + a couple of
value-adding tests around it.

## Confirmed SDK behavior for `signOut({ scope: 'local' })` (traced against
`@supabase/auth-js`'s `GoTrueClient._signOut`, same source T153.7's plan traced;
re-confirm against the actually-installed version once `yarn install` has run, per that
precedent — do not skip this if the installed version differs materially):

```ts
protected async _signOut({ scope }: SignOut = { scope: 'global' }) {
  return await this._useSession(async ({ data, error: sessionError }) => {
    if (sessionError) return { error: sessionError };
    const accessToken = data.session?.access_token;
    if (accessToken) {
      const { error } = await this.admin.signOut(accessToken, scope);
      if (error) {
        // 404/401/403 are ignored -- an already-invalid/expired session still signs out locally
        if (!(isAuthApiError(error) && [404, 401, 403].includes(error.status))) {
          return { error };            // <-- any OTHER error (incl. offline) is returned as-is
        }
      }
    }
    if (scope !== 'others') {
      await this._removeSession();      // clears storage, fires SIGNED_OUT
      await removeItemAsync(...);
    }
    return { error: null };
  });
}
```

Two concretely different outcomes the UI must handle, and they are NOT the same:

1. **Already-expired/invalid session** (server returns 401/403/404): the SDK swallows the
   error internally, still calls `_removeSession()`, still fires `SIGNED_OUT`. From the
   app's point of view this is **success** — `signOut()` resolves `{ error: null }`, and
   `AuthProvider`'s existing `onAuthStateChange` listener drives state to
   `{ status: 'guest', reason: 'signedOut' }` on its own. No new code needed for this case
   beyond the UI reacting to `authState.status` like every other screen already does.

2. **Offline / genuine network failure**: `admin.signOut`'s underlying fetch throws/returns
   an `AuthRetryableFetchError` (or, per `categorizeAuthError`'s existing `looksOffline`
   check, a `TypeError` mentioning "fetch"/"network"). That error's `name` is not
   `'AuthApiError'`, so `isAuthApiError(error)` is `false` — it is NOT one of the ignored
   404/401/403 cases, so `_signOut` returns `{ error }` **without** calling
   `_removeSession()`. Concretely: **an offline logout attempt leaves the local session
   fully intact and authenticated** — no `SIGNED_OUT` fires, `authState.status` stays
   `'authenticated'`. The Profile UI must surface this as an explicit, retryable error
   rather than silently doing nothing or (worse) locally forcing guest state itself. Do
   **not** have the new UI code call any `setState`/force a guest transition on error —
   let `AuthProvider`'s own event-driven state remain the single source of truth, exactly
   as the existing architecture already guarantees for every other Auth action.

`categorizeAuthError` (`src/features/auth/model/auth-errors.ts`) already classifies both of
these correctly with zero changes needed: case 1 never reaches the UI as an error at all;
case 2 categorizes to `'offline'` via the existing `looksOffline` check. An "unexpected"
non-ignorable, non-offline error (e.g. a real 500) will categorize to `'unknown'` — handle
generically, same as `sign-in-screen.tsx` does.

## Where the control lives

Profile (`src/app/app/profile/index.tsx`) has no Auth-state awareness today and no
account/session section. `AppFooterBar`'s "Leave app" in `src/components/app-tabs.web.tsx`
is unrelated pure navigation (its own comment explicitly says "must not sign the user out")
— leave it untouched; the new logout control is a distinct Profile-page section, not a
change to the footer bar. They can and should coexist.

Follow the established per-screen-component pattern (`sign-in-screen.tsx`,
`reset-password-screen.tsx`): a small, self-contained component that calls
`useAuthState()`/`useAuthActions()` itself, rather than the Sesh pattern of threading
`authState` down as a prop (that pattern exists because `Sesh` is a large pre-existing pure
component tested independently of routing/context — not the case here).

## Implementation steps, in order

1. **`src/features/auth/components/account-section.tsx` (new).**
   - `const authState = useAuthState(); const { signOut } = useAuthActions();`
   - Render `null` unless `authState.status === 'authenticated'`.
   - When authenticated: show identity context (`authState.session.user.email`, falling
     back to a generic "your account" string if `email` is undefined — `User.email` is
     optional in Supabase's type) and a "Log out" `Button`.
   - State: `isSubmitting` (drives disabled/label) + a synchronous `isSubmittingRef` guard,
     copying `sign-in-screen.tsx`'s exact same-tick double-submit fix (a real bug that
     screen's test suite caught — don't skip the ref guard here just because this is a
     simpler action).
   - On press: guard via ref, call `signOut()`. On `{ error }`: categorize via
     `categorizeAuthError`, render fixed copy from a `Record<AuthErrorCategory, string>` map
     (mirror `SUBMIT_ERROR_COPY`'s shape — only `'offline'` and `'unknown'` are realistically
     reachable per the SDK trace above; fill the rest with the same generic "Something went
     wrong" fallback sign-in-screen uses, for type completeness, with a comment saying so),
     call `logAuthWarning('Log out failed.', error)`, `trackAuthEvent('log_out_error',
     category)`, reset `isSubmitting`. On success (`error === null`): call
     `trackAuthEvent('log_out_success')` and reset `isSubmitting` — do **not** manually
     navigate or setState; `authState.status` flipping to `'guest'` via the provider's own
     `onAuthStateChange` listener is what makes this component render `null` next render,
     which is itself "returning to a usable guest workspace" since nothing else on
     `/app/profile` (or anywhere else in `/app`) is gated on auth status today.
   - No raw Supabase error message ever rendered — same invariant as every other Auth
     screen.

2. **`src/features/auth/components/__tests__/account-section.test.tsx` (new).** Mock
   `@/features/auth/state/auth-provider` and `@/features/auth/observability/auth-observability`
   exactly like `sign-in-screen.test.tsx` does. Cover:
   - `initializing` / `guest` / `passwordRecovery` status → renders nothing.
   - `authenticated` → renders the email and an enabled "Log out" button.
   - Success path: `signOut` resolves `{ error: null }` → `trackAuthEvent('log_out_success')`
     called, no error copy rendered, button re-enabled (not stuck disabled).
   - Offline path: `signOut` resolves `{ error: networkFailure() }` (reuse the existing
     `networkFailure()` fixture from `auth-test-fixtures.ts`) → offline copy rendered,
     `logAuthWarning`/`trackAuthEvent('log_out_error', 'offline')` called, button re-enabled
     so the user can retry, and — important — assert `mockAuthState` was never mutated /
     the component didn't call anything to force guest (there's nothing to force it with in
     this test's mock shape, but assert the rendered output still reflects `authenticated`,
     i.e. the button/email are still shown, proving the UI didn't fake a guest transition).
   - Unknown/unexpected error path: `signOut` resolves `{ error: { message: 'server error' } }`
     (no `code`, not offline) → generic "Something went wrong" copy.
   - Same-tick double-press guard: two synchronous presses only invoke `signOut` once
     (mirror the exact regression test `sign-in-screen.test.tsx` added).
   - No raw error message text ever appears in rendered output.

3. **`src/app/app/profile/index.tsx`.** Import and render `<AccountSection />` as its own
   labeled section (reuse the existing `SectionLabel`/`Divider`/`Title`/`Copy` idiom already
   used for "Kentei assessment"/"Daily streak"/"Feedback"). Exact position is an
   implementer call — e.g. directly after the rank line, since it's identity-adjacent — not
   fixed by the exit criteria.

4. **`src/app/app/profile/__tests__/index.test.tsx`.** This file currently mounts
   `<ProfileScreen />` with no `AuthProvider` in the tree, so once `index.tsx` renders
   `<AccountSection />` (which calls `useAuthState()`/`useAuthActions()` directly), the
   existing test will throw ("must be used within AuthProvider") unless the module is
   mocked. Add:
   ```ts
   let mockAuthState: AuthState = { status: 'guest', reason: 'unconfigured' };
   const mockSignOut = jest.fn(...);
   jest.mock('@/features/auth/state/auth-provider', () => ({
     useAuthState: () => mockAuthState,
     useAuthActions: () => ({ signOut: mockSignOut }),
   }));
   ```
   defaulting to `guest` so every existing assertion in this file (which knows nothing
   about Auth) keeps passing unchanged. Add one or two thin integration assertions here
   (authenticated → Log out control visible; guest → not visible) and leave deep
   behavioral coverage to `account-section.test.tsx` — don't duplicate the full matrix in
   both files.

## Order rationale

Steps 1–2 (component + its own tests) before step 3 (wiring into `index.tsx`) so the new
component is proven correct in isolation first; step 4 last because it only needs to adapt
to a change that already exists by that point, and getting the mock shape right is easiest
once the real hook usage (exact destructured shape) is settled in step 1.
