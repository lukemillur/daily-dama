# T260 implementation plan

## Investigation findings (confirmed against `development` HEAD, 2026-09-09)

Ran `node security/scripts/check-dependency-audit.mjs` on a clean checkout: exits 1 with
21 unaccepted high advisories (`@xmldom/xmldom` across two resolved versions, `js-yaml`
across two resolved versions), on top of the already-accepted nanoid/image-size entries
(unaffected, leave as-is).

`yarn.lock` currently resolves exactly two `@xmldom/xmldom` entries and one `plist` entry:

- `@xmldom/xmldom@^0.8.8` -> resolved `0.8.13`, required by `@expo/plist@0.8.1` (already
  the latest published `@expo/plist`; its own `package.json` still declares `^0.8.8`, so
  no upstream patch/version bump of `@expo/plist` exists that would move this).
- `@xmldom/xmldom@^0.9.10` -> resolved `0.9.10`, required by `plist@3.1.1` (already latest
  `plist`; still declares `^0.9.10`), itself pulled in by `simple-plist@1.3.1` <-
  `xcode@3.0.1` <- Expo's `@expo/config-plugins`.
- The newest published `@expo/cli` (`57.0.23`, current pin is `^57.0.12`) still pins
  `@expo/plist: ^0.8.1`, which still pins `@xmldom/xmldom: ^0.8.8`. No newer `@expo/cli`
  or `@expo/config-plugins` patch inside SDK 57 changes either xmldom pin, so exit
  criteria preference (1) (an `@expo/cli`/`@expo/config-plugins` patch bump) is not
  available right now. Re-check this via `npm view @expo/cli versions` / `npm view
  @expo/plist@latest dependencies` before implementing, in case newer 57.x patches landed.

npm registry advisory data (`yarn audit --json`, deduped `auditAdvisory` lines) gives exact
patched-version floors:

- All `<=0.8.14`-range `@xmldom/xmldom` advisories (hitting the `0.8.13` resolution) are
  fixed by `>=0.8.15`. `0.8.15` still satisfies `@expo/plist`'s declared range `^0.8.8`
  (patch-level bump within the same 0.8.x line -- semver-safe, confirmed with
  `semver.satisfies('0.8.15','^0.8.8') === true`).
- All `<=0.9.11`-range `@xmldom/xmldom` advisories (hitting the `0.9.10` resolution) are
  fixed by `>=0.9.12`. `0.9.12` still satisfies `plist`'s declared range `^0.9.10`.
- The `js-yaml` advisory on the 3.x line (affecting `<3.15.2`, resolved instance is
  `3.15.1` via `@istanbuljs/load-nyc-config` <- `babel-plugin-istanbul` <- `babel-jest` <-
  `jest-expo`, a Jest-coverage-only devDependency chain) is fixed by `>=3.15.2`, which
  still satisfies `@istanbuljs/load-nyc-config`'s declared range `^3.13.1`.
- The `js-yaml` advisory on the 4.x line (affecting `<4.3.2`, resolved instance is `4.3.1`,
  a single hoisted entry satisfying both `@eslint/eslintrc@3.3.6`'s `^4.3.0` and
  `@expo/xcpretty@4.4.4`'s `^4.1.0`) is fixed by `>=4.3.2`, which satisfies both ranges.

Every gated advisory has a same-line, semver-compatible patched version already published
upstream. This is exit-criteria preference (2): a scoped `yarn resolutions` override --
not a dependency bump, not an accepted-advisories entry. No `resolutions` field exists in
`package.json` yet -- this is a net-new top-level key.

Risk framing for "verified not to break Expo's plist/xcode tooling": both `@expo/plist`
(used by `@expo/cli`) and `plist`/`xcode`/`simple-plist` (used by `@expo/config-plugins`)
are invoked only by native-project-adjacent CLI paths (`expo prebuild`, credentials,
native config-plugin evaluation) -- not by `expo export --platform web` or the Metro/web
bundling path. Active platform scope is web-only, so the exposure this task closes is
CI-gate correctness and supply-chain hygiene, not a live web attack surface. The patched
versions are pure patch/point releases (parser hardening: ReDoS, quadratic-complexity,
injection bypasses -- no documented breaking API changes per the advisory titles), so risk
of the override itself breaking native tooling is low, but verify empirically per step 4
below rather than relying on this reasoning alone.

## Implementation steps

1. **Edit `package.json`**: add a top-level `"resolutions"` object (place it after
   `"devDependencies"` and before `"scripts"`). Use *scoped* resolution paths (parent
   package name + `/` + `@xmldom/xmldom` or `/js-yaml`), not bare package-name keys, so
   only the vulnerable resolution paths move and the independent 3.x-line `js-yaml`
   consumer is left alone:

   ```json
   "resolutions": {
     "@expo/plist/@xmldom/xmldom": "^0.8.15",
     "plist/@xmldom/xmldom": "^0.9.12",
     "@eslint/eslintrc/js-yaml": "^4.3.2",
     "@expo/xcpretty/js-yaml": "^4.3.2",
     "@istanbuljs/load-nyc-config/js-yaml": "^3.15.2"
   }
   ```

   Each parent name is unambiguous in the current tree (confirmed exactly one
   `yarn.lock` header for each of `@expo/plist@`, `plist@`, `@eslint/eslintrc@`,
   `@expo/xcpretty@`, and `@istanbuljs/load-nyc-config@`) -- re-verify with `grep -n
   '^"\?<name>@' yarn.lock` immediately before editing, in case the tree drifted since
   this plan was written. Do **not** use bare `"@xmldom/xmldom"` or `"js-yaml"` keys --
   that forces every occurrence to the same version regardless of which line the consumer
   actually declared, which is exactly the semver-incompatible jump the exit criteria
   warn against for the 3.x/4.x js-yaml split.

2. **Regenerate the lockfile**: run `yarn install` (not `--frozen-lockfile` -- this step
   is expected to rewrite `yarn.lock`). Confirm it completes without an unresolvable
   dependency-graph error. Inspect the diff: only the `@xmldom/xmldom` and `js-yaml`
   resolved-version/integrity lines (and any transitively-affected sub-dependency lines)
   should change -- no unrelated package should move. If `yarn install` cannot satisfy a
   resolution, stop and re-check the semver math in step 1 against the actual installed
   ranges rather than forcing it.

3. **Verify the audit gate directly**: run `node security/scripts/check-dependency-audit.mjs`
   and confirm exit code 0, with zero unaccepted high/critical advisories (the
   nanoid/image-size accepted entries may still legitimately appear as accepted -- do not
   touch `security/accepted-dependency-advisories.json`). If any `@xmldom/xmldom` or
   `js-yaml` advisory still appears unaccepted, use `yarn why @xmldom/xmldom` / `yarn why
   js-yaml` to find the missed resolution path, correct step 1, and repeat steps 2-3.

4. **Verify the resolutions didn't break the tooling they patch.** This is a
   dependencies-boundary change, so per AGENTS.md run the complete app sequence rather
   than a narrow slice:

   ```sh
   node .claude/scripts/verify.mjs
   ```

   This covers `yarn test --runInBand`, `yarn lint` (exercises the bumped `js-yaml`
   inside `@eslint/eslintrc`'s config-loading path directly), `yarn tsc --noEmit`, and
   `yarn expo export --platform web` (exercises the Metro/web bundling path end-to-end;
   confirms the xmldom/plist bump under `@expo/cli` doesn't break CLI command execution
   even though it isn't itself invoked by the web bundling code path). A green `expo
   export` is the concrete evidence for "verified that no web build-path code parses
   untrusted XML through this dependency" -- if it fails, capture the actual error before
   assuming it's the xmldom bump; isolate by reverting just the resolutions diff and
   re-running.

   Native prebuild/xcode config-plugin evaluation itself (the actual `xcode`/`simple-
   plist` consumer) is out of active verification scope per AGENTS.md's platform-scope
   section -- do not launch a simulator or run `expo prebuild --platform ios` to test it.
   State this scope boundary explicitly in the commit/PR description rather than silently
   skipping it.

5. **Update `TASKS.md`**: move the T260 entry out of `TASKS.md` into `TASKS_DONE.md`
   (matching existing `TASKS_DONE.md` entries' format -- `Status: Done`, `Planning:
   Required` preserved, and a completion note appended recording what was actually done:
   the specific scoped `resolutions` added, the two GHSA-floor version bumps, and that no
   `@expo/cli` patch or accepted-advisories entry was needed). Remove T260's `---`
   separator cleanly so neighboring entries (e.g. T261) aren't disturbed.

6. **Commit** `package.json`, `yarn.lock`, `TASKS.md`, `TASKS_DONE.md` together in one
   focused commit (dependency bump + task-queue update, per AGENTS.md's requirement to
   update TASKS.md in the same commit that closes a task).

## Ordering rationale

Steps 1-2 (package.json + lockfile) must precede step 3 (audit gate check) since the gate
reads the installed tree, not the manifest. Step 4 (full verification) must follow a
passing audit gate (step 3) -- no point running the expensive full suite against a config
that doesn't fix the target problem yet -- but must precede step 6 (commit) since this is
a dependencies-boundary change requiring the complete app sequence before completion per
AGENTS.md. Step 5 (TASKS.md bookkeeping) is independent of 1-4 and can happen any time
before the commit; doing it last keeps the diff review focused: verify the fix first, then
record it.

## Risks / non-obvious notes for the implementer

- **This is time-sensitive to re-verify, not just re-apply.** The advisory list and
  available patched versions were captured live against the npm registry on 2026-09-09.
  If significant time has passed before this plan is implemented, re-run `yarn audit
  --json` and the `npm view` checks from the Investigation section -- new
  `@xmldom/xmldom`/`js-yaml` releases, or a new `@expo/cli` patch, could change which
  preference-order option applies or the exact version floors needed.
- **Don't reach for bare-name resolutions.** `"js-yaml": "^4.3.2"` is shorter but would
  also force the independent 3.x-line consumer (`@istanbuljs/load-nyc-config`, Jest
  coverage tooling) onto an incompatible major version. Keep every resolution scoped to
  its actual parent package.
- **`yarn install`'s outcome is the real gate for whether the override is viable**, not
  just the audit script -- if it can't resolve the graph, that's the signal preference (2)
  isn't viable here: fall back toward re-checking preference (1), or as a last resort
  escalate to the owner for preference (3), which needs explicit sign-off and should not
  be self-authorized.
- If, contrary to this plan's findings, no semver-compatible patched version turns out to
  exist for some specific advisory when re-checked, do not force an incompatible major
  bump via resolutions just to make the gate pass -- that trades an audit finding for a
  real functional-regression risk in native tooling. Fall back to preference (3) (an
  accepted-advisories entry) for that specific advisory only, and flag it for owner
  sign-off rather than proceeding silently.
