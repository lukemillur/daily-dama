# T153.12 — Invite a guest after their first completed Sesh

## Scoping decisions made during planning (read first)

1. **T153.8's `/auth/sign-up` route does not need to exist for this task to be complete.**
   Confirmed no `src/app/auth/sign-up.tsx` exists yet (T153.8 unmerged, blocked on T153.1/Docker).
   The invite links to the fixed path `/auth/sign-up` via `<Link href="/auth/sign-up" asChild>`,
   the same forward-reference pattern already used elsewhere in this codebase (e.g.
   `sign-in-screen.tsx`'s "Continue as guest" replace-to-`/app/home`, and T153.9's own deferred
   `/auth/sign-up` link noted in `TASKS_DONE.md`). Expo Router's typed routes are **not** checked
   against a committed route union here — `.expo/` is gitignored (confirmed via `.gitignore`), so
   there is no committed `.expo/types/router.d.ts` for `tsc --noEmit` to validate `Href` strings
   against; a plain string literal href type-checks today regardless of whether the route file
   exists. Do not create `src/app/auth/sign-up.tsx` in this task — that is T153.8's job. Until it
   lands, pressing "Sign up" 404s in a real browser; that is expected and out of scope to fix here.

2. **Only the single-trick Sesh completion screen (`CompletedSesh` in `sesh.tsx`) gets the
   invite.** `MultiTrickSesh`'s own wrap-up screen (`MultiTrickWrapUp`, used by the Kentei
   assessment flow via `assessment-entry.tsx` and by the `sesh-sequence-sandbox` dev route) is
   **out of scope** for this iteration. Rationale: `CompletedSesh` is the only component actually
   named "completion UI" for a plain Sesh; the assessment flow is an onboarding-adjacent ritual
   where interrupting with a signup nag is poor UX and its records are already excluded from
   "regular" practice history (`selectRegularSessions`); and `BACKEND_ROADMAP.md`'s wording is
   "post-first-Sesh prompt" (singular), matching the primary single-trick flow. If the user wants
   the multi-trick wrap-up covered too, that's cheap follow-up once this lands (same eligibility
   helper, different render site) — flag it, don't fold it in here.

3. **Eligibility must be computed from *pre-record* history, not post-record**, mirroring the
   existing `isFirstLaceForTrick(sessions, summary)` contract already used one line above the new
   code in `Sesh`'s completion effect. `sessions` in that effect closure is captured *before*
   `recordCompletedSesh` dispatches; recomputing "is this the first regular session" *after* the
   dispatch (e.g. from `CompletedSesh`'s own props post-re-render) would already include the just
   -recorded session and always read as "not first" — get this backwards and the invite never
   shows. See the file's own comment on `isFirstLaceForTrick`/`hasPriorLaceForTrick` for the same
   pre/post distinction already solved once in this codebase.

4. **`CompletedSesh` stays fully prop-driven; no new context reads inside it.** It's currently
   rendered directly (no providers) in ~10 existing test blocks (e.g. `sesh.test.tsx:682, 692,
   720, 730, 744, 821, 837, 1509, 1526`). Reading `useAuthState()`/`usePracticeHistory()` inside
   `CompletedSesh` or its new child would break all of them. Instead: `Sesh` (which already reads
   `usePracticeHistory()` directly and is already wrapped with the relevant providers everywhere
   it's tested) computes a plain `showSignupInvite: boolean` and passes it down, mirroring how
   `personalBest`, `isFirstLace`, `justAchievedGoals` are already computed in `Sesh` and threaded
   into `CompletedSesh` as props. New sub-component `PostSeshSignupInvite` needs *zero* context
   access at all (no auth, no practice-history) — just an `onDismiss`-style local `useState` and a
   `Link`. This keeps every existing `CompletedSesh`-only test passing untouched (new prop
   defaults to `false`).

5. **`Sesh` gets a new optional `authStatus?: AuthStatus` prop (default: not shown).** Rather than
   calling `useAuthState()` directly inside `Sesh` (which would require adding `AuthProvider` to
   every one of the ~9 `<Sesh>`-mounting blocks in `sesh.test.tsx` that don't currently wrap it —
   see `grep -n "<GoalProvider>" sesh.test.tsx`), thread auth status in as a prop from the route
   file (`src/app/app/sesh/index.tsx`), which already sits under the real `AuthProvider` ancestor
   in `src/app/_layout.tsx`. Omitting the prop (as every existing test does) safely defaults to
   "not guest" → invite never shows — fail-closed, zero test breakage. This mirrors the existing
   split in this codebase where some cross-cutting inputs (`selectedTrickIds`, `availableTricks`)
   are prop-injected from the route rather than read via context inside `Sesh`, while others
   (`sessions`, `goals`, `notes`) are read directly — auth joins the prop-injected side because of
   the test blast-radius reasoning above, not because of a general rule.

## Files to touch, in order

### 1. `src/features/stats/model/practice-history.ts` (+ its test file)

Add one new pure helper, placed near `isFirstLaceForTrick`/`hasPriorLaceForTrick` (same file,
same section, same doc-comment convention — "priorSessions must be the history as it stood
BEFORE this summary was recorded"):

```ts
// True when no prior *regular* (non-assessment) session exists in `priorSessions` — i.e.
// completing this summary would be the guest's first completed Sesh ever, outside the Kentei
// assessment flow. Mirrors isFirstLaceForTrick's contract: `priorSessions` must be the history
// as it stood BEFORE this summary was recorded. `origin` is the origin this summary is *about*
// to be recorded under — if it's itself an assessment session, it can never be "the first
// regular Sesh" regardless of what came before it.
export function isFirstEverRegularSession(
  priorSessions: readonly PracticeSessionRecord[],
  origin: PracticeSessionOrigin | undefined,
): boolean {
  if (origin !== undefined) return false;
  return selectRegularSessions(priorSessions).length === 0;
}
```

No new imports needed — `PracticeSessionOrigin`, `PracticeSessionRecord`, and
`selectRegularSessions` are already defined in this file.

Unit tests to add in `practice-history.test.ts` (pure, no React, fast):
- Empty `priorSessions` + `origin: undefined` → `true`.
- One prior *regular* session + `origin: undefined` → `false`.
- Prior sessions containing only `origin: 'assessment'` records + `origin: undefined` → `true`
  (assessment history doesn't block the "first regular Sesh" invite — this is the case that
  matters most: a guest who did the Kentei assessment during onboarding should still see the
  invite on their first *real* Sesh).
- Empty `priorSessions` + `origin: 'assessment'` → `false` (this call is itself an assessment
  session, never eligible regardless of prior history).

Do this step first — it's a pure, independently testable unit with no downstream dependents yet,
and everything else in this plan consumes it.

"After reloading the persisted first record" exit criterion: no additional code path exists for
this today — `Sesh`'s reducer state (`useReducer(seshReducer, ...)` with `INITIAL_SESH_STATE`) is

that doesn't correspond to anything the app actually does — a full remount of the harness (fresh
`create(...)` call) with a `PracticeHistoryProvider` pre-seeded with one persisted regular session

`CompletedSesh` screen, so no invite renders at all (trivially true, since `CompletedSesh` only
renders when `state.status === 'completed'`, and a fresh mount starts at `'choosing'`). Add this as
a short explicit test for the exit criterion's record, even though it's a fairly direct
consequence of the existing architecture.
