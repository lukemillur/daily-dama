## Decision: blend text into background, not the accent
Record this in a code comment. Reasons: the accent is user-chosen and can sit close to a custom background (and already fills buttons/badges, so a accent bar would compete with them); text-vs-background is the one pair the theme already guarantees to be readable, so the blend moves toward a colour that always differs from the background, in the correct direction for light and dark themes.

## Numeric check (already computed; recompute in the test, do not trust constants blindly)
Bar = `blendHexColors(text, background, 0.12)`; inactive currently = `theme.textMuted` (65% text / 35% bg):
- default light (#18382e on #dfe8ca): bar #c7d3b7, active 8.17, inactive 3.16 (passes, thin margin), bar vs bg 1.23.
- dark (#f5f5f0 on #101820): bar #2b3339, active 11.74, inactive 5.36.
- black on white: bar #e0e0e0, 15.9 / 5.31. White on #4b2e83: bar #614792, 7.43 / 3.85.
- Pathological: black on #808080 gives active 4.30 and inactive 2.82 (fails); user-set low-contrast text/background fails everything. So the bar tints must not blindly reuse `textMuted`; re-derive against the bar with a fallback.
- Ratio 0.12 gives clear separation plus the border; 0.08 gives bar vs bg only ~1.15 (too subtle), 0.16 pushes light inactive below 3:1. Use 0.12.

## Risks
- Contrast on user-chosen themes is arbitrary; the fallback in step 1 only guarantees ratios where the bar-vs-tint math permits (a fully low-contrast theme can still fail; that is a theme problem, not covered by the tests beyond the mid-grey case, which should pass via the cream/ink fallback). If `deriveReadableForeground` falls back to ink/cream the active tint may still be unreadable on a mid-tone bar; assert and adjust in the test rather than loosening thresholds.
- Light default inactive margin is 3.16 vs 3.0; do not change `deriveMutedTextColor` (shared by all screens).
