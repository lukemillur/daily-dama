# T112.4 -- Landing-page call-to-action into the app

## Confirmed before planning
- `profile.hasCompletedOnboarding` already exists today on `UserProfile`
  (`src/features/profile/model/user-profile.ts`) and is readable via
  `useUserProfile()` from `src/features/profile/state/user-profile-provider.tsx`.
  `UserProfileProvider` wraps the whole app in `src/app/_layout.tsx`, above
  `<Slot />`, so the root `/` route (`src/app/index.tsx` -> `LandingPage`) can
  call `useUserProfile()` today. T112.5/T112.6 are not implementation
  dependencies for this task -- only the profile flag is needed, and it
  already exists. The task's own note already reasoned this out; this
  confirms it against the real provider code.
- Current placeholder CTA lives inline in
  `src/features/landing/components/landing-page.tsx`:
  ```
  <Link href="/app/home" asChild>
    <CtaButton accessibilityRole="link">Start your first Sesh</CtaButton>
  </Link>
  ```
  where `CtaButton = styled(Button)` -- a bare `Button` after a paragraph.
  This is structurally the same "heading -> copy -> single Button" shape as
  `onboarding-intro-step.tsx`'s `Get started` button, which the task
  explicitly says not to reuse. It must be replaced with a visually distinct
  treatment, not just a relabeled `Button`.
- `src/app/__tests__/index.test.tsx` currently renders `RootRoute` (=
  `LandingPage`) with no `UserProfileProvider` in the tree -- it mocks
  `expo-router` only. Once the CTA calls `useUserProfile()`, this test will
  throw unless it also mocks `@/features/profile/state/user-profile-provider`.
  This must be fixed as part of this change or the existing suite breaks.
- Established codebase pattern for "button press -> navigate," used in
  `kentei-onboarding.tsx`/`.test.tsx`: call `useRouter()` inside the
  component, navigate imperatively (`router.replace(...)` / `router.push(...)`)
  from `onPress`, and in tests mock `expo-router`'s `useRouter` to return a
  `jest.fn()`-based router, find the pressable, call `.props.onPress()`
  directly, and assert on the mock call. This is a cleaner fit for this
  task's exit criteria ("simulates pressing the CTA... asserts navigation")
  than the current `<Link asChild>` pattern, which the existing test mocks
  away entirely (`Link: ({ children }) => children`) and can't actually
  assert a navigation target through. Plan uses imperative
  `router.push('/app/home')` on press, not `<Link asChild>`. This does
  trade away real-anchor semantics (right-click / open-in-new-tab / no-JS
  fallback) for testability and consistency with the app's own established
  pattern -- flagging this explicitly as the one debatable call in this plan
  rather than silently dropping the anchor behavior. If that anchor
  semantics matters more than test-precedent consistency, the alternative is
  keeping `<Link href="/app/home" asChild>` and writing a smarter `Link`
  test-double that captures the `href` prop instead of asserting on
  `router.push` -- noted here so it's a deliberate choice either way, not
  revisit-without-reason territory.
- `landing-page.tsx` styles its own typography with the raw `AppColors`
  constants directly (not `theme.*`), even though it composes the shared
  `Button` (which internally reads `theme.buttonBackground` /
  `theme.accent`, resolved by `AppThemeProvider`, also mounted above `/`).
  The new CTA component should follow the same convention: panel-level
  styling uses `AppColors`/`Radii` directly; the actual pressable reuses the
  shared `Button` for its background/label styling so it still matches the
  rest of the app's button treatment and theme customization.

## Design: what makes this CTA distinct from the onboarding pattern

Not just a relabeled button -- a bordered, color-blocked panel (matching the
app's ink-border/bold-weight visual language already established by
`Button`, e.g. `border: 2px solid AppColors.ink`), placed at the end of the
page in place of the current bare button, containing an eyebrow-style tag, a
dedicated headline (distinct from the page's own `Headline`), one line of
supporting copy, and the action button. The two variants differ in copy
and the panel's accent color (`AppColors.yellow` for first-time,
`AppColors.sage` for returning), so the distinction is visible even
skimming, not just legible on close reading.

Suggested copy (implementer may polish wording, keep the meaning/tone):

| | First-time (default) | Returning (`hasCompletedOnboarding === true`) |
|---|---|---|
| Tag | "Ready when you are" | "Welcome back" |
| Headline | "Start your first sesh." | "Jump back into practice." |
| Body | "Pick one trick, hold your focus on it, and see what a deliberate ten minutes does." | "Your seshes, streak, and stats picked up right where you left them." |
| Action | "Start your first Sesh" | "Back to practice" |

Optional polish (not required for exit criteria, worth doing if cheap): wrap
the panel in `Animated.View` with a `FadeInUp`-style `entering` prop --
`react-native-reanimated` is already a dependency and this exact
mock-in-tests pattern is already used in both
`src/app/__tests__/index.test.tsx` and `kentei-onboarding.test.tsx`, so it's
low-risk to add. Skip it if it starts eating into the iteration rather than
being a quick addition -- the color/copy/panel distinction alone already
satisfies "not a restyled onboarding button."

## Steps

1. Create `src/features/landing/components/landing-cta.tsx`.
   Self-contained component (no props) that calls `useUserProfile()` and
   `useRouter()` itself:
   ```
   import { useRouter } from 'expo-router';
   import { styled } from 'styled-components/native';

   import { Button } from '@/components/ui/button';
   import { BodyText } from '@/components/ui/typography';
   import { AppColors, Radii } from '@/constants/theme';
   import { useUserProfile } from '@/features/profile/state/user-profile-provider';

   interface CtaCopy {
     readonly tag: string;
     readonly headline: string;
     readonly body: string;
     readonly action: string;
   }

   const FIRST_TIME_COPY: CtaCopy = { /* see table above */ };
   const RETURNING_COPY: CtaCopy = { /* see table above */ };

   export function LandingCta() {
     const profile = useUserProfile();
     const router = useRouter();
     const isReturning = profile.hasCompletedOnboarding;
     const copy = isReturning ? RETURNING_COPY : FIRST_TIME_COPY;

     return (
       <CtaPanel $variant={isReturning ? 'returning' : 'firstTime'}>
         <CtaTag>{copy.tag}</CtaTag>
         <CtaHeadline>{copy.headline}</CtaHeadline>
         <CtaBody>{copy.body}</CtaBody>
         <CtaButton onPress={() => router.push('/app/home')}>
           {copy.action}
         </CtaButton>
       </CtaPanel>
     );
   }
   // styled.View CtaPanel (border, radius, $variant-driven background),
   // styled.Text CtaTag/CtaHeadline, styled(BodyText) CtaBody,
   // styled(Button) CtaButton -- see design section for tokens
   ```
   `Button` defaults `accessibilityRole` to `'button'`, which is correct
   here since this is now an imperative press-to-navigate action, not a real
   anchor -- don't pass `accessibilityRole="link"` (that was only correct for
   the old `<Link asChild>` version).

2. Wire it into `src/features/landing/components/landing-page.tsx`.
   Replace the `<Link href="/app/home" asChild><CtaButton ...>...
   </CtaButton></Link>` block with `<LandingCta />`. Remove the now-unused
   `Link` and `Button` imports and the `CtaButton` styled component from
   this file (they move into `landing-cta.tsx`). Keep everything else on the
   page (features, screenshots, closing paragraph) unchanged -- this task is
   scoped to the CTA only.

3. Add `src/features/landing/components/landing-cta.test.tsx` with the
   two exit-criteria tests, following the `kentei-onboarding.test.tsx`
   convention:
   - Mock `expo-router`: `useRouter: () => mockRouter` where `mockRouter =
     { push: jest.fn() }`.
   - Mock `@/features/profile/state/user-profile-provider`'s
     `useUserProfile` as a `jest.fn()` so each test can set its own return
     value (`{ hasCompletedOnboarding: false, ... }` vs. `{
     hasCompletedOnboarding: true, ... }` -- check `INITIAL_USER_PROFILE` in
     `user-profile.ts` for the full required shape, or just supply the
     fields this component reads plus enough to satisfy the `UserProfile`
     type if the test imports it).
   - Test 1 (first-time): render `LandingCta` with
     `hasCompletedOnboarding: false`, find the pressable (by
     accessibilityLabel/visible text using the same
     `findByAccessibilityLabel`/`pressByVisibleText` style helpers as
     `kentei-onboarding.test.tsx`, or a local equivalent), call its
     `onPress`, assert `mockRouter.push` was called with `'/app/home'`.
   - Test 2 (returning): render `LandingCta` with `hasCompletedOnboarding:
     true`, assert the returning-variant copy is present (e.g. the
     "Welcome back" tag or "Jump back into practice." headline) and that
     the first-time copy is absent, then press the action and assert
     `mockRouter.push('/app/home')` again.
   - If the optional motion polish is added, mock
     `react-native-reanimated` the same way the other two test files do.

4. Update `src/app/__tests__/index.test.tsx`. This test renders
   `RootRoute` directly with no provider tree, so it must now mock
   `@/features/profile/state/user-profile-provider` (`useUserProfile: () =>
   ({ hasCompletedOnboarding: false, ... })`, mirroring the `Link`/`useRouter`
   mock already present) or the render will throw. Replace the stale
   CTA-specific assertions (`accessibilityRole === 'link'` and the literal
   `'Start your first Sesh'` text -- both are now owned by
   `landing-cta.test.tsx`) with a lighter integration check that
   `LandingPage` actually renders `LandingCta`'s default-variant output
   (e.g. assert the default headline/action text appears), so this test
   still catches a broken wire-up without duplicating the granular
   navigation assertions.

5. Run full verification. `node .claude/scripts/verify.mjs` (all four
   steps -- this touches TS component code, not docs-only, so don't use
   `--skip-export`).

## Order rationale

`landing-cta.tsx` first because both `landing-page.tsx` and both test files
depend on it existing. Wire-up into `landing-page.tsx` next since that's the
actual product change the exit criteria observe. New/updated tests after
the component and wiring are in their final shape, so tests aren't written
against an intermediate API. Verification last.
