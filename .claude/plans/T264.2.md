# T264.2 — Serve robots.txt and sitemap.xml with the deployed site

## Mechanism (established, not to re-litigate)

Expo Router's static web export (`web.output: "static"` in `app.json`) copies a
root-level `public/` directory verbatim into the export root. This was already
proven empirically by T264.1 (`public/images/daily-dama-og-share-card.png` →
`dist/images/daily-dama-og-share-card.png`), and confirmed against Expo's docs:
files under `public/` are copied as-is, nested paths are preserved, and the only
reserved path to avoid is `/assets` (Metro-reserved) — irrelevant here since
`robots.txt` and `sitemap.xml` are top-level files. `index.html` and `_expo/`
are the only paths Expo generates itself rather than copying.

So: adding `public/robots.txt` and `public/sitemap.xml` is sufficient. No
`vercel.json` change is needed — its `headers` rule matches `/(.*)` and already
applies uniformly to every static asset (proven by the OG image working), and
its `rewrites` array has no entries that could intercept these two paths.
`cleanUrls: true` only affects `.html` suffix stripping and does not touch files
that already have a `.txt`/`.xml` extension.

The production host is confirmed as `https://dailydama.com` per
`DEPLOYMENT_HANDOFF.md` and the existing `PRODUCTION_HOST` constant in
`src/app/index.tsx` (used for the canonical link, no trailing slash: `PRODUCTION_HOST = 'https://dailydama.com'`). The single public route to promote is
the root landing route (`/`) — nothing under `/app/*` is listed, per the task
Notes.

## Steps

1. **Create `public/robots.txt`**
   ```
   User-agent: *
   Allow: /

   Sitemap: https://dailydama.com/sitemap.xml
   ```
   - `Allow: /` (rather than no `Disallow` lines at all) makes the "indexing is
     allowed" intent explicit and machine-checkable, and satisfies "does not
     disallow the public landing route."
   - Do not add any `Disallow` for `/app/*` — the task Notes are explicit that
     enforcing crawler exclusion of the client-gated app routes is out of scope
     for this ticket. Only the sitemap's silence on those routes is required.
   - Optional, non-blocking judgment call: you may add `Disallow: /_sitemap` to
     keep Expo Router's own debug route-listing page (`_sitemap.html`, unrelated
     to the SEO sitemap being added here) out of search results, since it has no
     end-user value. This is not required by the exit criteria — skip it if you'd
     rather keep this ticket minimal; either choice is fine.

2. **Create `public/sitemap.xml`**
   ```xml
   <?xml version="1.0" encoding="UTF-8"?>
   <urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
     <url>
       <loc>https://dailydama.com</loc>
     </url>
   </urlset>
   ```
   - Hand-authored is correct here — there is exactly one public URL to list, so
     a generator script would be pure overhead.
   - Match `PRODUCTION_HOST` exactly (`https://dailydama.com`, no trailing
     slash) to stay consistent with the canonical link already emitted by
     `src/app/index.tsx`, avoiding a needless www/no-slash mismatch signal to
     crawlers.
   - Do not use Expo Router's own `_sitemap.html` output for this — it is a
     debug route listing, not a search-engine sitemap, and is already present
     in the export as an unrelated file.
   - Skip `<lastmod>`/`<changefreq>`/`<priority>` — Google ignores the latter
     two anyway, and there's no reliable source of truth for `<lastmod>` on a
     static landing page in this repo.

3. **No `app.json`, `vercel.json`, or route code changes.** This is the one
   part of the plan worth double-checking before considering the ticket done:
   confirm during verification that nothing needs to change here rather than
   assuming it from this plan alone.

## Verification

AGENTS.md's web-verification rule ("run the Expo development server rather
than serving the static export with a generic file server") exists because of
Expo Router's extensionless-route fallback behavior. `robots.txt` and
`sitemap.xml` are literal static files with extensions, not extensionless
router routes, so that specific hazard doesn't apply to them — but stay inside
the spirit of the rule (Expo-native serving, not an ad hoc static-file server
tool) for consistency and because the exit criteria explicitly calls out
avoiding a generic file server:

1. Run `yarn expo export --platform web --output-dir /tmp/daily-dama-web-export`
   and directly inspect `/tmp/daily-dama-web-export/robots.txt` and
   `/tmp/daily-dama-web-export/sitemap.xml` — confirm both exist at the export
   root (not nested under `/public`) with exactly the authored content.
2. Run `yarn expo start --web` (Metro's dev server also serves `public/`
   verbatim at the same top-level paths, which is the Expo-native serving path
   AGENTS.md steers toward for browser verification). Against that server, `curl
   -i http://localhost:<port>/robots.txt` and `.../sitemap.xml` and confirm
   HTTP 200 plus the expected body for each — this is the concrete "request
   returns 200" evidence the exit criteria ask for, obtained without reaching
   for a generic static-file-server tool.
3. Confirm `robots.txt`'s content has no `Disallow` line covering `/` or the
   root route — this is the "does not disallow the public landing route" exit
   criterion; a plain read of the two-line file is sufficient, no tooling
   needed.
4. This change is two new static passthrough files with no route, component,
   reducer, or persistence-domain code touched — per AGENTS.md's risk-based
   verification, this does not warrant `yarn test`, `yarn lint`, or
   `yarn tsc --noEmit` beyond what's already clean on `development`. It also
   isn't a dependency/configuration change to `app.json`/`package.json`, so the
   full app sequence (`node .claude/scripts/verify.mjs`) is not required — the
   export + dev-server checks above are the right-sized evidence.
