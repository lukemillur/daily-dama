# T162.1 -- Report-only CSP for the static web export

## Confirmed facts (from live investigation, not assumption)

- **Hosting**: Vercel serves `dist/` (from `yarn expo export --platform web --output-dir dist`) per `vercel.json`. `vercel.json` currently has only `buildCommand`, `outputDirectory`, and one `rewrites` entry (`/app/stats/:trickId` -> `/app/stats/[trickId].html`). No `headers` block exists yet -- this is greenfield.
- **Supabase**: the only network client is `src/shared/supabase/supabase-client.ts`, built from `EXPO_PUBLIC_SUPABASE_URL`/`EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (`src/features/auth/persistence/supabase-config.ts`), inlined at build time. No realtime/`.channel(` usage anywhere -- REST/PostgREST over HTTPS only, no websockets needed. The exact hosted project ref is not checked into the repo (by design -- it's an env var set in Vercel's dashboard), so the CSP must allow it without hardcoding a specific subdomain. Local dev uses `http://127.0.0.1:54321` (`supabase/README.md`).
- **Vercel Analytics**: `@vercel/analytics@2.0.1`, used in `src/app/_layout.tsx` (`<Analytics beforeSend={...}>`) and `src/features/auth/observability/auth-observability.ts` (`track`). Confirmed by reading `node_modules/@vercel/analytics/dist/index.js`: in production (`NODE_ENV=production`, which `expo export` sets) it loads its script from the **same-origin** path `/_vercel/insights/script.js` and posts beacons to the **same-origin** path `/_vercel/insights` -- both proxied by Vercel's edge, not an external origin. (Only in dev mode does it use `https://va.vercel-scripts.com/v1/script.debug.js`, which is out of scope since dev mode isn't served through `vercel.json`.) **Conclusion: Analytics needs no extra CSP origin beyond `'self'`.**
- **Fonts/external assets**: grepped the actual exported HTML/CSS (`yarn expo export --platform web --output-dir <scratch>`, then inspected `dist/**/*.html` and `dist/_expo/static/css/*.css`). No `@font-face`, no `fonts.googleapis.com`/`fonts.gstatic.com`, no external `<link>` tags besides same-origin CSS/favicon. Images use `data:image/svg+xml;base64,...` (react-native-web's spinner/reset assets) -- `img-src` needs `'self' data:`, nothing else. No `<iframe>` anywhere in `src/`. No `new Worker(`, no `blob:`, no `URL.createObjectURL` anywhere -- no `worker-src`/extra `img-src` needed for `trick-viz`'s WebGL canvas (canvas rendering isn't restricted by CSP the way `<img>`/network fetches are). Still worth an eyeball check of `/app/stats/trick-viz-sandbox` during the browser walkthrough (step 8) since it's the most complex rendering path and wasn't exercised interactively here.
- **Inline `<script>`/`<style>` in the static export** (this is the load-bearing finding -- read carefully): every one of the 27 exported HTML files contains one inline `<script type="module">globalThis.__EXPO_ROUTER_HYDRATE__=true;</script>` (Expo Router's static-hydration bootstrap) and three inline `<style>` blocks: `#expo-reset` (react-native-web's tiny reset), a plain `<style>html,body{background:#f4c94d}</style>` (from the single `dangerouslySetInnerHTML` in `src/app/+html.tsx` -- a hardcoded, non-user-derived string, not an injection risk itself, but it does force a style-src decision), and `#react-native-stylesheet` (the app's **entire** atomic CSS ruleset baked into every page at static-render time -- ~17.6KB, and it will change on virtually any commit that touches styling).
  - Verified byte-for-byte across all 27 pages: the inline `<script>` content is identical everywhere -> **hash-pinnable** (`sha256-67fhrP0+BkBqmgGGXTtgiVO/9EQs3QruYNU/7fnRkI8=` for the exact string `globalThis.__EXPO_ROUTER_HYDRATE__=true;`, computed directly from a real build -- recompute it yourself rather than trusting this string blindly, and build the hash computation into a script rather than hand-copying it again, see step 4).
  - `#react-native-stylesheet` content is also identical across all pages in one build, but it is the whole app's compiled CSS and will legitimately change often. Hash-pinning it would mean regenerating and re-committing `vercel.json` on nearly every styling PR -- not practical for this prototype. **Decision: `style-src` gets `'unsafe-inline'`, `script-src` gets the hash instead of `'unsafe-inline'`.** This is a deliberate, asymmetric tradeoff: script injection is the dangerous case (arbitrary JS execution) and stays hash-locked; inline style injection alone is much lower severity in modern browsers (no `expression()`/`-moz-binding`), and hash-pinning it isn't practical here. Note for the record: don't try to combine a hash *and* `'unsafe-inline'` in the same directive expecting both to apply -- per the CSP spec, browsers that understand hash sources ignore `'unsafe-inline'` in that directive entirely once a hash is present. `style-src` should carry `'unsafe-inline'` alone, no hash.
- **Raw-HTML sinks**: exactly one `dangerouslySetInnerHTML` in the whole `src/` tree, in `src/app/+html.tsx`, and its content is a fixed, hardcoded CSS string -- never note/custom-trick/user content. Confirmed via full-tree grep. Note body and custom-trick/sequence-step names render through React Native `Text`-derived components (e.g. `src/features/notes/components/trick-notes-screen.tsx`'s `<NoteBody>{note.body}</NoteBody>`) which render as plain escaped text nodes on web -- never parsed as HTML. This is safe *by construction* today; the job here is to (a) add a regression guard so it stays that way, and (b) add explicit tests proving it, per the exit criteria.

## Implementation plan (do in this order)

### 1. `vercel.json` -- add the `headers` block
Add a `headers` array with one rule matching every route (`"source": "/(.*)"`) and one header, `Content-Security-Policy-Report-Only` (report-only -- do **not** use the enforcing `Content-Security-Policy` header name; that's T162.2). Directive value, based on everything above:

```
default-src 'self';
script-src 'self' 'sha256-67fhrP0+BkBqmgGGXTtgiVO/9EQs3QruYNU/7fnRkI8=';
style-src 'self' 'unsafe-inline';
img-src 'self' data:;
font-src 'self';
connect-src 'self' https://*.supabase.co;
frame-src 'none';
frame-ancestors 'none';
object-src 'none';
base-uri 'self';
form-action 'self';
```

Notes on individual choices:
- `connect-src` uses a wildcard subdomain (`https://*.supabase.co`) rather than the literal project ref, because the ref isn't and shouldn't be hardcoded into a static, checked-in config file (it's an `EXPO_PUBLIC_*` env var set per-environment in Vercel). This is still a meaningfully scoped allow-list (not `*`), and is the honest way to keep `vercel.json` environment-independent. Record this as a known, deliberate looseness -- if the team later wants the exact ref hardcoded, that's a T162.2-time tightening once the "final web Auth/sync origin set" the task Notes mention is settled.
- No `http://127.0.0.1:54321`/`localhost:54321` (local Supabase) in this file -- see step 4 for how local/manual testing against local Supabase is supported without baking dev-only loopback origins into the production policy.
- `frame-src 'none'` and `frame-ancestors 'none'`: there are no iframes anywhere in the app (confirmed above); this directly satisfies the exit criterion "reject unlisted ... frame origins" since the allow-list is empty.
- No `report-to`/`report-uri`: there's no backend to receive reports, and none is needed for this ticket -- `securitypolicyviolation` fires client-side regardless (used in step 8's Playwright checks), and report-only violations are visible in DevTools without a collector. Don't add a reporting endpoint here; that would be new backend surface outside this ticket's scope.

### 2. Raw-HTML sink audit guard -- `security/dangerous-html-audit.test.ts`
New Jest test (repo root `security/` dir; jest-expo's default testMatch picks up any `*.test.ts` outside `node_modules`/`.claude/worktrees`/`e2e/`, confirmed from `package.json`'s `jest` config -- no config changes needed). It should:
- Recursively grep `src/` (excluding `node_modules`) for `dangerouslySetInnerHTML`, `.innerHTML =`, `.outerHTML =`, and `insertAdjacentHTML(`.
- Assert the result is **exactly** one match: `src/app/+html.tsx`, and that its value is the known static string (not a template/interpolation of any variable). Fail loudly (with a clear message pointing at this ticket's invariant) if any other occurrence appears, or if `+html.tsx`'s occurrence starts interpolating a non-literal value.

This turns "audit raw-HTML sinks" from a one-time check into a permanent regression guard, and runs as part of the standard `yarn test` / `verify.mjs` loop (no new command needed).

### 3. Hostile-content rendering regression tests
Add tests proving note/custom-trick/sequence-step text can't become executable HTML when rendered, in three places (extend existing colocated test files rather than new ones where a natural spot exists):
- `src/features/notes/components/trick-notes-screen.test.tsx` or `all-notes-screen.test.tsx` (check which already covers rendering `note.body`) -- add a case with a note body like `<img src=x onerror="window.__pwned=1">` / `<script>window.__pwned=1</script>`, mount via `react-test-renderer`, and assert the rendered tree's text node equals the raw string verbatim (proving it round-trips as literal text, not parsed markup).
- `src/features/tricks/components/trick-directory.test.tsx` -- same pattern for a custom trick whose `name` contains hostile markup.
- `src/features/sesh/components/sesh.test.tsx` or `multi-trick-sesh.test.tsx` -- same pattern for a sequence step's snapshot name (`existingTrick`'s name snapshot or `customText`).

Since these are React Native `Text`-based components, `react-test-renderer`'s tree will simply contain the raw string as a text child -- the assertion is just string equality, which is sufficient proof (there's no HTML parser in the render path to bypass). Keep these fast/no-DOM, consistent with the rest of the component test suite -- no need for jsdom/`@testing-library` (not currently a dependency; don't add it for this).

### 4. `security/scripts/serve-web-export.mjs` -- static server that mirrors Vercel's serving behavior
A small dependency-free Node `http` server (no new packages) that:
- Serves a given directory (default `dist/`) with Vercel's standard "clean URL" resolution: for a request path, try the exact file, then `<path>.html`, then `<path>/index.html`.
- Applies the one explicit rewrite already in `vercel.json` (`/app/stats/:trickId` -> `/app/stats/[trickId].html`) -- parse it out of `vercel.json` at startup rather than hardcoding it a second time, so the two files can't silently drift.
- Reads `vercel.json`'s `headers` block and applies every listed header to every response matching `source` (right now just the one CSP-Report-Only rule, but written generically).
- Accepts an optional `--extra-connect-src="<origin> <origin> ..."` CLI flag that, if given, appends those origins to the served response's `connect-src` directive only (string manipulation on the header value already read from `vercel.json` -- don't duplicate the policy). This is how a developer manually exercises the report-only policy against a locally running Supabase (`http://127.0.0.1:54321`) without that loopback origin ever being part of the committed production policy. Document this one-liner in `security/README.md` (step 9); it is **not** wired into any automated test -- the automated suites use a placeholder Supabase URL instead (see step 6).

### 5. `security/scripts/build-and-serve.mjs`
Runs `yarn expo export --platform web --output-dir dist` (with `EXPO_PUBLIC_SUPABASE_URL`/`EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY` set to a well-formed placeholder, e.g. `https://placeholder-project.supabase.co` / a dummy key string, *if not already set in the environment* -- see step 6 for why), then execs `serve-web-export.mjs` (forwarding `--extra-connect-src` if passed through). This is the single command both the header-check script and the Playwright config use to get a production-like served build; keeps the "build a fresh export, then serve it" sequence in exactly one place.

### 6. `security/scripts/check-csp-headers.mjs` -- the automated header-rejection check
This is what satisfies "automated header checks reject unlisted script/connect/frame origins." A `node --test`-based script (matching `.claude/scripts/test`'s style) that:
- Runs `build-and-serve.mjs` itself (spawn, wait for the port to answer), fetches a representative set of routes (`/`, `/app/home`, `/app/tricks`, `/app/sesh`, `/app/stats`, `/app/profile`, `/auth/sign-in`, `/auth/callback`), and for each: asserts the `content-security-policy-report-only` response header is present and byte-identical across all of them (it should be, since `vercel.json`'s rule is a single catch-all -- divergence would indicate a bug).
- Parses the header into a directive -> source-list map and asserts each directive equals a hardcoded expected allow-list **written independently in this test file** (not imported from `vercel.json`) -- so a manual edit to `vercel.json` that quietly widens an origin gets caught by an independent expectation, not just a round-trip of the same value.
- Asserts no directive contains a bare `*`.
- Recomputes the `script-src` hash live from the fresh `dist/` export's inline `<script type="module">` content (sha256 -> base64, same computation used to derive the value in step 1) and asserts it matches what's in `vercel.json`. This is the drift guard for the risk flagged in step 1: if an Expo Router upgrade ever changes that bootstrap snippet, this test fails with a clear "hash mismatch, regenerate" message instead of silently shipping a policy that either blocks the real hydration script (once T162.2 enforces it) or, worse, someone "fixes" it by loosening to `'unsafe-inline'`.
- Also asserts that if the inline script content is **not** identical across all sampled pages (recheck this assumption on every run, don't just trust step 1's one-time finding), the test fails loudly with a message explaining the single-hash assumption it depends on, rather than passing spuriously.

Add `"security:check-headers": "node security/scripts/check-csp-headers.mjs"` to `package.json`. Do **not** add this to `.claude/scripts/verify.mjs` -- same precedent as `test:db`/`test:e2e:auth`, it needs to build+serve a fresh export and isn't part of the fast default loop.

### 7. `playwright.security.config.ts` + `e2e/security/`
New Playwright config (testDir `e2e/security`, separate from `e2e/auth`) whose `webServer.command` is `node security/scripts/build-and-serve.mjs`. Two specs:
- `e2e/security/01-no-unexplained-violations.spec.ts`: for each Auth route (`/auth/sign-in`, `/auth/sign-up`, `/auth/forgot-password`, `/auth/reset-password`, `/auth/check-email`, `/auth/callback`) and each core app route (`/app/home`, `/app/tricks`, `/app/sesh`, `/app/stats`, `/app/profile`, plus one trick-detail route like `/app/tricks/laced` and `/app/stats/trick-viz-sandbox` per the residual-risk note in step 1's findings), register a `securitypolicyviolation` listener before navigation (`page.addInitScript` registering the listener + `page.exposeFunction` to forward violations back to the Node test, matching the "listen for a DOM event and collect it" pattern -- Playwright has no built-in CSP API), navigate, wait for hydration, and assert the collected violation list is empty. If anything unavoidable turns up here during implementation (e.g. `trick-viz`'s WebGL path does something CSP-relevant that step 1's static read missed), that's the point of report-only -- record it as an explained/allow-listed case with a comment citing what triggered it, don't just silence the check.
- `e2e/security/02-disallowed-origin-is-flagged.spec.ts`: on one loaded page, `page.evaluate(() => fetch('https://example.com/csp-test').catch(() => {}))` (a definitely-unlisted origin) and assert a `securitypolicyviolation` **was** recorded with `violatedDirective` starting with `connect-src` -- the positive-control proving the header is genuinely active end-to-end and would actually reject that request once T162.2 flips to enforcing mode, not just present as inert text nobody's listening to.

Why a placeholder Supabase URL instead of a live local stack (unlike `e2e/auth`): this suite is about page loads and CSP violations, not exercising real Auth flows or Data API calls -- a live Docker/Supabase dependency would be pure overhead here. Using `https://placeholder-project.supabase.co` still exercises the real `supabase-client.ts` code path (client gets constructed, `connect-src`'s wildcard still matches the placeholder's origin) without needing `supabase start`. Note this deliberately means the suite can't tell you whether a *real* Supabase call would violate `connect-src` (it can't, matching `*.supabase.co`) -- that's covered by the wildcard's construction, not by exercising a live call.

Add `"test:e2e:security": "playwright test --config=playwright.security.config.ts"` to `package.json`.

### 8. Manual browser walkthrough (do this once, by hand, before calling the ticket done)
Run `yarn security:check-headers` and `yarn test:e2e:security` first (steps 6-7 catch the mechanical cases), then do one manual pass in real Chrome DevTools against `node security/scripts/build-and-serve.mjs` serving on a real port: open DevTools' Console/Issues tab, click through Home -> Sesh -> Tricks (including a custom trick and a sequence, if any exist in the placeholder/local state) -> Stats -> Profile, plus `/app/stats/trick-viz-sandbox` and `/app/stats/sesh-sequence-sandbox` (the two sandbox routes visible in the export listing -- not part of the primary nav but still shipped routes). Confirm no unexpected `Content-Security-Policy-Report-Only` console warnings appear beyond what steps 6-7 already predicted. This is the human check behind the "browser walkthroughs cover Auth and core app routes with no unexplained violations" exit criterion -- the Playwright spec in step 7 automates the same thing, but a real-DevTools pass is worth doing once since it's cheap and catches anything a scripted listener might miss (e.g. browser-internal warnings that don't fire as `securitypolicyviolation` events).

## Risks / things to double-check during implementation, not just trust from this plan

- The script-src hash (`sha256-67fhrP0+BkBqmgGGXTtgiVO/9EQs3QruYNU/7fnRkI8=`) was computed from one real build during planning. Recompute it yourself when you actually implement step 1 rather than copy-pasting -- step 6's drift check will catch a wrong value immediately, but don't rely on that as a substitute for computing it correctly the first time.
- `style-src 'unsafe-inline'` is a real, if low-severity, loosening. If review pushback lands on it, the alternative is teaching `serve-web-export.mjs`/the Vercel config to extract+hash the per-page `react-native-stylesheet` content and list multiple hashes -- but that reintroduces the "changes on every styling commit" problem from step 1 and isn't worth it for a report-only prototype ticket. Don't silently go down that path without flagging the cost/benefit first.
- `connect-src`'s `https://*.supabase.co` wildcard is intentionally loose for the reason given in step 1. If the task's dependency ("the final web Auth/sync origin set") turns out to mean the team wants the literal project ref hardcoded instead, that's a small, mechanical change to step 1's directive value -- flag it as a question rather than assuming either way if it's ambiguous when you start.
- Re-verify the `trick-viz` WebGL/canvas routes (`/app/stats/trick-viz-sandbox`, and any trick detail page that renders `TrickScene`) during the manual walkthrough (step 8) -- this plan's static-code read didn't find anything CSP-relevant there (no workers, no blob URLs, no external texture URLs), but it's the least-inspected rendering path in this investigation and worth a specific look rather than assuming the general audit covered it.
