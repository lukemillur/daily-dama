# T155.1 — Create private and exposed schemas with deny-by-default privileges

## Context already confirmed on this branch

- `supabase/` (from merged T153.1) has `config.toml`, `templates/`, `README.md`,
  and `.gitignore`, but **no `supabase/migrations/` directory exists yet** —
  this ticket creates the first one.
- `config.toml`'s `[api]` block currently exposes `schemas = ["public",
  "graphql_public"]`.
- There are no application tables anywhere yet. This ticket is pure schema +
  privilege infrastructure; T155.2+ add the first real tables on top of it.
- Local stack: `npx --yes supabase@2.115.0 start` / `db reset` /
  `stop` work in this sandbox (Colima/Docker already verified running).
  **Always run these from the actual working directory you intend to affect**
  — `supabase start` names its containers after `project_id` in the
  *current* `config.toml`; if you `cd` to a different checkout of this repo
  first, you can accidentally start/stop a stack that isn't the one your
  migrations file lives next to (this happened once already while drafting
  this plan and was caught by checking `docker ps` container names).
- Verified empirically against a running local stack (this is not guesswork):
  Supabase's own bootstrap (run before any user migration) installs two
  `ALTER DEFAULT PRIVILEGES ... FOR ROLE` entries on `public` — one `FOR ROLE
  postgres`, one `FOR ROLE supabase_admin` — each auto-granting full CRUD on
  future tables and `USAGE` on future sequences to
  `anon`/`authenticated`/`service_role`. It also directly `GRANT USAGE ON
  SCHEMA public TO anon, authenticated, service_role` (owned by
  `pg_database_owner`, not just the ambient `PUBLIC` pseudo-role). Both facts
  matter below.
- `postgres` (the role migrations run as) is **not** a superuser and is
  **not** a member of `supabase_admin` (confirmed via `pg_roles`/`pg_has_role`
  on a live instance), so a migration cannot revoke the `FOR ROLE
  supabase_admin` default-privilege entry — see step 2 below for why this is
  fine in practice. `postgres` *is* effectively the owner of the `public`
  schema (owned by the `pg_database_owner` pseudo-role, which resolves to the
  database's actual owner, `postgres`), so it *can* revoke the direct `GRANT
  USAGE ON SCHEMA public` and the schema's `PUBLIC`-pseudo-role grant.

## Step 1 — Add the migration file

Run, from the repo root of whatever checkout you're actually working in:

```sh
npx --yes supabase@2.115.0 migration new create_private_and_exposed_schemas
```

This creates `supabase/migrations/<timestamp>_create_private_and_exposed_schemas.sql`.
Put exactly this content in it (already written, applied via a clean `db
reset`, and probed live against PostgREST in this planning session — copy it
verbatim rather than re-deriving it, then adapt only if a real discrepancy
shows up when you run it yourself):

```sql
-- Establish the exposed/private schema boundary and deny-by-default privileges
-- (T155.1). This migration creates no application tables; it only fixes the
-- privilege surface so that future objects are unreachable until a later
-- migration grants access explicitly and deliberately.
--
-- Baseline this corrects: Supabase's own bootstrap (run as `postgres` and
-- `supabase_admin`) installs `ALTER DEFAULT PRIVILEGES` entries on the
-- built-in `public` schema that auto-grant full CRUD on future tables and
-- USAGE on future sequences to `anon`/`authenticated`/`service_role`. Any
-- table created in `public` by a migration (which runs as `postgres`) would
-- silently inherit anonymous read/write access. This migration neutralizes
-- that default and moves the actual API surface to a schema Supabase never
-- auto-configures this way.

-- 1. Create the two application schemas.
--    `api`     - the only schema exposed to PostgREST (see supabase/config.toml).
--    `private` - never listed in config.toml's [api] schemas, so PostgREST
--                cannot route to it regardless of any grant below. Intended
--                for SECURITY DEFINER helper functions and internal-only
--                objects that must remain reachable solely via `api` wrappers
--                or direct database access (migrations, service_role).
create schema if not exists api;
create schema if not exists private;

comment on schema api is
  'Exposed Data API schema (see supabase/config.toml [api].schemas). Only objects granted here are reachable by anon/authenticated over the Data API.';
comment on schema private is
  'Never exposed via the Data API. Holds internal helpers; reachable only via SECURITY DEFINER wrappers in api or direct database access.';

-- 2. Revoke the automatic default privileges Supabase's bootstrap installed
--    "for role postgres" on `public` (migrations run as `postgres`, so this
--    is the entry that would otherwise auto-grant anon/authenticated full
--    CRUD on any table our own migrations create in `public`). A matching
--    "for role supabase_admin" entry also exists from the same bootstrap,
--    but `postgres` has no membership in `supabase_admin` and cannot alter
--    it; that is fine because application migrations never run as
--    `supabase_admin`, so it can never fire for objects we create. (`public`
--    itself is intentionally left out of [api].schemas as well, so this is
--    defense in depth against anything ever being created there.)
alter default privileges for role postgres in schema public
  revoke all on tables from anon, authenticated, service_role;
alter default privileges for role postgres in schema public
  revoke all on sequences from anon, authenticated, service_role;
alter default privileges for role postgres in schema public
  revoke all on functions from anon, authenticated, service_role;

-- 3. Strip `anon`/`authenticated`'s standing access to `public`. Two
--    separate grants currently give them this: an ambient PUBLIC
--    pseudo-role grant, and a direct GRANT USAGE Supabase's bootstrap makes
--    (owned by `pg_database_owner`, which `postgres` inherits as the
--    database owner). Both must be revoked; revoking only one leaves the
--    other in place. `service_role` keeps USAGE on `public` since Supabase's
--    own internal tooling relies on it and it already bypasses RLS.
revoke all on schema public from public;
revoke usage on schema public from anon, authenticated;

-- 4. Lock down the two application schemas by default: nobody but the
--    owning/administrative roles gets schema-level access, and no future
--    object in either schema is auto-granted to anon/authenticated. Each
--    later ticket that adds real tables/functions (T155.2-T155.7) must grant
--    access explicitly and per-object; nothing here is a standing exception.
revoke all on schema api from public, anon, authenticated;
revoke all on schema private from public, anon, authenticated;

alter default privileges in schema api
  revoke all on tables from public, anon, authenticated;
alter default privileges in schema api
  revoke all on sequences from public, anon, authenticated;
alter default privileges in schema api
  revoke all on functions from public, anon, authenticated;

alter default privileges in schema private
  revoke all on tables from public, anon, authenticated;
alter default privileges in schema private
  revoke all on sequences from public, anon, authenticated;
alter default privileges in schema private
  revoke all on functions from public, anon, authenticated;

-- 5. `authenticated` may enter the exposed schema itself (a prerequisite for
--    any future per-table GRANT to work at all); `anon` gets nothing here or
--    anywhere else, by deliberate policy of this prototype's threat model
--    (no publicly readable application resource is planned). `private` is
--    reachable only by `service_role`/`postgres` (for SECURITY DEFINER
--    helpers called from `api` wrappers); `authenticated`/`anon` never get
--    schema-level access to it.
grant usage on schema api to authenticated, service_role;
grant usage on schema private to service_role;
```

Why this order inside one migration (not split across several): schema
creation must precede every grant/revoke statement referencing `api`/
`private`; the `public`-schema cleanup has no dependency on the new schemas
and could technically run first or last, but keeping it as step 2-3 (right
after schema creation, before the new schemas' own lockdown) keeps the "fix
the inherited mess, then lock down the new territory" narrative readable in
one file. There is no reason to split this into multiple migration files —
it's one atomic policy change with no rollback/forward-compat concern (no
data exists yet).

## Step 2 — Change the Data API's exposed-schema config

In `supabase/config.toml`, under `[api]`:

```toml
schemas = ["api"]
```

(replacing `schemas = ["public", "graphql_public"]`). This is a real,
intentional narrowing: the built-in GraphQL endpoint (`graphql_public`)
becomes unreachable too, which is correct for "only `api` is exposed" and is
fine because nothing in this project uses GraphQL. Do **not** also add
`graphql_public` back in an attempt to preserve it — that would violate the
exit criterion literally ("only `api` is exposed") for a feature nothing
uses.

Leave `extra_search_path = ["public", "extensions"]` unchanged. That setting
only affects unqualified-name resolution inside function bodies executed via
the Data API (e.g. so `extensions.gen_random_uuid()` can be called as
`gen_random_uuid()`), not what PostgREST routes to — it does not reopen any
exposure. Extensions (`pgcrypto`, `uuid-ossp`, `pg_stat_statements`) already
live in the separate `extensions` schema, not `public`, confirmed via
`pg_extension` on a live instance, so the `public`-schema privilege revokes
above don't affect extension-function callability at all.

Leave the commented-out `# auto_expose_new_tables = true` alone (still
commented = still off = still deny-by-default; that's already correct and is
not this ticket's concern to touch).

**Important operational note discovered while validating this plan:**
`supabase db reset` does **not** pick up a `config.toml` `[api].schemas`
change — it only re-applies migrations/seed to the already-running Postgres
container. You must `supabase stop` then `supabase start` (a full container
recreation) for PostgREST/Kong to reload the new exposed-schema list. Budget
for this in verification: a `db reset` after only editing SQL migrations is
enough, but after editing `config.toml` you need a full `stop`/`start`.

## Step 3 — Verify

This exact recipe was run live against a real local stack while drafting
this plan; every response quoted below is a real observed result, not a
prediction.

From the repo root:

```sh
npx --yes supabase@2.115.0 stop
npx --yes supabase@2.115.0 start   # picks up the new config.toml
```

(A plain `db reset` is sufficient for iterating on the SQL alone once the
container has already picked up the new config once.)

**A. Catalog assertions** (`docker exec <db-container> psql -U postgres -d
postgres -c "..."`; the container is named `supabase_db_<project_id>`, e.g.
`supabase_db_daily-dama` for this worktree's `config.toml`). `supabase db
reset` succeeding at all is itself the first proof — it errors loudly on any
privilege-related SQL mistake, as happened twice while drafting this: once
for the `supabase_admin` default-privilege statement `postgres` isn't
allowed to run, and once where `public`'s direct USAGE grant was missed on
the first pass.

1. Both schemas exist:
   ```sql
   select schema_name from information_schema.schemata
   where schema_name in ('api','private') order by 1;
   -- expect exactly: api, private
   ```

2. Schema-level USAGE matches the intended matrix exactly:
   ```sql
   select nspname,
          has_schema_privilege('anon', nspname, 'USAGE') as anon_usage,
          has_schema_privilege('authenticated', nspname, 'USAGE') as auth_usage,
          has_schema_privilege('service_role', nspname, 'USAGE') as service_usage
   from pg_namespace where nspname in ('public','api','private') order by 1;
   ```
   Expected (confirmed live):
   ```
    nspname | anon_usage | auth_usage | service_usage
   ---------+------------+------------+---------------
    api     | f          | t          | t
    private | f          | f          | t
    public  | f          | f          | t
   ```

3. No default-ACL entries remain for `api`/`private` (i.e. nothing is
   auto-granted to anyone for future objects there):
   ```sql
   select n.nspname, da.defaclrole::regrole, da.defaclobjtype, da.defaclacl
   from pg_default_acl da join pg_namespace n on n.oid = da.defaclnamespace
   where n.nspname in ('api','private');
   -- expect 0 rows
   ```

**B. Live PostgREST/Data-API probes** (proves the exposure boundary, not
just the catalog state — get `ANON_KEY`/`API_URL` from `supabase status -o
env`):

4. Anonymous request to the exposed schema's root succeeds (200) and to
   any non-exposed schema is rejected with PostgREST's own "not exposed"
   error, independent of grants:
   ```sh
   curl -s http://127.0.0.1:54321/rest/v1/ -H "apikey: $ANON_KEY"
   # -> 200, standard OpenAPI doc for the api schema

   curl -s http://127.0.0.1:54321/rest/v1/ -H "apikey: $ANON_KEY" -H "Accept-Profile: private"
   # -> 406 {"code":"PGRST106",...,"message":"Invalid schema: private"}

   curl -s http://127.0.0.1:54321/rest/v1/ -H "apikey: $ANON_KEY" -H "Accept-Profile: public"
   # -> 406 {"code":"PGRST106",...,"message":"Invalid schema: public"}
   ```

5. A temporary probe function proves anon truly has no application-resource
   access even when the resource exists and is nameable, while an
   authenticated caller (with explicit grant) can reach `api` but never
   `private`. Create these **only** for this manual check, then drop them —
   they are not part of the migration itself, since this ticket intentionally
   ships zero permanent objects beyond the schemas/privileges:
   ```sql
   create function private.__t155_1_probe() returns text language sql stable
     as $$ select 'private-hit' $$;
   create function api.__t155_1_probe() returns text language sql stable
     security invoker as $$ select 'api-hit' $$;
   grant execute on function api.__t155_1_probe() to authenticated;
   ```
   Then (mint a quick HS256 `{"role":"authenticated"}` JWT signed with the
   local `JWT_SECRET` from `supabase status`, or use any already-existing
   test-account access token if one is easier to obtain in your session):
   ```sh
   # anon, no grant at all -> permission denied, not silently "not found"
   curl -s http://127.0.0.1:54321/rest/v1/rpc/__t155_1_probe -H "apikey: $ANON_KEY"
   # -> 401 {"code":"42501","message":"permission denied for schema api"}

   # authenticated, has the one explicit grant -> succeeds, from api only
   curl -s http://127.0.0.1:54321/rest/v1/rpc/__t155_1_probe \
     -H "apikey: $ANON_KEY" -H "Authorization: Bearer $AUTHENTICATED_JWT"
   # -> 200 "api-hit"

   # authenticated, asking for the private-schema function by name via
   # Content-Profile -> PostgREST does not route there at all; it silently
   # continues to resolve against the sole exposed schema (api), so the
   # *private* function is never reached even by an authenticated caller
   # explicitly asking for it
   curl -s http://127.0.0.1:54321/rest/v1/rpc/__t155_1_probe \
     -H "apikey: $ANON_KEY" -H "Authorization: Bearer $AUTHENTICATED_JWT" \
     -H "Content-Profile: private"
   # -> 200 "api-hit" (NOT "private-hit" -- proves private is unreachable,
   #    not merely that this one request was misrouted)
   ```
   Then clean up: `drop function private.__t155_1_probe(); drop function
   api.__t155_1_probe();` and run `supabase db reset` once more to confirm
   the migration alone (without the temporary probes) still resets cleanly.

6. Finally, `npx --yes supabase@2.115.0 db reset` succeeding with no errors,
   from a container that has never seen this migration before (i.e. after a
   `stop`), is itself the "clean local reset succeeds" exit criterion.

## Notes / things to not second-guess

- Do not try to make `postgres` revoke the `supabase_admin`-owned default
  privilege entry on `public` — it's a real permission wall (`postgres` is
  not a superuser and not a member of `supabase_admin` on this local stack),
  and it doesn't matter: no migration this project writes will ever run as
  `supabase_admin`, so that stale entry can never fire for anything we
  create. Don't spend time trying to work around it with `SET ROLE` or
  similar; it's a dead entry for our purposes.
- Do not add seed data or `supabase/seed.sql` as part of this ticket — it
  isn't referenced by the exit criteria, the `WARN: no files matched pattern:
  supabase/seed.sql` warning on reset is pre-existing/harmless (glob simply
  matches nothing), and introducing a seed file now would be scope creep.
- Do not grant `anon` USAGE on `api`/`private`/`public` "just in case" some
  future table wants to be public. If a later ticket needs an anonymous-
  readable resource, that is an explicit, reviewable `GRANT` added in that
  ticket's own migration — this ticket's job is to make the *default* be
  nothing.
- If, when you actually implement this, `postgres`'s relationship to
  `pg_database_owner`/`public` differs (e.g. a future Supabase CLI version
  changes bootstrap ownership), the `revoke usage on schema public from
  anon, authenticated;` statement is the one most likely to need
  re-verification — rerun query 2 above and adjust only if `public`'s
  `anon_usage`/`auth_usage` don't come back `f`/`f`.
