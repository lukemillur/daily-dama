# T150 — Automatically focus a trick when a goal is set for it

## Decision summary

- **Call site**: inside `GoalProvider.addGoal`, in `src/features/goals/state/goal-provider.tsx`.
  `GoalProvider` is already rendered as a descendant of `UserProfileProvider` in
  `src/app/app/_layout.tsx` (`UserProfileProvider > PracticeHistoryProvider > NoteProvider >
  GoalProvider`), so `GoalProvider` can call `useUserProfileActions()` directly. This keeps the
  cross-domain trigger in one place (the action itself) instead of duplicating it at both current
  `addGoal` call sites (`trick-goals-screen.tsx` and `all-trick-goals-screen.tsx`), and guarantees
  a third future call site can't forget it.
  - Trade-off to note explicitly: this makes `GoalProvider` newly depend on being mounted inside
    `UserProfileProvider` (it will throw via `useUserProfileActions`'s existing guard if not). That
    dependency already exists in practice via `_layout.tsx`'s nesting order, so this makes an
    existing implicit ordering explicit rather than introducing a new one. This is a deliberate,
    narrow coupling of two provider components in the tree, not a merge of their reducers,
    persistence, or storage keys, so it does not violate AGENTS.md's "don't combine domains into a
    global store."
  - This differs from the existing `KenteiRankAutoPromotion` cross-domain pattern (a separate
    non-rendering component reacting via `useEffect` to derived state). That pattern fits a
    continuously-recomputed derivation (auto-promotion rank). This task is a one-shot imperative
    side effect tied to a single user action ("as part of the same save action" in the exit
    criteria), so a direct synchronous call inside `addGoal` is simpler and avoids effect-timing
    edge cases (no need to track "previous" render state to detect a real transition).

- **Add-only profile action**: add a new reducer action rather than reusing `toggleSelectedTrick`
  conditionally. `toggleSelectedTrick` unconditionally flips membership, so calling it from
  `GoalProvider` would require first reading `selectedTrickIds` and only calling it when the trick
  is absent, an extra state read at the call site and a latent bug magnet if that guard is ever
  dropped. A dedicated action mirrors the existing `selectedTrickRemoved` action (which already
  no-ops safely when the trick isn't present) and keeps the "add if missing, else no-op" invariant
  inside the reducer where it can't be bypassed.

- **Write ordering**: no coordination needed between the two providers' persistence writes. Goals
  persist under `daily-dama:goals` (`GOALS_STORAGE_KEY`) and the profile persists under
  `daily-dama:user-profile` (`USER_PROFILE_STORAGE_KEY`), distinct AsyncStorage keys, each behind
  its own `createWriteQueue` instance. `createWriteQueue` only serializes writes within one queue
  to stop an in-flight write from being clobbered by a slower earlier one; it says nothing about
  cross-queue ordering, and there's no shared key for a cross-domain race to corrupt. Firing
  `dispatch({ type: 'goalAdded' })` and `addSelectedTrick(trickId)` back-to-back (each triggering
  its own provider's effect leading to enqueueWrite) is sufficient. Do not add awaiting or
  sequencing logic between them.

## Implementation steps

1. Profile reducer, add the mirror action (`src/features/profile/model/user-profile.ts`)
   - Add `{ readonly type: 'selectedTrickAdded'; readonly trickId: string }` to the
     `UserProfileAction` union, placed next to `selectedTrickRemoved` (around line 67-68).
   - Add a reducer case, mirroring `selectedTrickRemoved`'s no-op-when-absent shape: if
     `state.selectedTrickIds` already includes `action.trickId`, return `state` unchanged;
     otherwise return `{ ...state, selectedTrickIds: [...state.selectedTrickIds, action.trickId] }`.
   - Do this first, it's the foundation the provider and the goal-provider both depend on.

2. Profile provider, expose the action (`src/features/profile/state/user-profile-provider.tsx`)
   - Add `addSelectedTrick` to the `UserProfileActions` interface (near `toggleSelectedTrick`).
   - Add a `useCallback` that dispatches `{ type: 'selectedTrickAdded', trickId }`.
   - Add `addSelectedTrick` to the `actions` object and its `useMemo` dependency array (both the
     object literal and the deps list, this file keeps them manually listed, do not miss the deps
     array entry).

3. Goal provider, call across the boundary (`src/features/goals/state/goal-provider.tsx`)
   - Import `useUserProfileActions` from `@/features/profile/state/user-profile-provider`.
   - Inside `GoalProvider`, call `const { addSelectedTrick } = useUserProfileActions();` at the top
     of the component body, alongside the other hooks.
   - In `addGoal`, after `dispatch({ type: 'goalAdded', goal })` and before `return`, call
     `addSelectedTrick(goal.trickId)` (the created `goal` already carries `trickId` from
     `GoalCreationInput`/`createGoal`). Add `addSelectedTrick` to `addGoal`'s `useCallback`
     dependency array, it is stable (memoized with empty deps in step 2) so this will not cause
     churn.
   - Do not gate this call on the goal's `kind` or any other property, the exit criteria apply to
     any goal creation.

4. Keep the boundary constraint documented locally
   - `KenteiRankAutoPromotion`'s existing comment explains why it must render under both
     providers. Add a short comment above the new `useUserProfileActions()` call in
     `GoalProvider` (or above the import) noting that `GoalProvider` must be rendered inside
     `UserProfileProvider` for this reason, so a future reader considering reordering
     `_layout.tsx`'s providers sees the constraint locally rather than only in `_layout.tsx`.

5. Tests

   a. Reducer unit test (`src/features/profile/model/user-profile.test.ts`): add a test near the
      existing `selectedTrickToggled`/`selectedTrickRemoved` tests asserting `selectedTrickAdded`
      (i) adds a missing trick id, and (ii) is a no-op (same contents, ideally same reference) when
      the trick id is already present.

   b. New provider-level test (`src/features/goals/state/goal-provider.test.tsx`, a new file,
      following the `kentei-rank-auto-promotion.test.tsx` pattern for a harness that renders two
      nested real providers together):
      - Mock `@react-native-async-storage/async-storage` with the jest async-storage mock, same
        hoisting-comment pattern as `kentei-rank-auto-promotion.test.tsx`.
      - Build a small harness component rendered as
        `<UserProfileProvider><GoalProvider><Harness/></GoalProvider></UserProfileProvider>` that
        reads `useUserProfile().selectedTrickIds` and `useGoalActions().addGoal`, exposing both to
        the test (mirror the existing harness style in `kentei-rank-auto-promotion.test.tsx`,
        which exposes actions and state via pressable/text stand-ins found through the test
        renderer tree).
      - Test 1 (exit criterion 1): assert `selectedTrickIds` does not include a given trick id,
        call `addGoal({ trickId, ... })`, then assert it now does.
      - Test 2 (exit criterion 2): pre-seed `selectedTrickIds` to already include the trick id
        (check how `kentei-rank-auto-promotion.test.tsx`'s harness seeds `selectedTrickIds`, for
        example via `completeOnboarding` or a `profileRestored`-shaped seed, and reuse that
        approach), call `addGoal` for that same trick id, and assert `selectedTrickIds` is
        unchanged, same contents, not just "still includes it", confirm no duplicate got appended.
      - This test file is the one place that actually exercises the cross-provider wiring
        end-to-end; the reducer test in (a) only proves the reducer case is correct in isolation.

   c. Existing `trick-goals-screen.test.tsx` / `all-trick-goals-screen.test.tsx` fully mock
      `@/features/goals/state/goal-provider`, so they are unaffected by this change and need no
      edits, confirmed by inspection; do not add redundant assertions there.

6. Update TASKS.md in the same commit that closes T150, per AGENTS.md's instruction to update it
   in the same commit that closes a task (mark T150 done, matching the file's existing style for
   closed entries).

## Order rationale

Steps 1 to 3 are strictly bottom-up: the reducer case must exist before the provider action can
dispatch it, and the provider action must exist before `GoalProvider` can call it. Tests (5) follow
the implementation since the new provider-level test exercises the real wiring. Step 6 is last
because it is task-closing bookkeeping, not implementation.

## Risks / non-obvious pitfalls

- Do not forget the `useMemo` deps array in `user-profile-provider.tsx` when adding
  `addSelectedTrick`, this file lists callbacks explicitly, so it is easy to add the function to
  the object literal and forget the array, silently freezing `actions.addSelectedTrick` to a stale
  closure. (In this case the callback has no captured state, so the practical risk is low, but
  keep it consistent with the file's existing pattern.)
- Verify `createGoal`'s returned `Goal` actually carries `trickId` (it does, per `GoalBase` in
  `src/features/goals/model/goal.ts`) before wiring `addSelectedTrick(goal.trickId)`, use the
  validated `goal` object's field, not the raw `input`, since `input.trickId` is not guaranteed
  trimmed/normalized the same way `validateGoalCreation` produces it.
- The exit criteria only require `selectedTrickIds` gains the trick id; they do not ask for any
  change to `manuallyUnlockedTrickIds`, Kentei-rank promotion, or Stats. Do not let this task creep
  into re-running `KenteiRankAutoPromotion`-style logic, adding to `selectedTrickIds` alone is a
  UI-focus concern (which tricks show in the picker/session flows), unrelated to lacing/rank
  progression.
- Run the full verification sequence (`node .claude/scripts/verify.mjs`) before considering this
  done, this change touches a reducer, two providers, and adds a new cross-provider test file.
