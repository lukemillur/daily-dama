# T083.2 — Free-form color picker with a contrast guardrail

## Context confirmed before planning

- T083.1 (merged) added `themeBackgroundColor`/`themeAccentColor: string | undefined` (6-digit
  `#rrggbb` hex) to `UserProfile`, the `themeColorsUpdated` reducer action (both fields set
  together, clear-via-`undefined`), matching persistence validation (`isThemeColor` regex in
  `src/features/profile/persistence/user-profile-persistence.ts`), and
  `setThemeColors(bg, accent)` on `useUserProfileActions()`.
- Profile screen is `src/app/profile/index.tsx`. It already has one comparable inline
  self-contained settings section (`StreakSettings`): local text-input state, a dirty-gated Save
  button, an inline validity hint, styled-components styling with `AppColors`/typography from
  `src/components/ui`.
- The app's fixed text color is `AppColors.ink` (`#18382e`) in `src/constants/theme.ts` — the
  color used for headings/labels/primary button text throughout (`DisplayTitle`, `RankLabel`,
  `ButtonLabel` on the secondary variant, etc.). **Decision**: use `AppColors.ink` as the single
  "fixed text color" the contrast check validates against. Body copy (`BodyText`) uses the
  lighter `AppColors.textMuted`, but the task refers to one fixed text color, and `ink` is both
  the dominant text token and the stricter (darker) reference. Flagging this as a judgment call
  rather than a re-litigated decision — cheap to change the one constant later if it's wrong.
- No color-picker library is installed and none should be added: T083 Notes explicitly call for a
  free-form picker, not curated presets, and the codebase's existing convention for free-form
  numeric input (`StreakSettings`' minutes field) is a plain validated `TextInput`. A hex-code
  `TextInput` per color (with a live swatch preview) is the lowest-risk way to satisfy "free-form"
  without a native `<input type="color">` (which would need web-only branching and isn't
  necessary — hex entry is already fully free-form).
- "Picked independently" (T083 Notes) is taken literally: background and accent get separate
  fields, separate validity/contrast feedback, and separate Save actions — not one form that
  requires both to be edited together. Because `setThemeColors` replaces both fields on every
  call, each per-field Save must pass through the *other* field's current persisted value
  unchanged (e.g. saving background calls `setThemeColors(newBg, currentAccent)`).
- Contrast check is against the fixed text color only (task wording: "versus the app's fixed text
  color"), not background-vs-accent. So background and accent each get an independent WCAG AA
  (4.5:1) check against `AppColors.ink`; there is no cross-check between the two picked colors.

## Files to add/change, in order

1. **`src/shared/color/contrast.ts`** (new) — generic WCAG relative-luminance/contrast utility,
   not profile-specific, so it lives under `src/shared` rather than `src/features/profile`:
   - `hexToRgb` (accepts `#rrggbb`, returns `undefined` for anything else — reuse this permissive
     shape rather than throwing, since callers will feed it live user input).
   - `contrastRatio(hexA, hexB): number | undefined` — standard WCAG relative luminance formula
     (sRGB channel linearization, `0.2126/0.7152/0.0722` weights, `(L1+0.05)/(L2+0.05)` with
     `L1 >= L2`). Returns `undefined` if either hex is invalid.
   - `export const WCAG_AA_MIN_CONTRAST_RATIO = 4.5`.
   - `meetsMinimumContrast(hexA, hexB, minimumRatio = WCAG_AA_MIN_CONTRAST_RATIO): boolean`.
   - **`src/shared/color/contrast.test.ts`** alongside it (matches this repo's colocated-test
     convention, e.g. `model/user-profile.test.ts`): assert `contrastRatio('#000000','#ffffff')
     === 21`, same-color ratio `=== 1`, and the well-known WCAG boundary pair `#767676` vs
     `#ffffff` (~4.54:1, i.e. the standard reference gray that just clears AA) to pin the formula
     against a widely-cited real value rather than only self-consistent assertions.

2. **`src/features/profile/model/user-profile.ts`** — add
   `export function isValidThemeHexColor(value: string): boolean` (the `/^#[0-9a-fA-F]{6}$/`
   check), next to the other validators (`isValidStreakThresholdMinutes`). Add a couple of cases
   to `user-profile.test.ts` (or a new small test block) covering a valid hex, a 3-digit hex
   (invalid — this domain only accepts 6-digit), and a missing `#`.

3. **`src/features/profile/persistence/user-profile-persistence.ts`** — replace the local
   `isThemeColor` regex body with a call to `isValidThemeHexColor` (already imports from the model
   file). Pure refactor, no behavior change; confirm
   `user-profile-persistence.test.ts` still passes unmodified. Do this before building the UI so
   the UI and persistence share one validation source instead of a second hand-copied regex.

4. **`src/features/profile/components/theme-color-picker.tsx`** (new) — the picker itself,
   self-wired to the provider (calls `useUserProfile()` / `useUserProfileActions()` directly,
   matching how `index.tsx` currently reads hooks at the top level; unlike `StreakSettings` it
   does not need callback props since it owns both fields end to end).
   - Two `ColorField` blocks (`background`, `accent`), each rendering:
     - A section label (e.g. `SectionLabel`/`Title` reuse or simpler `DurationLabel`-style text —
       reuse existing typography/styled tokens rather than inventing new ones).
     - A hex `TextInput` (`accessibilityLabel="Background color hex"` /
       `"Accent color hex"`, `maxLength={7}`, `autoCapitalize="none"`), defaulting to the
       persisted value or `''`.
     - A small swatch `View` styled with the live typed hex as `background-color` when valid
       (dynamic styled-components prop, e.g. `$hex`), otherwise a neutral placeholder swatch.
     - A validity/contrast hint line, three states: malformed hex ("Enter a 6-digit hex color,
       e.g. #4477aa."), valid but insufficient contrast ("Too close to the app's text color to
       read clearly — pick something darker or lighter." plus the computed ratio, e.g.
       "Contrast vs. text: 2.1:1, need at least 4.5:1"), or valid and passing (contrast ratio
       shown, framed positively).
     - A per-field Save button, `disabled` unless: hex is valid via `isValidThemeHexColor`, it
       meets `meetsMinimumContrast(hex, AppColors.ink)`, and it differs from the currently
       persisted value for that field (dirty-gating, mirroring `StreakSettings`). On press, calls
       `setThemeColors(newBg, currentAccentColor)` (or the symmetric call for accent).
   - One shared "Reset to default" `Button` (secondary/small) below both fields, enabled only when
     either `themeBackgroundColor` or `themeAccentColor` is currently set; calls
     `setThemeColors(undefined, undefined)` and resets both local text fields to `''`.
   - Export both the default component and, if useful for tests, no extra named exports are
     required — tests can drive it through visible text/labels like the rest of this codebase's
     RN-testing-library-free `react-test-renderer` conventions.

5. **`src/features/profile/components/theme-color-picker.test.tsx`** (new, colocated — this repo
   colocates feature-level tests next to the file, e.g. `state/kentei-rank-auto-promotion.test.tsx`;

   - Typing a valid, sufficiently-contrasting background hex and pressing its Save button updates

   - Typing a hex with insufficient contrast against `AppColors.ink` (e.g. `AppColors.ink` itself,
     or another near-identical dark color) renders a visible warning message and leaves the Save
     button disabled / the probe's value unchanged after a press attempt.
   - (Optional but cheap) same two cases mirrored for the accent field, to cover the "picked

## Order rationale

Utility → model validator → persistence reuse → component → component tests → screen wiring →
screen-level reachability test. Contrast math and hex validation are pure and independently
testable, so they're built and pinned first; the component depends on both and should not be
written against an unverified formula. Persistence refactor happens before the component so the
component imports the same `isValidThemeHexColor` the persistence layer already relies on,
avoiding a second hand-written regex drifting from it later.

## Non-obvious risks / things to double check while implementing

- `setThemeColors` overwrites both fields on every dispatch (confirmed in the T083.1 reducer: no
  partial-merge semantics). Every per-field save call **must** pass the other field's current
  value, not `undefined` — passing `undefined` would silently clear the field the user wasn't
  touching. Get this right in both the background-save and accent-save handlers.
- Confirm `styled-components/native` supports a dynamic `background-color` from a transient prop
  cleanly for the swatch (`DurationHint`'s `$invalid` prop is the existing precedent for
  boolean-driven dynamic styling in this file's sibling — a string-driven color prop is the same
  pattern, just confirm interpolation of a runtime hex string works the same way).
- Keep `Date.now()`/timers out of this entirely — not applicable here, no timing behavior, but
  worth confirming the picker introduces no such coupling given the Sesh-reducer convention
  elsewhere in the codebase.
- This ticket does not apply the chosen colors anywhere in the app's chrome — that's T083.3. Don't
  scope-creep into wiring the theme into `Screen`/navigation here; the picker only previews via its
  own swatch and persists via the provider.
- Verification: run `node .claude/scripts/verify.mjs` (full sequence, not `--skip-export`, since
  this changes UI and TS types) before considering the task done. Web is the only active
  verification target per AGENTS.md — no iOS/Android checks.
