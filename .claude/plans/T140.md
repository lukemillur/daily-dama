# T140 -- Trigger the screenshot showcase's entrance animation on scroll into view

## Current state (verified in code)

landing-page.tsx's LandingPage maps screenshots directly to JSX, giving each
ScreenshotItem (a styled(Animated.View)) an entering prop using FadeInUp.
Reanimated's entering only fires the first time a given element instance
mounts, so today it always fires at initial page mount regardless of scroll
position (T131).

landing-page.test.tsx mounts LandingPage with react-test-renderer under
jest-expo's default (Node, no DOM) test environment, with Platform.OS
force-set to 'web'. There is no window/IntersectionObserver global in that
environment. Existing assertions expect all four screenshot-item nodes, and
their title/caption text, to be present immediately after mount() with no
extra scroll simulation. Any new gating logic must default to "already
entered" in that environment or these tests break.

ScreenshotItem's ref, once attached, resolves to the underlying
react-native-web DOM node on web (both plain View and Reanimated's
Animated.View forward refs through to the host node) -- this is what makes
observing it with IntersectionObserver viable, but has no precedent
elsewhere in this codebase, so verify it explicitly with a real browser
check per the exit criteria, not just by reading the type signatures.

## Approach

Gate each item's *first* mount of the animated element behind visibility,
using a key swap to force a genuine remount (since entering cannot be
retriggered by changing props on an already-mounted instance):

1. Each screenshot list entry becomes its own small component
   (ScreenshotEntry) instead of an inline JSX expression in the .map(),
   because it needs its own ref + hook state per item. The outer .map()
   keeps its existing stable key={screenshot.alt} on this wrapper so the
   *hook state itself* survives re-renders of the list.

2. Add a local hook, useHasEnteredViewport(ref), colocated in
   landing-page.tsx (per the task notes -- no shared hook file yet, nothing
   else in the codebase uses IntersectionObserver). Sketch (adapt exact
   TypeScript to what tsc accepts):

     function useHasEnteredViewport(ref) {
       const [hasEntered, setHasEntered] = useState(
         () => Platform.OS !== 'web' || typeof IntersectionObserver === 'undefined',
       );

       useEffect(() => {
         if (hasEntered) return;
         const node = ref.current;
         if (!node) return;

         const bottomMargin = Math.round(window.innerHeight / 3);
         const observer = new IntersectionObserver(
           (entries) => {
             const entry = entries[0];
             if (entry && entry.isIntersecting) {
               setHasEntered(true);
             }
           },
           { rootMargin: '0px 0px -' + bottomMargin + 'px 0px', threshold: 0 },
         );
         observer.observe(node);
         return () => observer.disconnect();
       }, [hasEntered, ref]);

       return hasEntered;
     }

   Key decisions baked into this shape:
   - Fallback default true: non-web platforms and any environment without a
     real IntersectionObserver (including the Jest test environment and the
     Node-side static export prerender pass) skip gating entirely and
     behave exactly like today (animate on mount). This is what keeps
     landing-page.test.tsx passing unmodified.
   - rootMargin '0px 0px -N%' semantics: shrinking the bottom edge of the
     (default, root: null) viewport by one-third makes the *effective*
     observed region the top two-thirds of the viewport, so isIntersecting
     only flips true once the element scrolls into that band -- exactly the
     "top two-thirds of the viewport" requirement.
   - Pixel margin computed from window.innerHeight, not a CSS percentage
     string: percentage rootMargin against the implicit (null) root is a
     newer, less universally-relied-on part of the spec. Computing an
     absolute pixel value from window.innerHeight at observer-creation time
     is unambiguous across browsers and easy to reason about. Do not add a
     resize listener to keep it live -- this is a one-shot, play-once
     trigger, not a continuously accurate breakpoint; recomputing only at
     mount is an intentional simplification, not an oversight.
   - No unobserve/disconnect-then-reobserve complexity: once isIntersecting
     is seen, hasEntered flips to true permanently (no reset), and the
     effect's cleanup (returned on the next render, since hasEntered is now
     true) disconnects the observer for good. This directly implements
     "scrolling past and back doesn't need to replay it" -- there is no
     code path that ever sets hasEntered back to false.

3. In ScreenshotEntry, keep an always-mounted ref (useRef pointed at the
   ScreenshotItem instance -- check the exact type with tsc; it may need
   to be the ref type Animated.View forwards, e.g.
   React.ComponentRef of typeof Animated.View, rather than plain View)
   and render ScreenshotItem itself with an *inner* key that flips once,
   forcing the remount that makes entering fire at the right time.
   Sketch of ScreenshotEntry's body:

     - const itemRef = useRef(null)
     - const hasEntered = useHasEnteredViewport(itemRef)
     - return ScreenshotItem, with:
         - key set to 'entered' once hasEntered is true, 'pending' before
           that (this is the remount trigger)
         - ref set to itemRef
         - testID="screenshot-item" (unchanged)
         - $isWebLayout unchanged
         - entering set to the existing FadeInUp expression when
           hasEntered is true, and undefined otherwise
         - style merging the existing boxShadow with opacity: hasEntered
           ? 1 : 0
         - the same Image / ScreenshotTitle / ScreenshotCaption children
           as today, unchanged

   Why this shape and not two separate styled components (an "animated"
   version and a "static placeholder" version): reusing the *same*
   ScreenshotItem styled component for both the pre-visible and
   post-visible render means the placeholder's box (border, background,
   padding, max-width) is pixel-identical to the final card automatically
   -- there's no separate CSS block to keep in sync, and no layout shift
   when it swaps in. The pre-visible instance is simply invisible
   (opacity: 0), still fully laid out (so sibling items don't jump and the
   IntersectionObserver measures a correctly-positioned, correctly-sized
   target), and carries no entering prop, so it doesn't animate. When
   hasEntered flips, the key change unmounts that instance and mounts a
   fresh one with entering set and opacity: 1 -- Reanimated sees a genuine
   new mount and plays FadeInUp.

   Items already inside the top two-thirds band at load:
   IntersectionObserver.observe() fires its callback with the element's
   actual current intersection state very shortly after observe() is
   called (next frame, effectively immediate), so these items flip
   hasEntered to true and remount with the animation almost immediately
   after first paint -- satisfying "items already in that band on load
   animate in immediately" without any special-cased branch. Don't try to
   special-case this by pre-computing layout synchronously; it isn't
   necessary and adds complexity for no behavior gain.

4. Update the .map() in LandingPage to render a ScreenshotEntry (keyed by
   screenshot.alt, same as today) instead of the inline ScreenshotItem
   JSX, passing screenshot, index, and isWebLayout through as props.

5. Leave ScreenshotItem's styled-components definition, ScreenshotSection,
   ScreenshotTitle, ScreenshotCaption, and the animation duration/easing
   (T139) completely untouched -- only the trigger condition and the new
   ScreenshotEntry/useHasEnteredViewport wrapper are new.

   styled(Animated.View)'s forwarded ref is the one genuinely unfamiliar
   piece here; resolve any mismatch before chasing runtime behavior.
2. yarn test --runInBand -- confirm landing-page.test.tsx passes
   unmodified (this is the regression signal that the
   no-IntersectionObserver fallback path is wired correctly).
3. yarn lint.
4. yarn expo export --platform web --output-dir /tmp/daily-dama-web-export
   -- confirms the static export's prerender pass doesn't choke on
   window/IntersectionObserver references (they're only touched inside
   useEffect, which doesn't run during that pass, but export catches any
   accidental top-level access).
5. Browser check (required by the exit criteria, not optional polish):
   run the Expo dev server (yarn expo start --web or equivalent per
   AGENTS.md's verification guidance -- do not serve the static export
   with a generic file server), then:
   - Load the landing page at a desktop width and confirm any screenshot
     item already in the top two-thirds of the viewport animates in
     immediately, and items further down do not animate until scrolled up
     into that band.
   - Scroll down slowly and confirm each remaining item's FadeInUp plays
     once as it crosses into the top two-thirds band.
   - Scroll past all items, then scroll back up, and confirm the
     animation does not replay.
   - Repeat at a mobile width (this is also the width where the CTA's own
     FadeInUp -- a different component, out of scope here -- already
     animates on mount only; don't confuse the two while checking).
   - Confirm no new console warnings/errors beyond the two known-benign
     ones documented in AGENTS.md.

## Risks / non-obvious things for the implementer

- The ref-through-styled-components/native-through-Animated.View-to-DOM-node
  chain has no precedent in this codebase. If itemRef.current turns out to
  be null or a non-DOM wrapper object on web, IntersectionObserver.observe()
  will throw or silently no-op -- catch this in the browser check, not just
  by trusting the type system.
- Do not attach the IntersectionObserver effect unconditionally -- guard on
  Platform.OS === 'web' (or the typeof IntersectionObserver === 'undefined'
  check alone, which is already platform-agnostic) so native builds never
  attempt this even though the active platform scope is web-only right now.
- Keep the key swap scoped to the inner ScreenshotItem, not the outer
  ScreenshotEntry wrapper -- swapping the outer key would remount the hook
  itself and reset hasEntered back to false every render, breaking the
  "once" guarantee.
- Resist the temptation to add a resize listener or re-observe on
  breakpoint change; it's unneeded complexity for a one-shot, play-once
  trigger tied to initial scroll position.
