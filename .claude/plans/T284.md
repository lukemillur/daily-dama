# T284 plan: native tab clearance for scroll content

## Findings (verified in source)

- `src/components/app-tabs.tsx` uses `NativeTabs` (expo-router 57.0.29, `expo-router/unstable-native-tabs`). Tab routes `sesh`, `tricks`, `profile` host a nested `Stack` (`_layout.tsx`); `home` and `stats` are plain screens.
- Installed `native-tabs/types.d.ts` (`disableAutomaticContentInsets`, line ~560): on iOS "the **first scroll view** nested inside a native tabs screen has automatic content inset adjustment enabled" (react-native-screens `overrideScrollViewContentInsetAdjustmentBehavior`, `NativeTabsView.ios.js:78`). The nav also wraps content in a `SafeAreaProvider` (`NativeTabsView.ios.js:71`). Android auto-wraps a bottom SafeAreaView (out of scope).
- Every tab-hosted screen uses shared `Screen` (`src/components/ui/screen.tsx`, a `react-native-safe-area-context` `SafeAreaView`) with `edges={['top','left','right']}` (Tricks: `['left','right']`) so no bottom inset is applied; native `Screen` sets `padding-bottom` only on web (`webBottomInset`).
- Inconsistent bottom reserves today: Home `paddingBottom: 24` (`daily-home.tsx:14`), Stats 24 (`stats/index.tsx:138`), Sesh `SCROLL_CONTENT_PADDING` = `{padding: 24}` native (`sesh.tsx:71`, used at 389/701/1034), multi-trick `padding: 24` (`multi-trick-sesh.tsx:504,555`), directory 24 or 0 with `fixedFooter` (`trick-directory.tsx:154,189`), custom form `FormScroll` 24 (`tricks/index.tsx:246`), notes/goals 24 (`trick-notes-screen.tsx:53,167`, `all-notes-screen.tsx:33,133`, `trick-goals-screen.tsx:56,206`, `all-trick-goals-screen.tsx:74`), Profile `120 + BottomTabInset` where `BottomTabInset = ios 50` (`theme.ts:99`, the only user). `CenteredPanel` in sesh/multi-trick uses `padding: ... 140px` bottom (non-scroll centred panels).
- Unknown (must be settled empirically, step 1): whether UIKit auto-adjust actually applies to each screen. It targets only the first scroll view and may not reach scroll views under the nested Stack, `SafeAreaView`, or a `SectionList` wrapped in `ListContainer` with `overflow: hidden`. The audit saw overlap on Home/Stats (non-stack) too, so the automatic path is evidently not covering the floating iOS 26 bar everywhere. Do not assume; measure.

## Risks and notes

- Double padding: auto content-inset adjustment plus a `Screen` bottom inset would add the tab height twice on the first scroll view. Step 1 must show this explicitly (compare content end position before/after). If double, set `contentInsetAdjustmentBehavior="never"` on the shared scroll styles or `disableAutomaticContentInsets` on the Trigger (that prop is the supported switch) rather than shaving values.
- `edges` bottom on a `SafeAreaView` under a tab screen: depends on the provider seeing the native screen's safeAreaInsets, which `NativeTabsView.ios` supplies via its own `SafeAreaProvider`; stack-nested screens (`tricks/*`) may report differently from `home`, so test a stack child specifically.
- Keyboard-visible behavior belongs to T044; do not add `KeyboardAvoidingView` here. Native lifecycle, providers, persistence unchanged.
- Web must be unchanged: gate everything on `Platform.OS !== 'web'` and keep existing web tests (`app-tabs.web.test.tsx`, home tests) green.
- Android and physical devices are out of scope; do not alter the Android `BottomTabInset` value.
