# T274 — Fix header bar disappearing after password-reset redirect to landing page

## Root cause (confirmed by reading code, not guessed)

`src/features/auth/model/auth-state.ts`'s `deriveAuthState` has a blanket carry-forward rule:

```ts
if (previous.status === 'passwordRecovery') {
  return { status: 'passwordRecovery', session };
}
```

This was added (per its own comment and the `auth-state.test.ts` case "keeps
passwordRecovery across a later TOKEN_REFRESHED") to stop `autoRefreshToken`'s
background `TOKEN_REFRESHED` events from silently promoting an in-progress
password-recovery session to `authenticated` mid-flow. But the guard is written
as "any event while previous status is passwordRecovery stays passwordRecovery,"
not "TOKEN_REFRESHED specifically stays passwordRecovery." That over-broad
condition also swallows `USER_UPDATED`.

`USER_UPDATED` is the real GoTrue event supabase-js's `GoTrueClient.updateUser()`
emits via `onAuthStateChange` on a successful password update (confirmed against
the installed `@supabase/supabase-js@^2.112.3` contract; this is standard,
documented supabase-js behavior, not project-local code). `completePasswordRecovery`
in `src/features/auth/state/auth-provider.tsx` calls exactly this:

```ts
const { error } = await client.auth.updateUser({ password: newPassword });
return { error };
```

...and deliberately does **not** touch `state` itself — per the existing test
"State does not mutate directly from the action -- only via a subsequent real
event," state transitions are meant to flow only through the real
`onAuthStateChange` subscription. That's the correct design; the bug is that the
subsequent real `USER_UPDATED` event gets discarded by the carry-forward guard
instead of being allowed to promote the state to `authenticated`.

Consequence: after a successful password reset, `AuthState.status` stays stuck at
`'passwordRecovery'` for the remainder of that page load. `LandingAuthCta`
(`src/features/landing/components/landing-auth-cta.tsx`, the actual "header bar" —
`testID="landing-header-bar"`) gates on:

```ts
const isGuest = authState.status === 'guest';
const isAuthenticated = authState.status === 'authenticated';
if (!isGuest && !isAuthenticated) return null;
```

`'passwordRecovery'` matches neither, so the header renders `null` on the landing
page the user is redirected/navigates to after completing the reset. A manual
refresh reloads the whole app: `AuthProvider`'s init effect starts a fresh
`useState<AuthState>(INITIALIZING_AUTH_STATE)`, and the first real event
(`INITIAL_SESSION`/`SIGNED_IN`) is derived with `previous = INITIALIZING_AUTH_STATE`
(not `passwordRecovery`), so it correctly resolves to `authenticated` and the
header reappears. This exactly matches the reported "refresh fixes it" symptom —
it is a stuck-status bug, not a missing-element or CSS bug, and not a
hydration/SSR gap.

This also explains why the note in `landing-auth-cta.tsx`'s own comment ("T265's
actual reported bug turned out to be unrelated to this component") didn't catch
this: that prior investigation was about scroll-position/`includeWebHeaderInset`
layout, a different bug in the same area.

## Fix

Narrow the carry-forward guard in `deriveAuthState` (`src/features/auth/model/auth-state.ts`)
so `USER_UPDATED` is treated as flow completion and promotes to `authenticated`,
while any other event during `passwordRecovery` (chiefly `TOKEN_REFRESHED`) still
carries `passwordRecovery` forward as today. Add the `USER_UPDATED` branch
**before** the existing `previous.status === 'passwordRecovery'` check:

```ts
if (event === 'USER_UPDATED') {
  return { status: 'authenticated', session, lastEvent: event };
}

if (previous.status === 'passwordRecovery') {
  return { status: 'passwordRecovery', session };
}
```

This is safe for the other current `updateUser` caller too: `changePassword` in
`auth-provider.tsx` only runs when `stateRef.current.status === 'authenticated'`,
so a `USER_UPDATED` event it triggers already falls through the normal
"promote to authenticated" path today (`previous.status` isn't `passwordRecovery`)
— the new explicit branch changes nothing for that flow, it only fixes the
`passwordRecovery` → `USER_UPDATED` case that was previously swallowed.

No change is needed to `completePasswordRecovery` itself, `LandingAuthCta`, or
any redirect/navigation code — the state machine was the only broken link.

## Ordered implementation steps

1. **`src/features/auth/model/auth-state.ts`** — add the `USER_UPDATED` branch
   above the `passwordRecovery` carry-forward check, as shown above. This is the
   only production code change. Update/add the doc comment above `deriveAuthState`
   (currently says the carry-forward exists so a recovery session "survive[s] a
   later `TOKEN_REFRESHED`... without being silently promoted to plain
   `authenticated` mid password-reset flow") to note that `USER_UPDATED` is the
   deliberate exception that *does* promote it, since that event signals the
   recovery flow's own completion.

2. **`src/features/auth/model/__tests__/auth-state.test.ts`** — add unit coverage
   for the fixed behavior (this is the primary, fastest-feedback test surface for
   a pure function change):
   - `deriveAuthState('USER_UPDATED', session)` with no `previous` → `authenticated`
     (guards against a regression where `USER_UPDATED` ever needs default
     handling not tied to recovery).
   - A `passwordRecovery` → `USER_UPDATED` case: given `previous = deriveAuthState('PASSWORD_RECOVERY', fakeSession)`,
     `deriveAuthState('USER_UPDATED', updatedSession, previous)` →
     `{ status: 'authenticated', session: updatedSession, lastEvent: 'USER_UPDATED' }`.
     This is the exact regression case for T274.
   - Keep the existing `TOKEN_REFRESHED` carry-forward test passing unchanged —
     it proves the narrowing didn't over-correct.

3. **`src/features/auth/state/__tests__/auth-provider.test.tsx`** — add one
   integration-level test exercising the real event path end to end: mount,
   `fake.emit('PASSWORD_RECOVERY', session)`, call
   `completePasswordRecovery('new-password-123')` (as the existing test at
   line ~482 does), then `fake.emit('USER_UPDATED', updatedSession)` and assert
   `captured.state` is now `{ status: 'authenticated', session: updatedSession, lastEvent: 'USER_UPDATED' }`.
   This is the test that would have caught the original bug — the existing
   `completePasswordRecovery calls updateUser...` test at line ~482 only checks
   state immediately after the action resolves (still `passwordRecovery`, which
   is correct given the fake client doesn't auto-emit `USER_UPDATED`), so it
   never exercised the subsequent real-event promotion this fix depends on.
   Do **not** modify that existing test's assertion — it remains correct for
   what it's testing (the action itself doesn't mutate state).

4. **No change** to `landing-auth-cta.tsx`, `landing-auth-cta.test.tsx`,
   `reset-password-screen.tsx`, or any redirect/navigation code — confirmed by
   reading `LandingAuthCta`'s existing `AuthState`-driven test file, which
   already exercises `authenticated`/`guest` states correctly; the component was
   never the bug.

## Risks / non-obvious notes for the implementer

- Do not widen the fix by making `USER_UPDATED` always promote regardless of
  context, or by removing the `previous.status === 'passwordRecovery'` guard
  entirely — `TOKEN_REFRESHED` during an in-progress (not-yet-submitted) recovery
  session must still carry `passwordRecovery` forward, or a background token
  refresh while the user is still looking at the "choose a new password" form
  would silently boot them out of the recovery UI (this exact regression is
  already covered by the existing `keeps passwordRecovery across a later
  TOKEN_REFRESHED` test — do not touch that test or that behavior).
- The `SIGNED_OUT`/null-session guards at the top of `deriveAuthState` already
  run before either the new `USER_UPDATED` branch or the `passwordRecovery`
  carry-forward, so no ordering conflict there — verify this remains true after
  editing (i.e. keep the new branch below the `SIGNED_OUT` and `!session` checks,
  above the `PASSWORD_RECOVERY` and carry-forward checks).
- This is a state-machine correctness fix with no UI/layout change, so the
  320px/desktop parts of the exit criteria are about confirming the *same* fix
  renders correctly at both breakpoints, not about needing separate per-breakpoint
  code paths.
