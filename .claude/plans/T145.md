# T145 -- Eliminate the flash of unstyled content on `/`

## Root cause (confirmed by reading the current tree)

`src/app/_layout.tsx` wraps *every* route -- including `/` (`src/app/index.tsx`) --
in `CustomTrickProvider > UserProfileProvider > PracticeHistoryProvider >
NoteProvider > GoalProvider > AppThemeProvider`. Each of the four persistence
providers (`custom-trick-provider.tsx`, `user-profile-provider.tsx`,
`practice-history-provider.tsx`, `goal-provider.tsx`; `note-provider.tsx` too)
independently returns its own full-screen "Loading..." fallback until its own
`hasHydrated` flips true, and each provider only starts its `AsyncStorage`
read once it mounts -- which, because they're nested, only happens after the
provider above it has already hydrated. So today's load sequence for `/` is a
strict waterfall of distinct full-screen paints (splash -> custom-tricks
fallback -> profile fallback -> practice-history fallback -> landing page),
not a single hydration wait. That waterfall is the "jarring sequence of
sub-second paints" QA reported.

Separately, `LandingCta` (`src/features/landing/components/landing-cta.tsx`)
and `useRedirectOnboardedVisitorHome`
(`src/features/landing/state/redirect-onboarded-visitor-home.ts`) both call
`useUserProfile()`, which only exists inside `UserProfileProvider` -- so the
landing route is architecturally coupled to that provider today, not just
incidentally rendered under it.

A third, less obvious coupling: `LandingCta`'s `CtaButton` is `styled(Button)`,
and `Button` (`src/components/ui/button.tsx`) reads
`theme.buttonBackground` / `theme.accent` / `theme.text` from the
styled-components theme with no fallback. That theme is only ever provided by
`AppThemeProvider` (`src/features/profile/components/app-theme-provider.tsx`),
which calls `useResolvedTheme()` -> `useUserProfile()`. If the persistence
providers are removed from wrapping `/` without replacing this, the CTA
button's colors silently resolve to `undefined` in production
(styled-components without an ancestor `ThemeProvider` supplies `theme = {}`,
not a throw -- so nothing fails loudly; existing unit tests don't wrap
`LandingCta` in a `ThemeProvider` either and don't assert on color, so this
regression would go unnoticed by the test suite). This must be fixed as part
of the provider-tree change, not left as a follow-up.

## Decisions this plan settles

1. Scope hydration-gated persistence providers to `/app/*` only. Move
   `CustomTrickProvider`, `UserProfileProvider`, `PracticeHistoryProvider`,
   `NoteProvider`, `GoalProvider`, `AppThemeProvider`, and
   `KenteiRankAutoPromotion` out of `src/app/_layout.tsx` and into
   `src/app/app/_layout.tsx` (the existing `/app` route-group layout, which
   today is just `export default function AppShellLayout() { return
   <AppTabs />; }`). `/` is the only route today outside `/app/*` that reads
   any of these (grep confirms -- `+html.tsx` is a static document shell with
   no React state). This directly satisfies "scope rehydration-driven UI to
   the `/app` routes only."

2. Give the root layout a small, synchronous, non-personalized
   styled-components theme, so components shared between `/` and `/app/*`
   (here: `Button`) still resolve real colors on `/` without needing
   `UserProfileProvider`. Add `DefaultAppThemeProvider` next to the existing
   `AppThemeProvider` in `app-theme-provider.tsx`, wrapping children in
   `StyledThemeProvider` with `theme={resolveTheme({})}` -- the same pure,
   synchronous function `AppThemeProvider` already calls, just invoked with no
   preferences instead of the user's profile. `resolveTheme({})` is exactly
   what every pre-onboarding user already sees today (theme fields are only
   ever set post-onboarding), so this is a no-op for the common case. The only
   behavior change: a returning user who has picked custom theme colors and
   navigates back out to `/` will now see the landing CTA button in the fixed
   default palette instead of their personal colors. Landing already uses the
   fixed `AppColors` palette everywhere else (`CtaPanel`, `Screen`'s explicit
   `background={AppColors.paper}`, etc.) -- the button was the one accidental
   exception -- so this is a correctness fix, not a new inconsistency. Flag it
   to the user as an intentional, low-risk side effect; don't silently work
   around it some other way.

   Mount `DefaultAppThemeProvider` in `src/app/_layout.tsx` around `<Slot />`
   (outside the `/app` subtree's own `AppThemeProvider`, which nests inside it
   and overrides it for anything under `/app/*` -- ordinary styled-components
   theme nesting, no special wiring needed).

3. Resolve `hasCompletedOnboarding` for the landing route via a synchronous,
   pre-hydration cache read, following the exact precedent already in the
   codebase for the same storage key
   (`src/features/profile/persistence/read-cached-theme-background.ts`,
   consumed by `src/components/animated-icon.web.tsx`) and the sibling
   precedent in `src/features/landing/components/landing-hero.tsx`'s
   `useSyncExternalStore`-for-hydration-boundary pattern (used there for
   WebGL availability, not storage, but the exact same "static export's Node
   prerender pass and the very first client render must agree" reasoning
   applies here). Concretely:

   - New pure reader: `src/features/profile/persistence/read-cached-onboarding-status.ts`,
     mirroring `read-cached-theme-background.ts` structurally (same
     `getItem: (key: string) => string | null` injection so it stays
     platform-agnostic and unit-testable, same try/catch-to-safe-default
     shape, reuses `deserializeUserProfile` and `USER_PROFILE_STORAGE_KEY`
     from `user-profile-persistence.ts`). Returns
     `{ hasCompletedOnboarding: boolean; kenteiRank: number | undefined }`
     (both fields, since `useRedirectOnboardedVisitorHome` needs
     `kenteiRank !== undefined` too -- don't split into two readers for one
     extra field).
   - New hook: `src/features/landing/state/use-cached-onboarding-status.ts`,
     `useCachedOnboardingStatus()`. On web: use the
     `useSyncExternalStore(emptySubscribe, () => true, () => false)`
     hydration-boundary flag exactly as `animated-icon.web.tsx` does, and once
     that flag is true, call `readCachedOnboardingStatus((key) =>
     window.localStorage.getItem(key))` directly in the render body (not
     itself wrapped in `useSyncExternalStore` -- match the existing
     precedent, which only uses `useSyncExternalStore` for the boolean
     hydration gate, not for the storage read itself, avoiding the "snapshot
     must be referentially stable" pitfall a naive read-as-snapshot would
     hit). On native (`Platform.OS !== 'web'`, no synchronous storage API
     exists), fall back to one non-blocking `AsyncStorage.getItem` read in a
     `useEffect` that updates local state when it resolves -- this preserves
     today's native behavior (delayed correction, no hard requirement for a
     synchronous first paint) at low cost, per AGENTS.md's "keep React
     Native code portable where low-cost, don't spend iteration time
     validating it" -- don't invest further in native correctness or verify
     it in a simulator.
   - Update `LandingCta` to call
     `useCachedOnboardingStatus().hasCompletedOnboarding` instead of
     `useUserProfile().hasCompletedOnboarding`.
   - Update `useRedirectOnboardedVisitorHome` to call
     `useCachedOnboardingStatus()` and read both fields instead of
     `useUserProfile()`.

   Why this avoids a visible flip (not just a plausible-sounding hook):
   Expo's web output is `"output": "static"` (`app.json`), which prerenders
   route HTML at build time in Node -- there is no `window`/`localStorage`
   at that point, so the first paint (prerendered HTML) and the first client
   render must agree on a fixed default, exactly the pattern
   `landing-hero.tsx`'s own comment documents for its `getServerSnapshot`.
   `useSyncExternalStore`'s post-hydration mismatch check is applied
   synchronously before the browser paints (this is why
   `AnimatedSplashOverlay` and `LandingHero` both use it instead of
   `useState` + `useEffect`, which would paint the default, then paint again
   after an effect -- a visible flip). Using the same primitive here gets the
   same "no extra visible frame" guarantee for `hasCompletedOnboarding`, for
   the same underlying reason, rather than by coincidence.

## Risks / things to double-check while implementing

- Ordering of steps 7 and 8 matters: moving the providers into
  `src/app/app/_layout.tsx` first (step 7) means both layouts briefly
  provide them (harmless -- nested duplicate providers, each independently
  hydrating/writing its own AsyncStorage key so no cross-talk) until step 8
  removes the outer copy. Never remove the root providers before the
  `/app` layout has its own copy, or `/app/*` routes will crash on
  `useUserProfile()` outside a provider.
- `useSyncExternalStore` snapshot stability: do not pass
  `readCachedOnboardingStatus(...)` itself as the `getSnapshot` argument to
  `useSyncExternalStore` -- it returns a fresh object each call, which trips
  React's "the result of getSnapshot should be cached" infinite-loop
  warning. Use `useSyncExternalStore` only for the boolean hydration-gate
  (stable literals), then call the reader as a plain function in the render
  body, exactly as `animated-icon.web.tsx` does today.
- Practice-history and custom-trick domains are untouched by this change --
  this plan only relocates where their providers mount, not their reducers,
  persistence adapters, or hydration-skip-first-write behavior. Verify
  after the move that `PracticeHistoryProvider`'s and `CustomTrickProvider`'s
  `shouldSkipInitialWrite` refs still behave correctly -- they should, since
  nothing about a provider's own internal effect timing changes when its
  parent component changes, only when it itself mounts/unmounts, which now
  happens once, at `/app/*` navigation, instead of once at app boot. One
  consequence worth confirming empirically: today all three persistence
  domains mount once at boot and stay mounted for the app's lifetime
  (client-side navigation doesn't remount `_layout.tsx`). After this
  change, they mount only once the user first navigates under `/app/*` and,
  importantly, will unmount if the user navigates back to `/` (e.g. via the
  "exit to landing" link) and remount if they return to `/app/*` --
  re-running the full hydration/loading-fallback sequence each time.
  Confirm this round-trip re-hydration is acceptable (it likely is, since
  `/` itself no longer blocks, and `/app/home` briefly re-showing its
  existing loading fallback on return is a pre-existing,
  in-scope-for-`/app` experience) rather than assuming it away -- if it's
  judged too jarring, the fallback-screen-per-domain UX for `/app/*` (not
  just where the providers mount) may be the right follow-up, but that's
  out of this task's scope per the "ideally just the one flag" framing,
  which is specifically about `/`.
- `DefaultAppThemeProvider` vs. `AppThemeProvider` naming: make sure the
  export doesn't get confused with expo-router's own `ThemeProvider`
  already imported in `_layout.tsx` under the unaliased name
  `ThemeProvider` -- keep the existing file's `StyledThemeProvider`
  aliasing convention.
- Do not introduce any new persistence document version or migration
  scaffolding -- `read-cached-onboarding-status.ts` reads the existing v1
  `daily-dama:user-profile` document via the existing
  `deserializeUserProfile`, it does not define a new schema.
