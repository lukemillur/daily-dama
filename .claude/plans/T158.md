# T158 — Protect logout when account changes are unsynchronized

## Confirmed current state (read in full before starting)

- **Dependencies are all merged into `development`**: T154.2 (`048e47f`, current-device logout via `signOut({ scope: 'local' })`), T156.3 (`c27b08d`, cross-account local-data isolation), T157.9 (`c6d96db`, the shared `useSyncCoordinator`/`SyncCoordinatorProvider`). Nothing is blocking.
- **`src/features/auth/state/auth-provider.tsx`**: `signOut()` already calls `client.auth.signOut({ scope: 'local' })` -- this already satisfies "other-device sessions remain signed in" and must not change. `AuthProvider`'s own `onAuthStateChange` listener is the single source of truth for the transition to `'guest'`; nothing should force it.
- **`src/features/auth/components/account-section.tsx`**: today, "Log out" directly calls `signOut()` with a local `isSubmitting`/`errorCategory` `useState` pair and a synchronous double-press guard (`isSubmittingRef`). It has no knowledge of pending sync work. `src/features/auth/components/__tests__/account-section.test.tsx` mounts `<AccountSection />` standalone (no `SyncCoordinatorProvider`, no `IdentityProvider`) and mocks `@/features/auth/state/auth-provider` directly -- any new dependency this component takes on sync/coordinator hooks must be added to that mock or the existing 9 tests will throw "must be used within provider".
- **Each of the five domains has an independent, structurally-identical sync driver hook** (`use-profile-domain-sync.ts`, `use-custom-trick-domain-sync.ts`, `use-practice-history-domain-sync.ts`, `use-goal-domain-sync.ts`, `use-note-domain-sync.ts`), each wrapping a parallel `useIdentityScopedDomain<SyncEnvelope<Snapshot>, ...>` instance (the outbox/cursor bookkeeping envelope, separate from the primary reducer state). Each hook's result (re-exported one-for-one by each provider as `UserProfileSync`/`CustomTrickSync`/`PracticeHistorySync`/`GoalSync`/`NoteSync`) currently exposes only `{ runSync, isSyncing, lastResult, hasHydrated, localMutationTick }` -- no pending-outbox count and no discard action exist anywhere today.
- **`src/shared/sync/sync-envelope.ts`** is the single shared reducer/mutation-function file backing all five envelopes (`syncEnvelopeReducer`, `applyLocalMutation`, `acknowledgeOutboxOperation`, `recordOutboxOperationAttempt`, etc., each guarded by `checkIdentity`). Each domain's own `XSyncEnvelopeAction` type is a bare alias and each domain's own `xSyncEnvelopeReducer` is a bare re-export of `syncEnvelopeReducer` -- adding one new action/case here propagates to all five domains with zero per-domain edits.
- **`src/shared/persistence/use-identity-scoped-domain.ts`** is the shared hook behind every identity-scoped domain (both the five primary reducers and the five sync envelopes). Its internal `enqueueWrite` (built once via `useMemo(() => createWriteQueue(...), [context])`, stable) is the only writer that should ever touch a given domain's storage key -- a second, independent write path risks a stale queued write clobbering a fresher one. It currently returns `{ state, dispatch, hasHydrated }`; `enqueueWrite`'s own promise is discarded (`void enqueueWrite(...)`) by its one call site inside an effect.
- **`src/shared/sync/coordinator.ts`** (`syncCoordinatorReducer`) is pure/single-flight: `syncRequested` starts a run or coalesces into `queuedRerunTrigger` if one is already running; `domainSettled` accumulates per-domain results and returns to `idle` once all `SYNC_DOMAINS` have reported; `identityChanged` cancels an in-flight run. `src/shared/sync/use-sync-coordinator.ts` is the React driver: `requestManualSync()` dispatches a `'manual'` trigger; single-flight coalescing means a manual retry pressed while another trigger is already running still gets folded into that run or the queued rerun that follows -- a caller waiting on "did my retry actually run" only needs to observe one full `running -> idle` transition after requesting it, not track a specific `runId`.
- **`src/shared/sync/sync-coordinator-provider.tsx`** (`SyncCoordinatorProvider`) already holds direct references to all five real domain sync objects before narrowing them into the `SyncDomainHandles` shape `useSyncCoordinator` consumes -- this is the natural place to aggregate cross-domain facts (pending count, discard-all) without touching `use-sync-coordinator.ts`/`coordinator.ts` at all. It currently exposes only `useSyncCoordinatorStatus()` returning `{ state, requestManualSync }`; no UI consumes it yet.
- **`src/shared/persistence/identity-provider.tsx`** (`useIdentityHandle()` -> `{ identity, generation, context }`) and **`use-identity-scoped-domain.ts`** together already guarantee that once identity/generation changes, every domain provider re-shows its hydration-fallback screen (`hasHydrated` is redefined per-generation, not one-shot) until the new identity's own namespace finishes loading -- this is what makes "subsequent guest/user identities cannot access discarded account cache" structurally already true for the rendered UI; T158 does not need to invent new state-clearing infra for that part. What T158 does need to guarantee is that a discarded outbox is durably written to the old identity's own storage before that identity's own generation moves on, so the discarded operations can never resurface and be pushed on a later login as this same user.
- **`src/app/app/_layout.tsx`** nesting: `IdentityProvider > CustomTrickProvider > UserProfileProvider > PracticeHistoryProvider > NoteProvider > GoalProvider > SyncCoordinatorProvider > AppThemeProvider > AppTabs`. `AccountSection` renders inside the Profile route, itself inside `AppTabs`, so it is already inside `SyncCoordinatorProvider` in the real app -- only the standalone component test needs a new mock.
- **No React Native `<Modal>` precedent** -- `RankUpCelebrationModal` (`src/features/profile/components/rank-up-celebration-modal.tsx`) sets the precedent: a full-screen absolute-fill `<View accessibilityLabel="...">` overlay styled with the app's own `Button`/`BodyText` primitives, not the RN `Modal` API. Follow this for the logout prompt.
- **`Button`** (`src/components/ui/button.tsx`) only has `variant: 'primary' | 'secondary'`, no dedicated destructive variant -- convey "Discard" as destructive through its label text, not color alone.
- **This ticket is explicitly narrower than T160.1** ("Add a trustworthy synchronization status model and Profile surface", not started, depends only on T157.9). T160.1 will later build a full derived, mutually-exclusive status model and a Profile-wide status surface with manual retry. T158 must add only the minimal `pendingCount`/discard primitives it needs for the logout gate -- do not build a general status model, a Profile status card, or a `/app/profile/sync-conflicts`-style route here. It is fine (and expected) for T160.1 to later reuse the `pendingCount`/`discardAllPending` aggregation this ticket adds to `SyncCoordinatorProvider`.

## Design decisions

1. **Expose pending-outbox facts and a discard action from each domain's sync driver, uniformly.** Add two fields to each `UseXDomainSyncResult`/provider-level `XSync` interface (all five domains):
   - `pendingCount: number` -- read directly from the driver's own render-time `envelope.state.outbox.length` (a plain derived value, not stashed in a ref, so it stays reactive across renders -- unlike `runSyncImpl`'s internals, this must NOT be read through `latestRef`).
   - `discardPending: () => Promise<void>` -- clears that domain's outbox durably (see decision 2) without touching the primary reducer's rendered state. Discarding removes only the sync obligation; the local edit itself stays applied in the primary domain state exactly as-is. This is a deliberate simplification: T158 does not add any "revert local state to last-synced snapshot" mechanism (none exists in this codebase today, and building one is a materially larger, five-domain-touching feature). Flag this as a known limitation in the closing notes: after Discard, an abandoned local-only edit sits in the primary domain's own persisted state and will not be automatically re-queued for sync on a later login by this same user (the outbox diff effects in each `use-X-domain-sync.ts` only fire on a subsequent state change, not on initial hydration) -- acceptable prototype behavior per this ticket's scope, not silently swept under the rug.

2. **Route the discard write through the same write queue the envelope already uses, to avoid a durability race.** Add `saveNow: (value: State) => Promise<void>` to `UseIdentityScopedDomainResult` (`use-identity-scoped-domain.ts`), implemented as a thin wrapper around the hook's existing internal `enqueueWrite` (`const taggedGeneration = context.getGeneration(); return enqueueWrite({ value, taggedGeneration });`). This is additive and backward-compatible -- no existing caller destructures exhaustively. Each `use-X-domain-sync.ts` hook's new `discardPending()`:
   - reads the current identity/envelope state from its existing `latestRef` (same pattern `runSyncImpl` already uses),
   - no-ops if `envelopeState.outbox.length === 0`,
   - computes the discarded envelope via a new pure `discardPendingOperations(envelope, identity)` (decision 3), no-oping (via the existing `checkIdentity` rejection path) if the identity has already changed underneath,
   - awaits `envelopeSaveNow(result.envelope)` -- durably persisting the cleared outbox through the FIFO queue before the promise resolves -- then dispatches `{ type: 'outboxDiscarded', identity }` to sync the in-memory copy (the effect-driven write that follows this dispatch is redundant but harmless/idempotent).

   This guarantees: by the time `discardPending()`'s returned promise resolves, the identity's own storage no longer has the discarded operations, before the caller is allowed to proceed to `signOut()`. Do not build a second, independent write path outside `enqueueWrite` -- that would reopen exactly the stale-write-ordering race `use-identity-scoped-domain.ts`'s doc comments already call out.

3. **New shared primitive in `src/shared/sync/sync-envelope.ts`**: `discardPendingOperations<State>(envelope, identity): SyncEnvelopeMutationResult<State>` -- mirrors `acknowledgeOutboxOperation`'s identity guard but unconditionally clears the whole outbox (`{ ...envelope, outbox: [] }`), since these operations were never applied server-side (no revision-cache changes needed). Add `{ readonly type: 'outboxDiscarded'; readonly identity: Identity }` to `SyncEnvelopeAction<State>` and a matching case in `syncEnvelopeReducer`. This single edit is inherited by all five domains' action/reducer aliases automatically.

4. **Aggregate pending count and a cross-domain discard in `SyncCoordinatorProvider`**, not in `use-sync-coordinator.ts`/`coordinator.ts` (those stay untouched -- they only need the narrower `SyncDomainHandle` shape they already have). Extend the exposed context value:
   ```ts
   interface SyncCoordinatorStatus extends UseSyncCoordinatorResult {
     readonly pendingCount: number; // sum of all five domains' pendingCount, reactive
     readonly discardAllPending: () => Promise<void>; // Promise.all across all five discardPending()
   }
   ```
   Computed directly from the five already-in-scope domain sync objects the provider holds, memoized on those five objects. This is the one piece of this ticket that overlaps with T160.1's eventual scope -- keep it to exactly these two fields, no UI here.

5. **New pure state machine for the logout-guard UI flow**, `src/features/auth/state/logout-guard.ts` (mirrors the `syncCoordinatorReducer`/`use-sync-coordinator.ts` pairing precedent -- pure reducer, thin React driver, no `Date.now()`/network/timers inside the reducer):
   ```ts
   type LogoutGuardStatus = 'idle' | 'prompt' | 'retrying' | 'discarding' | 'signingOut';
   interface LogoutGuardState {
     readonly status: LogoutGuardStatus;
     readonly retryFailed: boolean;       // prompt-retained "retry didn't clear everything" copy
     readonly errorCategory: AuthErrorCategory | undefined; // signOut() itself failed
   }
   type LogoutGuardAction =
     | { type: 'logOutPressed'; pendingCount: number }   // pendingCount === 0 -> 'signingOut' directly; else -> 'prompt'
     | { type: 'retryPressed' }                           // 'prompt' -> 'retrying'
     | { type: 'retryFinished'; remainingPendingCount: number } // 0 -> 'signingOut'; else -> 'prompt' w/ retryFailed=true
     | { type: 'discardPressed' }                          // 'prompt' -> 'discarding'
     | { type: 'discardFinished' }                          // 'discarding' -> 'signingOut'
     | { type: 'cancelPressed' }                            // 'prompt' -> 'idle'
     | { type: 'signOutFinished'; error: AuthErrorCategory | undefined } // -> 'idle', errorCategory set iff error
     | { type: 'reset' };                                   // any -> INITIAL (identity changed underneath / unmount guard)
   ```
   Every transition is a guarded pure function of `(state, action)` with no ambient reads, directly unit-testable against every exit-criterion scenario as exact input/output pairs -- mirror `coordinator.test.ts`'s style.

6. **New driver hook `useLogoutGuard()`, `src/features/auth/state/use-logout-guard.ts`**, consuming `useAuthActions().signOut`, `useSyncCoordinatorStatus()` (`state`, `requestManualSync`, `pendingCount`, `discardAllPending`), and `useIdentityHandle()` (`generation`). Responsibilities:
   - `useReducer(logoutGuardReducer, INITIAL_LOGOUT_GUARD_STATE)`.
   - `handleLogOutPress = () => dispatch({ type: 'logOutPressed', pendingCount })` -- reads the live `pendingCount`, not a snapshot from an earlier render.
   - Retry: on entering `'retrying'`, call `requestManualSync()`; wait for one full `running -> idle` transition of the shared coordinator's `state.status` (track via two refs -- `armedRef` set when `'retrying'` is entered, `sawRunningRef` set the first time `state.status === 'running'` is observed while armed -- then on the next `state.status === 'idle'` observed while both are set, read the live `pendingCount` and dispatch `retryFinished`). This correctly covers the coalesced-into-an-already-running-run case for free, since coalescing still guarantees a subsequent full run completes before returning to idle.
   - Discard: on entering `'discarding'`, call `discardAllPending()`, await, dispatch `discardFinished` (do not re-check `pendingCount` here -- a discard is unconditional by definition).
   - Sign-out: on entering `'signingOut'`, call `signOut()`; on resolution, categorize any error via the existing `categorizeAuthError` (reuse `account-section.tsx`'s existing import) and dispatch `signOutFinished`. On success, deliberately do nothing else -- `AuthProvider`'s own listener flips `authState.status`, and `AccountSection`'s existing top-level `if (authState.status !== 'authenticated') return null;` guard naturally unmounts everything, including any open prompt. This preserves the existing "no fake guest transition" behavior/tests unchanged.
   - **Stale-identity guard**: capture `generation` when entering any non-`'idle'` status (a ref, `armedGenerationRef`); a `useEffect` on `[generation]` dispatches `{ type: 'reset' }` whenever `generation !== armedGenerationRef.current` while `status !== 'idle'` -- this is the concrete mechanism for "identity changes during the prompt": it aborts the local UI flow immediately without attempting any further sign-out/retry/discard action, on top of (not instead of) the structural protections already in decisions 1-4 (`checkIdentity` guards inside `discardPendingOperations`, the coordinator's own `identityChanged` cancellation, and `AccountSection`'s existing render guard).
   - **Unmount guard**: an `isMountedRef` (same pattern as `use-sync-coordinator.ts`) around every dispatch reached via an async `.then`, to avoid "set state after unmount" noise -- not a correctness mechanism (the reducer/generation guards already make a late dispatch inert), matching this codebase's own stated rationale for that pattern elsewhere.
   - Return `{ state, pendingCount, handleLogOutPress, handleRetry, handleDiscard, handleCancel }` for `AccountSection`/the new prompt component to consume.

7. **UI**: extend `src/features/auth/components/account-section.tsx` to use `useLogoutGuard()` in place of its current local `isSubmitting`/`errorCategory`/`isSubmittingRef` state (the double-press guard becomes redundant -- the reducer's own status transitions already prevent re-entrant presses). Add a new sibling component, `src/features/auth/components/logout-prompt.tsx`, rendered when `state.status` is `'prompt' | 'retrying' | 'discarding'` -- a `RankUpCelebrationModal`-style absolute-fill overlay (`accessibilityLabel="Unsynced changes"` or similar) with:
   - copy stating there are unsynced changes (interpolate `pendingCount` for "N changes" pluralization, matching the existing pluralization conventions elsewhere in this codebase),
   - a `retryFailed` line ("Still couldn't sync. Check your connection or discard these changes.") shown only when `state.retryFailed`,
   - three `Button`s: "Retry" (disabled while `status !== 'prompt'`), "Discard and log out" (`variant="primary"`, destructive wording carries the meaning), "Cancel" (`variant="secondary"`) -- all disabled while `status === 'retrying' | 'discarding'`.
   Keep `LOG_OUT_ERROR_COPY`/`categorizeAuthError` usage exactly as today for the `errorCategory` inline text near the Log Out button (covers both the no-prompt-path and post-prompt sign-out failures identically).

## Risk callouts for the implementer

- **The durability ordering in decision 2 is the crux of this ticket.** Do not let `discardPending()` write directly to `AsyncStorage`/a fresh scoped-storage call outside `saveNow`/`enqueueWrite` -- a second parallel writer can have its result clobbered by an already-in-flight queued write for the same key that resolves later, silently resurrecting a "discarded" operation. If this feels awkward to route through `saveNow`, that awkwardness is signal to keep it going through the queue, not to bypass it.
- **`pendingCount` must be a plain per-render value, not read through `latestRef`.** `latestRef` is synced in a `useLayoutEffect` specifically so imperative callbacks always see the latest value without becoming a render dependency -- but that means it lags the actual current render by one commit for anything read reactively. Keep the callback-facing copy (via `latestRef`) and the render-facing copy (`envelope.state.outbox.length` directly) clearly separate.
- **Do not add `navigator.onLine`/browser connectivity detection.** No such utility exists anywhere in this codebase today (confirmed by search); the "offline behavior" exit criterion is satisfiable as a fixture-driven variant of "failed Retry" (the sync transport call itself fails), not a new detection mechanism. Introducing one would be scope creep beyond what T158 or T160.1 ask for.
- **Do not build T160.1's Profile-wide sync-status surface or a general derived status model.** `pendingCount`/`discardAllPending` on `SyncCoordinatorProvider` are the only additions there; resist the temptation to also add "last synced"/"syncing"/"offline" derived fields while already in this file.
- **Do not add a "revert local state to last-synced snapshot" mechanism.** Confirmed no such primitive exists in any of the five `use-X-domain-sync.ts` hooks today; building one is a materially larger change than this ticket's stated scope. Document the resulting limitation (an abandoned local-only edit isn't automatically re-queued on a later login) in the closing `TASKS_DONE.md` note rather than silently building around it.
- **`account-section.test.tsx` mounts `<AccountSection />` with no providers at all.** Every new hook this component (transitively) calls must have a corresponding `jest.mock(...)` added there, exactly like the existing `@/features/auth/state/auth-provider` mock -- check this before assuming the 9 existing tests will keep passing unmodified.
- **The retry-wait "one full running->idle transition" mechanism in decision 6 depends on observing at least one `state.status === 'running'` render.** If `requestManualSync()`'s dispatch and the resulting run somehow complete within the same React commit, confirm the `armedRef`/`sawRunningRef` design doesn't get stuck waiting forever -- add a test that specifically exercises a same-tick-fast domain sync (mock `runSync` resolving immediately) to prove this.
