Notes INSERT covers `user_id,id,trick_id,trick_name,body,practice_session_id`; notes UPDATE covers `body,deleted_at`.

- `goal-persistence.ts`/`note-persistence.ts` currently keep their `isNormalizedText`/`isFiniteNonNegative`/`isPositiveInteger` helpers **unexported** (unlike `custom-trick-persistence.ts`/`practice-history-persistence.ts`, which already export theirs for the cloud-mapping layer to reuse). This is the one small change needed to existing files.

## Design decisions for this task specifically

1. **New concept needed that no prior mapping task had: a tombstone-aware domain-cloud entry type.** Local `Goal`/`Note` have no tombstone concept (the local reducer hard-deletes). Introduce, in each new mapping file:
   ```ts
   export interface GoalCloudMeta { readonly revision: number }
   export type GoalCloudEntry =
     | { readonly status: 'active'; readonly goal: Goal; readonly meta: GoalCloudMeta }
     | { readonly status: 'deleted'; readonly goal: Goal; readonly meta: GoalCloudMeta & { readonly deletedAt: number } };
   ```
   (same shape for `NoteCloudEntry`/`NoteCloudMeta` with `note: Note`). Reusing the full `Goal`/`Note` type for both statuses (rather than inventing a separate slimmed-down "tombstone" shape) is deliberate: the row always carries the full snapshot even after tombstoning (the trigger never nulls `trick_id`/`trick_name`/`kind`/target columns/`body` on delete), so nothing is lost, and it makes the round-trip test meaningful (a "deleted" entry is a fully valid `Goal`/`Note` plus deletion metadata, not a bag of loose fields). This is what satisfies "a tombstoned row needs its own valid mapped representation, not absent or invalid."

2. **Timestamp conversion is new territory.** `practice_sessions` stores timing as `bigint` epoch-ms columns, so the existing template never had to convert. `goals`/`notes` use `timestamptz`, serialized by supabase-js as ISO strings, while the local domain stores epoch-ms numbers (`Date.now()`-based, per `createGoal`/`createNote`). Add a small local helper in each mapping file:
   ```ts
   function parseTimestampMs(value: unknown): number | undefined {
     if (typeof value !== 'string') return undefined;
     const ms = Date.parse(value);
     return Number.isFinite(ms) ? ms : undefined;
   }
   ```
   Used for `created_at` (both), `updated_at` (notes only — `Goal` has no `updatedAt` field, so goals row-mapping does not need to read `updated_at` at all), and `deleted_at` (both, only when non-null). Deliberately duplicated verbatim in both files rather than factored into a shared util — mirrors this codebase's existing per-file-helper style (e.g. `hasExactKeys` in `custom-trick-cloud-mapping.ts`, `deepFreeze` duplicated across test files) for two call sites; not worth a shared module for this task's scope.

3. **"Reject ambiguous variants" — mirror `goals_count_shape`/`goals_time_shape` exactly, defense in depth:**
   - `kind === 'count'`: `target_ms` must be `null`/`undefined` (else issue reason `'ambiguousVariant'`), `target_count` must satisfy `isValidGoalTargetCount` (import from `goal.ts`, do not reimplement the range).
   - `kind === 'time'`: `target_count` must be `null`/`undefined` (else `'ambiguousVariant'`), `target_ms` must satisfy `isValidGoalTargetMinutes(target_ms / 60_000)` **and** be an exact multiple of 60 000 — compute bounds from the model constants (`MIN_GOAL_TARGET_MINUTES * 60_000`, `MAX_GOAL_TARGET_MINUTES * 60_000`) rather than hardcoding `60000`/`6000000000` literals, so the mapper can't silently drift from `goal.ts` if those constants ever change.
   - `kind` not `'count'|'time'` → `'malformedShape'`.
   - The "both target_count and target_ms populated regardless of kind" case is already covered by the per-kind branches above (whichever branch runs, the *other* field being non-null trips the `'ambiguousVariant'` issue) — no separate check needed, but write an explicit test for it since it's a named exit criterion.

4. **"Reject stale or malformed revisions" — this is two distinct, narrow checks, not a fabricated staleness comparator.** Re-read `T155.4`'s own SQL test (`supabase/tests/t155_4_goals_and_notes.test.sql`, lines ~116–148): "stale mutation" there literally means *attempting any UPDATE against a row whose `deleted_at` is already set* — the trigger rejects it unconditionally regardless of the revision value in the WHERE clause. Mirror that exact semantic client-side as defense in depth, do not invent revision-comparison/conflict-resolution logic (explicitly out of scope, T157's job):
   - Row → domain: `revision` must be a positive integer (`Number.isInteger(value) && value >= 1`) or the row is `'invalid'` with reason `'invalidRevision'` — this is the "malformed" half.
   - Domain → mutation-payload preparation (new functions, see below): given a `GoalCloudEntry`/`NoteCloudEntry` the caller believes is current, reject preparing a further mutation if `known.status === 'deleted'` (reason `'alreadyDeleted'` — this is the "stale" half, since attempting to mutate an already-tombstoned known-entry is definitionally trying to act on stale/dead state) or if `known.meta.revision` is not a sane positive integer (reason `'invalidRevision'` — defensive, since `GoalCloudEntry`/`NoteCloudEntry` values may originate from hand-built test fixtures or future non-mapper code paths, not only from this file's own row-mapper).
   - Add the mutation-preparation functions:
     ```ts
     export type GoalMutationPrepIssueReason = 'invalidRevision' | 'alreadyDeleted';
     export interface GoalMutationPrepIssue { readonly reason: GoalMutationPrepIssueReason; readonly message: string }
     export type GoalDeletionPrepResult =
       | { readonly status: 'rejected'; readonly issue: GoalMutationPrepIssue }
       | { readonly status: 'prepared'; readonly patch: GoalCloudPatch };
     export function prepareGoalDeletionPatch(known: GoalCloudEntry, deletedAtMs: number): GoalDeletionPrepResult
     ```
     `deletedAtMs` is an explicit parameter, not `Date.now()` inside the function — matches AGENTS.md's "keep `Date.now()` calls outside pure logic, pass timestamps through" convention (the server will overwrite whatever value is sent anyway per the trigger, but the function itself stays pure/testable). On success: `{ status: 'prepared', patch: { deleted_at: new Date(deletedAtMs).toISOString() } }`.
     Notes get the analogous `prepareNoteDeletionPatch` plus `prepareNoteEditPatch(known: NoteCloudEntry, body: string): NoteEditPrepResult` (same rejection rules; `body` is assumed already validated/trimmed by `validateNoteEdit` upstream — this boundary function does a defensive `isNormalizedText` check on it, reason `'malformedShape'`, but does not reimplement note-body validation UX).

5. **"Reject invalid session associations" — `practice_session_id` shape is exactly "non-blank string," nothing stricter.** Checked `createPracticeSessionRecordId` (`src/features/stats/model/practice-history.ts`): the id format is `` `${startedAt}:${endedAt}:${trickId}` `` with no fixed regex contract, and the existing `practice-history-cloud-mapping.ts` itself only validates practice-session `id` as non-empty string. The DB's own `notes_practice_session_id_not_blank` CHECK is exactly `length > 0`. So: `practice_session_id === null` → valid, no association; present and `isNormalizedText` → valid, mapped to `Note.practiceSessionId`; present and not a non-empty trimmed string (wrong type, empty, or whitespace-only) → `'invalid'` with a dedicated reason `'invalidSessionAssociation'` (distinguish from generic `'malformedShape'` so the exit criterion is independently testable/greppable). Do **not** add a stronger regex/format check — that would be inventing a contract the codebase doesn't actually have, and full referential validity is explicitly the FK's job server-side.

6. **Foreign-user check**: same as every prior mapping file — `row.user_id !== expectedUserId` → `'invalid'`, reason `'foreignUser'`, checked first before any other field validation (matches existing files' ordering).

7. **Batch mapper**: no "absent" status (empty array is a valid empty result, same as practice-history/custom-tricks). Duplicate-`id` defense across rows, same pattern as the two existing batch mappers (belt-and-suspenders even though the PK already prevents it server-side). Explicitly does **not** filter out `'deleted'` entries — preserves `list()`'s own documented behavior (see the repository file's header comment) that tombstones are visible to callers; filtering is a future selector/sync-layer concern (T157), not this mapping boundary.

## Test matrix (both `goal-cloud-mapping.test.ts` and `note-cloud-mapping.test.ts`, adapted per-domain)

Row → domain (`mapGoalRowToDomainEntry` / `mapNoteRowToDomainEntry`):
- valid `'count'`/`'time'` (goals) or a plain note with/without `practice_session_id` → `'valid'`, `status: 'active'`, fields match.
- tombstoned row (`deleted_at` set) → `'valid'`, `status: 'deleted'`, `meta.deletedAt` parsed correctly, snapshot fields (`trick_id`/`trick_name`/target or body) still present on `entry.goal`/`entry.note`.
- ambiguous variant: `kind:'count'` with non-null `target_ms` → `'invalid'`, `'ambiguousVariant'`; `kind:'time'` with non-null `target_count` → same; both populated regardless of `kind` → same.
- unknown `kind` value → `'invalid'`, `'malformedShape'`.
- out-of-range `target_count` (0, negative, non-integer, > MAX) and `target_ms` (not a multiple of 60 000, below/above bounds) → `'invalid'`, `'outOfRange'`/`'wrongType'`.
- malformed `revision` (`0`, `-1`, `1.5`, `'1'`, `NaN`) → `'invalid'`, `'invalidRevision'`.
- malformed `deleted_at` (non-ISO-parseable string) → `'invalid'`.
- foreign user (`row.user_id !== expectedUserId`) → `'invalid'`, `'foreignUser'`.
- (notes only) `practice_session_id`: `null` → valid, no association; non-empty trimmed string → valid, mapped; `''`/whitespace-only/non-string → `'invalid'`, `'invalidSessionAssociation'`.
- (notes only) `updated_at < created_at` → `'invalid'`, `'invariantViolation'`.

Batch mapper (`mapGoalRowsToDomainEntries` / `mapNoteRowsToDomainEntries`):
- empty array → `'valid'`, `entries: []` (no `'absent'` status).
- duplicate `id` across two rows → `'invalid'`, `'duplicateId'`.
- mixed active + tombstoned rows in one batch → both appear in `entries` (proves tombstones are not filtered).
- preserves input order.

Domain → row / mutation-payload preparation:
- `mapGoalToInsertInput`/`mapNoteToInsertInput`: correct field mapping for every variant; never includes `revision`/`created_at`/`updated_at`/`deleted_at` keys (assert via `Object.keys` and/or rely on the type-check file for the compile-time half).
- `prepareGoalDeletionPatch`/`prepareNoteDeletionPatch`: valid active entry + sane revision → `'prepared'`, `patch.deleted_at` is the ISO string derived from the passed `deletedAtMs`; `known.status === 'deleted'` → `'rejected'`, `'alreadyDeleted'` (the "stale mutation" case, directly mirroring `t155_4_goals_and_notes.test.sql`'s "a stale mutation ... cannot undelete a tombstoned goal" DB-level test); hand-constructed entry with `meta.revision` malformed (`0`, `1.5`) → `'rejected'`, `'invalidRevision'`.
- `prepareNoteEditPatch`: valid active entry + non-blank body → `'prepared'`; `known.status === 'deleted'` → `'rejected'`, `'alreadyDeleted'`; malformed revision → `'rejected'`, `'invalidRevision'`; blank/whitespace-only `body` → `'rejected'`, `'malformedShape'`.

Round-trip:
- `Goal`/`Note` (both goal kinds; note with and without `practiceSessionId`) → `mapGoalToInsertInput`/`mapNoteToInsertInput` → splice into a full row fixture (helper like the template's `toPracticeSessionRow`) → `mapGoalRowToDomainEntry`/`mapNoteRowToDomainEntry` → `entry.status === 'active'` and `entry.goal`/`entry.note` deep-equals the original.
- Tombstone round-trip: a `GoalRow`/`NoteRow` fixture with `deleted_at` set → map to a `'deleted'` entry → assert every snapshot field and `meta.deletedAt`/`meta.revision` match the row's own values (this is the only round-trip direction that exists for tombstones, since the domain never constructs a tombstoned `Goal`/`Note` locally — deletion is expressed only as a patch, not a full row).

No-mutation proofs (reuse the template's `deepFreeze` helper, duplicated locally in each test file as the templates already do):
- `deepFreeze` a `Goal`/`Note`, call the insert mapper, assert the frozen object throws on no further access issue and its JSON serialization is unchanged before/after the call.
- `deepFreeze` a `GoalRow`/`NoteRow` (both active and tombstoned), call the row mapper and batch mapper, assert unchanged.
- `deepFreeze` a `GoalCloudEntry`/`NoteCloudEntry`, call the mutation-prep functions, assert unchanged.

## Risks / things to get right

- Don't let the goals/notes `GoalCloudEntry`/`NoteCloudEntry` types leak into any provider/reducer code in this task — this is explicitly mapping-only, same boundary every prior T155.1x task held. Nothing in `src/app/_layout.tsx` or the `goal-provider.tsx`/`note-provider.tsx` files should change.
- Don't reuse `Goal`array duplicate-id detection logic from the domain reducer (`goalReducer`) — the batch mapper's duplicate check is a fresh, small implementation on raw row `id`s, same as the three prior mapping files, not a call into reducer code.
- Keep the `'ambiguousVariant'` and `'invalidSessionAssociation'`/`'invalidRevision'`/`'alreadyDeleted'` reason codes distinct and dedicated (not folded into generic `'malformedShape'`) — the exit criteria call these out by name, and dedicated reasons make each exit-criterion independently assertable in tests without string-matching messages.
- `Number.isInteger` vs `Number.isSafeInteger` for `revision`: use `Number.isInteger` (matches the rest of the codebase's `isPositiveInteger` helpers) — no realistic revision count will exceed `Number.MAX_SAFE_INTEGER`, don't over-engineer this.
