# T160.1 — Add a trustworthy synchronization status model and Profile surface

## Good enough for this iteration

An authenticated user can open Profile and see a truthful, identity-scoped
summary of synchronization: syncing, offline, pending work, retryable failure,
conflicts, last successful sync, or an initial/no-sync-yet state. The summary
must remain serializable and reload-safe, must never call a state "synced"
while pending or conflict operations exist, and must offer a manual retry that
uses the existing coordinator trigger. The web target is the only platform to
verify in this iteration; native hardening remains deferred.

## Current boundaries and findings

- T157.1–T157.9 are archived as Done, including the single-flight
  `syncCoordinatorReducer`, the coordinator driver, five domain sync hooks, and
  the mounted `SyncCoordinatorProvider`.
- `SyncCoordinatorProvider` currently exposes ephemeral coordinator state,
  `requestManualSync`, aggregate `pendingCount`, and `discardAllPending`.
  `SyncCoordinatorState` is intentionally reset on reload.
- Each domain's `SyncEnvelope` durably owns its state and outbox, while the
  domain hooks expose transient `isSyncing`/`lastResult` values and reactive
  pending counts. The five envelopes are independent and must stay that way.
- The outbox currently persists `lastErrorMessage` but not whether the parked
  operation failed due to a retryable transport error or a revision conflict.
  Parsing error text would make the Profile status untrustworthy after reload.
- Profile is `src/app/app/profile/index.tsx`; the app shell already mounts the
  sync provider above the Profile route. Existing Profile tests mock the sync
  provider for account-section coverage and will need a status-aware fixture.
- T160.2 owns the conflict-resolution route and resolution behavior. This task
  should expose durable conflict facts and a stable status model without
  implementing that route.

## Ordered implementation plan

1. **Define the serializable status contract and pure derivation.**
   - Add a shared model, preferably
     `src/shared/sync/sync-status.ts`, containing JSON-safe facts and a
     discriminated/explicit status result. Model the coordinator phase,
     aggregate pending count, conflict count, retryable-failure count, online
     state, and persisted last-success timestamp separately so combined states
     (for example offline + pending, or syncing + conflict) remain representable.
   - Centralize precedence and invariants in one pure selector/deriver. In
     particular, `synced` is legal only when the coordinator is not running,
     online, there are no pending operations, and there are no conflicts or
     retryable failures. Define the no-success-yet case explicitly instead of
     displaying a fabricated timestamp.
   - Add pure formatting helpers in the same boundary (or a narrowly scoped
     `src/shared/sync/format-sync-status.ts`) for singular/plural pending and
     conflict copy and deterministic timestamp rendering. Keep `Date.now()` and
     locale/time-zone reads out of the derivation; pass `now`/format options in
     tests where needed.

2. **Make parked outbox outcomes distinguishable and durable.**
   - Extend `OutboxOperation` with a JSON-safe failure classification such as
     `lastFailureKind: null | 'retryable' | 'conflict'`, preserving the existing
     error message and attempt metadata. Update creation, runtime validation,
     envelope reducer actions, and sync-envelope helpers so malformed or
     obsolete data follows the existing provisional-v1 recovery behavior.
   - Extend the operation-attempt action/call sites in all five domain sync
     hooks. A `conflict` transport result records `conflict`; a failed pull,
     push, or adapter exception records `retryable`. Successful
     acknowledgement removes the operation as before. Do not store server
     clients, promises, timers, Maps/Sets, or error objects.
   - Preserve enough operation identity/payload/revision information for T160.2
     to inspect the pending conflict later; do not resolve or discard conflicts
     here. Keep independent domain envelopes and existing FIFO/coalescing
     semantics intact.
   - Update focused outbox, envelope, transport, and five domain-sync tests for
     the new serialized field and verify old valid test fixtures are adjusted
     consistently.

3. **Persist only coordinator status metadata under the current identity.**
   - Add an identity-scoped, versioned persistence adapter—likely
     `src/shared/sync/sync-status-persistence.ts`—for the minimal durable
     metadata needed across reloads: last fully successful coordinator sync
     timestamp (and, if required by the chosen contract, a persisted status
     generation/identity marker). Use the existing scoped storage/write-queue
     conventions and self-describing identity namespace; never persist the
     reducer's active run, request callbacks, or connectivity listeners.
   - Hydrate/clear this metadata on identity generation changes. Do not expose
     the prior user's timestamp or pending/conflict facts under a new identity;
     pending/conflict counts always come reactively from the current identity's
     envelopes. Preserve the app's hydration gating and skipped-initial-write
     protections so initial empty state cannot overwrite restored metadata.
   - Persist a last-success timestamp only after a completed coordinator run
     whose domain outcomes are all successful, using the run's supplied end
     timestamp. A run with a retryable domain result, parked conflict, or
     cancellation must not advance freshness. Decide and document whether an
     already-pending conflict means a later run can update freshness; the
     selector must still suppress `synced` until the conflict is resolved.

4. **Integrate status facts in `SyncCoordinatorProvider`.**
   - Add a status-facing hook/context value that combines the pure selector
     inputs from the coordinator state, all five domain sync handles' pending
     and last-result/failure facts, the persisted freshness metadata, and web
     connectivity.
   - Keep `requestManualSync` as the sole retry dispatch. The status surface
     should expose a stable `retry`/manual action (and, if useful, an explicit
     pending-conflict count) without exposing runtime handles. Ensure provider
     callbacks and metadata writes are identity/run guarded so late completion
     from the old generation cannot update current status.
   - Subscribe to `online`/`offline` only in the web driver/provider boundary;
     provide a deterministic online default for non-web code without adding
     native networking dependencies. Clean up listeners on unmount.

5. **Render the status section in Profile.**
   - Add a focused Profile sync-status component, preferably
     `src/features/profile/components/sync-status-section.tsx`, consuming only
     the status context and retry action. Place it near the account section so
     account/synchronization health is discoverable without restoring the old
     trick directory to Profile.
   - Use the existing typography, colors, Button, and layout language. Show
     clear labels for syncing, offline, pending work with correct pluralization,
     retryable failure, conflicts requiring resolution, last successful sync,
     and no-sync-yet. Ensure meaning is available in text/labels and not by
     color alone. The retry control should be disabled or labeled appropriately
     while a run is active and should not mutate Sesh state.
   - Avoid claiming all data is synced when any outbox operation—including a
     conflict or retryable failure—is still present.

6. **Add tests for every stated exit criterion.**
   - Add table-driven selector tests covering initial/no-success, fully synced,
     syncing, offline, pending singular/plural, retryable failure, conflicts,
     and meaningful combined states such as offline+pending and
     conflict+pending. Assert the synced invariant directly.
   - Add persistence/provider tests proving a successful timestamp survives a
     reload, failed/cancelled runs do not advance it, pending/conflict facts
     reload from the identity's envelope, and switching identities clears old
     freshness/status rather than leaking it. Include late old-generation
     completion protection.
   - Add component tests for all user-visible branches, timestamp copy and
     pluralization, and pressing Retry dispatching the coordinator's manual
     trigger. Update the existing Profile integration mock so it supplies the
     expanded status contract; retain existing account/theme/assessment tests.
   - Keep conflict resolution itself out of this test set except for proving
     that conflicts are surfaced and remain pending for T160.2.

7. **Run proportional verification and review the boundary.**
   - During implementation, run the exact shared sync/outbox/envelope tests,
     status/provider tests, and Profile component tests; run scoped ESLint on
     changed files.
   - Before completion, run `yarn tsc --noEmit` and the affected persistence,
     sync, domain-hook, and Profile suites. Because this changes provider
     hierarchy/state persistence and Profile rendering, run the complete app
     sequence from `AGENTS.md` (including the Expo web export) if the
     implementation changes shared provider wiring or dependencies.
   - Inspect the 320px web navigation/profile layout and verify no new warning
     is mistaken for the two known-benign warnings. Do not launch mobile
     tooling.

## Risks and guardrails

- **False synced state:** centralize precedence and test the invariant against
  every combined input; never infer conflicts from human-readable error text.
- **Cross-account leakage:** key and validate status metadata with the existing
  identity namespace and clear it on generation changes; test guest → user and
  user A → user B transitions.
- **Reload regression:** preserve envelope atomicity, write ordering, hydration
  fallback, and skipped-first-write behavior. A status write must not race a
  domain restore or overwrite it with defaults.
- **Conflict scope creep:** expose durable facts and a path for later typed
  resolution, but leave `/app/profile/sync-conflicts` and resolution policy to
  T160.2.
- **Coordinator coupling:** do not put connectivity listeners or persistence
  side effects in `coordinator.ts`; keep the reducer pure and clocks/async work
  in React effects or persistence adapters.
- **Product scope:** no Realtime, background scheduling, automatic conflict
  resolution, mobile hardening, new backend tables, or Profile trick-directory
  work belongs in T160.1.
