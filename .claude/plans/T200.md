# T200 — Add sign-up/sign-in entry points to the landing page

## Confirmed root cause / why this is reachable today only via a redirect-free path

- `src/components/app-tabs.tsx` sets `hidden={!hasCompletedOnboarding}` on every tab trigger
  (`sesh`, `tricks`, `stats`, `profile`). Profile — the only existing sign-up/sign-in entry point
  (`GuestAccountSection` in `src/app/app/profile/index.tsx`) — is therefore genuinely unreachable
  until onboarding (the Kentei rank picker) is complete. This confirms the task's premise exactly;
  it is not stale.
- `src/app/app/home.tsx` renders `<KenteiOnboarding />` in place of `<DailyHome />` whenever
  `!profile.hasCompletedOnboarding || !profile.kenteiRank`, regardless of what local data
  (practice history, custom tricks) already exists in storage. Onboarding completion and "has
  existing local data" are independent booleans — a guest can have seeded/real local data and
  still be pre-onboarding.
- The landing route (`src/app/index.tsx`) only redirects away (`useRedirectOnboardedVisitorHome`
  → `/app/home`) when onboarding **is** complete (`hasCompletedOnboarding && kenteiRank !==
  undefined`) and the arrival isn't the in-app `LANDING_ARRIVAL_PARAM` exit link. A pre-onboarding
  visitor — brand new or with existing-but-unonboarded local data — always sees `LandingPage`
  render normally, with no redirect race to guard against.

This means the safe, minimal design is: add a new component to the landing page that is gated
**only** on `useAuthState()` status (`'guest'` → render; anything else → render nothing), exactly
like `GuestAccountSection` already does in Profile. It must not read or depend on
`useCachedOnboardingStatus`, `useRedirectOnboardedVisitorHome`, or `LANDING_ARRIVAL_PARAM` at all
— those stay completely untouched, which is what keeps this change out of the hydration/redirect
risk class those hooks already carry (T145/T170/T189/T199 history). `AuthProvider` is mounted at
the root layout (`src/app/_layout.tsx`), above the landing route, so `useAuthState()` is already
safely available on `/` with no provider changes needed (same precedent T153.1 established: Auth
is mounted above the root `Slot` with no hydration gate).

## Steps

1. **New component: `src/features/landing/components/landing-auth-cta.tsx`**
   - Export `LandingAuthCta`. Call `useAuthState()` from `@/features/auth/state/auth-provider`;
     return `null` unless `authState.status === 'guest'` (mirrors `GuestAccountSection`'s
     mutually-exclusive render-null gating — do not also condition on onboarding status).
   - `useRouter()` from `expo-router`; two `Button` presses:
     `onPress={() => router.push('/auth/sign-up')}` (`accessibilityLabel="Sign up"`) and
     `onPress={() => router.push('/auth/sign-in')}` (`accessibilityLabel="Sign in"`,
     `variant="secondary"`). Reuse the same accessibility labels `GuestAccountSection` uses for
     consistency, even though they're on different screens.
   - Do **not** reuse `GuestAccountSection` directly — its chrome (`Divider`, `SectionLabel`
     "Account") assumes it's one entry in a settings-style list following other Profile content,
     which doesn't fit the landing page's marketing-page visual language. Write new, smaller
     framing local to this file (short one-line copy + a compact button row), matching
     `landing-cta.tsx`'s existing pattern of owning its own styled-components rather than
     importing Profile's. Keep it visually subordinate to `LandingCta`'s bold sticker-card
     treatment (no `boxShadow`/heavy panel) — it's a secondary, parallel entry point, not a
     second primary CTA.

2. **Wire into `src/features/landing/components/landing-page.tsx`**
   - Import `LandingAuthCta` and render `<LandingAuthCta />` immediately after `<LandingCta />`
     and before `<FeatureList>`. This keeps it high enough to satisfy "reachable without
     completing onboarding" while staying visually secondary to the primary Sesh CTA above it.
   - No changes to `useWindowDimensions`/`isWebLayout` plumbing, `Content`, or any of the
     screenshot-showcase code.

3. **New test: `src/features/landing/components/landing-auth-cta.test.tsx`**
   - Mirror `src/features/auth/components/__tests__/guest-account-section.test.tsx`'s pattern
     exactly: mock `@/features/auth/state/auth-provider`'s `useAuthState` with a mutable
     `mockAuthState`, and mock `expo-router`'s `useRouter` to a `{ push: mockPush }`.
   - Cases: renders nothing for `initializing`, `authenticated`, `passwordRecovery`; renders
     "Sign up"/"Sign in" for `guest`; pressing each navigates to `/auth/sign-up` /
     `/auth/sign-in` respectively.

4. **Update `src/features/landing/components/landing-page.test.tsx`**
   - This test currently does not mock `@/features/auth/state/auth-provider` at all. Since
     `LandingAuthCta` now calls `useAuthState()` unconditionally when mounted under `LandingPage`,
     add a mock (mutable `mockAuthState`, default `{ status: 'guest', reason: 'signedOut' }` in
     `beforeEach`) — otherwise every existing test in this file will start throwing
     `useAuthState must be used within AuthProvider`.
   - Add at least one assertion that the new entry points render for a guest (e.g. find nodes by
     `accessibilityLabel === 'Sign up'` / `'Sign in'`) and one that they're absent when
     `mockAuthState = { status: 'authenticated', ... }`, reusing this file's existing
     `findByVisibleText`-style helper pattern or a small `findAllByLabel` helper like the one in
     `guest-account-section.test.tsx`.
   - The existing "renders the CTA before the feature-list content in document order" test
     compares indices of `'Start your first Sesh'` and `'Pick one trick and stick to it'` in a
     flat text-node array; inserting new text nodes between them does not break that ordering
     assertion, so no change needed there.
   - `src/app/__tests__/index.test.tsx` mocks `LandingPage` wholesale and needs no change.

5. **Verification (per AGENTS.md's App UI/routes tier)**
   - Scoped lint: `yarn eslint src/features/landing/components/landing-auth-cta.tsx
     src/features/landing/components/landing-auth-cta.test.tsx
     src/features/landing/components/landing-page.tsx src/features/landing/components/landing-page.test.tsx`
   - Targeted Jest: the two new/updated test files above, plus
     `guest-account-section.test.tsx` and `index.test.tsx` for regression sanity.
   - Full `yarn tsc --noEmit` before completion (route/component change).
   - Run a web export (`yarn expo export --platform web ...`) since this changes the landing

6. **In-browser verification — exit criteria require this explicitly, not just unit coverage**
   Run the Expo web dev server (per AGENTS.md, not a static-export file server). Check:
   - **Brand-new guest, no local data:** load `/`, confirm no redirect fires (not onboarded),
     confirm the new Sign up/Sign in controls render and each navigates directly to
     `/auth/sign-up` / `/auth/sign-in` without visiting onboarding first.
   - **Existing local data, not yet onboarded:** seed guest-scoped practice-history/custom-trick
     `localStorage` keys directly (bypassing the picker, so `hasCompletedOnboarding` stays
     false — this is the realistic "existing local data but pre-onboarding" case the task
     describes), load `/`, use the new entry point to sign up against the local Supabase stack
     (per `supabase/README.md`: real signup, Mailpit confirmation, PKCE callback). Confirm the
     import completes per T198/T199 — no visible guest-import panel, `/app/home` renders
     `DailyHome` (not `KenteiOnboarding`) with the imported data present, no onboarding re-flash
     on reload. This is the same regression class T199's own live check exercised, just entered
     through the new landing control instead of Profile.
   - **True brand-new guest signing up via the new entry point:** confirm `/app/home` still shows
     `KenteiOnboarding` normally afterward — unchanged from today's post-signup behavior for an
     empty-data account.
   - **Returning onboarded guest, fresh arrival at `/`:** confirm `useRedirectOnboardedVisitorHome`
     still redirects straight to `/app/home` as before (the new component never renders in that
     path, since the redirect happens before `LandingPage` mounts) — a quick sanity check that
     nothing about this change touches that existing behavior.

## Risks / non-obvious notes for the implementer

- The core risk this task is flagged for (redirect race / hydration ordering) is avoided by
  construction: `LandingAuthCta` depends only on `useAuthState()`, which is orthogonal to the
  `useCachedOnboardingStatus`/`useRedirectOnboardedVisitorHome`/`LANDING_ARRIVAL_PARAM` machinery.
  Do not add any onboarding-status condition to this component — that would reintroduce exactly
  the kind of coupling those past tickets had to unwind.
- `AuthProvider`'s initial state is `{ status: 'initializing' }` on both server-prerender and
  first client render (no async/localStorage read before that), so there is no hydration-mismatch
  risk analogous to `useCachedOnboardingStatus`'s `useSyncExternalStore` guard — none is needed
  here.
- Every test file that mounts `LandingPage` (or anything that transitively mounts
  `LandingAuthCta`) without mocking `@/features/auth/state/auth-provider` will now throw. Search
  for any other such mount sites beyond `landing-page.test.tsx` before considering this done.
- Keep the new component visually secondary to `LandingCta` — this is an explicitly parallel,
  not a replacement or competing, entry point per the task notes.
