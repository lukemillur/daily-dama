# T064 — Baseline goal progress at creation time

## Root cause

`selectGoalProgress` in `src/features/goals/model/goal.ts` (lines 146–157) sums
`laceCount`/`durationMs` across every session matching `goal.trickId`, with no
lower bound on `session.completedAt`. `Goal`/`GoalBase` already carries
`createdAt` (set via `createGoal(id, value, createdAt = Date.now())`), so the
fix is a single filter added to `selectGoalProgress` itself.

## Why a single-point fix covers every call site

`selectGoalProgress` is the only function that reads session history to
compute progress. Every other progress-producing entry point calls through
it, so fixing it once propagates everywhere without touching call sites:

- `selectGoalProgressByTrick` (same file, lines 165–187) calls
  `selectGoalProgress(goal, sessions)` internally — used by
  `all-trick-goals-screen.tsx`.
- `trick-goals-screen.tsx` line 35: `trickGoals.map((goal) =>
  selectGoalProgress(goal, sessions))`.
- `sesh.tsx` line 126 (`useEffect` that computes `justAchievedGoals` when a
  sesh completes): `const baseline = selectGoalProgress(goal, sessions)`.
- `sesh.tsx` line 164 (`handleTrickSelected`, sets `goalBaselines` when a
  trick is chosen to start a sesh): `selectGoalsForTrick(goals,
  trick.id).map((goal) => selectGoalProgress(goal, sessions))`.
- `sesh.tsx` line 254 (`onRepeat` in the completed-sesh view, resets
  `goalBaselines` for a repeat sesh): same pattern as line 164.
- `sesh.tsx` line 960 (`CompletedSesh`'s `goalProgressList` memo, drives the
  progress display on the completion screen): `trickGoals.map((goal) =>
  selectGoalProgress(goal, sessions))`.

No call site needs to change. Do not add filtering at any of these sites —
that would duplicate the `createdAt` comparison and risk drift.

## Relationship to `goalBaselines`/`isGoalNewlyAchieved` (do not conflate)

`goalBaselines` in `sesh.tsx` is an unrelated, in-Sesh concept: it snapshots
`selectGoalProgress(goal, sessions)` at trick-selection time (before the
in-progress sesh's own session is recorded), then `isGoalNewlyAchieved`
compares `baseline.current` against `baseline.current + contribution` to
detect a goal crossing its target mid-session. This mechanism doesn't need
and shouldn't get any direct change — it already delegates to
`selectGoalProgress`, so it automatically inherits the creation-time filter.

This is actually the *correct* behavior, not an incidental side effect: if a
goal is created against a trick with prior history, its `goalBaselines` at
the next sesh should also reflect 0 (or whatever accrued since creation), not
the inflated pre-existing count — otherwise the in-sesh celebration could
under-fire (looking like it needs `target - N` more laces when it actually
needs `target` more from a 0 baseline) or fire at the wrong lace. Confirm
this in the plan verification step below, but do not add separate logic for
it.

`sessions` passed into all of the above `sesh.tsx` call sites is prior
history *before* the current in-progress session is recorded (the
`recordCompletedSesh` call happens after `justAchievedGoals` is computed, and
`goalBaselines` is snapshotted at trick-selection, before the sesh's own
session exists at all) — so this filter change only ever removes sessions
that predate the goal, never the in-progress session itself. No reordering
or timing changes needed.

## Implementation steps

1. **`src/features/goals/model/goal.ts`** — in `selectGoalProgress`, change
   the `trickSessions` filter from:
   ```ts
   const trickSessions = sessions.filter((session) => session.trickId === goal.trickId);
   ```
   to:
   ```ts
   const trickSessions = sessions.filter(
     (session) => session.trickId === goal.trickId && session.completedAt >= goal.createdAt,
   );
   ```
   This is the entire production-code change. Do not touch
   `selectGoalProgressByTrick`, `getGoalContribution`, `isGoalNewlyAchieved`,
   or any `sesh.tsx`/screen call site.

2. **`src/features/goals/model/goal.test.ts`** — add a new test (or extend
   the existing `describe('selectGoalProgress', ...)` block) covering the
   exit criteria directly:
   - A trick with N prior laces in session history completed *before* the
     goal's `createdAt`.
   - A goal created afterward (`createGoal(id, value, createdAt)` with
     `createdAt` greater than those sessions' `completedAt`) with target M.
   - Assert `selectGoalProgress(goal, sessions).current === 0` (reads 0/M,
     not N/M).
   - Add a second session with `completedAt >= goal.createdAt` and assert
     progress now includes that session's contribution (increments normally
     after creation).
   - Also add a boundary case: a session with `completedAt === goal.createdAt`
     counts (the exit criteria says `>=`), and a session strictly before does
     not.
   - Existing tests in this file already use `createdAt: 1` with sessions at
     `completedAt: 61_000`, so they remain valid as "session after goal
     creation" cases — no existing test needs to change.

3. **`src/features/sesh/components/sesh.tsx`** (or its own test file, if one
   exists — check `find src/features/sesh -name "*.test.tsx"`) — verify with
   a targeted read/run of the existing goal-celebration tests that
   `isGoalNewlyAchieved`/`goalBaselines` still pass unmodified. No code
   change expected here; this step is verification only. If an existing
   sesh test constructs a goal with `createdAt` *after* the fixture sessions
   it expects to count toward baseline, that test will need its fixture
   `createdAt` value adjusted to precede those sessions (this would indicate
   the test was relying on the pre-fix inflated-progress bug rather than the
   intended behavior) — inspect before assuming a failure is the fix's
   fault.

4. Run the standard verification sequence:
   ```sh
   yarn test --runInBand
   yarn lint
   yarn tsc --noEmit
   yarn expo export --platform web --output-dir /tmp/daily-dama-web-export
   ```
   (`node .claude/scripts/verify.mjs` runs all four.) Given the change is
   confined to one filter predicate with no UI/schema surface, `--skip-export`
   is reasonable, but there's no cost to running the full sequence.

## Risk notes

- This is a narrow, low-risk change: one added clause in one filter
  predicate, no new persisted field, no schema/migration (per the task's
  Notes and `AGENTS.md`'s custom-trick/goal domain guidance — `createdAt`
  already exists on `GoalBase`).
- The only subtlety is confirming `sesh.tsx`'s four call sites don't
  pre-filter or otherwise assume unfiltered `sessions` — confirmed above they
  all pass the full `sessions` array from `usePracticeHistory()` straight
  into `selectGoalProgress`, so the fix applies uniformly.
- Do not add a second "baseline" concept or rename anything in `sesh.tsx` —
  the task's Notes flag the naming collision only as a reading hazard, not
  something to refactor.
