### The one trap in this ticket

The ticket Notes say "reuse the existing logout mechanism from `AccountSection`". `AccountSection`'s
mechanism is `useLogoutGuard()`, and **it cannot be used on `/`**:

- `useLogoutGuard` calls `useSyncCoordinatorStatus()`, which is
  `if (!status) throw new Error('useSyncCoordinatorStatus must be used within SyncCoordinatorProvider.')`
  (`src/shared/sync/sync-coordinator-provider.tsx:76`).
- `pendingCount` is summed from `profile/customTricks/practiceHistory/goals/notes` provider handles
  (same file, line 63). There is no provider-free way to compute it.
- Mounting that stack at the root would break T145's explicit invariant that the landing route must
  not block first paint on any persistence provider (documented in
  `use-cached-onboarding-status.ts`). **Do not do this.**

So the reused mechanism is the other one the Notes allow: `useAuthActions().signOut` from
`auth-provider.tsx`, called directly. Do not import `useLogoutGuard`, `LogoutPrompt`, or
`logout-guard.ts` into the landing feature — it typechecks fine and throws at runtime in the browser.

## 2. Decisions (settled — implement these, don't re-open)

1. **One bar, two right-hand sides.** Keep a single `HeaderBar` with the same
   `testID="landing-header-bar"`, the same `Brand`, and the same `visible`/`pointerEvents`
   behaviour. Swap only the contents of `ButtonRow`. This keeps every existing
   `landing-page.test.tsx` scroll/visibility assertion valid and means the hidden-bar
   `pointerEvents="none"` guard automatically covers the new logout button (an invisible but
   clickable logout would be a real hazard — it is already prevented, keep it that way).
2. **Render matrix.**
   - `initializing` → `null` (unchanged). This is what prevents a flash of the *guest* bar on a
     signed-in reload: `AuthProvider` starts at `initializing` and only resolves once the Supabase
     listener fires.
   - `guest` → existing Sign up / Sign in bar, byte-for-byte unchanged.
   - `authenticated` → `Daily Dama` + a single `Log out` button.
   - `passwordRecovery` → `null` (unchanged). A recovery session is mid-flow; offering logout there
     is wrong. Keep the existing behaviour and its test.
3. **No redirect after logout.** `AccountSection` does `router.replace('/')` because Profile lives
   behind the app shell. On `/` the visitor is already on a public route: after `signOut()` the auth
   state flips to `guest` and the same bar re-renders as the sign-up/sign-in bar, which is its own
   confirmation. Do not add navigation. (Also verified: nothing else on `/` reacts to `SIGNED_OUT` —
   `IdentityProvider` is not mounted there, so there is no identity-generation churn, and
   `useRedirectOnboardedVisitorHome` does not read auth state at all.)

### Step 2 — Rewrite `src/features/landing/components/landing-auth-cta.tsx`

Hooks first, early return after (React Compiler is enabled — `app.json` `experiments.reactCompiler:
true` — so no conditional hook calls, no ref mutation during render):

```tsx
const authState = useAuthState();
const router = useRouter();
const { signOut } = useAuthActions();
const [isSigningOut, setIsSigningOut] = useState(false);
const [logOutError, setLogOutError] = useState<AuthErrorCategory | undefined>(undefined);

const isGuest = authState.status === 'guest';
const isAuthenticated = authState.status === 'authenticated';
if (!isGuest && !isAuthenticated) return null;
```

Handler (module-scope-free, defined in the component body):

```tsx
const handleLogOutPress = async () => {
  if (isSigningOut) return;                 // double-press guard, on top of `disabled`
  setIsSigningOut(true);
  setLogOutError(undefined);
  const { error } = await signOut();
  if (error) {
    const category = categorizeAuthError(error);
    logAuthWarning('Log out failed.', error);
    trackAuthEvent('log_out_error', category);
    setLogOutError(category);
  } else {
    trackAuthEvent('log_out_success');
  }
  setIsSigningOut(false);                   // always reset, incl. on success
};
```

- Imports needed: `useState` from react; `categorizeAuthError` + `type AuthErrorCategory` from
  `@/features/auth/model/auth-errors`; `logAuthWarning`, `trackAuthEvent` from
  `@/features/auth/observability/auth-observability`; `LOG_OUT_ERROR_COPY` from step 1;
  `useAuthActions` added to the existing `auth-provider` import.
- `trackAuthEvent(name: string, category?)` takes a free-form name; `'log_out_success'` /
  `'log_out_error'` are the names `useLogoutGuard` already emits — match them exactly so
  observability stays comparable across the two logout surfaces.
- **Always reset `isSigningOut` on success too.** The component itself is not unmounted by the
  auth-state flip (only its authenticated branch is), so a stuck `true` would show "Logging out..."
  again if the visitor later signs in and returns. This is the one lifecycle difference from
  `AccountSection`, which relies on its own top-level `return null` to unmount everything.
- `onPress` must not be a raw `async` function passed where a `() => void` is expected if lint
  complains; wrap as `onPress={() => { void handleLogOutPress(); }}`.

JSX shape:

```tsx
<HeaderBar testID="landing-header-bar" $visible={visible} pointerEvents={visible ? 'auto' : 'none'}>
  <Brand>Daily Dama</Brand>
  <ButtonRow>
    {isGuest ? (
      <>{/* existing SignUpButton + SignInButton, unchanged */}</>
    ) : (
      <LogOutColumn>
        {logOutError ? <ErrorText>{LOG_OUT_ERROR_COPY[logOutError]}</ErrorText> : null}
        <LogOutButton
          accessibilityLabel="Log out"
          size="medium"
          variant="secondary"
          disabled={isSigningOut}
          onPress={() => { void handleLogOutPress(); }}>
          {isSigningOut ? 'Logging out...' : 'Log out'}
        </LogOutButton>
      </LogOutColumn>
    )}
  </ButtonRow>
</HeaderBar>
```

- `accessibilityLabel="Log out"` and the label text must both be `Log out` — same string
  `AccountSection` uses.
- New styled components: `LogOutColumn` (`align-items: flex-end; gap: 6px;`) and `LogOutButton`
  (copy `SignInButton`'s `align-self: flex-start; padding: 10px 14px;`), plus a small `ErrorText`
  mirroring `account-section.tsx`'s (`color: ${AppColors.red}; font-size: 12px; font-weight: 800;`).
  Keep the file's existing single-quote style (this file uses `'`, `account-section.tsx` uses `"` —
  don't reformat either).
- **Rewrite the doc comment.** The block at lines 16-35 currently asserts "It renders nothing once a
  visitor is authenticated, matching GuestAccountSection's mutually-exclusive render-null gating."
  Replace that sentence with the new contract and the reason, roughly: *for an authenticated

## 5. Risks and edge cases

- **Unsynced-changes guard is bypassed on this surface.** This is the accepted trade-off, not an
  oversight: `pendingCount` is unknowable on `/`. It is not data loss — `signOut({ scope: 'local' })`
  leaves the `user:<id>:` namespace and its outbox on disk, and the next sign-in on this device
  flushes it — but it is a real gap versus Profile's guarded logout. Call it out explicitly in the
  PR body and in the TASKS.md Notes. If the owner wants parity, that's a separate ticket (see §6).
- **Don't weaken `useSyncCoordinatorStatus`'s throw** to make the guard importable here. That
  invariant is what keeps the sync provider hierarchy honest; a silent null-object fallback would
  make a genuinely-pending logout look clean.
- **No flash of the wrong bar** depends on `initializing` staying `null`. If you "simplify" the
  matrix to `isGuest ? guestBar : authedBar`, a signed-in reload paints a logout button before auth
  resolves, and a signed-out visitor paints it forever when Supabase is unconfigured
  (`guest/unconfigured` arrives one microtask later). Keep the explicit four-way matrix.
- **320px width**: `Daily Dama` + one `Log out` button is narrower than the existing guest bar, so
  the authenticated variant cannot regress the measured 320px fit. Still glance at it while the dev
  server is open.
- `getSupabaseClient()` returning null makes `signOut` fail with "Supabase is not configured" — but
  in that configuration `authState` is `guest/unconfigured`, so the logout button never renders.
  No extra handling needed.
