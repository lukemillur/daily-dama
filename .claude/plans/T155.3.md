# T155.3 -- Model custom tricks and immutable practice sessions

## Context already confirmed on this branch

- T155.1 (merged) created the api/private schema split with deny-by-default
  privileges. T155.2 (merged) added api.profiles/api.user_trick_states on
  top of it and established the working conventions this ticket reuses:
  (user_id, ...) ownership via RLS using/with check (user_id = auth.uid()),
  opaque trick_id text columns with no FK (standard Kentei tricks live only
  in app code), revision/created_at/updated_at columns present but inert
  until T155.5's server-owned triggers, and inline CHECK constraints rather
  than a shared JSON-invariant helper (T155.6's concern).
- supabase/tests/t155_2_profiles_and_trick_states.test.sql is the only
  existing pgTAP file and is the style template for the new one.
- Local domain read directly before writing SQL (not re-derived from
  AGENTS.md alone):
  - src/features/custom-tricks/model/custom-trick.ts -- CustomTrick is a
    discriminated union on kind ('standalone' | 'sequence').
    SequenceStep is a second discriminated union: existingTrick carries
    sourceTrickId + a name snapshot; customText carries only a name.
    selectSequenceStepCandidates is the single place that limits sequence
    step candidates to standard tricks + *standalone* custom tricks -- this
    is the "no nested sequences" rule the exit criteria calls out, and it
    has no server-side equivalent yet, so this migration has to invent one.
  - src/features/custom-tricks/persistence/custom-trick-persistence.ts --
    confirms runtime validation rules to mirror: normalized (non-empty,
    trimmed) name/step name, optional integer kenteiRank 1-12, a
    sequence needs steps.length >= 2, and duplicate ids across the
    collection are rejected (new Set(ids).size !== ids.length).
  - src/features/stats/model/practice-history.ts -- PracticeSessionRecord
    is the *actual* row shape to mirror, not SeshSummary/SeshPlan. It has
    no "plan" field at all: id, trickId, trickName, startedAt,
    completedAt, durationMs, laceCount, optional plannedDurationMs,
    optional origin (currently only 'assessment'). Do not add a plan
    jsonb column -- that would be modeling SeshSummary, not the persisted
    record.
  - id there is a deterministic composite of startedAt, endedAt and trick.id
    (see createPracticeSessionRecordId), not a random id. The local reducer
    already dedups on this id by silently ignoring a re-insert; this
    migration's job is different: the exit criteria ask for a *duplicate id
    to be rejected*, so a repeat insert should throw (client's insert-only
    contract), not no-op.
- Local stack re-verified in this planning session (npx --yes
  supabase@2.115.0 start / db reset / test db --local all still work).
  supabase test db --local needs Docker via Colima running (colima
  status / docker ps).
- **Verified empirically, this session:** CHECK constraints cannot contain
  subqueries at all (not just cross-table ones) -- confirmed T155.2's own
  planning note, and additionally confirmed that even a bare
  jsonb_array_elements(...)-backed EXISTS(...)/derived-table subquery
  referencing only the row's own column is rejected by Postgres inside a
  CHECK. Per-element step-shape validation and the nested-sequence rule
  (which needs to see *other* rows) are therefore both implemented as a
  single BEFORE INSERT OR UPDATE trigger function, not CHECK constraints.
  Cheap scalar-only shape rules (kind enum, non-blank/trimmed name,
  kentei_rank range, "sequence needs steps to be an array of length >= 2")
  stay as ordinary CHECK constraints.
- **Verified empirically, this session:** two *separate* CHECK constraints
  combined implicitly by AND are not guaranteed to short-circuit each other --
  check (kind <> 'sequence' or jsonb_typeof(steps) = 'array') as one
  constraint and check (kind <> 'sequence' or jsonb_array_length(steps) >=
  2) as a second, separate constraint caused jsonb_array_length to be
  evaluated (and error: "cannot get array length of a non-array") even when
  steps wasn't an array, despite the first constraint "protecting" it. The
  fix is to combine both conditions inside **one** constraint's OR/AND
  expression: check (kind <> 'sequence' or (jsonb_typeof(steps) = 'array'
  and jsonb_array_length(steps) >= 2)). Postgres does short-circuit AND/OR
  *within a single boolean expression* in practice; it does not do so across
  independently-declared constraints. Keep this in mind if the implementer is
  tempted to split shape constraints for readability -- combine conditions
  that depend on each other's truth into one constraint instead.
- **Verified empirically, this session:** jsonb_array_elements(NULL::jsonb)
  used as a FROM-clause / CROSS JOIN LATERAL item yields zero rows rather
  than erroring, which is what lets the "does any other sequence already
  reference this row" query below run across all rows (including standalone
  rows whose steps column is NULL) without a WHERE ct.kind = 'sequence'
  guard *before* the lateral join -- the query still filters by
  ct.kind = 'sequence', but that filter can safely apply in the outer
  WHERE alongside the join rather than needing to precede it.

## Step 1 -- Design decisions

1. **Two tables, not a shared "documents" table.** api.custom_tricks and
   api.practice_sessions are structurally unrelated (mutable owned
   documents vs. an append-only log) and have different grant/RLS shapes;
   keep them as separate create table statements in one migration file
   (mirrors T155.2 doing two tables in one file).
2. **(user_id, id) composite primary key on both tables**, not a
   surrogate uuid PK. id is the client-generated stable id
   (createCustomTrickId / createPracticeSessionRecordId) that must
   survive renames and must reject same-user duplicates -- a composite PK
   gets both properties for free and is the natural analogue of
   user_trick_states_unique_per_user's composite unique constraint.
   Cross-user id collisions are irrelevant (each user's rows are a disjoint
   partition) and are not a thing either id-generation scheme risks in
   practice.
3. **Sequence steps stored as one jsonb column on the trick row**, not a
   child table. Like api.profiles.last_sesh, steps are a small,
   wholesale-replaced-together, always-read-with-the-parent document (a
   sequence is edited/re-saved as a whole in the local UI), not
   independently queried or paginated rows.
4. **No FK from practice_sessions.trick_id or from a sequence step's
   sourceTrickId to api.custom_tricks.id.** Both cases mirror
   api.user_trick_states.trick_id's existing precedent: the referenced id
   may name a standard Kentei trick (never a database row), and even when it
   does name a custom trick, trick_name/the step's name is an
   authoritative *snapshot* -- AGENTS.md is explicit that editing/deleting a
   custom trick must never rewrite historical Stats or existing sequences.
   A FK would either block deletion (wrong) or force on delete set null
   (would silently blank a snapshot that must stay put). Don't add one later
   without revisiting this invariant first.
5. **Nested-sequence enforcement is one trigger function, both directions.**
   The exit criteria says "reject nested sequences." That has two distinct
   failure shapes, both required:
   - *Direct*: inserting/editing a sequence whose existingTrick step points
     at a row that is currently kind = 'sequence'.
   - *Retroactive*: a sequence Y already references standalone trick X;
     later, X itself is edited to kind = 'sequence'. Without an explicit
     check in this direction, X's conversion would silently turn Y into a
     nested sequence.
   Self-reference (a sequence step naming its own row) is handled as a
   degenerate case of the direct check, checked first for a clearer error.
   Both checks live in private.enforce_custom_trick_step_invariants(),
   the SQL analogue of centralizing this in selectSequenceStepCandidates.
6. **practice_sessions is select+insert only, at the grant level *and* the
   policy level.** grant select, insert on api.practice_sessions to
   authenticated (no update/delete grant at all) plus only a
   practice_sessions_select_own/practice_sessions_insert_own policy pair
   (no update/delete policy exists). Belt-and-suspenders: even if a future
   migration mistakenly added an update/delete grant, there would still be no
   permissive policy to allow it (RLS defaults to deny). A client attempt
   fails with a plain 42501 permission error, before RLS policy evaluation
   is even reached.
7. **User-scoped pagination indexes** beyond the PK: (user_id, created_at
   desc, id) on custom_tricks and (user_id, completed_at desc, id) on
   practice_sessions -- both tables are read back "this account's rows,
   most-recent-first, a page at a time," which the (user_id, id) PK alone
   only supports in id order.

```sql
-- Model custom tricks and immutable practice-history sessions (T155.3). Adds
-- the third and fourth application tables on top of the api/private schema
-- boundary (T155.1) and the ownership/JSON-invariant patterns established by
-- T155.2 (api.profiles, api.user_trick_states).
--
-- Local domain mirrored (see AGENTS.md "Custom-trick model invariants" and
-- "Sesh and Stats behavior", and src/features/custom-tricks/model/custom-trick.ts,
-- src/features/stats/model/practice-history.ts):
--   - api.custom_tricks mirrors CustomTrick (standalone | sequence). Sequence
--     steps are a discriminated union (existingTrick: sourceTrickId + name
--     snapshot; customText: name only). Sequences may reference standard
--     tricks (opaque, not in this database) or standalone custom tricks, but
--     never another sequence -- enforced centrally by one trigger function,
--     mirroring how selectSequenceStepCandidates centralizes the same rule
--     client-side.
--   - api.practice_sessions mirrors PracticeSessionRecord: an immutable,
--     insert-only historical snapshot (trick id + name, timing, lace count).
--     "Client-fact timing" means started_at/completed_at/duration_ms are
--     supplied by the client as historical fact (the Sesh reducer already
--     owns countdown/active/completed transitions locally); this migration
--     validates shape and internal consistency, not elapsed-time correctness.
--
-- As with T155.2, server-owned timestamp/revision triggers and comprehensive
-- per-operation grant audits are T155.5-T155.7's concern; this migration
-- still needs working ownership enforcement and domain invariants now
-- because its own exit criteria require proving both today.

-- 1. api.custom_tricks: one row per (user, custom trick). `id` is the
--    client-generated stable id from createCustomTrickId, unrelated to the
--    editable `name` -- renaming a trick never changes its id, and nothing
--    here regenerates it. Primary key is (user_id, id): stable per account,
--    and naturally rejects a duplicate id for the same user re-using
--    createCustomTrickId's collision-resistant scheme.
create table api.custom_tricks (
  user_id uuid not null references auth.users(id) on delete cascade,
  id text not null,

  kind text not null,
  name text not null,
  kentei_rank smallint,
  -- Sequence steps live as a jsonb array here rather than a child table:
  -- like api.profiles.last_sesh, they are a small, wholesale-replaced,
  -- read-together-with-the-parent document, not independently queried rows.
  steps jsonb,

  revision integer not null default 1,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),

  primary key (user_id, id),

  constraint custom_tricks_id_not_blank check (length(id) > 0),
  constraint custom_tricks_kind_known check (kind in ('standalone', 'sequence')),
  constraint custom_tricks_name_shape check (length(name) > 0 and name = btrim(name)),
  constraint custom_tricks_kentei_rank_range
    check (kentei_rank is null or kentei_rank between 1 and 12),

  -- Cheap, purely-scalar shape checks live here as ordinary CHECK
  -- constraints. Per-element step validation and the nested-sequence rule
  -- need to inspect array elements and (for nesting) sibling rows, which
  -- CHECK constraints cannot do (no subqueries, no other-row visibility) --
  -- both live in the trigger below instead.
  constraint custom_tricks_standalone_has_no_steps
    check (kind <> 'standalone' or steps is null),
  constraint custom_tricks_sequence_steps_shape
    check (
      kind <> 'sequence'
      or (jsonb_typeof(steps) = 'array' and jsonb_array_length(steps) >= 2)
    )
);

comment on table api.custom_tricks is
  'One row per custom trick (standalone or sequence) owned by an account. Mirrors CustomTrick (src/features/custom-tricks/model/custom-trick.ts). id is the stable client-generated id; name is independently editable. Sequence steps are validated (shape + no nesting) by custom_tricks_enforce_step_invariants.';

-- 2. Centralized step-shape and no-nested-sequences enforcement. Runs on
--    every insert/update because both directions of the nesting rule need
--    checking, not just "this row's own steps":
--      (a) a sequence's own existingTrick steps must not point at another
--          row that is itself kind = 'sequence' (the direct case: creating
--          or editing a sequence to reference another sequence).
--      (b) a row becoming/remaining kind = 'sequence' must not already be
--          referenced as an existingTrick step by some *other* sequence
--          (the retroactive case: converting a standalone trick that an
--          existing sequence already references into a sequence itself).
--    Self-reference (a sequence step naming its own row) is rejected as a
--    degenerate case of (a).
create function private.enforce_custom_trick_step_invariants()
returns trigger
language plpgsql
as $$
declare
  step jsonb;
  referenced_kind text;
  referencing_count integer;
begin
  if new.kind = 'sequence' and jsonb_typeof(new.steps) = 'array' then
    for step in select * from jsonb_array_elements(new.steps)
    loop
      if jsonb_typeof(step) <> 'object'
        or not (step ? 'kind')
        or not (step ? 'name')
        or jsonb_typeof(step -> 'name') <> 'string'
        or length(step ->> 'name') = 0
        or step ->> 'name' <> btrim(step ->> 'name')
      then
        raise exception 'malformed sequence step: %', step using errcode = '23514';
      end if;

      if step ->> 'kind' = 'customText' then
        if step <> jsonb_build_object('kind', 'customText', 'name', step -> 'name') then
          raise exception 'malformed customText step (unexpected keys): %', step using errcode = '23514';
        end if;

      elsif step ->> 'kind' = 'existingTrick' then
        if not (step ? 'sourceTrickId')
          or jsonb_typeof(step -> 'sourceTrickId') <> 'string'
          or length(step ->> 'sourceTrickId') = 0
          or step <> jsonb_build_object(
               'kind', 'existingTrick', 'name', step -> 'name', 'sourceTrickId', step -> 'sourceTrickId'
             )
        then
          raise exception 'malformed existingTrick step: %', step using errcode = '23514';
        end if;

        if step ->> 'sourceTrickId' = new.id then
          raise exception 'a sequence cannot reference itself as a step (trick %)', new.id
            using errcode = '23514';
        end if;

        select ct.kind into referenced_kind
        from api.custom_tricks ct
        where ct.user_id = new.user_id and ct.id = step ->> 'sourceTrickId';

        if referenced_kind = 'sequence' then
          raise exception 'nested sequences are not allowed (step references sequence %)', step ->> 'sourceTrickId'
            using errcode = '23514';
        end if;

      else
        raise exception 'unknown sequence step kind: %', step ->> 'kind' using errcode = '23514';
      end if;
    end loop;

    select count(*) into referencing_count
    from api.custom_tricks ct
    cross join lateral jsonb_array_elements(ct.steps) as s(value)
    where ct.user_id = new.user_id
      and ct.kind = 'sequence'
      and ct.id <> new.id
      and s.value ->> 'kind' = 'existingTrick'
      and s.value ->> 'sourceTrickId' = new.id;

    if referencing_count > 0 then
      raise exception 'trick % cannot become a sequence: it is already referenced as a step by another sequence', new.id
        using errcode = '23514';
    end if;
  end if;

  return new;
end;
$$;

create trigger custom_tricks_enforce_step_invariants
before insert or update on api.custom_tricks
for each row execute function private.enforce_custom_trick_step_invariants();

-- 3. api.practice_sessions: one row per completed Sesh, mirroring
--    PracticeSessionRecord (src/features/stats/model/practice-history.ts).
--    trick_id/trick_name are the authoritative snapshot -- editing or
--    deleting a custom trick must never rewrite historical Stats, so there
--    is deliberately no FK to api.custom_tricks (same reasoning as
--    api.user_trick_states.trick_id: it may name a standard Kentei trick,
--    which never has a row in this database, or a custom trick that may
--    later be renamed or deleted). Timestamps are epoch milliseconds
--    (client-fact timing), matching the numbers already stored locally.
create table api.practice_sessions (
  user_id uuid not null references auth.users(id) on delete cascade,
  id text not null,

  trick_id text not null,
  trick_name text not null,

  started_at bigint not null,
  completed_at bigint not null,
  duration_ms bigint not null,
  lace_count integer not null,

  -- Set only for a comparable timed attempt (see isEligibleTimedAttempt);
  -- absent for open-ended seshes and for timed seshes that don't qualify.
  planned_duration_ms bigint,
  -- Set only for a Kentei-assessment-recorded session; absent otherwise.
  origin text,

  created_at timestamptz not null default now(),

  primary key (user_id, id),

  constraint practice_sessions_id_not_blank check (length(id) > 0),
  constraint practice_sessions_trick_id_not_blank check (length(trick_id) > 0),
  constraint practice_sessions_trick_name_shape
    check (length(trick_name) > 0 and trick_name = btrim(trick_name)),

  constraint practice_sessions_started_at_positive check (started_at > 0),
  constraint practice_sessions_completed_not_before_started
    check (completed_at >= started_at),
  constraint practice_sessions_duration_matches_timing
    check (duration_ms = completed_at - started_at),
  constraint practice_sessions_lace_count_nonnegative check (lace_count >= 0),
  constraint practice_sessions_planned_duration_positive
    check (planned_duration_ms is null or planned_duration_ms > 0),
  constraint practice_sessions_origin_known
    check (origin is null or origin = 'assessment')
);

comment on table api.practice_sessions is
  'One immutable row per completed Sesh. Mirrors PracticeSessionRecord (src/features/stats/model/practice-history.ts). Insert-only: no update/delete grant or policy exists for authenticated (see RLS below), matching the local invariant that historical Stats records never change after being recorded.';

-- 4. User-scoped pagination indexes. Both tables are read back "give me
--    this account's rows, most-recent-first, a page at a time"; the
--    (user_id, id) primary key alone only supports id-ordered access.
create index custom_tricks_user_created_at_idx
  on api.custom_tricks (user_id, created_at desc, id);

create index practice_sessions_user_completed_at_idx
  on api.practice_sessions (user_id, completed_at desc, id);

-- 5. Ownership and immutability. custom_tricks follows T155.2's own-row
--    pattern (full CRUD, scoped to auth.uid()). practice_sessions is
--    deliberately narrower: only select/insert are granted at all, and only
--    select/insert policies exist, so there is no permissive path to
--    update or delete a row post-insert -- a client attempt fails with a
--    plain permission error (42501) before RLS policy evaluation even
--    matters, giving defense in depth against a future accidental grant.
alter table api.custom_tricks enable row level security;
alter table api.practice_sessions enable row level security;

grant select, insert, update, delete on api.custom_tricks to authenticated;
grant select, insert on api.practice_sessions to authenticated;

create policy custom_tricks_own_row on api.custom_tricks
  for all
  to authenticated
  using (user_id = auth.uid())
  with check (user_id = auth.uid());

create policy practice_sessions_select_own on api.practice_sessions
  for select
  to authenticated
  using (user_id = auth.uid());

create policy practice_sessions_insert_own on api.practice_sessions
  for insert
  to authenticated
  with check (user_id = auth.uid());
```

## Step 5 -- What this ticket deliberately does not do

- No server-owned-timestamp/revision triggers for custom_tricks (T155.5):
  created_at/updated_at/revision have plain default expressions only,
  same posture as T155.2's tables. practice_sessions has no revision or
  updated_at at all (rows never change post-insert, so there is nothing to
  version) -- only created_at (server-side ingestion time), which stays a
  plain default too.
- No shared JSON-invariant helper function (T155.6): the step-shape checks
  live inline in private.enforce_custom_trick_step_invariants() rather than
  as a reusable validator, consistent with T155.2's profiles_last_sesh_shape
  precedent. Expect T155.6 to refactor rather than introduce this from
  scratch, and expect it may also want to fold the *shape* half of this
  trigger into that shared helper while leaving the *nesting* half (which
  needs cross-row visibility) as a trigger regardless.
- No comprehensive per-table grant/RLS audit across all six tables (T155.7):
  the grants/policies here are real, tested, and already prove select-only
  vs. full-CRUD ownership isolation for exactly these two tables -- but
  T155.7 is the ticket that reviews grants across all six tables together and
  tests grants/RLS independently of each other. Do not skip writing working
  RLS now on the theory T155.7 will "really" do it.
- No client wiring, no sync/upload path, no reconciliation with the local
  AsyncStorage-backed collections -- this ticket is schema-only, matching its
  Area ("Custom tricks / practice-history cloud schema").
- No pagination *query* helpers (e.g. an RPC or view) -- only the indexes
  that a future paginated read would need. Building the actual paginated
  read is a later ticket's concern.

## Open items for the implementer to note, not resolve here

- practice_sessions.origin only accepts NULL or 'assessment' today
  (PracticeSessionOrigin is currently a one-member union client-side). If a
  future origin value is added client-side, practice_sessions_origin_known
  must be updated in the same change -- it will otherwise silently reject the
  new value with a generic 23514, which is the intended fail-closed
  behavior but worth remembering as the reason for a mysterious rejection.
- duration_ms = completed_at - started_at is enforced exactly (both are
  epoch-millisecond bigints asserted as client-fact history, not
  recomputed). If a future client ever needs to record a session with
  paused/excluded time such that displayed duration and wall-clock elapsed
  time diverge, that is a schema change, not a bug in this constraint --
  today's local Sesh reducer already reports durationMs as the actual
  elapsed practice time it wants recorded, so this is a faithful mirror, not
  an oversight.
- The nested-sequence trigger currently re-queries api.custom_tricks on
  every insert/update of a kind = 'sequence' row (once per existingTrick
  step for the direct check, once more for the retroactive check). Fine at
  prototype scale (a handful of custom tricks per user); revisit only if a
  future ticket's data volume assumptions change.
