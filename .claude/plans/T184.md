# T184 -- Make auth-screen text and background theme-responsive

## Context confirmed in the current codebase

- src/app/auth/_layout.tsx already mounts CachedAppThemeProvider (T170) around all four /auth/* routes, using useCachedGuestTheme (synchronous pre-hydration cache read, gated by the same useSyncExternalStore hydration guard T145 introduced). This ticket does not touch the provider layer at all -- it is a pure consumer-side change. There is no new hydration path to invent and no risk of reintroducing T145 flash-of-unstyled-content regression, provided no new useEffect/useState pre-hydration gating is added in the screens themselves. Plan below adds none -- it only swaps AppColors.* literals for theme.* interpolations inside already-mounted styled-components templates and wraps existing JSX in <Screen>, which reads theme via useContext(ThemeContext) synchronously on the same render.
- All four screens (sign-up-screen.tsx, sign-in-screen.tsx, forgot-password-screen.tsx, reset-password-screen.tsx) already use <Screen> for every placeholder branch (initializing/authenticated/redirecting/requested/completed/link-invalid), each with align="center". Only the final, primary-form return statement in each file skips <Screen> and renders <FormScroll> (a bare styled(ScrollView)) directly. That is the literal bug this ticket fixes: the placeholder branches already resolve theme.background via Screen; the form people actually use does not.
- account-security-screen.tsx (T172) is the exact target pattern already in the codebase. The whole component return wraps everything, including the primary form, in one <Screen> (not per-branch align="center" <Screen> wrappers plus a bare form) -- but for the four /auth/* screens we should keep each branch own existing <Screen align="center"> as-is and just add <Screen> (no align, i.e. default "stretch") around the primary-form <FormScroll> return, matching what those screens already do for their other branches rather than restructuring all branches into one shared wrapper. This is a smaller, lower-risk diff and keeps each branch existing centered-vs-stretch layout intent intact.
  FieldInput there is styled(TextInput).attrs(({ theme }) => ({ placeholderTextColor: theme.textMuted })) with background-color: theme.background, border: 2px solid theme.text, color: theme.text via template interpolation. The JSX call site has no inline placeholderTextColor prop -- the .attrs supplies it. Plain styled.Text labels (FieldLabel, SectionLabel) already use theme.text in all four screens already (pre-existing, not part of this ticket).
- password-input.tsx InputRow (background-color: AppColors.paper, border: 2px solid AppColors.ink), Input (color: AppColors.ink), and ToggleText (color: AppColors.ink) are the only hardcoded paper/ink usages there. FieldHint (AppColors.textSubtle) and ErrorText (AppColors.red) are not paper/ink and are out of this ticket explicit scope per the task description -- leave them as-is. The inline placeholderTextColor={AppColors.textSubtle} prop on Input is also not paper/ink; leave it as-is too (do not add a .attrs placeholder-color swap here -- it is not requested and it is not needed for the exit criteria, which only requires background and field colors, not placeholder color, to resolve from theme).
- Styled-components ThemeContext default is {}, not undefined -- confirmed by the existing account-security-screen.test.tsx unwrapped mount() helper, which renders the component with no ThemeProvider at all and never throws even though FieldInput/FieldLabel already read theme.text/theme.background. So switching AppColors.paper/AppColors.ink to theme.background/theme.text is safe for every existing unthemed test in all four screens and in password-input.test.tsx -- theme.text just evaluates to undefined there, which react-native/styled-components tolerates in a style object today (existing tests never assert on those colors).
- Test pattern to reuse (from account-security-screen.test.tsx): mount with <StyledThemeProvider theme={customTheme}>...</StyledThemeProvider> (imported from styled-components/native) using a literal DefaultTheme object with distinct hex values per field -- not CachedAppThemeProvider/localStorage seeding, which the existing T170 tests use for the button-color assertions and which is unnecessary extra indirection for this ticket background/field-color assertions. Reuse resolvedStyle (finds the first node with a plain resolved RN style object) to read Screen resolved $background-driven backgroundColor and FieldInput/PasswordInput resolved backgroundColor/borderColor/color.
