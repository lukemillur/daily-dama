# T161.2 implementation plan

## Outcome for this iteration

Harden the existing `delete-account` Edge Function so an authenticated account
deletion attempt has bounded abuse impact, does not leak credentials or account
facts, never caches a response, and converges safely when the first successful
deletion response was lost. The implementation remains a single server-side
deletion boundary; it does not add a frontend route, local cleanup, delayed
deletion, or a new database domain (those belong to T161.4/T161.5).

## Current evidence and dependency boundary

- T161.1 is present and archived in `TASKS_DONE.md`.
- `supabase/functions/delete-account/index.js` currently validates a closed
  body, resolves the caller with `auth.getUser()`, verifies the password with a
  non-persisted client, and calls `auth.admin.deleteUser()` with the service
  role. It only adds `Cache-Control: no-store` to the success response.
- `supabase/tests/functions/t161_1_delete_account.test.mjs` is the existing
  real-HTTP contract suite; its successful deletion and cleanup assertions must
  remain valid.
- `supabase/config.toml` enables the function with `verify_jwt = true` and a
  JavaScript entrypoint. Supabase's built-in Auth rate limits do not provide the
  required per-delete user and IP dimensions, so the function needs its own
  bounded limiter.
- `supabase/README.md` documents `yarn test:functions`, its local-stack
  prerequisite, and the required clean `db reset` after the suite. There is no
  separate account-deletion handoff.

## Ordered implementation steps

1. Extract the request handler's policy and dependencies from the Deno entry
   point into a testable function module (for example
   `supabase/functions/delete-account/handler.js`). Inject the Supabase client
   factory, clock, rate-limit store, safe logger, and request-IP resolver so
   Node tests can exercise all branches without importing the Deno runtime or
   making real Auth calls. Keep `index.js` responsible only for importing the
   Supabase dependency and starting `Deno.serve`.

2. Add an explicit, named rate-limit configuration in the function module: a
   bounded attempt window and maximum attempts (with one local/test-visible
   configuration source). Count deletion attempts after a gateway-accepted
   request has enough information to associate it with the trusted identity,
   and maintain both dimensions independently: trusted user identity and the
   resolved client IP. A request is rejected when either dimension is
   exhausted; failed password/confirmation/deletion attempts must not reset
   either bucket. Use an injectable monotonic/test clock and an in-memory
   bounded store for this prototype, with eviction of expired buckets and a
   documented deployment limitation that multiple Edge isolates do not share
   memory. Do not use `user_id`, email, or any identity field from the JSON
   body. Do not let a caller-controlled forwarding header become an
   authorization identity; centralize the platform-provided IP extraction and
   document the trusted-proxy assumption.

3. Preserve the authentication order and strengthen the identity boundary.
   Resolve the caller through the gateway-validated bearer token and the
   server-side Auth API; use only that result's identity/email for password
   verification and only that result's user ID for admin deletion. Configure
   both the identity lookup client and password-check client with
   `persistSession: false` and `autoRefreshToken: false`, and explicitly discard
   the `signInWithPassword` result rather than returning, storing, or logging
   its session. The success and all error responses must remain generic.

4. Define the lost-response/idempotency rule explicitly. If the request carries
   a gateway-verified bearer identity but the Auth identity is already absent,
   return the same completed `204` result with `Cache-Control: no-store`, do no
   password sign-in, do not call an operation that could recreate the user, and
   expose no distinction in the response body or headers. This is safe because
   the only remaining operation is deletion of an already-absent identity; a
   retry for an existing identity still requires the current password. If the
   admin delete call races with another successful delete and reports “not
   found”, normalize that result to the same completed response. Keep invalid
   or unverifiable bearer tokens on the generic unauthorized path rather than
   treating arbitrary caller input as a deleted identity.

5. Centralize response construction so every response path includes
   `Cache-Control: no-store`: `OPTIONS`, unsupported methods, missing/invalid
   authorization, malformed body, confirmation/password failures, rate-limit
   responses, configuration failures, and unexpected failures. Preserve CORS
   headers and the existing empty `204` body. Use a generic rate-limit response
   with no account-specific retry detail unless the chosen contract requires a
   fixed, non-sensitive `Retry-After` value.

6. Add a structured, allow-listed security logger. Log only fixed event names,
   outcome/status, and non-sensitive operational categories such as
   `malformed_body`, `password_rejected`, `rate_limited_user`, or
   `delete_completed`. Never pass the request body, password, Authorization
   header/JWT, email, raw Auth error, response body, or arbitrary exception to
   `console.*`. If correlation is needed, use a generated request identifier
   that is not derived from user data, and keep it out of responses unless
   explicitly needed. Remove or update comments that claim redaction without
   enforcing it.

7. Extend the function test coverage in a new focused file
   `supabase/tests/functions/t161_2_delete_account_security.test.mjs` (or the
   equivalent handler-test file if the extraction makes that clearer):

   - table-driven response checks assert `Cache-Control: no-store` on every
     status path, including `OPTIONS` and rate limiting, and assert no response
     body/session is returned from successful password verification;
   - user-dimension tests make exactly the configured number of attempts,
     assert those are accepted/rejected according to the contract, then assert
     the next attempt is limited and a different trusted user has an
     independent bucket;
   - IP-dimension tests use two trusted users from one IP and two IPs for one
     user, proving both dimensions are independently enforced and that a
     caller-supplied body identity cannot move or bypass a bucket;
   - window-expiry tests advance the injected clock and prove the bucket can
     accept a new attempt without unbounded store growth;
   - log-capture tests invoke success, malformed, wrong-password,
     unauthorized, rate-limited, Auth-error, and unexpected-error paths with
     sentinel password/JWT/email/body values, then assert none of those values
     occurs in structured logger arguments or console output;
   - fake-client assertions prove the password-check client has disabled
     persistence/refresh, its returned session is not exposed, and admin
     deletion receives only the server-resolved user ID;
   - idempotency tests cover an already-absent user and an admin delete
     not-found race, asserting completed `204`/`no-store`, no recreation call,
     no password verification for the absent identity, and no account-fact
     response difference.

8. Keep or minimally strengthen
   `supabase/tests/functions/t161_1_delete_account.test.mjs` for the real local
   stack: add `no-store` assertions to representative rejection responses and
   retain the end-to-end cascade proof. Avoid using repeated real password
   sign-ins for deterministic limiter tests if GoTrue's own local Auth limits
   can interfere; those tests should exercise the injected handler policy, with
   one real HTTP smoke test proving wiring.

9. Update `supabase/README.md` only if the new test file or local configuration
   changes the documented command/setup. Document the configured attempt limit,
   the in-memory single-isolate limitation, and the fact that deployment-grade
   multi-isolate enforcement must be validated in the launch-security work
   (T162.4), without silently introducing a paid provider or a new persistence
   schema in this ticket.

## Security boundaries to preserve

- `verify_jwt = true` remains enabled; the function must not authorize from a
  body `user_id`, email, or any other caller-supplied identity.
- The service-role key remains server-only and is used only for the admin
  deletion call.
- Current-password verification is a one-shot check using a non-persisted
  client. No access/refresh session, password, token, email, raw body, or raw
  error may enter logs, response JSON, analytics, or durable state.
- All response paths are non-cacheable, including preflight and failures.
- Rate limiting is fail-closed when the limiter cannot safely determine its
  dimension, and it must not disclose whether a user exists.
- An already-absent identity is a completed deletion result only after the
  bearer request has passed the gateway/server authentication boundary; it is
  never recreated and never treated as permission to delete another identity.

## Verification and dedicated commands

During implementation, run the focused deterministic Node test file and the
existing function regression file. Then run:

```sh
yarn test:functions
yarn tsc --noEmit
```

Because this is Supabase/Edge security work, the final evidence must include a
clean local stack and database reset before `yarn test:functions`; finish with
another `npx --yes supabase@2.115.0 db reset` as required by
`supabase/README.md`. Also run the repository's dedicated security checks that
are affected by function source changes (at minimum the relevant secret scan)
and `node .claude/scripts/verify.mjs --test-file ...`/the documented equivalent
for the changed test files. The implementer should not claim the full
Docker-backed DB suite from a planner-only branch.

## Risks and review points

- An in-memory limiter is per isolate and can be bypassed across horizontally
  scaled instances or after restart. This is acceptable only as the prototype
  implementation boundary if the limitation is explicit and T162.4 measures
  hosted enforcement; do not present it as a global production guarantee.
- IP headers are proxy-sensitive. Review the chosen Supabase Edge runtime
  header and avoid trusting arbitrary client-provided forwarding values without
  the platform boundary documented.
- GoTrue error shapes can vary between local and hosted versions. Match
  not-found only through a narrow, tested classifier; all other admin/Auth
  errors remain generic server/unauthorized failures.
- Treating an authenticated retry for an absent identity as `204` intentionally
  gives no existence signal. The test must prove it does not become a route for
  deleting or recreating a different user.
- Do not add a durable idempotency table, distributed limiter, CAPTCHA, or
  hosted-project change here; those would change the persistence/infrastructure
  boundary and belong to a separately approved task.
