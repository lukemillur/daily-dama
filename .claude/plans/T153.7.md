# T153.7 — Fixed-destination PKCE callback foundation

## Confirmed mechanics (checked against the installed `@supabase/supabase-js@2.112.3` /
`@supabase/auth-js@2.112.3` source, not just docs)

- `client.auth.exchangeCodeForSession(code: string)` takes only the bare code string. It does
  **not** need (or read) a `type`/`next` query param from us. Internally (`GoTrueClient.ts`
  `_exchangeCodeForSession`, ~line 2026-2068) it looks up the stored PKCE verifier, which was
  saved with a `${verifier}/recovery` suffix at flow-initiation time only when the flow was
  started via `resetPasswordForEmail`. After a successful exchange it calls
  `_notifyAllSubscribers(redirectType === 'recovery' ? 'PASSWORD_RECOVERY' : 'SIGNED_IN', session)`
  — so **the existing `onAuthStateChange` subscription in `auth-provider.tsx` already receives the
  correct event**, and `deriveAuthState` (unchanged) already turns that into
  `{ status: 'passwordRecovery' }` or `{ status: 'authenticated' }`. This is exactly what
  `reset-password-screen.tsx` already keys off. Do not add any separate recovery/signup detection
  — the plumbing already exists.
- **Type-system trap**: the *runtime* success payload also includes `redirectType: 'recovery' |
  null` directly (confirmed in `GoTrueClient.ts` source), but the public method's declared
  TypeScript return type is the narrower `AuthTokenResponse`, which does **not** declare
  `redirectType` on `data`. Reading `data.redirectType` needs an explicit narrow/cast with a
  comment explaining the mismatch — see step 1. Do not spend time trying to get a "clean" typed
  read; the cast is the correct outcome here, not a workaround to avoid.
- Reason to prefer the SDK's own `redirectType` over watching shared `useAuthState()` from the
  callback route: `_notifyAllSubscribers` is `await`ed *inside* `_exchangeCodeForSession` before
  it resolves, so the state-setting call happens-before our `await exchangeCodeForSession(...)`
  resolves in JS microtask terms — but that only guarantees `setState` was *called*, not that
  React has committed it and re-rendered our component with the new context value by the time our
  async continuation runs. Gating navigation on watching `useAuthState()` from the callback route
  itself is a real (if narrow) race; reading the SDK's own returned `redirectType` is synchronous
  and race-free. Keep the two concerns separate: `onAuthStateChange` still updates the shared
  `AuthState` for every other consumer (unchanged); the callback route's own destination decision
  uses the direct return value.
- **Known Supabase gotcha, must be handled explicitly**: an already-expired/invalid link does not
  always arrive at `/auth/callback` with a `code` param at all. Supabase's Auth server itself can
  redirect straight to the callback URL with `error`/`error_code`/`error_description` params
  instead — and inconsistently, sometimes as a query string (`?error_code=otp_expired`) and
  sometimes as a URL **hash fragment** (`#error_code=otp_expired`) depending on which server path
  produced the redirect. `useLocalSearchParams()` only sees the query string. This route must also
  read `window.location.hash` on web, inside an effect (never at module scope / render body), to
  catch the fragment-borne error case — mirroring the existing hash-handling already present in
  `redact.ts`'s `redactUrl` (which anticipates exactly this).
- `getSupabaseClient()` already returns `null` off-web and during the Node static-export pass
  (via `Platform.OS !== 'web'`), and is only ever invoked from inside effects/callbacks elsewhere
  in this codebase. Follow the same rule for every new Supabase/window access in this task.

## Files to change, in order

### 1. `src/features/auth/state/auth-provider.tsx`

Add one new action to `AuthActions` and the provider:

```ts
readonly exchangeCodeForSession: (
  code: string,
) => Promise<{ redirectType: 'recovery' | null; error: AuthError | null }>;
```

Implementation:

```ts
const exchangeCodeForSession = useCallback(async (code: string) => {
  const client = getSupabaseClient();
  if (!client) {
    return { redirectType: null, error: new AuthError('Supabase is not configured.') };
  }
  const { data, error } = await client.auth.exchangeCodeForSession(code);
  if (error) return { redirectType: null, error };
  // supabase-js's public TS signature under-declares this: exchangeCodeForSession's runtime
  // success payload includes `redirectType: 'recovery' | null`, used to distinguish a
  // password-recovery code from a signup-confirmation code, but the declared return type
  // (AuthTokenResponse) omits it. Confirmed against the installed 2.112.3 GoTrueClient source.
  const redirectType = (data as unknown as { redirectType: 'recovery' | null }).redirectType;
  return { redirectType, error: null };
}, []);
```

Add it to the `actions` memo and its dependency array. Extend
`src/features/auth/state/__tests__/auth-provider.test.tsx`'s fake client (it currently mocks
`onAuthStateChange`, `signInWithPassword`, `signOut`, `updateUser`) with an
`exchangeCodeForSession` jest mock, and add cases: success with `redirectType: 'recovery'`,
success with `redirectType: null`, and an error pass-through. This is the one piece of new
provider-level surface the rest of the route depends on — land and test it before the route
itself.

### 2. `src/features/auth/components/auth-callback-screen.tsx` (new)

Mirrors `reset-password-screen.tsx`'s shape: a route-level screen component, no props, reading
`useLocalSearchParams`, `useRouter`, and the new `useAuthActions().exchangeCodeForSession`.

Behavior:

- On mount, in a single `useEffect`:
  1. Resolve `code` from `useLocalSearchParams<{ code?: string | string[]; error?: string |
     string[]; error_code?: string | string[] }>()`. Only treat a plain `string` value as valid
     (an array means a malformed/duplicated param — treat as malformed, same as missing).
  2. If `error`/`error_code` is present in the query params, skip the exchange entirely and go
     straight to the error branch using a synthetic `{ code: error_code }`-shaped object through
     the existing `categorizeAuthError` (do not invent new categories).
  3. Otherwise, if `code` is missing, go to the same error branch with a fixed
     `expiredOrInvalidLink`-shaped synthetic error (no code to exchange, no network call).
  4. Otherwise, guard against a duplicate exchange with a `useRef<string | null>(null)` set
     **synchronously, before the `await`**, to the code being processed; a second effect firing
     with the same `code` value (re-render, param identity change, etc.) short-circuits here rather
     than re-exchanging. Track an `isMounted`/`cancelled` flag from the effect's cleanup so a late
     resolution after unmount doesn't call `router.replace` or `setState` on an unmounted screen.
  5. Await `exchangeCodeForSession(code)`.
     - On `error`: `setCallbackErrorCategory(categorizeAuthError(error))`,
       `logAuthWarning('Auth callback exchange failed.', error)`,
       `trackAuthEvent('auth_callback_error', category)`. Do not navigate.
     - On success: `trackAuthEvent('auth_callback_success')`, then
       `router.replace(redirectType === 'recovery' ? '/auth/reset-password' : '/app/home')`.
       `router.replace` (not `push`) so the address bar's `?code=...` never survives as a
       back-navigable history entry, and so the final URL is the clean destination path with no
       query string — this is what satisfies "final browser URL contains no code or token" for the
       success path, no separate strip-then-navigate step is needed.
  6. On web only (`Platform.OS === 'web'`), also check `window.location.hash` for the same
     `error`/`error_code` pattern before falling through to step 3, per the gotcha above. Guard
     this read the same way `supabase-client.ts` guards `Platform.OS !== 'web'` — never read
     `window` unconditionally.
- While no error is set and no navigation has happened yet, render a minimal loading state
  (reuse the `Screen`/`Eyebrow`/`DisplayTitle` styling pattern from `reset-password-screen.tsx`,
  e.g. "Finishing sign-in...").
- On error, render a small fixed screen (same visual pattern as `reset-password-screen.tsx`'s
  "This link is no longer valid" branch) with copy keyed by `AuthErrorCategory`, and a single
  "Back to home" button (`router.replace('/')`). Do not surface `error_description` text or any
  raw Supabase message.
- **Never read a `next`/destination param from the URL at all** — the component's only two
  possible `router.replace` success targets are the two literal path strings above. There is no
  code path that accepts or forwards any URL-derived destination. This is what satisfies "rejection
  of an attempted `next`/open redirect" — there's simply no parameter read that could carry one,
  rather than a param that's read and then validated against an allowlist.

## Risks / non-obvious things to flag to the implementer

- The `redirectType` cast in step 1 is the correct, deliberate outcome of a real gap between
  `@supabase/supabase-js`'s declared types and its runtime behavior for this SDK version — don't
  "fix" it by switching to watching shared Auth state instead (that path is racier, as explained
  above), and don't downgrade/upgrade the SDK to chase a cleaner type — that's out of scope and a
  version bump has its own cross-cutting risk.
- Keep the hash-fragment error check web-only and effect-only; it is the one part of this task
  that's easy to accidentally write in a way that breaks the Node static-render pass by touching
  `window` at module or render-body scope.
- Do not add a `type=recovery`/`type=signup` URL-param read anywhere, even as a hint or
  double-check alongside `redirectType` — the exit criteria and BACKEND_ROADMAP.md are explicit
  that destination must not depend on an arbitrary URL value, and adding a redundant read of a
  spoofable param invites exactly the confusion this task is meant to close off.
- `src/features/auth/model/auth-errors.ts` has a `T153.8` comment reserving `accountAlreadyExists`
  as its own category — this task doesn't need to touch `auth-errors.ts` at all; every case here
  already maps through existing categories (`expiredOrInvalidLink`, `offline`, `rateLimited`,
  `unknown`).
