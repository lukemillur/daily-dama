# T155.2 — Model profiles and per-trick user state

## Context already confirmed on this branch

- T155.1 (merged) created the `api`/`private` schema split with deny-by-default
  privileges. `supabase/migrations/20260822191737_create_private_and_exposed_schemas.sql`
  exists. This ticket adds the first two `api` tables on top of it.
- No `supabase/tests/` directory exists yet. This ticket creates the first
  one; T155.8 later consolidates the harness across all six tables into one
  repeatable command.
- Local stack verified in this planning session:
  `npx --yes supabase@2.115.0 start` / `db reset` / `test db --local` all
  work against Docker (`supabase_db_daily-dama` container). `supabase test db
  --local` pulls a `public.ecr.aws/supabase/pg_prove:3.36` image on first run
  (needs network access once).
- Read the actual local `UserProfile` domain before touching SQL:
  `src/features/profile/model/user-profile.ts` (shape/reducer) and
  `src/features/profile/persistence/user-profile-persistence.ts` (the
  authoritative runtime-validation rules — kentei rank 1-12 only when
  `hasCompletedOnboarding`, `LastSesh` discriminated union backed by
  `isValidSeshTargetLandingCount`/`isValidTimedSeshMinutes` from
  `src/features/sesh/model/sesh.ts`, streak threshold a whole multiple of
  60_000ms in 1-60 minutes via `isValidStreakThresholdMinutes`, theme colors
  validated by `isValidThemeHexColor` = `^#[0-9a-fA-F]{6}$`). The SQL below
  was written directly against these functions so it stays in lockstep with
  the client-side rules, not a re-derivation from AGENTS.md alone.
- `selectedTrickIds` and `manuallyUnlockedTrickIds` are both trick-id arrays
  scoped to a user — this is the "per-trick user state" the ticket title
  calls out, modeled as one `api.user_trick_states` row per `(user_id,
  trick_id)` with two boolean flags rather than two arrays on the profile
  row (this is the S034 partitioning: it lets goal/note/session tickets
  later reference "the trick states for this user" without unpacking a JSON
  array, and keeps "duplicate trick states" a plain unique constraint the
  exit criteria explicitly asks for).
- `trick_id` is deliberately **not** a foreign key. Standard Kentei tricks
  are defined only in app code
  (`src/features/tricks/data/kendama-kentei-tricks.ts`), never in Postgres,
  and custom tricks get their own table only in T155.3 (not created yet). Do
  not add a FK here; do not block on T155.3.
- Verified empirically (not guesswork) that CHECK constraints cannot call
  set-returning functions like `jsonb_object_keys` or contain subqueries —
  `last_sesh`'s "no unknown keys" rule below instead uses the jsonb `<@`
  containment operator against a `jsonb_build_object(...)` built from the
  row's own values, which rejects any extra key without needing a SRF.
- Verified empirically that `set_config('request.jwt.claims', ..., true)`
  (the `is_local` flag) only survives to the end of the *current implicit
  transaction* — in a plain `psql -f` session each statement autocommits
  separately, so the GUC vanishes before the next statement runs. Use
  `is_local = false` for a multi-statement manual smoke test at the psql
  prompt, or rely on the fact that the whole pgTAP test file already runs
  inside one `begin`/`rollback` block (see the test file below), where
  `true`/`set local` is correct and intentional.

## Step 1 — Design decision: what belongs to `api.profiles` vs `api.user_trick_states`

`api.profiles` gets every profile field that is a single scalar or a single
small object per user: `has_completed_onboarding`, `kentei_rank`, `last_sesh`
(jsonb), `streak_threshold_ms`, and the three `theme_*_color` fields.
`api.user_trick_states` gets everything that is presently a *trick-id array*
on `UserProfile`: `selectedTrickIds` and `manuallyUnlockedTrickIds`,
collapsed into `is_selected`/`is_manually_unlocked` booleans on one row per
`(user_id, trick_id)`. Mapping this table shape back to the two arrays is
explicitly out of scope (T155.10); this step only needs the table itself to
be correct and testable.

## Step 2 — Write the migration

Run from the repo root:

```sh

```

This creates
`supabase/migrations/<timestamp>_add_profiles_and_user_trick_states.sql`. Put
exactly this content in it — already written, applied via a clean `db
reset`, and pgTAP-tested in this planning session (see Step 4); copy it
verbatim rather than re-deriving it, and only adapt it if a real discrepancy
shows up when you run it yourself:

```sql
-- Model per-account profiles and per-trick user state (T155.2). Adds the
-- first two application tables on top of the api/private schema boundary
-- established by T155.1. Server-owned timestamp/revision *triggers*,
-- comprehensive per-operation grants, and centralized JSON-invariant helpers
-- are deliberately owned by later tickets (T155.5-T155.7); this migration
-- still needs a *working* ownership-enforcement mechanism and domain
-- invariants now, because its own exit criteria require proving both today.
-- Expect T155.5/T155.7 to formalize/extend what is bootstrapped here rather
-- than to introduce these mechanisms from scratch.

-- 1. api.profiles: one row per Supabase Auth user, mirroring the local
--    `UserProfile` shape (src/features/profile/model/user-profile.ts) minus
--    its two trick-id array fields, which live in api.user_trick_states
--    instead (see below). `user_id` is both the primary key and the FK, so
--    there is exactly one profile row per account and it cannot be
--    re-parented to a different id.
create table api.profiles (
  user_id uuid primary key references auth.users(id) on delete cascade,

  has_completed_onboarding boolean not null default false,
  kentei_rank smallint,
  last_sesh jsonb,
  streak_threshold_ms integer,
  theme_background_color text,
  theme_accent_color text,
  theme_text_color text,

  -- Optimistic-concurrency counter for future sync (Phase 3). No tombstone
  -- column: a profile is deleted only by `on delete cascade` when the
  -- owning auth.users row is deleted (account deletion), never by a
  -- client-initiated soft delete.
  revision integer not null default 1,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),

  constraint profiles_kentei_rank_range
    check (kentei_rank is null or kentei_rank between 1 and 12),
  constraint profiles_kentei_rank_requires_onboarding
    check (
      (has_completed_onboarding and kentei_rank is not null)
      or (not has_completed_onboarding and kentei_rank is null)
    ),

  constraint profiles_streak_threshold_range
    check (
      streak_threshold_ms is null
      or (
        streak_threshold_ms % 60000 = 0
        and streak_threshold_ms between 60000 and 3600000
      )
    ),

  constraint profiles_theme_background_color_format
    check (theme_background_color is null or theme_background_color ~ '^#[0-9a-fA-F]{6}$'),
  constraint profiles_theme_accent_color_format
    check (theme_accent_color is null or theme_accent_color ~ '^#[0-9a-fA-F]{6}$'),
  constraint profiles_theme_text_color_format
    check (theme_text_color is null or theme_text_color ~ '^#[0-9a-fA-F]{6}$'),

  constraint profiles_last_sesh_shape
    check (
      last_sesh is null or (
        jsonb_typeof(last_sesh) = 'object'
        and (last_sesh ?& array['trickId', 'plan'])
        and last_sesh <@ jsonb_build_object('trickId', last_sesh->'trickId', 'plan', last_sesh->'plan')
        and jsonb_typeof(last_sesh->'trickId') = 'string'
        and length(last_sesh->>'trickId') > 0
        and jsonb_typeof(last_sesh->'plan') = 'object'
        and (last_sesh->'plan' ? 'kind')
        and (
          (
            last_sesh->'plan'->>'kind' = 'openEnded'
            and (last_sesh->'plan') <@ jsonb_build_object(
              'kind', 'openEnded',
              'targetLandingCount', last_sesh->'plan'->'targetLandingCount'
            )
            and (
              not (last_sesh->'plan' ? 'targetLandingCount')
              or (
                jsonb_typeof(last_sesh->'plan'->'targetLandingCount') = 'number'
                and (last_sesh->'plan'->>'targetLandingCount')::numeric between 1 and 999
                and (last_sesh->'plan'->>'targetLandingCount')::numeric
                  = floor((last_sesh->'plan'->>'targetLandingCount')::numeric)
              )
            )
          )
          or (
            last_sesh->'plan'->>'kind' = 'timed'
            and (last_sesh->'plan') <@ jsonb_build_object(
              'kind', 'timed',
              'durationMinutes', last_sesh->'plan'->'durationMinutes'
            )
            and (last_sesh->'plan' ? 'durationMinutes')
            and jsonb_typeof(last_sesh->'plan'->'durationMinutes') = 'number'
            and (last_sesh->'plan'->>'durationMinutes')::numeric between 1 and 60
          )
        )
      )
    )
);

comment on table api.profiles is
  'One row per Supabase Auth account. Mirrors UserProfile (src/features/profile/model/user-profile.ts) minus selectedTrickIds/manuallyUnlockedTrickIds, which live in api.user_trick_states.';

-- 2. api.user_trick_states: one row per (user, trick) that is either
--    selected for practice or manually laced/unlocked, mirroring the local
--    `selectedTrickIds`/`manuallyUnlockedTrickIds` arrays. `trick_id` is a
--    free-form opaque identifier (no FK): it may name a standard Kentei
--    trick (defined only in app code, not the database) or a custom trick
--    (whose table arrives in T155.3), so it cannot reference either today.
create table api.user_trick_states (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  trick_id text not null check (length(trick_id) > 0),

  is_selected boolean not null default false,
  is_manually_unlocked boolean not null default false,

  revision integer not null default 1,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),

  constraint user_trick_states_unique_per_user unique (user_id, trick_id),
  constraint user_trick_states_has_state check (is_selected or is_manually_unlocked)
);

comment on table api.user_trick_states is
  'One row per (user, trick) that is selected for practice and/or manually laced/unlocked. Mirrors UserProfile.selectedTrickIds/manuallyUnlockedTrickIds. trick_id is an opaque id with no FK: it may name a standard Kentei trick (app-code only) or a future custom trick (T155.3).';

-- 3. Ownership enforcement: `user_id` is never client-controlled. RLS
--    policies compare every row against `auth.uid()` for both the existing
--    row (USING) and the proposed row (WITH CHECK), so a client cannot
--    insert a row claiming another user's id, and cannot repoint an
--    existing row at another user's id via UPDATE. This also happens to
--    give cross-user SELECT/UPDATE/DELETE isolation, which T155.7 will
--    audit and extend per-table (e.g. making practice_sessions
--    select/insert-only); nothing here should be read as the final grant
--    surface for every table.
alter table api.profiles enable row level security;
alter table api.user_trick_states enable row level security;

grant select, insert, update, delete on api.profiles to authenticated;
grant select, insert, update, delete on api.user_trick_states to authenticated;

create policy profiles_own_row on api.profiles
  for all
  to authenticated
  using (user_id = auth.uid())
  with check (user_id = auth.uid());

create policy user_trick_states_own_row on api.user_trick_states
  for all
  to authenticated
  using (user_id = auth.uid())
  with check (user_id = auth.uid());
```

## Step 3 — Order and rationale

1. `api.profiles` is created first because `api.user_trick_states` has no FK
   dependency on it (both only depend on `auth.users`), so there is no hard
   ordering requirement between the two tables themselves — but keeping
   profile-first mirrors the ticket title and the local domain's
   primary/secondary framing, and keeps the migration file readable
   top-to-bottom.
2. Table + column + CHECK-constraint definitions come before `enable row
   level security` and the policies, because `alter table ... enable row
   level security` and `create policy` both require the target table (and,
   for the policy body, `auth.uid()`) to already exist; there is no earlier
   point they could run.
3. RLS is enabled and both a `USING` and a `WITH CHECK` clause are added on
   the *same* `for all` policy (rather than only `WITH CHECK` on insert)
   specifically because the exit criteria requires proving both "cannot
   assign another `user_id`" (insert) and implicitly "cannot repoint an
   existing row" (update) — a `WITH CHECK`-only policy on `for all` still
   lets an owner flip `user_id` to someone else's id as long as the *old*
   row passed a permissive `USING`; the `USING (user_id = auth.uid())` clause
   here additionally makes sure the *pre-image* row targeted by the UPDATE is
   the caller's own, and the `WITH CHECK` makes sure the *post-image* still
   is.

## Step 5 — What this ticket deliberately does not do

- No server-owned-timestamp/revision *triggers* (T155.5): `created_at`/
  `updated_at`/`revision` have plain `default` expressions here so inserts
  work, but nothing yet stops a client from supplying its own `updated_at` or
  `revision` on insert/update, or from leaving `revision` unincremented after
  a real edit. T155.5 adds the `private`-schema `SECURITY DEFINER` trigger
  functions (with audited `search_path`) that make these truly server-owned;
  do not attempt that here.
- No centralized/shared JSON-invariant helper (T155.6): the
  `profiles_last_sesh_shape` CHECK constraint above is real and tested, but
  it is written inline rather than as a reusable function, because T155.6 is
  where profile/goal/custom-trick/sequence-step JSON validation gets
  centralized across all four domains. Expect T155.6 to refactor this
  constraint into a shared helper, not to introduce JSON validation from
  scratch.
- No comprehensive per-table grant/RLS audit (T155.7): the
  `profiles_own_row`/`user_trick_states_own_row` policies and `grant ... to
  authenticated` above are real, tested, and already give correct owner-only
  CRUD isolation for exactly these two tables — but T155.7 is the ticket
  that reviews grants across all six tables together (e.g. it makes
  `practice_sessions` select/insert-only once T155.3 exists) and tests
  grants and RLS independently of each other. Do not skip writing working
  RLS now on the theory that T155.7 will "really" do it — this ticket's own
  exit criteria requires the ownership proof today, and T155.7 audits/
  extends this rather than creating it.
- No `anon` access anywhere (consistent with T155.1's stated threat model:
  no publicly readable application resource is planned).

## Open items for the implementer to note, not resolve here

- `is_selected`/`is_manually_unlocked` both `false` is rejected by
  `user_trick_states_has_state`. If a future rollout wants to represent
  "seen but neither selected nor laced," that needs a new column/flag, not a
  relaxation of this constraint — flag it back to the user rather than
  quietly loosening it.
- `revision` exists on both tables now but is inert until T155.5. Do not
  treat its presence as evidence optimistic-concurrency checks already work.
