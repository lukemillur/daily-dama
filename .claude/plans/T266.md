# T266 — Fix spurious lace logged when skipping the Sesh "get ready" countdown

## What's actually going on (confirmed by static analysis; runtime confirmation still required — see Step 0)

`Countdown` and `ActiveSesh` are two structurally distinct components (`src/features/sesh/components/sesh.tsx`), swapped by `state.status` in both `Sesh` (`sesh.tsx`) and `MultiTrickSesh` (`multi-trick-sesh.tsx`). Both host components share the same `seshReducer` (`src/features/sesh/model/sesh.ts`).

Key facts gathered from the code, not just the ticket text:

- `Sesh`'s own `'countdown'` branch (sesh.tsx ~L238-247) does **not** wire `onSkipCountdown` at all — there is no manual "Skip" button in the single-trick flow. The only place a user-facing "Skip countdown" control exists is `MultiTrickSesh` (multi-trick-sesh.tsx ~L352-374), and only when `origin === undefined` (i.e. the ad hoc "Practice several tricks" flow, not the Kentei assessment flow, which sets `origin: 'assessment'`).
- Because of that, "skipping the countdown" for single-trick Sesh can only mean the *natural* 3-2-1 auto-complete transition (`Countdown`'s internal `useEffect`/`setTimeout` firing `onComplete`), not a manual Skip tap. The bug is therefore best understood as being about the **countdown→active transition frame itself** (whatever triggers it — manual Skip or natural expiry), not specifically the Skip button. This matches the ticket's own framing ("Skip and Laced render in the same screen position across the countdown→active transition frame").
- `seshReducer`'s `trickLaced` case already contains a temporal sanity check that discards landings claimed to have happened before the trick started or after a timed deadline:
  ```ts
  case 'trickLaced': {
    if (state.status !== 'active' || state.pausedAt !== undefined) return state;
    if (
      action.now < state.startedAt ||
      (state.plan.kind === 'timed' &&
        action.now >= state.startedAt + state.plan.durationMs + state.pausedDurationMs)
    ) {
      return state;
    }
    ...
  }
  ```
  It does **not** guard against a lace landing *immediately at or just after* `startedAt` — exactly what "spurious lace at 00:00" describes. `action.now` from a bled-through tap would be `>= state.startedAt`, so this existing guard silently lets it through today.
- Existing coverage in `multi-trick-sesh.test.tsx` ("MultiTrickSesh countdown Skip (T075)") already presses "Skip countdown" via `pressByAccessibilityLabel`, which calls `match.props.onPress()` directly — this bypasses real browser event timing entirely (no pointer capture, no click retargeting), so it cannot exercise whatever real click/tap race QA observed. That's why this suite is green today despite the bug: the existing tests never simulate the second, bleed-through tap at all — they only exercise the deliberate Skip tap in isolation. The exit criteria's "reproduces skipping the countdown ... and asserts zero trickLaced dispatches" only becomes a meaningful regression test if the new test *also* simulates the stray/immediate press on Laced that a real device would deliver, immediately after the skip completes.

## Step 0 — Confirm the mechanism before implementing (required by the ticket, don't skip)

1. Run the web dev server (`yarn expo start --web`, per AGENTS.md guidance — do not serve the static export). Start an ad hoc multi-trick Sesh (`/app/sesh/multi-trick`) with 2+ tricks, open-ended plan.
2. On trick 1's countdown, tap "Skip countdown" once, deliberately, and watch the resulting Active screen's lace count. Then let trick 1 finish/advance to trick 2 (or use "Next trick"), and on trick 2's countdown, tap "Skip countdown" once again the same way you would naturally continue tapping (i.e. don't lift and reposition your cursor/finger — tap where your hand rests right after the first tap completes). Confirm whether the resulting Active screen for trick 2 shows a lace count of 1 (spurious) before you've touched Laced.
3. If reproducible: use browser devtools (Elements panel, or a temporary `console.log(Date.now(), action)` in `seshReducer`) to confirm two facts: (a) whether it's actually two separate pointer/click events reaching the app (a real second physical tap that happens to land where the new button now is — the QA "same position" theory), or a single input event somehow producing two dispatches (an app-level double-dispatch bug); (b) the actual time delta between the `countdownCompleted` dispatch and the spurious `trickLaced` dispatch, to calibrate the grace window in Step 2 below realistically instead of guessing.
4. If it's a single input event producing two dispatches (not a real second tap), stop and re-scope: that's a distinct, more serious bug (e.g. a stale closure or effect double-firing) and the fix in this plan (a temporal reducer guard) is the wrong tool — a dispatch-dedupe fix is needed instead, and this plan's Step 2 will need to be replaced with a direct fix at the actual double-dispatch site. Note in the PR whichever branch you took.
5. Assuming the "two real inputs, same screen position" mechanism is confirmed (the expected outcome, given the code above): proceed to Step 2. Record the observed delta from 3(b) in the PR description since it directly informs the constant chosen below.

## Step 1 — Reducer-level fix (contingent on Step 0 confirming the same-position/stray-tap mechanism)

In `src/features/sesh/model/sesh.ts`:

- Add a small named constant near the existing `MIN_TIMED_SESH_MINUTES` etc. constants, e.g. `LACE_INPUT_LOCKOUT_MS`, sized conservatively based on the real delta measured in Step 0 (a few hundred ms is the right order of magnitude — long enough to swallow a same-position continuation tap, short enough that no real kendama trick could plausibly land faster than that from a cold `startedAt`). Document the reasoning in a comment: this is a UX/product judgment call about the fastest physically plausible first lace, not a hard architectural constant — flag it for the user's (owner's) sign-off if you land on anything above ~500ms, since a larger value risks discarding a genuinely fast player's real first lace.
- Extend the `trickLaced` case's existing temporal-sanity block to also discard a lace whose `action.now` falls within `LACE_INPUT_LOCKOUT_MS` of `state.startedAt`:
  ```ts
  if (
    action.now < state.startedAt + LACE_INPUT_LOCKOUT_MS ||
    (state.plan.kind === 'timed' && ...)
  ) {
    return state;
  }
  ```
  This keeps the reducer as sole authority and keeps timestamps flowing through actions (`action.now`, `state.startedAt`) rather than introducing any ambient UI timer/state — consistent with AGENTS.md's Sesh invariants. It applies uniformly to every countdown→active transition (manual Skip or natural 3-2-1 expiry, first trick or a later one in a multi-trick run), which is the right scope: the vulnerability is the transition itself, not the Skip control specifically.
  - Double check this doesn't change the meaning of `action.now < state.startedAt` for cases where `action.now` is already far in the past (e.g. a stale action) — it doesn't; the new bound is strictly larger, so it subsumes the old check.

This is the only production code change anticipated. If Step 0 revealed a genuine double-dispatch instead, replace this step with a fix at the actual duplicate-dispatch call site (likely in `MultiTrickSesh`'s `onSkipCountdown`/`seedNextTrick` wiring or `Countdown`'s internal effect) and skip the reducer change.

## Step 2 — Tests (exit criteria)

Order: reducer/model test first (fastest feedback, characterizes the guard in isolation), then the two component suites.

1. `src/features/sesh/model/sesh.test.ts` — extend the `'sesh reducer'` describe block:
   - A `trickLaced` dispatched with `now` at or just after `state.startedAt` (within the new lockout window) is discarded — reuse the existing `startSesh(plan, startedAt)` helper, dispatch `trickLaced` at `startedAt` and at `startedAt + (LACE_INPUT_LOCKOUT_MS - 1)`, assert the returned state is unchanged (`toBe(active)`, matching the existing `'ignores a lace at or after a timed sesh deadline'` test's style).
   - A `trickLaced` dispatched at `startedAt + LACE_INPUT_LOCKOUT_MS` (or comfortably past it) is still recorded normally — a boundary-clearing positive test, so the guard can't be accidentally widened later without a visible failure.
   - Confirm `LACE_INPUT_LOCKOUT_MS` is exported (or import it from wherever it's defined) so the test doesn't hardcode a magic number that could silently drift out of sync with the implementation.

2. `src/features/sesh/components/sesh.test.tsx` — new `describe` block for the single-trick flow:
   - Mount `Sesh` (or `ActiveSesh`/`Countdown` directly, matching this file's existing harness patterns), advance through the natural 3-2-1 countdown with `jest.advanceTimersByTime` (existing idiom throughout this file), then — in the same `act()` as the final tick that flips to `'active'`, or immediately after — invoke the Laced button's `onPress` before advancing any further timers. Assert zero recorded landings / no `trickLaced`-driven UI change (e.g. lace count still 0, no history entry recorded to `PracticeHistoryProvider`).
   - Then advance timers past the lockout window and press Laced again (a genuine, later tap): assert it now records normally. This is the "explicit tap on Laced" half of the exit criteria.

3. `src/features/sesh/components/multi-trick-sesh.test.tsx` — extend the existing `'MultiTrickSesh countdown Skip (T075)'` describe block with two new cases mirroring its existing two ("skips the first casual countdown..." / "skips a later casual countdown..."):
   - First trick: press "Skip countdown", then immediately (same `act()`, before any timer advance) press "Laced" — assert `session-count:0`/no landing recorded until a subsequent, clearly separated press.
   - After advancing to the second trick (reuse the existing "Next trick" advance pattern already in this file): press "Skip countdown" on trick 2, then immediately press "Laced" — assert the *second* trick's landing count stays 0 (use the existing `session-{index}-lace-count` labels to distinguish trick 1's recorded history from trick 2's in-progress state). This is the literal "after advancing from a prior one" / "mid-Sesh" case the ticket calls out.
   - Keep the existing two T075 cases as-is; they still validate the deliberate-Skip-only path (no immediate second press) continues to work exactly as before.
