# T047 - Allow backing out of the pre-sesh countdown

## Scope for this iteration

Required (exit criteria floor): single-trick Sesh choosing -> countdown
transition (src/app/sesh/index.tsx via Sesh in
src/features/sesh/components/sesh.tsx) gets a visible Cancel control on the
countdown screen that returns to the trick/setup picker without recording a
session.

Also in scope, per the task Notes explicit "if picked up together" allowance
(low incremental cost since it reuses the same Countdown component and the
same unconditional seshReset semantics): the first trick countdown in both
ad hoc multi-trick entry (src/features/sesh/components/multi-trick-sesh-entry.tsx)
and Kentei assessment entry (src/features/sesh/components/assessment-entry.tsx),
both of which render their first trick through the shared
src/features/sesh/components/multi-trick-sesh.tsx. Explicitly NOT in scope:
any countdown between tricks mid-sequence (a different UX moment per the
task Notes, not requested here).

Do not touch the reducer (src/features/sesh/model/sesh.ts) - seshReset
already matches from any status. This is UI-only wiring.

## Files and order

### 1. src/features/sesh/components/sesh.tsx - Countdown component

Add an optional onCancel?: () => void prop next to the existing
onSkipRank?: () => void prop (around line 409-421). Render a Cancel control
when provided, using the existing Button import (already imported near the
top of this file) rather than inventing new styling:

    {onCancel ? (
      <CancelButton variant="secondary" size="medium" onPress={onCancel}>
        Cancel
      </CancelButton>
    ) : null}

Place it above the existing onSkipRank block (around line 456-460) so that
when both are present (assessment first countdown on a multi-rank flow has
both onCancel and onSkipRank), Cancel reads as the primary "back out
entirely" action and "Skip this rank" stays the secondary, lower-emphasis
text link below it. They must stay visually distinct since they are
different actions: Skip moves forward past a rank, Cancel aborts the run
entirely. Add a CancelButton styled-component near the other styled
declarations at the bottom of the file (near SkipRankButton, around line
1088), for example styled(Button) with margin-top: 14px. Reuse the Button
component secondary variant bordered look so it reads as a real, visible
control per the exit criteria, unlike SkipRankButton, which is deliberately
a lower-emphasis underlined text link for a forward-moving action.

Use a plain accessibility-friendly label such as "Cancel" (or "Cancel
sesh" if a more explicit label is preferred - either is fine, just stay
consistent with what the tests assert).

### 2. src/features/sesh/components/sesh.tsx - Sesh component wiring

In the countdown-status render branch (around line 155-163), pass
onCancel={() => dispatch({ type: "seshReset" })}. Confirm this returns the
reducer state to the choosing status (check the seshReset case in
src/features/sesh/model/sesh.ts if needed), which re-renders TrickPicker -
the trick/setup selection screen. No practice-history write occurs since
recordCompletedSesh only fires from the completed-status effect, which is
never reached on this path.

This alone satisfies the required floor of the exit criteria. Verify it in
isolation before moving to the multi-trick pieces below.

### 3. src/features/sesh/components/multi-trick-sesh.tsx - first-countdown-only cancel

Add an optional onCancelRun?: () => void prop to MultiTrickSeshProps, with a
doc comment matching the style of the other props in this file - note
explicitly that it only fires from the very first trick countdown of the
run, mirroring the existing skipCountdownBetweenTricks doc comment
precedent for "only affects transitions between tricks, not the first
trick" framing.

This component seeds its reducer directly into the countdown status at
mount (there is no separate choosing status of its own here - see the
useReducer lazy initializer, around line 122-129), so "first countdown"
must be tracked explicitly, not derived from state.status. Add:

    const [isFirstCountdown, setIsFirstCountdown] = useState(true);

Set it to false the moment the run progresses past the first trick
countdown by any path - normal completion or skip - so the Cancel control
never reappears later in the run:

- In the countdown-status render branch, wrap the existing onComplete
  callback: onComplete={() => { setIsFirstCountdown(false);
  dispatch({ type: "countdownCompleted", now: Date.now() }); }}.
- At the top of handleSkipRank, add setIsFirstCountdown(false); before the
  existing skip logic - covers the case where the first action on the
  first trick countdown is "Skip this rank" rather than waiting it out or
  cancelling.

Then in the countdown-status render branch, pass
onCancel={isFirstCountdown ? onCancelRun : undefined} to Countdown.
onCancelRun defaulting to undefined means no Cancel control renders at
all, so this is opt-in per caller and backward-compatible with any other
MultiTrickSesh usage not updated in step 4.

Note: setIsFirstCountdown(false) inside onComplete fires on every completed
countdown dispatch, but the guard on read (isFirstCountdown ? ... :
undefined) makes that harmless - just confirm nothing later resets it back
to true (nothing should).

### 4. Wire the two MultiTrickSesh callers

- src/features/sesh/components/multi-trick-sesh-entry.tsx: pass
  onCancelRun={handleFinished} to the MultiTrickSesh call in the running
  branch. handleFinished already resets step back to choosingTricks and
  clears selectedTrickIds / advanceOnFirstLace / perTrickDurationMinutes -
  reusing it for cancel is intentional (no session was recorded yet, so
  wiping the transient run config back to a clean picker is reasonable and
  avoids a near-duplicate reset function). Preserving the trick selection
  on cancel instead is a reasonable alternative product call too - note the
  deviation if taken; it is not required by the exit criteria.
- src/features/sesh/components/assessment-entry.tsx: pass
  onCancelRun={() => setStep({ kind: "choosingFlow" })} to the
  MultiTrickSesh call in the running branch - returns to the top-level flow
  picker, matching the task Notes wording about "returning to that flow
  setup/flow-picker step" (not choosingRank, which is a narrower
  intermediate step only reachable for the "Start from a rank" flow).

## Risks / non-obvious things

- The biggest correctness risk is isFirstCountdown in multi-trick-sesh.tsx
  leaking Cancel into later countdowns. Get the regression test in step 4
  above right - it is the one place a state-tracking bug would silently
  violate the explicit scope boundary from the task Notes.
- Countdown is also used with onSkipRank in the active-status render branch
  of both sesh.tsx (around line 483-505, the ActiveSesh onSkipRank) and
  multi-trick-sesh.tsx - do not confuse the ActiveSesh skip control with
  the Countdown one; only Countdown gets onCancel here. ActiveSesh (mid-
  trick, already counting/practicing) is out of scope - cancelling an
  active sesh is a different, unrequested action.
- Keep all Date.now() calls in the existing dispatch call sites, not in any
  new code - this task adds no new timer logic, only a new dispatch of the
  already-existing seshReset action (and, for onCancelRun, pure local-state
  resets in the two entry components, no reducer involvement at all).
