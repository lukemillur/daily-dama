# T155.5 — Protect server-owned timestamps, revisions, and ownership

Status: planned and locally verified end-to-end (migration applies cleanly
from a full `supabase db reset`; all pgTAP suites, including a new one for
this ticket, pass: 140/140 assertions across `t155_2`, `t155_3`, `t155_4`,
`t155_5`). This plan contains the exact SQL already authored and exercised
against local Supabase (CLI `2.115.0`, Docker running) so the implementer can
apply it directly rather than re-deriving it.

## Scope confirmation

This is audit/hardening only, over the tables and triggers T155.2 (profiles,
user_trick_states), T155.3 (custom_tricks, practice_sessions), and T155.4
(goals, notes) already created. No new tables. Does not touch T155.1's
api/private schema boundary.

## Inventory of gaps found (read every migration under `supabase/migrations/`
before starting — this is the full list, nothing else was found)

1. **Trigger-level ownership enforcement.**
   - `api.profiles`, `api.user_trick_states`, `api.custom_tricks`: only had
     column *defaults* (`revision default 1`, `created_at/updated_at default
     now()`). No trigger. A client INSERT could set `revision`/`created_at`/
     `updated_at` (and, for `user_trick_states`/`custom_tricks`, the identity
     columns `id`/`trick_id`/`kind`) to anything, since only RLS restricted
     *which rows* were reachable, never *which values* were acceptable inside
     a reachable row's write.
   - `api.custom_tricks` additionally needed `kind` pinned on UPDATE: nothing
     in the local domain (`src/features/custom-tricks/model/custom-trick.ts`)
     converts a live row between `standalone`/`sequence` — `customTrickUpdated`
     replaces the whole document, so without a pin a forged UPDATE could
     silently convert a row's kind in place.
   - `api.user_trick_states` needed `trick_id` pinned on UPDATE: `trick_id` is
     half of this row's identity (`user_trick_states_unique_per_user`); an
     unpinned UPDATE could retarget an existing selection/unlock row onto a
     different trick instead of requiring a fresh INSERT.
   - `api.goals`/`api.notes` (T155.4) already had a correct, working shared
     trigger (`private.enforce_goal_note_mutation_invariants`) — no gap here
     beyond its `search_path` (below).
   - `api.practice_sessions`: `created_at` (the row's "receipt" timestamp —
     when the server recorded the historical fact, distinct from the
     legitimately client-supplied `started_at`/`completed_at`) had a default
     but no trigger; a forged INSERT payload could set it to anything.

2. **`search_path`.** Zero functions in the project set an explicit
   `search_path` (`private.enforce_custom_trick_step_invariants` from T155.3,
   `private.enforce_goal_note_mutation_invariants` from T155.4). Fix: add
   `search_path = ''`. This is safe with **no other code changes** to either
   function body: Postgres always implicitly searches `pg_catalog` first when
   it is not otherwise named in the path, so every existing unqualified
   builtin call (`now()`, `jsonb_typeof()`, `jsonb_array_elements()`,
   `jsonb_build_object()`, `btrim()`, `length()`) keeps resolving correctly;
   only `api.*`/`private.*` table references need to stay schema-qualified,
   and they already are in both functions. Verified by re-running both
   functions' existing pgTAP coverage after applying `ALTER FUNCTION ... SET
   search_path = '';` — no behavior change, no rewrite needed.

3. **`SECURITY DEFINER` audit.** Zero functions in `api`/`private` are
   `SECURITY DEFINER` today (all are the default `SECURITY INVOKER`, correct,
   since none needs privileges beyond what the invoking role's own
   RLS-scoped statement already reached). The exit criterion "every
   `SECURITY DEFINER` function has an audited fixed `search_path`" holds
   vacuously. Add a pgTAP assertion pinning this fact (count of
   `prosecdef = true` in `api`/`private` is 0) so a future `SECURITY DEFINER`
   addition is a deliberate, reviewed change, not a silent gap.

4. **Column-level grants.** Every mutating table's INSERT/UPDATE grant was
   whole-table (from T155.2–T155.4), so RLS's row-scoping was the *only*
   thing stopping a forged column value from being written verbatim before
   the trigger got a chance to override it — the trigger already prevented
   the forged value from being *stored*, but a client sending it got no
   signal it was rejected (silent overwrite, not an error). Postgres cannot
   revoke a privilege at column level while an equivalent table-level grant
   stands (table-level grant implies it on every column), so each table's
   whole-table INSERT/UPDATE grant must be revoked and re-granted
   column-by-column, naming only the columns a legitimate request needs:
   - `api.profiles`: mutable = `has_completed_onboarding`, `kentei_rank`,
     `last_sesh`, `streak_threshold_ms`, `theme_background_color`,
     `theme_accent_color`, `theme_text_color`. `user_id`/`revision`/
     `created_at`/`updated_at` are never UPDATE-grantable; `user_id` plus the
     mutable list are INSERT-grantable.
   - `api.user_trick_states`: mutable = `is_selected`, `is_manually_unlocked`.
     `id`/`revision`/`created_at`/`updated_at` are never INSERT-grantable
     (force the server default/trigger); `user_id`/`trick_id` are
     INSERT-only identity, never UPDATE-grantable.
   - `api.custom_tricks`: mutable = `name`, `kentei_rank`, `steps`.
     `user_id`/`id`/`kind` are INSERT-only identity, never UPDATE-grantable;
     `revision`/`created_at`/`updated_at` are never INSERT-grantable.
   - `api.practice_sessions`: `created_at` is never INSERT-grantable; every
     other column (`user_id`, `id`, `trick_id`, `trick_name`, `started_at`,
     `completed_at`, `duration_ms`, `lace_count`, `planned_duration_ms`,
     `origin`) stays INSERT-grantable as legitimate client-supplied
     historical fact. No UPDATE grant exists at all (unchanged from T155.3).
   - `api.goals`: UPDATE-grantable = `deleted_at` **only** — the local
     reducer only adds/deletes goals today (T155.4's own comment: T157.7
     wires up in-place target editing later). `target_count`/`target_ms`
     are therefore INSERT-only, not yet UPDATE-grantable; when T157.7 lands,
     extend the UPDATE grant to include them. `revision`/`created_at`/
     `updated_at`/`id`/`user_id` are never INSERT- or UPDATE-grantable.
   - `api.notes`: UPDATE-grantable = `body`, `deleted_at` (body editing is
     already exercised locally via `validateNoteEdit`/`noteUpdated`). Same
     server-owned exclusions as goals.

## Ordered implementation steps

1. **New migration file**
   `supabase/migrations/20260822210000_protect_server_owned_timestamps_and_ownership.sql`
   (timestamp must sort after `20260822201500_add_goals_and_notes.sql`; bump
   if the real implementation date differs). Full verified contents:

   ```sql
   -- Protect server-owned timestamps, revisions, and ownership (T155.5). This
   -- is an audit/hardening pass over every table T155.2-T155.4 already created;
   -- it adds no new tables. It closes two kinds of gap those tickets explicitly
   -- deferred to this one:
   --
   --   1. api.profiles, api.user_trick_states, and api.custom_tricks had column
   --      defaults (revision/created_at/updated_at) but no trigger forcing
   --      them on every write, unlike api.goals/api.notes (T155.4), which
   --      already got a real ownership-enforcing trigger because their tombstone
   --      exit criteria required one immediately. A client INSERT or UPDATE
   --      against those three tables could set revision/created_at/updated_at
   --      (and, for user_trick_states/custom_tricks, id/kind/trick_id identity
   --      columns) to any value it chose, because only RLS scoped *which rows*
   --      were reachable, never *which column values* were acceptable within a
   --      reachable row. api.practice_sessions had the same gap for its single
   --      receipt timestamp, created_at (its historical-fact columns --
   --      started_at/completed_at/duration_ms/lace_count -- are deliberately
   --      client-supplied and already validated by CHECK constraints; only
   --      created_at, "when the server recorded this row," is server-owned).
   --
   --   2. No function in this schema set an explicit `search_path`, which is
   --      Postgres/Supabase best practice for every function regardless of
   --      SECURITY DEFINER/INVOKER, to prevent a hijacked search path from
   --      resolving an unqualified identifier to an attacker-controlled object.
   --      `search_path = ''` is used rather than `pg_catalog, pg_temp` because
   --      pg_catalog is *always* implicitly searched first when the session's
   --      path does not otherwise mention it (see the Postgres docs on the
   --      search path), so every existing unqualified builtin call in these
   --      functions (now(), jsonb_typeof(), btrim(), etc.) keeps resolving to
   --      the real pg_catalog builtin with no call site rewrite required; only
   --      references to `api`/`private` objects need to stay schema-qualified,
   --      and they already are.
   --
   -- No function in this project is declared SECURITY DEFINER (every function
   -- below stays SECURITY INVOKER, the default): each one only ever inspects or
   -- rewrites NEW/OLD of the row the invoking role's own RLS-scoped statement
   -- already reached, so none needs the owning role's elevated privileges. The
   -- "every SECURITY DEFINER function has an audited fixed search_path" exit
   -- criterion therefore holds vacuously today; if a future ticket introduces
   -- one, it must set search_path following this migration's precedent.

   -- 1. Fix search_path on the two functions T155.3/T155.4 already created.
   --    ALTER FUNCTION ... SET is sufficient (a session-level GUC override
   --    baked into the function's pg_proc.proconfig); it does not require
   --    recreating the function body.
   alter function private.enforce_custom_trick_step_invariants()
     set search_path = '';

   alter function private.enforce_goal_note_mutation_invariants()
     set search_path = '';

   -- 2. api.profiles: own revision/created_at/updated_at, and pin user_id, on
   --    every insert/update. Mirrors the shape of T155.4's shared trigger, but
   --    profiles has no id/tombstone columns, so it gets its own function
   --    rather than forcing an artificial shared shape onto a mismatched table.
   create function private.enforce_profile_mutation_invariants()
   returns trigger
   language plpgsql
   set search_path = ''
   as $$
   begin
     if TG_OP = 'INSERT' then
       new.revision := 1;
       new.created_at := now();
       new.updated_at := now();
       return new;
     end if;

     -- TG_OP = 'UPDATE'
     new.user_id := old.user_id;
     new.created_at := old.created_at;
     new.revision := old.revision + 1;
     new.updated_at := now();
     return new;
   end;
   $$;

   create trigger profiles_enforce_mutation_invariants
   before insert or update on api.profiles
   for each row execute function private.enforce_profile_mutation_invariants();

   -- 3. api.user_trick_states: own revision/created_at/updated_at/id on insert;
   --    pin user_id/id/trick_id (the row's identity) and own
   --    revision/updated_at on update. trick_id is pinned because it, together
   --    with user_id, is this row's whole reason for existing (the
   --    user_trick_states_unique_per_user constraint) -- letting an UPDATE
   --    repoint trick_id would let a client silently retarget an existing
   --    selection/unlock row onto a different trick's identity instead of
   --    inserting a new row for it.
   create function private.enforce_user_trick_state_mutation_invariants()
   returns trigger
   language plpgsql
   set search_path = ''
   as $$
   begin
     if TG_OP = 'INSERT' then
       new.id := gen_random_uuid();
       new.revision := 1;
       new.created_at := now();
       new.updated_at := now();
       return new;
     end if;

     -- TG_OP = 'UPDATE'
     new.id := old.id;
     new.user_id := old.user_id;
     new.trick_id := old.trick_id;
     new.created_at := old.created_at;
     new.revision := old.revision + 1;
     new.updated_at := now();
     return new;
   end;
   $$;

   create trigger user_trick_states_enforce_mutation_invariants
   before insert or update on api.user_trick_states
   for each row execute function private.enforce_user_trick_state_mutation_invariants();

   -- 4. api.custom_tricks: own revision/created_at/updated_at on insert; pin
   --    user_id/id/kind (own revision/updated_at) on update. `kind` is pinned
   --    because nothing in the local domain (createCustomTrick) or this
   --    migration's own step-invariant trigger supports converting a live row
   --    between standalone and sequence in place -- a client edit always
   --    replaces name/kentei_rank/steps within the same kind. This is a new
   --    trigger, separate from T155.3's
   --    private.enforce_custom_trick_step_invariants, which owns step-shape/
   --    nesting rules only; both fire BEFORE INSERT OR UPDATE and, since this
   --    one's name sorts before "custom_tricks_enforce_step_invariants"
   --    alphabetically, it runs first (though the two touch disjoint columns,
   --    so firing order is not actually load-bearing here).
   create function private.enforce_custom_trick_mutation_invariants()
   returns trigger
   language plpgsql
   set search_path = ''
   as $$
   begin
     if TG_OP = 'INSERT' then
       new.revision := 1;
       new.created_at := now();
       new.updated_at := now();
       return new;
     end if;

     -- TG_OP = 'UPDATE'
     new.user_id := old.user_id;
     new.id := old.id;
     new.kind := old.kind;
     new.created_at := old.created_at;
     new.revision := old.revision + 1;
     new.updated_at := now();
     return new;
   end;
   $$;

   create trigger custom_tricks_enforce_mutation_invariants
   before insert or update on api.custom_tricks
   for each row execute function private.enforce_custom_trick_mutation_invariants();

   -- 5. api.practice_sessions: own created_at (the row's "receipt" timestamp --
   --    when the server recorded this immutable history fact) on insert.
   --    started_at/completed_at/duration_ms/lace_count/planned_duration_ms
   --    remain client-supplied historical fact, per T155.3's own comments; nothing
   --    here touches them. No UPDATE trigger is needed: T155.3 already grants no
   --    UPDATE privilege on this table at all (see also the column-level
   --    tightening in section 6, which is pure defense-in-depth here).
   create function private.enforce_practice_session_receipt_timestamp()
   returns trigger
   language plpgsql
   set search_path = ''
   as $$
   begin
     new.created_at := now();
     return new;
   end;
   $$;

   create trigger practice_sessions_enforce_receipt_timestamp
   before insert on api.practice_sessions
   for each row execute function private.enforce_practice_session_receipt_timestamp();

   -- 6. Column-level grants: defense-in-depth beyond RLS and the triggers
   --    above. Today, every gap the triggers close is already unreachable
   --    end-to-end (a forged value is silently overwritten, never stored) --
   --    but a forged PATCH/POST that merely targets a server-owned column
   --    should itself be rejected outright (42501, insufficient_privilege)
   --    rather than silently rewritten, so a client can distinguish "my request
   --    was malformed" from "my request succeeded." Postgres has no way to
   --    revoke a privilege at the column level while the equivalent table-level
   --    grant still stands (the table-level grant is checked first and
   --    implies the privilege on every column) -- each block below revokes the
   --    whole-table INSERT/UPDATE grant T155.2-T155.4 made and re-grants it
   --    column-by-column, naming only the columns a legitimate client request
   --    ever needs to write. SELECT and DELETE (where granted) are unaffected;
   --    only INSERT/UPDATE are ever column-scoped here.

   -- api.profiles: mutable columns are exactly UserProfile's own editable
   -- fields; user_id/revision/created_at/updated_at are fully server-owned.
   revoke insert, update on api.profiles from authenticated;

   grant insert (
     user_id, has_completed_onboarding, kentei_rank, last_sesh,
     streak_threshold_ms, theme_background_color, theme_accent_color, theme_text_color
   ) on api.profiles to authenticated;

   grant update (
     has_completed_onboarding, kentei_rank, last_sesh,
     streak_threshold_ms, theme_background_color, theme_accent_color, theme_text_color
   ) on api.profiles to authenticated;

   -- api.user_trick_states: id/revision/created_at/updated_at are fully
   -- server-owned; user_id/trick_id are client-supplied identity at insert
   -- time only (immutable thereafter, per the trigger above) and so are never
   -- grantable for UPDATE.
   revoke insert, update on api.user_trick_states from authenticated;

   grant insert (
     user_id, trick_id, is_selected, is_manually_unlocked
   ) on api.user_trick_states to authenticated;

   grant update (
     is_selected, is_manually_unlocked
   ) on api.user_trick_states to authenticated;

   -- api.custom_tricks: user_id/id/kind are client-supplied identity at insert
   -- time only (immutable thereafter); revision/created_at/updated_at are
   -- fully server-owned.
   revoke insert, update on api.custom_tricks from authenticated;

   grant insert (
     user_id, id, kind, name, kentei_rank, steps
   ) on api.custom_tricks to authenticated;

   grant update (
     name, kentei_rank, steps
   ) on api.custom_tricks to authenticated;

   -- api.practice_sessions: created_at is fully server-owned; every other
   -- column is legitimate client-supplied historical fact at insert time (this
   -- table has no UPDATE grant at all, from T155.3, so there is no update
   -- column list to narrow).
   revoke insert on api.practice_sessions from authenticated;

   grant insert (
     user_id, id, trick_id, trick_name, started_at, completed_at,
     duration_ms, lace_count, planned_duration_ms, origin
   ) on api.practice_sessions to authenticated;

   -- api.goals: id/user_id/created_at/revision/updated_at are fully
   -- server-owned; trick_id/trick_name/kind/target_count/target_ms are
   -- client-supplied identity/content at insert time but not yet editable in
   -- place (the local reducer only adds/deletes goals today -- see T155.4's
   -- comment that T157.7 wires up in-place target editing). deleted_at is the
   -- one column genuinely meant to be UPDATE-granted: setting it is how a
   -- client requests a soft delete, even though
   -- private.enforce_goal_note_mutation_invariants always substitutes now()
   -- for whatever value is sent. When T157.7 adds goal-target editing, extend
   -- the UPDATE grant here to include target_count/target_ms.
   revoke insert, update on api.goals from authenticated;

   grant insert (
     user_id, id, trick_id, trick_name, kind, target_count, target_ms
   ) on api.goals to authenticated;

   grant update (
     deleted_at
   ) on api.goals to authenticated;

   -- api.notes: same reasoning as goals, except `body` is already genuinely
   -- editable today (validateNoteEdit / noteUpdated), so it is UPDATE-granted
   -- alongside deleted_at.
   revoke insert, update on api.notes from authenticated;

   grant insert (
     user_id, id, trick_id, trick_name, body, practice_session_id
   ) on api.notes to authenticated;

   grant update (
     body, deleted_at
   ) on api.notes to authenticated;
   ```

   -- === 7-12: trigger-level forced ownership on api.user_trick_states,
   -- including the identity columns (id, user_id, trick_id). ===
   select lives_ok(

        where user_id = '00000000-0000-0000-0000-00000000002a' and trick_id = 'lighthouse' $$,
     'updating a trick-state row with a forged trick_id/revision succeeds (both are ignored, the legitimate flag edit is applied)'

## Non-obvious things worth flagging to the implementer

- **Ordering matters within step 1's single migration file, but not much**:
  functions must exist before their triggers are created (already ordered
  correctly above), and the `ALTER FUNCTION` calls can run at any point
  relative to the new `CREATE FUNCTION`s since they target different,
  pre-existing functions.
- **The t155_4 test amendment is not optional** — it is a direct, expected
  consequence of tightening `api.goals`'s UPDATE grant to `deleted_at` only.
  Do not "fix" it by loosening the grant back to include `target_count`;
  that would defeat the point of this ticket. Extend the grant for real only
  when T157.7 actually wires up in-place goal-target editing.
- **`search_path = ''` needed no call-site rewrites** in either amended
  function, which is easy to over-engineer (e.g. by schema-qualifying every
  builtin as `pg_catalog.now()`) unnecessarily. Verified empirically: adding
  only the `ALTER FUNCTION ... SET search_path = '';` line and rerunning
  `t155_3`/`t155_4`'s existing pgTAP coverage produced zero new failures.
- **Column-level REVOKE/GRANT requires revoking the whole-table grant
  first.** Postgres has no operation that narrows an existing whole-table
  grant down to specific columns in place; each block in step 1 section 6
  does `revoke insert, update on <table> from authenticated;` before
  re-granting column lists — skipping the revoke silently leaves the
  original whole-table grant in force and every column-level grant below it
  a no-op (this was hand-verified: forgetting the revoke while testing left
  the `throws_ok`/42501 assertions in step 3 failing as `lives_ok` instead).
- **`api.user_trick_states.id` insert is now fully server-owned** (the new
  trigger overwrites it with `gen_random_uuid()` regardless, and the column
  grant additionally blocks a client from targeting it in the INSERT column
  list at all). This is slightly stricter than strictly required by the
  ticket (the column already had no semantic weight), but keeps this table's
  posture consistent with every other identity column elsewhere in this
  migration; flagging in case a future reviewer wonders why `id` isn't in
  `api.user_trick_states`'s INSERT grant list.
- **Local Supabase was already running** during this planning session
  (Docker + CLI `2.115.0`); the implementer should run `supabase start` once
  if it is not already up, then follow step 4 as written.
