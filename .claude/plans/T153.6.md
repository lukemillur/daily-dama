# T153.6 -- Build the recovery-session password reset route

## Context already confirmed

- `PASSWORD_RECOVERY` is a real, distinct `AuthChangeEvent` emitted by
  `@supabase/auth-js` (`node_modules/@supabase/auth-js/dist/module/lib/types.d.ts`),
  alongside `INITIAL_SESSION | SIGNED_IN | SIGNED_OUT | TOKEN_REFRESHED | USER_UPDATED`.
  This is the hook the task description points at.
- Supabase stable `ErrorCode` union (`node_modules/@supabase/auth-js/dist/module/lib/error-codes.d.ts`)
  includes `session_not_found` and `session_expired`, which are not yet in
  `EXPIRED_OR_INVALID_LINK_CODES` in `src/features/auth/model/auth-errors.ts`.
- No Auth route exists yet anywhere under `src/app`; this is the first one. `AuthProvider`
  is already mounted at the root (`src/app/_layout.tsx`), above `Slot`, so a route outside
  the `(app)` tree already has provider access with no extra wiring.
- `app.json` has `web.output: "static"` and `typedRoutes: true`. Do not reference a
  route href that does not exist yet in this commit (e.g. `/auth/forgot-password`,
  `/auth/callback`) -- those are T153.7/T153.10, and referencing them now breaks
  `yarn tsc --noEmit` against generated route types.
- Repo convention (`src/app/app/sesh/index.tsx`, `src/app/index.tsx`): the route file
  under `src/app/**` is a thin wrapper; the real component and its local styled
  primitives live under `src/features/<feature>/components/`.
- Form convention (`CustomTrickForm` in `src/app/app/tricks/index.tsx`): local
  `useState` draft plus a pure `validate*Draft` function in the model layer plus a
  `hasSubmitted` flag that gates when validation errors become visible plus a
  `FieldLabel`/`FieldInput`/`ErrorText`/`FormActions` set of local styled-components
  primitives. Reuse this shape rather than inventing a new one.
- No route in the repo currently calls `trackAuthEvent`, and `AuthProvider` actions
  never auto-log their own errors -- the caller decides. Follow that: this route does
  not need to log anything itself, since it never touches raw Supabase errors directly
  (everything is categorized first), so there is nothing un-redacted to log.

## Step 1 -- Extend the Auth state model (`src/features/auth/model/auth-state.ts`)

This must land first: everything else (route gating, provider action, tests) depends
on the state shape.

1. Add `passwordRecovery` to `AuthStatus` and add a new `AuthState` member:
   ```ts
   | { readonly status: 'passwordRecovery'; readonly session: Session }
   ```
   Keep it separate from `authenticated` -- the whole point is the route can gate on
   `status === 'passwordRecovery'` and nothing else accidentally satisfies that check.
2. Change `deriveAuthState` signature to accept the previous state, defaulted so
   every existing 2-arg call site and test keeps compiling and keeps its current
   result:
   ```ts
   export function deriveAuthState(
     event: AuthChangeEvent,
     session: Session | null,
     previous: AuthState = INITIALIZING_AUTH_STATE,
   ): AuthState {
     if (event === 'SIGNED_OUT') return { status: 'guest', reason: 'signedOut' };
     if (!session) return { status: 'guest', reason: 'signedOut' };
     if (event === 'PASSWORD_RECOVERY') return { status: 'passwordRecovery', session };
     if (previous.status === 'passwordRecovery') return { status: 'passwordRecovery', session };
     return { status: 'authenticated', session, lastEvent: event };
   }
   ```
   Rationale for the `previous.status === 'passwordRecovery'` carry-forward: Supabase
   fires `PASSWORD_RECOVERY` exactly once, at the moment the recovery link/session is
   established. `autoRefreshToken: true` is on (`supabase-client.ts`), so a long-lived
   visit to this route could see a later `TOKEN_REFRESHED` (same session) -- without
   carrying `passwordRecovery` forward across it, that refresh would silently and
   incorrectly promote the user to plain `authenticated` mid-flow, defeating the
   recovery-only gate. `SIGNED_OUT` and a null session both still unconditionally win
   over the carry-forward, so signing out (or an actually invalidated session) still
   exits recovery. A fresh mount (default `previous = initializing`) does NOT
   carry forward, so reloading the tab after `PASSWORD_RECOVERY` has already fired
   once (e.g. right after a successful reset) naturally drops back out of recovery --
   this is the mechanism that makes a page-reload replay of the reset form
   impossible without a fresh recovery link, on top of the local one-shot UI flag in
   Step 4.
3. Update `src/features/auth/model/__tests__/auth-state.test.ts`: add cases for
   `PASSWORD_RECOVERY` mapping to `passwordRecovery`, `TOKEN_REFRESHED` after a
   `passwordRecovery` previous state staying `passwordRecovery`, and `SIGNED_OUT`
   overriding a `passwordRecovery` previous state back to `guest`.

## Step 2 -- Extend `AuthProvider` (`src/features/auth/state/auth-provider.tsx`)

1. Update the `onAuthStateChange` callback to thread previous state through:
   ```ts
   setState((current) => deriveAuthState(event, session, current));
   ```
2. Add a new action, `completePasswordRecovery(newPassword: string)`, to
   `AuthActions` and the provider. It must reject at the provider layer (not just
   trust the route UI) when the current state is not `passwordRecovery` -- this is
   what makes "Route/provider tests prove... permit password submission only while
   the Auth provider holds a valid password-recovery session" a provider-level,
   independently testable guarantee rather than only a UI convention:
   ```ts
   const stateRef = useRef(state);
   useEffect(() => { stateRef.current = state; }, [state]);

   const completePasswordRecovery = useCallback(async (newPassword: string) => {
     if (stateRef.current.status !== 'passwordRecovery') {
       return { error: new AuthError('No active password recovery session.', 401, 'session_not_found') };
     }
     const client = getSupabaseClient();
     if (!client) return { error: new AuthError('Supabase is not configured.') };
     const { error } = await client.auth.updateUser({ password: newPassword });
     return { error };
   }, []);
   ```
   Add `completePasswordRecovery` to the `actions` `useMemo`.
3. Extend `src/features/auth/state/__tests__/auth-provider.test.tsx`:
   - emitting `PASSWORD_RECOVERY` with a session yields `{ status: 'passwordRecovery', session }`.
   - `completePasswordRecovery` when not in `passwordRecovery` status resolves
     `{ error }` with `code: 'session_not_found'` and never calls `client.auth.updateUser`.
   - `completePasswordRecovery` when in `passwordRecovery` status calls
     `client.auth.updateUser({ password })` with the given password and forwards
     its `{ error }` result (success and failure cases), without directly mutating
     state (state changes only via a subsequent real `onAuthStateChange` event, same
     pattern already used for `signInWithPassword`/`signOut` in this file).

## Step 4 -- Password policy model (`src/features/auth/model/password-policy.ts`, new file)

A small, pure, reusable module (T153.8 signup will want the same minimum-length
constant later):

```ts
export const MIN_PASSWORD_LENGTH = 10; // BACKEND_ROADMAP.md: ten-character minimum

export interface ResetPasswordFieldErrors {
  readonly password?: string;
  readonly confirmPassword?: string;
}

export type ResetPasswordValidation =
  | { readonly status: 'valid' }
  | { readonly status: 'invalid'; readonly errors: ResetPasswordFieldErrors };

export function validateNewPassword(password: string, confirmPassword: string): ResetPasswordValidation {
  const errors: { password?: string; confirmPassword?: string } = {};
  if (password.length < MIN_PASSWORD_LENGTH) {
    errors.password = `Use at least ${MIN_PASSWORD_LENGTH} characters.`;
  }
  if (password !== confirmPassword) {
    errors.confirmPassword = 'Passwords do not match.';
  }
  return Object.keys(errors).length > 0 ? { status: 'invalid', errors } : { status: 'valid' };
}
```

Add `src/features/auth/model/__tests__/password-policy.test.ts` covering: too short,
mismatch, both at once, and a valid pair.

## Step 5 -- Route component (`src/features/auth/components/reset-password-screen.tsx`, new file)

Follow the `CustomTrickForm` shape (local styled primitives: `FormScroll`,
`FormContent`, `Field`, `FieldLabel`, `FieldInput` (`TextInput` with
`secureTextEntry`), `ErrorText` in `AppColors.red`, `FormActions`, reusing
`Button`/`Screen`/`Eyebrow`/`DisplayTitle`/`BodyText` from `@/components/ui/*`).

State:
- `password`, `confirmPassword` (local `useState`).
- `hasSubmitted` (gates showing `validateNewPassword` field errors, same idiom as
  `CustomTrickForm`).
- `isSubmitting` (in-flight guard, also disables the submit button so a fast
  double-click cannot call the action twice).
- `completed` (one-shot local flag; once `true`, the form is not rendered again for
  this mount -- this plus the state-model reload behavior from Step 1.2 is what
  satisfies "exactly once" / "repeat submission").
- `submitCategory: AuthErrorCategory | undefined` for the last submission server-side
  failure, cleared on every new submit attempt.

Render branches, keyed off `useAuthState()`:
- `status === 'initializing'` -> loading copy (e.g. "Checking your recovery link...").
  No form, no back link needed yet -- this state should be brief and is not
  actionable.
- `status !== 'passwordRecovery'` (covers both "direct visit, never had a recovery
  session" and "session dropped out of recovery e.g. via sign-out or reload after
  completion") -> one shared "expired or invalid" view: explain the link is no longer
  valid and provide a way back (`useRouter().replace('/')` -- do NOT link to
  `/auth/forgot-password`, it does not exist until T153.10).
- `status === 'passwordRecovery' && completed` -> completion view: confirmation copy,
  no inputs, no submit button.
- `status === 'passwordRecovery' && !completed` -> the form.

Submit handler:
```ts
const handleSubmit = async () => {
  if (isSubmitting || completed) return; // repeat-submission guard
  setHasSubmitted(true);
  setSubmitCategory(undefined);
  const validation = validateNewPassword(password, confirmPassword);
  if (validation.status === 'invalid') return; // mismatch / weak-password UI
  setIsSubmitting(true);
  const { error } = await completePasswordRecovery(password);
  setIsSubmitting(false);
  if (error) {
    setSubmitCategory(categorizeAuthError(error));
    return; // offline / expiredOrInvalidLink / weakPassword / rateLimited / unknown
  }
  setCompleted(true);
};
```
Map `submitCategory` to copy with a small switch/lookup covering at least
`weakPassword`, `expiredOrInvalidLink`, `offline`, `rateLimited`, and a generic
fallback for anything else (`invalidCredentials`/`unverifiedEmail`/
`accountAlreadyExists` are unreachable here but the type is shared, so keep an
exhaustive default rather than per-category dead branches).

Accessibility: label both inputs (`accessibilityLabel="New password"` /
`"Confirm new password"`), and the submit button
(`accessibilityLabel="Set new password"`), matching existing conventions.

## Order and why

Step 1 (state model) before Step 2 (provider) before Steps 4-6 (route/UI): the route
gate and the provider action both depend on the new `passwordRecovery` status
existing first. Step 3 (error codes) is independent and can happen anytime before
Step 5 needs `expiredOrInvalidLink` to include session-expiry codes. Step 7 tests
last, after the component exists.

## Risks / non-obvious pitfalls

- Do not reference `/auth/forgot-password` or `/auth/callback` as hrefs anywhere in
  this commit -- those routes do not exist yet (T153.7/T153.10), and `typedRoutes: true`
  means an invalid href fails `yarn tsc --noEmit`, not just lint.
- Do not let `completePasswordRecovery` skip its own `stateRef` check "just because
  the route already gates it" -- the exit criteria frames this as an Auth-provider
  guarantee, and it is cheap, real defense-in-depth against any future call site.
- Keep `deriveAuthState` new third parameter defaulted -- every existing call site
  in `auth-provider.tsx` and every existing test passes only two arguments, and the
  default must reproduce today behavior exactly (verify by running the existing
  `auth-state.test.ts` cases unmodified before adding new ones).
- Do not add a second, competing minimum-password-length constant later in T153.8 --
  this task is the right place to introduce the shared one.
