# T315 plan: restore scrolling in Android onboarding trick selection

Status of inputs verified on this branch (2026-11-10): `OnboardingSelectionStep` renders `TrickDirectory` (a bare `SectionList`) directly inside `SelectionContent` (`flex:1; max-height:864px; align-self:center; overflow:hidden`). On native the Start-practicing footer is the SectionList `ListFooterComponent` (not pinned; pinning is web >=768px only). `home.tsx` wraps it in `Screen` with `edges={['top','left','right']}` (no bottom inset). Emulator emulator-5554 is up, `GLES:` names Apple M1 Max (Metal), and `com.dailydama.app` is already installed (owner data: never clear/uninstall). No `/android` dir exists yet (prebuild is generated and git-ignored). No blocker found.

## Principle
Reproduce first. Do not code a fix before the cause is observed. If it does not reproduce on the responsive pinned build, stop, record exact evidence (device/API/viewport/density/font scale/commit/GPU line) and report for owner reconciliation (per task Notes) rather than inventing a fix.

## Candidate causes to discriminate (rank order)
1. No bottom safe-area/system-bar inset: `Screen` omits `bottom` on Home and Android API 35+ is edge-to-edge, so the list's last rows / footer sit under the 3-button/gesture nav bar and the tab bar (check whether the tab bar overlays the scene on Android; see `src/components/app-tabs.tsx`). Symptom matches "Pull up spike" (last rank-1 row) and "Start practicing" unreachable even though gestures scroll.
2. Measured viewport wrong: `SelectionContent` `flex:1` + `max-height` + `align-self:center` inside `Screen` (`align-items: stretch`, `width:100%`) giving the SectionList a height equal to content (no scroll) or larger than the visible area (scroll range clipped by `overflow:hidden`). Compare `onLayout` of Screen / SelectionContent / SectionList / content size.
3. Gesture ownership: parent `overflow:hidden` + `border-radius`, nested `Pressable` rows (`SelectableIdentity`, whole-row `Pressable`) swallowing drags on Android, or `stickySectionHeadersEnabled` behaviour. Less likely.
Also check Profile and other ScrollViews are NOT broken (task says do not assume).
