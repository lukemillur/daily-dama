# T170 -- Make /auth/* follow the user's theme

## Context established during planning

- Root `src/app/_layout.tsx` wraps everything (both `/app/*` and `/auth/*`) in
  `DefaultAppThemeProvider` (`resolveTheme({})`, fixed palette, no user
  preferences -- this is the T145 landing-page fix's provider).
- `src/app/app/_layout.tsx` re-wraps the `/app/*` subtree in the real
  `AppThemeProvider`, which calls `useResolvedTheme()` -> `useUserProfile()`,
  requiring `UserProfileProvider` (and `IdentityProvider` above it) to already
  be mounted and hydrated.
- `src/app/auth/_layout.tsx` currently only mounts
  `PendingVerificationEmailProvider` around `<Slot />` -- no theme override, so
  `/auth/*` inherits the root's fixed `DefaultAppThemeProvider` value. This is
  the bug.
- `UserProfileProvider` (`src/features/profile/state/user-profile-provider.tsx`)
  renders a "Loading your practice..." fallback view while `hasHydrated` is
  false. `IdentityProvider` similarly blocks render while
  `authState.status === 'initializing'`. Mounting either of these under
  `/auth/*` to get a "real" theme would reintroduce exactly the
  hydration-gated first-paint problem T145 fixed (stated explicitly as
  forbidden in this task's Notes).
- T145 already solved this exact class of problem for the landing route (`/`)
  and for the splash overlay, via a synchronous pre-hydration cache read
  pattern, not a context/provider dependency:
  - `src/features/profile/persistence/read-cached-theme-background.ts` +
    `src/components/animated-icon.web.tsx` (splash overlay background).
  - `src/features/profile/persistence/read-cached-onboarding-status.ts` +
    `src/features/landing/state/use-cached-onboarding-status.ts` (landing CTA
    copy/redirect) -- this is the more complete, more recent precedent: single
    hook file, `Platform.OS === 'web'` branch reads `window.localStorage`
    synchronously (gated by a `useSyncExternalStore(emptySubscribe, () => true,
    () => false)` hydration-mismatch guard, matching `use-color-scheme.web.ts`),
    `Platform.OS !== 'web'` branch does one non-blocking `AsyncStorage.getItem`
    read that updates state once it resolves (no hydration gate on native
    either, just a delayed correct value -- native is deferred scope anyway).
  - T170 should reuse this exact pattern, not invent a new one.

- IMPORTANT divergence from the two existing precedents, found during
  planning -- do not copy this part of them: both
  `read-cached-theme-background.ts` and `read-cached-onboarding-status.ts`
  read the bare, unscoped `USER_PROFILE_STORAGE_KEY`
  (`daily-dama:user-profile`) directly. That was correct when T145 shipped,
  but T156.1/T156.2 (identity namespacing, shipped after T145) changed
  `UserProfileProvider` to persist through `createGuestMigratingStorage`,
  which writes every value to the identity-scoped physical key
  (`guest:daily-dama:user-profile` for a guest, via `physicalKey()` /
  `identityNamespace()` in `src/shared/persistence/scoped-storage.ts`) and
  only ever reads the bare legacy key as a one-time fallback when the scoped
  key is empty. In practice this means today's landing-page and splash
  pre-hydration reads are already stale for any post-T156.2 user -- they
  read a key that new writes never land in, and will silently show the
  default palette/onboarding status instead of the real cached one. This
  looks like an undiscovered gap introduced by T156.2 landing after T145, not
  an intentional tradeoff (no test or code comment anywhere accounts for
  scoping in either helper). It is out of scope to fix those two existing
  helpers here -- flag it back to the user as a worth-filing follow-up
  backlog item, don't fold the fix into this ticket. But T170's own new
  helper must not repeat this mistake, because the exit criteria requires an
  actual in-browser confirmation that a non-default theme shows up on
  sign-up -- copying the stale bare-key approach would fail that check for
  any current user. T170's helper must read the guest-scoped key first
  (`guest:daily-dama:user-profile`), falling back to the bare legacy key,
  mirroring `createGuestMigratingStorage`'s own read order (read-only mirror;
  it must not write anything back -- that stays `UserProfileProvider`'s job
  once it eventually mounts under `/app/*`).

- Scope decision: which identity to read. `/auth/*` renders outside
  `IdentityProvider` entirely (that only wraps `/app/*`), so there is no live
  identity resolution available there without reintroducing a hydration/auth
  gate. All four screens are reachable pre-authentication and three of them
  (sign-up, sign-in, forgot-password) are strictly guest-only flows --
  matching exactly the QA scenario in the exit criteria ("a user with a
  non-default theme sees it reflected on sign-up": onboarding happens as a
  guest, before ever signing up). The fourth, reset-password, is reached via
  a Supabase PASSWORD_RECOVERY session, which `deriveIdentityFromAuthState`
  (`src/features/auth/model/identity-from-auth-state.ts`) maps to a real
  `user:<uuid>` identity, not guest -- so reading the guest-scoped key for
  reset-password is a known, deliberate approximation: it renders that
  account's locally-cached-as-guest theme if this device happens to still
  have one (e.g. the same device that originally onboarded before signing
  up), and otherwise falls back to today's default palette -- i.e. never
  worse than today, just not personalized to the recovering account's synced
  theme when it isn't guest-cached on this device. This is an acceptable,
  explicitly documented scope boundary for a prototype; do not attempt to
  wire `IdentityProvider`/session-scoped reads into `/auth/*` to fully solve
  reset-password's case -- that would need `IdentityProvider`'s own
  `initializing` gate, directly reintroducing the forbidden hydration block.

## Implementation steps, in order

1. Add `readCachedGuestTheme` (persistence layer). New file
   `src/features/profile/persistence/read-cached-guest-theme.ts`, modeled on
   `read-cached-theme-background.ts` and `read-cached-onboarding-status.ts`:
   - Compute the guest physical key once at module scope:
     `physicalKey(GUEST_IDENTITY, USER_PROFILE_STORAGE_KEY)` using
     `physicalKey` from `@/shared/persistence/scoped-storage` and
     `GUEST_IDENTITY` from `@/shared/persistence/identity`.
   - `export function readCachedGuestTheme(getItem: (key: string) => string | null): ResolvedTheme`
     -- inside a single try/catch (mirroring the existing helpers' "any throw
     -> default theme" behavior): read the scoped key, fall back to the bare
     `USER_PROFILE_STORAGE_KEY` if the scoped read is null
     (`getItem(scopedKey) ?? getItem(USER_PROFILE_STORAGE_KEY)`), deserialize
     with `deserializeUserProfile`, and call `resolveTheme` from
     `@/features/profile/state/use-resolved-theme` with
     themeBackgroundColor/themeAccentColor/themeTextColor from the parsed
     profile (all fields, not just background -- theme.accent and theme.text
     are both actually consumed by the four screens, see step 6). Return
     `resolveTheme({})` for null/malformed/thrown cases.
   - Doc comment should explicitly note the divergence from
     `read-cached-theme-background.ts`/`read-cached-onboarding-status.ts`
     (identity-scoped key, with the "why" from the Context section above) so
     a future reader doesn't "fix" this file back into consistency with the
     stale ones.

2. Add `readCachedGuestTheme` tests. New file
   `src/features/profile/persistence/read-cached-guest-theme.test.ts`,
   directly mirroring `read-cached-theme-background.test.ts`'s structure
   (same `jest.mock('@react-native-async-storage/async-storage', ...)`
   hoisting comment/pattern, since this file also transitively imports
   `resolveTheme` from `use-resolved-theme.ts` -> `user-profile-provider.tsx`
   -> AsyncStorage). Cover: no cached value (default theme); a value under
   the scoped guest key (background and accent and text all reflected); a
   value only under the legacy bare key (fallback path); a value under the
   scoped key taking priority when both exist; malformed JSON; wrong document
   version; getItem throwing.

3. Add `useCachedGuestTheme` (state layer). New file
   `src/features/profile/state/use-cached-guest-theme.ts`, modeled directly
   on `use-cached-onboarding-status.ts` (single file, no `.web` split --
   this codebase's established idiom for this exact problem shape):
   - `Platform.OS === 'web'`: `useSyncExternalStore(emptySubscribe, () => true, () => false)`
     hydration gate; before that boundary return the fixed default
     (`resolveTheme({})`, computed once at module scope so identity is
     stable across renders); after it, call
     `readCachedGuestTheme((key) => window.localStorage.getItem(key))`.
   - `Platform.OS !== 'web'`: one non-blocking `AsyncStorage.getItem` read
     (of the same guest-scoped key, computed via `physicalKey`) in a
     `useEffect`, updating local state once it resolves, matching
     `use-cached-onboarding-status.ts`'s native branch -- no gate, no
     blocking; native is deferred/unverified scope so this is best-effort
     only.
   - Return type: `ResolvedTheme` (not just background).

4. Add a `CachedAppThemeProvider` alongside the existing theme providers.
   Edit `src/features/profile/components/app-theme-provider.tsx`: add a new
   exported component that calls `useCachedGuestTheme()` and renders
   `<StyledThemeProvider theme={theme}>{children}</StyledThemeProvider>`,
   same shape as the existing `AppThemeProvider`/`DefaultAppThemeProvider`
   pair in this file. Update `DefaultAppThemeProvider`'s doc comment: it
   currently says it's used "for routes -- currently just the landing
   route, /" -- after this change that's still literally true for routes
   that render outside any override (it's still the root-level ambient
   default, inherited pre-hydration by `/auth/*` too, just no longer the
   final value `/auth/*` settles on) but worth a one-line update noting
   `/auth/*` now overrides it via `CachedAppThemeProvider` rather than
   inheriting it directly.

5. Wire `CachedAppThemeProvider` into the `/auth/*` route group. Edit
   `src/app/auth/_layout.tsx` -- wrap the existing tree (the
   `PendingVerificationEmailProvider` around `<Slot />`) in
   `CachedAppThemeProvider`. This is the only routing-tree change needed. It
   nests inside the root's `DefaultAppThemeProvider` (still the
   SSR/pre-hydration value, so no flash -- same default on both) and shadows
   it for every screen in this route group. Do not touch
   `src/app/_layout.tsx` or `src/app/app/_layout.tsx`.

6. Screen-level tests, one file per screen -- add two new `it` blocks to
   each of:
   - `src/features/auth/components/__tests__/sign-up-screen.test.tsx`
   - `src/features/auth/components/__tests__/sign-in-screen.test.tsx`
   - `src/features/auth/components/__tests__/forgot-password-screen.test.tsx`
   - `src/features/auth/components/__tests__/reset-password-screen.test.tsx`

   Add the same `jest.mock('@react-native-async-storage/async-storage', ...)`
   hoisting line these files don't currently need (they don't today because
   the screens mount with no theme provider at all) -- required once tests
   import `CachedAppThemeProvider`. Add a
   `beforeEach(() => window.localStorage.clear())` for isolation. For each
   screen:
   - Default-theme test: mount `<CachedAppThemeProvider><XScreen /></CachedAppThemeProvider>`
     with `window.localStorage` empty; assert the rendered background color
     resolves to the default sage (`resolveTheme({}).background`) and the
     screen's primary submit button (found by its existing
     accessibilityLabel, reusing the `resolvedButtonRootStyle`-style helper
     from `button.test.tsx`/`sesh.test.tsx`) resolves theme.accent/
     theme.buttonBackground to their default values.
   - Persisted-theme test: seed `window.localStorage` at
     `physicalKey(GUEST_IDENTITY, USER_PROFILE_STORAGE_KEY)` with a
     serialized v1 profile document containing custom
     themeBackgroundColor/themeAccentColor values (import `physicalKey`/
     `GUEST_IDENTITY`/`USER_PROFILE_STORAGE_KEY` from their real modules
     rather than inlining the literal key string, so this can't silently
     drift from the real scoping scheme) before mounting; then mount the
     same way and assert the background/accent now reflect the custom
     colors.
   - Use each screen's existing default authState/router mocks already in
     the file (e.g. sign-up's `{ status: 'guest', reason: 'signedOut' }`) so
     the new tests render the actual form, not an "initializing"/
     "redirecting" placeholder branch.
   - Do not touch the screens' existing (unwrapped, no-ThemeProvider) tests
     -- they exercise a different, still-valid path (Screen's own
     `theme?.background ?? AppColors.sage` fallback when there's no
     ThemeContext at all) and must keep passing unmodified.

7. Order rationale. Persistence helper (1-2) before the hook (3) before the
   provider (4) before the route wiring (5) before screen tests (6) -- each
   step's tests can only be written meaningfully once the layer below it
   exists, and the route wiring is the one line that actually closes the
   loop the exit criteria checks in-browser.

## Verification

- Per AGENTS.md's "App UI/routes" tier: exact tests while iterating
  (`yarn eslint` on changed files, targeted jest runs via
  `node .claude/scripts/verify.mjs --test-file <path>` for each new/changed
  test file), then full `yarn tsc --noEmit` before completion.
- This is a provider/routing-boundary change per the task's own Required
  framing, and it touches a hydration-adjacent invariant (T145) -- escalate
  to the complete app sequence (`node .claude/scripts/verify.mjs`, all four
  steps) before opening the PR, not just the narrower tier, specifically
  because of the hydration-flash risk called out explicitly in this task's
  Notes.
- In-browser confirmation (exit criteria, cannot be automated): run the
  Expo dev server; as a fresh guest, complete onboarding and set a
  non-default theme (or seed localStorage directly at the
  `guest:daily-dama:user-profile` key via devtools); navigate to
  `/auth/sign-up` and confirm the background/accent match; hard-reload on
  `/auth/sign-up` directly (not just client-side nav) and confirm there is
  no visible flash of the default palette before the real one appears
  (matching T145's frame-by-frame verification style) and no
  hydration-mismatch console warning beyond the two known-benign ones.
- Also manually check `/auth/sign-in`, `/auth/forgot-password`,
  `/auth/reset-password` in-browser even though only sign-up is explicitly
  named in the exit criteria's in-browser check, since all four are the
  ticket's stated scope.

## Risks / things to double check while implementing

- Confirm `@react-native-async-storage/async-storage`'s web implementation
  really does back onto window.localStorage with unprefixed keys (this is
  an existing assumption already relied on by animated-icon.web.tsx and
  use-cached-onboarding-status.ts, not a new one introduced here, but worth
  a quick sanity check with the dev server + devtools during in-browser
  verification since it's load-bearing for correctness).
- Double check resolveTheme's import chain doesn't get accidentally lighter
  or heavier under React Compiler/babel-jest in a way that breaks the "mock
  AsyncStorage before importing" ordering used throughout this file set (see
  the existing comment in read-cached-theme-background.test.ts for why
  hoisting order matters).
- The bare-legacy-key staleness found in read-cached-theme-background.ts/
  read-cached-onboarding-status.ts (see Context above) is worth surfacing to
  the user as a candidate follow-up backlog item -- not something to fix as
  part of T170, but flag it rather than silently leaving it undiscovered.
