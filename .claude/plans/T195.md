# T195 — Make the branded confirmation email reach real signups

## Root cause (confirmed, not hypothesized)

- `supabase/config.toml` already points `[auth.email.template.confirmation]` at
  `./supabase/templates/confirmation.html` — this drives the **local** CLI/Mailpit
  stack only (per `supabase/README.md:281`), which is why T192 verified correctly
  against Mailpit but real signups didn't change.
- The **hosted** project (`Daily Dama Dev`, ref `ylyoqswauqyesuwmetnl`, the one
  `EXPO_PUBLIC_SUPABASE_URL` actually points at, confirmed live and healthy) has
  its own independent Auth config reachable only via the Management API or
  dashboard — `supabase/RESEND_DNS_AUTH.md`'s "Delivery record" section documents
  that T153.3 (2026-08-24) already pushed the confirmation/recovery template
  *content that existed at that time* to the hosted project via
  `PATCH /v1/projects/{ref}/config/auth`, setting `mailer_subjects_confirmation`
  and `mailer_templates_confirmation_content` directly from
  `supabase/templates/confirmation.html`, verified byte-for-byte at that time.
- T192 (2026-08-31, commit `12d6315`) restyled `supabase/templates/confirmation.html`
  **after** that hosted push and nothing re-ran the push. `git log` shows no
  hosted-sync commit since. The hosted project is therefore serving the
  pre-T192 (unstyled/old-copy) HTML while the repo file has moved on. This is a
  plain staleness bug, not a missing integration — the pipe exists, it just
  wasn't re-run.
- `recovery.html` has not changed since the T153.3 commit that both wrote it and
  pushed it hosted, so it is presumably still in sync — out of scope for this
  ticket, but worth a one-line confirmation in step 2 below since it's nearly
  free once the GET is already being run.

## Explicit non-approach: do NOT use `supabase config push`

`npx supabase config push` uploads the **entire** local `config.toml` `[auth]`
block to the linked hosted project. Local and hosted deliberately diverge on
several fields documented in `supabase/HOSTED_DEV_CONFIG.md`:
- local `site_url = "http://localhost:8081"` vs hosted `https://dailydama.com`
- local `additional_redirect_urls` (localhost only) vs hosted `uri_allow_list`
  (`http://localhost:8081/auth/callback,https://dailydama.com/auth/callback`)
- hosted has custom SMTP (`smtp_host=smtp.resend.com`, etc., wired by T153.3)
  that local `config.toml` doesn't even have uncommented.

A full `config push` would clobber the hosted redirect allowlist and site URL
with the local-only values, breaking real auth callbacks — a much bigger
regression than the one this ticket fixes. Use the targeted Management API
`PATCH` on just the mailer template fields instead, exactly matching the
precedent already set by T153.3.

## Implementation steps

1. **Confirm PAT access in this session's environment.** The gitignored PAT at
   `.env.supabase-pat.local` (repo root) is untracked, so a fresh worktree
   will *not* automatically have it — worktrees only share tracked git state.
   Before starting, confirm the file (or an exported `SUPABASE_ACCESS_TOKEN`)
   is actually present in the implementer's worktree. If it isn't, stop and
   ask rather than trying to read it from outside the worktree.

2. **Read current hosted state before writing anything.**
   `GET https://api.supabase.com/v1/projects/ylyoqswauqyesuwmetnl/config/auth`
   with `Authorization: Bearer <PAT>`. Extract `mailer_subjects_confirmation`
   and `mailer_templates_confirmation_content` and diff the content against
   the current `supabase/templates/confirmation.html` bytes. This confirms
   the staleness diagnosis above empirically instead of assuming it, and
   gives you the exact before-state to record in the delivery-record doc
   (step 5). While the response is in hand, also check
   `mailer_templates_recovery_content` against `supabase/templates/recovery.html`
   — expected to already match; just note the result, don't act on it unless
   it's actually stale (out of this ticket's scope if so — flag instead).

3. **PATCH only the confirmation template fields.**
   `PATCH https://api.supabase.com/v1/projects/ylyoqswauqyesuwmetnl/config/auth`
   with a JSON body containing only:
   - `mailer_templates_confirmation_content`: the exact current contents of
     `supabase/templates/confirmation.html`
   - `mailer_subjects_confirmation`: `"Confirm your Daily Dama account"`
     (matches `config.toml`'s local subject and the value RESEND_DNS_AUTH.md
     already recorded as live — included for explicitness/idempotency, not
     because it's expected to have drifted)
   Build the JSON body with a tool that safely escapes the HTML (e.g.
   `jq -Rs` or `python3 -c 'import json,sys; ...'` reading the file directly)
   rather than hand-quoting in shell — the template contains quotes, braces,
   and a Go template placeholder (`{{ .ConfirmationURL }}`) that are easy to
   mis-escape by hand.
   Do not touch `site_url`, `uri_allow_list`, `smtp_*`, or any other field in
   this PATCH — send only the two keys above.

4. **Re-GET and verify byte-for-byte.** Repeat the `GET` from step 2 and
   confirm `mailer_templates_confirmation_content` now matches
   `supabase/templates/confirmation.html` exactly. This mirrors T153.3's own
   verification pattern and is the cheapest strong signal before spending a
   real send.

5. **Trigger one real signup against the hosted project and inspect the
   actual email.** Use a real (non-`@example.com` — the hosted project
   rejects that domain, per `HOSTED_DEV_CONFIG.md`) disposable inbox and
   `POST https://ylyoqswauqyesuwmetnl.supabase.co/auth/v1/signup` with the
   anon/publishable key as `apikey`, following the same curl pattern already
   used in `supabase/README.md`'s local verification section and
   `RESEND_DNS_AUTH.md`'s delivery record. Confirm the received HTML visually
   shows all five branding elements named in the exit criteria: cream/paper
   background, ink border, hard drop shadow, red uppercase eyebrow, and an
   ink-background/yellow-text button. This is the actual exit criterion —
   the API round-trip in steps 2–4 is necessary but not sufficient evidence
   on its own.

6. **Record the result.** Add a dated update section to
   `supabase/RESEND_DNS_AUTH.md` (matching the existing "2026-08-24 update —
   T154.1" pattern in `HOSTED_DEV_CONFIG.md`) documenting: what the hosted
   template content actually was before the patch (stale/pre-T192), the
   PATCH performed, the re-GET verification, and the real-signup email
   observation from step 5. Do not put the PAT or any secret in this file.

7. **Update `TASKS.md`.** Mark T195 done with a one-line pointer to the new
   record in `RESEND_DNS_AUTH.md`, per the project's task-tracking convention
   (update in the same commit that closes the task).

## Order rationale

Steps 2→3→4 are strictly ordered (read-before-write, then verify-the-write)
because this is a live production-adjacent config mutation with no local
undo — confirming the before-state and the after-state around a single
narrow PATCH is what keeps this safe and auditable, consistent with how
T153.3 already did it. Step 5 (the real send) is deliberately last and
singular: real sends against the hosted project aren't free (rate limits,
real inbox noise) and the exit criteria only need one successful observed
email, not repeated confirmation.

## Risks / things to double-check while implementing

- Verify the exact Management API field names (`mailer_subjects_confirmation`,
  `mailer_templates_confirmation_content`) against the live `GET` response in
  step 2 rather than trusting this plan's names blindly — they're taken
  directly from `RESEND_DNS_AUTH.md`'s own prior live-verified session, so
  confidence is high, but confirm before the `PATCH`.
- The subject rate limit is real on the hosted project (unlike local, which
  no-ops without SMTP configured — see `supabase/README.md`'s rate-limit
  notes). Don't loop real signups against the same address; one send should
  be enough to confirm branding.
- If the `GET` in step 2 shows the hosted content already matches current
  `confirmation.html`, stop and report that the diagnosis was wrong rather
  than patching a no-op and claiming success — re-investigate why real
  signups still show no branding (e.g. a caching layer, a different template
  field actually rendered, or the wrong project ref being hit).
