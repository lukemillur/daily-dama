# T104 — Clear a custom text color when a preset theme is selected

## Decision: extend the reducer action, not the preset handler

Two approaches were on the table. Chosen: **extend `themeColorsUpdated` in the
reducer** (`src/features/profile/model/user-profile.ts`) to unconditionally reset
`themeTextColor` to `undefined`, rather than having
`rainbow-theme-presets.tsx`'s tap handler additionally dispatch
`setThemeTextColor(undefined)`.

Why:
- The exit criteria's reducer test dispatches `themeColorsUpdated` *alone* and
  asserts `themeTextColor` is `undefined` afterward. That can only pass if the
  reducer case itself clears the field — a two-action component-level fix
  would leave a bare `themeColorsUpdated` dispatch not clearing text, failing
  that literal test.
- It centralizes the invariant in the reducer (this project's stated pattern:
  "the reducer is the authority" for domain transitions), so any *current or
  future* caller of `setThemeColors` gets correct behavior for free, instead
  of requiring every call site to remember a second dispatch.
- `setThemeColors` / `themeColorsUpdated` currently has exactly three call
  sites: `RainbowThemePresets` (this bug), `ThemeColorPicker`'s own
  background/accent `ColorField` saves and its "Reset background & accent"
  button, and `kentei-onboarding.tsx`'s preset tap during onboarding.

**Material side effect to flag explicitly (not hidden in the diff):** because
`ThemeColorPicker`'s manual background-color and accent-color `Save` buttons
also call `setThemeColors`, they will now also clear a previously-saved custom
text color as a side effect of saving just the background or accent field.
Today they do not touch text color at all. No existing test asserts the old
"text survives a manual background/accent save" behavior, so nothing in the
current suite breaks, and the task's own exit criteria only requires the
*text-color-only* save/reset paths (`themeTextColorUpdated`, dispatched by
`setThemeTextColor`) to stay unaffected — which they do, since that reducer
case is untouched. Product-wise this is arguably *more* correct: a background
change can invalidate the contrast a custom text color was tuned against, so
resetting it forces a fresh, still-legible choice. If the user disagrees after
seeing it, the fallback is to split `setThemeColors` into two variants (one
that clears text, one that doesn't) — flagged here as an assumption, not
silently decided.

## Files and order

1. **`src/features/profile/model/user-profile.ts`** — reducer change first,
   since everything else exercises it.
   - In `userProfileReducer`, case `'themeColorsUpdated'` (currently ~line
     142-147), add `themeTextColor: undefined` to the returned object
     alongside the existing `themeBackgroundColor`/`themeAccentColor`
     overwrite. No change to the `UserProfileAction` union shape is needed —
     `themeColorsUpdated` doesn't need a new field, it just always zeroes text
     now.
   - No change needed to `setThemeColors` in
     `src/features/profile/state/user-profile-provider.tsx` (~line 125-129):
     it already forwards straight to `themeColorsUpdated` with no
     `themeTextColor` argument, so the reducer-level fix is sufficient and the
     action's public signature is unchanged.

2. **`src/features/profile/model/user-profile.test.ts`** — add the reducer
   test the exit criteria specifies, next to the existing
   `'sets both theme colors and allows clearing one independently'` test
   (~line 151-166):
   - New test: start from a state with `themeTextColor: '#abcdef'` (e.g.
     via a preceding `themeTextColorUpdated` dispatch or an inline state
     literal, matching the existing style in that file), dispatch
     `themeColorsUpdated` with some background/accent, and assert
     `result.themeTextColor` is `undefined`.
   - Leave the two existing `themeTextColorUpdated`-focused tests (~line
     196-231) untouched — they exercise a different action and must keep
     passing unmodified per the exit criteria.
   - Optionally extend the existing `'does not clobber unrelated profile
     fields when updating theme colors'` test or add a sibling to confirm
     `selectedTrickIds` etc. still survive a `themeColorsUpdated` dispatch
     that also clears text — not required by the exit criteria but cheap
     insurance given the reducer case is being touched.

3. **`src/features/profile/components/rainbow-theme-presets.test.tsx`** — add
   the component-level test the exit criteria specifies:
   - Extend the local `ProfileProbe` to also read and render `themeTextColor`
     (mirroring the pattern already used in `theme-color-picker.test.tsx`'s
     `ProfileProbe`).
   - Add a small helper element (mirroring `theme-color-picker.test.tsx`'s
     `PresetButton` pattern) that calls `setThemeTextColor` from
     `useUserProfileActions`, so the test can seed a custom text color before
     selecting a preset — `RainbowThemePresets` itself has no UI for setting
     text color, so the test needs its own trigger for that setup step.
   - New test: mount `RainbowThemePresets` plus the probe and the text-color
     setter helper; call the setter to persist a custom `themeTextColor`;
     select any preset via `findByLabel(root, preset.label + " theme
     preset").props.onPress()`; assert `probeValue(root, "probe-text")` is
     `"unset"` afterward. Optionally also assert it survives a remount (same
     pattern as the existing "persists ... across a remount" test) to prove
     it round-tripped through storage rather than only updating in-memory
     state.
   - No changes needed to `rainbow-theme-presets.tsx` itself — the fix lives
     entirely in the reducer, so this component and its existing
     `setThemeColors` call site are unchanged.

4. **`src/features/profile/components/theme-color-picker.test.tsx`** — no
   changes required. Confirm after step 1 that the full file still passes:
   none of its existing assertions check that a *previously saved* text color
   survives a subsequent background/accent save or the "Reset background &
   accent" button, so the new clearing behavior doesn't trip any existing
   expectation. Do not add a new test here proactively — if the user wants
   the "manual single-field save preserves text" behavior *preserved*, that's
   a product call to make after seeing this side effect, not something to
   pre-empt with speculative test/behavior changes.
