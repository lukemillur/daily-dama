  - `id`: `length(id) > 0` only (DB does **not** require it trimmed).

    check): a sequence row's `existingTrick` steps must not reference
    another row in the same batch whose `kind` is `'sequence'`.

## Deliberate design decisions (confirm-or-flag if you disagree, otherwise proceed)

1. **No `'absent'` status for the collection mapper.** Unlike
   `profiles` (one row per user, "no row yet" is meaningful), an empty
   `custom_tricks` row list is simply a valid empty collection —
   `{ status: 'valid', collection: INITIAL_CUSTOM_TRICKS }`. Don't invent
   an absent branch that has no local meaning.
2. **Whole-batch invalidation on any bad row**, mirroring
   `mapTrickStateRowsToDomainFields`: one malformed/foreign/nested-sequence
   row invalidates the whole collection mapping rather than silently
   dropping it. A partial custom-trick library is worse than a loud
   failure.
3. **Nested-sequence defense-in-depth only applies to the row→domain
   direction.** The domain→row direction stays a total, non-`Result`
   pure function (like `mapUserProfileToProfileUpsertInput`), because
   `CustomTrick`/`CustomTrickCollection` are already trusted,
   reducer-constructed shapes by the time anything calls the write-side
   mapper, and `selectSequenceStepCandidates` already prevents the local
   UI from constructing a nested sequence in the first place. Don't add
   cross-row validation to the write path.
4. **Mapping layer is intentionally stricter than the DB's `id` check**:
   validate `id` with the same `isNormalizedText` (non-empty *and*
   trimmed) used for `name`, even though the DB CHECK only requires
   `length(id) > 0`. `createCustomTrickId` never produces whitespace, so
   this never rejects legitimate data, and being stricter here is
   consistent with "loud failure over silently wrong state." Don't try to
   exactly mirror the DB's laxer `id` constraint.

## Implementation order

1. **`src/features/custom-tricks/persistence/custom-trick-persistence.ts`**
   — export `isNormalizedText`, `isOptionalKenteiRank`, and
   `isSequenceStep` (add `export` only, no logic change). Run
   `yarn tsc --noEmit` mentally/quickly after — no other file references
   change yet.

2. **New file:
   `src/features/custom-tricks/persistence/custom-trick-cloud-mapping.ts`**
   — the mapping module itself. Structure, in order:

   a. Header comment matching `profile-cloud-mapping.ts`'s style: what
      this file does, what it explicitly does not do (no
      provider/reducer/sync wiring — that's a future ticket), and the
      row→domain "treat every field as unknown" vs domain→row "trusted,
      total function" split.

   b. Types:
      ```ts
      export type CustomTrickMappingIssueReason =
        | 'wrongType'
        | 'outOfRange'
        | 'malformedShape'
        | 'foreignUser'
        | 'duplicateId'
        | 'nestedSequence';

      export interface CustomTrickMappingIssue {
        readonly path: string;
        readonly reason: CustomTrickMappingIssueReason;
        readonly message: string;
      }

      export type CustomTrickRowMappingResult =
        | { readonly status: 'invalid'; readonly issues: readonly CustomTrickMappingIssue[] }
        | { readonly status: 'valid'; readonly trick: CustomTrick };

      export type CustomTrickCollectionMappingResult =
        | { readonly status: 'invalid'; readonly issues: readonly CustomTrickMappingIssue[] }
        | { readonly status: 'valid'; readonly collection: CustomTrickCollection };
      ```
      (No `invariantViolation` reason carried over from profiles — nothing
      here needs it; `nestedSequence` replaces it for this domain's one
      cross-field/cross-row rule.)

   c. `mapCustomTrickRowToDomainTrick(row: CustomTrickRow, expectedUserId: string): CustomTrickRowMappingResult`
      — single-row, self-contained validation (no sibling-row lookups):
      - `row.user_id !== expectedUserId` → `foreignUser` issue at path
        `user_id`, short-circuit return (matches
        `mapProfileRowToDomainFields`'s early return for this case).
      - Treat `row as unknown as Record<string, unknown>` for the rest,
        same rationale as the profile mapper.
      - `id`: `isNormalizedText` → else `malformedShape` at `id`.
      - `kind`: must be `'standalone'` or `'sequence'` → else
        `malformedShape` at `kind` (unknown kind isn't really "wrongType"
        since it's a string already, so use `malformedShape` for an
        unrecognized enum value, consistent with how the profile mapper
        uses `malformedShape` for shape problems vs `wrongType` for
        wrong-JS-type problems).
      - `name`: `isNormalizedText` → else `malformedShape` at `name`.
      - `kentei_rank`: null/undefined → absent; else must be
        `isOptionalKenteiRank`-valid (reuse the *value*, not the
        undefined-shortcut) → else `outOfRange` at `kentei_rank` (mirror
        profile's `wrongType` vs `outOfRange` split: non-number →
        `wrongType`, number outside 1–12 or non-integer → `outOfRange`).
      - `steps` + `kind` cross-check (still single-row, this is the
        row's own two columns, not a sibling lookup):
        - `kind === 'standalone'`: `steps` must be `null`/`undefined` →
          else `malformedShape` at `steps`.
        - `kind === 'sequence'`: `steps` must be a non-empty array with
          `length >= 2` → else `malformedShape` at `steps`; then validate
          each element:
          - Must satisfy the reused `isSequenceStep` predicate → else
            `malformedShape` at `steps[i]`.
          - **Exact key-set check** beyond what `isSequenceStep` proves
            (`isSequenceStep` only checks presence/type of the fields it
            cares about, not absence of extras — mirror the DB trigger's
            `step <> jsonb_build_object(...)` exactness check): a
            `customText` step's raw object must have exactly the keys
            `kind`,`name`; an `existingTrick` step's raw object must have
            exactly `kind`,`name`,`sourceTrickId`. Reject extra keys as
            `malformedShape` at `steps[i]`.
          - Self-reference: `existingTrick` step with
            `sourceTrickId === row.id` → `malformedShape` at `steps[i]`
            with an explicit self-reference message (this is *not* the
            `nestedSequence` reason — it's caught row-locally, without
            needing sibling rows, so keep it distinct from the batch-level
            nested check for a clearer failure message).
      - Collect *all* issues (don't short-circuit after the first, mirror
        `mapProfileRowToDomainFields`'s "collect multiple simultaneous
        issues" behavior) and return `invalid` if any exist.
      - On success, build a fresh `CustomTrick` object literal (never
        spread `row`): `{ id, kind, name, ...(kenteiRank !== undefined ?
        {kenteiRank} : {}), ...(kind === 'sequence' ? {steps: mappedSteps}
        : {}) }`, where `mappedSteps` are freshly constructed
        `SequenceStep` objects (not the raw JSON references) —
        `{kind:'customText', name}` or
        `{kind:'existingTrick', name, sourceTrickId}` — this is what
        makes "does not resolve names from current source tricks" true by
        construction: the mapper only ever reads `name` off the step
        object itself, never looks anything up by `sourceTrickId`.

   d. `mapCustomTrickRowsToDomainCollection(rows: readonly CustomTrickRow[], expectedUserId: string): CustomTrickCollectionMappingResult`
      — the batch composer:
      - Map every row through `mapCustomTrickRowToDomainTrick`, collecting
        issues with a `rows[i].` path prefix (mirror
        `mapTrickStateRowsToDomainFields`'s `pathPrefix` pattern) and
        collecting successfully-mapped tricks separately.
      - Duplicate-id defense-in-depth: track seen ids across the batch
        (same `Set`-based duplicate-detection shape as the profile
        mapper's `duplicateTrickIds`), issue `duplicateId` at
        `id=<value>` for repeats.
      - Nested-sequence cross-row check: build an `id -> kind` map from
        the **raw rows** (`row.id`/`row.kind`, not the mapped tricks — a
        malformed row can still carry a `kind` worth checking against,
        and this keeps the check independent of whether that row itself
        passed validation). For every row whose own `kind === 'sequence'`
        and whose `steps` is an array, walk its `existingTrick` steps'
        `sourceTrickId`s; if the map says that id's `kind === 'sequence'`,
        push a `nestedSequence` issue at `rows[i].steps[j].sourceTrickId`.
        Run this pass regardless of whether the row-level pass already
        flagged that row, since both are useful independent signals — but
        it will naturally also fire for otherwise-valid sequence rows
        that reference an otherwise-valid sequence sibling, which is
        exactly the case this check exists for.
      - If any issues (row-level, duplicate, or nested) exist anywhere in
        the batch, return `{status: 'invalid', issues}` — whole batch
        fails together (decision 2 above).
      - Otherwise return `{status: 'valid', collection: {tricks: mappedTricks}}`.

   e. `mapCustomTrickToUpsertInput(trick: CustomTrick, userId: string): CustomTrickInsert`
      — trusted, total, pure. Fresh object literal, no spreading
      `trick`:
      ```ts
      {
        user_id: userId,
        id: trick.id,
        kind: trick.kind,
        name: trick.name,
        kentei_rank: trick.kenteiRank ?? null,
        steps: (trick.kind === 'sequence'
          ? trick.steps.map((step) =>
              step.kind === 'customText'
                ? { kind: 'customText', name: step.name }
                : { kind: 'existingTrick', name: step.name, sourceTrickId: step.sourceTrickId },
            )
          : null) as unknown as Json | null,
      }
      ```
      Rebuilding each step object explicitly (rather than spreading
      `step`) is what proves the write path can't accidentally leak an
      extra property onto a stored step, and structurally guarantees
      "source-name re-resolution" can't happen here either — the mapper
      only ever copies `step.name` through, never dereferences
      `sourceTrickId` against anything.

   f. `mapCustomTrickCollectionToUpsertInputs(collection: CustomTrickCollection, userId: string): readonly CustomTrickInsert[]`
      — thin `collection.tricks.map((trick) => mapCustomTrickToUpsertInput(trick, userId))` convenience wrapper, matching the shape of
      `mapUserProfileToTrickStateUpsertInputs` (one row per domain item).

3. **New file:
   `src/features/custom-tricks/persistence/custom-trick-cloud-mapping.type-check.ts`**
   — same purpose/header comment as
   `profile-cloud-mapping.type-check.ts` (compile-time only, not
   `*.test.ts`, not under `__tests__/`, no runtime behavior). Prove:
   - `CustomTrickRowMappingResult`'s `'invalid'` branch has no `.trick`
     property without narrowing (`@ts-expect-error` on unnarrowed
     access); `'valid'` branch requires narrowing to read `.trick`.
   - Same pair of checks for `CustomTrickCollectionMappingResult` /
     `.collection`.
   - No ambiguous empty-object stand-in compiles for `CustomTrick` (e.g.
     `const empty: CustomTrick = {}` must `@ts-expect-error`) and for
     `SequenceStep` (`const emptyStep: SequenceStep = {}` must
     `@ts-expect-error`) — this is the discriminated-union-specific proof
     this task's exit criteria implicitly need, since the whole point of
     rejecting "malformed rows" is that the type system already refuses
     to let a valid `CustomTrick`/`SequenceStep` be constructed without
     its discriminant-appropriate fields.

4. **New file:
   `src/features/custom-tricks/persistence/custom-trick-cloud-mapping.test.ts`**
   — mirror `profile-cloud-mapping.test.ts`'s structure (fixture
   builders, `deepFreeze`, `describe` blocks per concern). Fixture
   builder:
   ```ts
   function makeCustomTrickRow(overrides: Partial<CustomTrickRow> = {}): CustomTrickRow {
     return {
       user_id: USER_ID,
       id: 'custom-1',
       kind: 'standalone',
       name: 'Around the World',
       kentei_rank: null,
       steps: null,
       revision: 1,
       created_at: TIMESTAMP,
       updated_at: TIMESTAMP,
       ...overrides,
     };
   }
   ```
   Test groups (all required by the exit criteria — treat this list as
   the minimum bar, not exhaustive):

   - **Round-trip (domain → row → domain), one `it` per variant**, using
     a `toCustomTrickRow(trick)` helper analogous to the profile test's
     `toProfileRow` (splice `mapCustomTrickToUpsertInput`'s output into a
     full row fixture with `revision`/`created_at`/`updated_at` filled
     in), then assert
     `mapCustomTrickRowToDomainTrick(row, USER_ID) === {status:'valid', trick}`:
     - standalone, no `kenteiRank`.
     - standalone, `kenteiRank` at 1 and at 12 (boundary values).
     - sequence with only `existingTrick` steps.
     - sequence with only `customText` steps.
     - sequence with a mix of both step kinds.
     - sequence with `kenteiRank` set.
     - Also one **collection-level** round-trip: several of the above
       tricks together through
       `mapCustomTrickRowsToDomainCollection`/`mapCustomTrickCollectionToUpsertInputs`,
       asserting order and full-collection equality (order should be
       preserved — don't let the mapper silently reorder; if it doesn't
       naturally preserve order, that's worth a comment, not a bug to
       "fix" by sorting).

   - **Malformed-row rejection** (`it.each` where the shape repeats),
     each asserting `status === 'invalid'` and that the right
     `path`/`reason` is present:
     - unknown `kind` value.
     - blank/untrimmed `name`.
     - `kentei_rank` = 0, 13, 1.5 (non-integer).
     - standalone row with non-null `steps`.
     - sequence row with `steps: null`.
     - sequence row with `steps: []` or a single-element array (length
       < 2).
     - sequence step missing `name`.
     - sequence step with untrimmed/empty `name`.
     - `customText` step carrying an extra `sourceTrickId` key.
     - `existingTrick` step missing `sourceTrickId`.
     - `existingTrick` step with an empty `sourceTrickId`.
     - `existingTrick` step referencing its own row's `id`
       (self-reference) — assert `malformedShape`, not `nestedSequence`
       (per the row-local vs batch-level distinction above).
     - a row belonging to a different user (`foreignUser` at `user_id`).
     - "collects multiple simultaneous issues" case analogous to the
       profile test (e.g. bad `kind` *and* bad `kentei_rank` on the same
       row → both issues present).

   - **Nested-sequence rejection** (batch-level, the exit criterion's
     explicit named case):
     - Two rows: row A (`kind: 'sequence'`) has an `existingTrick` step
       whose `sourceTrickId` is row B's `id`; row B is itself
       `kind: 'sequence'`. Assert
       `mapCustomTrickRowsToDomainCollection([rowA, rowB], USER_ID)` is
       `invalid` with a `nestedSequence` issue.
     - Confirm a *non*-nested batch (row A referencing a *standalone*
       row B) round-trips as `valid`, as a negative control right next to
       the positive one.

   - **Duplicate-id rejection**: two rows sharing the same `id` →
     `invalid` with `duplicateId`.

   - **Stored-name-preservation fixtures** (the exit criterion's other
     explicit named case — this is the one that most needs a real test,
     not just a design read-through):
     - Build a sequence row whose `existingTrick` step stores
       `{ sourceTrickId: 'trick-b', name: 'Old Name' }`, alongside a
       *separate* row for `trick-b` whose current `name` is
       `'New Name'` (simulating a rename after the step was recorded).
       Map the sequence row and assert the mapped step's `name` is
       `'Old Name'` — the mapper must never have looked at `trick-b`'s
       row at all for this.
     - Same setup but *omit* the `trick-b` row entirely from the batch
       (simulating deletion). Assert the sequence row still maps
       successfully with the stored `name` intact, and that this does
       **not** trigger a `nestedSequence` issue (the referenced id isn't
       in the batch at all, so there's nothing to flag — a step
       referencing a deleted or standard-Kentei trick id is exactly the
       normal case, not an error case).

   - **Mutation-freedom**: `deepFreeze` a `CustomTrick` (both a
     standalone and a sequence variant, since the sequence variant
     exercises the nested-array steps case) before calling
     `mapCustomTrickToUpsertInput`/`mapCustomTrickCollectionToUpsertInputs`,
     and `deepFreeze` `CustomTrickRow`/an array of rows before calling
     `mapCustomTrickRowToDomainTrick`/`mapCustomTrickRowsToDomainCollection`;
     assert no throw and `JSON.stringify` before/after is unchanged for
     each, mirroring the profile test's two "no input mutation" cases.
