# T262 — Bound the auth session-refresh hydration gate

## Confirmed root cause (supabase-js / auth-js 2.112.3, verified against installed source)

`node_modules/@supabase/auth-js/dist/module/GoTrueClient.js` (2.112.3):

- `onAuthStateChange()` (line ~3614) registers the callback, then does
  `await this.initializePromise` before it ever emits **any** event — including
  `INITIAL_SESSION`. `getSession()` (line ~2398) has the identical
  `await this.initializePromise` gate. There is no SDK entry point that returns a
  cached/local session without first waiting on the full init chain.
- `initializePromise` resolves from `_initialize()` → `_recoverAndRefresh()`
  (line ~4056). When a persisted session exists and is inside its expiry margin,
  that function does `await this._callRefreshToken(refreshToken)` — the literal
  network call that hung in the incident — before `_initialize()` can resolve.
- `_refreshAccessToken` (line ~3993) retries with backoff (200ms, 400ms, 800ms…)
  bounded by `AUTO_REFRESH_TICK_DURATION_MS = 30_000` (`lib/constants.js`). This
  is why the incident "resolved on its own" at ~30+ seconds — that's GoTrue's own
  internal retry ceiling, not a deliberate design choice we can rely on for UX.
- **Conclusion for the Notes' open question:** there is no event-ordering trick
  that surfaces a cached session ahead of the refresh — `INITIAL_SESSION` itself
  is gated behind the same stuck promise. Trusting a cached session optimistically
  requires reading it directly from `AsyncStorage`, fully independent of
  `onAuthStateChange`/`getSession()`/`initializePromise`.
- Also confirmed and important for step 5 below: `signOut()` (line ~3395) *also*
  does `await this.initializePromise` first. **The existing `signOut` action
  cannot be reused as the escape hatch** — calling it while the refresh is still
  hung would await the same stuck promise and hang identically, defeating the
  escape hatch entirely.
- The default GoTrue storage key is computed in `@supabase/supabase-js`'s
  `SupabaseClient` constructor as `` `sb-${new URL(supabaseUrl).hostname.split('.')[0]}-auth-token` `` — this
  project does not currently override `storageKey`, so this default applies.
  Do **not** set an explicit `storageKey` in `createClient()`'s auth options as
  part of this change — that would silently force a local sign-out for every
  currently-authenticated production user on next deploy (GoTrue itself would
  look under a different key and find nothing). Instead, replicate the same
  derivation in our own code so we read the exact key GoTrue already uses.

## Design

Two independent, separately-testable mechanisms, both scoped to
`src/features/auth/state/auth-provider.tsx`'s init effect:

1. **Optimistic direct read (exit criterion a).** In parallel with (not gating)
   the existing `client.auth.onAuthStateChange` subscription, read the persisted
   session directly from `AsyncStorage` under the same key GoTrue uses, validate
   its shape, and — if usable — immediately set `AuthState` to `authenticated`
   without waiting for any GoTrue event. This is a single `AsyncStorage.getItem`
   call with no network dependency, so it resolves in effectively one microtask
   tick regardless of what the refresh call is doing.
2. **Bounded app-level timeout (exit criterion b).** A `setTimeout` started at
   the same time as the subscription. If neither a real `onAuthStateChange`
   event nor the optimistic read has moved `AuthState` off `initializing` by the
   deadline, force a transition to a new `refreshFailed` status. If the
   optimistic read already fired (cached session found), the timeout firing is a
   no-op — direction (1) explicitly makes a stale/erroring background refresh
   invisible to a user with a live cached session.

The existing `onAuthStateChange` subscription is always authoritative and is
**never torn down** by the timeout firing — it keeps listening for the rest of
the component's lifetime. This matters: if GoTrue's own init eventually
resolves (its own ~30s retry ceiling, or later), the real event still arrives
and self-corrects `AuthState` away from `refreshFailed` or away from the
optimistic guess, exactly as `deriveAuthState` already handles today (a
`SIGNED_OUT` arriving after an optimistic `authenticated` correctly downgrades
to guest).

Do **not** design an in-process "retry" that re-subscribes or re-derives state
from the same client instance: `initializePromise` is memoized once per
`GoTrueClient` instance, so a fresh subscription during the same hang would just
await the identical still-pending promise — it would not restart the network
attempt. The only thing that genuinely restarts the attempt is a fresh client,
i.e. a page reload. Use `window.location.reload()` for "Try again" (guarded for
`typeof window !== 'undefined'`, matching this file's existing convention).

     `{ readonly status: 'refreshFailed' }` variant to `AuthState`.
   - Leave `deriveAuthState` untouched — it only maps real GoTrue events, and
     GoTrue never reports this status; it is purely a local timeout-driven

   - Update `src/features/auth/model/__tests__/auth-state.test.ts` only if it

2. **`src/features/auth/model/identity-from-auth-state.ts`**

     as `'initializing'`), not to `GUEST_IDENTITY`. `IdentityProvider` must keep

3. **New `src/features/auth/model/cached-session.ts`**

     synchronous. `JSON.parse` in a try/catch; validate `typeof === 'object'`,
     `access_token: string`, `refresh_token: string`, `user.id: string` present.
     No expiry check (direction 1 trusts optimistically regardless of
     freshness; the real event corrects it later if actually invalid). Return
     the parsed value cast to `Session` only after the structural check passes.
   - New `src/features/auth/model/__tests__/cached-session.test.ts`: null raw,

   - Keep this file free of any AsyncStorage/IO — it only parses a string. This

     - `getGoTrueStorageKey(): string | null` — returns `null` when

       non-web), else the resolved key for the memoized config. Must share the

     - `resetSupabaseClientForTests()` must also clear whatever new memoized

   - New tests in `src/shared/supabase/__tests__/supabase-client.test.ts`:

     `getGoTrueStorageKey()` returning `null` when unconfigured and the correct

5. **`src/features/auth/state/auth-provider.tsx`** (core change)
   - Add `const AUTH_INIT_TIMEOUT_MS = 10_000;` near the top, with a comment
     explaining the value: comfortably above any realistic successful refresh
     round-trip, well under GoTrue's own internal ~30s retry ceiling
     (`AUTO_REFRESH_TICK_DURATION_MS`, auth-js 2.112.3 `lib/constants.js`) — the
     goal is actionable feedback well before that ceiling, not racing it.
   - Rewrite the init `useEffect` (current lines 59–84):
     - Keep the existing `!client` branch and the synchronous-throw `catch`
       branch unchanged.
     - Add a `let settled = false;` (plain closure variable, not state) that
       flips `true` the moment a real `onAuthStateChange` event fires. Both the
       optimistic-read branch and the timeout branch must check it before
       calling `setState`, so a late-arriving real event is never clobbered by
       either.
     - Kick off the optimistic read: `AsyncStorage.getItem(getGoTrueStorageKey())`
       (guard `null` key defensively, though it shouldn't happen once `client`
       is non-null) → `parseCachedSession` → if defined and `!settled`,
       `setState((current) => current.status === 'initializing' ? { status: 'authenticated', session: cached, lastEvent: 'INITIAL_SESSION' } : current)`.
       Use `'INITIAL_SESSION'` as `lastEvent` since that's the event GoTrue
       itself would have used for a session recovered from storage.
     - Start `const timeoutId = setTimeout(() => { if (settled) return; setState((current) => current.status === 'initializing' ? { status: 'refreshFailed' } : current); }, AUTH_INIT_TIMEOUT_MS);`.
     - In the `onAuthStateChange` callback: set `settled = true`,
       `clearTimeout(timeoutId)`, then the existing `setState((current) => deriveAuthState(event, session, current))` unchanged.
     - Cleanup function: set `settled = true`, `clearTimeout(timeoutId)`, then
       `subscription.unsubscribe()` as today.
   - Add a new action to `AuthActions` / the provider, e.g.
     `abandonAuthAndContinueAsGuest: () => Promise<{ error: Error | null }>`.
     This is the sign-out/guest escape hatch for the `refreshFailed` screen and
     must **not** call `client.auth.signOut()` (see root-cause note above — it
     awaits the same stuck `initializePromise`). Implementation:
     - Resolve the storage key via `getGoTrueStorageKey()`.
     - `await AsyncStorage.removeItem(key)` in a try/catch (if key is `null`,
       there's nothing to remove — treat as success).
     - On success: `setState({ status: 'guest', reason: 'error' })`, return
       `{ error: null }`.
     - On failure: return `{ error }` **without** changing state — fail closed,
       per AGENTS.md's destructive/identity-transition rule. The UI must keep
       the user on the visible recovery screen with actionable copy rather than
       silently pretending the transition happened.
     - This does not need `stateRef.current.status === 'refreshFailed'` guard —
       it's harmless (if unlikely) to allow it from other states too, but note
       in a comment that it's designed for the `refreshFailed` recovery screen.
   - No new "retry" action — `identity-provider.tsx`'s retry button calls
     `window.location.reload()` directly (see Design section for why).

## Risks / non-obvious things to keep in mind

- The `signOut()`-also-awaits-`initializePromise` finding above is easy to miss
  and would silently reintroduce the exact same hang inside the "escape hatch"
  if the existing `signOut` action is reused instead of the new
  `AsyncStorage`-only `abandonAuthAndContinueAsGuest`. Don't reuse `signOut`
  here.
- `getGoTrueStorageKey()`'s derivation is a reimplementation of an undocumented
  supabase-js internal default. It is deliberately *not* configured explicitly
  (see root-cause note) to avoid forcing a mass logout. If a future supabase-js
  upgrade changes that default algorithm, this derivation silently stops
  matching and the optimistic read silently stops finding real sessions
  (degrading gracefully back to today's behavior — not a hard failure — but
  worth a comment pointing future upgraders at this file).
- Keep the optimistic-read `setState` and the timeout `setState` both guarded
  by `current.status === 'initializing'` (not unconditional), so ordering
  races between the two async branches and the real subscription can never
  stomp a state that already resolved another way.
- `jest.useFakeTimers()` interacting with the existing `await act(async () => …)`
  microtask-flushing pattern in these two test files needs care — verify each
  updated/new test still reliably flushes pending microtasks between fake-timer
  advances (`await act(async () => { jest.advanceTimersByTime(...); })` or
  `jest.advanceTimersByTimeAsync` if using modern fake timers) rather than
  assuming a synchronous `jest.advanceTimersByTime` alone flushes the
  `AsyncStorage.getItem` promise chain.
