# T161.3 — Prove cascade deletion and old-session denial

## Outcome and boundary

Add a real local-Supabase acceptance suite for the `delete-account` Edge
Function and the exposed `api` Data API. A clean reset must seed the complete
six-resource fixture for two confirmed users, delete user A through the
function, prove that only A's Auth identity and rows disappear, and prove that
anonymous, expired, wrong-user, stale, and pre-deletion credentials cannot
access or recreate A's application data or affect B. Simulate a lost successful
response and retry the same deletion until the observable result converges.

This is backend acceptance evidence only. Do not modify the app, local
persistence, mobile tooling, hosted Supabase, migrations, or the app Jest
suite. Do not duplicate T161.2's in-memory handler tests or T161.1's existing
malformed-body/password/confirmation cases except where a real-stack fixture is
needed to establish the acceptance boundary.

## Verified repository contracts

- The six exposed resources are `api.profiles`, `api.user_trick_states`,
  `api.custom_tricks`, `api.practice_sessions`, `api.goals`, and `api.notes`.
  Each owns rows through `user_id references auth.users(id) on delete
  cascade`; goals and notes are soft-delete domain records, but account
  deletion must remove their physical rows through the Auth cascade.
- `supabase/tests/functions/t161_1_delete_account.test.mjs` already uses
  `node:test`, `getLocalConfig()`, admin-created confirmed users, password
  sign-in, raw `fetch` through `callDeleteAccount`, and the target user's
  pre-deletion JWT for post-delete table reads. Keep that convention: the
  service-role key is valid for GoTrue admin checks but is not granted the
  exposed table privileges required for PostgREST row assertions.
- `supabase/tests/functions/t161_2_delete_account_security.test.mjs` is a
  handler-only fake-environment suite. Its relevant real contract is
  `Cache-Control: no-store`, trusted server-resolved identity, and
  already-absent/admin-not-found idempotency.
- `yarn test:functions` runs the function `node:test` files, and
  `yarn test:db` runs the clean-reset/data-api/function sequence followed by a
  cleanup reset. A standalone focused test is the iteration command; the
  complete backend command is the completion gate. Neither substitutes for or
  invokes the app Jest suite.
- Local Auth uses confirmed admin fixtures, one-hour JWT expiry, and a
  runtime-discovered API/anon/service-role configuration. The acceptance test
  must never commit or print keys and must finish with a reset when run outside
  the consolidated runner.

## Ordered implementation plan

### 1. Establish the test boundary and fixture helpers

Create `supabase/tests/functions/t161_3_delete_account_acceptance.test.mjs`
as a plain `node:test` suite. Reuse `getLocalConfig`,
`createConfirmedUser`, `signIn`, `deleteUser`, `restClient`, and
`callDeleteAccount`; add only small test-local helpers if the existing shared
helpers cannot express a required request.

Build deterministic, unique user-A and user-B fixtures in one suite setup:

1. Create both confirmed Auth users with the standard test password.
2. Sign both in and retain fresh A and B access tokens.
3. Insert one representative row for each of the six resources for each
   user, using stable IDs/names that make ownership and snapshots obvious.
4. Assert the setup has exactly six rows per user before deletion, so a
   missing seed cannot make a false-positive cascade test pass.

Use one cleanup hook that tolerates an already-deleted A and deletes B. If a
test fails before the deletion, cleanup must remove both users through the
admin API; the documented reset remains the final fixture cleanup boundary.

### 2. Prove isolation and complete physical cascade cleanup

Before deleting A, use B's client to assert every A-filtered select returns an
empty array, and assert B's six rows remain present. This keeps the acceptance
test tied to the real PostgREST/RLS path rather than only counting through an
admin connection.

Invoke `POST /functions/v1/delete-account` with A's fresh token, the correct
password, and exact `DELETE` confirmation. Assert `204`, empty body, and
`Cache-Control: no-store`.

After deletion, assert all of the following:

- GoTrue admin lookup for A is `404`.
- A has zero physical rows in all six resources when queried with the still
  cryptographically valid A token (the existing T161.1 rationale explains why
  this is the usable table-observation path).
- B's Auth user still exists and B's six fixture rows, values, and ownership
  are unchanged.
- A's former row IDs cannot be observed through B's client, and no B row was
  removed or altered.

Keep the cascade assertion resource-complete; a single profile check is not
evidence for the other five foreign keys.

### 3. Exercise credential-state denial and identity isolation

Add focused real-HTTP cases around the same local stack and distinguish the
expected endpoint contract from Data API authorization:

- Anonymous/no `Authorization` request to the function returns `401`.
- A deterministically expired but correctly signed local JWT returns the
  normal unauthorized response from an operation that requires a live user.
  Obtain the local JWT signing material from runtime `supabase status -o json`
  (extend the test-only config/helper shape if necessary), construct only an
  in-memory HS256 token with a past `exp`, and do not add a dependency or
  hardcode a secret. Do not wait for `jwt_expiry` and do not treat a forged
  signature as an expired-session proof.
- B's valid token cannot delete A, cannot name A in a request body, and cannot
  mutate/read A's rows. Assert B remains intact after the probe.
- A's retained pre-deletion token cannot perform an authenticated operation
  that requires A to still exist; for the delete endpoint specifically, honor
  T161.2's intentional already-absent behavior and assert a retry is `204`
  rather than incorrectly requiring `401`.
- A stale token captured before the destructive operation is used against the
  Data API and the delete function. Assert it cannot make A reappear or
  affect B; the only successful delete retry is the documented idempotent
  absent-user result.

If the local GoTrue version exposes a different status/code for an expired
token than a generic unauthorized token, assert the stable denial status and
avoid matching secret-bearing error text. Record the exact observed contract
in the test comment rather than weakening the case to an unsigned token.

### 4. Prove row-recreation prevention for every resource

Using A's old pre-deletion JWT after successful deletion, attempt to insert a
new row owned by A into each of the six resources. Send
`Prefer: return=representation` where needed so a zero-row success cannot be
mistaken for a mutation. Assert each request is rejected by the real
foreign-key/auth boundary and then verify, with B's client or a permitted
observation path, that no A row exists and no B row changed.

Also attempt a forged ownership payload that targets B with A's old token on
at least the representative mutation path; assert the ownership/RLS boundary
rejects it. The six-resource loop must remain explicit enough that a future
resource omission is visible in test output.

Do not claim that JWT signature validity alone means a deleted session is
revoked: the existing PostgREST behavior intentionally verifies the signature
without checking `auth.users` existence. The proof required here is that this
cannot recreate rows because the database ownership foreign key and policies
still reject the mutation.

### 5. Prove lost-response retry convergence

Model response loss at the client boundary without changing the function or
database result: issue a valid deletion for A, discard the first response
object as if the network failed after the server committed, and retry with the
same old A token and deletion body. Assert the retry returns the documented
`204`/empty/no-store result, does not create a new Auth user, and does not
recreate any application rows.

Make the convergence assertion observable and complete: repeat the six-table
zero-row checks, the Auth `404` check, and B's unchanged-six-row check after
the retry. Use a unique fixture isolated from the preceding denial cases so a
previous deletion cannot accidentally make the first call a no-op. Do not
mock the admin delete call; T161.2 already proves the fake-handler race and
this ticket must prove the real function/Auth interaction.

### 6. Wire, document, and verify only the backend suite

Keep the new file covered by the existing glob used by `yarn test:functions`;
only add a package/README change if the current command does not discover it.
Document the focused command, clean-reset prerequisite, runtime-key behavior,
and final cleanup reset in `supabase/README.md` if the new acceptance scope is
not discoverable from the existing T161.1 section. Do not add it to
`verify.mjs` or the app Jest command.

Run the narrow test while iterating:

```sh
node --test supabase/tests/functions/t161_3_delete_account_acceptance.test.mjs
```

Before completion, run the dedicated backend gate from the claimed worktree:

```sh
yarn test:functions
yarn test:db
```

`yarn test:db` is preferred as the final evidence because it performs the
clean reset, existing pgTAP/Data API/function suites, and unconditional
cleanup reset. If Docker/local Supabase is unavailable, report the blocked
backend verification explicitly; do not substitute `yarn test` or the app
Jest suite. Web-only scope means no iOS/Android tooling or validation.

## Exit criteria

Against a clean local Supabase reset, the dedicated real-HTTP acceptance suite
passes and proves all of the following in one mechanically checkable run:

- both confirmed users have all six seeded resources before deletion;
- deleting A removes A's Auth identity and all six physical resource rows,
  while B and all six B rows remain unchanged;
- anonymous, expired, wrong-user, stale, and pre-deletion credentials cannot
  read/mutate/recreate A's data or affect B, with the explicit exception that
  the delete endpoint's already-absent retry is the intentional `204` success;
- old A credentials cannot recreate a row in any of the six resources;
- a discarded successful response followed by retry converges to the same
  empty-A/unchanged-B result without Auth or row recreation;
- `yarn test:db` exits zero and leaves the local database clean via its final
  reset.

## Dependencies and assumptions

- Depends on completed T161.2 and T155.8, as recorded in `TASKS.md`.
- T161.1 remains the baseline for the function URL, request shape, six-table
  fixture vocabulary, and post-cascade observation technique; extend rather
  than rewrite that test.
- The local CLI status output must expose sufficient JWT signing material for a
  deterministic signed-expiry fixture. If it does not, the implementer must
  use the repository-supported local Auth mechanism to obtain an equivalent
  valid expired token or document the limitation as a blocking acceptance gap;
  never downgrade the case to a malformed/unsigned token.
- No migration change is expected. If a real-stack row-recreation probe shows
  a resource can be recreated after Auth deletion, stop and report that as a
  backend defect for a separate implementation decision rather than silently
  weakening this test.
