# T112.5 — Onboarded visitors skip the landing page

## Signal contract (decided by this task)

A query param on the `/` route: `from=app`.

- Param name: `from`
- Value that means "in-app arrival": `app`
- Full-onboarded + `from=app` → landing page renders, no redirect.
- Full-onboarded + no `from` param (or any other value) → redirect to `/app/home`.
- Incomplete onboarding → landing page renders regardless of `from`.

T112.6's "exit to landing" link must navigate with:

```ts
router.push({ pathname: '/', params: { from: 'app' } })
```

T112.4 (already landed, `LandingCta`) is unaffected — it already keys its copy
off `profile.hasCompletedOnboarding` directly, not off this param, and needs
no change.

This contract will be documented in code (see step 1) so a T112.6 implementer
can find it without re-deriving it.

## Files to add/change, in order

### 1. `src/features/landing/state/landing-navigation.ts` (new)

Exports the two literal constants plus a short doc comment describing the
contract (name, value, which route sets it, which route reads it, and that
T112.6 is the not-yet-built consumer that sets it). This is the single
source of truth so T112.5 and (later) T112.6 can't drift on the param name
or value:

```ts
export const LANDING_ARRIVAL_PARAM = 'from';
export const LANDING_ARRIVAL_FROM_APP = 'app';
```

Put this first — everything else imports from it.

### 2. `src/features/landing/state/redirect-onboarded-visitor-home.ts` (new)

Mirrors `src/features/onboarding/state/require-onboarding.ts` exactly in
shape (same `useEffect`/`router.replace` pattern, same "return the boolean
so the caller can bail on render" contract), but inverted and reading the
arrival param:

```ts
import { useLocalSearchParams, useRouter } from 'expo-router';
import { useEffect } from 'react';

import { useUserProfile } from '@/features/profile/state/user-profile-provider';
import { LANDING_ARRIVAL_FROM_APP, LANDING_ARRIVAL_PARAM } from './landing-navigation';

/**
 * Redirects a fresh arrival at `/` straight to `/app/home` when onboarding is
 * already complete. Skipped when the visit carries the in-app "exit to
 * landing" signal (see landing-navigation.ts) so T112.6's link isn't a dead
 * end.
 */
export function useRedirectOnboardedVisitorHome() {
  const profile = useUserProfile();
  const router = useRouter();
  const params = useLocalSearchParams<Record<string, string | string[] | undefined>>();
  const isOnboardingComplete = profile.hasCompletedOnboarding && profile.kenteiRank !== undefined;
  const isInAppArrival = params[LANDING_ARRIVAL_PARAM] === LANDING_ARRIVAL_FROM_APP;
  const shouldRedirect = isOnboardingComplete && !isInAppArrival;

  useEffect(() => {
    if (shouldRedirect) router.replace('/app/home');
  }, [shouldRedirect, router]);

  return shouldRedirect;
}
```

Note: `useLocalSearchParams` returns string | string[] for a param value;
compare with `===` against the literal so an array value (e.g. `?from=app&from=app`)
correctly fails the check rather than needing extra normalization.

### 3. `src/app/index.tsx`

Mirror the exact call-site pattern used in `src/app/app/tricks/index.tsx`
(`isOnboardingComplete = useRequireOnboarding(); ... if (!isOnboardingComplete) return null;`),
inverted:

```tsx
import { LandingPage } from '@/features/landing/components/landing-page';
import { useRedirectOnboardedVisitorHome } from '@/features/landing/state/redirect-onboarded-visitor-home';

export default function RootRoute() {
  const shouldRedirect = useRedirectOnboardedVisitorHome();
  if (shouldRedirect) return null;
  return <LandingPage />;
}
```

Returning `null` while the redirect effect fires avoids a landing-page flash,
consistent with the existing onboarding-guard convention.

## Order rationale

Step 1 before 2 (constants must exist before the hook imports them). Step 2
before 3 (the route imports the hook). Steps 4 and 5 last since they depend
on the implementation shapes above, but write them immediately after each
corresponding implementation file so behavior is verified incrementally
rather than in one big pass at the end.

## Risks / non-obvious things

- `useLocalSearchParams` values can be `string | string[]`; the `===`
  comparison against the literal `'app'` handles this correctly without
  extra code, but don't be tempted to `.includes()` or coerce — that would
  accept malformed multi-value params as a valid signal.
- Do not touch `LandingCta` (T112.4) — it doesn't read or set this param and
  the task notes confirm no coordination is needed there; only T112.6 (future)
  consumes `LANDING_ARRIVAL_PARAM`/`LANDING_ARRIVAL_FROM_APP`.
- The existing `index.test.tsx` mocks are currently static (fixed return
  values). Changing `useUserProfile`'s mock to `jest.fn()` and adding
  `useLocalSearchParams` to the `expo-router` mock touches shared test
  scaffolding used by both the pre-existing tests and the new ones — run the
  full file after the refactor, not just the new tests, to confirm nothing
  regressed silently.
- Keep `Date.now()`/timer concerns irrelevant here — this hook has no timing
  behavior, just a straight boolean derivation, so no reducer/timestamp
  plumbing is needed (unlike Sesh).
