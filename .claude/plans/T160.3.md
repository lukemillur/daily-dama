# T160.3 -- Prove stale revisions and tombstones cannot block or resurrect unrelated data

## Context already in place (do not re-derive)

- `src/shared/sync/sync-envelope.ts` / `conflict.ts`: the FIFO outbox + per-record
  revision cache + `conflicts` array (T157.x/T160.2). `conflictRecorded` replaces
  any existing conflict for the same `domain:recordId` (dedup by key, not
  duplication), `conflictResolved` requires the *current* pending op's
  `operationId` to match the conflict's, so a resolve against a stale conflict
  silently no-ops rather than corrupting state.
- `src/shared/sync/transport.ts`: `pushOutboxOperations` is sequential and never
  aborts the batch on one `'conflict'`/`'failed'` outcome -- this is the actual
  mechanism behind "one conflicting record doesn't block siblings."
- Four domain-local driver hooks already exist and already have solid per-domain
  coverage of the core mechanics: `use-goal-domain-sync.ts`,
  `use-note-domain-sync.ts`, `use-custom-trick-domain-sync.ts`,
  `use-profile-domain-sync.ts` (each with a matching `*.test.tsx`). In
  particular, goals and notes already have, per-domain:
  - "a stale-revision conflict on one X does not block an unrelated X" (direct
    `transport.push(...)` call bypassing the hook to simulate a write the
    local envelope never learned about -- this is the established technique
    for simulating both "another device wrote first" *and* "our own write
    succeeded but the ack was lost," since the sync protocol cannot and does
    not need to tell those two apart).
  - "an edit against a since-tombstoned X parks that X only" (goals/notes only
    -- these two tables use `deleted_at` soft-delete plus a DB trigger that
    makes a tombstoned row's `deleted_at` terminal).
  - "second-browser rehydrate filters out tombstoned entries."
  - One deliberate two-domain cross-check already exists:
    `use-note-domain-sync.test.tsx` -> "a notes conflict does not affect the
    goals domain driver (cross-domain independence)."
  - custom-tricks has its own "stale-revision conflict on one trick does not
    block an unrelated trick" test, but **no tombstone concept**: `custom_tricks`
    uses a real hard `DELETE`, not a `deleted_at` column
    (`custom-trick-sync-transport.ts` has no `deleted_at` anywhere). An edit
    against an already-hard-deleted trick takes a different code path than
    goals/notes: the revision-guarded `UPDATE` matches zero rows (`PGRST116`),
    the adapter re-`SELECT`s to disambiguate stale-revision-vs-gone, finds
    `existing === null`, and returns **`{ status: 'failed', ... }`**, not
    `'conflict'`. No `INSERT` ever happens on this path, so there is no
    resurrection -- but the *shape* of "cannot resurrect" for custom-tricks is
    "surfaces as a retryable failure, never re-creates the row," not "surfaces
    as a UI-resolvable conflict." Write assertions for the exact behavior, not
    the goals/notes shape.
  - Profile has no tombstone concept at all (a user profile is never soft- or
    hard-deleted by this sync machinery) -- do not invent a profile-tombstone
    test.
- `src/shared/sync/sync-coordinator-provider.tsx` aggregates all five domains'
  `pendingCount`/`conflictCount`/`retryableFailureCount`/`conflicts` and exposes
  one `resolveConflict(domain, recordId, choice)` and one `retry()`.
- `src/shared/sync/sync-coordinator.sesh-isolation.test.tsx` is the existing
  "fully wired" harness pattern to copy: it `jest.mock`s each domain's
  `createXSyncTransportAdapter` factory (`mockCreateProfileSyncTransportAdapter`
  etc.) to return an injected fake transport, then mounts all five real
  providers + `SyncCoordinatorProvider` under one `IdentityHandleTestProvider`.
  Reuse this mocking + mounting approach verbatim rather than inventing a new
  wiring strategy.
- Real read/write test surfaces already exist per domain and require no new
  product code: `useGoals()`/`useGoalActions()`, `useNotes()`/`useNoteActions()`,
  `useCustomTricks()`/`useCustomTrickActions()`,
  `useUserProfile()`/`useUserProfileActions()`, plus each domain's `useXSync()`
  (`pendingCount`, `conflicts`, `resolveConflict`, `runSync`) and the coordinator's
  own aggregated equivalents.

This task is test-only. No product code in `src/shared/sync/*`,
`src/features/*/persistence/*-sync-*`, or
`src/features/*/state/use-*-domain-sync.ts` should need to change -- if the
plan below surfaces a real behavioral gap, stop and report it rather than
quietly patching production code as a side effect of writing tests.

## Plan

### 1. Per-domain parity pass (fill gaps only, do not duplicate)

Read all four `use-*-domain-sync.test.tsx` files fully (goals and notes are the
reference shape; profile and custom-tricks are the ones most likely to have a
gap) and confirm each already has, or add if missing:

1. "a stale-revision conflict on one record does not block an unrelated record
   in the same domain" -- profile's version, if missing, should conflict on one
   trick-state row while an unrelated trick-state row and/or the scalar
   profile row still applies.
2. "an edit against a since-tombstoned record is rejected without
   resurrecting it" -- goals and notes already have this; add custom-tricks'
   own version asserting the **`'failed'`/retryable** shape described above
   (not a `SyncConflictRecord`), and assert no row was ever (re)inserted (the
   fake transport should track insert-vs-update calls the way
   `getUpsertCallCount`/`getPushAttemptCount` already do in the goals/notes
   fakes -- extend `use-custom-trick-domain-sync.test.tsx`'s fake transport the
   same way if it doesn't already distinguish insert from update calls).
3. "retrying the same operation after a lost acknowledgement is idempotent" --
   for at least goals and notes (the two with the clearest tombstone/revision
   semantics): drive one successful `runSync`, then call the fake transport's
   `push(...)` directly with the *same* payload the client already sent (this
   models a write whose HTTP response never reached the client -- indistinguishable
   from a concurrent edit from the sync protocol's point of view, which is
   exactly why the existing stale-revision tests already use this technique).
   Assert: (a) the record's server-side revision only advanced by the amount
   the direct call caused (no duplicate row, no double-apply), (b) the next
   `runSync` surfaces exactly one `SyncConflictRecord` for that record (not a
   growing count across repeated `runSync` calls -- call it 2-3 times and
   assert `conflicts.length` for that domain stays stable), (c) an unrelated
   record queued in the same batch still applies.
4. Confirm (via existing tests or a small addition) that resolving one
   domain's conflict with `resolveConflict(recordId, 'local' | 'server')`
   leaves every other pending/conflicting record in that same domain's outbox
   completely untouched -- T160.2 already covers this per T160.2's own
   completion notes; only add a test if a read of the actual file shows a gap.

Do this pass first -- it's the cheapest, most targeted evidence, and doing it
before the cross-domain files below means the cross-domain files can lean on
"per-domain mechanics are already proven" and focus purely on cross-domain
interaction, instead of re-proving single-domain mechanics at higher cost.

### 2. New file: `src/shared/sync/cross-domain-conflict-fault-injection.integration.test.tsx`

Copy the mounting/mocking scaffold from `sync-coordinator.sesh-isolation.test.tsx`
(the `jest.mock` calls for all four `createXSyncTransportAdapter` factories, the
`IdentityHandleTestProvider`, and a `mountHarness` that renders all five
providers + `SyncCoordinatorProvider`). Replace `Sesh` with a small
`ActionsExposer` component that captures `useGoals()`/`useGoalActions()`,
`useNotes()`/`useNoteActions()`, `useCustomTricks()`/`useCustomTrickActions()`,
`useUserProfile()`/`useUserProfileActions()`, and `useSyncCoordinatorStatus()`
into a `captured` ref via a render-time `useEffect`, matching the existing
`makeStatusExposer` pattern.

Cases:

1. **Interleaved valid + conflicting operations across domains, one coordinated
   run.** Seed one record per mutable domain (profile trick-state, one custom
   trick, one goal, one note) via each fake transport's seed rows. Mount, run
   one sync to adopt the seed. Then, in a single batch: edit the seeded goal
   locally (will conflict -- first make the fake goal transport's backing row
   change out from under it via a direct `push(...)` the same way the
   per-domain tests do), and make valid, unrelated edits to the profile
   trick-state, the custom trick, and the note. Call `coordinator.retry()`
   once. Assert: aggregated `conflictCount === 1` and `conflicts` names the
   goal record; aggregated `pendingCount === 0` for every other domain (their
   edits pushed and were acknowledged); each domain's own collection read
   (`useGoals()` etc.) shows the three valid edits applied and the goal
   collection still showing the *local* (not yet resolved) value.
2. **Resolving the one conflict doesn't disturb siblings.** Continuing from
   case 1 (or a fresh equivalent setup), call the coordinator's
   `resolveConflict('goals', goalId, 'local')`. Assert the goals conflict
   clears, the other three domains' `conflicts`/`pendingCount` are bit-for-bit
   unchanged from immediately before the call, and a follow-up
   `coordinator.retry()` completes with `pendingCount === 0`,
   `conflictCount === 0`, and `syncStatus` reporting fully synced.
3. **Tombstone-vs-edit race interleaved with valid cross-domain operations.**
   Tombstone a note server-side (direct fake-transport `push` with
   `operationType: 'delete'`), queue a stale local edit against that same
   note, and simultaneously make valid edits in the other three domains in
   the same run. Assert only the note's operation is parked (as `'failed'`
   retryable per the note/goal tombstone shape -- confirm the actual
   `failureKind` the real driver sets for this case by reading
   `use-note-domain-sync.ts` before asserting it), the note's body is not
   resurrected in `useNotes()`'s collection, and the other three domains
   fully apply.

### 3. New file: `src/shared/sync/two-browser-convergence.integration.test.tsx`

Same scaffold, but mount the full provider tree **twice** -- `BrowserA` and
`BrowserB` -- as two sibling `mountHarness()` calls in the same test, each with
its own `IdentityHandleTestProvider`/`SyncCoordinatorProvider`/etc., but with
`mockCreateXSyncTransportAdapter.mockReturnValue(sharedFakeTransport)` set
**once** per domain before mounting either browser, so both browser trees'
providers resolve to the exact same fake-transport instance/backing `Map` --
i.e. one simulated cloud, two independent local clients. This is the piece
that doesn't exist anywhere yet: every current "second-browser" test is a
single fresh envelope pulling a static seeded fixture, not two live browsers
mutating concurrently and converging.

Sequence (one test, since the whole point is one continuous story; split into
more than one `it()` only if a genuine natural checkpoint makes failures
easier to localize):

1. Mount Browser A only. Create one record in each of the four mutable
   domains via its `useXActions()`. Run A's `coordinator.retry()`. Assert push
   succeeded (via each fake transport's row map).
2. Mount Browser B. Run B's `coordinator.retry()` (pull-adopt, empty outbox).
   Assert B's four collections (`useGoals()` etc.) are `toEqual` A's four
   collections exactly -- the actual "two browser fixtures on identical domain
   state" baseline.
3. Concurrent conflicting + valid edits, no sync yet on either side: on A,
   edit the shared goal (say, `targetCount`) and create a brand-new, entirely
   separate note. On B, edit that *same* goal differently, and create a
   brand-new, entirely separate custom trick.
4. Sync A first (`A.coordinator.retry()`): its goal edit and new note push
   cleanly (A was still at the revision it pulled).
5. Sync B (`B.coordinator.retry()`): B's goal edit now conflicts (stale
   revision against A's just-applied write) -- assert `B` sees exactly one
   conflict for that goal -- while B's new custom trick still pushes
   successfully (unrelated record, unrelated domain).
6. Resolve B's conflict with `B.coordinator.resolveConflict('goals', goalId,
   'server')` (adopt A's value -- pick `'server'` here specifically, since
   `'local'` is already the well-trodden path in the per-domain tests, and
   this suite should exercise the less-covered "keep-server, discard local"
   branch at least once at the cross-domain level). Sync B again.
7. Sync A once more (`A.coordinator.retry()`) so it pulls B's new custom trick
   and observes B's other side effects -- make sure each side's pull-adopt is
   exercised for the field it *didn't* author (A pulls B's custom trick; B
   pulls A's note).
8. Final assertion: `A`'s and `B`'s `useGoals()`, `useNotes()`,
   `useCustomTricks()`, and `useUserProfile()` reads (if profile was touched)
   are `toEqual` each other exactly -- the goal shows A's value everywhere (B
   deferred to server), both new records (A's note, B's custom trick) are
   present on both sides, and neither side has any remaining
   pending/conflicting operations.
9. Idempotency/lost-ack fold-in: before the final round in step 7, issue one
   more direct fake-transport `push` against the shared note backing store
   representing a third write whose ack reached no browser (e.g. bump the
   note's `updated_at`/content once more out-of-band). Run each browser's
   sync twice in a row without any new local edit in between. Assert neither
   run duplicates a conflict entry, neither run re-sends an already-applied
   operation as a new server write (row `revision` only advances by the
   direct out-of-band push's own single increment), and both browsers still
   converge to the same final content for that note once resolved/pulled.

## Risks / non-obvious traps for the implementer

- **Don't assume custom-tricks conflicts look like goals/notes conflicts.**
  The hard-delete-vs-soft-delete difference means a "resurrection attempt"
  against a deleted custom trick is a `'failed'` push outcome, not a
  `SyncConflictRecord`. Read `use-custom-trick-domain-sync.ts`'s actual
  handling of a `'failed'` `PGRST116`-then-`existing === null` outcome before
  writing the assertion, rather than copy-pasting the goals/notes tombstone
  test's shape.
- **`mockReturnValue` vs `mockImplementation` for the two-browser file.** Both
  browser trees must resolve to literally the same transport object (shared
  closure state/backing `Map`) -- using `mockReturnValueOnce` per mount, or
  constructing a fresh fake transport per `mountHarness()` call, would
  silently give each browser its own isolated "cloud" and every convergence
  assertion would pass for the wrong reason (no real interaction happened).
  Construct each domain's shared fake transport exactly once per test, before
  either `mountHarness()` call.
- **Identity/generation plumbing.** Both browsers need their own
  `IdentityHandleTestProvider` instance (separate React trees, separate
  `createIdentityContext` calls) even though they share the same `USER_ID` --
  don't try to share one identity context object across both trees, since
  `useIdentityScopedDomain`'s generation-guard logic is keyed to the context
  instance, not just the identity value.
- **`act()` sequencing across two trees.** Driving both browsers' actions and
  `retry()` calls needs each awaited/flushed independently (same `flush()`
  helper the sesh-isolation file already defines) before reading either
  side's state -- interleaving without flushing risks assertions racing
  in-flight promises rather than reflecting settled state.
- **`resolveConflict`'s identity/generation/operationId guard.** Per
  `use-goal-domain-sync.ts`'s `resolveConflict`, a resolve silently no-ops if
  the conflict's `operationId` no longer matches the outbox's current
  operation for that record. If a test's timeline lets a second local edit
  slip in before the resolve call, the resolve will appear to do nothing --
  order operations carefully and assert `resolveConflict`'s effect
  immediately after establishing the conflict, not after further unrelated
  local mutations in the same domain.
- Keep this task test-only. If any of the above investigation turns up an
  actual behavioral bug (e.g. a genuine resurrection path, or a duplicate
  conflict entry across retries), stop and report it rather than silently
  fixing production code -- that would be a scope expansion beyond "prove," and
  the fix belongs in its own reviewable change.
