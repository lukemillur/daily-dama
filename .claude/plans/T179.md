# T179 -- Require current-password confirmation before changing email

## Context confirmed in current code

- `AuthActions.changeEmail` in `src/features/auth/state/auth-provider.tsx` is `(newEmail: string) => Promise<{ error: AuthError | null }>`. Its only caller is `account-security-screen.tsx`'s `handleEmailSubmit`.
- `changePassword` in the same file already implements the exact verification pattern this task should reuse: guard `stateRef.current.status !== 'authenticated'` -> `session_not_found`; read `stateRef.current.session.user.email`; call `client.auth.signInWithPassword({ email, password: currentPassword })` and return its error immediately if present; only then call the real mutation (`updateUser`). The code comment above it explains why re-sign-in is used instead of GoTrue's `reauthenticate()`/secure_password_change -- reference that comment rather than duplicating it.
- `account-security-screen.tsx` has two independent forms in one screen (Change password, Change email), each with its own submit handler, in-flight ref-guard, and error-category-to-copy map (`PASSWORD_ERROR_COPY`, `EMAIL_ERROR_COPY`). `EMAIL_ERROR_COPY.invalidCredentials` currently maps to the generic `'Something went wrong. Please try again.'` -- this must become the specific `'Your current password is incorrect.'` message once a current password exists in this form.
- `PasswordInput` (`password-input.tsx`) ties its `label` prop directly to both the visible field label and the `accessibilityLabel` on the input/toggle (no separate override prop exists today). The password-change form already renders a field with `label="Current password"` / `accessibilityLabel="Current password"`. Reusing that exact label for the new email-form field would create two nodes with the same `accessibilityLabel` on screen at once, which breaks `renderer.root.find(...)`-based test helpers (`find` throws on 0 or >1 matches) and is a genuine a11y ambiguity too. Use a different label for the new field -- `label="Password"` under the "Change email" section heading -- rather than adding a prop to `PasswordInput`. This is the smallest change; do not extend `PasswordInput` for this ticket.
- No other call sites of `changeEmail` exist besides the two files above (confirmed via repo-wide grep).

## Implementation order

1. **`src/features/auth/state/auth-provider.tsx` -- change `changeEmail`'s signature and behavior first** (everything else depends on this contract).
   - Update the `AuthActions` interface: `changeEmail: (newEmail: string, currentPassword: string) => Promise<{ error: AuthError | null }>`.
   - In the `changeEmail` callback, after the existing `authenticated` guard, `client` guard, and `window` guard (keep the authenticated check first so unauthenticated calls short-circuit before touching the client, matching `changePassword`'s ordering), read `stateRef.current.session.user.email` the same defensive way `changePassword` does (return a `session_not_found` `AuthError` if it's missing -- email/password-only app, defensive only).
   - Call `client.auth.signInWithPassword({ email, password: currentPassword })` before the existing `updateUser({ email: newEmail }, { emailRedirectTo })` call. If `signInError`, return `{ error: signInError }` immediately without calling `updateUser`.
   - Add a short comment cross-referencing `changePassword`'s existing rationale comment instead of repeating it (e.g. "Same current-password re-sign-in verification as `changePassword` above; see its comment for why.").
   - Do not touch `changePassword`, `deleteAccount`, or any other action.

2. **`src/features/auth/state/__tests__/auth-provider.test.tsx` -- update to the new contract and add coverage.**
   - Update the three existing `changeEmail` calls (`rejects with session_not_found`, `calls updateUser with the new email...`, `forwards a failure error from updateUser`) to pass a current-password argument, e.g. `captured.actions!.changeEmail('new@example.com', 'old-password')`.
   - In `'changeEmail rejects with session_not_found...'`, also assert `fake.signInWithPassword` was not called (mirrors the equivalent `changePassword` unauthenticated test).
   - In `'changeEmail calls updateUser with the new email...'`, assert `fake.signInWithPassword` was called with `{ email: 'person@example.com', password: 'old-password' }` before `updateUser`, and that `updateUser` is still called with exactly `{ email: 'new@example.com' }` and the same `emailRedirectTo` as today.
   - In `'changeEmail forwards a failure error from updateUser'`, assert `fake.signInWithPassword` was called exactly once (sign-in succeeded, `updateUser` is what failed) -- mirrors `'changePassword surfaces an offline error from the updateUser step...'`.
   - Add three new tests directly parallel to the existing `changePassword` ones:

   - Update `EMAIL_ERROR_COPY.invalidCredentials` from `'Something went wrong. Please try again.'` to `'Your current password is incorrect.'`.

     Use `label="Password"` specifically (not `"Current password"`) to avoid an `accessibilityLabel` collision with the password-change form's own "Current password" field -- both forms are visible in the DOM simultaneously.

## Risks / things to double check while implementing

- Don't let the new `emailCurrentPassword` field bleed into `trackAuthEvent` calls -- the existing `account_security_email_error` / `account_security_email_requested` events pass only a category string today; keep it that way.
- The `emailErrors`/`emailCurrentPasswordError` derivations are computed from render state independent of which `return` inside `handleEmailSubmit` fired first, so don't over-think blocking-check order for correctness -- only one early-return is needed per submit, and both error messages will still render correctly since both error-derivation expressions read `emailHasSubmitted` plus the current field value on every render, not a per-check flag.
- Keep the password re-sign-in call scoped to `changeEmail` only -- do not touch `changePassword` or `deleteAccount`, and do not add a shared "verifyCurrentPassword" helper for this ticket; `changePassword` already has its own inline copy of this same three-line pattern, so a shared extraction is a legitimate future cleanup but out of scope here.
