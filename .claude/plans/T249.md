# T249 -- Diagnose and fix the new-account welcome overlay not appearing

## Root cause (found by code inspection, to be confirmed by runtime reproduction in step 1)

`src/app/_layout.tsx` is the app's single root layout (above both the `auth/_layout.tsx` and `app/_layout.tsx` route groups) and therefore mounts exactly once per browser page load and never remounts on in-app navigation -- `<Slot />` just swaps out the group subtree beneath it.

`showNewAccountWelcome` is initialized with a lazy `useState` initializer that reads `useGlobalSearchParams()` only at that one mount:

```ts
const [showNewAccountWelcome, setShowNewAccountWelcome] = useState(
  () => firstStringOrUndefined(params.newAccount) === '1',
);
```

The real signup round trip is:

1. User clicks the email confirmation link -> full browser page load lands on `/auth/callback?code=...`. The root layout mounts here, with no `newAccount` param present, so the lazy initializer captures `false`.
2. `auth-callback-screen.tsx` exchanges the code, then calls `router.replace({ pathname: '/app/home', params: { newAccount: '1' } })`. On Expo Router web (static export) this is a client-side navigation (History API), not a full page reload -- the already-mounted root layout is not remounted.
3. The only effect that reacts to `params` changing afterward is the strip effect, which only calls `router.replace(pathname)` to remove the param from the URL -- it never sets `showNewAccountWelcome`. So the overlay never shows, and the param is silently stripped a moment later as if it had never mattered.

This matches T208's own verification method exactly: `TASKS_DONE.md`'s T208 entry and `root-layout.test.tsx` both test by mounting `TabLayout` with `newAccount=1` already present at mount time (a direct navigation to `/app/home?newAccount=1`), which is a different, easier case than the real callback-screen redirect chain. No existing test exercises "root layout mounts with no param, then params change post-mount" -- that gap is why this shipped green and still looks correct on static inspection.

T227 (rewrite/hosting layer) is very likely not the cause: `/app/home` is a static route (`app/home.html` in the export) with no `vercel.json` rewrite entry, and the transition into it from `/auth/callback` is a client-side SPA replace, not a hard navigation that would hit Vercel's rewrite rules. Confirm this in step 1 rather than assuming it, but do not spend time hardening the rewrite layer unless reproduction actually implicates it.

## Step 2 -- Fix: `src/app/_layout.tsx`

Make the strip effect also set `showNewAccountWelcome`, so a `newAccount=1` transition arriving after mount (the real-world case) is picked up, not just one present at mount (the only case currently handled):

```ts
const [showNewAccountWelcome, setShowNewAccountWelcome] = useState(
  () => firstStringOrUndefined(params.newAccount) === '1',
);
const hasHandledNewAccountParamRef = useRef(false);

useEffect(() => {
  if (hasHandledNewAccountParamRef.current) return;
  if (firstStringOrUndefined(params.newAccount) !== '1') return;
  hasHandledNewAccountParamRef.current = true;
  setShowNewAccountWelcome(true);
  router.replace(pathname as Href);
  // eslint-disable-next-line react-hooks/exhaustive-deps -- one-shot handle, guarded by the ref.
}, [params]);
```

Notes on this change:

- Keep the lazy initializer. It still matters for a hypothetical direct navigation to `/app/home?newAccount=1` (param present at the very first render): the overlay shows synchronously with no pop-in frame, exactly as T208 intended for that case.
- The effect's `setShowNewAccountWelcome(true)` is a no-op re-render when the initializer already set it `true` (same case, both fire, second is idempotent) -- this does not double-show or double-fire anything, because `hasHandledNewAccountParamRef` still guards a single strip/handle regardless of which path set the boolean.
- For the real-world case (param arrives after mount via the callback screen's `router.replace`), this necessarily costs one extra render after the param change before the overlay appears (Home's Slot content can paint for a frame first) -- this is an unavoidable consequence of Expo Router web using client-side history navigation rather than a full reload between `/auth/callback` and `/app/home`, not a regression to guard against. Do not attempt to eliminate it by adding a full-page reload or altering the callback screen's own navigation approach -- that would be a materially larger, unrequested change to the auth flow for a one-frame cosmetic concern.
- Rename `hasStrippedNewAccountParamRef` to `hasHandledNewAccountParamRef` (or similar) to reflect that it now guards "detected and handled" rather than only "stripped" -- small, but avoids a misleading name given it's now the single gate for both the state flip and the URL strip.
- Update the header comment block above `GlobalSearchParams` (currently describes only the "read once on mount" behavior) to describe the corrected two-path behavior (mount-time synchronous case + post-mount effect-driven case), so a future reader doesn't reintroduce this exact regression by "simplifying" back to a pure lazy initializer.
