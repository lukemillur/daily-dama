# T153.10 — Build the forgot-password request flow

## Scope split (read first)

The exit criteria have two parts with very different achievability in this sandbox:

1. **Achievable now, via mocked Jest tests** (matches the T153.6/T153.7/T153.9 precedent): the
   `/auth/forgot-password` route itself, its enumeration-safe generic response, loading/validation/
   offline/throttled/resend states, and the same-browser/device PKCE-limitation copy. All of this
   is pure frontend logic against a mocked Supabase client, exactly like every other T153.x screen
   merged so far.
2. **Not achievable here**: "a local same-browser Mailpit walkthrough" that exchanges a real PKCE
   code end to end. This requires T153.1's local Supabase/Mailpit stack, which requires Docker.
   Docker was re-checked fresh in this session (`which docker` → not found, no `Docker.app`
   installed) — it is genuinely unavailable in this sandbox, not just assumed unavailable from a
   stale finding.

**Do not silently skip or claim this criterion as passed.** When implementation is done, run the
full local verification sequence (`node .claude/scripts/verify.mjs`), and explicitly report the
Mailpit walkthrough as blocked/not-run pending a Docker-capable environment, rather than merging
with an unqualified "exit criteria met" claim. If a Docker-capable environment ever becomes
available before merge, re-check `docker ps`/`docker info` fresh and actually run the walkthrough
instead of assuming this still holds.

## Current state (confirmed by reading the code)

  `passwordRecovery`), `model/auth-errors.ts` (closed `AuthErrorCategory` enum +
  `categorizeAuthError`), `model/redact.ts` / `observability/auth-observability.ts` (the one
  logging/analytics boundary), `state/auth-provider.tsx` (context + actions:
  `signInWithPassword`, `signOut`, `completePasswordRecovery`, `exchangeCodeForSession`),
  `components/{sign-in-screen,reset-password-screen,auth-callback-screen}.tsx`, and routes at
  `src/app/auth/{sign-in,reset-password,callback}.tsx`.
- `src/app/auth/forgot-password.tsx` does not exist yet. `T153.8` (signup) is **Not started**, so
  there is no sign-up screen to integrate with — forgot-password only needs to interoperate with
  sign-in, callback, and reset-password, all of which exist.
- `getSupabaseClient()` in `persistence/supabase-client.ts` is web-only (`Platform.OS !== 'web'` →
  `null`), memoized, PKCE flow, `detectSessionInUrl: false`. No existing code builds a `redirectTo`
  URL anywhere yet — this task introduces that.
- Confirmed via Supabase docs: `resetPasswordForEmail()` is deliberately enumeration-safe by
  design — it returns `{ error: null }` for both existing and non-existing addresses (Supabase
  auth won't email an unknown address, but does not surface that to the caller). This is a
  meaningful simplification: unlike sign-in (which must collapse `invalid_credentials` /
  `user_not_found` in `categorizeAuthError`), the forgot-password success path needs **no new
  enumeration-defense logic** — the SDK already hands back one deterministic outcome. The only
  error paths this endpoint can realistically surface are transport/network failure (offline),
  Supabase's send-rate limiting (`over_email_send_rate_limit` → `rateLimited`), and malformed
  input (caught client-side before any network call).

## Design decision requiring explicit sign-off: split `expiredOrInvalidLink` → add `missingVerifier`

The task's Notes require: *"Supabase's same-browser/device PKCE verifier limitation must be
explained in the recovery guidance and missing-verifier error."* Today, `auth-errors.ts` collapses
`bad_code_verifier` and `flow_state_not_found` into the same `expiredOrInvalidLink` category as
plain expiry codes (`otp_expired`, `session_expired`, `flow_state_expired`, ...). That's a
different failure mode with different actionable guidance ("this link timed out, request a new
one" vs. "you opened this on a different browser/device than the one you started from — Supabase's
PKCE verifier only exists in that one browser's storage").

**Plan: add a new `missingVerifier` category to the closed `AuthErrorCategory` enum**, and move
only `bad_code_verifier` and `flow_state_not_found` into a new `MISSING_VERIFIER_CODES` set (leave
`otp_expired`, `session_not_found`, `session_expired`, `flow_state_expired`, `bad_oauth_callback`,
`bad_oauth_state` in `expiredOrInvalidLink` — verified none of the moved codes are covered by
today's `auth-errors.test.ts` assertions, so this is a safe, isolated recategorization, not a
behavior change to anything already tested).

This is a deliberate, non-trivial change to a shared model file three already-merged screens
depend on (`sign-in-screen.tsx`, `reset-password-screen.tsx`, `auth-callback-screen.tsx` all define
`Record<AuthErrorCategory, string>` copy maps). TypeScript's exhaustiveness checking on those
`Record` types means **every one of those three files needs a new `missingVerifier` entry added or
`tsc` fails** — this is the intended enforcement mechanism per the comment at the top of
`auth-errors.ts` ("closed set... UI is allowed to branch on"), not an accident to work around.

Alternative rejected: keep everything collapsed into `expiredOrInvalidLink` and just special-case
the copy string inline at the one call site that needs it. Rejected because the model's whole
point is that categorization — not ad hoc per-screen conditionals — drives copy, and the moved
codes' meaning really is distinct from plain expiry.

## Files to change, in order

1. **`src/features/auth/model/auth-errors.ts`**
   - Add `'missingVerifier'` to `AuthErrorCategory`.
   - Add `const MISSING_VERIFIER_CODES = new Set(['bad_code_verifier', 'flow_state_not_found'])`.
   - Remove those two codes from `EXPIRED_OR_INVALID_LINK_CODES`.
   - Add a branch in `categorizeAuthError` checking `MISSING_VERIFIER_CODES` (order doesn't matter
     relative to the expiry check since the sets are now disjoint, but keep it grouped near the
     expiry check for readability).

2. **`src/features/auth/model/auth-test-fixtures.ts`** and
   **`src/features/auth/model/__tests__/auth-errors.test.ts`**

   - Add both to `expectedCategoryByCode` mapping to `'missingVerifier'`.
   - Do this before touching any screen, so `categorizeAuthError`'s new behavior is locked in by a
     passing unit test before dependent UI copy is written against it.

3. **Fix the three existing screens' now-non-exhaustive `Record<AuthErrorCategory, string>` maps**
   (do this before writing the new screen, since `tsc --noEmit` will otherwise fail across the
   whole change and mask new-code errors):
   - `src/features/auth/components/auth-callback-screen.tsx` — this is the one place a missing
     verifier is actually surfaced to a user (recovery or, later, signup confirmation). Give it the
     specific, actionable copy, e.g.: *"This link only works in the browser and device you
     requested it from. Open your email there, or go back and request a new link from that same
     browser."* This is the one required "missing-verifier error" surface from the task Notes.
   - `src/features/auth/components/sign-in-screen.tsx` and
     `src/features/auth/components/reset-password-screen.tsx` — this category can't realistically
     occur at these two call sites (sign-in doesn't exchange a PKCE code; reset-password only runs
     once a `passwordRecovery` session already exists). Fill with the same generic fallback string
     already used for other inapplicable categories at each site (`'Something went wrong. Please
     try again.'`) — do not invent a new sentence with no real trigger path.
   - Update `src/features/auth/components/__tests__/auth-callback-screen.test.tsx` if it has any
     exhaustive-copy assertion depending on enumerating all categories (check before assuming none
     do — skim the file for a loop over `Object.keys` or similar before concluding no update is
     needed).

4. **`src/features/auth/state/auth-provider.tsx`** — add the `requestPasswordReset` action.
   - Add to the `AuthActions` interface:
     ```ts
     readonly requestPasswordReset: (email: string) => Promise<{ error: AuthError | null }>;
     ```
   - Implementation:
     ```ts
     const requestPasswordReset = useCallback(async (email: string) => {
       const client = getSupabaseClient();
       if (!client) return { error: new AuthError('Supabase is not configured.') };

       if (typeof window === 'undefined') {
         return { error: new AuthError('Unable to resolve the callback URL.') };
       }

       const redirectTo = `${window.location.origin}/auth/callback`;
       const { error } = await client.auth.resetPasswordForEmail(email, { redirectTo });
       return { error };
     }, []);
     ```
   - Add `requestPasswordReset` to the `actions` `useMemo` (both the object and its dep array).
   - **Why hardcode `/auth/callback` off `window.location.origin` rather than accept any
     destination**: this is exactly the task's "exact callback initiation... without putting an
     email or destination URL into route parameters" requirement, and mirrors
     `BACKEND_ROADMAP.md`'s "do not permit wildcard production redirects or accept arbitrary `next`
     URLs." `window.location.origin` is not attacker-influenceable the way a query param would be,
     and Supabase's own server-side redirect allowlist (T153.2) is the second layer of defense.
   - **Test** in `src/features/auth/state/__tests__/auth-provider.test.tsx`: add a
     `resetPasswordForEmail` jest mock to `createFakeClient()` (mirror `signInWithPassword`'s
     shape), then add cases modeled on the existing `signInWithPassword`/`exchangeCodeForSession`
     tests:
     - forwards `email` and a `redirectTo` ending in `/auth/callback` (stub
       `globalThis.window = { location: { origin: 'https://dailydama.com' } }` before the call and
       clean it up after — copy the exact stub/cleanup pattern already used in
       `auth-callback-screen.test.tsx` lines ~82–96, don't reinvent it).
     - forwards a `null` error on success.
     - forwards a non-null error (e.g. rate-limited) without mutating `AuthState`.

5. **New file `src/features/auth/model/forgot-password-validation.ts`** — pure, synchronous,
   mirrors `sign-in-validation.ts`'s shape and its "never infer an account-specific fact" comment:
   ```ts
   export interface ForgotPasswordFieldErrors { readonly email?: string }
   export type ForgotPasswordValidation =
     | { readonly status: 'valid' }
     | { readonly status: 'invalid'; readonly errors: ForgotPasswordFieldErrors };
   export function validateForgotPasswordEmail(email: string): ForgotPasswordValidation { ... }
   ```
   Reuse the same `EMAIL_SHAPE_PATTERN` regex as `sign-in-validation.ts` (kept as a second small
   duplicate file rather than a shared helper, consistent with the existing convention of one
   small file per flow — `sign-in-validation.ts` and `password-policy.ts` are already separate).
   Add `src/features/auth/model/__tests__/forgot-password-validation.test.ts` mirroring
   `sign-in-validation.test.ts`.

6. **New file `src/features/auth/components/forgot-password-screen.tsx`** — model directly on
   `reset-password-screen.tsx`'s structure (styled-components, `Screen`/`Button`/typography
   imports, the `FormScroll`/`FormContent`/`Field`/`ErrorText` styled blocks — copy them verbatim
   rather than reinventing layout).
   - `useAuthState()` — if `status === 'authenticated'`, redirect to `/app/home` via a `useEffect`
     (same pattern as `sign-in-screen.tsx`'s redirect-when-authenticated effect). A signed-in user
     has no reason to be on this screen.
   - Local state: `email`, `hasSubmitted`, `isSubmitting` + `isSubmittingRef` (same-tick guard,
     copied from `sign-in-screen.tsx`), `submitCategory`, and `requested: boolean` (whether the
     generic "check your email" confirmation is showing).
   - **Submit flow**:
     1. Client-side `validateForgotPasswordEmail` — invalid shows a field error, no network call,
        no state change to `requested`. (Empty/malformed-shape rejection happens identically
        regardless of whether any account uses that address, so it cannot leak existence.)
     2. Call `requestPasswordReset(email.trim())`.
     3. `error === null` → set `requested = true`, `submitCategory = undefined`. Render the fixed
        generic copy: *"If an account exists for that email, we've sent a link to reset the
        password."* — literally the same sentence regardless of the email entered; do not
        conditionally alter this copy on anything about the submitted value.
     4. `error !== null` → `categorizeAuthError(error)`:
        - `offline` → keep the form visible (do **not** set `requested`), inline copy: "You're
          offline. Check your connection and try again." (matches
          `reset-password-screen.tsx`'s offline-keeps-form behavior).
        - `rateLimited` → keep the form visible, inline copy: "Too many attempts. Wait a moment
          and try again." Rate limiting here is safe to surface distinctly (it does not depend on
          account existence — it's a per-address/per-IP send-rate limit that fires identically for
          real and nonexistent addresses), so this does not reopen enumeration.
        - Every other category (`missingVerifier`, `weakPassword`, `invalidCredentials`,
          `unverifiedEmail`, `accountAlreadyExists`, `unknown`) — none of these are realistically
          returned by `resetPasswordForEmail`, but the `Record<AuthErrorCategory, string>` copy map
          must still be exhaustive for `tsc`. Fill with the same generic
          `'Something went wrong. Please try again.'` fallback used elsewhere.
   - **Resend**: once `requested` is true, show a "Resend" button that re-invokes the identical
     submit flow with the same in-memory `email` (never place it in a route param, query string, or
     `router.push` call — it only ever lives in this component's local `useState`). Guard resend
     with the same `isSubmittingRef` used for the initial submit so a rapid double-click can't fire
     two requests — this is the "repeat submissions are deterministic" exit criterion; do not add a
     separate client-side cooldown timer on top of that guard (Supabase's own
     `over_email_send_rate_limit` already provides the throttling signal; inventing a parallel
     client-side timer would duplicate that with no clear product upside — flag this as the
     "good enough for this iteration" boundary, not a deferred gap).
   - **Same-browser/device PKCE guidance** ("recovery guidance" half of the task's Notes): render
     this as static copy on *both* the initial form and the post-submit confirmation, e.g.: "Open
     the email on this same browser, on this device, to finish resetting your password." This is
     independent of, and in addition to, the `missingVerifier` copy added to
     `auth-callback-screen.tsx` in step 3 — the Notes call for it in both places.
   - Optional observability parity (recommended, low-risk, matches every other Auth screen's
     convention): `trackAuthEvent('forgot_password_requested')` on success and
     `trackAuthEvent('forgot_password_error', category)` on failure — never call
     `logAuthWarning`/`trackAuthEvent` with the raw email; only the closed category, matching every
     existing screen.
   - Add a "Back to sign in" `Button` (`variant="secondary"`) navigating via
     `router.push('/auth/sign-in')` — small nearby affordance so the route isn't a dead end; not
     itself part of the exit criteria.

## Risks / non-obvious things for the implementer

- The `missingVerifier` category split touches three already-merged, tested files. Do steps 1–3
  fully (including their tests) before starting the new screen, or `tsc --noEmit` will fail in a
  way that's hard to distinguish from a mistake in the new code.
- `window.location.origin` is only safe to read from inside `requestPasswordReset` because it's
  only ever invoked from a button handler in a mounted web screen — never call it at module scope
  or in a render body (same constraint `supabase-client.ts` already documents for
  `getSupabaseClient`).
- Do not let `resetPasswordForEmail`'s uniform-success behavior tempt you into adding a fake
  artificial delay or any other enumeration-defense trick on top of it — the SDK already solves
  this problem; extra cleverness here would be unnecessary complexity with no defensive value.
- Keep `requested` (confirmation-shown) state and the submitted `email` in the screen's local
  `useState` only. Do not thread email through `useLocalSearchParams`, `router.push` query params,
  or any global/persisted state — that's the literal thing the task's Notes and
  `BACKEND_ROADMAP.md` prohibit.
