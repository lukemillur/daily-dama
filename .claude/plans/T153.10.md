this branch (see 629b7ab, and the prior plan file git history at 30d7f59). The only
remaining exit-criteria clause is: a local same-browser Mailpit walkthrough requests recovery,

This plan is a verification plan, not an implementation plan - no application code should need to
change to satisfy the remaining clause. If the walkthrough surfaces an actual bug, fix it narrowly
and re-run the walkthrough; do not restructure the already-merged screens.

## Step 1 - Bring up the local Supabase/Mailpit stack

From the repo root (per supabase/README.md, merged in by Step 0):

  npx --yes supabase@2.115.0 start
  npx --yes supabase@2.115.0 db reset
  npx --yes supabase@2.115.0 status

Copy the printed API URL (http://127.0.0.1:54321), anon key, and note the Mailpit URL
(http://127.0.0.1:54324) and Studio URL from status's output. Do not commit any of this -
supabase/README.md already says never to commit the output of status.

## Step 2 - Point the app at the local stack

Create .env at the repo root (already gitignored, confirmed via .gitignore lines .env and
.env*.local - do not use .env.example, which is tracked):

  EXPO_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321
  EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY=(anon key from supabase status)

Note the local stack has no custom recovery-email template configured (only the T153.1
confirmation template was made repository-owned) - the recovery email in Mailpit will show
Supabase's generic default "Reset Password" copy. That is expected and out of scope here; only
the redirect_to target and the app-side flow matter for this exit criterion.

## Step 3 - Create a pre-verified test account

There is no sign-up UI on this branch (T153.8 is Not started). Forgot-password requires an
existing, email-confirmed account, so create one directly against the local GoTrue admin API
using the service_role key from supabase status (not the anon key - admin endpoints require it):

  curl -i -X POST 'http://127.0.0.1:54321/auth/v1/admin/users' \
    -H "apikey: SERVICE_ROLE_KEY" \
    -H "Authorization: Bearer SERVICE_ROLE_KEY" \
    -H "Content-Type: application/json" \
    -d '{"email": "recovery-walkthrough@example.com", "password": "originalPassword1", "email_confirm": true}'

Expect a 200 with the created user's id. This sidesteps needing to click a confirmation email
first - the account is pre-verified, so the walkthrough starts directly at forgot-password. (This
account is scoped to the recovery walkthrough only; do not reuse the T153.1 README's
test@example.com fixture from an earlier run in the same reset database, to avoid an
already-unconfirmed duplicate colliding with email_confirm.)

## Step 4 - Start the web app on the fixed port

Per supabase/README.md and AGENTS.md: use the fixed port, not an arbitrary fallback, because the
PKCE verifier and redirect origin must match http://localhost:8081 exactly (browsers treat
localhost and 127.0.0.1 as different storage/PKCE origins - use localhost here, matching site_url
in supabase/config.toml).

  yarn web --port 8081

Open http://localhost:8081/auth/forgot-password in a normal (non-incognito) browser window - same
browser profile used for every remaining step, since Supabase's PKCE code verifier is written to
that browser's storage and can only be redeemed there.

## Step 5 - Drive the walkthrough and check each exit-criteria sub-clause

1. Request recovery. Submit recovery-walkthrough@example.com on /auth/forgot-password.
   - Confirm the generic confirmation copy ("If an account exists for that email, we've sent a
     link...") renders - same copy regardless of whether the address is known, per the already-
     merged unit tests; this step just confirms the live network call actually completes and does
     not crash against a real backend.
   - Open browser DevTools Network tab while submitting. Confirm the outgoing recovery request
     body/URL is the only place the email appears - expected, since Supabase's own API requires
     it - and that no application-owned log line or Analytics call includes it (see the no-leaks
     checklist below).
2. Open the email in Mailpit, same browser, http://127.0.0.1:54324. Confirm the recovery link's
   redirect_to/destination is http://localhost:8081/auth/callback (check the link's query
   parameters before clicking - this is the exact-callback-initiation part of the exit criteria).
3. Click the recovery link (in the same browser window/profile it was requested from).
   - Confirm the app lands on /auth/callback, briefly shows "Finishing sign-in...", and is then
     auto-redirected to /auth/reset-password (not /app/home - the callback screen's
     redirectType === 'recovery' branch is what should route here; landing on /app/home instead
     is a real bug, stop and investigate rather than continuing the walkthrough).
   - Check the address bar right after landing on /auth/reset-password: it should carry no code,
     access_token, or other Supabase param - auth-callback-screen.tsx calls router.replace (not
     push), so the ?code=... URL should not persist in the bar or in browser history once the
     replace happens. A transient ?code=... on /auth/callback itself, immediately before the
     replace, is expected and not a failure.
   - Reload /auth/reset-password before submitting anything, then check the URL again - confirm
     the recovery session persists (Supabase's own session storage, not a URL param) and the form
     is still usable; this proves the code is not being smuggled through the URL to survive a
     reload.
4. Change the password. Submit a new password (10+ characters) on /auth/reset-password. Confirm
   the "Your password has been updated" success screen renders.
5. Exercise the "exchanges the PKCE code once" clause. Re-navigate to the exact same
   /auth/callback?code=... URL from browser history (or a copy taken before it redirected).
   Confirm it now shows the expiredOrInvalidLink (single-use code already redeemed) error screen,
   not a second successful exchange - this proves "exchanges... once" rather than being silently
   idempotent or replayable.

## Step 6 - Sign in with the new password (forcing a fresh session)

Because there is no sign-out UI on this branch's own commits (see the T154.2 caveat above): if
the Step 0 merge brought in a working sign-out entry point (Profile, per T154.2), use it.
Otherwise, end the current session manually so "signs in with the new password" is a real,
independent sign-in rather than an already-authenticated bounce:

1. Open DevTools Application/Storage, Local Storage, http://localhost:8081.
2. Delete the sb-PROJECT_REF-auth-token key (or whichever key supabase-js wrote - inspect the
   keys first rather than guessing the exact name).
3. Reload the page. The app should now show guest state (unauthenticated), not bounce to
   /app/home.
4. Navigate to /auth/sign-in, enter recovery-walkthrough@example.com and the new password from
   Step 5.4, and confirm authenticated /app/home is reached. This is the literal "signs in with
   the new password" proof - it fails as expected if Step 4/5's password change was skipped or
   mistyped.

## Step 7 - No-leak checklist (URLs, logs, Analytics)

Do this across the entire walkthrough (Steps 5-6), not just at the end:

- URLs: at every screen transition, check the address bar and browser history for code=,
  access_token=, refresh_token=, token=, or a raw email anywhere in a URL after its owning
  screen's router.replace has run. A transient ?code=... on /auth/callback itself, before the
  replace fires, is expected and not a failure (see Step 5.3).
- Application logs: keep the browser DevTools console open throughout. Every Auth log call goes
  through logAuthWarning (src/features/auth/observability/auth-observability.ts), which redacts
  via redactValue/redactString before printing - confirm any warning that does print (e.g. from
  the deliberate single-use-code replay in Step 5.5) shows redacted-email/redacted-token/
  redacted-jwt placeholders, never the raw address, password, code, or JWT. Also check the
  terminal running yarn web for any server-side Metro/Expo log line containing the same values.
- Analytics: open DevTools Network, filter on vercel or insights. trackAuthEvent calls
  (forgot_password_requested, forgot_password_error, auth_callback_success,
  auth_callback_error) only ever send name plus an optional category, where category is the
  closed AuthErrorCategory enum - confirm the request payload for each never contains an email,
  code, or token. Separately, confirm the automatic pageview beacon's url field (sanitized by
  sanitizeAnalyticsEvent/redactUrl in src/app/_layout.tsx) shows redacted placeholders in place
  of any query/hash param that was present on /auth/callback's URL, rather than the raw value.
  (These requests will likely 404 locally since there is no real Vercel Analytics collector in
  this environment - that is fine, only the outgoing request payload matters here, not the
  response.)

## Risks / non-obvious things for the implementer

- Do not confuse the anon key (client-side, goes in .env) with the service_role key (admin-only,
  used solely for the one curl in Step 3, never put in .env or any tracked file).
- localhost vs 127.0.0.1 for the app's own origin is the one hard requirement (must be
  localhost:8081 to match site_url/PKCE storage). The Supabase API URL in .env can stay
  127.0.0.1 (that is just an HTTP endpoint the browser calls, not the PKCE storage origin) -
  do not over-generalize the localhost-only rule to a file it does not apply to.
- The single-use-code replay check (Step 5.5) is easy to skip by accident since the happy path
  naturally moves the walkthrough forward - do not skip it; it is the literal "exchanges the PKCE
  code once" wording in the exit criteria, not just "exchanges the PKCE code."
- If Step 0's merge did bring in a real Profile sign-out affordance from T154.2, use it instead
  of the manual localStorage-key deletion in Step 6 - it is the more realistic user path and
  worth preferring once available, but do not block on merging T154.2 if for some reason the
  merge is messier than expected; the manual-clear fallback is equally valid evidence for this
  exit criterion.
