# T159.1 -- Model resumable guest import and preview its scope

## Scope for this iteration

Build the pure state machine and durable progress record for guest-to-account
import, plus a read-only inventory step that counts local guest records vs.
cloud records per domain, plus a minimal Profile-adjacent UI that shows those
counts before any guest record is uploaded. No real upload/merge/conflict
logic is implemented here -- that is explicitly T159.2 (empty account),
T159.3 (existing-account merge), T159.4 (profile choice + conflicts),
T159.5 (finalize/clear). This ticket's uploading/awaitingProfileChoice/
conflicts reducer states must exist, be transition-tested, and be
resumable/persistable, but nothing in this ticket drives them with a real
network effect -- later tickets plug an effect into an already-correct state
machine, exactly like T157.2 (coordinator reducer) preceded T157.3+ (real
transport wiring).

Deferred, not part of this ticket: the actual outbox pushes that move guest
records into an account, the profile/preference choice UI, per-record
conflict resolution UI, and clearing guest data. Do not build any of these
now even partially -- modeling their reducer states and persisted-shape slots
is enough.

## Design

### 1. src/features/guest-import/model/guest-import.ts (new)

Pure reducer/state-machine, no React, no clocks, no network -- mirrors
src/shared/sync/coordinator.ts's style exactly (that file is the reference
implementation to imitate for structure and doc-comment conventions).

Core types:

- GuestImportStatus: 'idle' | 'inventorying' | 'awaitingConfirmation' |
  'uploading' | 'awaitingProfileChoice' | 'conflicts' | 'completed' |
  'cancelled'.
- GuestImportTargetKind: 'empty' | 'existing'.
- GuestImportDomainCounts: Readonly<Record<SyncDomain, { local: number;
  cloud: number }>>.
- GuestImportDomainOutcome: { status: 'pending'|'succeeded'|'failed'|
  'conflict'; errorMessage: string | undefined }.
- GuestImportConflict (container-only stub in this ticket -- shape exists so
  T159.4 can extend the reducer without a breaking persisted-shape change):
  { domain: SyncDomain; recordId: string }.
- GuestImportState: { status; importId: string | undefined;
  ownerIdentityNamespace: string | undefined (identityNamespace() of the
  target user account); inventory: GuestImportDomainCounts | undefined;
  targetKind: GuestImportTargetKind | undefined; domainOutcomes:
  Readonly<Partial<Record<SyncDomain, GuestImportDomainOutcome>>>;
  profileChoice: 'guest' | 'cloud' | undefined; conflicts: readonly
  GuestImportConflict[]; errorMessage: string | undefined; startedAt:
  number | undefined; updatedAt: number | undefined }.
- INITIAL_GUEST_IMPORT_STATE: all-undefined/empty defaults, status: 'idle'.

Actions (all carry now: number, no Date.now() inside the reducer):

- importRequested { importId, identityNamespace } -- idle to inventorying
  only (re-entrant guard: any other status is a no-op, same pattern as
  logoutGuardReducer's logOutPressed). Sets importId,
  ownerIdentityNamespace, startedAt.
- inventoryFailed { importId, errorMessage } -- inventorying to idle (stale
  importId mismatch is a no-op), sets errorMessage, clears importId/
  ownerIdentityNamespace so a retry can start clean. This is how a
  transport/client failure during inventory surfaces without wedging.
- inventoryCompleted { importId, inventory } -- inventorying to
  awaitingConfirmation. Derives targetKind: 'empty' iff every domain's
  cloud count is 0, else 'existing'. Stale importId is a no-op.
- confirmPressed { importId } -- awaitingConfirmation to uploading.
  Initializes domainOutcomes to pending for every SYNC_DOMAINS entry (use
  SYNC_DOMAINS from src/shared/sync/domain.ts to build this, don't
  hand-list it twice).
- domainUploadSettled { importId, domain, outcome } -- records one domain's
  outcome while status is uploading. Once every SYNC_DOMAINS entry has a
  non-pending outcome: if targetKind is 'empty' go to completed; else
  ('existing') go to awaitingProfileChoice. Mirrors syncCoordinatorReducer's
  domainSettled "all domains reported" check
  (Object.keys(...).length < SYNC_DOMAINS.length) -- reuse that exact
  pattern, don't reinvent it.
- profileChoiceMade { importId, choice } -- awaitingProfileChoice to either
  conflicts (if state.conflicts.length > 0) or completed. Sets
  profileChoice.
- conflictsResolved { importId } -- conflicts to completed. (T159.1 has no
  path that ever populates conflicts with entries -- this transition exists
  so the state machine is provably correct for T159.4 to drive later; test
  it by constructing a conflicts-status state directly via resumeRequested
  or a state literal, not by getting there through a real flow.)
- cancelPressed { importId } -- awaitingConfirmation to cancelled only.
  (Deliberately narrower than logout's cancel: once uploading has started,
  cancelling isn't modeled in this ticket -- some operations may already be
  server-acknowledged, and safe mid-upload cancellation is a merge-semantics
  decision that belongs with T159.2+, not this scaffold.)
- dismissPressed {} -- completed to idle or cancelled to idle, unguarded
  by importId (this is a user-initiated "start over" reset, not a
  continuation of any specific run), clears every field back to
  INITIAL_GUEST_IMPORT_STATE. No-op from any non-terminal status.
- resumeRequested { persisted, identityNamespace } -- from idle only: if
  persisted.ownerIdentityNamespace === identityNamespace, adopt persisted
  verbatim (mirrors envelopeRestored in sync-envelope.ts -- a restore
  always wins, no merging). If the namespaces don't match, no-op (the
  driver hook is responsible for never calling this with a mismatched
  record in practice, but the reducer must not trust that).
- identityChanged { identityNamespace } -- if state.ownerIdentityNamespace
  is set, differs from action.identityNamespace, and state.status is none
  of idle/completed/cancelled: reset to INITIAL_GUEST_IMPORT_STATE (the
  in-memory run for the old identity is abandoned; the persisted record for
  that old identity is untouched on disk -- it lives at that identity's own
  physical key and will still be there if that same account is used again
  later). Otherwise no-op. Mirrors syncCoordinatorReducer's identityChanged
  cancellation, simplified (no FinishedSyncRun-style history needed here).

Write src/features/guest-import/model/guest-import.test.ts covering, at
minimum, one test per exit-criteria phase plus these guards: stale
importId no-ops for every action that takes one; resumeRequested with a
matching vs. mismatched ownerIdentityNamespace; identityChanged cancelling
each of inventorying/awaitingConfirmation/uploading/awaitingProfileChoice/
conflicts but leaving idle/completed/cancelled alone; targetKind derivation
for all-zero-cloud vs. any-nonzero-cloud inventories; the full
uploading -> awaitingProfileChoice -> conflicts -> completed chain and the
shorter uploading -> completed (empty-target) chain, driven only by literal
actions (no real upload -- this is the reducer proving out T159.4's future
path, not this ticket exercising it).

### 2. src/features/guest-import/persistence/guest-import-persistence.ts (new)

Version-tagged durable record wrapping GuestImportState, storage key
daily-dama:guest-import, mirroring profile-sync-envelope.ts's shape
(version, runtime isGuestImportState validator checking every field
including the SYNC_DOMAINS-keyed domainOutcomes/inventory shapes and the
conflicts array), loadGuestImportState/saveGuestImportState functions with
the same PersistenceLoadResult/PersistenceSaveResult signatures every other
domain's persistence module uses. Malformed/wrong-version/wrong-shape data
recovers to INITIAL_GUEST_IMPORT_STATE (matching the codebase-wide
hydration-fallback convention), never throws.

Add a stateRestored { state: GuestImportState } action to the step-1
reducer specifically for this hydration path (unconditional adopt, no
identity-namespace check needed -- useIdentityScopedDomain already only
ever loads the record belonging to the current physical key by
construction). Keep resumeRequested reserved for the driver's own
"continue a leftover in-progress record" decision, which does need the
namespace check because it's driven by application logic layered on top of
hydration, not the hydration plumbing itself.

Unit test (guest-import-persistence.test.ts): round-trip a fully-populated
state through every status (including uploading with a mixed
domainOutcomes and a non-empty conflicts array) via serialize/parse, reject
malformed shapes field-by-field, reject a wrong schema version.

### 3. src/features/guest-import/persistence/guest-import-inventory.ts (new)

Two read-only functions, no reducer/React involvement.

countLocalGuestRecords(base: KeyValueStorage): Promise<GuestImportDomainCounts>
-- builds a guest-pinned storage via
createGuestMigratingStorage(base, { getIdentity: () => GUEST_IDENTITY })
(reuse src/shared/persistence/scoped-storage.ts as-is -- do not write a new
storage wrapper) and calls the five existing loadXxx functions directly
against it: loadUserProfile, loadCustomTricks, loadPracticeHistory,
loadGoals, loadNotes. Counts:
- profile: (profile has any non-default scalar field ? 1 : 0) plus the size
  of the union of selectedTrickIds and manuallyUnlockedTrickIds -- this
  matches exactly what diffProfileForOutboxOperations in
  profile-cloud-mapping.ts treats as one profile-domain "record" (one
  scalar op keyed by userId, one op per distinct trick id). Reuse that
  file's existing scalar-field extraction/comparison helpers
  (extractScalarFields, or export it if it's currently private) rather than
  re-deriving "non-default" by hand.
- customTricks: collection.tricks.length
- practiceHistory: collection.sessions.length
- goals: collection.goals.length
- notes: collection.notes.length
(Local goal/note collections have no tombstone concept -- Goal/Note model
types carry no deletedAt; a locally-deleted record is just absent. No
filtering needed on the local side.)

GuestImportTransports bundles the five already-existing per-domain sync
transports: profile (ProfileSyncTransport), customTricks (exact exported
type name to confirm in that file, referred to here as
CustomTrickSyncTransport), practiceHistory (PracticeHistorySyncTransport,
name to confirm), goals (GoalSyncTransport, name to confirm), notes
(NoteSyncTransport, name to confirm).

buildGuestImportTransports(client, userId) is a thin factory calling the
five already-built createProfileSyncTransportAdapter,
createCustomTrickSyncTransportAdapter,
createPracticeHistorySyncTransportAdapter, createGoalSyncTransportAdapter,
and createNoteSyncTransportAdapter functions -- do not build new adapters.

countCloudRecords(transports, userId) returns either a succeeded result
carrying counts, or a failed result carrying the domain and errorMessage.
It pulls all pages per domain with pullAllPages (page size
PULL_PAGE_SIZE = 200, matching use-profile-domain-sync.ts's existing
constant) against each transport, in the fixed order profile, customTricks,
practiceHistory, goals, notes so a failure always names a deterministic
first-failing domain, then derives counts:
- profile: pull pullProfileRow() (present means plus one, exactly like the
  local side -- a cloud profile row existing counts as 1 regardless of
  field values, since cloud rows are always fully-populated) plus the
  length of pullAllPages against transport.pullTrickStatePage. (Simpler
  than trying to detect "non-default" server-side -- a present row is
  evidence of some prior sync/account activity worth surfacing; this is a
  deliberate local/cloud asymmetry, note it in the code comment so it isn't
  mistaken for a bug later.)
- customTricks: mapCustomTrickRowsToDomainCollection(rows, userId), taking
  collection.tricks.length on a valid result, else failed.
- practiceHistory: rows.length directly -- no compose/tombstone step exists
  for this domain (confirmed: practice_sessions has no deleted_at/tombstone
  mechanism, per T157.6's completion notes).
- goals: mapGoalRowsToDomainCollection(rows, userId), taking
  collection.goals.length on a valid result, else failed (this already
  excludes tombstoned rows -- reuse it rather than filtering deleted_at by
  hand).
- notes: mapNoteRowsToDomainCollection(rows, userId), taking
  collection.notes.length on a valid result, else failed (same
  tombstone-exclusion reuse).

A pullAllPages failed result or a mapping invalid result for any domain
short-circuits the whole function with the failed shape above -- don't
partially report counts for the domains that happened to succeed before the
failure; the caller (the driver hook) treats any cloud-count failure as
"inventory failed," full stop.

Unit test (guest-import-inventory.test.ts): seed a fake KeyValueStorage
with guest-scoped documents (including the pre-T156.2 legacy-bare-key
fallback case, to prove countLocalGuestRecords picks it up) and assert
exact counts including the profile scalar/trick-id-union math; seed fake
transports (small local doubles satisfying the SyncTransportRepository
contract, same style as use-goal-domain-sync.test.tsx's fakes) with a mix
of active and tombstoned goal/note rows and prove tombstoned rows are
excluded from the cloud count; prove a pull failure on any one domain
reports that domain and stops (assert the later domains' transports were
never called, to lock in the fixed-order short-circuit).

### 4. src/features/guest-import/state/use-guest-import.ts (new)

Driver hook, mirrors use-logout-guard.ts's split (thin hook wrapping a pure
reducer, all effects/timestamps/network calls live here, not in the
reducer) and use-profile-domain-sync.ts's use of useIdentityScopedDomain
for durable persistence.

- Persists GuestImportState via useIdentityScopedDomain using step 2's
  load/save, with createRestoreAction producing the stateRestored action.
- On every render where identity.kind is 'user' and hydration for the
  current generation is complete: if status is 'idle' and importId is
  undefined (truly fresh -- never offered, and not a completed/cancelled/
  dismissed run), kick off inventory: build importId via a small
  createGuestImportId(now, random) helper (same timestamp+random base36
  pattern as createOutboxOperationId/createSyncRunId), dispatch
  importRequested, then in an effect gated on status being 'inventorying'
  call countLocalGuestRecords plus, if getSupabaseClient() returns
  non-null, countCloudRecords, and dispatch inventoryCompleted or
  inventoryFailed. If the client is null (SSR/misconfigured), dispatch
  inventoryFailed immediately rather than hanging.
- If a non-idle, non-terminal persisted status is found on hydration
  (interruption/reload case), dispatch resumeRequested instead of starting
  a fresh inventory -- this is the literal "resume" behavior the exit
  criteria names. Do NOT re-run countLocalGuestRecords/countCloudRecords on
  resume into awaitingConfirmation (the persisted inventory is still valid
  -- nothing has been uploaded yet, so counts can't have gone stale from
  this app's perspective). A resume into inventorying itself (interrupted
  before the counts even finished) does re-run the inventory read, since
  nothing durable was captured yet.
- Identity-change guard: an effect depending on generation (from
  useIdentityHandle()) that dispatches identityChanged with the new
  identityNamespace(identity) whenever generation changes after the first
  render -- mirrors use-logout-guard.ts's armedGenerationRef pattern
  closely enough to copy its shape, but simpler since this hook doesn't
  need a "was a flow armed" precondition -- any generation change is
  dispatched unconditionally; the reducer itself decides whether it's a
  no-op (idle/terminal) or a real cancellation.
- Exposed actions: confirmImport() dispatches confirmPressed, cancelImport()
  dispatches cancelPressed, dismiss() dispatches dismissPressed. No
  startUpload/resolveConflict/etc -- those belong to T159.2+ and shouldn't
  be stubbed here with fake bodies that look load-bearing but aren't.
- Returns { state, confirmImport, cancelImport, dismiss }.

RTL test (use-guest-import.test.tsx), fake getSupabaseClient/transport
style matching use-profile-domain-sync.test.tsx: guest identity never
inventories (no transport calls, state stays idle with importId undefined);
first hydration under a user identity with nonzero local guest data and a
reachable (empty) cloud auto-transitions from idle through inventorying to
awaitingConfirmation with correct counts and a targetKind of 'empty'; a
nonzero cloud count yields a targetKind of 'existing'; confirmImport() moves
to uploading and does not by itself settle any domain (proving no upload
effect is wired); remounting with a persisted awaitingConfirmation record
resumes without re-inventorying (assert the fake transport's pull methods
were not called again); remounting with a persisted inventorying record
re-runs inventory; an identity change (second IdentityHandle generation)
while awaitingConfirmation resets to idle and the newly-hydrated record for
the new identity is independent; a client/transport failure lands in idle
with errorMessage set instead of hanging in inventorying.

### 5. src/features/guest-import/components/guest-import-preview.tsx (new) plus wiring

Presentational component consuming useGuestImport():
- status idle, cancelled, or completed (or guest identity) renders nothing.
- status inventorying renders a small loading row ("Checking your local
  practice data...").
- status awaitingConfirmation: if every domain's local count is 0, render
  nothing (nothing to offer). Otherwise render one row per SYNC_DOMAINS
  entry with a nonzero local count, each showing local and cloud counts
  with a human label (reuse or add a small domain-label map -- check
  whether src/shared/sync/domain.ts or a UI-layer file already has
  domain-to-label copy before adding a second one), plus an "Import my
  practice data" button calling confirmImport() and a "Not now" button
  calling cancelImport().
- status uploading, awaitingProfileChoice, or conflicts renders a plain
  "Import in progress..." row (no interaction) -- real UI for these phases
  is T159.2+'s job; this ticket must not leave the screen blank once
  confirmImport() is pressed, but also must not invent premature UI for
  phases with no real behavior behind them yet.

Wire GuestImportPreview into src/app/app/profile/index.tsx (or inside
account-section.tsx, whichever keeps the authenticated-only gating in one
place -- check how AccountSection already guards and follow the same
pattern rather than duplicating the guard).

Component test (guest-import-preview.test.tsx) with a mocked
useGuestImport (the same "mock the hook, test the component" style already
used in account-section.test.tsx / logout-prompt tests): hidden for idle,

## Order and why

1. model/guest-import.ts plus its full test suite first -- no dependencies
   on anything else in this plan, and it's the actual "state-machine tests"
   deliverable named in the exit criteria. Getting the transition table
   right first means every later file targets a settled contract instead of
   a moving one.
2. persistence/guest-import-persistence.ts -- depends only on step 1's
   types. Must exist before step 4 can persist anything.
3. persistence/guest-import-inventory.ts -- depends on existing per-domain
   persistence/mapping/transport modules (already built in T155/T157;
   read-only reuse, no changes to those files). Independent of steps 1-2 in
   principle, but ordered after them so its GuestImportDomainCounts return
   shape is already settled.
4. state/use-guest-import.ts -- wires 1-3 together with
   useIdentityScopedDomain, useIdentityHandle, and getSupabaseClient. Needs
   all three prior steps to exist first.
5. components/guest-import-preview.tsx plus wiring -- last, purely a
   consumer of step 4.

## Risks / non-obvious things to watch

- Guests get a persisted record too, and that's fine. Every identity
  (including guest) gets its own useIdentityScopedDomain-hydrated
  GuestImportState at its own physical key. Don't special-case persistence
  itself for guests -- only the driver hook's effects (auto-inventory) are
  gated on identity.kind being 'user', matching every other domain sync
  hook's existing "guests never sync" branch.
- ownerIdentityNamespace is always a user:uuid namespace, never guest.
  There is exactly one guest workspace per device (the fixed guest:
  physical prefix) -- inventory always reads that fixed location for the
  local side, regardless of which user account is doing the importing.
  Don't try to disambiguate "which guest" -- there's only one.
- A second account signing in later can independently re-offer the same
  still-present guest data. Since dismiss/completed/cancelled state lives
  per target identity, guest data that was never cleared (clearing is
  T159.5's job) will look "fresh" again to a different account. This is
  expected under the "clear only after acknowledgement" roadmap rule, not a
  bug -- don't try to prevent it in this ticket.
- Do not let uploading grow a real effect in this ticket. It's tempting to
  "just wire the actual push while I'm in here" -- resist it; T159.2's exit
  criteria (interruption/resume/dedup fault-injection against real
  transports) is a separate, larger piece of work than this ticket's scope
  allows, and the reducer is already built to accept it later without a
  shape change.
- Verify exact exported type/function names before writing
  guest-import-inventory.ts. This plan names the four non-profile transport
  types and extractScalarFields by inference from surrounding code
  (confirmed for ProfileSyncTransport and the three
  mapXRowsToDomainCollection functions; not exhaustively grepped for the
  transport type aliases or whether extractScalarFields is currently
  exported). Grep the actual exports in each sync-transport.ts and
  cloud-mapping.ts file first and adjust names, not behavior.
- Keep effects/clocks/network calls out of guest-import.ts (the task note
  repeats this deliberately) -- every timestamp is an action field supplied
  by the driver hook, exactly like coordinator.ts and sesh.ts.
