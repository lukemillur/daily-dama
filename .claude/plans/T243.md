# T243 — Show returning-user CTA copy to an authenticated visitor on the landing page

Branch: `task/T243-show-returning-user-cta-copy-to-an`

## 1. What is actually broken (verified against the branch)

`LandingCta` (`src/features/landing/components/landing-cta.tsx:31-35`) derives its whole
variant from one value:

```ts
const { hasCompletedOnboarding } = useCachedOnboardingStatus();
const isReturning = hasCompletedOnboarding;
```

`useCachedOnboardingStatus` (`src/features/landing/state/use-cached-onboarding-status.ts`)
always reads the **guest-scoped** key — `GUEST_SCOPED_KEY = physicalKey(GUEST_IDENTITY,
USER_PROFILE_STORAGE_KEY)`, i.e. the literal string `guest:daily-dama:user-profile`, with a
fallback to the bare legacy `daily-dama:user-profile`
(`src/features/profile/persistence/read-cached-onboarding-status.ts`). A signed-in user's
profile lives under `user:<uuid>:daily-dama:user-profile`, which this reader never consults.
So for an authenticated visitor the cached flag reads `false` and the panel shows
`FIRST_TIME_COPY` ("Start your first sesh.") in the yellow variant.

That is the whole defect. Do **not** try to fix it by teaching
`readCachedOnboardingStatus` about user-scoped keys — that would change the landing route's
persistence read surface (and `useRedirectOnboardedVisitorHome`, which shares the hook) and
is out of scope. The ticket's chosen fix is to add auth status as an independent input to
the copy decision.

## 2. The rule to implement

```ts
const authState = useAuthState();
const { hasCompletedOnboarding } = useCachedOnboardingStatus();
const isReturning = authState.status === 'authenticated' || hasCompletedOnboarding;
```

Full matrix — only the one starred cell changes behavior:

| `authState.status` | `hasCompletedOnboarding` | copy | vs. today |
| --- | --- | --- | --- |
| `guest` | `false` | `FIRST_TIME_COPY` | unchanged |
| `guest` | `true` | `RETURNING_COPY` | unchanged |
| `initializing` | `false` | `FIRST_TIME_COPY` | unchanged (also the prerender/first-client-render output) |
| `initializing` | `true` | `RETURNING_COPY` | unchanged |
| `passwordRecovery` | `false` | `FIRST_TIME_COPY` | unchanged |
| `passwordRecovery` | `true` | `RETURNING_COPY` | unchanged |
| `authenticated` | `false` | `RETURNING_COPY` | **★ the fix** |
| `authenticated` | `true` | `RETURNING_COPY` | unchanged |

Decisions baked into that rule, with reasons — implement them as written, don't
re-derive:

- **Only `'authenticated'` counts, not "not guest".** `AuthState`
  (`src/features/auth/model/auth-state.ts:7-15`) is a four-way union. Treating
  `initializing` as returning would flip the prerendered HTML and every first client render
  to the sage returning panel for *everyone*, including true first-time visitors — a strictly
  worse regression than the bug being fixed. Treating `passwordRecovery` as returning is
  unnecessary (a visitor mid password-reset is not on the landing page in any real flow) and
  matches T242's conservative handling of that status in `landing-auth-cta.tsx`.
- **`||`, not "auth replaces onboarding".** The ticket says "regardless of the onboarding
  flag", which `||` satisfies, and keeping `hasCompletedOnboarding` as the second operand is
  what mechanically guarantees the onboarded-guest row is untouched.
- **Keep the logic inline in the component.** Do *not* extract a
  `selectLandingCtaCopy(...)` helper module or move `FIRST_TIME_COPY`/`RETURNING_COPY` out of
  the file. This is a one-line predicate; `landing-auth-cta.tsx` — the closest precedent on
  this exact surface — reads `authState.status` inline too. A new model module plus its own
  test file is scope creep for a one-cell behavior change.

## 4. Risks and edge cases worth knowing before you start

- **No SSR/hydration mismatch is introduced, and the plan depends on keeping it that way.**
  `/` is statically prerendered in Node. `AuthProvider` initializes to
  `INITIALIZING_AUTH_STATE` and only leaves it from an *effect* (`auth-provider.tsx:59-83`),
  so both the Node prerender and the very first client render see `initializing` → the
  `initializing + false` row → `FIRST_TIME_COPY`, byte-identical to today's prerendered
  markup. This is why §2 excludes `initializing`. `useCachedOnboardingStatus`'s own
  `useSyncExternalStore` hydration gate is untouched.
- **There will be a brief first-time→returning flip for a signed-in visitor.** After
  hydration, Supabase's `onAuthStateChange` fires `INITIAL_SESSION` asynchronously, so a
  signed-in visitor sees the yellow first-time panel for roughly one tick before it becomes
  the sage returning panel. This is inherent to reading async auth state and is the same
  trade-off T242 accepted (it renders `null` for `initializing` so the header bar simply
  appears late). **Do not** try to eliminate it by synchronously sniffing Supabase's
  persisted `sb-<projectRef>-auth-token` localStorage entry — that couples the landing route
  to SDK storage internals. Observe it during browser verification and, if it reads as a
  jarring flash rather than a normal load-in, report it as a follow-up ticket rather than
  fixing it here.
- **Redirect interaction (this is what will confuse you in the browser).**
  `useRedirectOnboardedVisitorHome` (`src/app/index.tsx` → `redirect-onboarded-visitor-home.ts`)
  still reads the *guest* cache and redirects `/` → `/app/home` when
  `hasCompletedOnboarding && kenteiRank !== undefined` and the URL has no `?from=app`. So:
  in the exact scenario this ticket targets (authenticated, guest cache says not onboarded)
  a direct hit on `/` does **not** redirect and the landing page renders — good. But if your
  browser profile still has an onboarded *guest* cache from earlier work, `/` will redirect
  before `LandingCta` ever mounts. Use `http://localhost:8081/?from=app` (per T242's note)
  or clear `guest:daily-dama:user-profile` from localStorage. This ticket does not change
  redirect behavior at all.
- **Untouched by design:** `useCachedOnboardingStatus`, `readCachedOnboardingStatus`,
  `useRedirectOnboardedVisitorHome`, `landing-auth-cta.tsx`, and the CTA's `/app/home`
  destination. If you find yourself editing any of them, stop and re-read §1.
