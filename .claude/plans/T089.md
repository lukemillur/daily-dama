# T089 -- Add button-background tokens to the resolved-theme system

## Context established by exploration

`src/features/profile/state/use-resolved-theme.ts` currently derives three fields
(`background`, `accent`, `text`) from saved preferences, falling back to
`AppColors.sage` / `AppColors.yellow` when unset, with `text` derived via
`deriveAutomaticTextColor(background, accent)` (picks whichever of `AppColors.ink` /
`AppColors.cream` has the better minimum contrast against both background and accent).

The two literal button colors this ticket is meant to replace are already visible today:

- `src/components/ui/button.tsx` -- `ButtonRoot`'s `background-color` is
  `AppColors.ink` for `variant="primary"` and `AppColors.paperStrong` for
  `variant="secondary"`. Not theme-driven at all today.
- `src/features/sesh/components/sesh.tsx:1191` -- `LacedButton` is hardcoded
  `background-color: #d84929` (a different color entirely; out of scope here, T097
  wires it later to `buttonBackground`, which is a signal that `buttonBackground`
  is expected to be a bold/loud CTA-appropriate color, not literally "whatever the
  Button component happens to use today" -- but there is no ticket requirement that
  `buttonBackground` render as red, so keep to the primary/secondary Button pairing
  as the ground truth for this schema).

T087's `RAINBOW_THEME_PRESETS` (`src/features/profile/model/theme-presets.ts`) are 7
presets, each a `{ backgroundColor, accentColor }` pair with a light pastel
`backgroundColor` (e.g. `#fbdcd6`) and a saturated `accentColor` (e.g. `#c0392b`).
They're plumbed into `ThemeColorPreferences` the same way a manually-picked custom
theme is (there's no separate "preset" resolution path -- a chosen preset just sets
`themeBackgroundColor`/`themeAccentColor` to the preset's values).

`src/types/styled-components.d.ts` declares `DefaultTheme` with the same three fields
as `ResolvedTheme`; `AppThemeProvider` passes a `ResolvedTheme` value straight into
`StyledThemeProvider`'s `theme` prop. Since `ResolvedTheme` will have strictly more
fields than the current `DefaultTheme` interface, TS's structural typing means
leaving `DefaultTheme` unchanged would still compile -- but T096/T097 need
`theme.buttonBackground` to be usable through the ambient `theme` prop the same way
`theme.accent`/`theme.text` are today, so `DefaultTheme` must be extended too, or
those tickets will hit a type error the moment they write `theme.buttonBackground`
in a styled-components template.

## Derivation design (decided during planning, not left for the implementer to invent)

Add a second automatic-derivation helper, `deriveAutomaticButtonBackgrounds`,
following the same shape as `deriveAutomaticTextColor`: pick between two fixed
`AppColors` neutrals by contrast, this time against the resolved `background` only
(buttons are opaque surfaces sitting on top of the page background, not on top of
the accent the way text can be), reusing `AppColors.ink` and `AppColors.paperStrong`
-- the exact two colors `Button`'s primary/secondary variants already hardcode today.

```ts
export function deriveAutomaticButtonBackgrounds(background: string): {
  buttonBackground: string;
  buttonBackgroundSecondary: string;
} {
  const inkContrast = contrastRatio(AppColors.ink, background) ?? 0;
  const paperContrast = contrastRatio(AppColors.paperStrong, background) ?? 0;

  return inkContrast >= paperContrast
    ? { buttonBackground: AppColors.ink, buttonBackgroundSecondary: AppColors.paperStrong }
    : { buttonBackground: AppColors.paperStrong, buttonBackgroundSecondary: AppColors.ink };
}
```

This was verified numerically (script run against the real hex values, not eyeballed):

- Default/unset background (`AppColors.sage` `#dfe8ca`): ink-vs-sage contrast ~= 10.06,
  paperStrong-vs-sage ~= 1.10 -> resolves to `{ buttonBackground: ink,
  buttonBackgroundSecondary: paperStrong }`. This exactly matches what `Button`
  already hardcodes today, so wiring it in later (T096) will be a visual no-op for
  the default theme.
- All 7 T087 preset backgrounds (`#fbdcd6`, `#fde3c8`, `#fbf0bd`, `#dcefd9`,
  `#d8e8f7`, `#e0dcf5`, `#f3d9f0` -- all light pastels): ink-contrast ranges ~=
  9.6-11.1, paperStrong-contrast ranges ~= 1.0-1.2 -> every preset also resolves to
  `{ buttonBackground: ink, buttonBackgroundSecondary: paperStrong }`. Flat but
  correct -- the exit criteria ask for a per-preset assertion, not a per-preset
  distinct value, and this is the actual derived result, not an assumption.
- A representative dark custom background (`#101418`, same value the existing
  "derives cream" test in `use-resolved-theme.test.ts` uses for `text`):
  ink-contrast ~= 1.45, paperStrong-contrast ~= 16.09 -> flips to
  `{ buttonBackground: paperStrong, buttonBackgroundSecondary: ink }`. This is the
  case that actually exercises the derivation logic (rather than just re-asserting
  the ink/paperStrong default), and demonstrates why this isn't just two constants.

`accent` deliberately does not participate in this derivation, unlike
`deriveAutomaticTextColor`. Text sits on top of both background and accent
surfaces (hence the `min()` of both contrast scores), but a button's own
background only ever sits on top of the page background -- there's no scenario in
the current UI where a button surface itself is rendered on top of the accent
color. Note this reasoning in a doc comment so a future reader doesn't wonder why
`accent` is unused here, unlike in `deriveAutomaticTextColor`.

## Ordered implementation steps

1. **`src/features/profile/state/use-resolved-theme.ts`**
   - Add `buttonBackground: string` and `buttonBackgroundSecondary: string` to the
     `ResolvedTheme` interface (after `text`, matching declaration order elsewhere).
   - Add `deriveAutomaticButtonBackgrounds` (exported, same visibility level as
     `deriveAutomaticTextColor`) with the JSDoc explaining the ink/paperStrong
     candidate pair, why it contrasts only against `background`, and why `accent`
     is intentionally excluded (see above).
   - In `resolveTheme`, call it and destructure `buttonBackground` /
     `buttonBackgroundSecondary` from the result, and include both in the
     returned object. No new fields on `ThemeColorPreferences` -- there is no
     "custom button background" user preference in scope (Notes confirm this is
     schema-only derivation, not a new user-settable preference), so these are
     always derived, never read from `preferences` directly, unlike `text`.
   - Update the function's top JSDoc comment to mention the new fields briefly,
     consistent with how it currently documents `text`'s derivation.

2. **`src/types/styled-components.d.ts`**
   - Extend `DefaultTheme` with the same two new `readonly` fields, keeping the
     interface in lockstep with `ResolvedTheme`. Do this in the same commit as
     step 1 -- a partially-updated theme contract is the kind of drift this file
     exists to prevent, and T096/T097 depend on this being present before they can
     start.

3. **New tests in `src/features/profile/state/use-resolved-theme.test.ts`**
   (append to the existing `describe('resolveTheme', ...)` block, following its
   existing style -- no new mocking needed, the file already mocks AsyncStorage at
   the top for the transitive import chain):
   - (a) No saved preference: `resolveTheme({})` returns
     `buttonBackground === AppColors.ink` and `buttonBackgroundSecondary ===
     AppColors.paperStrong`.
   - (b) Saved custom theme, reusing the file's existing dark-pair fixture
     (`themeBackgroundColor: '#101418', themeAccentColor: '#1a1f24'`, same as the
     existing "derives cream" test): expect `buttonBackground === AppColors.paperStrong`
     and `buttonBackgroundSecondary === AppColors.ink` (the flipped case -- this is
     the test that actually proves the derivation isn't hardcoded).
   - (c) Each of the 7 `RAINBOW_THEME_PRESETS` entries (import
     `RAINBOW_THEME_PRESETS` from `@/features/profile/model/theme-presets`, use
     Jest's `it.each` over them, calling `resolveTheme` with the preset's
     background/accent for each) and assert `buttonBackground === AppColors.ink`,
     `buttonBackgroundSecondary === AppColors.paperStrong` for every preset.
     Prefer `it.each` over a manual loop inside a single `it`, so a failure on one
     preset reports which preset failed rather than aborting the whole assertion
     silently.

4. **Verification** -- run `node .claude/scripts/verify.mjs` (full four-step
   sequence; this change touches TS types consumed by styled-components templates,
   so don't skip the export step). Confirm no existing test/consumer of
   `ResolvedTheme`/`DefaultTheme` needed changes -- the two new fields are additive
   and every current consumer (`AppThemeProvider`, `Button`, `sesh.tsx`) only reads
   the three pre-existing fields, so nothing else should need edits. If `tsc` or
   the export step surfaces an unrelated consumer expecting an exact/closed
   `ResolvedTheme` shape (e.g. an object-literal assignment rather than a variable
   assignment, which TS checks for excess properties), that's the one place this
   plan's "additive, no other file changes" assumption could be wrong -- fix it
   narrowly rather than reshaping the derivation.

## Risk / non-obvious notes for the implementer

- The three T087-preset-derived values are not distinct per preset (all 7
  resolve to the same ink/paperStrong pair) -- this is correct, not a shortcut. If
  the implementer expects one assertion per preset with unique expected colors
  and second-guesses this, the numeric contrast values above already confirm it's
  the actual derived output for every preset's background.
- Keep `deriveAutomaticButtonBackgrounds` taking `background` only, not `accent` --
  don't follow `deriveAutomaticTextColor`'s two-argument shape reflexively; the
  JSDoc reasoning above is what should stop a reviewer from "fixing" this to match
  the sibling function's signature.
- `DefaultTheme` (styled-components ambient type) must be extended in the same
  commit as `ResolvedTheme` -- deferring it will silently block T096/T097 with a
  type error on `theme.buttonBackground` that has nothing to do with their own
  changes.
