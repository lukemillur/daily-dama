# T197 — Fix account deletion still returning a 503 in the real environment

## Root cause (confirmed during planning, not yet fixed)

The hosted "Daily Dama Dev" Supabase project (ref `ylyoqswauqyesuwmetnl`,
region `us-east-2`) — confirmed by `supabase/HOSTED_DEV_CONFIG.md` and T195's
diagnosis to be the real environment behind both `EXPO_PUBLIC_SUPABASE_URL` in
every developer's `.env.local` *and* the live `dailydama.com` site — has **zero
Edge Functions deployed**:

```
$ npx supabase functions list --project-ref ylyoqswauqyesuwmetnl
{"functions":[],"message":""}
```

`delete-account` exists only in the repo (`supabase/functions/delete-account/`)
and on whichever local stacks individual developers have started. This is the
exact same class of bug T195 just fixed for the confirmation-email template:
T188's "fix" for the 503 was entirely a **local**-stack recovery step (stop/
start cycling a stale Docker container) — it never deployed anything to the
hosted project, because nothing in this repo or CI does. `npx supabase secrets
list --project-ref ylyoqswauqyesuwmetnl` is also empty, but that's expected and
not itself a problem: `SUPABASE_URL`, `SUPABASE_ANON_KEY`, and
`SUPABASE_SERVICE_ROLE_KEY` (the three env vars `supabase/functions/
delete-account/index.js` reads via `Deno.env.get`) are reserved names Supabase
auto-injects into every deployed Edge Function's runtime, hosted or local —
they don't need to be set as user secrets. So the fix is a straight deploy, not
a secrets/config problem.

A gateway 503 for an undeployed function slug is consistent with what the user
is seeing when they hit "Delete account" against the real app.

## Implementation steps, in order

1. **Copy the Management API PAT into this worktree** (it's gitignored and
   worktree-local, per the task's own note):
   ```
   cp "<main-checkout>/.env.supabase-pat.local" .env.supabase-pat.local
   ```
   Never print its contents. Use it only as `SUPABASE_ACCESS_TOKEN` for
   `npx supabase` invocations (the CLI reads that env var; it is not a
   `source`-able shell snippet — extract the token value with `cut`/`tr` as
   needed, matching how this plan's own diagnosis did it).

2. **Deploy `delete-account` to the hosted project:**
   ```
   npx supabase functions deploy delete-account --project-ref ylyoqswauqyesuwmetnl
   ```
   Run this from the repo root so the CLI picks up `supabase/config.toml`'s
   `[functions.delete-account]` block (`enabled = true`, `verify_jwt = true`,
   the `index.js` entrypoint) automatically — no extra flags should be needed.
   `verify_jwt = true` matches the function's own manual `Authorization`
   header check, so leave it as-is; do not pass `--no-verify-jwt`.

3. **Verify the deploy landed:**
   ```
   npx supabase functions list --project-ref ylyoqswauqyesuwmetnl
   ```
   should now show `delete-account`, `enabled: true`, `verify_jwt: true`, and
   a real `version`/`updated_at`. If this step still shows an empty list or an
   error, stop and re-diagnose (e.g. `deno_version` mismatch, entrypoint path
   issue) rather than proceeding to manual verification with a function that
   isn't actually live.

4. **Obtain the hosted anon/publishable key without touching the password

   Extract the `anon` key's `api_key` field. Never print it to a transcript

   EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY=<anon key from step 4>

## Order rationale

Steps 1-3 (deploy) must happen before any UI verification (5-7) — testing the
deletion flow before the function is actually live would just reproduce the
same 503 and waste a disposable-account cycle. Step 4 (key retrieval) only
needs to happen before step 5, not before the deploy. Documentation (step 9)
comes after verification succeeds, so the note reflects a confirmed fix rather
than a guess.

## Risks / non-obvious things

- **Don't confuse this with T195's specific fix.** T195 patched the hosted
  *Auth email template config* via `PATCH /v1/projects/{ref}/config/auth`.
  This ticket's fix is a different hosted resource entirely (an Edge
  Function binary/deploy), via `supabase functions deploy`, not the Management
  API's auth-config endpoint. Don't try to "deploy" the function through the
  Auth config PATCH pattern.
- **`verify_jwt = true` still requires a valid bearer token at the gateway
  layer**, before the function body's own `Authorization` check even runs. A
  malformed/missing token will fail at the gateway with a different status
  than the function's own `401` — don't mistake that for a fresh regression
  if it shows up while testing with a stale/expired session token.
- **The exit criteria requires the *real* environment**, not a fresh local
  `supabase start`/`db reset` cycle — re-verifying only locally (T188's
  mistake) would pass without actually fixing the reported bug. Step 6-7 must
  run against the hosted project.
- **Rate limiting is isolate-local** (`supabase/functions/delete-account/
  index.js`'s own comment, and `supabase/README.md:135`) — a single manual
  test run won't exercise or need to worry about this, but don't read a
  `429` from rapid repeated manual attempts as a new bug.
- If step 3's `functions list` still comes back empty after a deploy that
  reported success, check the CLI's exit code/output carefully before
  retrying blindly — a partial or failed deploy silently leaving the project in
  the same empty state would look identical to "nothing happened yet."
