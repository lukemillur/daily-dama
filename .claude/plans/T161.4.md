# T161.4 — Add the permanent account-deletion route

## Scope

Good enough for this iteration is a signed-in web route at
`/app/profile/account/delete` that warns deletion is immediate and permanent,
requires the current password plus exact uppercase `DELETE`, invokes the
existing hardened `delete-account` Edge Function, and provides safe validation,
loading, offline, unauthorized, rate-limited, generic-error, and success
states. Same-tick duplicate submits must be prevented, and passwords, tokens,
raw backend errors, and sensitive values must not reach UI, logs, analytics, or
URLs.

Do not implement T161.5 local purge/response-loss reconciliation, export,
delayed deletion, mobile hardening, or Edge Function changes.

## Findings and preserved contracts

- The supplied worktree is clean and resolves to the requested path.
- T154.1 is done: `AuthProvider`, `getSupabaseClient`, the closed-set Auth
  error categories, and the auth observability/redaction boundary are the
  existing account-action seams.
- T161.2 is done: `delete-account` accepts only authenticated POST bodies with
  `currentPassword` and exact `confirmation: 'DELETE'`; it returns generic
  401/429/500 failures, `204` for successful or already-absent users, and
  `Cache-Control: no-store`.
- The existing profile Stack and `useRequireOnboarding` pattern support the
  nested route. Web is the only active platform.

## Ordered implementation plan

1. **Add the Auth action and error mapping.** Extend
   `src/features/auth/state/auth-provider.tsx` with a `deleteAccount` action
   that requires an authenticated state, obtains `getSupabaseClient()`, and
   invokes `delete-account` with only `{ currentPassword, confirmation }`.
   Add focused provider tests in
   `src/features/auth/state/__tests__/auth-provider.test.tsx` for exact body
   forwarding, unauthenticated/no-client guards, success, and error
   propagation without changing Auth state. If `functions.invoke` errors lack
   stable Auth codes, use a deletion-specific status/network mapper rather
   than parsing unstable messages: 401 → generic wrong-password/session-safe
   copy, 429 → retry-later, network/fetch → offline, all else → generic retry.

2. **Add the screen and route.** Create a focused component such as
   `src/features/auth/components/account-deletion-screen.tsx` and route
   `src/app/app/profile/account/delete.tsx`, gated by
   `useRequireOnboarding`. Render an explicit immediate/permanent warning, a
   labeled `PasswordInput` for current password, an exact-match confirmation
   field, validation that disables the destructive action until both are
   valid, loading/disabled behavior, closed-set actionable errors, and a
   success state that cannot submit again. Use a synchronous ref guard as well
   as React state. Never log, track, render, persist, or navigate with either
   entered value or raw backend errors.

3. **Add discoverability.** Add a clearly labeled link from the authenticated
   account-security surface to `/app/profile/account/delete`, preserving the
   existing account section semantics. Extend the nearest component test for
   authenticated-only visibility and exact navigation if needed.

4. **Add component/route tests.** Create a focused suite beside the Auth
   components, covering initializing/guest/authenticated states, onboarding
   gating, both required fields, exact case-sensitive `DELETE`, no invocation
   on invalid input, loading, same-tick double-submit prevention, success
   lockout, and stable copy for wrong password, offline, rate-limited,
   expired/invalid session, and unknown errors. Assert no password, token, raw
   error, or sensitive value reaches rendered text, logs, analytics, or URL.

5. **Add browser evidence.** Extend Auth Playwright coverage, preferably with
   `e2e/auth/08-account-deletion.spec.ts`, using the existing seed/sign-in and
   redaction helpers. Verify validation gating, wrong-password generic copy,
   aborted-network offline recovery, intercepted 429 handling,
   expired/invalid-session handling, one successful submit with repeated
   clicks disabled, and absence of password/token/raw error in console,
   analytics requests, visible UI, and URL. Use controlled responses for UI
   cases; use a disposable real user only if a real success walkthrough is
   needed.

6. **Verify proportionally.** Run focused provider/component tests and scoped
   ESLint during implementation. Before completion run affected Auth tests,
   `yarn tsc --noEmit`, and
   `yarn expo export --platform web --output-dir /tmp/daily-dama-web-export`.
   Run `yarn test:e2e:auth` with the local Supabase prerequisites documented in
   `supabase/README.md`; record environment blockers rather than weakening the
   claim. Do not run mobile tooling. Keep T161.5 cleanup/recovery deferred.

## Exit-criteria mapping

- Focused tests prove both confirmations, safe disabled/loading/error states,
  and duplicate-submit prevention.
- Provider/observability assertions prove no password, token, raw error, or
  sensitive URL value leaks.
- Browser evidence covers wrong/offline/rate-limited/expired outcomes and a
  single-submit success flow.
- No export or delayed-deletion semantics are added.
