# T124 — Enlarge the screenshot showcase on desktop/web viewports

## Context confirmed in current code

- `src/features/landing/components/landing-page.tsx` already computes a single
  desktop/web boolean at the top of `LandingPage`:
  `const isWebLayout = Platform.OS === 'web' && width >= 768;` (line ~122). It's
  already used to swap `WEB_SCREENSHOTS` vs `MOBILE_SCREENSHOTS` assets. This task
  should reuse that exact boolean/threshold for sizing too, so the asset swap and
  the size bump always flip together at the same width — do not invent a second
  breakpoint.
- The three styled components to change are `ScreenshotItem` (max-width: 360px,
  padding 18px 16px 22px), `ScreenshotTitle` (font-size: 19px), and
  `ScreenshotCaption` (`styled(BodyText)`, max-width: 340px; `BodyText` itself sets
  `font-size: 16px; line-height: 24px`) — all defined at the bottom of
  `landing-page.tsx` (lines ~232–255).
- **Breakpoint mechanism convention**: this file is a shared (non-`.web.tsx`)
  component, and the codebase's established pattern for JS-driven responsive
  styling in shared files is a boolean transient prop on a styled component, not
  a styled-components `@media` query. See
  `src/features/onboarding/components/onboarding-selection-step.tsx`:
  `styled.View<{ readonly $pinned: boolean }>` with
  `${({ $pinned }) => $pinned ? X : Y}` interpolations, driven by the same
  `Platform.OS === 'web' && width >= 768` check. `@media` in styled-components is
  only used in `src/components/app-tabs.web.tsx`, which is a `.web.tsx` file that
  only ever runs under react-native-web's real CSS engine on web builds — that's
  also almost certainly the source of the "known-benign styled-components/native
  media-query" warning AGENTS.md calls out (it fires when `@media` syntax is
  evaluated outside a real DOM). Follow the transient-prop pattern, not `@media`,
  to stay consistent and avoid resurrecting that warning in a shared file.
- `Content`'s `max-width: 620px` (page-wide column cap) is explicitly out of scope
  per the task Notes (T128's territory). Keep the desktop `ScreenshotItem`
  max-width comfortably inside `Content`'s inner width (620px − 22px×2 padding =
  576px usable) — recommend 560px — so it doesn't collide with or get clipped by
  that unrelated boundary.
- Test infrastructure already exists for exercising both widths:
  `src/features/landing/components/landing-page.test.tsx` forces
  `Platform.OS = 'web'` for the whole file and has a working
  `mockUseWindowDimensions.mockReturnValue({ width: 375 | 1280, ... })` pattern
  already used in the "LandingPage platform-based screenshot set" describe block.
  Reuse it rather than re-deriving mocking.
- For asserting on styled-components' rendered numeric style values in tests,
  follow the existing pattern in `src/components/ui/typography.test.tsx`
  (`resolvedTextStyle` helper): `root.root.findAll(...)` matching by node type and
  an identifying prop, then filtering for the match whose `props.style` is a
  plain (non-array, non-null) object, and reading fields off it directly (e.g.
  `style.color`). Styled-components v6/native resolves its template to a plain
  style object on the host RN element in this test environment — there is no
  class name to inspect.

## Implementation steps

1. **`src/features/landing/components/landing-page.tsx` — wire the breakpoint
   through the three styled components.**
   - Extend `ScreenshotItem`, `ScreenshotTitle`, and `ScreenshotCaption` with a
     `readonly $isWebLayout: boolean` transient prop, matching the
     `styled.View<{ readonly $pinned: boolean }>` generic pattern from
     `onboarding-selection-step.tsx` (and `styled(BodyText)<{...}>` for
     `ScreenshotCaption`, since it extends `BodyText`).
   - `ScreenshotItem`: change `max-width: 360px;` to
     `max-width: ${({ $isWebLayout }) => ($isWebLayout ? 560 : 360)}px;`. Mobile
     value must stay literally `360` (exit criteria requires mobile sizing to be
     byte-for-byte unchanged). Optionally also grow the padding for desktop (e.g.
     `padding: ${({ $isWebLayout }) => ($isWebLayout ? '26px 26px 30px' : '18px 16px 22px')};`)
     since the task description calls out the "container" as one of the things
     that should visibly grow together — this is a light polish addition, not
     required by the exit criteria, which only measures rendered width.
   - `ScreenshotTitle`: change `font-size: 19px;` to
     `font-size: ${({ $isWebLayout }) => ($isWebLayout ? 24 : 19)}px;`.
   - `ScreenshotCaption`: change `max-width: 340px;` to
     `max-width: ${({ $isWebLayout }) => ($isWebLayout ? 480 : 340)}px;` and add an
     explicit font-size override (BodyText's own 16px is otherwise inherited
     unconditionally):
     `font-size: ${({ $isWebLayout }) => ($isWebLayout ? 18 : 16)}px;` (add a
     matching `line-height` bump, e.g. 26px vs BodyText's default 24px, so text
     doesn't feel cramped).
   - In the `screenshots.map(...)` JSX (lines ~152–163), pass
     `$isWebLayout={isWebLayout}` to all three (`ScreenshotItem`,
     `ScreenshotTitle`, `ScreenshotCaption`).
   - Add `testID="screenshot-item"` to the `ScreenshotItem` JSX usage so the new
     test (step 2) can locate its host View — this is additive and does not
     conflict with the component's existing
     `.attrs({ style: { boxShadow: '6px 6px 0 #18382e' } })`, which only sets a
     default `style` prop, not a replacement for other props passed at the call
     site.

2. **`src/features/landing/components/landing-page.test.tsx` — add a sizing
   assertion, after the wiring above exists.**
   - Add a new `describe('LandingPage screenshot showcase sizing', ...)` block
     near the existing "LandingPage platform-based screenshot set" block.
   - Write a small local helper mirroring `resolvedTextStyle` from
     `typography.test.tsx`, adapted to find nodes by `testID` (for
     `ScreenshotItem`) or by visible text (for title/caption, reusing the file's
     existing `findByVisibleText` helper) and picking the match whose
     `props.style` is a plain object.
   - One test mounts at `width: 375` (mobile) and asserts:
     - the first `screenshot-item` node's resolved `style.maxWidth` is `360`.
     - the first screenshot's title node's resolved `style.fontSize` is `19`.
     - the first screenshot's caption node's resolved `style.fontSize` is `16`
       (or `maxWidth` is `340`, whichever proves easiest to isolate — caption
       text nodes may wrap multiple styled layers, so use whichever style field
       is unambiguous once you see the actual rendered output).
   - A second test mounts at `width: 1280` (desktop) and asserts the same three
     fields are strictly greater than their mobile values (560 / 24 / 18+).
   - Keep the existing "renders both a title and a caption" and "platform-based
     screenshot set" tests unchanged — they should keep passing unmodified.

3. **Manual/visual spot check.** Deps aren't installed in the planning worktree,
   so this wasn't run empirically during planning — the implementer should do it
   for real. Per AGENTS.md, use the Expo dev server (`yarn expo start --web`),
   not a static export server, and resize the browser (or use device toolbar) to
   confirm:
   - at ~1280px width, the screenshot frame, title, and caption are visibly
     larger than at a mobile width.
   - at mobile widths (e.g. 375px), the showcase renders identically to before
     this change (this is a regression check, not just a new-behavior check).
   - the five-link web nav still fits at 320px (AGENTS.md's standing constraint) —
     this change shouldn't touch nav, but it's a fast confirmation since the dev
     server is already open.

4. **Run full verification.** `node .claude/scripts/verify.mjs` (all four steps:
   jest, lint, tsc, web export). Fix any fallout before considering the task
   done.

## Order rationale

Styled-component + prop wiring (step 1) must land before the test (step 2) can
reference the new `testID` and conditional style values. Visual check (step 3)
is cheap and catches anything the unit-level style assertions miss (e.g. the
image itself, which sizes via `width: '100%'` and doesn't need direct changes
but is worth eyeballing at both widths). Full verification (step 4) closes out.

## Risks / non-obvious things to watch

- Don't drift the mobile breakpoint values from their current literals — the
  exit criteria explicitly requires unchanged mobile sizing, and it's easy to
  accidentally round a value differently when introducing the conditional.
- `ScreenshotCaption`'s font-size currently comes entirely from `BodyText`
  (`styled(BodyText)` only overrides `max-width`, `text-align`, `color`). Adding
  an explicit `font-size` in `ScreenshotCaption`'s own template is required for
  the desktop bump — don't try to change `BodyText` itself, which is a shared
  primitive used elsewhere on this same page (`Lede`, `Closing`, `FeatureBody`)
  and should stay untouched.
- Verify TypeScript typing on `styled(BodyText)<{ readonly $isWebLayout: boolean }>`
  compiles cleanly — `styled(Component)<Props>` generics occasionally need the
  prop type spelled explicitly rather than inferred; if `tsc` complains, check
  how other `styled(SomeComponent)<{...}>` extensions in the codebase (if any)
  handle it, or fall back to `styled.Text` composition if `styled(BodyText)`
  proves awkward with the new prop.
