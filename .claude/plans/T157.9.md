# T157.9 — Trigger synchronization without disrupting active practice

## Context confirmed before planning

- `src/shared/sync/coordinator.ts` (T157.2) already contains the pure,
  fully-tested `syncCoordinatorReducer` state machine (single-flight run,
  `syncRequested` / `domainSettled` / `identityChanged` actions,
  `queuedRerunTrigger` coalescing where the first trigger wins while a run
  is active, and stale-completion/stale-generation guards). Do not modify
  this file. Its own header comment explicitly defers "the React driver
  hook" to this task.
- All five domain-local sync hooks (`use-profile-domain-sync.ts`,
  `use-custom-trick-domain-sync.ts`, `use-practice-history-domain-sync.ts`,
  `use-goal-domain-sync.ts`, `use-note-domain-sync.ts`) are structurally
  identical copies of one pattern. Each currently exposes only
  `runSync(trigger)` / `isSyncing` / `lastResult`, and each has its own ad
  hoc "login" trigger effect (a `triggeredGenerationRef`-guarded
  `useEffect` that self-fires `runSync('login')` once per identity
  generation once its internal `bothHydrated` flips true). Every hook's own
  comment says this is "superseded once T157.9 wires the real shared
  syncCoordinatorReducer" and that "everything else (foreground, real
  reconnect detection, debouncing) is T157.9". Each hook also has its own
  local `inFlightRef` single-flight guard on `runSync`, described in-line
  as "a deliberately simple per-domain stand-in".
- Grepped every `use-*-domain-sync.test.tsx` and
  `*-provider.sync-sesh-isolation.test.tsx` for reliance on the ad hoc
  login effect: none exists as a real assertion, only one stale comment in
  `use-profile-domain-sync.test.tsx` (~line 284). Every existing assertion
  drives `runSync('manual'|...)` explicitly. Removing the ad hoc login
  effect is safe for existing tests.
- The five domain providers (`user-profile-provider.tsx`,
  `custom-trick-provider.tsx`, `practice-history-provider.tsx`,
  `goal-provider.tsx`, `note-provider.tsx`) each export a Sync context
  interface (`UserProfileSync`, `CustomTrickSync`, `PracticeHistorySync`,
  `GoalSync`, `NoteSync`) with exactly `{ runSync, isSyncing, lastResult }`
  today, and a `useXSync()` hook that throws outside its own provider.
- `src/app/app/_layout.tsx` nests all five domain providers
  (`CustomTrickProvider > UserProfileProvider > PracticeHistoryProvider >
  NoteProvider > GoalProvider`) around `AppThemeProvider` /
  `KenteiRankAutoPromotion` / `AppTabs`, itself inside `IdentityProvider`.
  Every domain provider blocks rendering its children until its own
  primary reducer has hydrated. Anything mounted innermost (where this
  task's new coordinator provider must go, since it needs to call all five
  `useXSync()` hooks) only ever renders after all five primary reducers
  are hydrated. Sync-envelope hydration is separately/slightly async from
  that, which is exactly why each domain hook's own `bothHydrated` gate
  exists and must be surfaced.
- No `@react-native-community/netinfo` or Realtime dependency exists or
  should be added (Notes: "Do not add Realtime subscriptions"; AGENTS.md:
  web is the only active target). `Platform`/`AppState` from `react-native`
  are already used this way in `src/features/home/hooks/use-live-clock.ts`
  (jest-expo auto-mocks `AppState`, no explicit `jest.mock` needed).
- Test tooling in this repo is plain `react-test-renderer` plus a
  captured-ref "expose the hook result" component and
  `jest.useFakeTimers()`; there is no `@testing-library/react-hooks`/RTL.
  Reuse this convention, per `use-live-clock.test.tsx` and
  `use-profile-domain-sync.test.tsx`.

## Design decisions this plan settles

1. Login/foreground/reconnect/manual all funnel through one
   `requestSync(trigger)` call into the shared reducer. The reducer's
   existing `queuedRerunTrigger` coalescing already satisfies "overlapping
   triggers coalesce into a single-flight run" for any two of these — no
   additional debounce is needed for them beyond a light foreground-repeat
   throttle (AppState can fire `'change'` more than once in quick
   succession) and a login once-per-generation guard. Local-mutation is
   the one trigger that genuinely needs debouncing (batching several rapid
   edits into one push instead of one run per keystroke-level change),
   implemented as a real `setTimeout` debounce in the driver hook, not the
   reducer.
2. The ad hoc per-domain login effect is retired at the trigger level, not
   the guard level. Delete the `triggeredGenerationRef` effect from all
   five hooks (this task now owns firing `'login'`). Leave each hook's
   `inFlightRef` single-flight guard in place as defense in depth against
   any direct `runSync()` call bypassing the coordinator (tests do this
   deliberately); update its comment to say the coordinator is now the
   real single-flight authority.
3. Each domain hook gains exactly two new surface fields: `hasHydrated:
   boolean` (= today's internal `bothHydrated`) and `localMutationTick:
   number` (a counter incremented once per enqueued local-mutation diff).
   These are the only two facts the coordinator needs from a domain beyond
   `runSync`. Both are plain render-time values (not stashed only in a
   ref) so the coordinator's own effects can depend on them directly.
4. New files, not a rewrite of `coordinator.ts`:
   - `src/shared/sync/use-sync-coordinator.ts` — the pure-React driver
     hook, unit-testable with fake domain handles, no context dependency
     (mirrors how `use-profile-domain-sync.ts` derives identity internally
     via `useIdentityHandle()` rather than taking it as a prop).
   - `src/shared/sync/sync-coordinator-provider.tsx` — thin context
     wrapper that calls the five real `useXSync()` hooks, builds the
     `SyncDomainHandles` map, calls `useSyncCoordinator`, and exposes
     `useSyncCoordinatorStatus()` (throws outside the provider, matching
     every other `useXSync()` convention) — exposed now for T160.1's
     future Profile surface and for tests; no UI consumes it yet.
5. Reconnect trigger = browser `online` event, web-only, not Realtime.
   `Platform.OS === 'web' && typeof window !== 'undefined'` guard,
   `window.addEventListener('online', ...)`. This is a plain connectivity
   signal, unrelated to Supabase Realtime channels — does not violate "do
   not add Realtime subscriptions".
6. "Offline events remain pending" is proven at the outbox level, not by
   inventing a new browser-offline-detection gate. A trigger fired while
   the network is down simply runs, and every domain's `runSyncImpl`
   (already built, T157.4–T157.8) catches the network failure and returns
   `{status:'failed'}` without acknowledging any outbox operation — so the
   mutation stays durably pending in that domain's own envelope exactly as
   already proven by each domain's own "offline create" tests. The
   coordinator's job is only to ensure a failed/offline run still reaches
   `completed` (never wedges) so the next trigger (e.g. `'reconnect'`) can
   run normally — that's what the new coordinator-level tests must show.

### 2. `src/shared/sync/use-sync-coordinator.ts` (new)

```ts
export interface SyncDomainHandle {
  readonly runSync: (trigger: SyncTrigger) => Promise<DomainSyncRecord>;
  readonly hasHydrated: boolean;
  readonly localMutationTick: number;
}
export type SyncDomainHandles = Readonly<Record<SyncDomain, SyncDomainHandle>>;
export interface UseSyncCoordinatorResult {
  readonly state: SyncCoordinatorState;
  readonly requestManualSync: () => void;
}
export function useSyncCoordinator(domains: SyncDomainHandles): UseSyncCoordinatorResult
```

Internals (never call `Date.now()`/timers/`Math.random()` inside
`syncCoordinatorReducer` itself — matches `sesh.ts`'s reducer-authority
rule, generalized here; every timestamp/id is generated in the hook and
passed through the action):

- `identity`, `generation` via `useIdentityHandle()` (derived internally,
  same convention as every domain hook — do not accept identity as a prop).
- `const [state, dispatch] = useReducer(syncCoordinatorReducer, generation,
  createInitialCoordinatorState)`.
- `domainsRef`, synced in a `useLayoutEffect` every render (same
  ref-stashing convention as `latestRef` in every domain hook) — so the
  async run-driver effect below always reads the latest `runSync`
  functions without depending on the whole `domains` object (a fresh
  object literal every render from the provider wrapper).
- `isMountedRef`, set to `false` in the outermost effect's cleanup — the
  concrete "unmount cancels stale work" mechanism, guarding every
  `dispatch` reached via an async `.then()`.
- `requestSync = useCallback((trigger) => { if (identity.kind !== 'user')
  return; dispatch({ type: 'syncRequested', trigger, identityGeneration:
  generation, runId: createSyncRunId(), now: Date.now() }); }, [identity,
  generation])`.
- Identity-change cancellation effect: a ref holding the previously seen
  `generation`; when it changes, dispatch `identityChanged` (the reducer
  already cancels any in-flight run and clears `pendingRerunTrigger` — do
  not reimplement that logic here) and clear the local-mutation debounce
  timer synchronously in the same branch (don't wait for the debounce
  effect's own cleanup ordering) so a stale identity's queued debounce can
  never fire a trigger under the new identity.
- Run-driver effect: depends on `state`. When `state.status === 'running'`
  and `state.run.runId` differs from a `startedRunIdRef`, mark the ref and,
  for every entry in `SYNC_DOMAINS`, call
  `domainsRef.current[domain].runSync(trigger)` (trigger/runId/generation
  captured from `state.run` at kickoff) and on resolution — guarded by
  `isMountedRef.current` only to silence the unmounted-update warning, the
  reducer's own runId/generation check is what makes a stale result inert
  regardless — dispatch `domainSettled`.
- Pending-rerun effect: depends on `state`. When `state.status === 'idle'
  && state.pendingRerunTrigger !== undefined`, and this run hasn't already
  been consumed (track via a ref of the last-run id already re-triggered
  from), call `requestSync(state.pendingRerunTrigger)`.
- Login effect: depends on identity, generation, and all five domains'
  `hasHydrated` values as explicit scalar deps (not the `domains` object).
  Fires `requestSync('login')` once per generation, guarded by a
  `loginFiredGenerationRef`, only when `identity.kind === 'user'` and every
  domain's `hasHydrated` is `true`.
- Local-mutation debounce effect: depends on the five `localMutationTick`
  values as explicit scalar deps. Skip firing on the very first render
  (stash the previous sum in a ref so mount itself doesn't schedule a
  spurious debounce). On any subsequent change, clear the existing timer
  (stored in a ref shared with the identity-change effect above) and
  `setTimeout(() => requestSync('localMutation'),
  LOCAL_MUTATION_DEBOUNCE_MS)`. Clear it in the effect's own cleanup too
  (covers unmount).
- Foreground effect (mount-once): `AppState.addEventListener('change', (s)
  => { if (s !== 'active') return; const now = Date.now(); if (now -
  lastForegroundAtRef.current < FOREGROUND_MIN_INTERVAL_MS) return;
  lastForegroundAtRef.current = now; requestSync('foreground'); })`,
  `.remove()` in cleanup — mirrors `use-live-clock.ts` exactly.
- Reconnect effect (mount-once, web-only): if `Platform.OS !== 'web' ||
  typeof window === 'undefined'` return; else
  `window.addEventListener('online', () => requestSync('reconnect'))`,
  removed in cleanup.
- `requestManualSync = useCallback(() => requestSync('manual'),
  [requestSync])`.
- Export `LOCAL_MUTATION_DEBOUNCE_MS` (suggest `800`) and
  `FOREGROUND_MIN_INTERVAL_MS` (suggest `15_000`) as named constants so
  tests can reference them instead of hardcoding magic numbers (same
  convention as `HOME_CLOCK_INTERVAL_MS` in `use-live-clock.ts`).
- Return `useMemo(() => ({ state, requestManualSync }), [state,
  requestManualSync])`.

### 3. `src/shared/sync/use-sync-coordinator.test.tsx` (new)

Follow the `use-live-clock.test.tsx` / `use-profile-domain-sync.test.tsx`
harness convention: a `HookHost` component calling `useSyncCoordinator`
with injected fake `SyncDomainHandle`s (jest-mocked `runSync` per domain,
controllable `hasHydrated`/`localMutationTick` via props/state so a
rerender can flip them), wrapped in an `IdentityHandleTestProvider`-style
fixture (reuse the pattern from
`user-profile-provider.sync-sesh-isolation.test.tsx`) so generation
changes can be driven directly without going through real Auth. Cover, at
minimum:

1. A single trigger runs all five domains and the exposed `state` reaches
   `idle` / `lastRun.outcome === 'completed'`.
2. Two triggers fired synchronously back-to-back (e.g. two overlapping
   `requestManualSync()` calls, or a manual call immediately followed by a
   simulated `online` event) coalesce into one in-flight run (assert each
   domain's `runSync` mock was called the expected number of times, not
   doubled), and the coalesced trigger automatically starts a second run
   once the first completes.
3. All five `runSync` mocks resolving `{status:'failed', ...}` (simulating
   offline) still reaches `completed`, never throws, and a subsequent
   trigger (mocks now resolving `succeeded`) runs normally — proving a
   failed/offline run never wedges the coordinator.
4. Login fires exactly once per generation: start with one domain's
   `hasHydrated: false`, assert no run started; rerender with all five
   `true`, assert exactly one run with `trigger === 'login'`; rerender
   again at the same generation, assert no second login run.
5. Local-mutation debounce: bump a `localMutationTick` value three times
   within `LOCAL_MUTATION_DEBOUNCE_MS`, advance fake timers just short of
   the window (assert nothing ran yet), advance past it (assert exactly
   one run with `trigger === 'localMutation'`).
6. Foreground throttle: fire two `AppState` `'active'` changes within
   `FOREGROUND_MIN_INTERVAL_MS` (assert one run), advance past the
   interval and fire a third (assert a second run).
7. Reconnect: dispatch `window.dispatchEvent(new Event('online'))`, assert
   a run with `trigger === 'reconnect'`.
8. Manual: call the exposed `requestManualSync()`, assert a run with
   `trigger === 'manual'`.
9. Unmount cancels stale work: bump a `localMutationTick` (schedules the
   debounce timer), unmount before it fires, advance fake timers well past
   the debounce window, assert no domain `runSync` was subsequently
   called, and assert `console.error` was never called (no
   update-on-unmounted-component warning).
10. Logout/identity-change cancels an in-flight run: start a run whose
    domain `runSync` mocks return unresolved (deferred) promises, then
    change the identity handle's generation mid-run (simulate logout),
    assert `state` immediately reflects `idle` at the new generation;
    then resolve the deferred promises and assert `state` is unchanged
    afterward (the stale `domainSettled` dispatches were inert) and no
    console errors were logged.

### 4. `src/shared/sync/sync-coordinator-provider.tsx` (new)

Thin context wrapper:

```tsx
export function SyncCoordinatorProvider({ children }: PropsWithChildren) {
  const profile = useUserProfileSync();
  const customTricks = useCustomTrickSync();
  const practiceHistory = usePracticeHistorySync();
  const goals = useGoalSync();
  const notes = useNoteSync();

  const domains: SyncDomainHandles = {
    profile, customTricks, practiceHistory, goals, notes,
  };

  const status = useSyncCoordinator(domains);

  return (
    <SyncCoordinatorContext.Provider value={status}>{children}</SyncCoordinatorContext.Provider>
  );
}

export function useSyncCoordinatorStatus(): UseSyncCoordinatorResult {
  const status = useContext(SyncCoordinatorContext);
  if (!status) throw new Error('useSyncCoordinatorStatus must be used within SyncCoordinatorProvider.');
  return status;
}
```

No persistence, no hydration fallback screen — this provider owns no
durable state of its own (each domain's own envelope already persists
independently; the coordinator's `SyncCoordinatorState` is intentionally
ephemeral/in-memory only, reset to idle on reload, consistent with
"transient runtime handles outside provider/domain state" language already
used elsewhere in TASKS.md for this same effort).

## Risks / non-obvious pitfalls to flag to the implementer

- Do not leave the old per-domain login effect in place "just in case."
  Leaving both the old ad hoc effect and the new coordinator-driven login
  trigger would mean two independent triggers per domain in production.
  Each domain's own `inFlightRef` would prevent literal double execution,
  but it defeats the entire point of this task (one shared run across all
  five domains via `syncCoordinatorReducer`) and leaves misleading code.
  Delete it, don't duplicate it.
- `domains` object identity churns every render of
  `SyncCoordinatorProvider` (a fresh object literal each time). Depend on
  individual scalar fields (`hasHydrated` booleans, `localMutationTick`
  numbers) in `useEffect` dependency arrays, and stash `runSync` functions
  in a `useLayoutEffect`-synced ref — exactly the pattern every domain
  hook already uses for its own `latestRef`, for the same reason.
- Never add `Date.now()`/`setTimeout`/`Math.random()` inside
  `syncCoordinatorReducer` itself. It is already pure and already fully
  tested; all of that belongs in `use-sync-coordinator.ts`'s effects,
  exactly what the reducer's own header comment expects of "a future
  driver".
- Web-only reconnect signal, no new native dependency. Guard with
  `Platform.OS === 'web' && typeof window !== 'undefined'`; do not add
  `@react-native-community/netinfo`. This is a plain `online`/`offline`
  browser event, not a Realtime subscription — explicitly allowed despite
  the "do not add Realtime subscriptions" constraint, which is about
  Supabase Realtime channels, not browser connectivity events.
- `SyncCoordinatorProvider` must be innermost among the six providers in
  `src/app/app/_layout.tsx` — it calls all five `useXSync()` hooks, each
  of which throws if called outside its own provider.
- Confirm (already grepped once during planning, but re-verify after the
  edit) that no existing test in the five domain-hook suites or the five
  `*-provider.sync-sesh-isolation.test.tsx` files implicitly depended on
  the now-removed automatic login effect; run each suite individually
  before running the full jest suite so any regression is easy to
  localize.
