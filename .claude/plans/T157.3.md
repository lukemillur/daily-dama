# T157.3 — Paginated pulls and idempotent ordered pushes (transport layer)

## Scope boundary (read first)

T157.3 builds a **pure, storage-free, Supabase-free orchestration library** plus
its fake-repository test double. It does **not**:

- touch any `src/features/*` reducer, provider, or `*-cloud-repository.ts`/
  `*-cloud-mapping.ts` file (that's T157.4–T157.8, one domain at a time),
- call `saveSyncEnvelope`/`acknowledgeOutboxOperation`/`recordOutboxOperationAttempt`
  itself (those are the future per-domain *driver*'s job — this task returns
  typed results the driver applies),
- add a real adapter wrapping the concrete `GoalCloudRepository`/
  `CustomTrickCloudRepository`/etc. from T155.9 (that wiring is T157.4+).

This keeps T157.3 at the same layer as `coordinator.ts` (pure state/orchestration,
clock and network fully injected) rather than jumping ahead into domain
integration. New files only:

- `src/shared/sync/transport.ts`
- `src/shared/sync/transport.test.ts`

## Key finding that shapes the design (read before implementing)

I read all five concrete T155.9 repositories
(`src/features/{profile,custom-tricks,goals,notes,stats}/persistence/*-cloud-repository.ts`)
and `src/shared/supabase/{cloud-repository.ts,database-types.ts}`. Two things
that the task description assumes are **not actually present yet** in the
merged T155.9 contracts, and this plan works around them deliberately rather
than silently inventing behavior:

1. **No revision-guarded conditional update exists at the repository layer.**
   Every table has a `revision: number` column (DB-generated types confirm
   this for `custom_tricks`, `goals`, `notes`, `practice_sessions`,
   `profiles`), but none of the five repositories' `update`/`upsert*` methods
   take an `expectedRevision` parameter or do a `.eq('revision', expected)`
   guard — they blindly overwrite and return whatever the server now holds.
   There is no optimistic-concurrency enforcement to "call through to" yet.
2. **No `operation_id` column exists anywhere in `database-types.ts`.** The
   real repos' idempotency for retried creates comes entirely from
   `recordId` (the row's own stable, client-generated PK) via an
   insert-then-update-on-23505 fallback (see `custom-trick-cloud-repository.ts`
   `upsert()` and `profile-cloud-repository.ts` `upsertProfile()` for the
   proven pattern). `goal-cloud-repository.ts` doesn't even do that — it
   exposes separate `insert`/`update` with no fallback. `practice-history-cloud-repository.ts`'s
   `insertMany`/`insert` do a bare `.insert()` with no conflict handling at
   all, so a literal retry-after-lost-ack of an already-committed insert
   would 23505 forever under the current contract.

Given this, T157.3 defines **its own abstract repository contract**
(`SyncTransportRepository<Row>`, below) that is *shaped like* T155.9's
`CloudPage`/`CloudReadResult`/`CloudMutationResult`/`CloudPageRequest`
vocabulary (reusing those exact types — they're plain, Supabase-SDK-free, so
reusing them is not a repository-agnostic violation) but adds:

- a single `push()` method (not `insert`/`update`/`remove` split three ways)
  that takes an idempotency key (`operationId`) and an `expectedRevision`,
  and returns a **third** status, `'conflict'`, alongside `'succeeded'`/`'failed'`,
- a contract that the *implementer* of `push()` — real or fake — is
  responsible for applying idempotently-by-`operationId` and for the
  revision-guard check, exactly the way `custom_tricks`' `upsert()` already
  proves the insert-then-update-on-23505 pattern works for recordId-based
  idempotency today.

Building an adapter that makes the real T155.9 repos actually satisfy this
contract (recordId-idempotent creates already mostly work; revision-guarded
updates and `practice_sessions`' retry gap do not) is explicitly deferred to
T157.4+ — flag this gap to the user/next task rather than silently patching
T155.9 files, since those are merged and out of this task's dependency scope.

## `src/shared/sync/transport.ts` — types

```ts
import type {
  CloudPageRequest,
  CloudRepositoryError,
} from '@/shared/supabase/cloud-repository';
import type { OutboxOperation, OutboxOperationType } from '@/shared/sync/outbox-operation';

export interface SyncTransportPage<Row> {
  readonly items: readonly Row[];
  readonly nextCursor: string | null;
}

export type SyncTransportPullResult<Row> =
  | { readonly status: 'succeeded'; readonly page: SyncTransportPage<Row> }
  | { readonly status: 'failed'; readonly error: CloudRepositoryError };

export interface SyncConflict {
  readonly operationId: string;
  readonly recordId: string;
  readonly expectedRevision: number | null;
  readonly serverRevision: number;
}

export type SyncTransportPushResult<Row> =
  | { readonly status: 'succeeded'; readonly row: Row }
  | { readonly status: 'conflict'; readonly conflict: SyncConflict }
  | { readonly status: 'failed'; readonly error: CloudRepositoryError };

export interface SyncPushRequest {
  readonly operationId: string;
  readonly recordId: string;
  readonly operationType: OutboxOperationType;
  readonly payload: Record<string, unknown> | null;
  readonly expectedRevision: number | null; // null = "no known prior revision" (a create)
}

export interface SyncTransportRepository<Row> {
  pull(request: CloudPageRequest): Promise<SyncTransportPullResult<Row>>;
  push(request: SyncPushRequest): Promise<SyncTransportPushResult<Row>>;
}
```

Note `CloudPageRequest`/`CloudRepositoryError` come from
`src/shared/supabase/cloud-repository.ts`, which has zero `@supabase/supabase-js`
import (verified) — pure vocabulary. Reusing it keeps one pagination-cursor/error
vocabulary across the codebase instead of a second parallel one, without
coupling `transport.ts` to the Supabase SDK.

## `src/shared/sync/transport.ts` — `pullAllPages`

```ts
export interface PullAllPagesOptions {
  readonly pageSize: number;
  readonly startCursor: string | null;
  readonly maxPages?: number; // default e.g. 10_000; safety cap against a
                               // buggy/non-terminating nextCursor, never hit
                               // in normal operation
}

export type PullAllPagesResult<Row> =
  | { readonly status: 'succeeded'; readonly rows: readonly Row[]; readonly finalCursor: null }
  | {
      readonly status: 'failed';
      readonly error: CloudRepositoryError;
      readonly rowsPulledSoFar: readonly Row[];
      readonly cursorAtFailure: string | null; // caller can resume from here on retry
    };

export async function pullAllPages<Row>(
  repository: Pick<SyncTransportRepository<Row>, 'pull'>,
  options: PullAllPagesOptions,
): Promise<PullAllPagesResult<Row>>
```

Implementation: loop calling `repository.pull({ limit: pageSize, cursor })`,
accumulate `page.items`, advance `cursor = page.nextCursor`, stop when
`nextCursor === null` (succeeded) or a page fails (failed, returning partial
progress + the cursor it failed at so a caller *could* resume — resuming
itself is not implemented here, just data returned to make it possible).
Throw only if `maxPages` is exceeded (a real bug, not a normal outcome — same
philosophy as `decodeCloudCursor` throwing loudly on a malformed cursor rather
than silently truncating).

Deliberately **does not** call `updateSyncCursor`/`saveSyncEnvelope` — cursor
persistence stays the caller's job, keeping this function free of storage
side effects (mirrors `coordinator.ts` being free of `Date.now()`/network).

## `src/shared/sync/transport.ts` — `pushOutboxOperations`

```ts
export interface PushOutboxOperationsOptions {
  // Caller-supplied because "expected revision" is not part of
  // OutboxOperation (T157.1 deliberately kept `payload` domain-agnostic, and
  // `operationType === 'delete'` operations always have `payload: null` per
  // outbox-operation.ts's own validation, so revision can't ride in payload
  // for deletes). A real per-domain driver (T157.4+) is expected to close
  // over its own local revision cache (e.g. "last known server revision per
  // recordId") here, not parse it out of `operation.payload`.
  readonly getExpectedRevision: (operation: OutboxOperation) => number | null;
}

export interface PushOperationOutcome<Row> {
  readonly operationId: string;
  readonly recordId: string;
  readonly result: SyncTransportPushResult<Row>;
}

export interface PushOutboxOperationsResult<Row> {
  readonly outcomes: readonly PushOperationOutcome<Row>[]; // one per input operation, same order
}

export async function pushOutboxOperations<Row>(
  repository: Pick<SyncTransportRepository<Row>, 'push'>,
  operations: readonly OutboxOperation[],
  options: PushOutboxOperationsOptions,
): Promise<PushOutboxOperationsResult<Row>>
```

Implementation: plain sequential `for` loop over `operations` (outbox order =
FIFO, matches `sync-envelope.ts`'s `outbox` invariant), calling
`repository.push(...)` and pushing every outcome onto the result array
regardless of status. **Never breaks/returns early** on `'conflict'` or
`'failed'` — this is the literal mechanism for "continue unrelated operations
after one conflict." (Decision: also continues past a `'failed'` network
error for the same reason — each operation's outcome is independent and the
future driver is expected to inspect `attemptCount`/retry policy per
operation, not have one network blip silently swallow the rest of the queue.
Call this out to the user as a deliberate simplification if they want
different behavior, e.g. short-circuiting after N consecutive network
failures — nothing in the exit criteria requires it.)

## Fake repository test double (in `transport.test.ts`)

Define a minimal concrete row shape and an in-memory
`createFakeSyncTransportRepository`:

```ts
interface FakeRow {
  readonly id: string;
  readonly revision: number;
  readonly createdAt: number;
  readonly updatedAt: number;
  readonly deletedAt: number | null;
  readonly fields: Record<string, unknown>; // opaque payload passthrough
}

function createFakeSyncTransportRepository(options: {
  now: () => number; // injected clock, never Date.now()
  seed?: readonly FakeRow[]; // for the >1000-fixture pull test
}): SyncTransportRepository<FakeRow> & {
  // test-only inspection hooks, not part of the transport contract:
  getStoredRow(id: string): FakeRow | undefined;
  seedRevision(id: string, revision: number): void; // simulate "another device already edited this"
}
```

Internal state: `Map<string, FakeRow>` keyed by `recordId`, plus
`Map<string, SyncTransportPushResult<FakeRow>>` keyed by `operationId` — the
literal idempotency ledger.

`pull()`: sort the map's values by `(createdAt desc, id asc)` — the exact
tiebreak already proven at the DB level in T155.8/used by every real T155.9
repo — slice by the offset encoded in `cursor` via `decodeCloudCursor`/
`encodeCloudCursor` (reuse those two functions directly; no need to reinvent
cursor encoding), return `nextCursor: null` once exhausted.

`push()`:
1. If `operationId` is already in the op ledger, return the cached result
   verbatim **without touching the row map** — this is the idempotent-retry
   short-circuit.
2. Else, for `operationType === 'upsert'`:
   - if a row with `recordId` exists and `expectedRevision !== existingRow.revision`,
     build a `'conflict'` result (do **not** mutate the stored row), store it
     in the ledger under `operationId`, and return it.
   - else apply the upsert (create at `revision: 1` if new, else
     `revision: existing.revision + 1`), stamp `updatedAt`/`createdAt` from
     the injected clock (never from `payload`, modeling "server owns these
     fields"), store the row, build a `'succeeded'` result, store it in the
     ledger, return it.
3. For `operationType === 'delete'`: same conflict check against
   `expectedRevision`; on match, set `deletedAt` from the clock (tombstone,
   matching `goals`/`notes`/`practice_sessions` — do not hard-delete from the
   map, matching "list does not filter tombstones" per T155.9's own comment).
4. No network-fault mode is needed beyond this ledger — see the idempotency
   test design below for why a literal dropped-response simulation isn't
   necessary to prove the exit criterion.

## Test cases (`transport.test.ts`)

Numbered like `coordinator.test.ts`'s style (`'1. ...'`, `'2. ...'`).

**`pullAllPages`**
1. Pulls >1,000 ordered fixtures (use 1,200, matching T155.8's already-proven
   fixture count) with a page size that does *not* evenly divide it (e.g.
   47) — assert: total rows === 1200, zero duplicate ids (`Set` size check),
   order matches the fixtures' expected `(createdAt desc, id asc)` order,
   and `finalCursor === null`.
2. Empty repository: one call, `status: 'succeeded'`, `rows: []`.
3. Exactly one full page then a second call returning an empty
   nextCursor-terminated page (boundary: page size exactly divides fixture
   count) — no off-by-one duplicate/gap at the boundary.
4. A `pull()` failure on page 3 of N returns `status: 'failed'` with
   `rowsPulledSoFar` containing exactly the first two pages' rows (not
   dropped) and `cursorAtFailure` set to what page 3 was requested with.
5. Exceeding `maxPages` throws (construct a repository whose `pull()` always
   returns a fresh non-null `nextCursor`, i.e. never terminates).

**`pushOutboxOperations` — idempotency (the "lost ack" scenario)**
6. Push one `upsert` operation once: succeeds, row exists at revision 1.
   Build a *second*, distinct `OutboxOperation` array containing an
   operation with the **same `operationId`** (as if the client never saw the
   first response and is retrying an un-acknowledged outbox entry — this is
   the literal "simulated lost acknowledgement," modeled by the client simply
   not having called `acknowledgeOutboxOperation`, not by faking a dropped
   HTTP response) and call `pushOutboxOperations` again: assert `status:
   'succeeded'`, the returned row is `toEqual` the first call's row exactly
   (same `revision: 1`, same `updatedAt`), and `getStoredRow` still shows
   exactly one row at `revision: 1` — no duplication, no double-increment.
7. Same idempotency check for a `delete` operation retried twice: second
   call returns the same tombstoned row, `deletedAt` unchanged between calls.

**`pushOutboxOperations` — conflicts**
8. Seed a row at revision 1. Call `seedRevision(id, 2)` to simulate another
   device's edit landing first. Push an `upsert` operation whose
   `getExpectedRevision` returns 1 (stale): assert `status: 'conflict'`,
   `conflict.expectedRevision === 1`, `conflict.serverRevision === 2`, and
   `getStoredRow` still shows the pre-push state untouched (the stale write
   was rejected, not applied).
9. A genuine create (`expectedRevision: null`) against a `recordId` that
   does *not* yet exist always succeeds regardless of any other row's
   revision — proves `null` means "no prior knowledge," not "expect
   revision 0."

**`pushOutboxOperations` — server metadata authority**
10. Push a create whose `payload` includes made-up `revision`/`updatedAt`-like
    fields the client might optimistically guess (irrelevant plain data in
    `fields`); assert the returned row's `revision`/`createdAt`/`updatedAt`
    come from the fake's injected clock/counter, not anything echoed from
    `payload` — proves the transport surfaces authoritative server state.

**`pushOutboxOperations` — continue after one conflict**
11. Build an outbox of three operations against three different `recordId`s.
    Seed the second record's revision to force a conflict. Call
    `pushOutboxOperations` once with all three: assert `outcomes[0].result.status
    === 'succeeded'`, `outcomes[1].result.status === 'conflict'`,
    `outcomes[2].result.status === 'succeeded'`, and that all three
    `operationId`s/`recordId`s round-trip correctly in order — proves one
    conflict doesn't block or skip sibling operations, and results stay
    correctly associated with their originating operation.
12. Same shape but the middle operation gets a `'failed'` (network) result
    instead of a conflict (fake configured to fail on a specific
    `recordId`) — same "operations 1 and 3 still succeed" assertion, since
    the plan's decision above is to also continue past `'failed'`.

## Implementation order

1. Write `SyncTransportRepository`/`SyncPushRequest`/result types in
   `transport.ts` first (no logic yet) — this is the contract everything
   else, including the fake, is built against.
2. Implement `pullAllPages` and its tests (1–5) — no idempotency/conflict
   complexity, gets the pagination-loop shape and the fake's `pull()` right
   before layering push semantics on top.
3. Implement the fake's `push()` (ledger + revision-guard + tombstone
   branches) and `pushOutboxOperations`, then tests 6–12 in the order
   listed (idempotency before conflicts before continue-after-conflict) —
   each test group depends on the fake behavior the previous group already
   locked down.
4. Run `node .claude/scripts/verify.mjs --skip-export` (this is pure
   TS/jest work, no UI surface touched, so skipping the web export is
   appropriate per AGENTS.md's own guidance) once all tests are green.

## Risks / non-obvious things to flag to the implementer

- The single biggest risk is silently over-scoping into T157.4 territory
  (wiring a real domain provider/reducer to this transport). Resist that;
  the fake repository and these 12 tests are the actual deliverable.
- Do not let `pushOutboxOperations`' `getExpectedRevision` callback tempt you
  into reading `operation.payload.expectedRevision` inside `transport.ts`
  itself — `payload` is `null` for deletes by `outbox-operation.ts`'s own
  validation, so any such assumption breaks immediately for that operation
  type. Keep the callback fully caller-supplied.
- Flag the `practice_sessions` real-repository retry gap (bare `.insert()`,
  no 23505 fallback) to the user/TASKS.md as a known follow-up for whoever
  picks up T157.6, rather than fixing `practice-history-cloud-repository.ts`
  in this task (it's outside T157.3's dependency scope and outside "pure
  local transport-library" scope).
