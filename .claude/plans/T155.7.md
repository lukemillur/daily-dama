# T155.7 — Add explicit authenticated grants and row-level security

## Audit conclusion (verified live against a fresh local Supabase stack)

I started the local stack (`supabase start` + `db reset`) and drove the real
Data API over HTTP (not assumptions) to check every exit-criterion claim
before planning further work. Findings:

- RLS is `ENABLE`d on all six exposed tables (`profiles`, `user_trick_states`,
  `custom_tricks`, `practice_sessions`, `goals`, `notes`) — confirmed via
  `pg_class.relrowsecurity`. There is no exposed table missing RLS.
- Every table has a distinct, column-scoped grant per operation (verified via
  `information_schema.role_column_grants` / `role_table_grants` for
  `authenticated`). `practice_sessions` has `SELECT, INSERT` only — no
  `UPDATE`/`DELETE` grant exists at all, confirmed live: an owner's own
  `PATCH`/`DELETE` against their own `practice_sessions` row returns `403`
  `42501` ("permission denied for table practice_sessions").
- Cross-user isolation already works correctly end-to-end for every table I
  probed (`profiles`, `custom_tricks`, `practice_sessions`): user B's
  `SELECT`/`PATCH`/`DELETE` filtered against user A's row returns `200` with
  an **empty array** (RLS silently filters the row before the grant/operation
  ever "fails" — there is no error, just zero matching rows), and user A's row
  is unchanged afterward.
- Ownership reassignment is already rejected two ways: inserting a row that
  claims another user's `user_id` fails RLS `WITH CHECK` (`403`/`42501`), and
  repointing an existing row's `user_id` via `PATCH` fails even earlier,
  because `user_id` was never included in any table's column-scoped `UPDATE`
  grant (T155.5) — also `403`/`42501`, but for a different underlying reason
  (privilege, not policy). Both are real, both are already enforced.
- Anonymous access is denied for every table: a request using only the `anon`
  key gets `401` with `{"code":"42501","message":"permission denied for
  schema api"}`, because T155.1 deliberately never granted `anon` `USAGE ON
  SCHEMA api` at all. This is a schema-level denial, not a per-table RLS
  denial — worth knowing so a test doesn't mis-assert on the wrong layer.

**One genuine gap found:** `api.profiles` still carries `DELETE` in T155.2's
original `grant select, insert, update, delete on api.profiles to
authenticated` — verified live: an authenticated user can `DELETE
/rest/v1/profiles?user_id=eq.<self>` and it succeeds (`200`, row returned and
gone). This directly contradicts that same migration's own comment: *"No
tombstone column: a profile is deleted only by `on delete cascade`... never by
a client-initiated soft delete."* `user_trick_states`' `DELETE` grant, by
contrast, **is** correct and load-bearing: the
`user_trick_states_has_state check (is_selected or is_manually_unlocked)`
constraint means the only way for a client to fully clear both flags is to
delete the row — there's no legal "both false" `UPDATE`. `custom_tricks`'
`DELETE` grant is also correct and explicitly deliberate per its own
migration comment (full CRUD, no tombstone requirement).

So: **this task is an audit-confirms-mostly-correct pass, plus one real
grant-narrowing fix, plus closing a real raw-HTTP test-coverage gap** — no
new tables, no RLS redesign. Everything below is scoped accordingly.

## Ordered implementation steps

### 1. New migration: close the `api.profiles` DELETE gap + FORCE RLS (defense-in-depth)

Create `supabase/migrations/<timestamp>_close_profile_delete_grant_gap.sql`
with a timestamp later than the existing latest
(`20260822210000_protect_server_owned_timestamps_and_ownership.sql`) — do
**not** edit any already-merged migration file (append-only convention, per
existing file history).

Content:

- `revoke delete on api.profiles from authenticated;`
- Replace T155.2's single `profiles_own_row for all` policy with three
  explicit policies (`profiles_select_own`, `profiles_insert_own`,
  `profiles_update_own`), matching the split-policy style T155.4 already
  established for `goals`/`notes`. This isn't strictly required for
  correctness (grant absence alone already blocks `DELETE`, the same pattern
  `practice_sessions` already relies on) but removes a latent trap: today the
  `for all` policy silently still *covers* `DELETE` even though no grant
  reaches it, so a future accidental `GRANT DELETE` would immediately become
  exploitable with zero policy change needed. Splitting the policy removes
  that landmine now while it's free.
  ```sql
  drop policy profiles_own_row on api.profiles;

  create policy profiles_select_own on api.profiles
    for select to authenticated using (user_id = auth.uid());
  create policy profiles_insert_own on api.profiles
    for insert to authenticated with check (user_id = auth.uid());
  create policy profiles_update_own on api.profiles
    for update to authenticated using (user_id = auth.uid()) with check (user_id = auth.uid());
  ```
- `alter table api.<t> force row level security;` for all six tables
  (`profiles`, `user_trick_states`, `custom_tricks`, `practice_sessions`,
  `goals`, `notes`). **Write the comment honestly**: I confirmed live
  (`select rolname, rolsuper, rolbypassrls from pg_roles`) that the `postgres`
  migration/owner role has `rolbypassrls = true` as a *directly granted role
  attribute*, not merely via table ownership — so `FORCE ROW LEVEL SECURITY`
  changes no observable behavior today (BYPASSRLS always wins over FORCE, by
  Postgres's own semantics) and no test can demonstrate it doing anything.
  Add it only as recorded defense-in-depth against a future owner-role change
  that lacks `BYPASSRLS`; say this plainly in the migration comment so a
  future reader doesn't go looking for a test that proves it.

Why this table/order: the migration must land before any new test (pgTAP or
HTTP) that asserts the fixed behavior, because `db reset` replays migrations
top-to-bottom and both new test suites below depend on `profiles` `DELETE`
already being rejected.

### 2. New pgTAP file: prove grants and RLS block independently

Add `supabase/tests/t155_7_grants_and_rls_independence.test.sql`, same
`begin; ... select plan(N); ... select * from finish(); rollback;` shape as
the existing four files. Scope to **three representative tables**, not all
six — the remaining three (`user_trick_states`, `custom_tricks`, `notes`)
share the identical grant/RLS mechanics already exercised for ownership at
the SQL level in `t155_2`–`t155_5`; re-deriving independence for all six would
be repetitive without adding real coverage. Cover:

- **`api.practice_sessions`** (select/insert-only shape)
- **`api.goals`** (select/insert/update-no-delete, tombstoned shape)
- **`api.profiles`** (the just-fixed gap — this doubles as a regression test
  proving step 1's fix is real, not just today's live probe)

For each table, two directions, using fixture rows + `set local role
authenticated` + `set_config('request.jwt.claims', ...)`, matching the exact
pattern already used at the bottom of `t155_2_profiles_and_trick_states.test.sql`:

**(a) Grants block even with RLS disabled** (proves privilege alone denies
the operation, not incidentally masked by a policy that would have denied it
anyway):
```sql
alter table api.practice_sessions disable row level security;
-- as authenticated/user A:
select throws_ok($$ update api.practice_sessions set lace_count = 1 where user_id = '<A>' $$,
  '42501', null, 'grants alone block UPDATE on practice_sessions even with RLS disabled');
select throws_ok($$ delete from api.practice_sessions where user_id = '<A>' $$,
  '42501', null, 'grants alone block DELETE on practice_sessions even with RLS disabled');
alter table api.practice_sessions enable row level security;
```
Repeat for `goals` (`DELETE`) and `profiles` (`DELETE`, post-fix).

**(b) RLS blocks even with grants maximally widened** (proves the policy
alone denies cross-user access, not incidentally relying on a narrower grant
that happens to also block it):
```sql
grant delete on api.profiles to authenticated; -- temporarily wider than intended
-- as authenticated/user B, attempt against A's existing row:
select is(
  (select count(*)::int from api.profiles where user_id = '<A>'), 1,
  'sanity: A''s profile still exists before the widened-grant probe'
);
-- (delete as B against A's row, then re-check as postgres that the row is untouched)
delete from api.profiles where user_id = '<A>';  -- RLS should silently match 0 rows, not error
reset role;
select is(
  (select count(*)::int from api.profiles where user_id = '<A>'), 1,
  'RLS alone still protects A''s row even though authenticated was just granted DELETE'
);
revoke delete on api.profiles from authenticated;
```
Repeat the same shape for `practice_sessions` (temporarily `grant update`)
and `goals` (temporarily `grant delete`) against another user's row.

Note: `ALTER TABLE ... {DIS,EN}ABLE ROW LEVEL SECURITY` and `GRANT`/`REVOKE`
are transactional DDL, so the outer `rollback;` would undo all of this anyway
— restore explicitly regardless, so the file stays correct and
self-documenting if anyone ever runs a block of it outside the wrapping
transaction.

Run `supabase db reset && supabase test db --local` locally to confirm this
new file passes alongside the four existing ones (regression check that nothing
in steps 1–2 broke `t155_2`–`t155_5`).

### 3. New Data API (HTTP) test files: the actual "raw HTTP tests" the exit criteria ask for

Two new files under `supabase/tests/data-api/`, reusing
`supabase/tests/data-api/lib/local-supabase.mjs` exactly as `t155_6_*` does.

**3a. `t155_7_anonymous_denial.test.mjs`** — no user creation needed (cheap,
fast). Add a small `anonClient(config)` helper to `local-supabase.mjs`
(mirrors `restClient`, but both `apikey` and `Authorization` use the anon
key — no signed-in session), then for each of the six `api.*` tables:
`GET` the collection root and assert `status === 401` and
`body.code === '42501'`. One parameterized `test()` per table is enough;
don't invent six near-identical describe blocks.

**3b. `t155_7_cross_user_isolation.test.mjs`** — `before()` creates two
confirmed users (A, B), signs both in, builds two `restClient`s (same
`primaryClient`/`probeClient` naming convention as `t155_6_profiles`).
`after()` deletes both (cascade cleanup, same as existing files). One
`describe` per table, six total:

For every table, assert (only what the existing `t155_6_*` suite does *not*
already cover — don't re-prove valid-insert/valid-patch shapes that already
have coverage):
- A creates a row.
- B's filtered `GET` against A's row → `200`, `[]`.
- B's filtered `PATCH` (with `Prefer: return=representation` — see pitfall
  below) against A's row → `200`, `[]` (zero rows touched).
- Where the table has a `DELETE` grant at all (`custom_tricks`,
  `user_trick_states`; **not** `profiles` post-fix, **not**
  `practice_sessions`, **not** `goals`/`notes`): B's filtered `DELETE`
  (`Prefer: return=representation`) against A's row → `200`, `[]`.
- Re-`GET` as A after each probe → row unchanged / still present.
- A's `POST` claiming `user_id: <B's id>` → `403`, `code: '42501'`.
- A's `PATCH` on their own row setting `user_id: <B's id>` → `403`,
  `code: '42501'`.

Add these table-specific extras in the same file, since the exit criteria
name them explicitly:
- **`practice_sessions`**: A's own-row `PATCH` → `403`/`42501`; A's own-row
  `DELETE` (`Prefer: return=representation`, raw `fetch` since `restClient`
  has no `delete` method today — add one, mirroring `get`/`post`/`patch`) →
  `403`/`42501`. This is the literal "denial of practice-session
  updates/deletes even by the owner" exit criterion.
- **`profiles`**: A's own-row `DELETE` → `403`/`42501` (regression proof of
  step 1's fix, now visible at the real HTTP layer, not just the live probe
  I ran during this audit).
- **`goals`/`notes`**: A's own-row `DELETE` → `403`/`42501` (no delete grant
  exists on either; this is the "correct allowed operations" criterion for
  the two tombstoned tables).

**Pitfall to flag for the implementer**: PostgREST returns `204` with an
empty body for a `PATCH`/`DELETE` that matches zero rows *by default* —
that alone cannot distinguish "succeeded, touched 0 rows" from "succeeded,
touched N rows," so a bare status-code assertion is not a real isolation
proof. Add `Prefer: return=representation` to these specific requests so the
response is `200` with a JSON array whose length is the real signal — I
confirmed this live (`content-range` header alone was uselessly `*/*` in
this local setup; the returned array length is the reliable check).

`restClient` in `local-supabase.mjs` already threads `extraHeaders` through
`patch`; extend it with a `delete` method of the same shape, and add
`Prefer: return=representation` support via `extraHeaders` at each call site
that needs it (don't bake it into the client defaults — most `t155_6_*`
calls rely on the current `204`/plain-body behavior and shouldn't change).

## Risks / non-obvious things to carry into implementation

- The `profiles` DELETE gap is the only functional schema change in this
  task. Everything else is test coverage. Don't be tempted to "improve"
  other tables' grants while in here — they're already audited correct and
  every additional touch is additional risk for zero exit-criteria benefit.
- `FORCE ROW LEVEL SECURITY` is genuinely inert today (verified: `postgres`
  has `rolbypassrls = true` directly). Add it for defense-in-depth as
  instructed by the task notes, but do not write a test that claims to prove
  it does something — there is nothing to observe yet.
- Anonymous denial is a schema-level `USAGE` failure (`42501` "permission
  denied for schema api"), not a table-level RLS failure — assert on that
  specific code/message, verified live, not on a guessed RLS-style error.
- `user_trick_states`' `DELETE` grant is correct and must not be touched —
  it's the only legal way for a client to fully clear
  `is_selected`/`is_manually_unlocked` together, per that table's own CHECK
  constraint. `custom_tricks`' `DELETE` grant is also correct and deliberate.
  Only `profiles` is the outlier.
- Migrations are append-only in this repo (confirmed via file history/naming
  convention) — add a new timestamped file, never edit
  `20260822193659_add_profiles_and_user_trick_states.sql` in place even
  though that's where the original over-broad grant was introduced.
