# T159.3 — Merge immutable records and trick state into an existing account

## Iteration boundary

Good enough for this ticket is an existing-account import path that classifies the complete guest and cloud snapshots before writing, uploads only records that can be unioned without data loss, deduplicates canonical payload matches, unions focused/manually-laced trick flags, and durably records every same-ID/different-payload collision for T159.4. The path must preserve the cloud profile/preferences for the later explicit profile choice and must reach `awaitingProfileChoice` after all non-conflicting work settles.

This ticket does not add profile-choice UI, conflict-resolution UI or choices, final guest-namespace deletion, account switching, or new generic synchronization UX. T159.4 owns the user's profile/conflict decisions; T159.5 owns final acknowledgement auditing and namespace cleanup. T159.3 may remove an individual guest source record only after its accepted write is durably acknowledged, following T159.2's existing rule. Deduplicated, conflicted, and profile-choice source facts remain available for those later tickets.

## Confirmed implementation context

- T159.1 provides the pure `guestImportReducer`, identity-scoped persisted `GuestImportState`, `awaitingProfileChoice`/`conflicts` phases, and full-cloud inventory. The current conflict shape is only a `{ domain, recordId }` placeholder and is not sufficient for deterministic comparisons or later resolution.
- T159.2 provides `readGuestImportSnapshot`, `prepareGuestImport`, `runEmptyGuestImport`, stable import operation IDs, per-operation progress, and acknowledgement-before-source-cleanup. Its hook deliberately runs only when `targetKind === 'empty'`; an existing target currently remains in `uploading`.
- The cloud boundary already exposes the target profile row, paginated trick-state rows, and paginated custom-trick, practice-session, goal, and note rows. Existing row-to-domain mappers are the runtime-validation boundary and must be reused.
- `practice_sessions` are insert-only and have no revision. Custom tricks, goals, notes, profile, and trick-state rows are revisioned; goals/notes also retain tombstones. The existing normal-sync adapters may use an unconditional first-push collision fallback when no revision is known, while the practice-session adapter treats any duplicate ID as an idempotent success. The existing-account import must not call those fallbacks for an unclassified collision, because either behavior could hide a same-ID/different-payload conflict.
- `SyncConflictRecord` is the normal-sync conflict contract and intentionally excludes immutable practice history. Guest-import conflicts therefore remain a separate persisted contract (they may include `practiceHistory`) while reusing the shared JSON-safe `ConflictSnapshot` value type/validator where useful.
- T160.2's conflict UI/resolution records are not the owner of this import flow. Do not write guest-import conflicts into ordinary domain sync envelopes or couple this ticket to `/app/profile/sync-conflicts`.

The task assumptions and exit criteria remain valid. The implementation must treat the profile domain as two boundaries: scalar profile/preferences are preserved for T159.4's explicit choice, while `user_trick_states` are merged here.

## Deterministic merge rules

All equality checks compare canonical client-owned payloads, not raw cloud rows. Convert validated cloud rows back through the existing domain mappings and `map*To*Input` functions so `user_id`, server `revision`, `created_at`, `updated_at`, and tombstone timestamps cannot create false differences. Sort domains in `SYNC_DOMAINS` order and records by stable ID before assigning operation IDs or conflicts.

| Boundary | Guest only / disjoint ID | Same ID, canonical payload equal | Same ID, canonical payload different |
| --- | --- | --- | --- |
| Profile scalar/preferences | Do not upload in this ticket; persist guest/cloud comparison for T159.4 | Still defer the explicit choice; do not infer a preference | Still defer the explicit choice; this is a profile choice, not a record conflict |
| Focused/manually-laced trick state | Insert the guest flags | Deduplicate without a write | Logical-OR each flag. If OR changes the target row, emit one revision-guarded union upsert; if the target already contains both truths, deduplicate. Trick-state overlap is never a conflict because both facts can coexist without loss |
| Custom tricks/sequences | Insert the guest record | Deduplicate without a write | Emit a guest-import conflict; do not update/delete the target |
| Immutable practice sessions | Insert the guest record | Deduplicate without a write | Emit a guest-import conflict; never treat the duplicate ID alone as acknowledgement and never mutate the target |
| Goals | Insert the guest record | Deduplicate without a write | Emit a guest-import conflict; do not update/tombstone the target |
| Notes | Insert the guest record | Deduplicate without a write | Emit a guest-import conflict; do not update/tombstone the target |

A tombstoned cloud goal/note with the same ID as an active guest record is a different payload/conflict even if its former active fields match. Silently resurrecting it would violate the selected tombstone model. No guest-side absence creates a delete: union is additive.

## Ordered implementation plan

1. **Strengthen the durable guest-import merge facts.** Extend `src/features/guest-import/model/guest-import.ts` with:
   - a JSON-safe `GuestImportConflict` containing `domain`, `recordId`, canonical guest payload, canonical cloud payload (or explicit tombstone snapshot), and the cloud revision when one exists;
   - a scalar `GuestImportProfileComparison` that keeps canonical guest and cloud profile fields separate for T159.4 without choosing either;
   - durable deduplication references (`domain` + `recordId`) so an identical cloud record is distinguishable from a record never examined;
   - `expectedRevision` on each prepared import operation (null only for a proven-absent create; the current cloud revision for a trick-state union update).

   Add a guarded reducer action such as `existingMergePrepared` that applies progress, profile comparison, deduplications, and conflicts only to the matching `uploading` import. Keep network, clocks, and equality logic outside the reducer. After domain settlement, preserve the existing transition to `awaitingProfileChoice`; `profileChoiceMade` remains T159.4's trigger into `conflicts` or completion.

2. **Update persistence validation before orchestration uses the new facts.** Extend `guest-import-persistence.ts`'s v1 runtime validator in place (the contract is still provisional) to validate finite revisions, non-empty IDs, JSON-safe conflict snapshots, deduplication references, and profile comparisons. Reject malformed/foreign shapes to `INITIAL_GUEST_IMPORT_STATE` through the existing recovery path. Add round-trip and field-by-field rejection cases, including a practice-history conflict with no revision and a tombstoned goal/note snapshot.

3. **Add a validated target-snapshot loader for existing accounts.** In a focused `guest-import-existing-account.ts` module beside the T159.2 orchestrator, pull the profile row and every page of trick states/custom tricks/practice sessions/goals/notes in the existing deterministic domain order. Reuse `mapProfileRowToDomainFields`, `mapTrickStateRowsToDomainFields`, and each domain's row mapper; preserve active goal/note rows and tombstone metadata for collision classification. A pull or mapping failure pauses the import without preparing writes or reporting partial success. Keep this loader repository-injected so unit tests do not require Supabase.

4. **Implement a pure merge planner over complete snapshots.** The planner accepts the guest `GuestImportSourceSnapshot`, validated target snapshot, destination user ID, import ID, injected creation time, and deterministic operation-ID factory. It returns the profile comparison, sorted accepted operations, sorted deduplications, sorted conflicts, and per-domain disposition counts. Implement the table above with small domain classifiers rather than one untyped JSON merge:
   - canonicalize custom tricks, sessions, goals, and notes through their existing mapping functions before equality;
   - key collections by stable ID and reject duplicate IDs in either input rather than allowing `Map` construction to hide one;
   - merge trick-state flags with boolean OR and map the result through `mapUserProfileToTrickStateUpsertInputs` (or an equally canonical existing helper);
   - attach the target trick-state revision to an OR update;
   - never emit profile-scalar, delete, conflicted-record, or deduplicated-record operations.

   The planner must not mutate or reuse target collection objects. Its output is a new declarative plan, making “no target overwrite” inspectable before any effect runs.

5. **Make accepted creates race-safe.** Add a guest-import-only create-collision mode at the transport boundary (an optional request/options field with current normal-sync behavior as the default). In that mode, a `23505`/already-existing result must refetch and return the untouched existing row rather than invoking the adapters' unconditional update fallback. The existing-account runner compares that returned canonical payload: an identical row becomes a deduplication acknowledgement; a different row becomes a guest-import conflict. For immutable practice sessions, compare the refetched payload instead of treating every duplicate ID as success. Revisioned trick-state union updates use the preflight revision so a concurrent edit returns a conflict rather than overwriting it. Cover all five adapters/profile trick-state routing with focused tests and prove ordinary domain synchronization retains its current default behavior.

   If the cleanest implementation is an import-specific repository method rather than an optional shared `SyncPushRequest` field, keep the same externally verifiable semantics: create-only insert, return existing row on collision, no update fallback. Do not duplicate Supabase mapping or authorization logic in the React hook.

6. **Run the prepared existing-account plan without broadening finalization.** Refactor the narrow common mechanics from `runEmptyGuestImport` only as needed so both paths preserve stable operation IDs, expected revisions, deterministic domain order, durable progress before requests, durable acknowledgement before selective source cleanup, and identity-namespace checks. The existing path:

## Risks and constraints

- The preflight pull and writes are not one database transaction. The create-only collision mode and revision guard are therefore part of correctness, not optional polish.
- Canonical equality must ignore server-owned metadata but include every client-owned payload field and sequence/name snapshot. Comparing raw rows or IDs alone is insufficient.
- Goal/note tombstones must remain visible to classification even though normal domain collection mappers filter them from rendered state.
- Profile scalar data must not be smuggled into a general union. The explicit source choice is a product decision already assigned to T159.4.
- Guest-import conflicts may include practice history, so forcing them into T160.2's mutable-only `SyncConflictRecord` would erase an important invariant and couple unrelated lifecycles.
