## 0. Facts established by probing this branch (do not re-derive)

I ran these experiments against this branch's actual code. Trust them; they are the reason
the plan is shaped the way it is.

1. **`.attrs({ style: { boxShadow } })` is inert.** A `styled(View).attrs({ style: {...} })`
   component renders with the style silently dropped — the rendered node's style was
   `{"minHeight":56,"backgroundColor":"#00ff00"}`, no `boxShadow`. This confirms the inline
   comment in `src/features/landing/components/landing-cta.tsx` (lines 54-61) and confirms the
   `.attrs` usage in `src/features/tricks/components/trick-card.tsx:34` is dead code. **Do not
   use `.attrs`.**
2. **The CSS `box-shadow` shorthand (or a camelCase `boxShadow:` line) inside the styled
   template gets lowered** by css-to-react-native to
   `{"shadowOffset":{"width":4,"height":4},"shadowRadius":0,"shadowColor":"#18382e","shadowOpacity":1}`
   — the legacy RN shadow props react-native-web 0.21 warns are deprecated. AGENTS.md says only
   two warnings are known-benign; adding a third is unacceptable. **Do not put the shadow in the
   CSS template.**
3. **Passing `style` at the JSX call site works and produces an array.** The rendered node's
   style becomes `[{generated styled-components object}, {boxShadow: "..."}]`. This is the
   repo's established technique (`landing-cta.tsx`, `landing-hero.tsx:39`,
   `landing-page.tsx:237`, `trick-goals-screen.tsx:115,143`). **This is the approach to use.**
4. **`useTheme()` from `styled-components/native` throws** (`Accessing \`useTheme\` hook outside
   of a \`<ThemeProvider>\` element.`) — many existing auth screen tests mount without a
   `StyledThemeProvider`. I measured this: it turned 8 failures into **90 failures across the
   same 7 suites**. Use `useContext(ThemeContext)` instead, which returns `undefined` with no
   provider (styled-components' own error message recommends exactly this escape hatch).
5. **Exact blast radius, measured with the full suite** (`npx jest --runInBand`, 157 suites /
   1899 tests) with the intended change applied: **8 failing tests in 7 files, nothing else.**
   Every failure is a theme-resolution style finder that rejects array styles. Listed in step 3.
6. `theme.text` is always a 6-digit hex: it is `AppColors.ink`/`AppColors.cream` from
   `deriveAutomaticTextColor`, or a user override validated by `isValidThemeHexColor`
   (`/^#[0-9a-fA-F]{6}$/`, `src/features/profile/model/user-profile.ts:42`). So
   `hexToRgba(theme.text, alpha)` from `src/constants/theme.ts:86` is safe, with a defensive
   guard for the no-provider case.
7. Layout has room for the shadow: every screen that renders a `TextField` sits inside a
   container with >= 22px horizontal padding, and CSS `overflow: hidden` clips at the padding
   box, so the two `overflow: hidden` ancestors (`src/features/tricks/components/trick-directory.tsx:404`,
   `src/features/sesh/components/multi-trick-sesh-entry.tsx:195`) will not clip a 3px shadow.
   Vertically, `ErrorText` has `margin-top: 7px` and `Field` has `margin-top: 24px`, both > 3px.

## 1. Change `src/components/ui/text-field.tsx`

This is the only production file that changes.

**a. Imports.** Add `useContext` to the `react` import, swap `styled` for
`styled, ThemeContext` from `styled-components/native`, and add `hexToRgba` to the
`@/constants/theme` import (keep `AppColors`, `Radii`, `Spacing`).

**b. Add a module-level shadow helper above `TextFieldProps`:**

```ts
const SHADOW_OFFSET_PX = 3;
const SHADOW_ALPHA = 0.35;

function inputShadow(themeText: string | undefined): string {
  const base = themeText && /^#[0-9a-fA-F]{6}$/.test(themeText) ? themeText : AppColors.ink;
  return `${SHADOW_OFFSET_PX}px ${SHADOW_OFFSET_PX}px 0 ${hexToRgba(base, SHADOW_ALPHA)}`;
}
```

The guard matters: without a `ThemeProvider` (several existing tests), `theme` is `undefined`,
and `hexToRgba` on a non-hex string yields `rgba(NaN, NaN, NaN, 0.35)`, which silently voids the
whole `boxShadow` declaration.

**c. In the component body**, next to the existing `useState`:

```ts
const theme = useContext(ThemeContext);
```

**d. Pass the shadow at the JSX call site** (the `$isFocused` prop stays exactly as-is):

```tsx
<InputRow $isFocused={isFocused} style={{ boxShadow: inputShadow(theme?.text) }}>
```

**e. Thicken the border** in the `InputRow` template: `border: 2px solid ...` →
`border: 3px solid ...`. Leave `min-height: 56px`, `border-radius`, `margin-top`, and the
focus/blur color interpolation untouched. (RN's box model is border-box, so the 56px row still
fits the 18px/12px-padded input at a 3px border — verified by arithmetic, 50px interior vs ~46px
content.)

**f. Add a short comment above `InputRow`** explaining the technique, in the spirit of
`landing-cta.tsx:54-61` but non-duplicative — roughly: the `boxShadow` is passed as an explicit
`style` prop at the call site because styled-components/native drops `.attrs({ style })` and
lowers the CSS `box-shadow` shorthand to RN's deprecated `shadow*` props; the color is read via
`useContext(ThemeContext)` rather than `useTheme()` because `useTheme()` throws when a caller
mounts the field without a `ThemeProvider`.

### Deliberate design decisions (do not "improve" these without a reason)

- **The shadow does not change on focus.** Focus already changes `borderColor` to `theme.accent`.
  Keeping the shadow constant keeps focus a single, unambiguous signal and avoids a second
  animated-looking change on every keystroke-entry. The shadow reads as depth, not as state.
- **Blur radius stays 0.** The rest of the app uses hard-edged "sticker" shadows; a soft shadow
  here would look foreign.
- **The color is theme-derived, not hardcoded `AppColors.ink`.** The landing page can hardcode
  ink because it is not themeable; the input row is, and a themed dark background with an ink
  shadow would render the effect invisible.
- `inputShadow` stays local to `text-field.tsx`. Only promote it into `@/constants/theme` if a
  second component needs the same treatment — not in this ticket.

### Tuning (this is a visual ticket; settle it in the browser, not on paper)

Start at `3px` offset / `0.35` alpha / `3px` border. On the default theme (sage background, ink
text) that is `rgba(24, 56, 46, 0.35)`. While looking at it in the browser:

- too faint against a light background → raise `SHADOW_ALPHA` toward `0.5`;
- too heavy / competing with the button shadows → drop `SHADOW_OFFSET_PX` to `2`;
- keep the border at `3px` unless it visibly crowds the 56px row (it does not at the measured
  sizes). `4px` is available but was not the intent of "increase the border width".

Whatever you settle on, keep the constants named at the top of the file so the next tweak is a
one-line change.

## 2. Update `src/components/ui/text-field.test.tsx`

Do this immediately after step 1 — it is the fastest feedback loop and it establishes the helper
shape you will copy into the six auth test files.

The current `resolvedRowStyle` (lines 17-27) finds the row with
`node.props.style?.minHeight === 56` and then explicitly requires a **non-array** style. Both
halves break once the row's style is an array. Replace with a flatten-based version (verified
passing):

```ts
function flattenStyle(style: unknown) {
  return StyleSheet.flatten(style as never) as Record<string, string | number> | undefined;
}

function resolvedRowStyle(renderer: ReactTestRenderer) {
  const matches = renderer.root.findAll((node) => flattenStyle(node.props.style)?.minHeight === 56);
  const withResolvedStyle = matches.find(
    (node) => typeof flattenStyle(node.props.style)?.backgroundColor === 'string',
  );
  return flattenStyle(withResolvedStyle?.props.style);
}
```

Add `StyleSheet` to the existing `import { Text } from 'react-native';`. Leave
`resolvedInputStyle` alone — the inner `TextInput` is unaffected by this change (note that the
notes/sesh screens already pass their own `style={NOTE_INPUT_STYLE}` to the `TextInput`, and
those tests already cope with it).

**Add one regression test** so the ticket's intent is pinned:

```tsx
it('renders a drop shadow and a thicker border on the input row', async () => {
  const root = await mountField();

  const rowStyle = resolvedRowStyle(root);
  expect(rowStyle?.borderWidth).toBe(3);
  expect(typeof rowStyle?.boxShadow).toBe('string');
});
```

Assert the *shape*, not the exact shadow string — otherwise the tuning pass in step 1 turns into
a test edit. (If you change the border to something other than 3, update the number here.)

Run `npx jest src/components/ui/text-field.test.tsx` before moving on.

## 3. Update the six auth test files

These are the exact 8 failures the full suite produces. Nothing else in the suite regresses.

| File | What to fix |

| `src/features/auth/components/__tests__/reset-password-screen.test.tsx` | inline row predicate at lines 376-390 |

Two patterns:

- **Files with a `resolvedStyle(nodes)` helper** (password-input, account-security): the helper
  currently picks the first node whose style is a plain object. Change it to return
  `StyleSheet.flatten(node.props.style)` for the first node with a style at all, and change the
  `findAll((node) => node.props.style?.minHeight === 56)` call site to use the flattened value.
- **Files with an inline finder** (sign-up, sign-in, forgot-password): the shape is
  `findAll((node) => node.props.style?.minHeight === 56).find(<non-array plain object>)`.
  Replace both halves with the flattened lookup, mirroring `resolvedRowStyle` from step 2.
  Leave the neighbouring `screenStyle` and email-input finders untouched — those nodes still
  carry plain-object styles.
- **`reset-password-screen.test.tsx`** is slightly different: its predicate is
  `!Array.isArray(style) && style.minHeight === 56 && style.flexDirection === 'row'`, and it then
  loops `for (const row of rowStyle)` asserting `row.props.style`. Flatten inside the predicate,
  drop the `!Array.isArray` clause, and assert on the flattened style inside the loop. The
  existing `expect(rowStyle.length).toBeGreaterThan(0)` stays and still holds (the count goes up,
  because both the composite and the host node now match — that is fine, they carry identical
  styles).

Five of these six files do not import from `react-native` yet — add
`import { StyleSheet } from 'react-native';` in the external-import group, positioned as in
`text-field.test.tsx` (after `@jest/globals`, before `react-test-renderer`) so lint's import
ordering stays happy. `password-input.test.tsx` already imports `{ View }`; extend that import.

**Do not weaken any assertion.** Every `toMatchObject({ backgroundColor, borderColor })` stays
exactly as it is — the change is purely in how the node and its effective style are located.

A useful precedent to read if a finder fights you:
`src/features/landing/components/landing-page.test.tsx:215-232` (`resolvedStyleFor`) already
solved this exact array-vs-object problem, and its comment explains it.

## 4. Explicitly rejected alternatives

Recorded so they are not re-explored mid-implementation:

- **Wrapping `InputRow` in a shadow-only `View`** would keep all 7 test finders untouched, but it
  adds a phantom node to every text field app-wide, forces the border radius to be duplicated on
  the wrapper, and leaves the tests passing by accident rather than by intent. Rejected: the test
  helpers are the thing that is wrong here, not the component structure.
- **A hardcoded `AppColors.ink` shadow** (matching the landing page literally) breaks on
  user-chosen dark themes. Rejected.
- `.attrs`, the CSS shorthand, and `useTheme()` are rejected on measured evidence — see section 0.
