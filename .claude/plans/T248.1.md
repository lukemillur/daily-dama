# T248.1 -- Retain and expose failed local writes

## Context established during planning

- The shared mechanics live entirely in src/shared/persistence/use-identity-scoped-domain.ts
  (useIdentityScopedDomain), backed by createWriteQueue in
  src/shared/persistence/storage.ts. All five domain providers
  (goal-provider.tsx, custom-trick-provider.tsx, note-provider.tsx,
  user-profile-provider.tsx, practice-history-provider.tsx) call this same
  hook for their primary reducer state, with near-identical
  onSaveFailed: (error) => console.warn(...) diagnostic-only callbacks.
  Today a failed effect-driven write (the useEffect that calls
  void enqueueWrite({ value: state, taggedGeneration }) whenever state
  changes) is silently dropped after logging -- no consumer can see or retry it.
  saveNow (the imperative path) already returns a ScopedSaveOutcome, but
  callers must remember to check it themselves; nothing retains the value for
  retry.
- Each of the five domain-sync hooks (use-goal-domain-sync.ts etc.) calls
  useIdentityScopedDomain a SECOND time, for the sync envelope/outbox
  state, saved via explicit saveNow calls. This is the T157.7 "second,
  parallel identity-scoped domain instance" already documented inline in each
  provider. The new durability handle must come from the PRIMARY state's
  hook call only -- the envelope hook call's durability field is simply never
  read/exposed by any provider. This is how "distinct from cloud outboxes/
  SyncStatus" is enforced structurally rather than by convention.
- createWriteQueue chains pending = pending.then(() => write(value)), so
  writes execute strictly one at a time: write N+1's worker function does not
  even start until write N's has fully resolved. This means the order in
  which write outcomes resolve is already guaranteed to match call order,
  regardless of each write's individual latency (use-identity-scoped-domain
  .test.tsx's "keeps back-to-back writes ordered..." test already proves
  this). Consequently, if the new durability state is set from inside the
  queue's worker callback (not from an external .then() on the returned
  promise), "never replace newer state with an older failed snapshot" falls
  out of the existing ordering guarantee for free -- no new sequence-number
  bookkeeping is needed.
- IdentityContext (identity-context.ts) exposes getGeneration() and
  isCurrentGeneration(captured); the existing worker already re-checks
  isCurrentGeneration before and after save() to detect an in-flight
  identity switch (supersededDuringWrite). The new durability-set calls must
  reuse that exact guard so a write from a since-superseded generation can
  never write into the new identity's durability status.
- useIdentityHandle() falls back to a per-module-instance DEFAULT_HANDLE
  (guest, generation 0) when no IdentityProvider ancestor exists
  (identity-provider.tsx), which is how goal-provider.test.tsx mounts
  UserProfileProvider/GoalProvider directly today. The new provider-level
  durability tests can do the same -- no need to stand up the full app's
  IdentityProvider/Supabase stack.
- Real save* functions (e.g. saveGoals in goal-persistence.ts) already
  catch a thrown storage.setItem and return { status: 'failed', error },
  so provider-level tests can force a realistic failure by rejecting
  AsyncStorage.setItem for the specific storage key under test (via
  jest.spyOn(AsyncStorage, 'setItem').mockImplementation(...) filtering on
  key), rather than needing to mock each persistence module.

## Implementation steps, in order

### 1. Add the shared typed durability vocabulary -- src/shared/persistence/storage.ts

Add, alongside ScopedSaveOutcome, a new exported type:

    export type LocalDurabilityStatus<State> =
      | { readonly status: 'saved' }
      | {
          readonly status: 'failed';
          readonly snapshot: State;
          readonly retry: () => Promise<ScopedSaveOutcome>;
        };

Document it as: runtime-only local-durability status for a domain's primary
persisted state, as tracked by useIdentityScopedDomain. Distinct from
ScopedSaveOutcome (a single write's resolved outcome) and from
SyncStatus/cloud outbox state (which track remote durability): this answers
"is the current in-memory value for this domain known to be safely on disk,"
derived purely from local write attempts.

Keep this next to ScopedSaveOutcome since it is built directly out of it
(retry resolves to the same outcome type), and both are hook-level
vocabulary distinct from PersistenceSaveResult.

### 2. Wire it into useIdentityScopedDomain -- src/shared/persistence/use-identity-scoped-domain.ts

- Add a useState<LocalDurabilityStatus<State>> holding durability, initialized
  to { status: 'saved' }.
- In the hydration useEffect (the one keyed on [context, generation]),
  reset durability to { status: 'saved' } synchronously at the top of the
  effect body (before the load(...).then(...)), so an identity switch
  clears any prior-identity failure immediately, independent of whether the
  new generation's load succeeds. This satisfies "identity changes clear
  prior-identity status."
- Inside the createWriteQueue worker (the function currently computing
  saved/failed/superseded), after the existing
  context.isCurrentGeneration(taggedGeneration) guards, add the durability
  update at the two points that currently just return:
  - On success (result.status !== 'failed', and no supersession): if
    context.isCurrentGeneration(taggedGeneration), set durability back to
    { status: 'saved' }.
  - On failure (returned {status:'failed'} or a caught throw): if
    context.isCurrentGeneration(taggedGeneration), set durability to
    { status: 'failed', snapshot: value, retry: () => enqueueWrite({ value,
    taggedGeneration: context.getGeneration() }) }.
    Note retry recomputes context.getGeneration() at call time (mirroring
    saveNow's existing pattern), not the stale taggedGeneration -- a retry
    issued after an identity switch is naturally a no-op (superseded)
    rather than writing into the wrong namespace. enqueueWrite is the
    const from the enclosing useMemo; the worker closure may reference it
    before its own literal position in source because it only reads the
    binding when actually invoked, well after useMemo has returned -- same
    self-referencing-closure pattern already implicitly relied on elsewhere
    in this file.
  - On superseded (either branch): do NOT touch durability at all --
    it belongs to a generation that the hydration effect has already reset.
- Add durability to UseIdentityScopedDomainResult<State, Action> and to
  the final returned object.
- Update the doc comment above the hook (the block explaining
  hydration/generation/write-queue mechanics) with one short paragraph
  describing the durability guarantee and pointing at this plan's ordering
  argument, so a future reader doesn't have to re-derive it.

No changes to UseIdentityScopedDomainOptions are needed -- onSaveFailed
stays as the diagnostic-only console hook; durability is the new
first-class signal per AGENTS.md's "logging cannot be the only failure
signal."

### 3. Extend shared-hook tests -- src/shared/persistence/use-identity-scoped-domain.test.tsx

Extend Captured/makeHarness to also capture durability (re-read every
render via the existing useEffect in the harness, same as state/
hasHydrated). Add new it() blocks (co-locate near the existing saveNow
failure/success tests):

1. "exposes a failed durability status with the latest snapshot after a
   returned save failure" -- mock save to resolve {status:'failed'} once;
   trigger a state change (not saveNow) so the effect-driven write path
   is exercised; assert captured.durability is {status:'failed', snapshot:
   {value: N}, retry: fn}.
2. Same for a thrown save (mirrors the existing thrown-saveNow test,
   but via the effect-driven path).
3. "a later successful write clears the failure" -- fail once, then mutate
   state again with save succeeding; assert durability returns to
   {status:'saved'}.
4. "retry() re-attempts the retained snapshot through the same queue and
   clears the failure on success" -- fail once (retaining snapshot), flip the
   mocked save to succeed, call captured.durability's retry(), assert
   the resolved ScopedSaveOutcome is {status:'saved'} and durability
   becomes {status:'saved'}.
5. "rapid mutations never let an earlier failure's snapshot win over a later
   write's outcome" -- dispatch value 1 (save fails) then value 2 (save
   succeeds) back-to-back before awaiting; assert final durability is
   {status:'saved'} (not stuck on value 1's failure). Add the converse: both
   fail, and assert the final failed snapshot is value 2, not value 1.
6. "identity switch clears a prior generation's failed durability status, and
   a stale write's completion cannot resurrect it" -- reuse the existing
   "discards a queued write tagged with a superseded generation" scaffolding
   (deferred save gate): trigger a failing write, switch identity before it
   resolves, assert durability is already {status:'saved'} immediately
   after the switch (not waiting for the stale write to resolve), then
   resolve the stale write's save as failed and assert durability is
   still {status:'saved'} (the stale completion must not touch it).

### 4. Expose the handle from each of the five domain providers

For each of goal-provider.tsx, custom-trick-provider.tsx,
note-provider.tsx, user-profile-provider.tsx,
practice-history-provider.tsx, follow the existing *Sync
context/hook pattern exactly, but as a NEW, SEPARATE context (do not add
a field to the existing GoalSync/CustomTrickSync/etc. interfaces -- those
are cloud SyncStatus, and AGENTS.md/T248.1's notes require these stay
distinct):

- Destructure durability from the existing useIdentityScopedDomain(...)
  call for the domain's PRIMARY state (not the domain-sync hook's envelope
  instance).
- Add a new DurabilityContext = createContext<LocalDurabilityStatus<DomainState>
  | undefined>(undefined) per domain.
- Wrap children in that context's Provider inside the existing provider
  tree (innermost is fine -- no ordering dependency on the sync context).
- Export use<Domain>Durability() following the same
  "throw if used outside its provider" pattern as useGoalSync/etc.

Concretely: useGoalDurability(), useCustomTrickDurability(),
useNoteDurability(), useUserProfileDurability(),
usePracticeHistoryDurability(). Naming should mirror each domain's existing
use<Domain>Sync hook name exactly, substituting Durability for Sync, so
call sites and future T248.2 aggregation code have a predictable, uniform
shape (LocalDurabilityStatus<GoalCollection>,
LocalDurabilityStatus<CustomTrickCollection>,
LocalDurabilityStatus<NoteCollection>, LocalDurabilityStatus<UserProfile>,
LocalDurabilityStatus<PracticeHistory>). This uniformity is what T248.2
will later aggregate across all five -- do not introduce five differently
shaped ad hoc types.

Order these five provider edits after step 2/3 land (the shared hook is the
dependency), but they are otherwise independent of each other and can be done
in any order/batched together.

- A harness component that reads use<Domain>Durability() and the domain's

- Test 2: "retry() clears the failure once the underlying write can
  succeed" -- restore/relax the setItem spy to succeed, call the captured
  retry(), assert the resolved outcome is {status:'saved'} and the
  captured durability updates to {status:'saved'}.

## Risks / non-obvious points for the implementer

- The single riskiest correctness point is where the durability state is set
  from: it MUST be inside the createWriteQueue worker itself (which
  runs strictly serially per the queue's chaining), not from an external
  .then() on enqueueWrite's returned promise or from saveNow's
  wrapper. Setting it externally would reintroduce exactly the ordering race
  the exit criteria warn about, even though today's queue does guarantee
  resolution order for the returned promises too -- keeping the state update
  physically inside the worker is what makes this obviously and locally
  correct rather than correct-by-a-subtle-cross-file argument.
- Don't let retry's closure capture the stale taggedGeneration -- it must
  call context.getGeneration() fresh at retry-call time, exactly like
  saveNow does, or a retry issued shortly after a valid identity
  switch could be misreported.
- Resist the temptation to fold durability into the existing GoalSync-
  shaped interfaces. The task and AGENTS.md are explicit that local
  durability and cloud SyncStatus/outbox state must stay structurally
  separate; a shared interface would make that boundary easy to blur later
  (exactly the kind of consolidation AGENTS.md warns against "merely because
  they are all persistent").
- The domain-sync hooks' SECOND useIdentityScopedDomain call (for the
  envelope) will also gain a durability field for free, since it's the same
  hook. Do not expose or wire that one up anywhere -- only the primary-state
  call's durability is part of this task's public contract. Leaving the
  envelope's durability field unused and unexported is intentional, not an
  oversight to "finish."
- When forcing a save failure in the provider-level tests, filter the
  AsyncStorage.setItem spy by storage key rather than rejecting
  unconditionally -- each domain's own domain-sync envelope hook may also call
  setItem around the same time (background pull/push bookkeeping), and an
  unconditional rejection could produce a false pass/fail unrelated to the
  primary state's durability.
