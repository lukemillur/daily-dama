# T161.5 -- Purge account state and reconcile deletion response loss

## Context established during planning

- T161.4 (`c12b35e`) added `/app/profile/account/delete` and `AuthProvider.deleteAccount`, which
  today **only** invokes the `delete-account` Edge Function and returns `{ error }`. It never
  signs the session out locally and never touches AsyncStorage. That is the entire gap this
  ticket closes -- everything else it needs already exists.
- The Edge Function (`supabase/functions/delete-account/handler.js`) is already idempotent: it
  calls `callerClient.auth.getUser()` first and returns `204` (no error) if the user is already
  gone (`isNotFound`), before checking the confirmation text or password. This means a plain
  retry through the existing UI (same non-empty password field, `DELETE` typed) is exactly the
  "Auth verification proves the user no longer exists" reconciliation the ticket describes --
  no new client-side `getUser()` probe is needed. A fresh success and a reconciled
  lost-response both surface identically to the client as `{ error: null }` from
  `client.functions.invoke`. Do not build a second reconciliation path; there is only one
  success branch to handle, and it covers both scenarios.
- Every domain (profile, custom tricks, practice history, goals, notes) plus guest-import
  progress plus sync-status metadata are persisted through
  `src/shared/persistence/use-identity-scoped-domain.ts`, which namespaces every physical
  AsyncStorage key as `${identityNamespace(identity)}:${logicalKey}` via
  `createScopedKeyValueStorage`/`physicalKey` in `src/shared/persistence/scoped-storage.ts`. For
  a verified user this is always `user:<uuid>:...`. Each domain's `SyncEnvelope` (in
  `src/shared/sync/sync-envelope.ts`) bakes its own outbox and conflicts into that same
  physical document -- there is no separate outbox/conflict storage key to purge independently.
  Consequence: purging every key with the `user:<uuid>:` prefix is a complete purge of
  credentials-adjacent app state (profile, custom tricks, practice history, goals, notes,
  outboxes, conflicts, guest-import progress, and the `daily-dama-sync-status-v1` sync metadata
  key). No per-domain purge code is required.
- Session/credential storage (Supabase's own AsyncStorage-backed session) is already cleared by
  `client.auth.signOut({ scope: 'local' })` -- the exact call `signOut()` in `auth-provider.tsx`
  already makes for ordinary logout. No separate "account cache" storage exists in this codebase
  today (`AccountSection` reads the email straight off `authState.session`, in memory only) -- the
  Notes' "account cache" language is satisfied by this same local sign-out call.
- `IdentityProvider` (`src/shared/persistence/identity-provider.tsx`) already reactively derives
  `guest` and bumps the identity generation the moment Auth reports `SIGNED_OUT`
  (`deriveIdentityFromAuthState` -> `context.setIdentity`). Calling `signOut({ scope: 'local' })`
  is therefore also how "invalidate the identity generation ... enter a fresh guest namespace" is
  satisfied -- reuse this existing, already-tested (T156/T158) mechanism instead of adding a new
  one. Every identity-scoped write already self-discards via
  `context.isCurrentGeneration(taggedGeneration)` before it touches storage, so a stale in-flight
  write from the deleted account's generation cannot land in the live (now-guest) namespace
  regardless of purge timing.
  - The one residual race (a stale in-flight write completing after purge but before the
    generation has actually flipped, re-materializing a key in the now-dead `user:<uuid>:`
    namespace) is accepted, not fixed: nobody can ever sign back in as that `uuid` again, so that
    namespace is permanently unreachable orphaned data. This matches the Notes verbatim:
    "AsyncStorage purge is accepted prototype cleanup, not claimed forensic erasure." Do not
    build extra synchronization to close this window.
- `identityNamespace`/`createUserIdentity` in `src/shared/persistence/identity.ts` already reject
  malformed ids and use a `:`-delimited scheme, so a `user:<uuid>:` prefix match can never
  collide with `guest:` or a different `user:<other-uuid>:` namespace.

## Implementation steps, in order

1. **Add the purge primitive** -- new file `src/shared/persistence/account-purge.ts`:
   - Define a minimal storage seam (not `KeyValueStorage`, which only has `getItem`/`setItem`):
     ```ts
     export interface NamespacePurgeStorage {
       readonly getAllKeys: () => Promise<readonly string[]>;
       readonly multiRemove: (keys: readonly string[]) => Promise<void>;
     }
     ```
   - `export async function purgeIdentityNamespace(storage: NamespacePurgeStorage, identity: Identity & { kind: 'user' }): Promise<void>` -- lists all keys, filters by `${identityNamespace(identity)}:` prefix, `multiRemove`s the matches (no-op if none). Typing the parameter as `Identity & { kind: 'user' }` makes it a compile-time error to ever call this with `GUEST_IDENTITY`, mirroring the existing "only sanctioned way" pattern in `identity.ts`. This is the only new production module the ticket needs.
   - Unit test `src/shared/persistence/__tests__/account-purge.test.ts`: purges only prefixed keys; leaves a `guest:...` key and a different `user:<other-uuid>:...` key untouched; no-ops cleanly when nothing matches; confirm no accidental substring collision (e.g. a `user:aaaaaaaa-...-1:` key must survive purging `user:aaaaaaaa-...-2:`, differing only in the last id character -- the trailing `:` in the prefix is what prevents this, but assert it explicitly).
   - Do this step first: everything else calls it, and its own tests catch a wrong-mock-API assumption (`getAllKeys`/`multiRemove` support in `@react-native-async-storage/async-storage/jest/async-storage-mock`) before it's relied on elsewhere.

2. **Wire the purge + local sign-out into `deleteAccount`** -- `src/features/auth/state/auth-provider.tsx`:
   - Capture `const userId = stateRef.current.session.user.id;` while still inside the existing `status !== 'authenticated'` guard (so it's always defined past that point).
   - After `const { error } = await client.functions.invoke('delete-account', { body: { currentPassword, confirmation } });`:
     - If `error` is present, `return { error };` unchanged -- this is both the "response loss, user still present" and "offline" branches; no purge, no sign-out.
     - If `error` is `null` (covers a genuinely fresh success and a reconciled lost-response retry -- see Context above, they are indistinguishable and identical to handle):
       1. `const identity = createUserIdentity(userId);` then `if (identity) await purgeIdentityNamespace(AsyncStorage, identity);` -- the `if` is a defensive no-op guard only (Supabase always supplies a valid uuid in practice; skip purge rather than throw if it somehow isn't).
       2. `await client.auth.signOut({ scope: 'local' });` -- purge before sign-out, so the purge always runs while the SDK still considers the session nominally valid, and sign-out is what starts the (already-tested) reactive generation-invalidation chain.
       3. `return { error: null };`
   - New imports needed: `AsyncStorage` from `@react-native-async-storage/async-storage`, `createUserIdentity` from `@/shared/persistence/identity`, `purgeIdentityNamespace` from `@/shared/persistence/account-purge`.
   - Do this after step 1 since it depends on `purgeIdentityNamespace`'s exact signature.

3. **Extend `src/features/auth/state/__tests__/auth-provider.test.tsx`** to cover the five exit-criteria scenarios at the unit level (this file already has `createFakeClient()` with a mocked `signOut`/`functions.invoke`; it has no AsyncStorage mock yet -- add
   `jest.mock('@react-native-async-storage/async-storage', () => require('@react-native-async-storage/async-storage/jest/async-storage-mock'))`
   at the top, matching `logout-guard.discard-isolation.test.tsx`'s existing convention):
   - Emit `SIGNED_IN` with a session whose `user` includes a real-shaped `id` (a fixed valid uuid string), not just `email` -- the two pre-existing `deleteAccount` tests only set `email`, which is fine for them (they hit the reject/error branches, where `userId` is never read for purge), but the new success tests need it.
   - **Normal success**: seed `AsyncStorage.setItem('user:<uuid>:daily-dama:user-profile', '...')` before calling, resolve `invoke` with `{ error: null }`, assert: the seeded key is now `null`, `fake.signOut` was called with `{ scope: 'local' }`, and the result is `{ error: null }`.
   - **Response loss with missing user (reconciled retry)**: identical to the above -- add it as a separate test but with a one-line comment explaining it exercises the same `error === null` branch as the fresh-success case, because the Edge Function's own idempotent `already_absent -> 204` makes the two indistinguishable to this client code (cite `handler.js`'s `isNotFound` check). Don't skip this test just because the code path is shared -- the exit criteria list it explicitly and a future refactor could accidentally split the branches.
   - **Response loss with user still present**: resolve `invoke` with `{ error: { status: 401 } }` (server ran the password check and rejected it, as it would for a real user still on file). Assert: the seeded key is untouched, `fake.signOut` was not called, result is `{ error: { status: 401 } }`.
   - **Offline retry**: resolve `invoke` with `{ error: { name: 'FunctionsFetchError' } }`. Assert: same non-destructive outcome as above.
   - Optional but cheap defensive case: a session whose `user.id` is malformed (not a uuid) still signs out on success but does not attempt to touch AsyncStorage (i.e. doesn't throw) -- exercises the `if (identity)` guard from step 2.
   - Run scoped: `yarn jest src/features/auth/state/__tests__/auth-provider.test.tsx src/shared/persistence/__tests__/account-purge.test.ts` while iterating.

4. **New integration test for the cross-domain/late-in-flight scenario** --
   `src/shared/sync/account-deletion-purge.integration.test.tsx`, closely modeled on the existing
   `src/shared/sync/logout-guard.discard-isolation.test.tsx` (same harness shape: real
   `CustomTrickProvider`/`UserProfileProvider`/`PracticeHistoryProvider`/`NoteProvider`/
   `GoalProvider`/`SyncCoordinatorProvider`, fake sync transports, a test-only
   `IdentityHandleTestProvider` driving identity directly instead of going through real Auth --
   that file's own header comment explains why: this level proves storage durability and
   cross-identity isolation, not the sign-out call itself, which is already covered by step 3).
   This is the one exit criterion the unit tests in step 3 cannot reach, because
   `auth-provider.test.tsx` never mounts the real domain providers/sync coordinator.
   - Seed, before touching the "deleted" user's identity: a `guest:...` key (via the guest
     identity) and a `user:<other-uuid>:...` key (a second, unrelated user identity) -- these must
     survive the whole test untouched.
   - Switch to `USER_IDENTITY` (the "about to be deleted" account), add a custom trick so a
     pending outbox operation exists and gets persisted into that identity's envelope.
   - Configure the custom-trick fake transport's `push` to return a controllable, not-yet-resolved
     promise (a deferred pattern), then trigger whatever this harness already uses to start a
     sync run (mirror how `sync-coordinator.sesh-isolation.test.tsx` or
     `cross-domain-conflict-fault-injection.integration.test.tsx` kicks off a run -- check their
     exact call before writing this) so the push is genuinely in flight when the next step runs.
   - While that push is still pending: call `purgeIdentityNamespace(AsyncStorage, USER_IDENTITY)`
     directly (this test intentionally does not go through `deleteAccount`/Auth -- see the header
     comment it should carry, matching the discard-isolation file's own rationale) and then flip
     the harness identity to `GUEST_IDENTITY` via the test driver (modeling what `signOut` +
     `IdentityProvider`'s reactive effect achieves in production).
   - Then resolve the deferred push promise with a success result, and flush effects.
   - Assert: (a) the guest identity's custom-trick collection is still empty -- the late ack must
     not land in the live namespace; (b) `AsyncStorage.getAllKeys()` has no key with the
     `user:<uuid-of-deleted-account>:` prefix remaining -- the late write did not resurrect a
     purged key; (c) the previously-seeded `guest:...` and `user:<other-uuid>:...` keys are still
     present with their original values, unchanged.
   - Do this step after steps 1-3 land (it exercises `purgeIdentityNamespace` directly and should
     follow its final signature), but it is independent of the `auth-provider.tsx` change and can
     be written in parallel if useful.

5. **`AccountDeletionScreen` UI correction** --
   `src/features/auth/components/account-deletion-screen.tsx`. This is a necessary companion fix,
   not scope creep: today, success just sets local `succeeded = true` and renders a "proceeding"
   message while `deleteAccount` never signs out, so `authState.status` stays `'authenticated'`
   forever afterward (a latent bug the ticket's own local sign-out fix would otherwise expose).
   Once step 2 lands, `authState.status` will flip to `'guest'` shortly after a successful
   deletion, and the component's existing render order (`authState.status !== 'authenticated'`
   checked before the success view) would silently swap the success message for "Sign in to
   permanently delete your account" -- factually confusing copy after the account is already gone.
   - Move the `succeeded` check to the top of the render function, before the `authState.status`
     branches, so it always wins once true regardless of what `authState` does afterward.
   - Update the copy: `deleteAccount` now completes the local purge and sign-out synchronously
     within the awaited call, so "Account deletion is proceeding..." is no longer accurate -- use
     something like "Your account has been permanently deleted." Keep it short, matches existing
     copy register (see `Warning`/`Introduction` styled text above it).
   - Update `src/features/auth/components/__tests__/account-deletion-screen.test.tsx`'s existing
     assertion on `/deletion is proceeding/i` to match the new copy, and add one test that sets
     the mocked `mockAuthState` to `{ status: 'guest' }` before the delete button is pressed
     (simulating "auth state has already flipped by the time this render happens") and confirms
     the success view still renders instead of the guest/"Go to sign in" branch -- this is the
     concrete regression test for the render-order fix.

   `.claude/scripts/run-auth-e2e.mjs` against the local Supabase stack per
   `supabase/README.md`. Update it, don't skip it -- it's the only evidence path that proves the
   purge fires against the real Auth/Identity/persistence stack end-to-end:
   - Update the `/deletion is proceeding/i` text assertion in the third test to match the new
     copy from step 5.
   - After the successful-deletion assertion, add an evaluation reading
     `window.localStorage.getItem('user:<userId>:daily-dama:user-profile')` and assert it is now
     `null` (thread `userId` out of `signedInDeletionPage`'s return value, which currently only
     returns `{ password }`) -- this is the concrete end-to-end proof that "completed deletion
     exposes no former account data."
   - Run via `.claude/scripts/run-auth-e2e.mjs`, not the plain Jest suite -- this file needs the
     local Supabase stack per the dedicated Auth suite rules in `AGENTS.md`.
