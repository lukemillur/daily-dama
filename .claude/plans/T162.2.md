# T162.2 - Enforce CSP and the remaining defensive web headers

## Context established during planning

T162.1 (merged) shipped a report-only CSP plus a full local verification harness that
mirrors Vercel's static-serve behavior: security/scripts/serve-web-export.mjs,
security/scripts/build-and-serve.mjs, security/scripts/check-csp-headers.mjs,
yarn security:check-headers, playwright.security.config.ts plus
e2e/security/01-no-unexplained-violations.spec.ts and
e2e/security/02-disallowed-origin-is-flagged.spec.ts (yarn test:e2e:security), and
security/README.md. Its README already states the enforcement flip is "the only
mechanical change that ticket needs to make, assuming the report-only phase does not
turn up anything that requires a policy change first" - the existing Playwright suite
already proves zero unexplained violations across every Auth/core/sandbox route, so
that precondition is satisfied. Do not redesign the CSP directives themselves.

frame-ancestors 'none' is already live as a CSP directive from T162.1 - it is not a
standalone HTTP header. The task's Notes list it alongside HSTS/XCTO/Referrer-Policy/
Permissions-Policy, but no separate frame-ancestors header or legacy X-Frame-Options
header should be added; that would be redundant scope creep. Say this explicitly in
the README update so a later reader doesn't go looking for a header that was never
meant to exist.

No Vercel CLI/project link exists in this environment (checked: vercel not on PATH, no
.vercel/project.json file). The exit criteria's "production preview" cannot be hit
literally from here. Follow T162.1's own precedent (its PR was reviewed and merged on
the strength of the local harness, not a live preview URL): treat
security/scripts/build-and-serve.mjs's local server, which serves the real dist
export through the real vercel.json headers and rewrites, as the stand-in for
"production preview" in all automated checks. State this substitution plainly in the
README and in the TASKS.md Done-entry evidence - don't gloss over it. A real
live-preview header spot-check (curl or devtools once this PR's Vercel preview
deploys) is a manual, owner-side step, same pattern as the existing manual checklist
in DEPLOYMENT_HANDOFF.md section 6.

Grepped src for camera, microphone, geolocation, fullscreen, clipboard, share, and
sensor API usage - none found anywhere in the app, including
src/features/trick-viz. A fully restrictive Permissions-Policy is safe.

Strict-Transport-Security is only honored by browsers over a real HTTPS connection;
the local harness serves plain HTTP, so its enforcement can only be checked for
presence and value (via check-csp-headers.mjs), never runtime effect, in this
environment. Don't attempt a Playwright test that expects HSTS to actually upgrade a
connection locally - it structurally can't.

## Ordered steps

1. Baseline regression check before touching anything. Run yarn security:check-headers
   and yarn test:e2e:security against current development tip to confirm T162.1's
   report-only suite is still green (catches any drift, e.g. an Expo Router bump
   between T162.1 and now changing the inline-bootstrap-script hash, before it gets
   conflated with this ticket's changes).

2. vercel.json (do this first - everything else validates against it):
   - Rename Content-Security-Policy-Report-Only to Content-Security-Policy. Keep the
     directive value byte-identical; this is the mechanical flip the T162.1 README
     already promised.
   - Add four new entries to the same headers[0].headers array (same catch-all
     source "/(.*)" rule - keep everything under one rule so the existing "one
     identical header value across every sampled route" test pattern still holds):
     - Strict-Transport-Security: max-age=63072000; includeSubDomains
       (no preload - that's a separate, harder-to-reverse commitment involving
       submission to a browser-shipped preload list; leave it for the product owner
       to opt into deliberately, don't bundle it into this ticket).
     - X-Content-Type-Options: nosniff
     - Referrer-Policy: strict-origin-when-cross-origin
     - Permissions-Policy: a full deny-list covering every standard gated feature
       (accelerometer, ambient-light-sensor, autoplay, battery, camera,
       display-capture, document-domain, encrypted-media, fullscreen, geolocation,
       gyroscope, magnetometer, microphone, midi, payment, picture-in-picture,
       publickey-credentials-get, screen-wake-lock, sync-xhr, usb, web-share,
       xr-spatial-tracking, each written as feature=()), consistent with the grep
       above finding zero usage of any of them.

3. security/scripts/check-csp-headers.mjs:
   - Change the header lookup from content-security-policy-report-only to
     content-security-policy.
   - Extend the existing per-route sampling loop to also assert exact, byte-identical
     values for the four new headers (mirror the existing EXPECTED_DIRECTIVES pattern,
     an independently written expected-value map, not round-tripped from vercel.json,
     same anti-tautology discipline T162.1 used for the CSP itself).
   - Leave the script-src hash drift-guard test logic alone; it still reads from the
     now-renamed header.
   - Cosmetic: update string literals like "report-only CSP header (T162.1)" to
     reflect enforcement and T162.2 where they describe current behavior, not history.

4. e2e/security/02-disallowed-origin-is-flagged.spec.ts: add disposition to the
   collected Violation fields (already present in spec 01's interface, missing here)
   and assert the recorded connect-src violation has disposition equal to "enforce".
   This is the one place that actually proves the browser is blocking, not merely
   still logging - a report-only header left behind by accident would still pass this
   spec's existing assertions otherwise.

5. e2e/security/01-no-unexplained-violations.spec.ts: no behavior change required (it
   already expects zero violations everywhere). Optional: add a comment noting that
   under enforcement, a violation here also means broken functionality on that route,
   not just a console warning - raises the stakes for whoever debugs a red run here
   later.

6. New file e2e/security/03-enforcement-blocks-inline-script-and-framing.spec.ts,
   covering the exit criteria's "an inline/unlisted script and framing attempt are
   blocked":
   - Script test: navigate to /app/home with the same seeded-profile plus
     securitypolicyviolation-listener pattern as specs 01/02. Via page.evaluate,
     dynamically create and appendChild a script element with a distinguishing side
     effect (for example, sets window.__unlisted_script_executed to true). Assert two
     things: (a) a script-src violation was recorded with disposition equal to
     "enforce", and (b) window.__unlisted_script_executed is undefined afterward,
     proving the browser actually refused execution, not just logged it.
   - Framing test: page.goto("about:blank"), then page.setContent with an iframe
     pointed at the served export's /app/home route. Listen for the
     page's requestfailed event and assert a request matching that URL fails rather
     than succeeds (Chromium reports a frame-ancestors violation as a blocked
     navigation, commonly surfaced as net::ERR_BLOCKED_BY_RESPONSE). Treat the exact
     failure-text matching as the fiddliest part of this whole ticket - Chromium
     version and timing can affect exactly how the block surfaces; if asserting on
     the requestfailed error text proves flaky, fall back to asserting the iframe's
     content never populates with the app's content within a bounded wait. Budget
     real iteration time here rather than assuming the first attempt works.

7. security/README.md:
   - Flip the "Status" section from "ships report-only" to enforced-as-of-T162.2.
   - Add a rationale subsection for the four new headers, in the same bullet style as
     the existing CSP rationale: HSTS's includeSubDomains-without-preload choice;
     Permissions-Policy's full-lockdown rationale (cite the grep finding); explicitly
     note frame-ancestors needs no new standalone header since it is already enforced
     via CSP as of T162.1.
   - Update "Running the checks" to mention the new enforcement-specific spec (03).
   - Add the "production preview" substitution caveat from the Context section above,
     stated plainly, not buried.

8. Auth regression smoke check: run yarn test:e2e:auth after the header flip. None of
   the four new headers or the enforcement flip plausibly interact with connect-src
   or script execution paths Auth depends on, but the callback flow is the one place
   a header regression would be worst to miss silently - cheap to re-run, worth doing
   rather than asserting from first principles alone.

9. Full verification, in this order (schema and config changes are already in from
   step 2, so run tooling last):
   - yarn security:check-headers
   - yarn test:e2e:security
   - yarn test:e2e:auth
   - node .claude/scripts/verify.mjs

10. TASKS.md and TASKS_DONE.md: move T162.2 to Done in the same commit as the code
    changes, per repo convention. Verification evidence should list: the enforcement
    flip, the four new headers and their exact values, the new and updated Playwright
    specs and their pass counts, and the "local harness stands in for production
    preview" caveat from the Context section - don't let that caveat get lost between
    this plan and the final PR description.

## Non-obvious risks and things to not do

- Don't touch the CSP's own directives (script-src hash, style-src, connect-src,
  frame-src, frame-ancestors, img-src, font-src, object-src, base-uri, form-action) -
  T162.1 already scoped this ticket as a pure enforcement flip plus new headers.
- Don't add HSTS preload or a legacy X-Frame-Options header - both are explicitly out
  of scope (see Context section).
- Don't assume step 1's baseline is green without running it - an unrelated Expo or
  dependency bump since T162.1 merged could have drifted the inline-script hash, and
  that failure would be pre-existing, not something this ticket's changes caused.
- The framing Playwright test (step 6) is genuinely the highest-risk piece of this
  ticket for flakiness - treat first-draft failure as expected, not a sign the
  approach is wrong.
