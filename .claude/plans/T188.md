# T188 — Fix account deletion returning a 503

## Root cause (confirmed by reproduction)

This is **environmental, not a handler/app defect.**

Reproduction steps taken during planning:

1. `npx --yes supabase@2.116.0 start` on the pre-existing local stack reported
   success but printed `Stopped services: [supabase_imgproxy_daily-dama
   supabase_edge_runtime_daily-dama supabase_pooler_daily-dama]` and exited 0.
2. `docker ps -a --filter name=supabase` showed every container `Up`/`healthy`
   **except** `supabase_edge_runtime_daily-dama`, which was `Exited (15) 3 days
   ago`. `docker logs` on that container showed a clean `shutdown signal
   received: 15` — a routine SIGTERM from three days prior, not a crash.
3. Since `[edge_runtime]` in `supabase/config.toml` is `enabled = true`,
   `supabase start` should keep/bring it up, but it does not restart an
   already-`Exited` container when the rest of the stack is already `Up` —
   it just reports the mixed state and returns success. Kong (the local API
   gateway) then has no live upstream for `/functions/v1/delete-account` and
   returns `503` to any caller, including the app's
   `client.functions.invoke('delete-account', ...)` call in
   `src/features/auth/state/auth-provider.tsx`.
4. `npx --yes supabase@2.116.0 stop` followed by a fresh `npx --yes
   supabase@2.116.0 start --debug` brought every container up cleanly
   (`supabase_edge_runtime_daily-dama` now `Up`, no `Stopped services` line,
   `FUNCTIONS_URL` present in the printed status).
5. After that clean start plus `db reset`, `yarn test:functions` passed all
   26 tests across `t161_1_delete_account.test.mjs`,
   `t161_2_delete_account_security.test.mjs`, and
   `t161_3_delete_account_acceptance.test.mjs` (204 on valid deletion, cascade
   of Auth user + application rows, idempotent retry, rate limiting, all
   rejection paths) — i.e. the exact suites the task's Notes point to as the
   first diagnostic step.

Conclusion: the `delete-account` handler (`supabase/functions/delete-
account/handler.js`, `supabase/functions/delete-account/index.js`) and the
app-side call site (`src/features/auth/state/auth-provider.tsx`,
`src/features/auth/components/account-deletion-screen.tsx`) are correct as
shipped in T161.4. No handler or app code change is required. The fix is:
(a) get this specific local stack into a clean state, and (b) document the
recovery step so a developer hitting this again doesn't misattribute it to
app code.

Also confirmed while reading the UI code: the exit criterion "the deletion
control cannot be resubmitted after success" is **already implemented** —
`account-deletion-screen.tsx` guards resubmission three ways (`disabled=
{!isValid || isSubmitting || succeeded}` on the button, an early `if
(submittingRef.current || succeeded) return;` at the top of `handleSubmit`,
and a `succeeded` early-return that swaps in a terminal "Your account has
been permanently deleted." view before any authenticated-state branch can
re-render the form). Nothing to change there either.

## Implementation steps

1. **Recover this branch's local stack** (already done once during planning,
   but the implementer's own worktree needs it too — Docker state is local
   to the machine/session, not committed):
   ```sh
   npx --yes supabase@2.116.0 stop
   npx --yes supabase@2.116.0 start
   npx --yes supabase@2.116.0 db reset
   docker ps -a --filter name=supabase   # confirm every container is Up, none Exited
   ```

2. **Confirm the existing suites pass against the clean stack** (no code
   change expected, this is the acceptance evidence the task's Notes ask
   for):
   ```sh
   yarn test:functions
   node --test supabase/tests/functions/t161_3_delete_account_acceptance.test.mjs
   ```
   Finish with another `npx --yes supabase@2.116.0 db reset` per
   `supabase/README.md`'s convention of never leaving fixture rows behind.

3. **Document the recovery step in `supabase/README.md`.** Add a short
   subsection — e.g. "Troubleshooting: Edge Functions return 503 after a
   stale local stack" — placed right after "First-time / clean-reset
   workflow" (before "Running migration tests (pgTAP)"), since this can
   affect any local Edge Function invocation, not just `delete-account`, and
   a developer chasing a 503 is most likely to search this file first. It
   should state plainly:
   - Symptom: any Edge Function call (including `delete-account` invoked
     from the app) returns `503` even though `supabase start` reported
     success.
   - Cause: `supabase start` does not reliably restart an individual
     container (most commonly `supabase_edge_runtime_<project_id>`) that is
     `Exited` while the rest of the stack is already `Up`/`healthy` — it
     silently leaves it down and returns success anyway (sometimes visibly,
     via a `Stopped services: [...]` line in its own output; sometimes not).
   - Fix: `npx --yes supabase@2.116.0 stop` then `npx --yes supabase@2.116.0
     start` (a full stop/start cycle, not another `start` alone), then
     verify with `docker ps -a --filter name=supabase` that every listed
     container is `Up`.
   Cross-reference this subsection from the existing "Running the
   delete-account Edge Function tests" section with a one-line pointer, since
   that's the section this task's Notes sent the implementer to first.
   Do not touch `DEPLOYMENT_HANDOFF.md` — this is purely a local-stack
   reconciliation issue, not a hosted-deployment concern (`supabase/
   README.md`'s own "Non-goals" section already scopes hosted-project
   changes out of this directory's docs).

4. **Manual end-to-end UI verification** (the exit criterion explicitly
   requires this, not just the automated suites): with the local stack clean
   and the Expo web dev server running, sign up a real disposable test
   account through the app (confirm via Mailpit at
   `http://127.0.0.1:54324` per the existing manual-verification
   conventions in `supabase/README.md`), sign in, navigate to the account
   deletion screen, submit with the correct password and `DELETE`
   confirmation, and confirm:
   - The network call returns `204`.
   - The screen swaps to the terminal "Your account has been permanently
     deleted." state and the delete control cannot be resubmitted (already
     guaranteed by the guards described above — this step is about
     confirming it in practice, not adding new guards).
   - The Auth user is gone (Studio at `http://127.0.0.1:54323` → Auth →
     Users, or `db reset`'s absence of the row) and its application rows
     (profile, custom tricks, practice sessions, etc.) are gone too —
     cascade already proven by `t161_1_delete_account.test.mjs`, this is a
     spot-check through the real UI path rather than re-deriving that proof.

5. **Update task tracking.** In the same commit as the README change, move
   the `[T188]` entry from `TASKS.md` to `TASKS_DONE.md` per the existing
   "Completing a task" convention, flipping its status to `Done` and adding
   a short closing note describing the environmental root cause (stale
   `edge_runtime` container not restarted by a bare `supabase start`) and
   pointing at the new `supabase/README.md` subsection. Since T188 has no
   parent umbrella entry, no cascade move is needed.
