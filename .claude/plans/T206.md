# T206 -- Fix Home rendering blank after logging into a populated account

## Root-cause finding from this planning pass

Reading src/app/app/home.tsx, src/features/guest-import/state/use-guest-import.ts,
and src/features/guest-import/model/guest-import.ts end-to-end surfaces a concrete,
code-verified state-machine bug that produces exactly this symptom (genuinely blank,
survives refresh) -- but it has a precondition worth confirming during runtime repro
(see Step 1). Treat this as the primary, well-evidenced hypothesis to verify and fix,
not an assumed-correct diagnosis to implement blind -- the task explicitly calls for
runtime tracing first.

The mechanism:

1. use-guest-import.ts's "fresh-start kickoff" effect (around line 113) begins a
   guest-import inventory for any signed-in 'user' identity with an idle guest-import
   record -- this fires identically on signup and on a plain login to an existing
   account. It does not distinguish the two.
2. If this device has any local guest-scoped data at all (even trivial -- e.g. the
   person browsed Tricks or started onboarding before deciding to log into their
   existing account), hasAnyLocalGuestData is true, and the auto-confirm effect
   (around line 210) automatically drives the import into 'uploading' against
   whichever targetKind the inventory resolved. Because the destination account
   already has cloud data, deriveTargetKind resolves 'existing', so the merge path is
   readExistingAccountSnapshot + planExistingAccountMerge
   (guest-import-existing-account.ts), then the same runEmptyGuestImport push
   executor as the empty-account path.
3. home.tsx gates rendering entirely (blockingOnboardingRender renders null, not even
   KenteiOnboarding) whenever isGuestImportPendingResolution(guestImportState) is
   true, and that function treats any 'uploading' status as unconditionally pending
   (guest-import.ts around line 250) -- there's no timeout or escape hatch.
4. The bug: the uploading effect's catch block (use-guest-import.ts lines 304-308)
   only dispatches domainUploadSettled for domain: 'profile' on any thrown error,
   regardless of which domain/step actually failed. But guestImportReducer's
   domainUploadSettled case only transitions out of 'uploading' once
   allDomainsSettled is true across all 5 SYNC_DOMAINS. With only profile ever
   marked, the other 4 domains stay 'pending' forever, so the state machine can
   never leave 'uploading' -- it is permanently wedged, isGuestImportPendingResolution
   returns true forever, and Home renders null forever.
5. This durably persists (useIdentityScopedDomain under the hood) and resumes into
   the same stuck 'uploading' status on every reload -- matching "manual refresh
   doesn't fix it either" exactly, rather than being a one-off in-memory race.
6. The 'existing'-account merge path (readExistingAccountSnapshot /
   planExistingAccountMerge) has far more ways to throw against a real, populated
   account than the empty-account path T199 already fixed does: 5 additional cloud
   pulls (customTricks/practiceHistory/goals/notes on top of profile/trickState), an
   explicit throw new Error(target.error.message) on any pull failure
   (use-guest-import.ts line 260), and byId/trickStatesById helpers in
   guest-import-existing-account.ts that throw on a duplicate record id. None of this
   is exercised by T199's empty-account fix or its tests, and there is no existing
   test anywhere (checked use-guest-import.test.tsx, model/guest-import.test.ts) that
   covers a mid-upload exception -- only inventory-phase failures are tested. This is
   a genuine, previously unexercised gap, not a regression in already-tested code.

Precondition to confirm empirically: this mechanism requires the device to have had
some local guest-scoped data before the login (however small). If S087's actual
repro device was completely clean (never touched as a guest) before logging in, this
specific mechanism cannot have fired (auto-confirm never triggers) and Step 1 below
must broaden to the fallback hypotheses.

## Plan

1. Reproduce empirically first, per the task's own instruction -- do not skip to the
   fix.
   - Follow supabase/README.md's local Auth stack workflow to seed one real, existing
     account with practice-history/tricks/goals data (a fresh signup through the
     local stack, complete onboarding, log a session or two, add a custom trick --
     this makes it "populated"). Then, in a separate/incognito browser context, sign
     out (or start fresh) and, before logging in with that account's credentials,
     touch the app briefly as a guest (e.g. view Tricks, or partially start
     onboarding) so some local guest-scoped data exists on this device. Then log in
     with the seeded account's credentials.
   - Watch the browser console for a thrown/uncaught error during this login. If one
     appears, that's very likely the exception being swallowed into the stuck
     'uploading' state described above -- capture the exact error and where it
     originates (inventory pull for one of the 5 domains, snapshot mapping
     validation, or a duplicate-id throw).
   - Also try the same login without any prior guest interaction on a clean context,
     to confirm whether the precondition holds or whether Home is blank even then
     (in which case this hypothesis is ruled out and the search must widen -- see
     "If this hypothesis doesn't hold" below).
   - Confirm "refresh doesn't fix it" reproduces (reload the tab after the blank
     render) -- this is consistent with durably-persisted stuck 'uploading' state
     and rules out a pure in-memory timing race.

2. If confirmed: fix the state-machine gap in
   src/features/guest-import/model/guest-import.ts and its driver in
   src/features/guest-import/state/use-guest-import.ts. Order matters -- fix the
   reducer's vocabulary first, then the driver:
   - Add a new GuestImportAction case, e.g. { type: 'uploadFailed'; importId:
     string; errorMessage: string; now: number }, mirroring the existing
     'inventoryFailed' case exactly: guard on state.status === 'uploading' &&
     state.importId === action.importId, then reset to
     { ...INITIAL_GUEST_IMPORT_STATE, status: 'idle', errorMessage:
     action.errorMessage, updatedAt: action.now }.
     Follow the established pattern deliberately -- do not just dispatch
     domainUploadSettled for all 5 domains as a shortcut fix: domainUploadSettled's
     operationsSettled check falls back to an empty operations list when progress
     was never set (i.e. the throw happened before progressPrepared or
     existingMergePrepared, which is exactly the likely
     readExistingAccountSnapshot or duplicate-id failure case) -- an empty list is
     vacuously "settled", so that shortcut would silently flip the status to
     completed on a real failure instead of surfacing it, a worse and quieter bug
     than the current one.
   - In use-guest-import.ts's catch block (around lines 304-308), dispatch a new
     uploadFailed action (importId, the caught error message, and now) instead of
     the current single-domain domainUploadSettled dispatch.
   - isGuestImportPendingResolution's 'idle' fallthrough already returns false, so
     no change is needed there -- resetting to 'idle' is what unblocks home.tsx
     immediately.
   - Note this reset means the failed import is not automatically retried this
     session (attemptedGenerationRef in use-guest-import.ts already consumed this
     generation) -- that matches the existing inventoryFailed precedent and is an
     acceptable, consistent scope boundary; do not add a retry UI as part of this
     fix unless it turns out to be necessary to meet the exit criteria.
   - Also check, but do not necessarily fix as part of this ticket unless it's
     clearly the same bug: whatever the underlying thrown error actually is (found
     in Step 1) may itself be a separate, fixable defect (e.g. a mapping validator
     too strict for legitimate real data, or a genuine duplicate-id collision in
     the existing-account merge planner). Fix the state-machine wedge regardless
     (it's a hazard independent of what triggers it), and only also fix the
     throw's root cause if Step 1's repro shows it's the actual blocking issue for
     this account.

3. Tests, in this order:
   - src/features/guest-import/model/guest-import.test.ts: add reducer-level
     coverage for the new uploadFailed action -- from 'uploading' with partial
     domainOutcomes, confirm it resets to status idle, importId undefined, and
     errorMessage set; confirm a stale importId or non-'uploading' status is a

   - src/features/guest-import/model/guest-import.test.ts: add or confirm an

     confirm the new action doesn't require a new state shape it misses).
   - src/features/guest-import/state/use-guest-import.test.tsx: add a driver-level
     test that throws mid-upload (e.g. mock readExistingAccountSnapshot or the
     transport to reject) and assert the hook's state.status ends at 'idle' with
     errorMessage set, not stuck at 'uploading' -- this is the test that would
     have caught the current bug.
   - New or extended integration test at src/app/app/__tests__/ (sibling to
     home.guest-import-resync.test.tsx from T199): drive a real guest-import state
     machine through HomeScreen where the upload phase throws, and assert Home

   - Run the full guest-import domain test suite plus home.*.test.tsx, then full

4. Live-verify against the local Supabase stack, following T199's own precedent
   (TASKS_DONE.md's T199 entry describes exactly this workflow: real signup/login
   through /auth/v1/signup or /auth/v1/token, real Mailpit confirmation if needed,
   a real populated account) -- reproduce the original blank-Home symptom
   pre-fix, confirm it's fixed post-fix, and confirm it's stable across a reload,
   per the exit criteria. This is a guest-import/render-race class of change per

## If Step 1's hypothesis doesn't hold

If the repro device genuinely has zero local guest data and Home is still blank on
a plain login (no guest-import ever reaches 'uploading'), broaden the diagnosis
along these lines, in order of likelihood based on this session's reading of the
code:

- Uncaught render exception, no ErrorBoundary anywhere in the tree (confirmed:
  grepped the whole src/ tree for ErrorBoundary, componentDidCatch, and
  getDerivedStateFromError and found none). In React 18 web, an uncaught
  render-phase error with no boundary unmounts the entire root -- a fully blank
  page that would recur identically on every reload if triggered deterministically
  by this specific account's real data shape (something a mocked or seeded test
  account might not exercise). Check the browser console during repro before
  ruling this out. src/features/home/model/home-summary.ts and
  src/features/home/components/daily-home.tsx were both read in this planning
  pass and looked defensively written (no unguarded array access found), but this
  doesn't rule out a crash triggered by a real-account data shape not covered by
  existing tests or fixtures -- re-check both against whatever real data actually
  caused the blank render.
- useProfileDomainSync's pull-adopt path
  (src/features/profile/state/use-profile-domain-sync.ts) is the mechanism that
  should update the primary UserProfile reducer on a plain login -- read in this
  planning pass and appears correctly wired for the common case, but worth
  instrumenting or tracing live rather than assuming, since this ticket is
  explicitly "runtime diagnosis, not a known fix."
- Consider whether use-sync-coordinator.ts's allDomainsHydrated gate for firing
  the 'login' sync trigger (all 5 of profile, customTricks, practiceHistory,
  goals, and notes must report hydrated) could itself stall if one domain's
  hydration never resolves against real persisted data -- this wouldn't produce a
  blank screen (the per-provider hydration fallback screens would show instead,
  not null), but is worth ruling out if the reported "blank" is actually this
  fallback UI being mistaken for blank.

## Risks and non-obvious things for the implementer

- Do not conflate this with T199 -- T199's fix (the home.tsx isResyncingAfterImport
  effect) is for the empty-account signup path and is unrelated to this bug; don't
  touch it unless Step 1 shows an actual interaction between the two.
- The reducer fix must use a distinct terminal transition (uploadFailed resetting
  to idle), not a shortcut through domainUploadSettled, for the vacuous-truth
  reason explained in Step 2 -- this is the one place a "simpler" fix would
  introduce a worse, silent bug (an import that actually failed being reported as
  completed).
- Confirm during live verification that a second login attempt after a first
  failed import (still same session, attemptedGenerationRef already consumed)
  does not re-trigger importRequested and instead leaves guest-import at
  idle/non-blocking -- this is expected per the inventoryFailed precedent, not a
  new bug, but worth confirming it doesn't itself block anything.
