# T199 plan — stop re-showing onboarding to a guest whose data just got imported

## Confirmed root cause (traced, not assumed)

Sequence on a real guest-to-user signup with existing local data:

1. `IdentityProvider` flips `identity` to `{kind:'user', userId}` (new generation).
2. `UserProfileProvider`'s `useIdentityScopedDomain` hydrates the new, empty
   local storage namespace for that user (`user:<uuid>:...`) - this is a
   brand new account, so the freshly hydrated local `UserProfile` is
   `INITIAL_USER_PROFILE` (`hasCompletedOnboarding: false`, no `kenteiRank`).
   `hasHydrated` becomes `true` quickly with these empty-but-valid defaults,
   so `UserProfileProvider` stops blocking render.
3. `useSyncCoordinator`'s "login" effect
   (`src/shared/sync/use-sync-coordinator.ts` lines ~186-197) fires
   `runSync('login')` exactly once per identity generation, as soon as all 5
   domains report hydrated. At this point the cloud account is brand
   new/empty too (nothing has been imported yet), so the pull finds nothing
   and the local profile stays at defaults.
4. Independently, `useGuestImport()`
   (`src/features/guest-import/state/use-guest-import.ts`) runs its own
   state machine: `importRequested -> inventorying -> awaitingConfirmation ->
   (auto-confirm, T186.1) -> uploading`. The `uploading` phase
   (`runEmptyGuestImport`, called from
   `src/features/guest-import/persistence/guest-import-empty-account.ts`)
   pushes the guest's local profile (including `hasCompletedOnboarding` /
   `kenteiRank`) directly to the cloud `profile` row via its own outbox
   push. This is a separate write path from `useProfileDomainSync`'s
   envelope/outbox, and it never touches the local storage or dispatches
   into the primary `UserProfile` reducer for the new identity.
5. Once every `SYNC_DOMAINS` entry reports `domainUploadSettled` with
   `succeeded`, `guestImportReducer` transitions `state.status` to
   `'completed'` (`src/features/guest-import/model/guest-import.ts` lines
   ~234-244). `home.tsx`'s `importPending` gate
   (`isGuestImportPendingResolution`, same file, lines ~300-309) returns
   `false` for `'completed'`, so the import-in-progress blank screen goes
   away.
6. Nothing ever re-triggers a profile pull after step 4's cloud write.
   `useSyncCoordinator`'s login effect already fired once (step 3, before
   the import pushed anything) and is explicitly gated to fire only once
   per generation. The cloud row now holds the correct
   `hasCompletedOnboarding`/`kenteiRank`, but the local primary
   `UserProfile` reducer, the only thing `home.tsx` reads, was never told
   to re-pull it.
7. `home.tsx` renders: `importPending` is now `false`,
   `profile.hasCompletedOnboarding` is still `false` locally, so
   `<KenteiOnboarding/>` renders. This is the reported flash: blank during
   import, then onboarding paints once import "finishes".

This is confirmed structurally by reading `use-profile-domain-sync.ts` (the
only code path that ever dispatches `profileRestored` from cloud data into
the primary reducer, gated behind `runSync`) and `use-sync-coordinator.ts`
(`runSync('login')` fires once per generation; no other automatic trigger is
guaranteed to fire in this window). It matches T189's bug class per the task
Notes: an identity-scoped read (the primary profile reducer, as read by
`home.tsx`) lands before a write (the import's cloud push) is reflected back
locally, except here there is no automatic second read at all, not just a
race.

The same underlying gap almost certainly affects the other 4 sync domains
(customTricks, practiceHistory, goals, notes) too. See "Deliberately out of
scope" below for why this plan does not fix that general case now.

## Fix

Add a profile-domain resync, awaited and gating the onboarding render,
triggered exactly when guest-import reaches `'completed'`. Implement this in
`src/app/app/home.tsx`, the one place that already composes
`useGuestImport()` state with `useUserProfile()`/identity and already reads
`isGuestImportPendingResolution` (T186.1's precedent for this exact kind of
gate). No new provider wiring is needed since `home.tsx` already renders
under `UserProfileProvider` in both the real app tree (`_layout.tsx`) and its
own test harness (`mountHomeScreen()` in
`src/app/app/__tests__/home.test.tsx`).

### 1. `src/app/app/home.tsx`

- Import `useUserProfileSync` from
  `@/features/profile/state/user-profile-provider` (already exported,
  currently only used from `SyncCoordinatorProvider`).
- Call `const { runSync } = useUserProfileSync();`. `runSync`'s identity is
  fully stable across renders (`useCallback(fn, [runSyncImpl])` where
  `runSyncImpl` itself has an empty dep array in
  `use-profile-domain-sync.ts`), so it is safe as an effect dependency
  without causing spurious re-fires.
- Add local state `const [isResyncingAfterImport, setIsResyncingAfterImport] = useState(false);`
  and a ref `const resyncedImportIdsRef = useRef<Set<string>>(new Set());`
  (mirrors the existing `autoConfirmedRef`/`importStartedRef` idiom already
  used in `use-guest-import.ts`; keep the same style).
- Add an effect along these lines:

```tsx
useEffect(() => {
  if (identity.kind !== 'user') {
    // Covers logout/account-switch while a resync was in flight: never
    // leave a stale identity's in-progress flag blocking a different
    // (possibly guest) identity's render.
    setIsResyncingAfterImport(false);
    return;
  }
  if (guestImportState.status !== 'completed') return;
  const importId = guestImportState.importId;
  if (importId === undefined) return;
  if (resyncedImportIdsRef.current.has(importId)) return;
  resyncedImportIdsRef.current.add(importId);

  let cancelled = false;
  setIsResyncingAfterImport(true);
  void runSync('login').finally(() => {
    if (!cancelled) setIsResyncingAfterImport(false);
  });
  return () => {
    cancelled = true;
  };
}, [identity, guestImportState.status, guestImportState.importId, runSync]);
```

Notes on this shape:

- Gate strictly on `state.status === 'completed'`, not on
  `hasAnyLocalGuestData`/inventory checks. Per the reducer
  (`guest-import.ts`), `'completed'` is only reached after every
  `SYNC_DOMAINS` entry settles from a real `uploading` phase, so it is
  already an "a real import just finished" signal on its own.
- `runSync('login')` reuses the existing trigger label used for the normal
  post-hydration pull; it does not add a new `SyncTrigger` variant. It calls
  `useUserProfileSync().runSync` directly, not
  `useSyncCoordinatorStatus().requestManualSync()`. The coordinator's
  `requestManualSync` is fire-and-forget (no promise to await), so it
  cannot precisely gate the render the way this fix needs to. Calling the
  profile domain's own `runSync` directly is safe: it has its own
  single-flight guard (`inFlightRef` in `use-profile-domain-sync.ts`), and
  bypassing the coordinator only means this one resync will not be
  reflected in `SyncStatusSection`'s "last successful sync" timestamp,
  which is acceptable for a background catch-up pull.
- The `resyncedImportIdsRef` guard (keyed by `importId`, not a one-shot
  "first render" flag) means a page reload after a previous session's
  already-completed import will safely re-fire this resync once more
  (component-local ref resets on remount): a harmless, idempotent extra
  pull, and actually a self-healing property if a prior resync attempt
  failed (e.g. offline at the time).

- Replace the render-gating condition. Currently:

```tsx
const importPending = identity.kind === 'user' && isGuestImportPendingResolution(guestImportState);
...
background={importPending || profile.hasCompletedOnboarding ? undefined : ...}
...
{importPending ? null : profile.hasCompletedOnboarding && profile.kenteiRank ? <DailyHome .../> : <KenteiOnboarding/>}
```

Both usages of `importPending` must also block on the new in-flight resync,
otherwise there is still a window between `status` flipping to `'completed'`
(import-blank-screen gate lifts) and `runSync('login')` actually resolving
and dispatching `profileRestored`. During that window `hasCompletedOnboarding`
is still locally `false`, so onboarding would flash anyway. Combine them,
e.g.:

```tsx
const importPending = identity.kind === 'user' && isGuestImportPendingResolution(guestImportState);
const blockingOnboardingRender = importPending || isResyncingAfterImport;
```

and use `blockingOnboardingRender` everywhere `importPending` is currently
read in the JSX (both the `background` ternary and the
`{importPending ? null : ...}` branch).

### 2. Tests

Add coverage that actually exercises the fixed sequence end-to-end at the
component level (not just the reducer). A plain reducer test would not have
caught this bug, since the reducer transitions were all individually
correct; the bug was in the composition of `home.tsx` with both hooks.

- Extend `src/app/app/__tests__/home.test.tsx`. Its `mountHomeScreen()`
  helper only wraps `CustomTrickProvider` / `UserProfileProvider` /
  `PracticeHistoryProvider` around `HomeScreen`, and existing tests rely on
  the `DEFAULT_HANDLE` guest-identity fallback from `useIdentityHandle()`
  (no `IdentityProvider` in the tree). For the new test(s), follow
  `src/features/guest-import/state/use-guest-import.test.tsx`'s own pattern
  instead: wrap with `IdentityHandleContext.Provider` directly (supplying a
  `user` identity plus a real `createIdentityContext()` so
  `generation`/`isCurrentGeneration` work), and reuse its established mocks
  for `@/features/guest-import/persistence/guest-import-inventory`
  (`countLocalGuestRecords`, `countCloudRecords`, `buildGuestImportTransports`)
  to drive a deterministic `inventorying -> awaitingConfirmation ->
  uploading -> completed` sequence with nonzero local guest data.
  - Additionally mock (or use a lightweight fake) the profile pull path so
    `runSync('login')`'s `transport.pullProfileRow()` resolves with a row
    reflecting `hasCompletedOnboarding: true` / a `kenteiRank` after the
    import "uploads" it. The test needs to simulate the cloud gaining that
    data as a result of the mocked upload, then confirm the resync picks it
    up. `getSupabaseClient` is already mockable via
    `jest.mock('@/shared/supabase/supabase-client', ...)`, matching
    `use-guest-import.test.tsx`'s own convention.
  - Assert the specific regression: at no point during the full act/flush
    sequence does `<KenteiOnboarding/>`'s content render (e.g. assert its
    known heading/copy never appears via `findByText`), and the screen
    settles on `<DailyHome/>` (assert on content that only `DailyHome`
    renders, using existing helpers already in this file such as
    `findByText`/`findTimeLoggedTileValue`).
  - If wiring a full mocked push+pull profile transport turns out to be
    excessive for `home.test.tsx`'s existing scope, an acceptable
    alternative is a new integration test file under
    `src/features/guest-import/state/` or `src/shared/sync/`, modeled on
    `src/shared/sync/two-browser-convergence.integration.test.tsx`'s
    provider-wiring plus mocked-Supabase-client harness (it already
    assembles the full `CustomTrickProvider -> UserProfileProvider ->
    PracticeHistoryProvider -> NoteProvider -> GoalProvider ->
    SyncCoordinatorProvider` stack with a working mock transport). Mount
    `HomeScreen` inside that stack instead of raw hook consumers, seed
    guest `AsyncStorage` with a completed profile before flipping identity
    to `user`, and assert the same "onboarding never renders" property.
    Prefer whichever of these two keeps the test closest to actually
    re-triggering the bug: do not just unit-test the new effect in
    isolation with a mocked `runSync`.
- No reducer-level test changes are needed. `guest-import.test.ts`'s
  existing coverage of the `'completed'` transition stays valid as-is.

### 3. Live verification (required by the exit criteria)

The exit criteria explicitly require a real signup through the actual auth
flow, not a seeded fixture. Use the local Supabase Auth stack per
`supabase/README.md` (already the project's normal local dev workflow). This
does not require the hosted Supabase project: `supabase/README.md`'s local
CLI stack fully implements signup, email verification via Mailpit, and
session issuance against `localhost`, and nothing about this bug's mechanism
(a client-side timing gap in when the local profile reducer gets refreshed)
depends on which Supabase project is targeted. Unlike T195/T197, this
ticket's fix and its verification are both purely local.

Steps:

1. `supabase start` (or confirm it is already running) and run the app
   against the local stack per `supabase/README.md`.
2. As a guest (no account), complete onboarding and log at least one
   practice Sesh so there is real local profile plus practice-history data
   to import.
3. Sign up with a fresh email through the real `/auth/sign-up` flow, verify
   via Mailpit per `supabase/README.md`'s documented flow.
4. Watch the Home screen through the entire post-signup sequence: confirm
   the import's blank/import-pending window is followed directly by
   `DailyHome`. `KenteiOnboarding` must never paint, not even briefly.
   Check the browser console for unexpected errors/warnings during this
   window (the two known-benign warnings from `AGENTS.md` are expected;
   anything else is not).
5. Reload the page after signup completes and confirm Home still renders
   directly (covers the "stale ref, page reload" idempotent-resync case
   noted above).

## Deliberately out of scope for this task

- Fixing the equivalent local-staleness gap for the other 4 sync domains
  (customTricks, practiceHistory, goals, notes) after a guest import. The
  same "no automatic re-pull after the import's cloud push" mechanism
  likely affects them too (e.g. Tricks/Stats/Goals/Notes could render
  empty immediately post-signup until `foreground`/`reconnect`/a local
  edit eventually triggers a real sync), but nothing in the codebase
  currently gates rendering on that in a user-visible way the way
  `home.tsx` gates onboarding, so there is no equivalent "flash" bug
  report for those screens yet. If live verification (step 4 above) shows
  e.g. Tricks or Stats also render empty right after signup, note it as a
  new backlog candidate rather than folding a 5-domain fix into this
  ticket.
- Triggering the full `useSyncCoordinatorStatus().requestManualSync()`
  (all 5 domains) as a fire-and-forget addition alongside the awaited
  profile-only resync. This would reduce the other domains' staleness
  window too and is cheap to add, but pulls in a `SyncCoordinatorProvider`
  dependency that `home.tsx` does not otherwise need for this fix, and
  would require wrapping `mountHomeScreen()` in
  `GoalProvider`/`NoteProvider`/`SyncCoordinatorProvider` for every
  existing test in `home.test.tsx` (not just new ones), since hooks
  cannot be called conditionally. Consider this only if live verification
  turns up a visible problem in one of the other domains.
- `useGuestImport()`'s `UseGuestImportResult` not exposing its own
  `hasHydrated`. There is a latent, narrower version of "stale read before
  identity's own hydration completes" inside `use-guest-import.ts` itself
  (a brief window where `guestImportState` can still reflect a previous
  identity's restored value before this generation's own hydration effect
  resolves). It does not affect this fix's correctness (the ref-guard is
  harmless either way), but is worth flagging as a possible follow-up
  rather than fixing here.
