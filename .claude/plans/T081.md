# T081 — Preselect direct-practice trick on the Sesh screen with a cancel affordance

## Context already confirmed in current code (development, post-T077.2)

- All six direct-practice-style links (`neglected-tricks-section.tsx:37`,
  `trick-goals-screen.tsx:141`, `trick-directory.tsx:314`, `daily-home.tsx:70`
  and `:120`, `stats/[trickId].tsx:82`) pass **both** `trickId` and
  `mode: 'practice'` — `mode` is never sent without `trickId` and vice versa.
  So "is this a direct-practice entry" can be computed as
  `mode === 'practice' && trickId is present`, exactly as the task description
  implies.
- `src/app/sesh/index.tsx` currently destructures only `trickId` and
  `plannedDurationMs` from `useLocalSearchParams`; `mode` is not read at all.
- `preferredTrickId` (`trickIdParam ?? lastSesh?.trickId`) is today the only
  mechanism that influences trick choice, and it just reorders/highlights the
  full `TrickPicker` list (`selectSeshPracticeTricks`) — it does not restrict
  the list. This behavior is still wanted for the plain "Sesh" tab visit case
  (prioritize whatever trick was last practiced), it's only wrong for the
  direct-practice case.
- `seshReducer`'s `'choosing'` state (`src/features/sesh/model/sesh.ts:93`)
  currently carries no fields. `INITIAL_SESH_STATE = { status: 'choosing' }`.
  `'seshReset'` unconditionally returns `INITIAL_SESH_STATE` and is already
  reused for "cancel countdown" and "reset after completed"
  (`src/features/sesh/components/sesh.tsx:181`, `:213`).
- `TrickPicker` (internal, not exported, `sesh.tsx:260-437`) already renders
  exactly the tricks it's given — passing it a one-element `tricks` array
  today would already render only that one card. The only things it always
  renders regardless of list size are the "Practice several tricks" promo
  link and the fixed heading copy.
- `Countdown` in the same file already has an established, optional
  `onCancel?: () => void` prop pattern that conditionally renders a
  `CancelButton`. Reuse that same pattern name/shape on `TrickPicker` rather
  than inventing a different shape.
- There is no existing `src/app/sesh/__tests__/index.test.tsx`; the
  established test pattern for this exact behavior (T077.2's "Sesh
  direct-practice planning" describe block) mounts `Sesh` directly with props,
  not through the route file. `src/app/sesh/__tests__/layout.test.tsx` fully
  mocks `Sesh`, so it is insulated from any prop changes here.

## Design decisions (settled, not to re-litigate mid-implementation)

1. **Reducer state carries the flag, on the existing `'choosing'` variant, not
   a new top-level status.** Change:
   ```ts
   | { readonly status: 'choosing'; readonly directPracticeTrickId?: string }
   ```
   Do **not** introduce a fourth `SeshAction`/new dispatch type. This keeps
   every other reducer case (`trickSelected`, etc.) untouched — they already
   discard extra fields when transitioning away from `'choosing'`.
   `INITIAL_SESH_STATE` stays `{ status: 'choosing' }` (field omitted), so
   `'seshReset'` dispatched from anywhere always lands back on the plain,
   un-preselected choosing state. This is exactly what lets the Cancel
   control reuse `'seshReset'` with zero new reducer logic, per the task's
   notes.

2. **`Sesh` picks up the direct-practice trick id via lazy `useReducer` init,
   not via a reactive effect.** i.e.:
   ```ts
   const [state, dispatch] = useReducer(
     seshReducer,
     directPracticeTrickId,
     (id): SeshState => (id ? { status: 'choosing', directPracticeTrickId: id } : INITIAL_SESH_STATE),
   );
   ```
   This is a deliberate, documented scope limitation: if the same mounted
   `/sesh` screen instance somehow received a *different* `directPracticeTrickId`
   prop later without unmounting (e.g. browser back/forward while still on the
   Sesh tab), the reducer would not re-sync to it. The realistic recurrence of
   this — re-selecting the Sesh tab while stale params are showing — is
   already handled by the existing `tabPress` listener in
   `src/app/sesh/_layout.tsx`, which force-replaces to bare `/sesh`. Do not
   add a prop-sync `useEffect`/extra action for this unless you find a real
   repro; it adds a second source of truth (a ref tracking "last seen prop
   value") purely to avoid re-entering direct-practice mode right after the
   user presses Cancel, and isn't worth it for this iteration.

3. **`TrickPicker` gets one new optional prop, `onCancel?: () => void`**,
   mirroring `Countdown`'s existing pattern. When present, treat the call as
   direct-practice mode:
   - Skip the `<Link href="/sesh/multi-trick">` promo block entirely (it
     would navigate away from the focused flow the user was dropped into,
     which conflicts with Cancel being the intended escape hatch).
   - Swap the `Eyebrow`/`DisplayTitle`/`BodyCopy` heading copy for
     direct-practice wording (e.g. `Eyebrow`: "Direct practice",
     `DisplayTitle`: the trick's name, `BodyCopy`: something like "Adjust the
     format below, then start whenever you're ready.").
   - Render a `CancelPracticeButton` (a `styled(Button)`, secondary variant,
     matching `CancelButton`'s pattern at `sesh.tsx:1169`) with
     `accessibilityLabel="Cancel practice"` and visible text "Cancel
     practice", wired to the new `onCancel` prop.
   - Leave the "Practice format" fields, duration/target inputs, the
     "beat your best" challenge field, and the `TrickChoices` map entirely
     unmodified — they already work correctly for a one-element `tricks`
     array (validation state, disabled Start button, personal-best lookup are
     all generic over the array, not hardcoded to "multiple tricks").
   - Do not pass `preferredTrickId` in the direct-practice call (there's
     nothing to prioritize among one trick), so `isPreferred` naturally stays
     `false` and no "Up next ·" prefix renders on the single card.

4. **`Sesh`'s `'choosing'` render branch does the lookup and picks the
   variant**, checked *before* the existing `practiceTricks.length === 0`
   `EmptyState` early-return — a direct-practice link must work even for a
   user with an empty focused practice list, since the linked trick doesn't
   have to be in `selectedTrickIds`:
   ```ts
   if (state.status === 'choosing') {
     const directPracticeTrick = state.directPracticeTrickId
       ? availableTricks.find((trick) => trick.id === state.directPracticeTrickId)
       : undefined;
     if (directPracticeTrick) {
       return (
         <TrickPicker
           initialPlan={initialPlan}
           tricks={[directPracticeTrick]}
           sessions={sessions}
           onSelect={handleTrickSelected}
           onCancel={() => dispatch({ type: 'seshReset' })}
         />
       );
     }
     if (practiceTricks.length === 0) return <EmptyState />;
     return (
       <TrickPicker
         initialPlan={initialPlan}
         preferredTrickId={validatedPreferredTrickId}
         tricks={practiceTricks}
         sessions={sessions}
         onSelect={handleTrickSelected}
       />
     );
   }
   ```
   Lookup against `availableTricks` (not `practiceTricks`/`selectedTrickIds`),
   matching the existing fallback semantics `selectSeshPracticeTricks` already
   uses for `preferredTrickId`. If the linked trick id isn't found (e.g. a
   deleted custom trick), fall straight through to the normal multi-trick
   picker — this mirrors T077.2's existing "falls back to the focused
   practice list when the preferred trick is unavailable" behavior, now for
   this new prop instead of `preferredTrickId`.

5. **`index.tsx` reads `mode` and computes a new, separate
   `directPracticeTrickId`**, keeping `preferredTrickId` exactly as it is
   today (still `trickIdParam ?? lastSesh?.trickId`, still passed through)
   for the plain-visit prioritization case and as the fallback path's input:
   ```ts
   const { trickId: trickIdParam, plannedDurationMs: plannedDurationMsParam, mode: modeParam } =
     useLocalSearchParams<{ trickId?: string | string[]; plannedDurationMs?: string | string[]; mode?: string | string[] }>();
   const linkedTrickId = typeof trickIdParam === 'string' ? trickIdParam : undefined;
   const isDirectPractice = linkedTrickId !== undefined && (typeof modeParam === 'string' ? modeParam : undefined) === 'practice';
   const preferredTrickId = linkedTrickId ?? lastSesh?.trickId;
   ...
   <Sesh
     availableTricks={availableTricks}
     initialPlan={initialPlan}
     preferredTrickId={preferredTrickId}
     directPracticeTrickId={isDirectPractice ? linkedTrickId : undefined}
     selectedTrickIds={selectedTrickIds}
   />
   ```
   The `plannedDurationMs` → `initialPlan` wiring is untouched; the "Challenge"
   link from `stats/[trickId].tsx` already sends `mode: 'practice'` alongside
   it, so a challenge now also lands on the focused single-trick card with
   the timed duration prefilled, editable before starting — consistent with
   the exit criteria ("format and duration/target remain editable").

## Implementation order

1. `src/features/sesh/model/sesh.ts` — widen the `'choosing'` union member to
   add `readonly directPracticeTrickId?: string`. No other reducer changes.
   Do this first; it's the type both the component and its tests depend on.
2. `src/features/sesh/model/sesh.test.ts` — add reducer-level coverage next
   to the existing `describe('sesh reducer', ...)` block:
   - `'seshReset'` from `{ status: 'choosing', directPracticeTrickId: 'x' }`
     returns exactly `INITIAL_SESH_STATE` (i.e. the field is gone, not just
     falsy) — this is the concrete "reducer/state path" the exit criteria
     asks for.
   - `'trickSelected'` from that same state still transitions to
     `'countdown'` normally (the field doesn't block or alter the existing
     transition).
3. `src/features/sesh/components/sesh.tsx`:
   - Add `directPracticeTrickId?: string` to `SeshProps`.
   - Switch `useReducer(seshReducer, INITIAL_SESH_STATE)` to the 3-arg lazy
     form described in decision 2 above.
   - Update the `'choosing'` render branch per decision 4.
   - Add `onCancel?: () => void` to `TrickPicker`'s props and implement the
     conditional heading/promo-link/Cancel-button rendering per decision 3.
     Add the `CancelPracticeButton` styled component near `CancelButton`
     (`sesh.tsx:1169`) and the `MultiTrickAction`-family styles for a
     consistent look.
4. `src/app/sesh/index.tsx` — wire `mode`/`directPracticeTrickId` per
   decision 5.
5. `src/features/sesh/components/sesh.test.tsx` — add a new
   `describe('Sesh direct-practice entry (T081)', ...)` block (reuse the
   existing `mountSesh` helper pattern from the T077.2 block just above it,
   or lift it to a shared local helper if that reads more cleanly) covering:
   - Mounting with `directPracticeTrickId={TRICK.id}` renders **only**
     `Start a sesh with ${TRICK.name}` — assert `OTHER_TRICK.name` does not
     appear anywhere in the rendered tree at all (not just "not as a start
     choice"), since the exit criteria is "no other trick cards shown."
   - Format controls remain present and editable: duration input changes
     re-enable/disable the Start action exactly as the existing T077.2
     "customized timed plan" test does; reuse/adapt that test body against
     the new prop.
   - An open-ended target can be set and carried into the started session
     (adapt the existing "customized open-ended target" test body).
   - `accessibilityLabel: 'Cancel practice'` is present and pressing it
     returns to the standard picker: after pressing, both `TRICK.name` and
     `OTHER_TRICK.name` render as separate `Start a sesh with ...` choices,
     and the "Practice several tricks" link is back.
   - Falls back to the normal multi-trick picker (both tricks shown, no
     Cancel button) when `directPracticeTrickId` doesn't match any
     `availableTricks` entry — mirrors the existing "falls back... when the
     preferred trick is unavailable" test, but for this prop.
   - Works even when `selectedTrickIds` is empty (regression guard for the
     "checked before `EmptyState`" ordering in decision 4) — mount with
     `selectedTrickIds={[]}` and `directPracticeTrickId={TRICK.id}` and
     assert the single card renders instead of the "Nothing queued" empty
     state.
   - Leave the existing `describe('Sesh direct-practice planning (T077.2)', ...)`
     block's tests as-is (they exercise `preferredTrickId` directly, still a
     real, unchanged code path). Its title is now slightly misleading since
     T081 owns "direct practice" — a rename to something like
     `'Sesh preferred-trick prioritization (last sesh)'` is reasonable
     cleanup but not required for correctness; use your judgment.
