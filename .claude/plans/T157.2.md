# T157.2 — Single-flight identity-aware sync coordinator

## Scope for this iteration

Pure reducer/state-machine + unit tests only, in `src/shared/sync/`, matching
the sibling files from T157.1 (`domain.ts`, `outbox-operation.ts`,
`sync-envelope.ts`). No React hook/provider, no Supabase/network calls, no
login/foreground/reconnect listeners, no backoff/debounce timers. Those are
explicitly later tickets:

- The actual per-domain network calls and idempotent push/pull transport are
  T157.3's job. This ticket only defines the shape of a domain's outcome
  (`DomainSyncOutcome`) that T157.3's transport will eventually report back
  through `domainSettled` — it does not call any repository.
- Wiring real triggers (login, foreground, local mutation, reconnect, manual
  retry) with debouncing/coalescing timers is T157.9's job. This ticket only
  defines the `SyncTrigger` union and the coordinator's reaction to a trigger
  arriving; nothing here starts a timer or listens to app state.
- A React driver hook (a `useSyncCoordinator`-style wrapper comparable to
  `useIdentityScopedDomain`) is *not* built in this ticket. `useIdentityScopedDomain`
  (`src/shared/persistence/use-identity-scoped-domain.ts`) is the reference
  pattern a later ticket (T157.9) should follow to drive this reducer from
  `useIdentityHandle()` — read it, but do not build it now. Note this
  explicitly to the user as a deliberate scope boundary, not an oversight.

Good enough for this iteration: the state machine's transitions are fully
specified and unit-tested against every exit-criteria scenario, using plain
`reducer(state, action)` calls with hand-supplied timestamps/ids/generations
(no timers, no promises) — exactly like `src/features/sesh/model/sesh.test.ts`
tests `seshReducer` and `src/shared/sync/sync-envelope.test.ts` tests envelope
mutations.

## Key existing pieces this design builds directly on

- `src/shared/sync/domain.ts` — `SYNC_DOMAINS` / `SyncDomain` (profile,
  customTricks, practiceHistory, goals, notes). The coordinator considers a
  run "finished" once all five domains have reported a result.
- `src/shared/persistence/identity-context.ts` — `IdentityContext` already
  tracks `generation` (`getGeneration`, `setIdentity` returns the new
  generation, `isCurrentGeneration`). The coordinator does **not** duplicate
  this; it receives `identityGeneration` values as action payloads (supplied
  by the future driver reading `context.getGeneration()` /
  `context.setIdentity()`'s return value), exactly the way
  `useIdentityScopedDomain` captures `context.getGeneration()` before async
  work and later calls `context.isCurrentGeneration(captured)`.
- `src/shared/persistence/use-identity-scoped-domain.ts` — the template for
  "external driver dispatches actions with injected generation/timestamps;
  reducer/guard is the authority that discards stale results." The
  coordinator reducer plays the same authority role `isCurrentGeneration` /
  `checkIdentity` (in `sync-envelope.ts`) play elsewhere.
- `src/features/sesh/model/sesh.ts` — the reference for "reducer takes a
  caller-supplied `now`, never calls `Date.now()` itself, and effects/timers
  live entirely outside the reducer." Follow this exact discipline.
- `src/shared/sync/outbox-operation.ts` — the injectable-id pattern
  (`createOutboxOperationId(now, random)`); mirror it for run ids.

## `coordinator.ts` design

### Types

```ts
import { SYNC_DOMAINS, type SyncDomain } from '@/shared/sync/domain';

export type SyncTrigger = 'login' | 'foreground' | 'localMutation' | 'reconnect' | 'manual' | 'retry';

export type DomainSyncOutcome =
  | { readonly status: 'succeeded' }
  | { readonly status: 'failed'; readonly errorMessage: string };

export interface DomainSyncRecord {
  readonly domain: SyncDomain;
  readonly outcome: DomainSyncOutcome;
  readonly settledAt: number;
}

export interface ActiveSyncRun {
  readonly runId: string;
  readonly identityGeneration: number;
  readonly trigger: SyncTrigger;
  readonly startedAt: number;
  readonly domainResults: Readonly<Partial<Record<SyncDomain, DomainSyncRecord>>>;
  // A trigger that arrived while this run was in flight, coalesced instead of
  // starting a second concurrent run. First coalesced trigger wins (see
  // "Design notes" below) -- deliberately simple, not priority-ordered.
  readonly queuedRerunTrigger: SyncTrigger | undefined;
}

export type FinishedSyncRunOutcome = 'completed' | 'cancelled';

export interface FinishedSyncRun {
  readonly runId: string;
  readonly identityGeneration: number;
  readonly trigger: SyncTrigger;
  readonly startedAt: number;
  readonly endedAt: number;
  readonly outcome: FinishedSyncRunOutcome;
  // Partial when outcome === 'cancelled' (identity changed mid-run); full
  // (one entry per SyncDomain) when outcome === 'completed'.
  readonly domainResults: Readonly<Partial<Record<SyncDomain, DomainSyncRecord>>>;
}

export type SyncCoordinatorState =
  | {
      readonly status: 'idle';
      readonly identityGeneration: number;
      readonly lastRun: FinishedSyncRun | undefined;
      // Set when the run that produced `lastRun` had a coalesced trigger
      // queued; a future driver (T157.9) should immediately start a new run
      // for this trigger and the reducer will clear the field naturally
      // (the 'running' state variant has no such field).
      readonly pendingRerunTrigger: SyncTrigger | undefined;
    }
  | {
      readonly status: 'running';
      readonly identityGeneration: number;
      readonly run: ActiveSyncRun;
    };
```

### Actions

```ts
export type SyncCoordinatorAction =
  | {
      readonly type: 'syncRequested';
      readonly trigger: SyncTrigger;
      readonly identityGeneration: number; // generation captured by the driver at trigger time
      readonly runId: string;
      readonly now: number;
    }
  | {
      readonly type: 'domainSettled';
      readonly runId: string;
      readonly identityGeneration: number;
      readonly domain: SyncDomain;
      readonly outcome: DomainSyncOutcome;
      readonly now: number;
    }
  | {
      readonly type: 'identityChanged';
      readonly identityGeneration: number; // the NEW generation
      readonly now: number;
    };
```

### `createInitialCoordinatorState(identityGeneration: number): SyncCoordinatorState`

Returns `{ status: 'idle', identityGeneration, lastRun: undefined, pendingRerunTrigger: undefined }`.
A future driver seeds this from `context.getGeneration()`, mirroring
`useIdentityScopedDomain`'s use of `useIdentityHandle()`.

### `createSyncRunId(now = Date.now(), random = Math.random()): string`

Same shape as `createOutboxOperationId` (`` `run-${now.toString(36)}-${...}` ``)
so it's deterministic/injectable in tests.

### `syncCoordinatorReducer(state, action): SyncCoordinatorState`

**`syncRequested`**
- If `action.identityGeneration !== state.identityGeneration`: no-op, return
  `state` unchanged. (A trigger captured under a since-superseded generation —
  e.g. a debounced foreground check that fires after the user switched
  accounts — must not start or affect anything.)
- If `state.status === 'idle'`: start a new run —
  `{ status: 'running', identityGeneration: action.identityGeneration, run: { runId: action.runId, identityGeneration: action.identityGeneration, trigger: action.trigger, startedAt: action.now, domainResults: {}, queuedRerunTrigger: undefined } }`.
- If `state.status === 'running'`: single-flight — do not start a second run.
  Coalesce: `run.queuedRerunTrigger = state.run.queuedRerunTrigger ?? action.trigger`
  (first-wins; document this as a deliberate simplification, not a priority
  scheme — nothing in the exit criteria requires trigger-priority ordering).

**`domainSettled`**
- Guard (stale-completion protection): if `state.status !== 'running'`, or
  `state.run.runId !== action.runId`, or
  `state.run.identityGeneration !== action.identityGeneration`, return `state`
  unchanged. This is the literal mechanism for "no late result can mutate
  current state after logout or account switching" and for the general
  stale-completion scenario (a straggling result from an already-finished or
  already-cancelled run).
- Otherwise merge:
  `domainResults = { ...state.run.domainResults, [action.domain]: { domain: action.domain, outcome: action.outcome, settledAt: action.now } }`.
  A failing domain is recorded, never thrown/rejected up — this is the
  concrete "contained operation failure" mechanism; nothing else about the
  run state changes because one domain failed.
- If `Object.keys(domainResults).length < SYNC_DOMAINS.length`, stay
  `running` with the updated `domainResults`.
- Else (all five domains reported) the run is finished. Transition to idle:
  ```ts
  {
    status: 'idle',
    identityGeneration: state.identityGeneration,
    lastRun: {
      runId: state.run.runId,
      identityGeneration: state.run.identityGeneration,
      trigger: state.run.trigger,
      startedAt: state.run.startedAt,
      endedAt: action.now,
      outcome: 'completed',
      domainResults,
    },
    pendingRerunTrigger: state.run.queuedRerunTrigger,
  }
  ```
  Note `outcome: 'completed'` means "ran to conclusion," independent of
  whether individual domains succeeded — callers inspect `domainResults` for
  partial failure, exactly like `SeshSummary` records what happened rather
  than judging it.

**`identityChanged`**
- If `state.status === 'running'`: the in-flight run is cancelled. Produce
  `lastRun` with `outcome: 'cancelled'`, `endedAt: action.now`, and whatever
  partial `state.run.domainResults` had accumulated (possibly `{}`). Drop
  `queuedRerunTrigger` entirely — it was a reason to resync under the *old*
  identity and must not leak into the new one.
  ```ts
  {
    status: 'idle',
    identityGeneration: action.identityGeneration,
    lastRun: { runId: state.run.runId, identityGeneration: state.run.identityGeneration, trigger: state.run.trigger, startedAt: state.run.startedAt, endedAt: action.now, outcome: 'cancelled', domainResults: state.run.domainResults },
    pendingRerunTrigger: undefined,
  }
  ```
- If `state.status === 'idle'`: still reset — adopt the new generation and
  clear `lastRun`/`pendingRerunTrigger`. Even though nothing was running, a
  previous identity's "last synced"/pending-rerun info must not be visible
  under the new identity (this is the same isolation principle as
  `identity-isolation-matrix.test.tsx`, applied to sync status rather than
  domain state).
  `{ status: 'idle', identityGeneration: action.identityGeneration, lastRun: undefined, pendingRerunTrigger: undefined }`.
- No generation-ordering guard is added here: `identityChanged` is documented
  as only ever dispatched with a strictly-increasing generation, matching
  `IdentityContext.setIdentity`'s own contract (it only increments, never
  decrements/repeats).

### Tiny selectors (optional but cheap; add if they read naturally, don't overbuild)

- `isSyncRunning(state): boolean`
- `getActiveRunId(state): string | undefined`

Do not add anything resembling backoff scheduling, elapsed-time formatting,
or Profile-facing "last synced X ago" formatting here — that belongs to the
Phase 3 roadmap item "Add Profile status for last sync..." (a later ticket),

## Design notes / risks to flag to the implementer

- **Why coalescing doesn't invent a runId itself:** the reducer never
  generates its own run id or reads a clock — `createSyncRunId`/`now` are
  always caller-supplied, consistent with "keep scheduling effects and clocks
  outside the reducer/state machine" from the task notes and with
  `createOutboxOperationId`'s existing convention. When a run finishes with a
  `pendingRerunTrigger` set, the reducer surfaces that fact but does not
  start the rerun itself; a future driver (T157.9) is expected to notice
  `pendingRerunTrigger !== undefined` on the idle state and dispatch a fresh
  `syncRequested`. Document this contract clearly in a comment above
  `pendingRerunTrigger` so T157.9 doesn't have to reverse-engineer it.
- **Single-flight is structural, not just enforced by an `if`:** because
  `SyncCoordinatorState` is a union with only one `run: ActiveSyncRun` slot
  (not an array/map), it is impossible at the type level to represent two
  concurrent runs. Call this out — it's a stronger guarantee than "we check
  before starting," worth a comment and a test that hammers overlapping
  triggers and asserts the run id never changes mid-run.
- **`domainSettled` guards on both `runId` and `identityGeneration`:** `runId`
  alone (via `createSyncRunId`'s timestamp+random construction) is
  sufficient in practice, but checking `identityGeneration` too mirrors the
  double-check pattern already established in `sync-envelope.ts`
  (`checkIdentity` alongside physical key namespacing) and makes the
  "identity change" test scenarios directly legible without relying on run
  id uniqueness as the only line of defense.
- **Do not let `identityChanged` try to literally abort in-flight promises.**
  That's impossible for this pure reducer to do anyway (no promises exist at
  this layer). The guard in `domainSettled` is what makes late results inert;
  a future driver may additionally use `AbortController`s per run purely as
  a network-efficiency optimization, but that's out of scope here and not
  required for correctness.
- **`FinishedSyncRun.domainResults` is per-run, not cumulative.** A retried
  run starts again from `{}`, exactly like history-derived Stats (per
  AGENTS.md) rather than a mutable running total — a domain that failed in
  run 1 and succeeds in run 2 should show as succeeded in run 2's own
  `domainResults`, not silently patched over stale run-1 data. Add a test
  that proves this explicitly (retry scenario below).

## `coordinator.test.ts` — required scenarios (mirror `sesh.test.ts` / `sync-envelope.test.ts` style: no timers, no async, plain `reducer(state, action)` calls with explicit `now`/`runId`/`identityGeneration` values)

1. **Initial state** — `createInitialCoordinatorState(1)` is idle, gen 1, no
   `lastRun`, no `pendingRerunTrigger`.
2. **Basic run lifecycle** — `syncRequested` from idle starts running with the
   given `runId`/`trigger`/`startedAt`; five `domainSettled` (all succeeded)
   transition back to idle with `lastRun.outcome === 'completed'` and all five
   domains present.
3. **Overlapping triggers (single-flight)** — while running (`run-1`), a
   second `syncRequested` (different trigger, same generation) does not
   change `state.run.runId`, sets `queuedRerunTrigger` to the second trigger;
   a third overlapping trigger while still running is also coalesced and does
   not overwrite the already-queued trigger (first-wins). Settle all five
   domains → idle with `pendingRerunTrigger` equal to the *first* coalesced
   trigger. Then dispatch a fresh `syncRequested` for that trigger (simulating
   the future driver reacting to `pendingRerunTrigger`) → transitions to
   running with a new `runId`.
4. **Stale trigger (generation mismatch on `syncRequested`)** — from idle at
   generation 2, a `syncRequested` carrying `identityGeneration: 1` is a
   no-op; state is unchanged (still idle, gen 2).
5. **Cancellation via identity change mid-run** — start a run at gen 1, settle
   2 of 5 domains, dispatch `identityChanged` to gen 2. Assert: idle, gen 2,
   `lastRun.outcome === 'cancelled'`, `lastRun.runId` is the cancelled run's
   id, `lastRun.domainResults` has exactly the 2 partial entries,
   `pendingRerunTrigger` is `undefined` even if a `queuedRerunTrigger` had
   been set on the run before cancellation (assert this explicitly — set one
   up first, then cancel, then check it's dropped).
6. **Identity change while idle** — from idle with a populated `lastRun` (from
   a prior completed run), dispatch `identityChanged`. Assert `lastRun` and
   `pendingRerunTrigger` are both cleared and generation is updated, without
   spuriously entering `running`.
7. **Network failure contained** — start a run; dispatch `domainSettled` with
   `outcome: { status: 'failed', errorMessage: ... }` for one domain. Assert
   state stays `running` (does not throw, does not abort other domains) and
   the failed record is stored. Then settle the remaining four as succeeded →
   run completes normally (`outcome: 'completed'`) with the mixed
   success/failure `domainResults`.
8. **Retry after failure** — starting from scenario 7's finished state
   (`lastRun` shows one failed domain), dispatch a fresh `syncRequested` with
   `trigger: 'retry'` and a new `runId`. Assert a brand-new run starts with
   `domainResults: {}` (not seeded from the previous failure), and settling
   the previously-failed domain as succeeded this time results in that run's
   own `domainResults` showing success — explicitly assert the *new* run's
   `domainResults` object doesn't reference or merge the old failed record.
9. **Partial-domain failure, order-independent** — start a run; settle the
   five domains in a shuffled order with a mix of success/failure (e.g.
   customTricks fails, then goals fails, then the other three succeed).
   Assert the run still completes once all five report, and each domain's
   final recorded outcome matches what was dispatched for it regardless of
   dispatch order (i.e. an earlier failure for one domain isn't clobbered or
   reset by a later failure/success dispatched for a *different* domain).
10. **Stale completion after normal finish** — run completes (all 5 settled,
    idle). Dispatch one more `domainSettled` for the same `runId`/generation
    (a straggling late resolution). Assert state is completely unchanged
    (`lastRun` still exactly the original completed summary, status stays
    idle, does not flip back to `running`).
11. **Stale completion after cancellation** — run starts at gen 1, gets
    cancelled via `identityChanged` to gen 2 (scenario 5's setup). A late
    `domainSettled` for the cancelled run (`runId` matches, but
    `identityGeneration: 1`) arrives. Assert state is completely unchanged
    (still idle at gen 2 with the `cancelled` `lastRun`) — this is the most
    direct test of the exit criterion's literal wording ("no late result can
    mutate current state after logout or account switching").
12. **Stale completion across a new run under a new generation** — run-1
    starts at gen 1; `identityChanged` to gen 2 cancels it; `syncRequested`
    starts run-2 at gen 2; a late `domainSettled` for run-1 (`runId` "run-1",
    `identityGeneration: 1`) arrives while run-2 is actively running. Assert
    it does not get merged into run-2's `domainResults` and run-2's state is
    byte-for-byte unaffected by the stale dispatch.
13. **`isSyncRunning` / `getActiveRunId` selectors** (if added) — trivial
    true/false and id/undefined checks across idle and running states.
