# T068 — Return to Tricks home when the Tricks tab is pressed from a nested view

## Key finding that changes the approach from the task Notes

The Notes suggest detecting "Tricks tab pressed while already focused" in `app-tabs.web.tsx` /
`app-tabs.tsx` and explicitly resetting `tricks.tsx`'s state from there. Having read the actual
`expo-router` (57.0.10) source, that's unnecessary and the wrong layer. Both tab primitives already
emit a standard React Navigation `tabPress` event **every time the tab button is pressed, including
when it's already the focused tab** — only the follow-up `JUMP_TO` navigation is skipped when
already focused, not the event emission:

- Web (`expo-router/ui` `TabTrigger`, `node_modules/expo-router/build/ui/TabTrigger.js`,
  `handleOnPress`): always calls
  `navigation?.emit({ type: 'tabPress', target: trigger.route.key, canPreventDefault: true })`
  before the `if (!trigger.isFocused) switchTab(...)` guard.
- Native (`NativeTabs`, `node_modules/expo-router/build/native-tabs/NativeBottomTabsNavigator.js`,
  `onTabChange`): for any native-originated tab selection it always calls
  `navigation.emit({ type: 'tabPress', target: selectedKey, data: { __internalTabsType: 'native', isPrevented: false } })`
  before dispatching `JUMP_TO`.

This is exactly the mechanism React Navigation ships for the "reselect a tab to scroll to top"
convention, and the official pattern for handling it is: inside the screen itself, call
`navigation.addListener('tabPress', () => { if (navigation.isFocused()) { /* reset */ } })`. Since
`src/app/tricks.tsx` is registered directly as a screen of the tab navigator (there's no
`src/app/_layout.tsx` under it, unlike `profile/`, `sesh/`, `stats/`), `useNavigation()` called
inside `TricksScreen` returns the navigation object scoped to that exact tab route, and
`navigation.isFocused()` is true precisely when Tricks was already the active tab at the moment of
the press — i.e. exactly the no-op-press case this task needs to catch.

**Net effect: `app-tabs.web.tsx` and `app-tabs.tsx` need no changes at all.** The fix is entirely
inside `src/app/tricks.tsx`, and it's identical for web and native because both primitives feed the
same underlying `tabPress` event — no per-platform branching needed. This was verified by installing
the pinned `expo-router@57.0.10` in this worktree, reading `TabTrigger.js` and
`NativeBottomTabsNavigator.js` directly, and confirming with a throwaway `tsc --noEmit` check (see
below) that `useNavigation()` + `addListener('tabPress', ...)` + `isFocused()` type-checks.

## One TypeScript wrinkle to carry into the implementation

`useNavigation()` from `expo-router` defaults its generic to a `NavigationProp` whose event map
does **not** know about `tabPress` (that event is defined on `BottomTabNavigationEventMap`, which
`expo-router` does not re-export as a public type). A direct
`navigation.addListener('tabPress', ...)` call fails `tsc --noEmit` with:

```
Argument of type '"tabPress"' is not assignable to parameter of type 'keyof EventMapCore<...>'.
```

The confirmed fix (verified to both `tsc --noEmit` and `eslint` clean in this environment) is a
narrow, well-scoped cast on the event name only:

```ts
navigation.addListener('tabPress' as never, () => {
  if (navigation.isFocused()) {
    resetNestedTricksView();
  }
});
```

Do not widen this to casting the whole `navigation` object or the callback — keep the `as never`
scoped to the string literal so a real typo in the event name would still be caught structurally
elsewhere (there's only one string here, so this is a non-issue, but keep the pattern narrow if it's
copied elsewhere later).

## Implementation steps

1. **`src/app/tricks.tsx`** — the only file that changes.
   - Add `import { useNavigation } from 'expo-router';` (there's no existing `expo-router` import in
     this file to merge with — `useRequireOnboarding` wraps the router access instead — so this is a
     new import line).
   - The nested-view-selector state currently lives as 7 independent `useState` calls (lines
     54–61 as read at plan time):
     `creationStep`, `editingTrick`, `deletingTrick`, `notesTrick`, `goalsTrick`, `showLacedTricks`,
     `showAllGoals`, `showAllNotes`. Leave them as separate `useState` calls (no need to consolidate
     into a reducer for this fix — that would be a larger, unrelated refactor) but add one function,
     e.g. `resetNestedView`, that calls all 7 setters back to their list-view defaults
     (`'list'`, `undefined`, `undefined`, `undefined`, `undefined`, `false`, `false`, `false`).
   - Call `useNavigation()` and add a `useEffect` that subscribes/unsubscribes a `tabPress` listener
     calling `resetNestedView()` when `navigation.isFocused()` is true. Place this **after** all the
     existing `useState`/`useMemo` calls and **before** the `if (!isOnboardingComplete) return null;`
     early return, so the Rules of Hooks are preserved (all hooks must run unconditionally on every
     render; the existing early return already sits below all other hooks, so this slots in the same
     spot).
   - No change needed to `CustomTrickForm`'s own internal `useState` (name/kenteiRank/steps/etc,
     lines ~274+) — it's fully unmounted when `resetNestedView` flips `creationStep` back to
     `'list'`, so its local state is discarded for free. Same for the delete-confirmation and other
     nested screens — they're conditionally rendered `if` branches in `TricksScreen`, not
     always-mounted, so resetting the parent's selector state is sufficient.

2. **No changes to `src/components/app-tabs.web.tsx` or `src/components/app-tabs.tsx`.** Confirm
   this explicitly while implementing rather than reflexively touching them per the task Notes — the
   Notes' suggested approach was a reasonable guess pending confirmation, and confirmation is what
   step 0 above did.

## Verification

- **Web:** `yarn expo start --web` (or the existing dev server), for each of the nested views —
  edit trick, delete-confirmation, trick notes, trick goals, laced-tricks grid, all-goals, all-notes,
  the "choose new trick kind" screen, and both custom-trick creation forms (standalone and
  sequence) — open it, press the Tricks tab in the tab bar, and confirm it returns to the trick list
  rather than doing nothing. Also confirm pressing Tricks while *already on the list* is inert (no
  visible flicker/relayout from the redundant `resetNestedView` calls — the setters are all being
  set to values equal to their current defaults, so React should bail out re-rendering those, but
  eyeball it once).
- **iOS simulator and Android emulator:** run via `expo start` (iOS/Android targets) and repeat the
  same nested-view/tab-repress check. This is the part of the exit criteria explicitly flagged as
  "confirm rather than assume" — the source-level reasoning above strongly suggests `NativeTabs`
  behaves the same as web (same `tabPress` emission on every native tab selection, per
  `NativeBottomTabsNavigator.js`), but that's a source-reading inference, not an on-device
  observation, and native tab reselect has historically had OS-level quirks (e.g. iOS's own
  UITabBarController popping a nav stack or scrolling to top independent of RN) that could interact
  with or mask this fix. Do not close this task without actually pressing the tab on both simulators.
- No new automated test is required to close this task. There is currently no test file for
  `src/app/tricks.tsx` and no existing convention in this repo for mocking `expo-router`'s
  `useNavigation`/tab-navigator context (the one file that mocks `expo-router` at all,
  `src/app/profile/__tests__/index.test.tsx`, only mocks `useRouter`, not `useNavigation`, and
  doesn't render inside a real `Tabs`/`NativeTabs` tree). Building that harness from scratch — mocking
  `useNavigation` to return a fake `addListener`/`isFocused`, then simulating a press — is possible
  but is disproportionate setup cost for one behavior that's directly and easily hand-verified across
  all three target platforms per the exit criteria. Treat manual verification as sufficient; if a
  cheap way to unit-test this emerges naturally while implementing, add it, but don't block on it.
- Run the standard verification sequence (or `node .claude/scripts/verify.mjs`):
  `yarn test --runInBand`, `yarn lint`, `yarn tsc --noEmit`, `yarn expo export --platform web`.

## Risk / things to double check while implementing

- `resetNestedView` will discard any in-progress, unsaved edits in `CustomTrickForm` (name, rank,
  sequence steps typed so far) if the user re-presses Tricks mid-edit. That's the intended behavior
  per the task description (nested views should return to the list on tab re-press) and matches how
  a real "go back to tab root" action behaves elsewhere in the app — not a gap to fix here, just
  worth confirming during manual testing that it feels acceptable rather than surprising/destructive
  in practice.
- Keep the `useNavigation()` call and its effect above the `if (!isOnboardingComplete) return null;`
  line — moving it below (e.g. tucked next to the JSX return blocks for tidiness) would violate the
  Rules of Hooks by making the hook conditional.
