## Key finding: tombstones make goal deletion an UPDATE, not a DELETE

This is the one genuinely new mechanic versus every prior domain in this
chain (profile/custom-tricks/practice-history all use hard DELETE or no
delete at all):

- `api.goals` has no DELETE grant at all. A local `goalDeleted` outbox
  operation must push as `.update({ deleted_at: <iso> })`, revision-guarded
  exactly like an edit.
- The trigger makes a tombstoned row's `deleted_at` terminal: **any** further
  UPDATE against an already-tombstoned row — whether it's another delete
  attempt, an edit, or an attempted "undelete" — is unconditionally rejected
  with `raise exception ... using errcode = '23514'`, *regardless of whether
  the WHERE clause's own revision filter matched*. Read
  `supabase/tests/t155_4_goals_and_notes.test.sql` lines ~108-148 for the
  proof this is already pgTAP-tested at the DB layer, including the "a
  stale mutation *matching the current identity/revision* cannot undelete a
  tombstoned goal" case — i.e. even a request whose revision filter matches
  exactly still gets rejected, because the trigger checks `old.deleted_at`
  before honoring anything the client's WHERE clause matched.
- **Do not change this trigger's error code or message.** It's already
  exercised by two merged, passing test suites
  (`supabase/tests/t155_4_goals_and_notes.test.sql` and
  `supabase/tests/data-api/t155_6_goals.test.mjs`) that hard-assert
  `'23514'` for this path. Changing it would be an out-of-scope blast-radius
  expansion into already-shipped T155.4/T155.6 work. Disambiguate at the
  **adapter layer** instead (see below) — this is intentionally scoped
  narrowly to the new `goal-sync-transport.ts` file, not a shared classifier
  change.

### The 23514 ambiguity and how the adapter resolves it

`23514` (`check_violation`) is raised by **two different things** on
`api.goals`: the CHECK constraints (`goals_count_shape`, `goals_time_shape`,
ambiguous-variant rejection — genuine malformed writes, which should be
unreachable through this adapter because of defensive payload
re-validation, same posture as the custom-tricks adapter's own comment on
this) **and** the tombstone-rejection trigger exception above (a legitimate,
reachable race). `mapPostgrestError` classifies both as `'validation'` today
and that's fine for every other domain — but for goals this adapter must
distinguish them before falling through to that generic classification.

Do this by checking the tombstone trigger's fixed message text (`'cannot
modify a tombstoned'`) on any `23514` returned from an `.update()` call, in
both the delete-push and edit-push branches:

- `23514` **with** that message → the row is (now) tombstoned. Fetch the
  current row (`.select('*').eq('user_id', userId).eq('id', goalId).maybeSingle()`)
  to get a real `revision`/row for reporting, then:
  - if the local operation was `operationType === 'delete'` → **succeeded**
    (the row is already gone server-side; deleting an already-deleted goal
    satisfies the operation's own intent — same "delete something that's
    already gone is a success, not a conflict" precedent the trickState and
    custom-trick delete branches already establish, just reached via a
    tombstone check instead of a 0-row DELETE). Return the fetched
    tombstoned row.
  - if the local operation was `operationType === 'upsert'` (an edit) →
    **conflict**, `serverRevision` from the fetched row. This is the literal
    "stale-device resurrection attempt" exit criterion: a device that
    doesn't know the goal was deleted elsewhere tried to mutate it, and the
    push must not silently succeed, not silently discard, and not crash the
    whole sync run — it parks just this one goal's outbox operation.
- `23514` **without** that message → fall through to
  `mapPostgrestError` → `'failed'`, unchanged from every other domain's
  posture on a genuine CHECK violation.
- `PGRST116` (0 rows matched the revision-guarded WHERE clause, no trigger
  ever fired) → the existing, already-proven pattern from every prior
  domain: fetch current row; missing entirely → delete-branch success
  (never existed server-side) / edit-branch `'failed'` (editing something
  that was never created is not a real state, treat as unknown/failed, do
  not fabricate); found but tombstoned → same split as above (delete
  succeeds, edit conflicts); found live at a different revision → `'conflict'`
  for both branches (the standard case).

Write a small shared helper inside `goal-sync-transport.ts`,
`classifyGoalUpdateFailure(error, refetchedRow, operationType)`, used by
both the delete and edit push branches, rather than duplicating this
six-way branch twice. Keep it colocated in this one file — it is
goal-specific, not shared-file material.

## The adapter: `goal-sync-transport.ts`

New file `src/features/goals/persistence/goal-sync-transport.ts`, built the
same way `custom-trick-sync-transport.ts` is —
`createGoalSyncTransportAdapter(client: SupabaseClient<Database, 'api'>, userId: string): SyncTransportRepository<GoalRow>`.
One table, no `recordId === userId` routing (every `recordId` is a goal id).

**Pull** — delegate directly to `createGoalCloudRepository(client).list(request)`,
same one-line-wrapper pattern as the other three adapters (`list`'s shape is
already `CloudReadResult`-compatible with `SyncTransportPullResult`).
Deliberately pulls tombstoned rows too (the repository's own `list` already
doesn't filter them, per its header comment) — the driver hook's
pull-composition step is what turns that into an active-only
`GoalCollection` (see below).

**Push** — routes on `request.operationType`:

- `operationType === 'delete'`: build the patch `{ deleted_at:
  new Date(<pushed-at timestamp>).toISOString() }` directly (see note above
  on not routing this through `prepareGoalDeletionPatch`). If
  `expectedRevision === null`, `.update(patch).eq('user_id', userId).eq('id', goalId).select('*').single()`
  unconditionally; 0 rows (`PGRST116`) → the goal was never created
  server-side (an offline create-then-delete before ever syncing) →
  succeeded, fabricate a placeholder row (same pattern as
  `fabricateDeletedTrickStateRow`/`fabricateDeletedCustomTrickRow`; add
  `fabricateDeletedGoalRow`). If `expectedRevision !== null`, add
  `.eq('revision', expectedRevision)`; on failure, run it through
  `classifyGoalUpdateFailure` as described above.
- `operationType === 'upsert'` (create-or-edit): defensively re-validate
  `request.payload` first (`validateGoalUpsertPayload`, mirroring
  `validateCustomTrickUpsertPayload`'s style: check `user_id`/`id` match,
  `kind` is `'count'|'time'`, and reuse `isValidGoalTargetCount`/
  `isValidGoalTargetMinutes`-style checks so a malformed payload never
  reaches Postgrest). If `expectedRevision === null`: `.insert(input).select('*').single()`;
  on `23505` (lost-ack retry of the *same first create*), fall back to a
  blind `.update({ target_count, target_ms }).eq('user_id',...).eq('id',...)`
  (no revision filter — matches the accepted, already-precedented
  first-push limitation from every other domain) and run *that* through
  `classifyGoalUpdateFailure` too (the extremely narrow "someone tombstoned
  it between my lost-ack create and my retry" race — treat as `'conflict'`,
  not a crash, per the general edit-vs-tombstone rule above). If
  `expectedRevision !== null`: `.update({ target_count,
  target_ms }).eq('user_id', userId).eq('id', goalId).eq('revision',
  expectedRevision).select('*').single()`; on failure, `classifyGoalUpdateFailure`.

**Real-stack tests**: new file
`supabase/tests/data-api/t157_7_goal_sync_transport.test.mjs`, built like
`t157_6_practice_history_sync_transport.test.mjs` (real `supabase-js`
client via `register(alias-loader)`, `createConfirmedUser`/`signIn`, plain
`node --test` via `yarn test:data-api`). Cover, at minimum:
1. Idempotent retry of a first-ever goal create (lost ack): second push
   succeeds via the `23505`-fallback path, no duplicate row, revision only
   bumped once.
2. Idempotent retry of a goal delete (push twice): both succeed.
3. Delete of a goal never created server-side (`expectedRevision: null`)
   succeeds as a no-op with a fabricated row.
4. Revision-guarded edit with a stale `expectedRevision` (seed a second
   write via the plain repository first) → `'conflict'` with the correct
   `serverRevision`; the row's actual target is untouched.
5. **The new case**: tombstone a goal directly via the plain repository,
   then push a `delete` operation against it at the tombstone's own current
   revision → `'succeeded'` (idempotent, matches intent).
6. Same tombstone setup, then push an `upsert` (edit) operation against it
   at the tombstone's own current revision → `'conflict'`, not `'failed'`
   and not a thrown exception — this is the pgTAP-proven "even a
   revision-matching mutation is rejected" case, now proven through the
   *adapter*, not just the raw SQL layer.
7. Basic `pull` smoke test against seeded active + tombstoned rows,
   confirming tombstoned rows come back (not filtered).

## Risks / non-obvious things to flag to the implementer

- The single biggest risk is under-scoping this by treating "editing" in
  the exit criteria as already-existing and only building the sync
  plumbing. It is not already-existing — confirmed above by reading
  `goal.ts`/`goal-provider.tsx` directly. Build the local edit capability
  first; everything downstream depends on it.
- The second biggest risk is treating the tombstone-rejection `23514` the
  same way the custom-tricks adapter treats its own step-invariant `23514`
  (a genuine, unreachable-in-practice validation failure that falls through
