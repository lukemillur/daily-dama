## Resolved ambiguity: what "expired-session" means for sign-in

Unlike `reset-password-screen.tsx`, a plain email/password sign-in has no
pre-existing session to expire, so there's no natural place `session_expired`
/ `session_not_found` would come from `signInWithPassword` itself. Rather than
inventing new provider surface or a route-guard redirect contract that
doesn't exist yet, treat this as: **if `signInWithPassword` ever resolves an
error that categorizes to `expiredOrInvalidLink` (which already includes
`session_expired`/`session_not_found`), show sign-in-specific copy for it**
("Your session has expired. Sign in again to continue."). This costs no new
model code — it's just one more entry in the screen's local copy map, exactly
like `reset-password-screen.tsx` and `auth-callback-screen.tsx` each already
supply their own per-screen copy for the same shared categories. This is a
judgment call, not a discovered fact from Supabase's API — flag it as such in
the commit/TASKS_DONE note so it can be corrected later if a live Supabase
instance later shows a different real-world code path here.

## Files to add, in order

### 1. `src/features/auth/model/sign-in-validation.ts` (new, pure, no IO)

Mirrors `password-policy.ts`'s shape/precedent. Export:

```ts
export interface SignInFieldErrors {
  readonly email?: string;
  readonly password?: string;
}
export type SignInValidation =
  | { readonly status: 'valid' }
  | { readonly status: 'invalid'; readonly errors: SignInFieldErrors };

export function validateSignInFields(email: string, password: string): SignInValidation
```

Rules:
- `email` trimmed non-empty, and matches a minimal shape check (e.g.
  `/^\S+@\S+\.\S+$/`) — just enough to catch empty/obviously-malformed input
  client-side; real validity is Supabase's problem and must never be inferred
  from a client-side "your email doesn't exist" message.
- `password` non-empty. **Do not** reuse `MIN_PASSWORD_LENGTH` here — a
  10-character floor only governs *setting* a new password (T153.6's
  `validateNewPassword`), not checking an existing one; an existing account's
  password could be shorter, and enforcing a length rule client-side on
  sign-in would also leak information about the account's password length
  vs. an unknown-email attempt with a short guess.

Add `src/features/auth/model/__tests__/sign-in-validation.test.ts` covering:
empty email, malformed email (no `@`/no dot), empty password, and a valid
pair.

Build/test this first — the screen depends on it and it has zero other
dependencies.

### 2. `src/features/auth/components/sign-in-screen.tsx` (new)

Follow `reset-password-screen.tsx`'s structural pattern exactly (styled-components
layout primitives, `Screen`/`Button`/`BodyText`/`DisplayTitle`/`Eyebrow`,
`AppColors`). Import `useAuthActions`, `useAuthState` from
`state/auth-provider`, `categorizeAuthError`/`AuthErrorCategory` from
`model/auth-errors`, `validateSignInFields` from the new file above, and
`logAuthWarning`/`trackAuthEvent` from `observability/auth-observability`
(mirror `auth-callback-screen.tsx`'s use of these two, which
`reset-password-screen.tsx` does not currently use — add them here since this
is the first *credential-submission* failure surface and needs the same
warn+track-on-error discipline the callback screen already has).

State shape: `email`, `password`, `hasSubmitted`, `isSubmitting`,
`submitCategory: AuthErrorCategory | undefined`. No separate "completed" flag
is needed (unlike reset-password) — on success the screen navigates away via
`router.replace('/app/home')` and unmounts, so there's no terminal render
state to guard against re-submission; guard re-entrancy purely with
`if (isSubmitting) return;` at the top of `handleSubmit`, same as disabling
the button while `isSubmitting`.

Render branches, top to bottom:

1. `authState.status === 'initializing'` → loading copy, no inputs (mirrors
   reset-password's first branch). This is the "explicit loading" state.
2. `authState.status === 'authenticated'` → `useEffect` that
   `router.replace('/app/home')` immediately and renders the same loading
   copy while it does (don't flash the credential form at an already-signed-in
   visitor). This is a UX addition beyond the literal task text but is cheap,
   consistent with `auth-callback-screen.tsx`'s success redirect, and avoids
   a confusing state; note it as an assumption if you'd rather skip it, but
   it doesn't conflict with anything in scope.
3. Otherwise (`guest` or `passwordRecovery` — don't special-case
   `passwordRecovery`, just render the normal form; if that combination ever
   occurs in practice, a fresh sign-in simply transitions state normally) →
   render the form:
   - Email field: `TextInput` (`autoCapitalize="none"`, `autoCorrect={false}`,
     `keyboardType="email-address"`, `textContentType="username"`,
     `accessibilityLabel="Email"`).
   - Password field: `TextInput` (`secureTextEntry`, `autoCapitalize="none"`,
     `autoCorrect={false}`, `textContentType="password"`,
     `accessibilityLabel="Password"`).
   - Field-level errors from `validateSignInFields`, shown only once
     `hasSubmitted` (same gating pattern as reset-password).
   - One submit-level error line from `submitCategory`, using a
     `Record<AuthErrorCategory, string>` copy map:
     - `invalidCredentials`: `'Incorrect email or password. Try again.'`
       (the one fixed string for both wrong-password and unknown-email — see
       enumeration note above)
     - `unverifiedEmail`: `'Verify your email before signing in. Check your inbox for the confirmation link.'`
     - `offline`: `"You're offline. Check your connection and try again."`
     - `rateLimited`: `'Too many attempts. Wait a moment and try again.'`
     - `expiredOrInvalidLink`: `'Your session has expired. Sign in again to continue.'`
     - `weakPassword`, `accountAlreadyExists`, `unknown`: the same generic
       `'Something went wrong. Please try again.'` (these three shouldn't
       realistically occur for sign-in but `Record<AuthErrorCategory, ...>`
       must stay exhaustive, same as the other two screens' maps)
   - Submit button: `accessibilityLabel="Sign in"`, label `'Signing in...'`
     while `isSubmitting`, disabled while `isSubmitting`.
   - A second, always-visible action: `accessibilityLabel="Continue as guest"`,
     `onPress={() => router.replace('/app/home')}` — no confirmation, no
     analytics event, just a plain navigation escape hatch.

`handleSubmit` logic:

```
if (isSubmitting) return;
setHasSubmitted(true);
setSubmitCategory(undefined);
const validation = validateSignInFields(email, password);
if (validation.status === 'invalid') return; // field errors already render from hasSubmitted+validation
setIsSubmitting(true);
const { error } = await signInWithPassword(email.trim(), password);
setIsSubmitting(false);
if (error) {
  const category = categorizeAuthError(error);
  setSubmitCategory(category);
  logAuthWarning('Sign-in failed.', error);
  trackAuthEvent('sign_in_error', category);
  return;
}
trackAuthEvent('sign_in_success');
router.replace('/app/home');
```

Never render `error.message` or any raw error field directly — only the
copy-map string keyed by `categorizeAuthError(error)`.

### 4. `src/features/auth/components/__tests__/sign-in-screen.test.tsx` (new)

Mirror `reset-password-screen.test.tsx`'s mocking pattern (`jest.mock` on
`expo-router`'s `useRouter`, and on `state/auth-provider`'s
`useAuthState`/`useAuthActions`) plus `auth-callback-screen.test.tsx`'s mocks
for `trackAuthEvent`/`logAuthWarning`. Cases to cover:

- Loading: `status: 'initializing'` → loading copy, zero inputs.
- Already authenticated: `status: 'authenticated'` → `mockReplace` called
  with `'/app/home'`, no form submitted.
- Validation: empty email and/or empty password on submit → field errors
  shown, `signInWithPassword` never called.
- **Enumeration-safety (the specific assertion the exit criteria calls
  out):** resolve `signInWithPassword` with `{ code: 'invalid_credentials' }`
  in one test and `{ code: 'user_not_found' }` in another; assert **the exact
  same rendered copy string** appears in both, and that no test-observable
  output differs between the two beyond that shared string.
- Unverified email: `{ code: 'email_not_confirmed' }` → the unverified-email
  copy specifically (distinct from the generic invalid-credentials copy).
- Offline: `TypeError('Failed to fetch')` (same shape used in
  `reset-password-screen.test.tsx`) → offline copy, form stays for retry.
- Throttled: `{ code: 'over_request_rate_limit' }` → rate-limited copy.
- Expired session: `{ code: 'session_expired' }` → the expired-session copy.
- Success: `signInWithPassword` resolves `{ error: null }` → called exactly
  once with the entered (trimmed) email/password, then `mockReplace` called
  exactly once with `'/app/home'`.
- Repeat-submit guard: fire `onPress` twice in quick succession (before the
  first `await` resolves, same technique as timers/async races elsewhere in
  the suite, or simply call `handleSubmit` twice synchronously via
  `act(async () => { button.props.onPress(); await button.props.onPress(); })`)
  → `signInWithPassword` called exactly once.
- Guest escape hatch: pressing "Continue as guest" calls `mockReplace` with
  `'/app/home'` and never calls `signInWithPassword`.
- No raw password leak: after a submission, no rendered text node contains
  the raw password string (mirror reset-password's equivalent assertion).
- Redaction discipline: assert `logAuthWarning`/`trackAuthEvent` are the only
  observability calls exercised (i.e. nothing routes around them) — this can
  just be "logAuthWarning was called on error, trackAuthEvent was called with
  the right category" since `redactValue`'s actual redaction is already unit
  tested elsewhere and out of scope to re-prove here.

## Risks / things to double-check while implementing

- Don't let the "already authenticated → redirect" branch (item 2 above)
  fight with the guest escape hatch — they're mutually exclusive render
  branches, but double-check the effect doesn't fire on every render (use a
  ref or rely on `router.replace` + unmount, same as
  `auth-callback-screen.tsx`'s `isMountedRef` discipline, if a repeated-call
  guard turns out to be needed).
- Keep `router.replace` (never `push`) for both the success path and the
  guest escape hatch, consistent with the no-back-button-into-a-stale-form
  pattern already used by the other two Auth screens.
- Double-check `email.trim()` before calling `signInWithPassword` doesn't
  fight with the field-level validation copy (validate the untrimmed vs.
  trimmed value consistently, or you can get a validation pass followed by a
  silently-different value being submitted).
