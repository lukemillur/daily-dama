# T053 — Add breathing room before auto-advancing on a lace

## Confirmed current state (read fresh from `development`, post T045-T052)

  branch builds `handleLaced`, which dispatches `trickLaced` then, when
  `advanceOnFirstLace && state.landings.length === 0`, immediately dispatches `seshEnded` in

  confirms the notes' framing: there is no reducer status to hook into, and adding one would
  need reducer changes disproportionate to the ask.
- `MultiTrickSeshEntry` (`src/features/sesh/components/multi-trick-sesh-entry.tsx`) is the only
  ad hoc entry point; it renders `MultiTrickSesh` with `advanceOnFirstLace={advanceOnFirstLace}`

- `AssessmentEntry` (`src/features/sesh/components/assessment-entry.tsx`) renders
  `MultiTrickSesh` with `advanceOnFirstLace`, `skipCountdownBetweenTricks`, and `hideTimer` all
  set — the deliberate zero-friction path from T029.2/T029.4. It does not currently reference
  any new prop, and per the task notes should stay that way unless the user asks otherwise.
- `Countdown` in `src/features/sesh/components/sesh.tsx` (lines ~409-463) is the existing
  precedent for a component-local timed transition: `useState` counter + a single `setTimeout`
  per tick inside a `useEffect`, cleaned up via `clearTimeout` in the effect's return. This is
  the pattern to mirror, not a new interval/animation system.
- `multi-trick-sesh.tsx` already defines reusable panel primitives at the bottom of the file
  (`CenteredPanel`, `Eyebrow`, `DisplayTitle`, `BodyCopy`) used today for the one-tick
  "Sequence complete" fallback. These are the right building blocks for the new acknowledgment
  panel's markup — no new styled-component vocabulary needed.

  helper that takes a fixed prop list and uses `jest.useFakeTimers()` /
  `act(() => jest.advanceTimersByTime(...))`. The existing `advanceOnFirstLace` test presses
  `'Laced'` once per trick with no intervening timer advance — confirms the new behavior must
  default to off, or that test breaks.

## Design

Add a new opt-in boolean prop, `pauseAfterLace`, to `MultiTrickSesh`. Default `undefined`
(falsy) — `AssessmentEntry` is untouched unless explicitly opted in later. Only
`MultiTrickSeshEntry` passes it, tied to the same `advanceOnFirstLace` flag (not a separate
setting — the task doesn't ask for a user-facing configuration, just a fixed acknowledgment
window whenever advance-on-lace is enabled).

Do **not** add a new `SeshState` status. Instead, add one piece of component-local transient
state in `MultiTrickSesh`:

```ts
const [laceAcknowledgment, setLaceAcknowledgment] = useState<{ readonly trickName: string } | undefined>(undefined);
```

Behavior:

1. In `handleLaced` (only reachable when `state.status === 'active'`): keep the existing
   `dispatch({ type: 'trickLaced', now })` unconditional call (the landing is still recorded
   immediately — only *advancing* is delayed). Where the code today does
   `if (advanceOnFirstLace && ...) dispatch({ type: 'seshEnded', now })`, branch:
   - if `pauseAfterLace` is also set, call `setLaceAcknowledgment({ trickName: state.trick.name })`
     instead of dispatching `seshEnded`.
   - otherwise (today's behavior), dispatch `seshEnded` immediately as now.
2. Add a `useEffect` keyed on `laceAcknowledgment` that, when it's set, starts a `setTimeout`
   for a fixed duration constant (e.g. `LACE_ACKNOWLEDGMENT_DURATION_MS = 1500`, module-level
   const near the top of `multi-trick-sesh.tsx`) that clears the acknowledgment and dispatches
   `seshEnded` with a fresh `Date.now()`, mirroring `Countdown`'s single-timeout-with-cleanup
   shape exactly. Return `clearTimeout` from the effect for the unmount/re-trigger case.
3. In the `'active'` render branch, when `laceAcknowledgment` is set, render the new
   acknowledgment panel *instead of* `<ActiveSesh ... />`. Reuse `CenteredPanel`/`Eyebrow`/
   `DisplayTitle`/`BodyCopy` already defined in this file. Suggested copy: `Eyebrow` "Trick
   landed", `DisplayTitle` the trick name (`laceAcknowledgment.trickName` — use the captured
   snapshot, not `state.trick.name`, though they're the same value at this point; capturing at
   set-time avoids any risk from state shape changing before the timeout fires), `BodyCopy`
   something like "Nice! Next trick coming up." Give the panel an
   `accessibilityLabel="Trick landed"` (or similarly stable, testable label) for the test to
   assert against.
4. No change needed to the `'completed'`-status effect (`seedNextTrick`, `recordCompletedSesh`,
   etc.) — it already reacts to `seshEnded` producing `status: 'completed'`, whenever that
   dispatch happens to land. The delay is entirely upstream of that effect.

Why local state and not a reducer status: matches the notes' explicit reasoning and the
project's stated convention (timer effects and `Date.now()` stay outside `seshReducer`; the
reducer is authority only for `choosing | countdown | active | completed`). This is exactly the
same category of decision `Countdown`'s local `count` state already made for essentially the
same kind of "timed transitional UI" problem.

### Edge cases to check while implementing

- **Last trick in the run:** when the last trick's first lace triggers the acknowledgment, the
  panel should still show for the full window before `seshEnded` fires, then the existing
  `'completed'` effect runs, `isTrickSequenceFinished` is true, `nextTrick` is `undefined`, no
  `seedNextTrick` call, and `isRunFinished` renders `MultiTrickWrapUp` as today. Confirm this
  path renders the acknowledgment before the wrap-up screen, not skipped.
- **Unmount/navigation during the acknowledgment window:** the `useEffect` cleanup must
  `clearTimeout` so an unmounted component never dispatches — same pattern `Countdown` already
  relies on. Don't drop this cleanup.
- **`skipTarget`/"Skip this rank":** while the acknowledgment panel is showing, `ActiveSesh` and
  its `onSkipRank` are not rendered — the panel is a brief, un-interruptible beat, not a screen
  with escape hatches. Confirm this is acceptable (it should be, since `pauseAfterLace` is only
  ever passed by `MultiTrickSeshEntry`, which has no `skipTarget`), but note it if it looks off
  once built.
- **Timed per-trick plans:** `advanceOnFirstLace` already forces early completion on first lace
  today regardless of `plan.kind === 'timed'`, so no new interaction with the timer countdown is
  introduced — the acknowledgment window is strictly additive after that existing forced-end
  point, not a new timing path.
- **Double-lace race:** `state.landings.length === 0` is still evaluated at the same point as
  today (inside `handleLaced`, guarded by `state.status === 'active'`), so the acknowledgment is
  only ever set from the first lace, same as the existing guard for the immediate-dispatch path.

## Order of implementation

1. `multi-trick-sesh.tsx` first (the actual mechanism) — everything else depends on the prop
   existing and behaving correctly.
2. `multi-trick-sesh-entry.tsx` second — trivial prop wiring once (1) exists.
3. Tests last, but write/run them against (1) and (2) together before considering this done;
   this is exactly the kind of timer-sequencing change that's easy to get subtly wrong (off-by-one
   dispatch ordering, stale closures over `state.trick.name`) and the existing
   `advanceThroughCountdown`-style fake-timer test harness in this file is the right tool to
   catch it.
