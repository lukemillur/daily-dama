# T159 — Merge guest data into new or existing accounts

## Iteration boundary

Good enough for this umbrella is the completed guest-to-account conversion slice
already decomposed into T159.1–T159.5: a guest sees an explicit inventory and
confirmation, imports into either an empty or populated account through stable,
resumable operations, makes explicit profile/conflict choices, resumes after
reload/interruption/lost acknowledgements, and never loses a guest source record
before the corresponding destination acknowledgement is durable. The umbrella
closeout should validate and document that behavior; it should not add new
backend, Realtime, native, export, or general synchronization semantics.

## Validated prerequisites and current implementation

- T156 is archived Done. Identity-scoped storage, generation guards, hydration
  gating, and the guest legacy-key fallback are established by T156.1–T156.3.
- T157 is archived Done. The five independent domain envelopes, ordered
  transports, idempotent operation IDs, conflict-aware revisions, and the sync
  coordinator are available without changing the Sesh state machine.
- T159.1–T159.5 are archived Done on this branch. The relevant implementation is
  under `src/features/guest-import/`, with the profile entry surface in
  `src/app/app/profile/index.tsx`.
- The guest import intentionally composes the existing five domain persistence
  and transport boundaries. Do not combine them into one persistent store or
  infer success from an unacknowledged request response.
- The current provisional guest-import persistence schema may be extended in
  place if verification finds a defect; do not introduce migration machinery or
  a v2 schema during this prototype closeout.

## Ordered closeout plan

1. **Reconcile the umbrella against the child evidence.** Read the completed
   T159.1–T159.5 entries in `TASKS_DONE.md`, the T156/T157 dependency entries,
   and the implementation history. Confirm that the child scope collectively
   covers both `empty` and `existing` targets, all five domains, explicit
   profile/conflict decisions, resumability, and final cleanup. Treat any
   mismatch as a concrete defect to fix or report before closing T159.

2. **Audit the guest-import contracts and boundaries.** Review
   `model/guest-import.ts`, `guest-import-persistence.ts`,
   `guest-import-empty-account.ts`, `guest-import-existing-account.ts`,
   `guest-import-decisions.ts`, and `use-guest-import.ts`. Preserve the pure
   reducer/state-machine boundary; keep clocks, storage, network calls, and
   cleanup in drivers/orchestrators. Confirm every operation has a stable
   import-scoped ID and retains enough validated payload/progress to resume
   without rereading mutable guest state or regenerating IDs.

3. **Verify empty-account conversion as a complete path.** Use the existing
   `guest-import-empty-account.test.ts` and
   `guest-import-second-browser.integration.test.tsx` coverage, adding only
   narrowly targeted tests if a stated umbrella guarantee is not actually
   asserted. The evidence must cover all five domains, deterministic domain and
   record ordering, interruption at each boundary, server-write/lost-response
   retries, idempotent operation IDs, second-browser rehydration, and retention
   of every unacknowledged source record.

4. **Verify existing-account merge and explicit decisions.** Use the table-driven
   `guest-import-existing-account.test.ts`, `guest-import-decisions.test.ts`,
   model/persistence tests, and the Profile-adjacent component tests. Confirm
   additive trick-state merging, immutable-record deduplication, same-ID
   conflicts, tombstone handling, explicit guest/cloud profile choice, one
   conflict resolving without settling siblings, and completion blocked until
   every required decision is resolved. Do not route these import conflicts
   through the ordinary T160.2 sync-conflict lifecycle.

5. **Verify acknowledgement-first cleanup and recovery.** Inspect and exercise
   the finalization paths in `guest-import-empty-account.ts`,
   `guest-import-decisions.ts`, and the progress validator. For every domain,
   prove the ordering is: persist attempt metadata → push with the same
   operation ID → persist destination acknowledgement → perform selective guest
   cleanup → persist cleanup completion. Cleanup failure must preserve the source
   record and a replayable acknowledgement, while rejected/unresolved records,
   unrelated guest data, and other identity namespaces remain available. A late
   result from an old import ID or identity generation must be inert.

6. **Run the required verification evidence.** Iterate with the exact guest
   import model, persistence, runner, hook, and component suites plus scoped
   lint. Before closing the umbrella, run the repository’s complete verifier:

   ```sh
   node .claude/scripts/verify.mjs --json
   ```

   This must pass tests, lint, strict TypeScript, and web export. Web is the
   active platform; native validation remains deferred by project policy. If a
   failure is unrelated, record it explicitly rather than weakening the exit
   criteria.

7. **Close only the umbrella bookkeeping.** After all evidence passes, move T159
   from `TASKS.md` to `TASKS_DONE.md` in the same focused commit, preserving its
   original description and recording the aggregate verification and any honest
   limitations. Do not alter completed child-history entries, T160, T161, or the
   ordinary synchronization contracts. No product-code change is expected from
   this plan unless the audit identifies a specific uncovered guarantee.

## Material assumptions and deferred work

- “New account” means the cloud inventory is empty across all five domains;
  “existing account” means the merge planner, not last-write-wins, owns overlap
  behavior.
- Profile scalar choice and profile trick-state union remain separate operations.
- Guest cleanup is selective and acknowledgement-driven; it is not an atomic
  transaction across local storage and Supabase.
- Realtime synchronization, mobile hardening, forensic erasure, data export,
  and ordinary sync conflict UX beyond the already completed T160.2 work remain
  outside T159.
