## Tooling decision (flag this to the user if they would rather discuss it first)

Prior T153.x tickets used a disposable, not-committed Playwright install for one-off manual
walkthroughs. This ticket is different in kind: the exit criteria require a repeatable
"acceptance matrix" runnable by "one documented command," not a one-time manual session recorded
in a commit message. That requires an actual committed test suite. Recommendation: add
@playwright/test as a real devDependency (Chromium-only browser, installed via
"npx playwright install chromium" -- document this as a one-time host setup step alongside the
existing Docker/Supabase-CLI prerequisites in supabase/README.md, not vendored into the repo).
This is a devDependency only -- it never touches the shipped bundle -- so it does not cross the
"prototype web-only scope" boundary AGENTS.md cares about. Proceed with this unless the user
says otherwise; it is the only way to make "one documented command" literally true.

Jest (yarn test) stays exactly as-is and does not run these specs -- see wiring below.

## The email-budget constraint (design this first -- it drives file/ordering structure)

email_sent = 2 per hour is global to the whole local GoTrue instance, not scoped per
address or per IP (confirmed by the config.toml comment wording, and by T153.8's own closing
note: "isolating scenarios with db reset between runs given the local email_sent = 2/hour
cap"). A matrix that needs signup-equivalence, recovery-equivalence, verification, reset, and
resend-limit coverage cannot naively fire off five real emails against a 2/hour cap.

Two mechanisms make this tractable without weakening what is actually being verified:

1. supabase.auth.admin.generateLink() (service-role only) synthesizes a valid one-time
   signup/recovery action link without sending mail and without counting against
   email_sent -- confirmed via GoTrue's admin API semantics (generateLink returns the
   action_link/token dict directly; only signUp/resend/resetPasswordForEmail go through
   the SMTP rate limiter). Use this to synthesize the tokens needed for the callback edge cases
   (reused, malformed, verifier-mismatched) and for seeding confirmed accounts for sign-in tests
   -- zero email budget spent.
2. supabase.auth.admin.createUser({ email_confirm: true, ... }) seeds an already-verified
   account instantly, for every scenario that needs "a known, verified user" but is not itself
   testing the confirmation-email path (sign-in equivalence, wrong-password, expired/callback
   edge cases). Zero email budget spent.

That leaves exactly two scenarios that must fire a real email through the real
signUp/resetPasswordForEmail path (because the thing being verified is literally "the email
arrives and its link works"): one signup-confirmation send, one recovery send. Sequence the
suite so those two real sends happen back-to-back near the end of the run, immediately followed
by a third call (resendSignupConfirmation for the same still-pending signup address) to prove
the cap trips -- this reuses the same two real sends as both "verification/reset works" evidence
and "the 3rd request is rejected" evidence, rather than needing a dedicated reset+3-send block.

Net result: one db reset at the very start of the run is enough -- matches "one documented
command resets local Supabase" literally, not just in spirit. Do not add a second mid-run reset;
if a run needs to be repeated, rerunning the whole documented command (which resets first) is
the retry story, not a partial rerun.

## Acceptance-matrix structure (traceability: one file/describe per exit-criteria clause)

New top-level directory e2e/auth/ (sibling of src/, not under it -- this is deliberately not
application code). Suggested files, run via a single Playwright project in file order
(Playwright runs files in the order listed by directory scan by default when
fullyParallel is false; pin workers to 1 and fullyParallel to false in playwright.config.ts so
the budget sequencing above is guaranteed, not accidental):

- e2e/auth/support/local-supabase.ts -- thin Node helpers: read
  SUPABASE_SERVICE_ROLE_KEY/EXPO_PUBLIC_SUPABASE_URL from the local CLI's own status output at
  run time (never hardcode, never log), a service-role admin client
  (createClient(url, serviceRoleKey), Node-side only, never imported by app code or shipped to a
  browser context), seedConfirmedUser(), generateActionLink(type, email).
- e2e/auth/support/mailpit.ts -- fetch helper against Mailpit's JSON API
  (http://127.0.0.1:54324/api/v1/...) to pull the latest message to an address and regex out
  the confirmation/recovery link, instead of driving Mailpit's web UI in a second browser
  context (faster, and avoids the missing-verifier false-positive T153.8's notes already flagged
  when two browser contexts touch the same one-time link).
- e2e/auth/support/redaction-listener.ts -- attaches a console listener and a route
  interceptor on the Vercel Analytics collection request (confirm the exact path against
  @vercel/analytics's source once installed; it posts JSON to a fixed collection endpoint) to a
  page, accumulates every observed string, and exposes an assertNeverContains helper checking
  for raw email/password/token substrings. Reused by every spec below rather than
  re-implemented per file.

- e2e/auth/00-guest-route-access.spec.ts -- exit-criteria clause: "guest access to every
  existing /app top-level route while Auth is initializing, offline, or unavailable."
  Three Playwright projects (configured in playwright.config.ts, not just test cases):
  authConfigured, authUnconfigured (launches the web server with EXPO_PUBLIC_SUPABASE_URL and
  EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY unset -- proves the unconfigured guest reason),
  authOffline (configured normally, but the test aborts requests matching auth/v1 before
  navigation to simulate an initializing state that never resolves, plus a network failure).
  Each project visits /app/home, /app/sesh, /app/tricks, /app/stats, /app/profile and asserts
  each renders its known landmark content (no blank screen, no crash, no redirect to an auth
  route).
- e2e/auth/01-sign-in-equivalence.spec.ts -- unknown-email vs wrong-password: seed one
  confirmed user via createUser, then assert /auth/sign-in renders byte-identical error copy
  ("Incorrect email or password. Try again.") for (a) that email plus a wrong password and
  (b) a never-registered email plus any password. Zero email spend.
- e2e/auth/02-callback-edge-cases.spec.ts -- missing/reused/malformed/verifier-mismatched, all
  built from generateActionLink, zero email spend:
  - missing: visit /auth/callback with no code param.
  - malformed: visit /auth/callback with an obviously fake code value.
  - reused: exchange a generateActionLink('signup', ...) token once successfully (a browser
    context sharing the same storage that requested it), then replay the identical URL.
  - verifier-mismatched: open the generated link's URL in a second, unrelated browser
    context (fresh storage) so the PKCE code-verifier Supabase expects is not present -- this is
    exactly the scenario T153.8's closing note flagged as not cleanly isolated when two
    contexts touch the same link; do it deliberately and once, in its own context pair, so it
    does not collide with the reused case's context.

- e2e/auth/03-open-redirect-rejection.spec.ts -- for /auth/sign-up and /auth/forgot-password,
  visit with an attacker-shaped query string (a redirect or next param pointing off-origin)
  appended, submit the form, and capture the outgoing signup or recover request to assert its
  redirect_to query param is exactly http://localhost:8081/auth/callback regardless of the
  page's own query string. This is the correct black-box framing given there is no app-side
  allow-list to probe (see the dependency notes above).
- e2e/auth/04-real-email-flows.spec.ts -- the two real sends, run last, in this exact order:
  1. Fresh random address, submit /auth/sign-up, check-email copy, fetch the Mailpit message,
     open the link, land on /app/home (signup equivalence's "new" side plus verification, one
     send).
  2. Same fresh address, submit /auth/sign-up again (still-unconfirmed, so this does attempt a
     second confirmation send under the hood) -- assert byte-identical check-email response to
     step 1 (signup equivalence's "existing" side). This is deliberately the second of the two
     budget-relevant sends.
  3. A separately-seeded confirmed user (via createUser, not the one above) submits
     /auth/forgot-password (known-address path), fetch the Mailpit message, follow it through
     /auth/callback to /auth/reset-password, set a new password, sign in with it (recovery
     equivalence's "known" side plus reset). A never-registered address through the same form
     asserts the identical public response with zero send (recovery equivalence's "unknown"
     side).
  4. Immediately call resendSignupConfirmation again for step 1's address (a third send request
     in the same hour window) and assert the UI surfaces the fixed rate-limited copy ("Too many
     attempts. Wait a moment and try again.") -- this is the resend-limit clause, riding on the
     budget already spent above rather than a fresh spend.

- e2e/auth/05-expired-session.spec.ts -- pragmatic simulation, documented as such rather than
  waiting out the real 3600-second JWT TTL: visit /auth/reset-password directly in a fresh guest
  context with no prior recovery flow, and assert the existing "not in passwordRecovery status"
  branch's "This link is no longer valid" copy renders. This exercises the same
  expiredOrInvalidLink-shaped guard the real session_expired/session_not_found codes hit; note
  in the spec's own comment that a literal one-hour-wait test was rejected as impractical,
  mirroring how the exit criteria expect a deterministic suite, not a slow one.
- e2e/auth/06-redaction.spec.ts -- reuses redaction-listener.ts across the highest-risk
  moments already exercised above (wrong-password sign-in, offline signup attempt, callback
  error, forgot-password submission) plus one dedicated case: enter a real email and password
  into the sign-in form, trigger an invalidCredentials error, and assert neither the entered
  email nor password ever appears in captured console text or the intercepted Analytics
  payload.

Each spec file's top comment should name the exact exit-criteria clause it covers, so the whole
directory is traceable back to the task's exit criteria sentence by sentence.

   (a scratch Node script hitting generateLink/Mailpit against a manually-started local stack)
   before writing any Playwright spec -- these are the riskiest new pieces (unfamiliar admin

2. Add playwright.config.ts plus the test:e2e:auth wrapper script and confirm a trivial smoke
   spec runs end-to-end through the one documented command, including the authUnconfigured
   project. Get the plumbing green before writing real scenarios.
3. Write 00-guest-route-access.spec.ts -- no live Supabase interaction needed beyond what is
   already running, cheapest to get right, and it is the broadest single de-risking check that
   nothing in this area accidentally gates guest access.
4. Write 01-sign-in-equivalence.spec.ts and 02-callback-edge-cases.spec.ts (admin-API-only,
   zero email spend) next, in either order.
5. Write 03-open-redirect-rejection.spec.ts and 06-redaction.spec.ts's non-email cases.
6. Write 05-expired-session.spec.ts.
7. Write 04-real-email-flows.spec.ts last, exactly once end-to-end against a fresh db reset,
   since it is the only file that spends the real email budget and is expensive to debug

## Risks / non-obvious things to know before starting

- The email budget is the single biggest way this suite goes wrong. Any change to the matrix's
  file order, or any retry logic that resubmits a signup/recovery form, can blow the 2/hour cap
  and turn 04-real-email-flows.spec.ts flaky. Keep retries at 0 and workers at 1
  non-negotiable, and do not add real email sends to any other spec file.
- generateActionLink's exact runtime shape may be under-declared in the installed
  @supabase/supabase-js's TS types, the same way exchangeCodeForSession's redirectType was
  (auth-provider.tsx already has one documented workaround for this pattern) -- expect to need
  a similar cast-with-comment rather than assuming the public type is complete.
- Two-browser-context callback scenarios are genuinely fragile -- T153.8's own closing note
  found that opening the same one-time link in a second context can consume it out from under
  the first context's still-in-flight exchange, producing a generic unknown category instead
  of the specific one being tested. Give the reused and verifier-mismatched cases their own
  isolated generateActionLink calls (never share one link's token across two test cases) so
  one test's consumption cannot poison another's expected category.
- Confirm the exact Vercel Analytics collection request path once @playwright/test and the
  package are actually installed in a real environment (this planning pass had no node_modules
  available to inspect) before finalizing redaction-listener.ts -- treat the path named above
  as a starting guess, not a confirmed contract.
- Do not let this suite become a second implementation ticket. If any scenario above reveals a
  real gap (e.g. a route that does gate on authState.status, a redaction miss, a callback
  category that does not collapse the way auth-errors.ts claims), stop, do not patch it inline,
  and write it up as a defect for its owning ticket or a new focused follow-up -- per this
  task's explicit scope boundary.
