### 2. Draft the DNS record shapes and the delivery-record document skeleton

Cannot get exact DKIM CNAME target values without a live Resend domain
add (Resend generates a unique per-domain DKIM key), but the record shape
is fixed and worth documenting now so a credentialed follow-up session moves
fast instead of re-deriving Resend's conventions:

- SPF: a TXT record at auth.dailydama.com (or the domain Resend's UI
  specifies - Resend's docs currently model sending subdomains, confirm
  live) containing v=spf1 include:amazonses.com ~all (Resend sends via
  AWS SES infrastructure; confirm this exact include value against Resend's
  live domain-setup screen rather than hardcoding it from memory here).
- DKIM: typically one or more CNAME records Resend issues per domain
  (values are opaque/random per domain - cannot be predicted).
- DMARC: a TXT record at _dmarc.auth.dailydama.com with a v=DMARC1; p=none;
  policy value (matching the task's explicit p=none requirement; note T162
  may tighten this later using observed delivery evidence - do not
  preemptively set a stricter p= value here).

Add these as a new supabase/RESEND_DNS_AUTH.md (colocated with
supabase/README.md and following T153.2's planned
supabase/HOSTED_DEV_CONFIG.md naming/colocation convention) containing:
- The record shapes above, clearly marked as drafted, not yet verified
  live until Resend's dashboard confirms exact values.
- A short "what to do once credentials exist" runbook: add domain in
  Resend, copy exact SPF/DKIM values it shows, publish all three records
  with the DNS provider, wait for Resend to mark the domain verified,
  turn off "Open and click tracking" for that domain in Resend's settings
  (the exit criteria's tracking-disable requirement), configure Supabase
  custom SMTP with Resend's SMTP host/port/username and the Resend API key
  as the password, then re-send a real confirmation and recovery email to a
  real inbox (not Mailpit, since Mailpit never touches Resend/DNS) and
  confirm both arrive from auth.dailydama.com, SPF/DKIM/DMARC show as
  pass in the message headers, and the callback URL in each is untouched
  (no Resend link-rewrite domain in the href).
- A placeholder "Delivery record" section (dated, secret-free, matching the
  exit criteria's phrasing) with blank fields for: date, hosted project ref,
  SPF result, DKIM result, DMARC policy published, tracking-disabled
  confirmation, and the two observed message URLs/callback paths - to be
  filled in only once the live checks in the runbook actually pass, never
  pre-filled with assumed "pass" values.

This file is scaffolding, not a substitute for the live record the exit
criteria require. Say so explicitly in the file itself.
