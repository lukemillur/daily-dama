# T313.4 plan: existing accounts sign in from the Start screen without redoing onboarding

## Verified current state (nothing blocks the ticket)

- `src/app/_layout.tsx` mounts `AuthProvider` above `<Slot />`, so the root route `/` can call `useAuthState()`. `IdentityProvider`, the five domain providers and `SyncCoordinatorProvider` mount only in `src/app/app/_layout.tsx`. The root route therefore cannot use `useIdentityHandle()` (outside a provider it silently returns guest). Derive "signed in" from `useAuthState()` there.
- `useNativeOnboardingStatus` reads only the guest-scoped profile key. `resolveNativeStartDecision(status)` is pure and takes only that status.
- `src/features/auth/components/sign-in-screen.tsx` redirects to `/app/home` after sign-in (lines ~60, ~88). The Start screen is not revisited after sign-in.
- Home (`src/app/app/home.tsx`) computes `blockingOnboardingRender = importPending || isResyncingAfterImport`. A signed-in identity with no import and a not-yet-onboarded local profile renders `<KenteiOnboarding />` before the first pull lands. This is gap 2.
- The first pull is the coordinator's `login` run, fired once per identity generation after all five domains hydrate (`use-sync-coordinator.ts`). The profile domain settles into `state.run.domainResults.profile` while the run is still `running`. When the run finishes it is in `state.lastRun.domainResults.profile`. A failed profile pull is `{ status: 'failed', errorMessage }`. `identityChanged` cancels the run and stamps `lastRun.identityGeneration` with the OLD generation, so generation matching rejects stale results.
- `useSyncCoordinatorStatus()` (`src/shared/sync/sync-coordinator-provider.tsx`) exposes `state` and `retry` (= `requestManualSync`). It throws outside the provider.
- ARCHITECTURE.md lines ~24-36 describe the Start screen and say "Native sync ... remain disabled". T313.1/T313.3 landed, so update the Start-screen paragraph for this change. Do not rewrite the sync-disabled sentence beyond what this ticket proves; if it is already stale, correct only the part you can verify.

## Design

Two separate pure decisions, each in a model file with no React, storage or navigation:

1. Root route: `resolveNativeStartDecision({ auth, guestStatus })`.
2. Home: `resolveFirstProfilePull({ identityKind, generation, hasCompletedOnboardingLocally, coordinator })` returning `'not-applicable' | 'pending' | 'settled' | 'failed'`.

Decision for the root route: any signed-in identity (`authenticated`, `passwordRecovery`) and `refreshFailed` go to `redirect-home`. Home is where the `IdentityProvider` recovery screen and the pull gate already live. This means no per-user storage read is needed on `/` and the Start screen never renders for an account (exit criterion b). A brand-new signed-in account still reaches onboarding through Home after the pull (criterion e). `initializing` returns `loading`. A guest keeps today's behavior: the guest-profile read decides `loading` / `redirect-home` / `show-start`.

## Steps (in order)

1. **Pure model, `src/features/native-start/model/resolve-native-start-route.ts`.**
   - Change the signature to take `{ authStatus: AuthStatus; guestProfile: CachedOnboardingStatus | undefined }`.
   - `initializing` returns `'loading'`. Any other non-guest status returns `'redirect-home'`. `guest` falls through to the existing rule.
   - Keep it pure (no hooks, no storage).
   - Update `resolve-native-start-route.test.ts` with table cases: initializing; authenticated, passwordRecovery and refreshFailed redirect regardless of guest profile (including `undefined`); guest preserves the old three outcomes.

2. **Hooks.**
   - `use-native-start-route.ts`: read `useAuthState().status`, pass it with `useNativeOnboardingStatus()` into the resolver. Keep the `router.replace('/app/home')` effect.
   - `use-native-onboarding-status.ts`: no change in behavior; the guest read still runs. Skipping the read for signed-in users is an optional optimisation, not required.
   - Extend `use-native-start-route.test.tsx`. Mock `useAuthState`. Cases: authenticated with a completed cached profile redirects to Home; authenticated with no guest data still redirects (never `show-start`); initializing returns `loading`; guest unchanged.
   - `native-start-route.test.tsx` mocks `useNativeStartRoute`, so it needs no change except to assert the Start screen is not rendered for `redirect-home` (already covered).

3. **Sign in action, `native-start-screen.tsx`.**
   - Add a second `Button` inside `Actions`, below Get started, `accessibilityLabel="Sign in"`, `onPress={() => router.push('/auth/sign-in')}`.
   - Use `push`, not `replace`, so the route stack keeps `/`. Check that the sign-in screen has a way back, since `/auth` has no header; if none, `replace` is acceptable. Pick whichever the test and simulator confirm works.
   - Use a secondary/outline `Button` variant if one exists in `src/components/ui/button`. Do not add a new variant.
   - Update the doc comment (it says the second action "can join" later).
   - `native-start-screen.test.tsx`: assert both buttons render, and pressing Sign in calls the router with `/auth/sign-in` (criterion a).
   - Also gate on `areAccountsAvailable` only if other native entry points do. It is true on native now, so do not add the gate unless the existing screens use it.

4. **First-pull gate model, new `src/features/onboarding/model/first-profile-pull.ts`.**
   - Input: `identityKind`, `generation`, `hasCompletedOnboarding` (profile `hasCompletedOnboarding && kenteiRank !== undefined`), and the `SyncCoordinatorState`.
   - `not-applicable` if identity is not `user`, or the local profile is already onboarded. A device with a cached completed profile does not wait on the network (offline relaunch still works).
   - Otherwise find the profile record for this generation:
     - `state.status === 'running'` and `state.run.identityGeneration === generation`: use `state.run.domainResults.profile`.
     - else `state.status === 'idle'` and `state.lastRun?.identityGeneration === generation` and `lastRun.outcome === 'completed'`: use `lastRun.domainResults.profile`.
     - No record: `pending`. Record `succeeded`: `settled`. Record `failed`: `failed`.
   - Treat a `cancelled` last run as no record (`pending`).
   - Fail closed: no record means `pending`, never `settled`.
   - Add `first-profile-pull.test.ts` covering: guest; onboarded locally; no run yet; running with an empty `domainResults`; running with a profile result; idle after a completed run (succeeded and failed); a lastRun from an older generation; a cancelled run; a retry run (`running`, empty) after a failed run returns `pending` again.

5. **Gate hook plus retry UI.**
   - `src/features/onboarding/state/use-first-profile-pull.ts`: combines `useIdentityHandle()`, `useUserProfile()`, `useSyncCoordinatorStatus()` and the model. Returns `{ status, retry }` with `retry = coordinator.retry`.
   - `src/features/onboarding/components/first-pull-retry.tsx`: a calm message ("We could not load your account yet"), a Retry button, `accessibilityRole="alert"`, no onboarding content. Optional safe exit is out of scope; the decision is fail closed.
   - A hook has to call the context at the top of Home, so tests that render Home without `SyncCoordinatorProvider` will throw. Update those mocks rather than loosening `useSyncCoordinatorStatus`; fall back to a non-throwing optional variant only if updating mocks proves disproportionate.

6. **Home wiring, `src/app/app/home.tsx`.**

   - When `pull.status === 'failed'`, render `<FirstPullRetry onRetry={pull.retry} />` instead of onboarding or `DailyHome`.
   - Keep the `Screen` background rule consistent: treat `failed` like blocking so the yellow onboarding background does not flash.
   - Do not touch the resync-after-import effect. The guest-import gate stays authoritative for imports (criterion f). The new gate is additive. After import completes, `isResyncingAfterImport` still holds the render until `runSync('login')` settles.
   - Edge to check by test: guest with local data signs in. Import state is `awaitingConfirmation` with non-zero inventory (importPending true), and the pull gate is also pending or settled. Either way onboarding must not render before the import resolves.

## Risks and notes

- The root route reads auth state, not identity. Do not import `useIdentityHandle` there.
- `lastRun.identityGeneration` is the generation at run time; compare against the current `generation`, not just `status`, or a previous identity's completed run could release onboarding.
- Local-state skip (`hasCompletedOnboarding` true) is the offline-relaunch escape hatch. A signed-in not-yet-onboarded device offline stays on the retry state, which is the intended fail-closed behavior.
- The new gate also applies on web Home for signed-in users with a not-onboarded local profile. That is the same bug on web and an acceptable side effect; check the web Home and e2e auth tests do not assume instant onboarding for a fresh signed-in account.
- Do not add a persistence domain or schema; nothing here changes persisted shape.
