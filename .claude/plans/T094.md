# T094 — Make the web splash overlay reflect the user's theme

## Confirmed facts (verified against current code, not assumed)

- `src/app/_layout.tsx` renders `<AnimatedSplashOverlay />` before
  `UserProfileProvider`/`AppThemeProvider` mount, so it cannot consume
  `ResolvedTheme` via context or `useResolvedTheme()`.
- Platform extension resolution means only `src/components/animated-icon.web.tsx`
  is relevant; `animated-icon.tsx` (native) is untouched by this ticket per its
  own Notes.
- `@react-native-async-storage/async-storage`'s web implementation
  (`node_modules/@react-native-async-storage/async-storage/lib/module/AsyncStorage.js`)
  is a thin synchronous wrapper around `window.localStorage`, wrapped in a
  resolved `Promise`. So `window.localStorage.getItem(...)` is a valid,
  synchronous way to read the same data the async `AsyncStorage.getItem` would
  eventually resolve.
- The user-profile storage key and document shape live in
  `src/features/profile/persistence/user-profile-persistence.ts`:
  `USER_PROFILE_STORAGE_KEY = 'daily-dama:user-profile'`, versioned document
  `{ version: 1, profile: UserProfile }`, parsed/validated by the exported
  `deserializeUserProfile(serialized: string): UserProfile | undefined`. This
  already tolerates malformed/legacy data by returning `undefined` — reuse it
  rather than re-implementing parsing.
- `src/features/profile/state/use-resolved-theme.ts` exports `resolveTheme(prefs)`,
  a pure, hook-free function that takes `{ themeBackgroundColor?, ... }` and
  returns `{ background, accent, text, buttonBackground, buttonBackgroundSecondary }`,
  falling back to `AppColors.sage` (`#dfe8ca`, `src/constants/theme.ts`) when
  `themeBackgroundColor` is unset. This is exactly the "app's default theme
  background pre-selection" the ticket asks for, and it's already the single
  source of truth other code (`src/components/ui/screen.tsx`,
  `theme-color-picker.tsx`) uses for the same default. Reuse it — don't hardcode
  `#dfe8ca` a second time except in `app.json` (which can't import TS).
- Static export (`app.json` -> `"web": { "output": "static" }`) pre-renders
  routes to HTML server-side (confirmed by AGENTS.md's explicit note that
  providers "prevent the server-rendered app from exposing partially hydrated
  UI"). This means the overlay's initial render must not touch `window`, or
  the export step / SSR pass will crash (`window` is undefined there).
- The codebase already has a precedent for exactly this
  SSR-safe-but-swap-before-first-paint problem:
  `src/hooks/use-color-scheme.web.ts` uses
  `useSyncExternalStore(emptySubscribe, () => true, () => false)` to render a
  safe default on the server/first client render, then synchronously swap to
  the real client value before the browser paints (this is
  `useSyncExternalStore`'s documented hydration-mismatch-avoidance behavior,
  not a hack). `useLayoutEffect` is also used elsewhere in the codebase
  (`src/features/sesh/components/sesh.tsx`) but `useSyncExternalStore` is the
  better fit here because it's specifically designed to avoid a hydration
  mismatch warning on the very first render, whereas a plain
  `useState` + `useLayoutEffect` would render the wrong color first and then
  correct it (still before paint, but via an extra commit rather than the
  hydration-safe path this repo already established as its convention). Follow
  this existing convention rather than inventing a second pattern.
- Jest here uses `jest-expo`'s default (react-native) preset, not a jsdom/web
  project — there is no existing web-targeted test file for anything under
  `src/components/animated-icon*` or `src/hooks/use-color-scheme.web.ts`. Plan
  around this: keep any new pure logic dependency-injected (no direct
  `window` reference inside it) so it's unit-testable under the default
  test environment, and don't try to add a jsdom-dependent component test for
  the `.web.tsx` file itself — that would fight the existing test setup for no
  real coverage gain, given `useSyncExternalStore`/hydration timing is
  precisely the kind of thing a jsdom snapshot test won't meaningfully verify
  anyway. Exit criteria already call for in-browser verification instead.
- The current hardcoded overlay background is `'#f4c94d'`, which is
  `AppColors.yellow` (the theme's accent default), not the background
  default (`AppColors.sage` / `#dfe8ca`). So this change is a real, intended
  visual change even for users with no saved theme, not just a refactor.

## Implementation steps, in order

### 1. Add a pure, DI'd helper to resolve the cached background color

New file: `src/features/profile/persistence/read-cached-theme-background.ts`

```ts
import { deserializeUserProfile, USER_PROFILE_STORAGE_KEY } from './user-profile-persistence';
import { resolveTheme } from '@/features/profile/state/use-resolved-theme';

/**
 * Synchronously resolves the theme background color from a raw key/value read,
 * for use before the async UserProfileProvider hydration path completes (e.g.
 * the web splash overlay). `getItem` is injected so this stays platform-agnostic
 * and unit-testable; callers on web pass `(key) => window.localStorage.getItem(key)`.
 */
export function readCachedThemeBackgroundColor(getItem: (key: string) => string | null): string {
  try {
    const serialized = getItem(USER_PROFILE_STORAGE_KEY);
    if (serialized === null) return resolveTheme({}).background;
    const profile = deserializeUserProfile(serialized);
    return resolveTheme({ themeBackgroundColor: profile?.themeBackgroundColor }).background;
  } catch {
    return resolveTheme({}).background;
  }
}
```

Notes:
- No direct `window` reference in this file — keeps it importable/testable
  under the existing (non-jsdom) jest environment and keeps the
  `window.localStorage` coupling isolated to the one `.web.tsx` call site.
- Reuses `deserializeUserProfile`'s existing malformed/legacy-data tolerance
  (returns `undefined` -> falls through to `resolveTheme({})`'s default), so
  behavior stays consistent with the async hydration path's own recovery
  semantics — no new validation logic to keep in sync.
- The outer try/catch only exists to guard `getItem` itself throwing (e.g.
  `localStorage` blocked in a locked-down browser context), since
  `deserializeUserProfile` already guards its own `JSON.parse`.

New test file: `src/features/profile/persistence/read-cached-theme-background.test.ts`
Cover:
- `getItem` returns `null` -> default (`resolveTheme({}).background`, i.e. `#dfe8ca`).
- `getItem` returns a valid v1 document with `themeBackgroundColor` set -> that color.
- `getItem` returns a valid v1 document with no `themeBackgroundColor` -> default.
- `getItem` returns malformed JSON / wrong version -> default (exercises
  `deserializeUserProfile`'s existing failure path through this new caller).
- `getItem` throws -> default.

This step is independent and unblocks step 2; do it first so the `.web.tsx`
change is a small, mechanical wire-up against an already-tested function.

### 2. Wire the helper into the overlay with the hydration-safe pattern

Edit `src/components/animated-icon.web.tsx`:

- Import `useSyncExternalStore` from `react` (alongside the existing
  `useEffect`, `useState` import).
- Import `readCachedThemeBackgroundColor` from
  `@/features/profile/persistence/read-cached-theme-background`.
- Add the same `emptySubscribe = () => () => {}` local helper used in
  `use-color-scheme.web.ts` (small enough that duplicating it locally matches
  that file's existing pattern rather than extracting a shared util for a
  two-line function).
- Add:
  ```ts
  const hasHydrated = useSyncExternalStore(emptySubscribe, () => true, () => false);
  const backgroundColor = hasHydrated
    ? readCachedThemeBackgroundColor((key) => window.localStorage.getItem(key))
    : DEFAULT_SPLASH_BACKGROUND;
  ```
  where `DEFAULT_SPLASH_BACKGROUND` is a module-level constant computed once
  via `resolveTheme({}).background` (import `resolveTheme` here too) — this is
  the value rendered on the server and on the first client render, so it must
  match what `app.json`'s static splash shows (step 3) to avoid any visible
  seam between native-splash-hide and web-overlay-show.
- Remove the hardcoded `backgroundColor: '#f4c94d'` from `webSplashStyles.overlay`
  and instead spread it at the render site:
  `style={{ ...webSplashStyles.overlay, backgroundColor }}`.
- Leave `wordmark`'s hardcoded text color (`#18382e` / `AppColors.ink`) as-is —
  the ticket's description, exit criteria, and Notes all scope this to
  background only. Flag as a follow-up idea, not in scope now: a very dark
  or very light custom background could reduce wordmark contrast, since
  `resolveTheme(...).text` (which already handles this via
  `deriveAutomaticTextColor`) isn't consumed here. Don't fold this in without
  the user asking — it would expand the ticket's stated scope.

Why `useSyncExternalStore` and not a plain `useState` + `useLayoutEffect`:
the getSnapshot function itself doesn't need to change between server/client
here (only the rendered value derived from `hasHydrated` does), so this is a
direct application of the existing repo pattern, not a new one. It also
avoids a hydration-mismatch console warning that a naive
`useState(realValue)` initializer would trigger when SSR output and first
client-render output differ, and avoids an extra visible commit that plain
`useLayoutEffect` would take one render longer to reach.

### 3. Update the native/build-time baseline in `app.json`

Change the `expo-splash-screen` plugin config's `backgroundColor` from
`"#208AEF"` to `"#dfe8ca"` (matching `AppColors.sage` exactly — this is the
literal string value of `resolveTheme({}).background`'s fallback, so keep it
byte-for-byte in sync with `src/constants/theme.ts`'s `sage` value if that
constant ever changes). Do not touch `android.adaptiveIcon.backgroundColor`
(`#E6F4FE`) — that's the Android adaptive icon background, unrelated to the
splash screen, and out of scope.

This step has no code dependency on steps 1-2 and could be done in parallel,
but do it after so a single verification pass (step 4) covers everything
together.

### 4. Verify

Run the standard sequence: `node .claude/scripts/verify.mjs` (or the four
commands individually while iterating). This is web-only application code —
no `--skip-export` needed; the export step is exactly what will catch an
accidental `window` reference reached during SSR.

Then the in-browser exit-criteria check (`yarn expo start --web`, not a
static file server, per AGENTS.md):
1. Complete onboarding / open Profile, set a visually distinctive custom
   background color via the theme color picker, confirm it saved (check
   `localStorage.getItem('daily-dama:user-profile')` in devtools console
   shows that hex in `themeBackgroundColor`).
2. Reload. Verify the splash overlay visibly renders in that color rather
   than the old hardcoded yellow or the sage default — this is easy to see
   directly since the overlay holds the full-screen color for ~2 animation
   frames, no throttling needed for a visual check. For the literal
   "computed-style check" the exit criteria calls for, either: throttle
   CPU (devtools Performance tab, 6x slowdown) before reload so the overlay
   persists long enough to inspect via the Elements panel, or run a short
   console snippet on reload that grabs
   `document.querySelector('[aria-hidden="true"]')` and logs
   `getComputedStyle(el).backgroundColor` as early as possible (e.g. via a
   `DOMContentLoaded` listener registered before navigating, since that fires
   before React hydration completes).
3. Clear the saved profile (or open a fresh/incognito context) and reload;
   verify the overlay renders `#dfe8ca` (sage), not the old yellow.
4. Sanity-check no new console warnings appear on reload (specifically no
   hydration-mismatch warning — that would indicate the
   `useSyncExternalStore` wiring is wrong).

## Risks / non-obvious things to watch for

- SSR crash risk is the main hazard. Any `window` access that isn't
  gated behind the `hasHydrated` check (or an effect) will break
  `yarn expo export --platform web`, which pre-renders routes server-side.
  Keep `window.localStorage.getItem` only inside the ternary branch guarded by
  `hasHydrated`, never at module scope or in the unconditional part of the
  render body.
- Don't skip the DI on `readCachedThemeBackgroundColor`. It's tempting to
  reach for `window.localStorage` directly inside that helper since it's
  "only ever called on web," but keeping it injection-based is what makes it
  cheaply unit-testable under this repo's current (non-jsdom) jest setup, and
  matches the existing `loadUserProfile(storage: KeyValueStorage, ...)` DI
  convention already used in `user-profile-persistence.ts`.
- Keep the default value in sync in three places by construction, not by
  copy-paste: `resolveTheme({}).background` (source of truth, in
  `use-resolved-theme.ts`), the splash overlay's pre-hydration/SSR render
  value (step 2, should call `resolveTheme({})` rather than hardcode
  `#dfe8ca` again), and `app.json`'s literal (step 3, which genuinely must be
  a hardcoded string since it's build-time native config consumed outside the
  JS bundle — this is the one unavoidable duplication, per the ticket's own
  Notes).
- This ticket doesn't touch `UserProfileProvider`, `AppThemeProvider`, or any
  reducer/persistence write path — it only adds a read-only, synchronous,
  best-effort peek at already-persisted data. No schema or write-queue changes
  are needed or in scope.
