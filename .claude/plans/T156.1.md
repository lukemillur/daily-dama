# T156.1 — Define identity-scoped storage and generation ownership

## Scope for this iteration

Build three standalone primitives plus their unit tests. Do **not** touch:

- Any of the five providers (`user-profile-provider.tsx`, `custom-trick-provider.tsx`,
  `practice-history-provider.tsx`, `goal-provider.tsx`, `note-provider.tsx`) or
  `src/app/_layout.tsx`. Wiring these to the new scoped storage, cancelling stale

  avoid a flash of the wrong onboarding/theme state before the real provider

"Good enough" for this ticket: the identity model, the scoped storage adapter, and
the generation-tracking primitive exist, are fully unit-tested against the four

## Background confirmed by reading the code

- `KeyValueStorage` (`src/shared/persistence/storage.ts`) is the two-method
  `getItem`/`setItem` interface every domain's persistence module takes as a
  parameter. `AsyncStorage` is passed directly as a `KeyValueStorage` today (e.g.
  `user-profile-provider.tsx:62`, `.tsx:72`) — no wrapper exists yet.
- Five domains, five unscoped keys, all following the same
  `'daily-dama:<domain>'` literal pattern: `daily-dama:user-profile`,
  `daily-dama:goals`, `daily-dama:custom-tricks`, `daily-dama:notes`,
  `daily-dama:practice-history`. (AGENTS.md's "three domains" is stale; goals and
  notes were added later — five real domains exist today.)
- `AuthState` (`src/features/auth/model/auth-state.ts`) is
  `'initializing' | { guest, reason } | { authenticated, session, lastEvent } | { passwordRecovery, session }`.
  `session.user.id` (from `@supabase/supabase-js`'s `Session`) is the only place a
  verified user id can legitimately come from — it's populated by the SDK from a
  validated JWT, never from arbitrary app input. This is the sole trusted source
  for `user:<verified-user-id>`.
- `BACKEND_ROADMAP.md`'s synchronization-security section is this ticket's
  direct source: "Partition caches as `guest` and `user:<verified-user-id>`",
  "Ignore any `user_id` supplied in mutation payloads", "Tag sync runs with an
  identity/generation token so a late result cannot update state after logout or
  account switching."
- TASKS.md confirms the split: T156.2 does provider rehydration/injection and
  cancels stale hydration; T156.3 does the cross-account isolation test matrix.
  Both explicitly "Depends on T156.1" — this ticket only has to hand them
  working, tested primitives.

## Files to add (in this order — each depends only on the previous)

### 1. `src/shared/persistence/identity.ts` (foundation, no feature deps)

Keep this file free of any `@/features/*` import — `shared/` is depended on by
features, not the reverse, and nothing else in `shared/` imports from
`features/` today.

```ts
export type Identity =
  | { readonly kind: 'guest' }
  | { readonly kind: 'user'; readonly userId: string };

export const GUEST_IDENTITY: Identity = { kind: 'guest' };

// Supabase auth.users.id is always a UUID. Validating that shape is what makes
// "malformed identity rejected" concretely testable, and it also protects the
// key-namespacing scheme below: a userId containing ':' could otherwise be used
// to forge a colliding physical key across namespaces.
const VERIFIED_USER_ID_PATTERN =
  /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i;

export function isValidVerifiedUserId(value: unknown): value is string {
  return typeof value === 'string' && VERIFIED_USER_ID_PATTERN.test(value);
}

// The only sanctioned way to construct a `user:` identity. Returns undefined
// ("rejected") for anything that isn't a validly-shaped id — callers must not
// have any other path to producing a `{ kind: 'user' }` value.
export function createUserIdentity(userId: unknown): Identity | undefined {
  return isValidVerifiedUserId(userId) ? { kind: 'user', userId } : undefined;
}

export function identitiesEqual(a: Identity, b: Identity): boolean {
  if (a.kind !== b.kind) return false;
  return a.kind === 'user' && b.kind === 'user' ? a.userId === b.userId : true;
}

// Physical-namespace prefix for a logical key. Exported so a future migration
// wrapper (T156.2) can compute both the new scoped key and the old unscoped
// legacy key without duplicating this scheme.
export function identityNamespace(identity: Identity): string {
  return identity.kind === 'guest' ? 'guest' : `user:${identity.userId}`;
}
```

Test file `src/shared/persistence/identity.test.ts` (colocated `.test.ts`,
matching this directory's existing convention, not `auth`'s `__tests__/`):

- `createUserIdentity` accepts a well-formed UUID, rejects empty string,
  rejects a non-UUID string, rejects a string containing `:` (the
  injection/collision case), rejects `undefined`/numbers/objects.
- `identityNamespace` for guest vs. two different users produces three distinct
  strings; same user id twice produces the same string.
- `identitiesEqual` true for two guests, true for same-id users, false for
  different-id users, false for guest vs. user.

### 2. `src/shared/persistence/identity-context.ts` (depends on `identity.ts`)

This is the generation-token primitive. It's named `identity-context` rather
than `identity-generation` because it owns both "what is the current identity"
and "what generation are we on" as one atomic piece of state — splitting them
would let a caller read a `getIdentity()` and a `getGeneration()` that are
momentarily inconsistent with each other.

```ts
export interface IdentityContext {
  readonly getIdentity: () => Identity;
  readonly getGeneration: () => number;
  readonly setIdentity: (next: Identity) => number; // returns the (possibly unchanged) generation
  readonly isCurrentGeneration: (captured: number) => boolean;
}

export function createIdentityContext(initial: Identity = GUEST_IDENTITY): IdentityContext {
  let identity = initial;
  let generation = 0;

  return {
    getIdentity: () => identity,
    getGeneration: () => generation,
    setIdentity: (next) => {
      if (identitiesEqual(identity, next)) return generation; // no-op: same identity, no new generation
      identity = next;
      generation += 1;
      return generation;
    },
    isCurrentGeneration: (captured) => captured === generation,
  };
}

// Convenience wrapper for the exact pattern T156.2 needs in every provider's
// hydration effect: capture the generation before starting async work, then
// discard the result if the identity moved on while it was in flight.
export type GenerationGuardedResult<T> =
  | { readonly status: 'applied'; readonly value: T }
  | { readonly status: 'stale' };

export async function withGenerationGuard<T>(
  context: IdentityContext,
  operation: () => Promise<T>,
): Promise<GenerationGuardedResult<T>> {
  const generation = context.getGeneration();
  const value = await operation();
  return context.isCurrentGeneration(generation)
    ? { status: 'applied', value }
    : { status: 'stale' };
}
```

Test file `src/shared/persistence/identity-context.test.ts`:

- `setIdentity` to a genuinely different identity increments generation;
  calling it again with an identity `identitiesEqual` to the current one does
  **not** bump generation (idempotence — repeated `TOKEN_REFRESHED` events for
  the same user must not manufacture spurious generation churn).
- `isCurrentGeneration` returns true for the generation captured immediately
  before a `setIdentity` call that didn't change identity, and false after one
  that did.
- `withGenerationGuard`: start an operation, resolve a deferred promise
  *after* calling `setIdentity` with a new identity mid-flight, assert the
  guard reports `{ status: 'stale' }` and never `'applied'`. A second call
  where the identity does not change while in flight resolves `'applied'` with
  the correct value. This is the direct proof for "generation changes
  invalidate late results."

### 3. `src/shared/persistence/scoped-storage.ts` (depends on both above)

```ts
export function physicalKey(identity: Identity, logicalKey: string): string {
  return `${identityNamespace(identity)}:${logicalKey}`;
}

export function createScopedKeyValueStorage(
  base: KeyValueStorage,
  context: Pick<IdentityContext, 'getIdentity'>,
): KeyValueStorage {
  return {
    getItem: (key) => base.getItem(physicalKey(context.getIdentity(), key)),
    setItem: (key, value) => base.setItem(physicalKey(context.getIdentity(), key), value),
  };
}
```

Taking `Pick<IdentityContext, 'getIdentity'>` rather than a bare
`() => Identity` function makes the call site self-documenting (this always
comes from the shared context, never a one-off closure) while still being easy
to fake in tests.

Test file `src/shared/persistence/scoped-storage.test.ts`. Back this with a
tiny in-memory `Map`-backed fake `KeyValueStorage` (not `jest.fn()` stubs) so
the isolation tests read as a direct proof, not an implementation-detail
assertion:

- **Isolation proof (exit criterion 1):** write `'user-profile'` under a guest
  identity, switch the context to `user:A`, write a *different* value to the
  same logical key `'user-profile'`, switch to `user:B`, confirm
  `getItem('user-profile')` is `null` (never sees A's or guest's value), switch
  back to guest, confirm the original guest value is still intact. Prove this
  with real reads through the adapter, not by inspecting the fake store's
  internal keys.
- **Never accepts identity from payload data (exit criterion 4):** with the
  context fixed on guest, call
  `setItem('user-profile', JSON.stringify({ userId: 'user:someone-else' }))`.
  Assert the underlying fake store's key reflects only the guest namespace —
  the payload content is inert as far as key resolution goes. Also assert
  `getIdentity` is invoked fresh on every call (not memoized at
  `createScopedKeyValueStorage` construction time): change what the context
  returns between two calls with the same logical key and confirm two
  different physical keys result.
- Confirm `getItem`/`setItem` still surface the base storage's own
  resolution/rejection (pass-through of errors), since domain persistence
  modules (`loadUserProfile`, etc.) already handle `storage.getItem` throwing.

### 4. `src/features/auth/model/identity-from-auth-state.ts` (depends on `identity.ts` + `auth-state.ts`)

This is the one place `AuthState` and `Identity` meet. It lives in the `auth`
feature (not `shared/`) specifically to keep `shared/persistence` free of a
feature dependency — `shared` stays generic, `features/auth` depends on it,
matching every other existing dependency edge in the codebase.

```ts
import type { AuthState } from '@/features/auth/model/auth-state';
import { createUserIdentity, GUEST_IDENTITY, type Identity } from '@/shared/persistence/identity';

/**
 * Maps the app's actual Auth state to an Identity. Pure and synchronous.
 *
 * Returns `undefined` for `'initializing'` — the identity is genuinely
 * unresolved at that point (Supabase hasn't reported a session yet), not
 * safely assumed to be `guest`. T156.2 decides what a provider does with an
 * unresolved identity (recommendation below); this function only refuses to
 * guess.
 *
 * `authenticated` / `passwordRecovery` sessions always resolve to a
 * `user:<verified-user-id>` identity derived from `session.user.id` — the
 * only place a verified id can come from. If that id is somehow malformed
 * (defensive case; the Supabase SDK controls this in practice), the identity
 * is rejected back to `guest` rather than exposing a broken partial identity.
 */
export function deriveIdentityFromAuthState(state: AuthState): Identity | undefined {
  if (state.status === 'initializing') return undefined;
  if (state.status === 'guest') return GUEST_IDENTITY;

  // 'authenticated' | 'passwordRecovery'
  return createUserIdentity(state.session.user.id) ?? GUEST_IDENTITY;
}
```

Test file `src/features/auth/model/__tests__/identity-from-auth-state.test.ts`
(matching this feature's existing `__tests__/` convention — different from
`shared/persistence`'s colocated style; use whichever convention the
containing directory already uses, per file). Reuse `auth-test-fixtures.ts` if
it already builds `Session`/`AuthState` fixtures — check it before writing ad
hoc ones.

- `'initializing'` → `undefined`.
- `'guest'` (any `reason`) → `GUEST_IDENTITY`.
- `'authenticated'` with a well-formed `session.user.id` → `{ kind: 'user', userId: <that id> }`.
- `'passwordRecovery'` with a well-formed id → same mapping (a mid-recovery
  session is still a verified session).
- `'authenticated'` with a malformed/empty `session.user.id` (construct this
  fixture directly; don't assume the SDK can produce it in production) →
  `GUEST_IDENTITY`, not a broken user identity and not a thrown error. This is
  the direct proof for "unverified or malformed identities are rejected."

## Explicit open decision left for T156.2 (do not resolve it here)

`deriveIdentityFromAuthState` returning `undefined` for `'initializing'` means
a provider must decide what to do during that window: delay its first
hydration attempt until identity resolves, or optimistically hydrate as guest
and rely on the generation guard to discard a late result if it turns out to
be authenticated. Recommend delaying (avoids a wasted/racy guest read on the
common cold-start path where a session restores quickly), but this is a
provider-orchestration call, not a primitive-design call — leaving it to
T156.2 as its own Notes intend ("This changes provider orchestration but not
reducer state shapes").

## Recommendation for T156.2 on legacy unscoped keys (not implemented here)

Existing installs already have real guest data at the five unscoped
`daily-dama:<domain>` keys. Unlike the custom-trick v1 document (which AGENTS.md
explicitly says may reset to empty), user-profile and practice-history in
particular represent real accumulated prototype data, and there's no
architectural reason tied to this ticket to discard it. `identityNamespace` and
`physicalKey` are exported specifically so T156.2 can build a thin one-time
migration wrapper — e.g., on a guest identity, if the new scoped key
(`guest:daily-dama:<domain>`) is empty, fall back to reading the old unscoped
key once and write it forward under the new scoped key. This ticket does not
implement that wrapper; it only avoids blocking it.

## Risks / non-obvious things to watch

- Don't let `identity-context.ts`'s `setIdentity` bump generation on a
  same-identity call — Supabase's `onAuthStateChange` fires `TOKEN_REFRESHED`
  repeatedly for the same signed-in user, and if that churns the generation,
  every in-flight hydration read would spuriously invalidate itself once
  T156.2 wires this up.
- Keep `shared/persistence/identity.ts` free of any import from
  `@/features/auth` — the mapping function belongs in `features/auth`, not the
  other way around, to preserve the existing "shared has no feature deps"
  shape of this codebase.
- `createUserIdentity`'s UUID check is deliberately strict (real Supabase UUID
  shape) specifically so a malformed or attacker-influenced string can never
  reach `identityNamespace` and produce a colliding or `:`-injected physical
  key.
- Test the "never accepts identity from payload data" criterion against the
  *scoped storage adapter itself*, not just as a code-review observation — the
  adapter's `setItem`/`getItem` signatures already make this structurally true
  (no identity parameter exists to smuggle one in), but a test converts that
  from "true by construction" into a verified regression guard.
