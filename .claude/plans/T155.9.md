# T155.9 — Generate database types and define cloud repository contracts

## Scope decision (read first)

AGENTS.md's "State and persistence boundaries" section names three domains
(profile, custom tricks, practice history), but that text predates T155.4/the
goals and notes features. The repo now has **five** independent persistent
domains, each with its own reducer, persistence adapter, and provider:

- `src/features/profile/state/user-profile-provider.tsx` — `api.profiles` + `api.user_trick_states`
- `src/features/custom-tricks/state/custom-trick-provider.tsx` — `api.custom_tricks`
- `src/features/stats/state/practice-history-provider.tsx` — `api.practice_sessions`
- `src/features/goals/state/goal-provider.tsx` — `api.goals`
- `src/features/notes/state/note-provider.tsx` — `api.notes`

"One cloud repository contract per existing persistent domain" therefore
means **five** repository contracts, with the profile repository covering two
tables (`profiles` + `user_trick_states`) since T155.10 already groups them
as one future mapping ticket.

Per roadmap Phase 2 frontend items 1/3 ("define one cloud repository
interface per domain" / "keep reducers unaware of Supabase and network
state") and the explicit split against T155.10–T155.13 ("Do not integrate
the provider or synchronization yet" / row↔domain-model mapping is a
*separate* later ticket), this ticket's repositories operate on **generated
row types**, not domain models (`UserProfile`, `CustomTrick`, etc.). No
camelCase↔snake_case mapping, no discriminated-union reconstruction, no
runtime domain validation belongs here — that's T155.10–T155.13. This
ticket's job is the data-access boundary: typed reads/writes against
Postgrest, with Supabase's query-builder types never appearing in a public
signature.

Concrete implementations (not just interfaces) are in scope: the exit
criterion "each domain repository exposes typed paginated reads and mutation
results" is best proven by real, testable implementations backed by the
generated types and the local stack, not bare interface declarations.

## 1. Generate and check in database types

Add `supabase/scripts/generate-database-types.mjs` (plain Node, no deps,
same style as `supabase/tests/run-db-tests.mjs`):

- Pin `npx --yes supabase@2.115.0` (matches `run-db-tests.mjs`'s `SUPABASE`
  constant — copy it).
- Sequence: `supabase start` (idempotent) → `supabase db reset` (clean state
  is what makes the output deterministic/stable — never generate from a
  local stack with ad hoc manual changes) → `supabase gen types typescript
  --local --schema api` (explicit `--schema api` rather than relying on
  config.toml's default schema list, so the command's determinism doesn't
  depend on reading config.toml correctly) → capture stdout.
- Default mode: write stdout, prefixed with a generated-file banner comment
  ("Generated by `yarn db:generate-types` — do not hand-edit. Source:
  supabase/migrations/. Run `yarn db:generate-types` after any migration
  change."), to `src/shared/supabase/database-types.ts`.
- `--check` mode: write to a temp file instead, diff byte-for-byte against
  the committed file, print a diff-suggestive message and exit non-zero on
  mismatch, exit 0 on match. This is what makes the checked-in file "stable"
  rather than merely "generated once and hoped to stay current."
- Like `run-db-tests.mjs`, always finish with a cleanup `db reset` so the
  stack isn't left dirty, regardless of outcome.

Add yarn scripts:
```json
"db:generate-types": "node supabase/scripts/generate-database-types.mjs",
```
(`--check` is `yarn db:generate-types -- --check`, following the existing
`test:db -- --mutation-check` convention.)

Wire the `--check` mode into `supabase/tests/run-db-tests.mjs`'s default
sequence, right after `db reset` and before pgTAP (cheap, and it's exactly
where a schema/type drift should be caught — before the rest of the suite
wastes time against a schema the checked-in types no longer describe). Keep
the existing PASS/FAIL-line-per-step style; do not change unrelated steps.

Document this in `supabase/README.md` as a new section ("Generating
TypeScript database types"), matching the doc style of the existing
sections (prerequisites already covered by "First-time / clean-reset
workflow" above it — just add the generate/check commands and note the
output path and drift-check).

Run `node supabase/scripts/generate-database-types.mjs` for real once,
locally, to produce the actual checked-in `src/shared/supabase/
database-types.ts` — do not hand-write it. Confirm running it a second time
in `--check` mode reports no drift.

In the moved file:
- Import `Database` from `./database-types`.
- Change `createClient(...)` to `createClient<Database, 'api'>(url,

- Existing tests only assert on `options.auth`, url/key, and call count —

  that `options.db` is `{ schema: 'api' }` in the "constructs the client
  exactly once" test.

## 3. Shared cloud-repository contract vocabulary

New file `src/shared/supabase/cloud-repository.ts` — the shared types every
domain repository below is built from, so "typed paginated reads and
mutation results" is one vocabulary, not five ad hoc shapes:

```ts
export type CloudRepositoryErrorKind =
  | 'notFound' | 'authorization' | 'validation' | 'network' | 'unknown';

export interface CloudRepositoryError {
  readonly kind: CloudRepositoryErrorKind;
  readonly message: string;
  readonly cause?: unknown;
}

export type CloudMutationResult<T> =
  | { readonly status: 'succeeded'; readonly value: T }
  | { readonly status: 'failed'; readonly error: CloudRepositoryError };

export interface CloudPage<T> {
  readonly items: readonly T[];
  readonly nextCursor: string | null;
}

export type CloudReadResult<T> =
  | { readonly status: 'succeeded'; readonly page: CloudPage<T> }
  | { readonly status: 'failed'; readonly error: CloudRepositoryError };

export interface CloudPageRequest {
  readonly limit: number;
  readonly cursor?: string | null;
}
```

Plus implementation helpers used by every repository (also in this file, so
each domain file only wires them to its own table):

- `encodeCloudCursor(offset: number): string` / `decodeCloudCursor(cursor:
  string | null | undefined): number` — offset-based, encoded as a decimal
  string. Document explicitly that callers must treat the cursor as opaque
  (don't parse it) even though today's encoding is simple; this keeps the
  door open to switching to real keyset pagination later without an
  interface change. `decodeCloudCursor` throws (not silently falls back to
  0) on a malformed cursor — a corrupted cursor should fail loudly, not
  silently restart pagination from the top.
- `mapPostgrestError(error: { message: string; code?: string | null } | null
  | undefined): CloudRepositoryError` — classifies by Postgrest/Postgres
  error code: `42501` → `authorization`, `PGRST116` → `notFound`, `23514` /
  `23505` / `PGRST204` / `PGRST102` → `validation`, everything else →
  `unknown`.
- `mapNetworkError(cause: unknown): CloudRepositoryError` — wraps a thrown
  exception (fetch failure, abort, etc.) as `{ kind: 'network', ... }`.

Unit test file `src/shared/supabase/cloud-repository.test.ts` (real jest,
pure functions, no network): cursor encode/decode round-trips, decode throws
on garbage input, each Postgrest error code maps to the right `kind`,
unknown code falls back to `'unknown'`.

## 4. Per-domain repository contracts and implementations

One file per domain, colocated under that feature's existing `persistence/`
directory (matching the local-adapter naming convention already there,
e.g. `custom-trick-persistence.ts` → `custom-trick-cloud-repository.ts`).
Every repository factory takes an already-constructed `SupabaseClient
<Database, 'api'>` as a parameter (dependency injection) — never resolves
`getSupabaseClient()` internally — so each is trivially unit-testable with a
hand-written fake client, matching how local adapters take `storage` as a
parameter rather than reaching for `AsyncStorage` themselves.

Row/Insert/Update aliases come from `Database['api']['Tables'][...]`.
Where a table's T155.5 column-level grants are narrower than the generated
Update type (goals/notes only grant `update` on a subset of columns —
`deleted_at` for goals, `body`/`deleted_at` for notes), the repository's
public patch parameter type is `Pick<...Update, '...'>` of exactly the
grantable columns, not the full generated `Update` type. This gives a
compile-time guardrail matching the server's own column grants, rather than
only failing at runtime with `42501`.

**`src/features/profile/persistence/profile-cloud-repository.ts`**
(`api.profiles` + `api.user_trick_states`):
```ts
export interface ProfileCloudRepository {
  getProfile(): Promise<CloudReadResult<ProfileRow | null>>; // single row, RLS-scoped to caller
  upsertProfile(input: ProfileUpsertInput): Promise<CloudMutationResult<ProfileRow>>;
  listTrickStates(request: CloudPageRequest): Promise<CloudReadResult<UserTrickStateRow>>;
  upsertTrickState(input: UserTrickStateUpsertInput): Promise<CloudMutationResult<UserTrickStateRow>>;
  deleteTrickState(trickId: string): Promise<CloudMutationResult<{ readonly trickId: string }>>;
}
```
`getProfile` uses `.select('*').maybeSingle()` (no pagination — it's a
singleton row per user). `upsertProfile` uses `.upsert(row, { onConflict:
'user_id' })`. `listTrickStates` orders by `created_at desc, id asc` with
`.range(offset, offset + limit - 1)`; note there's no dedicated index on
`user_trick_states` for this ordering (only `custom_tricks`/
`practice_sessions`/`goals`/`notes` got one in T155.3/T155.4) — call this
out as a non-blocking observation, not something to fix here.
`upsertTrickState` uses `onConflict: 'user_id,trick_id'`. `deleteTrickState`
uses `.delete().eq('trick_id', trickId)` (the only DELETE-granted table
besides `custom_tricks`, per the T155.2 migration comment about it being
"the only legal way to fully clear is_selected/is_manually_unlocked").

**`src/features/custom-tricks/persistence/custom-trick-cloud-repository.ts`**
(`api.custom_tricks`, full CRUD):
```ts
export interface CustomTrickCloudRepository {
  list(request: CloudPageRequest): Promise<CloudReadResult<CustomTrickRow>>;
  upsert(row: CustomTrickInsert): Promise<CloudMutationResult<CustomTrickRow>>;
  remove(id: string): Promise<CloudMutationResult<{ readonly id: string }>>;
}
```
`list` orders by `created_at desc, id asc` (matches the
`custom_tricks_user_created_at_idx` index). `upsert` uses `onConflict:
'user_id,id'`.

**`src/features/stats/persistence/practice-history-cloud-repository.ts`**
(`api.practice_sessions`, insert-only/immutable — no update/remove method at
all, matching the table's actual grants):
```ts
export interface PracticeHistoryCloudRepository {
  list(request: CloudPageRequest): Promise<CloudReadResult<PracticeSessionRow>>;
  insertMany(rows: readonly PracticeSessionInsert[]): Promise<CloudMutationResult<readonly PracticeSessionRow[]>>;
}
```
`list` orders by `completed_at desc, id asc` — this exact tiebreak is what
`supabase/tests/data-api/t155_8_pagination.test.mjs` already proved
necessary and correct; reuse the same ordering here. `insertMany` is the
primitive; a convenience `insert(row)` wrapping `insertMany([row])` is
optional/implementer's call.

**`src/features/goals/persistence/goal-cloud-repository.ts`** (`api.goals`,
select/insert/update-only, tombstoned):
```ts
export type GoalCloudPatch = Pick<GoalUpdate, 'deleted_at'>;

export interface GoalCloudRepository {
  list(request: CloudPageRequest): Promise<CloudReadResult<GoalRow>>;
  insert(row: GoalInsert): Promise<CloudMutationResult<GoalRow>>;
  update(id: string, patch: GoalCloudPatch): Promise<CloudMutationResult<GoalRow>>;
}
```
`list` does **not** filter out tombstoned (`deleted_at is not null`) rows —
the migration's whole point is that other devices need to observe the
deletion fact during future sync (T157), so filtering belongs to a future
sync/selector layer, not this data-access boundary. Document this choice
explicitly in the file's comment so a future reader doesn't "fix" it into a
silent filter.

**`src/features/notes/persistence/note-cloud-repository.ts`** (`api.notes`,
same shape as goals plus editable `body`):
```ts
export type NoteCloudPatch = Pick<NoteUpdate, 'body' | 'deleted_at'>;

export interface NoteCloudRepository {
  list(request: CloudPageRequest): Promise<CloudReadResult<NoteRow>>;
  insert(row: NoteInsert): Promise<CloudMutationResult<NoteRow>>;
  update(id: string, patch: NoteCloudPatch): Promise<CloudMutationResult<NoteRow>>;
}
```

Every `list`/mutation method follows the same internal pattern (write this
once, mentally, and repeat it identically across files — do not vary it per
domain):
```ts
try {
  const { data, error } = await client.from('table')...;
  if (error) return { status: 'failed', error: mapPostgrestError(error) };
  return { status: 'succeeded', ... };
} catch (cause) {
  return { status: 'failed', error: mapNetworkError(cause) };
}
```

None of these five files should import anything from `@supabase/supabase-js`
in their exported type signatures (only in the implementation body, to type
the injected client parameter itself, which is fine — the client type is
the acknowledged seam, not a leak). The interfaces' return types are only
`CloudReadResult<Row>` / `CloudMutationResult<...>` from
`cloud-repository.ts`.

- Import `type { PostgrestFilterBuilder } from '@supabase/supabase-js'` once

  match any of the above return types — the actual negative-leak proof, not

Run `yarn tsc --noEmit` to confirm this file (and everything else) compiles.
This file has no runtime behavior, so also confirm `yarn lint` is clean

## Risks / non-obvious things

- **Generic client typing.** `createClient<Database, 'api'>(...)` requires
  the installed `@supabase/supabase-js` (`^2.112.3`) to support the
  three-generic-parameter form (`Database`, schema name, optionally a
  fourth `Options` param). This has been stable in v2 for a long time, but
  verify against the actually-installed version if TS complains — don't
  silently downgrade to an untyped client to make it compile.
- **`gen types` schema selection.** Confirm `--schema api` actually produces
  a `Database.api.Tables...` shape (not `Database.public...`) against this
  repo's `config.toml` (`[api] schemas = ["api"]`). If the CLI's default
  behavior without `--schema` already matches, keep the explicit flag
  anyway for determinism that doesn't depend on config.toml being read
  correctly by the generator.
- **Do not add domain mapping.** It will be tempting to also map
  `UserProfile`/`CustomTrick`/etc. to/from rows while already touching this
  code — that's explicitly T155.10–T155.13's job (all four already exist as
  separate "Not started" tasks depending on this one). Keep this ticket's
  repositories speaking only in generated Row/Insert/Update types.
- **Client relocation blast radius.** Confirmed only 4 importers
  (`auth-provider.tsx` + 3 test files) reference the current
  `features/auth/persistence/supabase-client.ts` path — re-grep before
  finishing to make sure nothing new was missed, since other in-flight work
  could have added an importer.
