# T156.2 — Rehydrate every provider from its current identity namespace

## Confirmed current state (read in full before starting)

- `src/shared/persistence/identity.ts` (T156.1): `Identity = {kind:'guest'} | {kind:'user', userId}`, `identityNamespace()` returns `'guest'` or `'user:<uuid>'`, `createUserIdentity` validates a UUID and rejects anything else back to `undefined`.
- `src/shared/persistence/identity-context.ts` (T156.1): `createIdentityContext(initial)` returns a **plain mutable object** (not React state) with `getIdentity`, `getGeneration`, `setIdentity` (bumps generation only when identity actually changes, via `identitiesEqual`), `isCurrentGeneration`. `withGenerationGuard(context, operation)` runs an async op and reports `{status:'applied'|'stale'}` by comparing generation before/after.
- `src/shared/persistence/scoped-storage.ts` (T156.1): `createScopedKeyValueStorage(base, context)` wraps a `KeyValueStorage` so every `getItem`/`setItem` call resolves `physicalKey(context.getIdentity(), key)` **freshly, synchronously, at call time** — not cached, not derived from payload data. Physical key shape: `` `${namespace}:${logicalKey}` ``, e.g. `guest:daily-dama:user-profile`.
- `src/features/auth/model/identity-from-auth-state.ts` (T156.1): `deriveIdentityFromAuthState(authState)` → `undefined` while `'initializing'`, `GUEST_IDENTITY` for `'guest'`, `user:<uuid>` for `'authenticated'/'passwordRecovery'` (falls back to guest if the session id is somehow malformed). Explicitly punts "what a provider does with an unresolved identity" to this ticket.
- `src/features/auth/state/auth-provider.tsx`: `AuthProvider` exposes `useAuthState()`/`useAuthActions()`. Auth state starts `'initializing'`, resolves to `'guest'` or `'authenticated'` via a Supabase `onAuthStateChange` subscription (or synchronously-deferred to `'guest'` if Supabase isn't configured/errors). No network round trip is required to leave `'initializing'`.
- **All five domain providers are structurally identical** (`user-profile-provider.tsx`, `custom-trick-provider.tsx`, `practice-history-provider.tsx`, `goal-provider.tsx`, `note-provider.tsx`): `useReducer` + `hasHydrated` boolean state + `shouldSkipInitialWrite` ref + one `createWriteQueue` instance + a mount-only `useEffect` that calls `loadX(AsyncStorage)` guarded by a local `isCurrent` closure flag, dispatches an `xRestored` action, then `setHasHydrated(true)` + a second `useEffect` on `[state]` that skips the very first post-hydration write via the ref, then calls `enqueueWrite(state)`. Each domain has **exactly one** AsyncStorage key (`daily-dama:user-profile`, `daily-dama:custom-tricks`, `daily-dama:practice-history`, `daily-dama:goals`, `daily-dama:notes`), and each `loadX`/`saveX` pair already takes a generic `KeyValueStorage`, not `AsyncStorage` directly — they drop into scoped storage with no signature changes.
- Provider nesting (`src/app/app/_layout.tsx`, inside `src/app/_layout.tsx`'s `<AuthProvider><Slot/></AuthProvider>`): `CustomTrickProvider > UserProfileProvider > PracticeHistoryProvider > NoteProvider > GoalProvider > AppThemeProvider > AppTabs`. `GoalProvider` depends on `useUserProfileActions()` and must stay nested inside `UserProfileProvider`.
- **Backward-compatibility gap confirmed real**: pre-T156.1 installs have data at the bare logical key (e.g. `daily-dama:user-profile`), not `guest:daily-dama:user-profile`. `identity.ts`'s own comment says this migration is deliberately deferred to this ticket ("a future migration wrapper (T156.2) can compute both the new scoped key and the old unscoped legacy key"). This ticket must add that fallback for the guest namespace, or existing local users lose their profile/tricks/history/goals/notes on upgrade. No migration is needed for `user:<uuid>` namespaces — those never existed before this ticket.

## Design decisions (read before implementing — these resolve the ambiguities called out in the task)

1. **Identity propagation**: one new `IdentityProvider` (new file `src/shared/persistence/identity-provider.tsx`) is the single source of truth. It calls `useAuthState()` internally and derives `Identity` via `deriveIdentityFromAuthState`, so none of the five domain providers touch Auth directly (no prop drilling, no five independent derivations). It owns one `createIdentityContext()` instance and exposes it plus a **reactive** mirror (`identity`, `generation` in React state, updated together whenever `setIdentity` actually bumps generation) through a `useIdentityHandle()` hook. The imperative `context` object is what closures inside async load/write callbacks use for generation checks (React state can't be read inside a stale closure safely across renders the way an object with live getters can).
2. **Blocking gate while identity is unresolved or mid-switch, not just at boot.** `IdentityProvider` renders a loading fallback (visually reusing the same wordmark/spinner style already used by each domain's hydration fallback) whenever `authState.status === 'initializing'` — i.e. it never lets a domain provider hydrate under a guessed identity. Each domain provider independently reuses its *existing* `hasHydrated` gate, but the meaning changes from "hydrated once, ever" to "hydrated **for the current generation**": track `hydratedGeneration` (state) instead of a boolean, and compute `hasHydrated = hydratedGeneration === identity.generation`. This means every identity switch (sign-in, sign-out, switching accounts) makes each provider briefly show its existing fallback screen again until its own domain's namespace finishes loading, exactly reusing the pattern the umbrella note requires to "survive unchanged" — it's the same mechanism, just re-triggered instead of one-shot. This is a deliberate, conservative choice: it removes an entire class of races (a user action dispatched against the wrong namespace mid-switch) by construction, at the cost of a brief loading flash on every sign-in/out. Flag this to the user as the one product-visible side effect of this ticket; the alternative ("keep serving the old identity's already-loaded data until the new load resolves, swap atomically, never blank the screen") is technically defensible against the exit criteria's wording but reintroduces a write-race window addressed in point 4, needs an *additional* interim UI state most of the five providers don't have today, and is meaningfully more code across five call sites for a marginal UX gain during what should be a sub-100ms transition. Recommend keeping the gate; only revisit if the flash is visibly janky once built.
3. **Single shared `createWriteQueue` per domain remains correct — do not fork it per identity.** Ordering guarantees only need to hold *within* an identity's own write history; a queue item that was enqueued under a since-superseded generation should simply no-op instead of writing to the new namespace. Concretely: capture `identityContext.getGeneration()` synchronously inside the write-triggering effect (not inside the queued async closure), tag the queued value with it, and inside the function passed to `createWriteQueue`, check `identityContext.isCurrentGeneration(taggedGeneration)` **immediately before** calling `scopedStorage.setItem` and bail out (no-op) if it's stale. Because `createScopedKeyValueStorage.setItem` resolves `physicalKey(context.getIdentity(), key)` synchronously the instant it's called (no `await` before that resolution), checking-then-immediately-calling in the same synchronous block closes the race where identity flips between "the write was queued" and "the write actually executes" (queue items can wait an arbitrary amount of time behind older items or slow AsyncStorage I/O).
4. **Hydration reads use the *ambient* fresh-reading scoped storage as-is (no extra binding needed) — protection is on the apply side, not the read side.** `storage.getItem(key)` inside each `loadX` resolves the physical key synchronously the moment `loadX` is invoked (checked: e.g. `loadUserProfile`'s first line is `await storage.getItem(...)`), so a load kicked off for generation G always reads generation G's physical key regardless of how long the underlying AsyncStorage promise takes to resolve. The actual risk the exit criteria call out ("a deliberately delayed user-A load cannot commit after user B becomes current") is entirely about *applying* a late result, which is what `withGenerationGuard` is for: capture `generation` before calling `loadX`, and only `dispatch({type:'xRestored', ...})` + advance `hydratedGeneration` if `context.isCurrentGeneration(capturedGeneration)` still holds when the promise resolves.
5. **Guest legacy-key fallback**, new function `createGuestMigratingStorage(base, context)` in `src/shared/persistence/scoped-storage.ts`: wraps `createScopedKeyValueStorage`. On `getItem`, if the scoped (namespaced) read returns `null` **and** the current identity is `guest`, fall back to `base.getItem(key)` (the bare pre-T156 logical key) and, if that hits, write it through to the new namespaced key via `scoped.setItem(key, legacyValue)` before returning it — so every subsequent read/write for that guest uses the namespaced key and the fallback path is only ever exercised once per domain per device. Do not delete the old bare key (out of scope, no correctness benefit, and matches the project's existing "accepted prototype cleanup, not forensic erasure" stance elsewhere). `user:<uuid>` identities skip the fallback entirely — there is no legacy data to reconcile there. All five domain providers build their storage via this wrapper, not the bare `createScopedKeyValueStorage`, so the migration is uniform.

## Implementation order (schema/primitives before UI wiring, since providers depend on both)

1. **`src/shared/persistence/scoped-storage.ts`**: add `createGuestMigratingStorage`. Add/extend `scoped-storage.test.ts` for: scoped hit skips legacy read; scoped miss + guest identity + legacy hit returns legacy value and write-throughs it to the namespaced key (assert both the returned value and the resulting physical keys in the fake store); scoped miss + guest identity + legacy miss returns `null`; scoped miss + **non-guest** identity never touches the legacy/bare key at all (assert the fake base store's `getItem` wasn't called with the bare key).
2. **`src/shared/persistence/identity-provider.tsx`** (new): `IdentityProvider` + `useIdentityHandle()` as described in Design Decision 1. Keep it dependency-free of any of the five domains — it only knows about Auth and `identity-context.ts`. Add `identity-provider.test.tsx`: renders `<AuthProvider><IdentityProvider><Harness/></IdentityProvider></AuthProvider>` using the same fake-Supabase-client mocking pattern as `auth-provider.test.tsx`; assert (a) children are gated behind a fallback while `'initializing'`, (b) `identity`/`generation` update together exactly once per real identity change (not on every Auth event — e.g. two consecutive `TOKEN_REFRESHED` events for the same user must not bump generation, mirroring `identitiesEqual`), (c) signing in as user A then user B produces two distinct, increasing generations.
3. **`src/shared/persistence/use-identity-scoped-domain.ts`** (new, generic hook): extract the shared mechanics used by all five providers so there is exactly one implementation of the hydration/generation/write-queue dance, not five hand-copies that can drift. Signature roughly:
   ```ts
   function useIdentityScopedDomain<State, Action>(options: {
     reducer: (state: State, action: Action) => State;
     initialState: State;
     load: (storage: KeyValueStorage) => Promise<PersistenceLoadResult<State>>;
     save: (storage: KeyValueStorage, value: State) => Promise<PersistenceSaveResult>;
     createRestoreAction: (value: State) => Action;
     onRecovered?: (error: unknown) => void;
     onSaveFailed?: (error: unknown) => void;
   }): { state: State; dispatch: Dispatch<Action>; hasHydrated: boolean }
   ```
   Internally: reads `useIdentityHandle()`; stabilizes `options` via a ref (it's a fresh object literal every render) so effects don't re-fire spuriously; `useReducer`; `hydratedGeneration` state (`undefined` initially); a `shouldSkipNextWrite` ref (starts `true`, matching today's semantics for the very first hydration); one effect keyed on `identity.generation` doing the guarded load exactly per Design Decision 4, setting `shouldSkipNextWrite.current = true` synchronously before dispatching the restored value; one effect keyed on `[state, identity.generation, hydratedGeneration]` doing the tagged-write per Design Decision 3, but only once `hydratedGeneration === identity.generation` (i.e., don't attempt to persist a domain that hasn't finished its own hydration for the current identity yet — this is the direct generalization of "skip the first write" and also prevents writing during the gated loading window). Storage is built once per effect run via `createGuestMigratingStorage(AsyncStorage, context)`.
   Add a standalone `use-identity-scoped-domain.test.tsx` using a tiny fake reducer/domain (not one of the five real ones) to prove the mechanics in isolation before wiring five real providers on top: initial hydration skips the first write; a second hydration (identity switch) skips exactly the write immediately following it, not later user-driven writes; a stale (superseded-generation) load never dispatches; a stale (superseded-generation) queued write never calls the underlying storage's `setItem`; writes stay ordered when several are queued back-to-back before any resolve.
4. **Wire the five real providers onto the hook**, one at a time, smallest/most isolated first: `practice-history-provider.tsx`, `note-provider.tsx`, `custom-trick-provider.tsx`, `goal-provider.tsx` (keep its `useUserProfileActions()` cross-domain call untouched — it still works once nested inside a hydrated `UserProfileProvider`), `user-profile-provider.tsx` last since `GoalProvider`'s test harness depends on it and you'll want its behavior to be maximally stable before touching it. For each: replace the local `useReducer`/`hasHydrated`/`shouldSkipInitialWrite`/`createWriteQueue`/two-`useEffect` block with a call to `useIdentityScopedDomain`, keep every action creator (`dispatch({...})` call sites) unchanged, keep the existing hydration-fallback JSX unchanged (just driven by the hook's `hasHydrated`). Do **not** change reducer state shapes, action types, or the public `useX`/`useXActions` hooks' external contracts — this ticket is provider orchestration only, per the task notes.
5. **`src/app/app/_layout.tsx`**: wrap the existing five-provider nest in `<IdentityProvider>` as the new outermost element (still inside root `_layout.tsx`'s `<AuthProvider>`, since `AppShellLayout` renders under root's `<Slot/>` which is inside `AuthProvider`). ## Risk callouts for the implementer

- The `hydratedGeneration` re-gating (Design Decision 2) means every one of the five providers' existing hydration-fallback screens will now flash briefly on sign-in/out, not just at cold boot. This is a deliberate, conservative call — confirm it doesn't read as a regression before shipping; it's the cheapest way to close the mid-switch write race described in Design Decision 3/4's discussion.
- Effect ordering during the very first mount when Auth resolves directly to `'authenticated'` (returning user, no visible `'guest'` interim): a domain's first hydration effect can fire once against the still-default guest generation before `IdentityProvider`'s own correction effect bumps the generation to the real user identity, because passive effects run children-before-parent within a commit. This is harmless and self-heals via the generation guard (the stale guest-generation load is discarded, `hasHydrated` stays false until the real user-generation load lands), but don't be surprised if tests observe a discarded guest read at boot for an authenticated session — that's expected, not a bug.
- Do not let `GoalProvider`'s existing `useUserProfileActions()` dependency break: it must still be textually nested inside a hydrated `UserProfileProvider`, and `UserProfileProvider` is being wired onto the shared hook in the same pass — sequence step 4's provider order (goal after user-profile) avoids finding this out late.
- Keep `Date.now()`/timer/generation-capture reads out of the reducers themselves, consistent with the Sesh reducer convention noted in AGENTS.md, even though these five reducers aren't Sesh's — the same "no ambient time/identity reads inside pure reducers" discipline applies to any new `xRestored` handling.
- This ticket explicitly does not need to add per-identity separation to `createWriteQueue` itself (see Design Decision 3) — resist the temptation to build one; it adds complexity the generation tag already makes unnecessary.
- Do not add migration/versioning infrastructure for the custom-trick document (still v1, still provisional) — the guest legacy-key fallback in this ticket is about the *storage key namespace*, not the document schema, and must not be conflated with a v2 document.
