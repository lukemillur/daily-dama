## Design decision: canonical visual treatment

Adopt PasswordInput's existing row-based shape as the one canonical shape, rather than the
bare-bordered-TextInput shape used by the four plain fields. Concretely: the border,
background, and border-radius live on a row container; the TextInput inside is transparent,
borderless, and flex 1; an optional trailing accessory (only used by PasswordInput's show/hide
toggle) sits in the same row, inside the same border. This is a deliberate visual change for
the four plain-FieldInput fields (previously bordered directly on the input) and is exactly
what "one consistent, polished visual style" in the exit criteria calls for -- it also means
adding a right-aligned accessory in the future (e.g. a clear button) doesn't require a
different structural pattern than password fields already use.

Additional polish, addressing the Notes' explicit call to pick a border/focus/spacing
treatment:
- Border radius: Radii.control (4px) on the row, matching Button's own border radius -- this
  was previously 0 on every field. Low-risk visual nicety, ties inputs to the same "control"
  language as buttons.
- Focus state: track focus locally (onFocus/onBlur, composed with any caller-supplied
  handlers) and switch the row's border color from theme.text to theme.accent while focused.
  No field has any focus treatment today. Also set outlineStyle: 'none' on the TextInput's
  style (a valid RN style prop that react-native-web maps to CSS outline-style: none) so the
  new themed border is the only focus indicator on web, rather than stacking with the browser's
  default blue focus ring.
- Spacing: standardize the field's own top margin to Spacing.four (24px) from
  @/constants/theme, replacing the two different ad hoc values in use today (28px in four
  files, 22px in account-security-screen.tsx). This uses the app's existing spacing scale
  instead of an arbitrary number.
- Field-level error text: always AppColors.red, 12px/800, margin-top 7px -- matching the
  majority existing convention and fixing account-security-screen.tsx's one outlier
  (theme.text) rather than preserving it as a second "valid" variant.

## Step 1 -- src/components/ui/text-field.tsx (new shared primitive)

Write this first; every other step depends on it existing. Structure and props (pseudo-code,
not a literal diff to paste unmodified -- match this repo's existing formatting/quote
conventions and verify styled-components' typing accepts styled(TextInput) with an added
generic prop object the same way button.tsx does for ButtonRoot/ButtonLabel):

Props: TextFieldProps extends ComponentProps of TextInput, plus required "label: string" and
optional "error?: string", "hint?: ReactNode", "rightAccessory?: ReactNode".

Component: forwardRef to TextInput. Destructure label, error, hint, rightAccessory,
"accessibilityLabel = label" (default), onFocus, onBlur, and spread the rest of the native
TextInput props through. Track local focus state via useState, wrapping onFocus/onBlur so any
caller-supplied handlers still fire. Render order: Field (View, margin-top Spacing.four) then
FieldLabel (Text) then FieldHint if present then InputRow (View: min-height 56, flex-direction
row, align-items center, background theme.background, border 2px solid -- theme.accent while
focused else theme.text, border-radius Radii.control) containing the underlying TextInput
(flex 1, color theme.text, font-size 18, font-weight 800, padding 12px 14px when no accessory
or 12px 0 12px 14px when an accessory is present, outline-style none, placeholderTextColor
theme.textMuted via .attrs) followed by rightAccessory if present, then ErrorText if error is
present (AppColors.red, 12px/800, margin-top 7px).

Notes:
- FieldHint is a straight lift of password-input.tsx's existing one; keep both call sites'
  visual output identical.
- The accessory-present flag only changes the input's right padding (so the trailing icon's own
  padding provides the visual gap, matching what password-input.tsx does today).
- Do not forget ref forwarding all the way to the underlying host TextInput node (needed by
  sign-up-screen.tsx's passwordInputRef.current?.focus() and
  confirmPasswordInputRef.current?.focus() patterns, once PasswordInput is rebuilt on top of

## Risks / non-obvious things to watch

- Do not accidentally change validation/error logic -- only the rendering of error text changes
  shape (color/position now owned by TextField), never which conditions set an error string.
  Diff each screen file narrowly around the swapped block to confirm no validation call or
  state read moved.
- account-security-screen.tsx's error-text color change (theme.text to AppColors.red for the
  "New email" field only) is an intentional part of "one consistent... visual style," not an
  accidental regression -- call this out in the PR description so a reviewer doesn't mistake it
  for scope creep, since it's the one place where the diff isn't a pure structural swap.
- outline-style none on web: verify in-browser that keyboard-only users still get a visible
  focus indicator (the themed border-color swap) since the native browser outline is being
  suppressed in favor of it -- don't ship a focus state that's invisible against theme.background
  when theme.accent happens to be close in value to it for some resolved theme (check at least
  the default/fixed palette in-browser; per-user custom accent colors are a pre-existing
  personalization feature, not something this task needs to newly validate exhaustively).
- styled(TextInput) typing with an added generic prop for the accessory-present flag should
  follow the same pattern button.tsx already uses for ButtonRoot/ButtonLabel -- if TypeScript
  complains about prop leakage onto the DOM/native node, check how button.tsx avoids that first
  rather than introducing a new workaround.
- Keep the write ordering of steps: Step 1 (component) must land before Step 2 (PasswordInput),
  and Step 2 should be verified in isolation (its test file already expects the row-based
  shape) before touching the five other call sites in Steps 3-6, so any structural mistake in
  TextField is caught against the one test file least likely to need edits, rather than
  discovered only after all six call sites have moved.
