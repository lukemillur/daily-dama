## Key finding: notes share goals' exact tombstone mechanics — same 23514 ambiguity, same fix needed

`api.notes` uses the **same shared trigger function**
(`private.enforce_goal_note_mutation_invariants`,
`supabase/migrations/20260822201500_add_goals_and_notes.sql`) as
`api.goals`, attached via `notes_enforce_mutation_invariants`. It has:
- No DELETE grant — a local `noteDeleted` outbox operation must push as
  `.update({ deleted_at: <iso> })`, revision-guarded exactly like an edit.
- The same terminal-tombstone rule: any further UPDATE against an
  already-tombstoned row (another delete, an edit, an attempted undelete) is
  unconditionally rejected with `raise exception ... using errcode = '23514'`
  and the **same fixed message text**, `'cannot modify a tombstoned % row'`
  (the function is genuinely shared, not just structurally similar — it's
  literally the same `TG_TABLE_NAME`-parameterized function for both
  tables). This is already pgTAP-tested for notes too in
  `supabase/tests/t155_4_goals_and_notes.test.sql`.
- The same `23514`-vs-`PGRST116`-vs-genuine-CHECK-violation ambiguity
  `goal-sync-transport.ts`'s `classifyGoalUpdateFailure` resolves. **Do not
  change the trigger.** Build `classifyNoteUpdateFailure` in
  `note-sync-transport.ts` following `classifyGoalUpdateFailure` almost
  verbatim (see "The adapter" below) — same six-way branch, same
  delete-succeeds/edit-conflicts split on a tombstoned row.

The one structural difference from goals: notes' UPDATE-grantable column is
`body` only (a single scalar), vs. goals' `target_count`/`target_ms` pair —
simpler, not more complex. `trick_id`/`trick_name`/`practice_session_id` are
insert-only (matches the insert grant at
`grant insert (user_id, id, trick_id, trick_name, body,
practice_session_id) on api.notes`) and are never part of an edit's patch.

## Note-specific consideration: optional practice-session association

`api.notes.practice_session_id` has a real FK to `api.practice_sessions`
(`on delete set null`). T155.13's `mapNoteToInsertInput` already passes it
through as shape-only (`note.practiceSessionId ?? null`), leaving
referential integrity to the server FK — this sync layer does not need to
resolve or join the actual session, just carry the string through
push/pull/diff untouched, same as `trick_id`/`trick_name` are carried as
authoritative name snapshots (never re-resolved from a live trick, per
AGENTS.md). No special handling needed beyond what `mapNoteToInsertInput`
and `mapNoteRowToDomainEntry` (both T155.13, already merged) already do —
confirm the diff function and adapter don't accidentally strip or
re-validate it beyond the existing shape check.

## The adapter: `note-sync-transport.ts`

New file `src/features/notes/persistence/note-sync-transport.ts`, built
exactly like `goal-sync-transport.ts` —
`createNoteSyncTransportAdapter(client: SupabaseClient<Database, 'api'>, userId: string): SyncTransportRepository<NoteRow>`.
One table, no `recordId === userId` routing.

**Pull** — delegate to `createNoteCloudRepository(client).list(request)`,
same one-line wrapper. Pulls tombstoned rows too; the driver's
pull-composition filters them.

**Push** — routes on `request.operationType`:
- `'delete'`: build `{ deleted_at: <iso> }` directly (not via
  `prepareNoteDeletionPatch`, same "attempt directly, fetch-to-disambiguate
  only after a failure" style as goals). `expectedRevision === null` →
  unconditional `.update(...).eq('user_id',...).eq('id',...)`; 0 rows →
  succeeded with a fabricated placeholder row (add
  `fabricateDeletedNoteRow`, same pattern as `fabricateDeletedGoalRow` but
  with note-shaped columns — `trick_id`/`trick_name`/`body` placeholder
  strings, `practice_session_id: null`). `expectedRevision !== null` → add
  `.eq('revision', expectedRevision)`; on failure run
  `classifyNoteUpdateFailure`.
- `'upsert'` (create-or-edit): defensively re-validate `request.payload`
  first — `validateNoteUpsertPayload(payload, userId, noteId)` mirroring
  `validateGoalUpsertPayload`'s style: check `user_id`/`id` match,
  `trick_id`/`trick_name`/`body` are non-blank normalized text (reuse
  `isNormalizedText` from `note-persistence.ts`), `practice_session_id` is
  `null` or non-blank text. `expectedRevision === null`: `.insert(input)`;
  on `23505` (lost-ack retry), fall back to a blind
  `.update({ body: input.body }).eq('user_id',...).eq('id',...)` (no
  revision filter, matches precedent), run through
  `classifyNoteUpdateFailure` on failure too. `expectedRevision !== null`:
  `.update({ body: input.body }).eq(...).eq('revision', expectedRevision)`;
  on failure, `classifyNoteUpdateFailure`.

`classifyNoteUpdateFailure(error, refetch, operationType, request, userId,
noteId)` — copy `classifyGoalUpdateFailure` near-verbatim: same
`PGRST116`/tombstone-message/genuine-CHECK-violation three-way split, same
delete-succeeds/edit(upsert)-conflicts rule on a tombstoned row, same
found-live-different-revision → conflict for both branches.

**Real-stack tests**: new file
`supabase/tests/data-api/t157_8_note_sync_transport.test.mjs`, built like
`t157_7_goal_sync_transport.test.mjs`. Cover the same seven cases from that
file's precedent, substituting notes' shape:
1. Idempotent retry of a first-ever note create (lost ack, `23505` fallback
   path).
2. Idempotent retry of a note delete (push twice, both succeed).
3. Delete of a note never created server-side succeeds as a no-op with a
   fabricated row.
4. Revision-guarded edit (body change) with a stale `expectedRevision` →
   `'conflict'` with correct `serverRevision`; body untouched server-side.
5. Tombstone a note directly via the plain repository, then push a
   `delete` operation at the tombstone's own current revision →
   `'succeeded'` (idempotent).
6. Same tombstone setup, push an `upsert` (edit) at the tombstone's own
   current revision → `'conflict'`, not `'failed'`, not a thrown exception.
7. Basic `pull` smoke test against seeded active + tombstoned rows,
   confirming tombstoned rows come back.
8. **Note-specific addition**: create a note with a valid
   `practice_session_id` referencing a real seeded practice session for the
   same user, push/pull it, confirm the association round-trips through the
   adapter unchanged (proves the FK-backed optional association survives
   sync, not just shape-validated locally).

## Risks / non-obvious things to flag to the implementer

- The biggest risk here is the opposite of T157.7's: **over-building**.
  There is no local-editing gap to fill, no migration to write, and Sesh's
  interaction with notes is display-only, not bookkeeping — resist the urge
  to copy T157.7's *heavier* mechanics (extra migration step, two-assertion
  isolation test) where the lighter T157.4/T157.5 precedent already
  applies. Read this plan's explicit call-outs above before assuming
  parity with every T157.7 step.
- The tombstone-`23514` disambiguation is still real work, not boilerplate
  — it is the one piece of genuine complexity this task inherits from
  goals (via the literally-shared trigger function), and it must not be
  skipped or hand-waved as "goals already solved this." Build
  `classifyNoteUpdateFailure` as its own real implementation in
  `note-sync-transport.ts`, not a re-export of goals' version (the row
  shapes differ — `NoteRow` vs `GoalRow` — so it cannot be literally
  shared without an awkward generic; a parallel, colocated copy matches
  every other domain's precedent of keeping this table-specific logic in
  its own transport file).
- Do not touch `private.enforce_goal_note_mutation_invariants` or its error
  code/message — it is shared with goals and already pgTAP-tested for both
  tables; any change here has blast radius into T155.4/T155.6/T157.7.
- Keep `Date.now()`/`Math.random()` out of `noteSyncEnvelopeReducer` and out
  of `note-sync-transport.ts`'s pure classification helper — generate
  timestamps in the driver hook's effect body / the caller of the adapter,
  passed through, same convention as every other domain.
- The cross-domain-independence test (goals unaffected by a notes conflict)
  is expected to pass without any implementation change, given each domain
  already owns fully independent state. If it doesn't, stop and report
  rather than adding cross-domain coupling to make it pass — that would be
  exactly the kind of architecture change AGENTS.md's domain-boundary rule
  guards against.
