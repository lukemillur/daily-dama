# T160.2 — Add per-record conflict resolution

## Iteration boundary

Good enough for this iteration is a web Profile flow that durably shows every
unresolved stale-revision conflict, presents typed local/server snapshots for
profile data, custom tricks, goals, and notes, and lets the user explicitly
keep either side. Keeping local data must enqueue a fresh revision-guarded
operation; keeping server data must adopt the server snapshot and retire only
that conflict. Practice-session conflicts are not user-choice conflicts:
same deterministic session identity and payload are deduplicated/acknowledged
according to the existing insert-only identity rule. No last-write-wins
fallback, Realtime, mobile hardening, or guest-import conflict UI is part of
this ticket.

## Current contracts and constraints

- `SyncCoordinatorProvider` already aggregates five independent domain sync
  handles and T160.1 exposes conflict counts through `SyncStatusSection`.
- Each domain has a separate `SyncEnvelope` persisted through
  `useIdentityScopedDomain`; the envelope currently stores local state, an
  outbox, a revision cache, and cursor, while a conflict is represented only
  by `lastFailureKind: 'conflict'` on an outbox operation.
- `pushOutboxOperations` deliberately continues after conflicts and the five
  domain drivers already leave conflicted operations pending. Preserve that
  behavior so resolving one record cannot block unrelated outbox work.
- Profile includes both the profile row and user trick-state rows; their
  existing mappings/revision caches must remain authoritative rather than
  being flattened into an untyped UI object.
- Goals and notes carry full tombstone entries in their cloud mappings. A
  server-deleted record therefore needs a typed comparison state, not an
  absent-row special case.
- Practice history is immutable and insert-only. Its existing deterministic
  `createPracticeSessionRecordId` identity and reducer deduplication remain
  the resolution rule; it should not appear as a keep-local/keep-server
  choice.

## Ordered implementation plan

1. **Define the serializable conflict contract.** Add a shared conflict model
   under `src/shared/sync/` with a discriminated resource/domain kind and
   explicit local and server representations, operation identity, record
   identity, expected/server revisions, operation type, and enough typed
   metadata to render deletes/tombstones. Keep the shared envelope layer
   generic: domain-specific payload validation and row-to-domain conversion
   stay in each feature mapping module. Add runtime validation and round-trip
   tests for malformed, cross-domain, stale-revision, upsert, and delete
   conflict records.

2. **Carry current server data through the transport boundary.** Extend the
   typed conflict result in `src/shared/sync/transport.ts` and each T157.4–T157.8
   transport adapter so a conflict includes the validated/current server row
   (or an explicit typed tombstone) in addition to revision metadata. Preserve
   the existing repository contracts and operation-id retry semantics. Add
   transport tests proving conflict responses contain comparable server data
   while successful and immutable-session duplicate paths remain unchanged.

3. **Persist conflicts in each domain envelope.** Extend
   `src/shared/sync/sync-envelope.ts` with a serializable conflict collection
   and reducer operations for recording, replacing/requeuing, adopting the
   server side, and removing one resolved conflict. Keep the collection
   identity-scoped, validate it during envelope load, and retain unresolved
   entries across reload. Do not clear all conflicts as a side effect of
   acknowledging an unrelated operation. Add shared reducer/persistence tests
   for identity guards, one-item removal, reload recovery, and preservation of
   sibling outbox operations.

4. **Make domain sync drivers produce typed records and resolve them.** Update
   `use-profile-domain-sync.ts`, `use-custom-trick-domain-sync.ts`,
   `use-goal-domain-sync.ts`, and `use-note-domain-sync.ts` to map conflict
   payloads through their existing cloud mapping validators, record a typed
   conflict in the envelope, and expose `conflicts` plus a narrowly typed
   `resolveConflict` command. A local choice must create a new operation ID,
   use the returned server revision as its expected revision, preserve the
   primary reducer’s local value, and remain pending until acknowledged. A
   server choice must dispatch the existing domain restore/update/delete
   action, update the revision cache, acknowledge only the conflicted
   operation, and remove only that conflict. Guard every command by identity,
   generation, operation ID, and record ID so stale UI actions are no-ops.
   Keep `lastFailureKind`/counts accurate and leave retryable failures and
   unrelated conflicts untouched.

5. **Handle profile and immutable-session edge cases explicitly.** For the
   profile domain, model scalar-profile and trick-state conflicts with their
   existing typed row/domain shapes and ensure server adoption cannot create a
   feedback outbox mutation. For practice history, update the T157.6 driver
   and transport tests so an identical deterministic session identity/payload
   is treated as an idempotent duplicate, while a genuinely unexpected stale
   result cannot become a user-selectable conflict. This keeps Stats derived
   from immutable history and avoids inventing a merge policy for sessions.

6. **Expose the Profile conflict route and interaction.** Add
   `src/app/app/profile/sync-conflicts.tsx` under the existing Profile Stack
   and a typed presentational component in
   `src/features/profile/components/` (with a corresponding test). Render
   grouped or clearly labeled comparisons for profile, custom trick, goal,
   and note conflicts, including delete/tombstone states and field-level
   values where practical. Provide explicit “Keep on this device” and “Keep
   on server” actions, accessible labels/selection feedback, a no-conflicts
   state, and stable ordering by domain/record identity. Link the existing
   sync-status conflict affordance to this route without changing the five-tab
   navigation layout or restoring the trick directory to Profile.

7. **Wire provider APIs and route-level state.** Extend the five sync context
   interfaces and `SyncCoordinatorProvider` with a read-only aggregate conflict
   list and per-record resolution dispatch, or provide a feature-level hook
   that composes the domain handles while preserving domain ownership. Prefer
   stable conflict view models over exposing raw `Record<string, unknown>` to
   UI code. Ensure hydration gates the route until all relevant envelopes are
   ready and identity changes clear the prior account’s visible conflicts.

8. **Add focused tests for the ticket’s exit criteria.** Add/update:

   - shared conflict model/envelope tests for runtime validation, persistence,
     identity/generation guards, and one-at-a-time removal;
   - profile, custom-trick, goal, and note domain-driver tests covering typed
     local/server comparisons, both resolution directions, fresh revision-aware
     operation IDs, tombstone adoption, and feedback-loop suppression;
   - practice-history tests covering deterministic duplicate identity and no
     user conflict choice;
   - a Profile conflict component test covering representative records for
     every mutable resource, both buttons, no-conflicts, and route navigation;
   - a fully wired route/provider test that seeds multiple conflicts plus an
     unrelated pending outbox operation, reloads the identity-scoped storage,
     proves unresolved conflicts return, resolves one item, and proves only
     that item disappears while the sibling operation/conflict continues.

9. **Verify and document the handoff.** Run the exact affected Jest suites,
   `yarn eslint` on changed TypeScript files, and `yarn tsc --noEmit`. Because
   this changes Expo Router files and provider wiring, run the web export:
   `yarn expo export --platform web --output-dir /tmp/daily-dama-web-export`.
   If the implementation changes shared persistence or cross-domain
   coordinator behavior materially, escalate to
   `node .claude/scripts/verify.mjs`. Do not launch iOS/Android tooling;
   native validation remains deferred by the project handoff.

## Risks and decisions to preserve

- The largest risk is accidentally making a generic conflict model depend on
  Supabase row types. Keep the shared layer serializable and use per-domain
  codecs/mappers at the boundary.
- A resolution must not reuse the stale operation ID: the server may already
  have accepted that idempotency key even if the client lost its response.
  Generate a new operation ID and guard it with the server revision.
- “Keep server” is a local adoption of already-authoritative server state,
  not a new server write; it must update local revision bookkeeping and avoid
  immediately re-enqueueing the adopted snapshot.
- Do not use current trick names to render stored sequence steps or history;
  existing snapshot invariants apply to conflict comparisons too.
- Do not offer a global “resolve all,” automatic newest-timestamp choice, or
  silent conflict discard. Those would violate the task’s explicit no-LWW
  requirement and make per-record recovery unverifiable.
