# T186.1 — Auto-trigger guest-to-account import and skip repeat onboarding

## Confirmed starting state

- `src/features/guest-import/` is untouched by T187.1/T187.2 (`git log -- src/features/guest-import` shows only T159.x commits). T187.1 added `updatedAt` to profile/custom-trick/goal records; T187.2 replaced the *general* sync-coordinator's manual per-record conflict UI with automatic most-recent-wins resolution and deleted `src/app/app/profile/sync-conflicts.tsx`. That is a **separate** conflict system from guest-import's own `GuestImportConflict`/`conflictResolved`/`chooseProfile`/`resolveConflict` machinery in `src/features/guest-import/persistence/guest-import-existing-account.ts` (`planExistingAccountMerge`), which still manually diffs guest vs. cloud records and still populates `state.conflicts` for a same-ID differing record during an *existing-account* merge. That machinery is real, still reachable, and untouched by this ticket — see the scope decision below.
- Reducer: `src/features/guest-import/model/guest-import.ts`. Driver hook: `src/features/guest-import/state/use-guest-import.ts`. Presentational: `src/features/guest-import/components/guest-import-preview.tsx`, rendered only from `src/app/app/profile/index.tsx` (`<GuestImportPreview />`, no other caller).
- `cancelImport` (hook) / `cancelPressed` (reducer) is currently reachable only via `GuestImportPreview`'s "Not now" button.
- `src/app/app/home.tsx`'s gate is `profile.hasCompletedOnboarding && profile.kenteiRank ? <DailyHome/> : <KenteiOnboarding/>`, with no awareness of identity or guest-import state at all today.
- `useGuestImport()` is safe to call unconditionally regardless of identity: every internal effect guards on `identity.kind !== 'user'`, and `useIdentityHandle()` falls back to a permanent guest `DEFAULT_HANDLE` when not wrapped in `<IdentityProvider>` (`src/shared/persistence/identity-provider.tsx:81-83`), so calling the hook from `home.tsx` cannot regress guest (never-signed-in) usage.

## Key design decision: what "no local data" does at `awaitingConfirmation`

The reducer has no auto-transition out of `awaitingConfirmation` other than `confirmPressed`/`cancelPressed`. This ticket only asks to auto-confirm "as soon as `awaitingConfirmation` is reached with any local data present." Read literally, if every domain's local count is zero, nothing dispatches and the record parks in `awaitingConfirmation` forever — which is **exactly today's behavior** (`GuestImportPreview` already renders `null` and does nothing in that case; see its existing "renders nothing... when every domain has zero local count" test). Do not invent new auto-cancel semantics for the empty case; that's unrequested reducer-behavior expansion. Instead, make `home.tsx`'s gate treat "`awaitingConfirmation` with an all-zero inventory" as *resolved* (not blocking), so the permanent parked state never wedges the UI. This is the load-bearing reason the gate predicate must inspect `state.inventory`, not just `state.status`.

## Scope decision: `GuestImportPreview`'s rendering

The task says "delete `GuestImportPreview`'s user-visible rendering." Taken as a blanket deletion of the whole component, this would also delete the only working UI for `awaitingProfileChoice`/`conflicts` — a still-reachable flow (existing-account merge with a same-ID differing record) that this ticket's Notes explicitly says doesn't need to be *resolved* by this ticket, but doesn't say may be *broken*. Deleting it would silently strand a second-device/existing-account sign-in with real data in an unresolvable state.

Plan: delete only the pieces whose purpose is the manual confirm/"Not now" decision this ticket eliminates — the `awaitingConfirmation` branch (per-domain count preview + Import/Not-now buttons) and the `inventorying` "Checking..." branch (also just transient/no-decision UI, and momentary now that confirmation is automatic). **Keep** the `uploading`/`awaitingProfileChoice`/`conflicts` branches exactly as they are — they're a different, still-required decision (profile/record conflict resolution), not the one this ticket removes. If Luke intended a literal full deletion instead, that's a one-line follow-up (delete the remaining branches + file), but implementing it as full deletion now would silently break a live flow, so don't do it without confirming first.

## Steps

1. **`src/features/guest-import/model/guest-import.ts`** (pure, no React — do this first since both the hook and `home.tsx` depend on it):
   - Add `export function hasAnyLocalGuestData(inventory: GuestImportDomainCounts): boolean` — `SYNC_DOMAINS.some((domain) => inventory[domain].local > 0)`. This centralizes the count check currently duplicated ad hoc inside `GuestImportPreview` (`domainsWithLocalData`).
   - Add `export function isGuestImportPendingResolution(state: GuestImportState): boolean` — the predicate `home.tsx` needs:
     - `true` for `'inventorying' | 'uploading' | 'awaitingProfileChoice' | 'conflicts'`.
     - for `'awaitingConfirmation'`: `state.inventory !== undefined && hasAnyLocalGuestData(state.inventory)`.
     - `false` for everything else (`'idle' | 'completed' | 'cancelled'`, and the empty-inventory `awaitingConfirmation` case).
   - Add reducer-adjacent unit tests for both functions in `guest-import.test.ts` (not required by the exit criteria, but they're cheap, pure, and directly gate the home.tsx behavior the exit criteria does require — cover: nonzero domain, all-zero, `awaitingConfirmation` with `inventory: undefined`, and each of the four other blocking statuses).

2. **`src/features/guest-import/state/use-guest-import.ts`**:
   - Add a new effect, modeled on the existing `inventoryStartedRef`/`importStartedRef` "once per importId" guard pattern: when `hasHydrated && identity.kind === 'user' && state.status === 'awaitingConfirmation' && state.importId !== undefined && state.inventory !== undefined` and this `importId` hasn't already been decided, mark it decided and, if `hasAnyLocalGuestData(state.inventory)`, `dispatch({ type: 'confirmPressed', importId, now: Date.now() })`. If there's no local data, do nothing (see design decision above — leave it parked; `home.tsx` is what stops treating it as blocking).
   - This effect must fire identically whether `awaitingConfirmation` was just reached via `inventoryCompleted` or restored on remount via `stateRestored`/hydration (both just flip `state.status`), so drive it off `state.status`/`state.importId`/`state.inventory`, not off which action produced them — this naturally makes a resumed `awaitingConfirmation` with local data continue automatically too, which is desired (no scenario should require a manual action).
   - Remove `cancelImport` from `UseGuestImportResult` and from the hook's return value. Do **not** touch the reducer's `cancelPressed` case or its model-level tests (`guest-import.test.ts`) — leave it fully implemented/tested per the file's own existing precedent for `resumeRequested` ("stays fully implemented and unit-tested... for a future caller"). Update the top-of-file doc comment block if it becomes misleading once `cancelImport` is removed (it currently only discusses `resumeRequested`, so likely no change needed — just confirm it doesn't reference `cancelImport`).
   - `confirmImport` itself can stay (it's now merely redundant once auto-fired — the reducer guard makes a second `confirmPressed` a no-op — and keeping it costs nothing; only `cancelImport` has zero remaining callers).

## Order rationale
