You are given one task entry from `TASKS.md`, the path to a plan already committed for it at `.claude/plans/<ID>.md` on this branch (the planner commits and pushes it before handing off), and the name of the `task/T0NN-*` branch already claimed for this task.

You're running in an isolated git worktree created fresh for this call — the branch is not checked out for you. Before anything else: `git fetch origin <branch>` then check it out. Then read the plan from `.claude/plans/<ID>.md` on that branch — it's the source of truth for this run, not a fallback. Only if the prompt tells you the file doesn't exist (the planner's commit/push failed) should you work from plan text pasted directly into the prompt instead.

## What to do

1. Follow the plan. If it turns out to be wrong once you're actually in the code, deviate — but note why in your final summary rather than silently doing something else.
2. Verify the task's own exit criteria yourself once the work is done — don't mark it done on assumption.
3. Run the project's standard verification sequence (`yarn test --runInBand`, `yarn lint`, `yarn tsc --noEmit`, and the web export check if relevant to the change — these are the same commands `AGENTS.md` documents, listed here so you don't need to open that file just to run them). The task isn't done if it breaks the baseline, even if its own criteria pass. Only read `AGENTS.md` itself if the plan or the code raises an architecture question these commands don't answer.
4. Commit the work on the current branch, referencing the task ID in the message. Move the task's entry from `TASKS.md`'s `Backlog` to `TASKS_DONE.md`, flipped to `Done`, in that same commit — per `TASKS.md` § Completing a task. If this task was the last `Not started`/`In progress` child of a parent umbrella entry (every sibling child is now `Done`), move the parent entry to `TASKS_DONE.md` too, flipped to `Done`, in the same commit. Check the parent's other children with a targeted `grep -n '^### \[<sibling-ID>\]'` against `TASKS_DONE.md` (and the `Status:` line just below each match) rather than reading the whole file — it's 100K+ chars and only grows, and a full read to check a couple of status lines wastes most of what it pulls in. Don't guess the outcome from memory either way. In that same commit, also delete `.claude/plans/<ID>.md` — its job (surviving an interruption before implementation started) is done once implementation is committed, and it shouldn't linger in the PR as a stale artifact.
5. Push the branch and open a PR into `development` (`gh pr create --base development`), with a summary that includes the task ID, the task's **Description** field verbatim from `TASKS.md`, and what changed.
6. Attempt exactly one plain squash-merge: `gh pr merge --squash --delete-branch`. No review gate, no waiting on CI — that much is pre-authorized for your own claimed branch per `AGENTS.md` § Git state expectations, same as step 5. If it succeeds, you're done here.

   If it's rejected for any reason — a failing required check, missing review, branch protection, a merge conflict, anything `gh pr merge` refuses — **stop. Do not retry with different flags, and never reach for `--admin`, `--force`, or any other bypass of branch protection.** That pre-authorization covers an ordinary squash-merge on your own branch; it does not extend to overriding whatever check or rule is stopping it, and forcing one through defeats the exact protection it's there to provide. Do not attempt to diagnose or fix the underlying cause either (e.g. broken CI config, a flaky test, an unrelated dependency issue) — that's outside this task's scope and belongs to a human or the orchestrating session to pick up separately. Leave the PR open and move straight to reporting.
7. Report back concisely: the task ID, the PR URL, and either confirmation the merge succeeded, or — if it was rejected — the exact rejection message `gh pr merge` gave verbatim, so the reason is unambiguous to whoever picks this up next. Add at most 1-2 lines on anything you deviated from in the plan. Don't restate implementation detail, verification output, or the reasoning behind decisions here — that record already lives durably in the `TASKS_DONE.md` commit itself (per its Notes field), and the orchestrator that reads this report only extracts the PR URL and status from it. A long report here is pure overhead.

If, once you're in the code, the task turns out bigger than scoped or depends on an undecided product call, stop — don't push a half-finished branch past that point. Follow `TASKS.md`'s own guidance instead: split it into new entries, or mark it `Blocked` with the specific open question, and report that back rather than guessing.
